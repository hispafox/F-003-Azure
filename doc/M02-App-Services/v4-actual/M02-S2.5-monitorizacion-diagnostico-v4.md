## Slide 2 — Por qué monitorizar
Una app en producción sin monitorización es como conducir de noche sin luces. Funciona — hasta que no funciona.

**Lo que necesitáis saber en todo momento:**
- ¿La app responde? ¿Con qué latencia?
- ¿Hay errores? ¿Cuántos? ¿De qué tipo?
- ¿Cuánta CPU y memoria consume?
- ¿Cuántas peticiones está atendiendo?
- ¿Las dependencias (DB, APIs externas) responden?

**La diferencia entre un equipo reactivo y uno proactivo:**
- Reactivo: un usuario reporta que la app va lenta → investigáis → encontráis el problema (horas después)
- Proactivo: una alerta os avisa que la latencia subió un 200% → investigáis → lo arregláis antes de que los usuarios lo noten

## Slide 4 — Métricas de App Service (built-in)

App Service genera métricas automáticamente sin configurar nada:

| Métrica | Qué mide | Threshold de alerta |
|---------|----------|---------------------|
| CPU Percentage | Uso de CPU del plan | > 80% → revisar |
| Memory Percentage | Uso de RAM del plan | > 85% → revisar |
| Http 2xx | Respuestas exitosas | Baseline normal |
| Http 4xx | Errores del cliente (bad request, not found) | Picos → posible ataque |
| Http 5xx | Errores del servidor (tu código falla) | > 0 sostenido → bug |
| Requests | Total de peticiones | Baseline de tráfico |
| Response Time | Tiempo medio de respuesta | > 2s → revisar |
| Data In / Data Out | Tráfico de red | Anomalías |
| Http Server Errors | Errores del servidor web | Debería ser 0 |

```bash
# Ver métricas desde CLI
az monitor metrics list \
  --resource "/subscriptions/<id>/resourceGroups/rg-prod/providers/Microsoft.Web/sites/app-ventas" \
  --metric "CpuPercentage" "MemoryPercentage" "Http5xx" "AverageResponseTime" \
  --interval PT1H \
  --output table
```

## Slide 6 — Health Check automático

Health Check hace que App Service verifique periódicamente si tu app está viva:

```bash
# Configurar health check
az webapp config set --name app-ventas -g rg-ventas-prod \
  --generic-configurations '{"healthCheckPath": "/health"}'
```

**Cómo funciona:**
1. App Service envía GET a `/health` cada 30 segundos
2. Si responde 200-299: instancia sana
3. Si falla 5 veces seguidas (2.5 minutos): instancia marcada como no sana
4. El load balancer deja de enviar tráfico a esa instancia
5. Si sigue fallando 1 hora: App Service reemplaza la instancia

**Endpoint de health check recomendado:**
```csharp
app.MapGet("/health", async (CosmosClient cosmos, IConfiguration config) =>
{
    try
    {
        // Verificar conexión a Cosmos DB
        await cosmos.ReadAccountAsync();
        
        // Verificar que la configuración crítica existe
        var dbName = config["Cosmos:DatabaseName"] 
            ?? throw new Exception("Cosmos:DatabaseName not configured");
        
        return Results.Ok(new { 
            status = "healthy",
            checks = new {
                cosmosDb = "connected",
                configuration = "valid"
            }
        });
    }
    catch (Exception ex)
    {
        return Results.Json(new { 
            status = "unhealthy",
            error = ex.Message 
        }, statusCode: 503);
    }
});
```

**No hagáis health checks demasiado pesados.** Un health check que tarda 5 segundos y consulta 3 bases de datos crea más problemas de los que resuelve.

- `Error` → algo falló, necesita atención

## Slide 16 — Log Analytics: queries para diagnosticar

```kusto
// Top 10 peticiones más lentas (últimas 24h)
requests
| where timestamp > ago(24h)
| where duration > 2000  // > 2 segundos
| project timestamp, name, duration, resultCode, client_IP
| top 10 by duration desc

// Tasa de errores por hora
requests
| where timestamp > ago(24h)
| summarize total=count(), errores=countif(resultCode >= 500) by bin(timestamp, 1h)
| extend tasaError = round(errores * 100.0 / total, 2)
| project timestamp, total, errores, tasaError

// Dependencias lentas (DB, APIs externas)
dependencies
| where timestamp > ago(24h)
| where duration > 1000
| summarize avg(duration), count() by target, type, name
| order by avg_duration desc
```

## Slide 20 — OpenTelemetry: el estándar abierto

Microsoft está migrando Application Insights SDK a **OpenTelemetry** (OTel), el estándar de la industria (CNCF). En 2026 es la forma recomendada para apps nuevas:

```csharp
// dotnet add package Azure.Monitor.OpenTelemetry.AspNetCore

using Azure.Monitor.OpenTelemetry.AspNetCore;

var builder = WebApplication.CreateBuilder(args);

// OpenTelemetry + Azure Monitor exporter en una línea
builder.Services.AddOpenTelemetry()
    .UseAzureMonitor(options =>
    {
        options.ConnectionString = builder.Configuration["ApplicationInsights:ConnectionString"];
    })
    .WithTracing(tracing => tracing
        .AddSource("VentasApi.*")
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation()
        .AddAspNetCoreInstrumentation())
    .WithMetrics(metrics => metrics
        .AddMeter("VentasApi.*")
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()
        .AddProcessInstrumentation());
```

**Ventajas vs SDK tradicional de App Insights:**
- Estándar abierto: el mismo código funciona con Azure Monitor, Grafana, Datadog, New Relic...
- Más control sobre sampling, processors, enrichment
- Future-proof: Microsoft invierte aquí
- Interop con librerías que ya emiten en OTel (Npgsql, MongoDB client, etc.)

**Migración desde AppInsights SDK clásico:**
- Se puede coexistir temporalmente (ambos envían a la misma AI instance)
- Migrar poco a poco: primero traces, luego metrics, luego logs

## Slide 21 — Distributed tracing con correlation IDs

Cuando vuestra app llama a varios servicios (API → Function → Storage → Cosmos), un request genera varios "spans". El **correlation ID** los vincula:

```csharp
// Automático con OpenTelemetry
app.MapGet("/api/pedido/{id}", async (string id, IPedidoService svc, HttpContext ctx) =>
{
    using var activity = Activity.Current;
    activity?.SetTag("pedido.id", id);
    activity?.SetTag("user.id", ctx.User.FindFirst("sub")?.Value);
    
    // Esta llamada a Cosmos se vincula automáticamente
    var pedido = await svc.GetByIdAsync(id);
    
    // Llamadas HTTP también se vinculan (HttpClient auto-instrumentation)
    var stockInfo = await httpClient.GetFromJsonAsync<StockInfo>(
        $"https://api-stock/items/{pedido.ProductoId}");
    
    return Results.Ok(pedido);
});
```

**En App Insights / Azure Monitor:**
```
Transaction (operation_Id: abc123)
├── Request: GET /api/pedido/P-42      (150 ms)
│   ├── Dependency: cosmosdb GetItem    (8 ms)
│   ├── Dependency: api-stock GetStock  (90 ms)
│   │   └── (en api-stock:)
│   │       ├── Request: GET /items/X  (85 ms)
│   │       └── Dependency: sql SELECT (60 ms)
│   └── Trace: "Pedido P-42 procesado OK"
```

**Un solo operation_Id** atraviesa todos los servicios. Facilita diagnosticar issues que cruzan apps.

## Slide 22 — Custom metrics: medir tus indicadores de negocio

Además de métricas técnicas (CPU, requests), medid métricas de **negocio**:

```csharp
// Definir un Meter (OpenTelemetry)
public class PedidoMetrics
{
    private readonly Meter _meter;
    private readonly Counter<long> _pedidosCreados;
    private readonly Counter<decimal> _importeTotal;
    private readonly Histogram<double> _tiempoProcesamiento;

    public PedidoMetrics(IMeterFactory meterFactory)
    {
        _meter = meterFactory.Create("VentasApi.Pedidos");
        _pedidosCreados = _meter.CreateCounter<long>("pedidos.creados.total");
        _importeTotal = _meter.CreateCounter<decimal>("pedidos.importe.total");
        _tiempoProcesamiento = _meter.CreateHistogram<double>("pedidos.tiempo.ms");
    }

    public void IncrementarPedidosCreados(string prioridad, decimal importe) 
    {
        _pedidosCreados.Add(1, new("prioridad", prioridad));
        _importeTotal.Add(importe, new("prioridad", prioridad));
    }

    public void RegistrarTiempo(double ms) => _tiempoProcesamiento.Record(ms);
}

// Uso
public class PedidoService(PedidoMetrics metrics)
{
    public async Task<Pedido> CrearAsync(CrearPedidoDto dto)
    {
        var sw = Stopwatch.StartNew();
        var pedido = await CrearInternoAsync(dto);
        sw.Stop();
        
        metrics.IncrementarPedidosCreados(dto.Prioridad, pedido.Total);
        metrics.RegistrarTiempo(sw.ElapsedMilliseconds);
        
        return pedido;
    }
}
```

**En App Insights** estas métricas aparecen como custom, y podéis:
- Graficarlas en dashboards
- Crear alertas ("más de 10 pedidos críticos sin procesar")
- Correlacionar con métricas técnicas (¿spike de pedidos correlaciona con CPU?)

**Consejo:** pocas métricas bien pensadas > muchas métricas ruido. 5-10 métricas de negocio core es lo razonable.

## Slide 23 — Structured logging con Serilog

`ILogger` nativo de .NET es OK, pero **Serilog** da mucho más control en apps serias:

```csharp
// dotnet add package Serilog.AspNetCore
// dotnet add package Serilog.Sinks.ApplicationInsights
// dotnet add package Serilog.Enrichers.Environment

using Serilog;

Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .MinimumLevel.Override("Microsoft.AspNetCore", LogEventLevel.Warning)
    .Enrich.FromLogContext()
    .Enrich.WithMachineName()
    .Enrich.WithEnvironmentName()
    .Enrich.WithProperty("Application", "VentasApi")
    .Enrich.WithProperty("Version", Assembly.GetExecutingAssembly().GetName().Version!.ToString())
    .WriteTo.Console(new CompactJsonFormatter())
    .WriteTo.ApplicationInsights(
        TelemetryConverter.Traces,
        restrictedToMinimumLevel: LogEventLevel.Information)
    .CreateLogger();

var builder = WebApplication.CreateBuilder(args);
builder.Host.UseSerilog();
```

**Uso con structured logging:**
```csharp
// ❌ MAL: string formatting (pierde estructura)
logger.LogInformation($"Pedido {pedido.Id} del cliente {pedido.ClienteId} de {pedido.Total}€");

// ✅ BIEN: structured logging (cada dato es un field)
logger.LogInformation(
    "Pedido {PedidoId} del cliente {ClienteId} de {Importe}€",
    pedido.Id, pedido.ClienteId, pedido.Total);
```

**En App Insights:**
- Buscable por PedidoId, ClienteId, Importe como campos individuales
- Filtrable: `traces | where customDimensions.PedidoId == "P-42"`
- Agrupable: `traces | summarize count() by customDimensions.ClienteId`

Con string formatting estaríais buscando en el texto — mucho más lento e impreciso.

## Slide 24 — Sampling: reducir coste de telemetría

App Insights cobra por GB ingerido (~€2-3/GB). Una API con tráfico alto puede generar mucho. **Sampling** reduce volumen manteniendo representatividad:

```csharp
// Adaptive sampling (default en App Insights SDK)
builder.Services.AddApplicationInsightsTelemetry(options =>
{
    options.ConnectionString = builder.Configuration["AppInsights:ConnectionString"];
    // Default: ajusta sampling automáticamente para <5 items/seg
});

// Fixed sampling: garantiza % concreto
builder.Services.Configure<TelemetryConfiguration>(config =>
{
    var builder = config.DefaultTelemetrySink.TelemetryProcessorChainBuilder;
    builder.UseSampling(10.0);   // mantener solo 10% de telemetría
    builder.Build();
});

// Sampling inteligente (custom processor)
public class IntelligentSamplingProcessor : ITelemetryProcessor
{
    public void Process(ITelemetry item)
    {
        // Siempre mantener: errores, requests lentos, telemetría crítica
        if (item is RequestTelemetry req)
        {
            if (req.Success == false) { /* keep */ return; }
            if (req.Duration.TotalMilliseconds > 2000) { /* keep */ return; }
        }
        
        // Para el resto, aplicar sampling
        if (Random.Shared.NextDouble() > 0.1) return;  // drop 90%
        _next.Process(item);
    }
}
```

**Sampling rates recomendados:**

| Volumen | Sampling | Notas |
|---|---|---|
| <100 req/s | 100% | Sin sampling |
| 100-1000 req/s | 25-50% | Mantener representatividad |
| 1000-10000 req/s | 5-10% | Solo muestras |
| >10000 req/s | Fixed + custom | Solo errores + 1% success |

**Regla:** siempre mantener **100% de errores** independientemente del sampling. Errores son raros — necesitáis verlos todos.

## Slide 25 — Log scrubbing: no loguear PII/secretos

Compliance (GDPR) obliga a no loguear datos personales. Azure tiene `TelemetryProcessor` para limpiar:

```csharp
public class PiiScrubProcessor : ITelemetryProcessor
{
    private readonly ITelemetryProcessor _next;
    private static readonly Regex EmailRegex = new(@"\b[\w\.-]+@[\w\.-]+\.\w+\b");
    private static readonly Regex CreditCardRegex = new(@"\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b");
    private static readonly Regex TokenRegex = new(@"\b(Bearer\s+)?[A-Za-z0-9\-_=]{20,}\.[A-Za-z0-9\-_=]+\.[A-Za-z0-9\-_.+/=]+\b");

    public PiiScrubProcessor(ITelemetryProcessor next) => _next = next;

    public void Process(ITelemetry item)
    {
        if (item is TraceTelemetry trace)
        {
            trace.Message = Scrub(trace.Message);
        }
        if (item is RequestTelemetry req)
        {
            req.Url = ScrubUri(req.Url);
            foreach (var prop in req.Properties.Keys.ToList())
                req.Properties[prop] = Scrub(req.Properties[prop]);
        }
        // Similar para Exception, Dependency, etc.
        _next.Process(item);
    }

    private string Scrub(string input) => input
        ?.Let(s => EmailRegex.Replace(s, "[REDACTED:EMAIL]"))
        ?.Let(s => CreditCardRegex.Replace(s, "[REDACTED:CC]"))
        ?.Let(s => TokenRegex.Replace(s, "[REDACTED:TOKEN]"))
        ?? "";
}

// Registrar
builder.Services.AddApplicationInsightsTelemetryProcessor<PiiScrubProcessor>();
```

**Tipos de PII típicos a scrub:**
- Emails, teléfonos, DNIs/NIEs
- Tarjetas de crédito (aunque PCI prohíbe almacenarlas directamente)
- Passwords, tokens JWT, API keys
- IPs (en algunos contextos)
- Nombres completos + fecha nacimiento (combinación es identificadora)

## Slide 27 — Metric alerts vs Log alerts: diferencias

Dos tipos de alertas en Azure, con usos distintos:

| | Metric alerts | Log (KQL) alerts |
|---|---|---|
| Qué monitorizan | Métricas Azure built-in | Queries KQL sobre logs |
| Frecuencia | Evalúan cada 1 min | Ejecutan queries cada 5-15 min |
| Latencia | Baja (casi real-time) | Mayor (query execution time) |
| Ejemplos | CPU > 80%, Requests > 1000 | "errores con message X en últimos 15min" |
| Coste | Gratis (primeras 10) | Coste por evaluación |
| Complejidad | Simple (métrica + umbral) | KQL completo (joins, aggregates) |

**Metric alert (simple, barato):**
```bash
az monitor metrics alert create \
  --name "app-ventas-cpu-high" -g rg-apps \
  --scopes "/subscriptions/<sub>/.../sites/app-ventas" \
  --condition "avg cpuPercentage > 80" \
  --window-size 5m --evaluation-frequency 1m \
  --action ag-oncall \
  --severity 2
```

**Log alert (potente, más caro):**
```bash
az monitor scheduled-query create \
  --name "errores-pedidos-5min" -g rg-monitoring \
  --scopes "<ai-resource-id>" \
  --condition "count > 5" \
  --condition-query "
    requests 
    | where timestamp > ago(5m)
    | where name startswith 'POST /api/pedidos'
    | where resultCode >= 500
  " \
  --window-size 5m --evaluation-frequency 5m \
  --action ag-oncall
```

**Regla:** empezad con metric alerts (simples, baratas). Log alerts solo cuando la condición requiere queries complejas.

## Slide 29 — Profiler y Snapshot Debugger

Dos herramientas avanzadas de App Insights que mucha gente no usa:

**Profiler** — captura CPU/memoria profiles de la app en producción:
```bash
# Habilitar Profiler en App Service
az webapp config appsettings set --name app-ventas -g rg-apps \
  --settings \
    APPINSIGHTS_PROFILERFEATURE_VERSION="1.0.0" \
    DiagnosticServices_EXTENSION_VERSION="~3" \
    APPINSIGHTS_INSTRUMENTATIONKEY="<key>"
```

**Qué hace:**
- Captura profile automático cuando hay request lento o CPU alta
- Muestra qué funciones consumen más CPU (hot paths)
- Identifica bottlenecks sin tener que reproducir localmente
- Overhead mínimo (~5% CPU)

**Cuándo usarlo:** cuando tenéis latencia P99 alta pero no sabéis por qué.

**Snapshot Debugger** — captura snapshot del estado cuando salta una excepción:
```csharp
// Instalar paquete
// dotnet add package Microsoft.ApplicationInsights.SnapshotCollector

// Program.cs
builder.Services.AddSnapshotCollector(
    (configureSnapshotCollectorFromApplicationInsights) => {});
```

**Qué hace:**
- Cuando una excepción se lanza en prod, captura dump del proceso
- Podéis abrirlo en VS y **debuggear en el snapshot** como si fuera local
- Variables locales, stack, heap objects visibles
- Como tener un debugger conectado a producción (pero asíncrono)

**Cuándo usarlo:** bugs que solo ocurren en producción con datos específicos (null reference en caso raro, etc.).

## Slide 30 — Grafana con Azure Monitor como datasource

**Azure Managed Grafana** (lanzado 2022, maduro 2025) es Grafana "as a service" con conexión nativa a Azure Monitor:

```bash
# Crear Managed Grafana
az grafana create \
  --name grafana-ventas -g rg-monitoring \
  --location westeurope \
  --skus Standard

# Ya viene pre-configurado con Azure Monitor como datasource
# Login con Entra ID (SSO)

# Acceder:
# https://grafana-ventas-xxx.grafana.azure.com
```

**Por qué Grafana si ya tenemos Azure Dashboards:**
- Queries más potentes (PromQL, LogQL además de KQL)
- Plantillas comunitarias (thousands de dashboards pre-hechos)
- Alerts más flexibles que Azure Monitor
- Integración con stacks no-Azure (Prometheus, Loki, Datadog)
- UI más agradable para visualización (opinable, cierto)

**Patrón típico:**
```
Azure Monitor = Storage de métricas y logs (donde VIVEN los datos)
Grafana = Visualización + Alerting UX (cómo los VEMOS)

Data flow:
Apps → App Insights → Azure Monitor (storage)
                                ↓
                             Grafana (queries + dashboards)
```

**Cuándo valoráis Grafana:**
- Equipo con experiencia Grafana (Prometheus/Loki en previa empresa)
- Dashboards complejos que Azure Dashboards no soporta bien
- Multi-cloud observability (Grafana muestra Azure + AWS + GCP juntos)

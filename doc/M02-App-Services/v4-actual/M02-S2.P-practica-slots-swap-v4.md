## Slide 1 — Portada
**Módulo 2 · Práctica**

## Slide 2 — Qué vais a hacer
Vais a simular un ciclo completo de despliegue a producción usando slots:

1. Partir de la Web App del módulo 1 (o crear una nueva)
2. Subir el plan a Standard S1 (necesario para slots)
3. Crear un slot de staging
4. Desplegar una "versión 2" al slot de staging
5. Verificar en staging que funciona
6. Hacer swap a producción
7. Verificar que producción tiene la v2 y staging la v1
8. Simular un rollback (swap inverso)

**Tiempo estimado:** 20-25 minutos
**Entregable:** Vuestra app con slot staging funcional y swap completado

## Slide 3 — Pre-flight: requisitos antes de empezar

Antes de tocar Azure, validad que tenéis todo en orden. Cinco minutos aquí ahorran 30 minutos de troubleshooting después.

**Checklist técnico:**

```bash
# 1. Azure CLI instalado y actualizado
az --version
# Esperado: azure-cli >= 2.65.0

# 2. Login activo
az account show --output table
# Si no estáis logueados:
az login

# 3. Suscripción correcta seleccionada
az account list --output table
az account set --subscription "<nombre-de-vuestra-sub>"

# 4. Verificar que tenéis el RG y App Service del Hello World (M01)
az group show --name rg-curso-azure-<tu-nombre> --query "name" -o tsv
az webapp show --name app-hello-<tu-nombre> --resource-group rg-curso-azure-<tu-nombre> --query "name" -o tsv
```

**Si algo falla aquí:**
- ❌ "No subscriptions found" → `az login --tenant <tenant-id>` con vuestro tenant
- ❌ "ResourceGroup not found" → Volver a M01 y completar el Hello World primero
- ❌ "Forbidden" → Pedir Contributor sobre el RG al instructor

**Cuenta personal vs corporativa:** si tenéis las dos asociadas, asegurad que `az account show` devuelve la correcta. Es el error más común en clase.

**Tiempo estimado para esta práctica:** 60-75 minutos. Reservad bloque continuo. Slot swap tiene tiempos de propagación (1-2 min cada operación) que no se pueden acelerar.

## Slide 9 — Configurar warm-up para swap sin downtime

Por defecto, App Service hace un health probe básico antes del swap. Pero si vuestra app necesita warm-up (cargar caches, conectar a BBDD, etc.), debéis configurarlo explícitamente o algunos usuarios verán latencias enormes durante el swap.

**1. Añadir `applicationInitialization` al `web.config`** (si tenéis uno) o en `Program.cs`:

```csharp
// Program.cs — endpoint de warm-up que pre-carga lo importante
app.MapGet("/warmup", async (IDbContext db, ICacheService cache) =>
{
    // Pre-cargar conexión a BBDD
    await db.Database.CanConnectAsync();
    
    // Pre-cargar caches críticos
    await cache.PreloadCriticalDataAsync();
    
    // Verificar dependencias externas
    return Results.Ok(new { status = "warm", timestamp = DateTime.UtcNow });
});
```

**2. Configurar App Service para llamar al warm-up antes del swap:**

```bash
az webapp config appsettings set \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --slot staging \
  --settings \
    WEBSITE_SWAP_WARMUP_PING_PATH=/warmup \
    WEBSITE_SWAP_WARMUP_PING_STATUSES=200
```

**3. Verificar manualmente el endpoint en staging antes del swap:**

```bash
curl -i https://app-curso-<tu-nombre>-staging.azurewebsites.net/warmup
# HTTP/1.1 200 OK
# {"status":"warm","timestamp":"2026-04-27T..."}
```

**Lo que pasa internamente durante el swap:**

```
1. App Service lanza warmup ping al slot staging
2. Espera 200 OK (o el código configurado)
3. Solo entonces inicia el routing change
4. Tráfico migra: producción → staging slot
5. Slot anterior (con código viejo) queda en "production" slot vacío
```

**Sin warm-up correcto, el primer request post-swap puede tardar 10-30 segundos.**

## Slide 10 — Paso 6: Swap — staging a producción

```bash
az webapp deployment slot swap \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --slot staging \
  --target-slot production
```

**Ahora verificad ambas URLs:**

**Producción** (`app-curso-<tu-nombre>.azurewebsites.net`):
- `version: "2.0"` ← código nuevo ✓
- `entorno: "Production"` ← sticky se quedó ✓
- `nota_entorno: "Entorno de producción"` ← sticky se quedó ✓

**Staging** (`app-curso-<tu-nombre>-staging.azurewebsites.net`):
- `version: "1.0"` (o el mensaje del módulo 1) ← código anterior
- `entorno: "Staging"` ← sticky se quedó ✓

## Slide 11 — Smoke tests automatizados post-swap

Verificar a mano que la nueva versión funciona es lento y propenso a olvidos. Un smoke test scripted detecta problemas en segundos.

**Crear `smoke-test.sh`:**

```bash
#!/bin/bash
set -e  # Falla al primer error

URL="https://app-curso-<tu-nombre>.azurewebsites.net"
EXPECTED_VERSION="2.0"
TIMEOUT_SEC=30

echo "🔍 Smoke tests sobre $URL"

# Test 1: Health endpoint responde 200
echo -n "  [1/4] Health check... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" --max-time $TIMEOUT_SEC "$URL/health")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 2: Versión correcta desplegada
echo -n "  [2/4] Versión correcta... "
ACTUAL=$(curl -s --max-time $TIMEOUT_SEC "$URL/" | grep -oP '"version":"\K[^"]+')
[ "$ACTUAL" = "$EXPECTED_VERSION" ] && echo "✓ ($ACTUAL)" || { echo "✗ (esperado $EXPECTED_VERSION, recibido $ACTUAL)"; exit 1; }

# Test 3: Variable sticky se mantiene (entorno = Production)
echo -n "  [3/4] Variable sticky... "
ENTORNO=$(curl -s --max-time $TIMEOUT_SEC "$URL/" | grep -oP '"entorno":"\K[^"]+')
[ "$ENTORNO" = "Production" ] && echo "✓" || { echo "✗ (recibido $ENTORNO)"; exit 1; }

# Test 4: Latencia P95 razonable (5 requests)
echo -n "  [4/4] Latencia... "
TOTAL=0
for i in {1..5}; do
  T=$(curl -o /dev/null -s -w "%{time_total}" --max-time $TIMEOUT_SEC "$URL/")
  TOTAL=$(echo "$TOTAL + $T" | bc -l)
done
AVG=$(echo "scale=3; $TOTAL / 5" | bc -l)
echo "avg ${AVG}s ✓"

echo ""
echo "✅ Todos los smoke tests pasados — swap exitoso"
```

**Ejecutar después del swap:**

```bash
chmod +x smoke-test.sh
./smoke-test.sh
```

**Si algún test falla → rollback inmediato** (siguiente slide).

**En producción real:** este script se ejecuta automáticamente desde el pipeline de despliegue. Si falla, el pipeline lanza el rollback sin intervención humana.

## Slide 14 — Slot diff: comparar configuración entre slots

Cuando algo va mal post-swap, lo primero que necesitáis es saber qué se diferencia entre slots. Azure no tiene un comando "diff" nativo — lo construimos:

```bash
# Exportar settings de ambos slots
az webapp config appsettings list \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --output json > production-settings.json

az webapp config appsettings list \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --slot staging \
  --output json > staging-settings.json

# Diff en formato legible
diff <(jq -r '.[] | "\(.name)=\(.value)"' production-settings.json | sort) \
     <(jq -r '.[] | "\(.name)=\(.value)"' staging-settings.json | sort)
```

**Output esperado:**
```diff
< entorno=Production              ← solo en producción
< nota_entorno=Producción         ← solo en producción
> entorno=Staging                 ← solo en staging
> nota_entorno=Staging            ← solo en staging
```

**Si veis diferencias inesperadas** (variables que deberían viajar pero no lo hacen, o al revés), es un bug de configuración antes del swap, no del swap en sí.

**Tip pro:** automatizad este diff en CI antes de cada swap. Si aparece algo no esperado, fallad el deploy.

## Slide 15 — Auto-swap: cuando manual no es suficiente

Para entornos donde queráis que cada deploy a staging haga swap automático a producción si pasan los smoke tests:

```bash
az webapp deployment slot auto-swap \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --slot staging \
  --auto-swap-slot production
```

**Cómo funciona:**

```
1. Deploy a slot staging
2. App Service hace warmup ping
3. Si responde 200 → swap automático a producción
4. Si responde error → no hay swap, slot queda con código nuevo para investigar
```

**Cuándo usar auto-swap:**
- ✅ Entornos dev/test donde la velocidad importa más que el control
- ✅ Equipos pequeños con buenos smoke tests
- ✅ Apps con bajo riesgo (internal tools, dashboards)

**Cuándo NO usar:**
- ❌ Producción crítica (queréis un humano en el loop)
- ❌ Sin smoke tests robustos (entonces auto-swap = auto-pwn)
- ❌ Compliance estricto (audit trail necesita approval explícito)

**Desactivarlo:**
```bash
az webapp deployment slot auto-swap \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --slot staging \
  --disable
```

## Slide 16 — Slots y pricing: límites según SKU

No todos los planes soportan slots. Saber esto antes de prometer arquitecturas evita reuniones incómodas:

| Plan | Slots máximos (incluye production) | Coste base |
|------|:---:|---:|
| F1 (Free) | ❌ 0 | €0 |
| D1 (Shared) | ❌ 0 | ~€8/mes |
| B1/B2/B3 (Basic) | ❌ 0 | ~€13-50/mes |
| **S1/S2/S3 (Standard)** | ✅ **5** | ~€70-280/mes |
| **P0v3-P3v3 (Premium v3)** | ✅ **20** | ~€105-840/mes |
| I1v2-I3v2 (Isolated) | ✅ 20 | desde ~€280/mes |

**Lo que esto significa en práctica:**

```
Necesidad: deployment slots para Blue/Green
│
├── Mínimo S1 (~€70/mes)
│   └── 4 slots adicionales disponibles
│
├── Si necesitáis Premium v3 (más performance, slots adicionales)
│   ├── P0v3 ~€105/mes — buen balance precio/features
│   └── 19 slots adicionales (overkill para casi todo)
│
└── Si tenéis Premium v3 ya, slots son "gratis"
    (el plan ya está pagado, slots no añaden coste)
```

**Coste real de cada slot:** un slot adicional **NO añade coste extra** sobre el plan. Si tenéis S1, podéis tener 4 slots sin pagar más. Lo que aumenta el coste es el plan, no los slots en sí.

**Trampa común:** intentar slots en B1 → "Operation not supported on this SKU". Hay que subir a S1 mínimo.

## Slide 17 — Troubleshooting: errores comunes durante swap

Los 6 errores más frecuentes en clase, con su solución:

**1. "Operation 'Slot' is not supported"**
```
Causa: Plan no es Standard o superior
Fix: az appservice plan update --sku S1
```

**2. Swap se queda colgado >10 min**
```
Causa: Warm-up ping no responde 200 OK
Diagnóstico:
  curl -v https://app-staging.azurewebsites.net/<warmup-path>
Fix: configurar WEBSITE_SWAP_WARMUP_PING_PATH correctamente,
     o añadir endpoint /warmup que devuelva 200
```

**3. Variables sticky desaparecen tras swap**
```
Causa: la variable NO estaba marcada como slot setting
Verificar:
  az webapp config appsettings list --name X -g Y --slot staging \
    --query "[?name=='entorno'].{Name:name, Slot:slotSetting}"
Fix: 
  az webapp config appsettings set --name X -g Y --slot staging \
    --slot-settings entorno=Production
  (debe ser --slot-settings, no --settings)
```

**4. App Insights mezcla telemetría de prod y staging**
```
Causa: connection string compartida no marcada como sticky
Fix: hacer APPLICATIONINSIGHTS_CONNECTION_STRING slot setting
     y usar dos App Insights distintos (uno por slot)
```

**5. Connection string de BBDD apunta a staging tras swap**
```
Causa: connection string no es slot-specific
Fix: usar Key Vault references con slot setting:
     ConnectionString = @Microsoft.KeyVault(VaultName=kv-curso;SecretName=db-prod)
     en producción slot, y db-staging en staging slot
```

**6. "Cannot delete production slot"**
```
Causa: estáis intentando borrar el slot principal (no se puede)
Fix: solo se borran los slots adicionales con su nombre:
     az webapp deployment slot delete --slot staging
     (sin pasar production como --slot)
```

**Si nada de esto resuelve:** revisad logs en tiempo real durante swap:
```bash
az webapp log tail --name app-curso-<tu-nombre> -g rg-curso-azure-<tu-nombre>
```

## Slide 20 — Variante: 3 slots (dev/staging/production)

Para práctica más completa, crear 3 slots y mover código entre ellos:

```bash
# Crear 3 slots (requiere Standard S1 mínimo)
az webapp deployment slot create --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> \
  --configuration-source app-ventas-<tu-nombre> --slot dev

az webapp deployment slot create --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> \
  --configuration-source app-ventas-<tu-nombre> --slot staging

# (production es el slot principal ya)

# Ejercicio:
# 1. Deploy v1 directo a production
# 2. Deploy v2 solo al slot dev
# 3. Test en dev. Si OK, swap dev → staging
# 4. Test en staging con tráfico limitado (traffic-routing 10%)
# 5. Si OK, swap staging → production
# 6. Verificar versión en prod
# 7. Detectar bug simulado → swap inverso (rollback)

# Ver estado de todos los slots
az webapp deployment slot list --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> -o table
```

**Reflexión:** ¿por qué separar dev/staging/prod si solo hay un equipo? Escenarios típicos:
- Dev: cambios experimentales, no garantizan estabilidad
- Staging: pre-prod con QA, último filtro antes de real
- Prod: lo que ven los usuarios

## Slide 21 — Variante: canary deployment con traffic routing

En lugar de swap directo (0% → 100%), probar con distribución gradual:

```bash
# Setup inicial: v1 en production, v2 en staging
# En vez de hacer swap, dividir tráfico

# Paso 1: 10% a staging (v2)
az webapp traffic-routing set --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> \
  --distribution staging=10

# Generar tráfico para verificar
for i in {1..50}; do
  curl -s https://app-ventas-<tu-nombre>.azurewebsites.net/ | jq -r '.hostname, .version'
done
# Deberías ver aprox 5 hits a v2 (10%) y 45 a v1 (90%)

# Paso 2: Si OK, subir a 50%
az webapp traffic-routing set --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> \
  --distribution staging=50

# Paso 3: 100% via swap
az webapp deployment slot swap --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre> \
  --slot staging

# Paso 4: limpiar el routing
az webapp traffic-routing clear --name app-ventas-<tu-nombre> -g rg-ventas-<tu-nombre>
```

**Reflexión:** ¿en qué casos preferiríais canary sobre swap directo?
- Cambios con riesgo desconocido (refactor grande, nueva librería)
- Observación de métricas reales antes de exposición total
- Para experimentos A/B (no es sobre calidad, sino comparativa)

## Slide 22 — Variante: pipeline GitHub Actions con swap automatizado

La práctica que acabáis de hacer manual es exactamente lo que se automatiza en CI/CD real. Aquí tenéis el equivalente listo para producción:

**`.github/workflows/deploy-with-slot-swap.yml`:**

```yaml
name: Deploy con slot swap

on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Build & publish
        run: |
          dotnet publish src/App.csproj -c Release -o ./publish
      
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      # Deploy SOLO al slot staging (production no se toca aún)
      - name: Deploy to staging slot
        uses: azure/webapps-deploy@v3
        with:
          app-name: app-curso-prod
          slot-name: staging
          package: ./publish
      
      # Smoke tests sobre staging
      - name: Smoke tests on staging
        run: |
          STAGING_URL="https://app-curso-prod-staging.azurewebsites.net"
          chmod +x ./smoke-test.sh
          STAGING_URL=$STAGING_URL ./smoke-test.sh
      
      # Solo si smoke tests pasan → swap a producción
      - name: Swap staging to production
        if: success()
        run: |
          az webapp deployment slot swap \
            --name app-curso-prod \
            --resource-group rg-curso-prod \
            --slot staging \
            --target-slot production
      
      # Verificar producción tras swap
      - name: Verify production
        run: |
          PROD_URL="https://app-curso-prod.azurewebsites.net"
          STAGING_URL=$PROD_URL ./smoke-test.sh
      
      # Auto-rollback si verificación falla
      - name: Rollback on failure
        if: failure()
        run: |
          az webapp deployment slot swap \
            --name app-curso-prod \
            --resource-group rg-curso-prod \
            --slot staging \
            --target-slot production
          echo "::error::Rollback ejecutado tras fallo en verificación"
          exit 1
      
      # Notificación a Teams
      - name: Notify Teams
        if: always()
        uses: jdcargile/ms-teams-notification@v1.4
        with:
          github-token: ${{ github.token }}
          ms-teams-webhook-uri: ${{ secrets.TEAMS_WEBHOOK }}
          notification-summary: "Deploy ${{ job.status }}"
          notification-color: ${{ job.status == 'success' && '00ff00' || 'ff0000' }}
```

**Lo que hace este pipeline (que vosotros hicisteis a mano):**

```
1. Build de la app
2. Deploy al slot staging (NO toca producción)
3. Ejecuta smoke tests sobre staging
4. SI pasan: hace swap → producción
5. Verifica producción tras swap
6. SI verificación falla: rollback automático
7. Notifica al equipo
```

**Setup requerido (one-time):**
- App Registration en Microsoft Entra (OIDC federated)
- 3 secrets en GitHub: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`
- 1 secret opcional: `TEAMS_WEBHOOK`

**Esto se cubre en profundidad en el M08 (DevOps).** Por ahora, sabed que la práctica manual = el 95% de lo que un pipeline real hace. La diferencia está en automatizar el orchestrator y los gates.

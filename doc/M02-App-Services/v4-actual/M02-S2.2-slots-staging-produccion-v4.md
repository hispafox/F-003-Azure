# Submódulo 2.2 — Entornos: staging/producción, slots de despliegue

## Slide 1 — Portada
**Módulo 2 · Submódulo 2.2**
Slots de despliegue: staging y producción
Despliegues sin downtime y entornos paralelos en App Service


---

## Slide 2 — El problema que resuelven los slots
Imaginad el escenario habitual sin slots:

1. Tenéis la app en producción atendiendo usuarios
2. Desplegáis una nueva versión directamente a producción
3. Durante el despliegue (30-90 segundos), la app se reinicia
4. Los usuarios ven errores 503 o respuestas lentas
5. Si la nueva versión tiene un bug, tenéis que redesplegar la anterior — otro reinicio, más downtime

Con slots, el flujo cambia completamente:
1. Desplegáis la nueva versión a un slot de staging (producción no se toca)
2. Probáis en staging con la URL de staging
3. Cuando estáis seguros, hacéis swap: staging se convierte en producción y viceversa
4. El swap es instantáneo — sin reinicio, sin downtime
5. Si algo falla, un swap inverso restaura la versión anterior en segundos


---

## Slide 3 — Qué es un deployment slot
Un slot es una instancia independiente de tu app dentro del mismo App Service Plan:

```
App Service Plan (S1)
├── app-ventas (producción)        ← URL: app-ventas.azurewebsites.net
│   ├── Código: v2.3 (versión actual)
│   ├── Config: DB_CONN=prod, LOG_LEVEL=Warning
│   └── Tráfico: 100% usuarios reales
│
└── app-ventas/staging             ← URL: app-ventas-staging.azurewebsites.net
    ├── Código: v2.4 (próxima versión)
    ├── Config: DB_CONN=staging, LOG_LEVEL=Debug
    └── Tráfico: solo QA y testing
```

**Cada slot tiene:**
- Su propia URL (accesible públicamente o restringible por IP)
- Su propia configuración (variables de entorno independientes)
- Su propio código desplegado
- Su propio historial de despliegues

**Comparten:**
- El mismo App Service Plan (los mismos recursos de cómputo)
- El mismo dominio base (azurewebsites.net)

## Slide 4 — Requisitos y límites de los slots

| Tier | Slots disponibles | Incluye producción |
|------|:-----------------:|:------------------:|
| Free (F1) | 0 | — |
| Basic (B1-B3) | 0 | — |
| Standard (S1-S3) | 5 | Sí (prod + 4 extras) |
| Premium (P1v3-P3v3) | 20 | Sí (prod + 19 extras) |
| Isolated (I1v2+) | 20 | Sí |

**Importante:** Los slots comparten los recursos del plan. Si tenéis un plan S1 con 1 core y 1.75 GB RAM, esos recursos se reparten entre todos los slots. Un slot de staging ejecutando tests pesados puede degradar producción.

**Recomendación:** Para testing de carga en staging, subid temporalmente el plan o usad un plan separado para los slots de testing.

## Slide 5 — Crear un slot de staging

```bash
# Crear slot
az webapp deployment slot create \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging

# Verificar que existe
az webapp deployment slot list \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --output table

# La URL del slot es:
# https://app-ventas-staging.azurewebsites.net
```

**Convención de nombres de slots:**
- `staging` — pre-producción, última verificación antes del swap
- `dev` — desarrollo, integración continua
- `canary` — versión nueva para un % de usuarios
- `hotfix` — correcciones urgentes

Para la mayoría de equipos, un solo slot `staging` es suficiente. Añadid más cuando el flujo lo requiera.

## Slide 6 — Desplegar al slot de staging

Los despliegues al slot son idénticos a los de producción, añadiendo `--slot`:

```bash
# Opción 1: Zip Deploy al slot
dotnet publish -c Release -o ./publish
cd publish && zip -r ../deploy.zip . && cd ..

az webapp deploy \
  --resource-group rg-ventas-prod \
  --name app-ventas \
  --slot staging \
  --src-path deploy.zip \
  --type zip

# Opción 2: desde VS Code
# Clic derecho → Deploy to Web App → elegir "app-ventas (staging)"

# Verificar
az webapp browse \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging
```

**Lo que NO cambia en producción:**
- La URL principal (`app-ventas.azurewebsites.net`) sigue sirviendo la versión anterior
- Los usuarios no ven ningún cambio
- Podéis probar en staging todo el tiempo que necesitéis

## Slide 7 — Configuración del slot: variables independientes

Cada slot tiene sus propias variables de entorno:

```bash
# Configurar variables SOLO en staging
az webapp config appsettings set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --settings \
    ASPNETCORE_ENVIRONMENT=Staging \
    DB_CONNECTION="Server=staging-db;..." \
    LOG_LEVEL=Debug \
    FEATURE_FLAG_NUEVA_UI=true

# Ver configuración del slot staging
az webapp config appsettings list \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --output table
```

**Producción puede tener valores diferentes:**
```bash
az webapp config appsettings list \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --output table
# DB_CONNECTION=Server=prod-db;...
# LOG_LEVEL=Warning
# FEATURE_FLAG_NUEVA_UI=false
```

Aquí es donde entra un concepto clave: **slot settings** (sticky settings).

## Slide 8 — Slot Settings (sticky): la pieza crítica

Cuando hacéis un swap, las variables de entorno se intercambian con el código. Pero a veces necesitáis que ciertas variables se queden en su slot:

**Ejemplo del problema:**
- Staging tiene `DB_CONNECTION=staging-db`
- Producción tiene `DB_CONNECTION=prod-db`
- Hacéis swap
- El código de staging ahora está en producción... pero si la variable viajó con el código, producción estaría apuntando a `staging-db`

**La solución: marcar variables como "slot setting" (sticky):**

```bash
# Marcar como sticky (se queda en el slot, no viaja con el swap)
az webapp config appsettings set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot-settings \
    DB_CONNECTION="Server=prod-db;..." \
    ASPNETCORE_ENVIRONMENT=Production \
    APP_INSIGHTS_KEY="prod-key-123"

# En staging, lo mismo pero con valores de staging
az webapp config appsettings set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --slot-settings \
    DB_CONNECTION="Server=staging-db;..." \
    ASPNETCORE_ENVIRONMENT=Staging \
    APP_INSIGHTS_KEY="staging-key-456"
```

**Después del swap:**
- El código nuevo está en producción ✓
- `DB_CONNECTION` sigue apuntando a `prod-db` ✓ (es sticky, no viajó)
- `ASPNETCORE_ENVIRONMENT` sigue siendo `Production` ✓


---

## Slide 9 — Qué marcar como sticky y qué no

| Variable | ¿Sticky? | Por qué |
|----------|:--------:|---------|
| `DB_CONNECTION` | ✓ Sí | Cada entorno tiene su propia DB |
| `ASPNETCORE_ENVIRONMENT` | ✓ Sí | Producción es Production, staging es Staging |
| `APP_INSIGHTS_KEY` | ✓ Sí | Cada entorno tiene su propio App Insights |
| `REDIS_CONNECTION` | ✓ Sí | Cache separada por entorno |
| `API_KEY_EXTERNA` | ✓ Sí | Si la API externa tiene keys por entorno |
| `FEATURE_FLAG_X` | Depende | Sticky si el flag es por entorno. No sticky si el flag va con la versión del código. |
| `LOG_LEVEL` | ✓ Sí | Debug en staging, Warning en prod |
| `APP_VERSION` | ✗ No | Debería viajar con el código |

**Regla simple:** Si el valor depende del entorno → sticky. Si depende de la versión del código → no sticky.

## Slide 10 — El swap: cómo funciona por dentro

El swap NO copia archivos. Lo que hace es intercambiar los punteros del balanceador:

```
ANTES del swap:
  Load Balancer → [Producción: código v2.3, config prod]
  URL staging   → [Staging: código v2.4, config staging]

DURANTE el swap (milisegundos):
  1. Azure "calienta" el slot staging (envía peticiones de warmup)
  2. Verifica que staging responde correctamente
  3. Intercambia los punteros del load balancer

DESPUÉS del swap:
  Load Balancer → [Producción: código v2.4, config prod*]
  URL staging   → [Staging: código v2.3, config staging*]
  
  *Las sticky settings se quedan en su sitio
```

**Tiempo del swap:** 1-5 segundos para el intercambio de punteros. Pero el warmup previo puede tardar 30-120 segundos dependiendo de cuánto tarda tu app en arrancar.

**Zero downtime:** Los usuarios no experimentan ninguna interrupción. Las peticiones en vuelo se completan con la versión anterior, las nuevas van a la versión nueva.

## Slide 12 — Swap con preview (multi-phase swap)

Para mayor seguridad, podéis hacer un swap en dos fases:

**Fase 1 — Preview:**
```bash
az webapp deployment slot swap \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --target-slot production \
  --action preview
```

En esta fase:
- Las configuraciones se aplican (staging recibe la config de producción)
- Pero el tráfico NO se redirige todavía
- Podéis verificar que staging funciona con la config de producción

**Fase 2 — Completar (si todo está bien):**
```bash
az webapp deployment slot swap \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --target-slot production \
  --action complete
```

**Cancelar (si algo falla):**
```bash
az webapp deployment slot swap \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --target-slot production \
  --action reset
```

El swap con preview es especialmente útil cuando tenéis configuraciones complejas y queréis verificar que todo funciona con los valores de producción antes de redirigir el tráfico.

## Slide 13 — Rollback: volver a la versión anterior

Si después del swap descubrís un bug en producción:

```bash
# Rollback = hacer swap otra vez (la versión anterior está en staging)
az webapp deployment slot swap \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --target-slot production
```

**Tiempo de rollback:** El mismo que un swap normal (1-5 segundos + warmup). Mucho más rápido que redesplegar la versión anterior.

**Ventana de rollback:** Hasta que desplegéis algo nuevo en staging. Mientras staging tenga la versión anterior, siempre podéis hacer swap para volver.

**Automatizar rollback:**
```bash
# Si la tasa de errores 5xx sube después del swap, rollback automático
# (Esto se hace con Application Insights + Azure Monitor Alerts + Logic App)
# Lo veremos en el módulo 8
```

## Slide 14 — Traffic routing: canary deployments

Podéis enviar un porcentaje del tráfico de producción al slot de staging sin hacer swap completo:

```bash
# Enviar 10% del tráfico a staging
az webapp traffic-routing set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --distribution staging=10

# Verificar
az webapp traffic-routing show \
  --name app-ventas \
  --resource-group rg-ventas-prod

# Subir gradualmente
az webapp traffic-routing set ... --distribution staging=25
az webapp traffic-routing set ... --distribution staging=50

# Si todo va bien, swap completo
az webapp deployment slot swap ...

# Si algo falla, quitar el tráfico
az webapp traffic-routing clear \
  --name app-ventas \
  --resource-group rg-ventas-prod
```

**Cómo funciona:**
Azure redirige aleatoriamente el % configurado de peticiones al slot. El usuario no sabe que está en staging — ve la misma URL de producción.

**Caso de uso:** Tenéis un cambio arriesgado. Lo desplegáis a staging, enviáis un 5% del tráfico, monitorizáis errores. Si todo va bien, subís gradualmente hasta 100% y hacéis swap.

## Slide 15 — Auto-swap: despliegue automático

Auto-swap hace el swap automáticamente después de cada despliegue exitoso al slot:

```bash
# Habilitar auto-swap en el slot staging
az webapp deployment slot auto-swap \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --auto-swap-slot production
```

**Flujo con auto-swap:**
1. El pipeline CI/CD despliega al slot staging
2. App Service espera a que staging arranque y responda
3. Automáticamente hace swap a producción
4. Sin intervención humana

**¿Cuándo usarlo?**
- Entornos de desarrollo o staging donde queréis despliegue continuo
- Cuando tenéis tests automáticos en el pipeline que verifican antes del deploy al slot

**¿Cuándo NO usarlo?**
- Producción sin tests automáticos — querréis verificar manualmente en staging antes del swap
- Cuando necesitáis aprobaciones manuales en el proceso de despliegue

## Slide 16 — Warmup personalizado

Antes del swap, Azure envía peticiones de "warmup" al slot para que la app esté lista:

**Por defecto:** Azure hace una petición GET a la raíz (`/`) del slot.

**Personalizado (web.config):**
```xml
<system.webServer>
  <applicationInitialization>
    <add initializationPage="/" />
    <add initializationPage="/health" />
    <add initializationPage="/api/warmup" />
  </applicationInitialization>
</system.webServer>
```

**Personalizado (App Setting):**
```bash
az webapp config appsettings set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --settings WEBSITE_SWAP_WARMUP_PING_PATH="/health" \
             WEBSITE_SWAP_WARMUP_PING_STATUSES="200"
```

**¿Por qué importa?**
Si vuestra app tarda 30 segundos en arrancar (carga de caché, conexiones a DB, compilación de vistas), sin warmup los primeros usuarios después del swap verían respuestas lentas. Con warmup, Azure espera a que la app esté "caliente" antes de redirigir tráfico.

**Endpoint de warmup recomendado:**
```csharp
app.MapGet("/warmup", async (IServiceProvider services) =>
{
    // Verificar conexión a DB
    var db = services.GetRequiredService<CosmosClient>();
    await db.ReadAccountAsync();
    
    // Verificar caché
    var cache = services.GetRequiredService<IMemoryCache>();
    
    return Results.Ok(new { status = "warm", timestamp = DateTime.UtcNow });
});
```

## Slide 17 — Proteger el slot de staging

El slot de staging tiene su propia URL pública. Si no lo protegéis, cualquiera puede acceder:

**Opción 1 — Restricciones de IP:**
```bash
# Solo accesible desde la oficina
az webapp config access-restriction add \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --rule-name "solo-oficina" \
  --action Allow \
  --ip-address 203.0.113.0/24 \
  --priority 100

# Bloquear todo lo demás
az webapp config access-restriction set \
  --name app-ventas \
  --resource-group rg-ventas-prod \
  --slot staging \
  --default-action Deny
```

**Opción 2 — Autenticación (Easy Auth):**
Habilitar autenticación de Azure AD en el slot de staging. Solo usuarios autenticados de vuestro tenant pueden acceder.

**Opción 3 — Header secreto:**
Configurar una regla que solo permita acceso si la petición lleva un header específico (útil para tests automatizados).

## Slide 19 — Slots en Azure DevOps Pipelines (preview)

En el módulo 8 configuraremos esto completo, pero así es como se ve en un pipeline YAML:

```yaml
stages:
- stage: Build
  jobs:
  - job: BuildAndTest
    steps:
    - script: dotnet build
    - script: dotnet test
    - script: dotnet publish -c Release -o $(Build.ArtifactStagingDirectory)
    - publish: $(Build.ArtifactStagingDirectory)
      artifact: app

- stage: DeployStaging
  dependsOn: Build
  jobs:
  - deployment: DeployToStaging
    environment: staging
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs:
              appName: app-ventas
              slotName: staging
              package: $(Pipeline.Workspace)/app

- stage: SwapToProduction
  dependsOn: DeployStaging
  jobs:
  - deployment: SwapSlots
    environment: production  # Requiere aprobación manual
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureAppServiceManage@0
            inputs:
              Action: Swap Slots
              WebAppName: app-ventas
              SourceSlot: staging
```

El stage `SwapToProduction` tiene un environment con aprobación manual — alguien del equipo tiene que dar OK antes del swap.

## Slide 20 — Buenas prácticas con slots

**1. Siempre marcar sticky las variables dependientes del entorno**
DB connections, App Insights keys, feature flags por entorno, log levels.

**2. Warmup antes del swap**
Configurad un endpoint `/health` o `/warmup` que verifique dependencias (DB, caché, APIs externas).

**3. Proteger staging**
IP restrictions o autenticación. Staging no debería ser accesible desde internet sin restricciones.

**4. Monitorizar después del swap**
Configurar alertas de Application Insights para detectar aumento de errores 5xx post-swap. Si suben, rollback.

**5. No usar staging para tests de carga**
Los slots comparten recursos del plan. Un test de carga en staging puede degradar producción. Usad un plan separado o un slot temporal con su propio plan.

**6. Automatizar con pipeline pero con aprobación para producción**
Deploy automático a staging, swap manual (con aprobación) a producción. Lo mejor de ambos mundos.

## Slide 22 — Multi-slot scenarios: más allá de staging/prod

Para equipos grandes o releases complejas, 2 slots no bastan:

```
Setup típico de 3 slots:
├── production (slot por defecto)
├── staging  (último release candidate, pre-swap)
└── dev      (integraciones diarias, experimental)

Flujo:
1. Cambios → deploy continuo a slot "dev"
2. Cuando dev estable → swap dev ↔ staging
3. QA valida en staging con datos productivos (read-only)
4. Swap staging ↔ production
5. Si problema: swap inverso automático

Requisitos del plan:
- Standard S1: hasta 5 slots (1 prod + 4)
- Premium P1v3: hasta 20 slots (1 prod + 19)
- Isolated I1v2: hasta 20 slots
```

```bash
# Crear varios slots
az webapp deployment slot create --name app-ventas -g rg-apps --slot dev
az webapp deployment slot create --name app-ventas -g rg-apps --slot staging
az webapp deployment slot create --name app-ventas -g rg-apps --slot uat

# Swap entre slots específicos (no solo con production)
az webapp deployment slot swap --name app-ventas -g rg-apps \
  --slot dev --target-slot staging

# Todos los slots del mismo plan → comparten recursos
# El coste NO se multiplica por slot (misma máquina)
```

## Slide 23 — Managed Identity en slots: gotcha importante

**Cada slot tiene su PROPIO Managed Identity.** Esto causa problemas si no lo configuráis bien:

```bash
# Verificar identity del slot production (main)
az webapp identity show --name app-ventas -g rg-apps

# Verificar identity del slot staging (diferente!)
az webapp identity show --name app-ventas -g rg-apps --slot staging

# DOS principalId diferentes → DOS asignaciones RBAC necesarias
```

**Problema clásico:**
1. Deploy a staging con MI del slot staging
2. Assignamos rol "Cosmos DB Data Contributor" al MI de staging
3. Smoke test en staging → todo OK
4. Swap staging ↔ production
5. Ahora el código que funcionaba en staging "es" production, pero usa el MI de production
6. MI de production NO tiene el rol asignado → fallo al acceder a Cosmos

**Soluciones:**
```bash
# OPCIÓN 1: Asignar rol a AMBOS MI (recomendado)
PROD_MI=$(az webapp identity show --name app-ventas -g rg-apps --query principalId -o tsv)
STAGING_MI=$(az webapp identity show --name app-ventas -g rg-apps --slot staging --query principalId -o tsv)

for MI in $PROD_MI $STAGING_MI; do
  az cosmosdb sql role assignment create \
    --account-name cosmos-ventas -g rg-apps \
    --role-definition-id 00000000-0000-0000-0000-000000000002 \
    --principal-id $MI \
    --scope "/"
done

# OPCIÓN 2: User Assigned Identity compartida
# Crear UAMI + asignarla tanto a prod como staging
# Un único rol RBAC cubre ambos slots
```

**Regla:** si usáis Managed Identity + slots, siempre **User Assigned** (UAMI) para evitar este lío.

## Slide 24 — Cost impact: ¿cuánto cuestan los slots?

Confusión común: "¿los slots duplican el coste?"

```
Respuesta corta: NO. Los slots comparten el plan.

Ejemplo:
├── App Service Plan S1 (~€85/mes)
│   ├── Slot production     → ya está pagado en el plan
│   ├── Slot staging        → comparte CPU/memoria del mismo plan
│   └── Slot dev            → idem
└── Coste total: €85/mes (no €255)

PERO OJO: recursos compartidos
├── Los 3 slots corren en la MISMA instancia(s)
├── Si el plan tiene 1 instancia, ambos slots comparten CPU/memoria
├── Si staging hace tests de carga, PRODUCCIÓN SUFRE
└── Por eso conviene: más instancias en el plan si usáis mucho staging

Escalado del plan = escala TODOS los slots:
az appservice plan update --name plan-ventas -g rg-apps --number-of-workers 3
# 3 instancias, repartidas entre slots según tráfico
```

**Conclusión práctica:** slots son "gratis" en términos de coste directo, pero consumen recursos del plan. Si exprimís los slots, subid el plan o las instancias.

## Slide 25 — A/B testing con traffic routing

Más allá de canary (slide 14), podéis hacer **A/B testing** real:

```bash
# Dividir tráfico 50/50 entre production y staging
az webapp traffic-routing set \
  --name app-ventas -g rg-apps \
  --distribution staging=50

# Con varios slots (30% staging, 20% beta, resto production)
az webapp traffic-routing set \
  --name app-ventas -g rg-apps \
  --distribution staging=30 beta=20

# El usuario se asigna a un slot por cookie (ARR Affinity)
# Una vez asignado, sigue en el mismo slot durante la sesión
# Esto garantiza consistencia de experiencia
```

**Patrones de A/B testing:**

```
1. Feature experiment:
   ├── staging tiene feature nueva
   ├── production tiene feature vieja
   ├── 10% tráfico a staging
   └── Comparar métricas (conversion, error rate, engagement)

2. Performance testing:
   ├── staging tiene nueva arquitectura (cache, query optimizado)
   ├── 20% tráfico a staging
   └── Medir latency, throughput con tráfico real

3. UI redesign:
   ├── Production = UI antigua
   ├── staging = UI nueva
   ├── 30% tráfico a staging
   └── Recoger feedback selectivo, medir engagement

A los usuarios se les da opt-out: x-ms-routing-name=self
en URL o cookie para forzar ir siempre al main slot.
```

## Slide 26 — Slots con networking: VNet integration y Private Endpoints

Cada slot puede tener su **propia configuración de red**:

```bash
# VNet integration del slot production
az webapp vnet-integration add \
  --name app-ventas -g rg-apps \
  --vnet vnet-corp --subnet subnet-webapp-prod

# VNet integration del slot staging (subnet distinta típicamente)
az webapp vnet-integration add \
  --name app-ventas -g rg-apps --slot staging \
  --vnet vnet-corp --subnet subnet-webapp-staging

# Private Endpoints: UNO por slot
az network private-endpoint create --name pe-ventas-prod ...
az network private-endpoint create --name pe-ventas-staging ...
```

**Consideraciones importantes:**
- VNet integration NO es sticky setting (hay que configurarla explícitamente por slot)
- Si staging debe conectarse a BBDD de staging (no de prod), la subnet correcta es la de staging
- Al hacer swap, la VNet integration **cambia** entre slots (sigue al código)
- Private DNS debe tener registros para ambos hostnames (prod + staging)

**Regla:** documentad claramente qué recursos de red usa cada slot. Fácil de liar.

## Slide 27 — Slots con diferentes runtimes: migración gradual

Caso real: migrar de .NET 6 a .NET 8 sin downtime:

```bash
# Production está en .NET 6
az webapp config show --name app-ventas -g rg-apps \
  --query netFrameworkVersion   # "v6.0"

# Crear slot staging con .NET 8
az webapp deployment slot create --name app-ventas -g rg-apps --slot staging-net8
az webapp config set --name app-ventas -g rg-apps --slot staging-net8 \
  --linux-fx-version "DOTNETCORE|8.0"

# Deploy código .NET 8 al slot staging
# Test exhaustivo (runtime cambia, puede haber incompatibilidades)

# Si OK, swap
az webapp deployment slot swap --name app-ventas -g rg-apps \
  --slot staging-net8

# Production ahora está en .NET 8
# El slot antiguo queda con .NET 6 — disponible como rollback
```

**Aplica también para:**
- Migración Node 18 → Node 20
- Python 3.10 → 3.12
- PHP 8.2 → 8.3
- Windows → Linux (requiere crear nueva app, no solo slot)

**Limitación importante:** NO se puede cambiar el OS del plan via slot. Si queréis pasar de Windows a Linux, hay que crear un App Service Plan nuevo.

## Slide 28 — Slots en GitHub Actions: workflow completo

Un ejemplo end-to-end de deploy con slots en GitHub Actions:

```yaml
# .github/workflows/deploy.yml
name: Deploy to Azure App Service with Slots
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - run: dotnet publish -c Release -o publish
      - uses: actions/upload-artifact@v4
        with: { name: app, path: publish }

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app, path: publish }
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - uses: azure/webapps-deploy@v3
        with:
          app-name: app-ventas
          slot-name: staging
          package: publish

      # Smoke test después del deploy a staging
      - name: Smoke test staging
        run: |
          sleep 30
          STATUS=$(curl -sf https://app-ventas-staging.azurewebsites.net/health | jq -r .status)
          [ "$STATUS" = "healthy" ] || exit 1

  swap-to-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production   # ← requiere aprobación manual
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - name: Swap slots
        run: az webapp deployment slot swap --name app-ventas -g rg-apps --slot staging

      # Post-swap smoke test
      - name: Verify production
        run: |
          sleep 15
          curl -sf https://app-ventas.azurewebsites.net/health
```

**El `environment: production`** en GitHub Actions permite configurar gates (aprobación manual de un reviewer, wait timer, branch protection) antes del swap.

## Slide 29 — Custom warmup paths: más allá del /health simple

El warmup por defecto llama a `/` de la app. Podéis customizar:

```xml
<!-- applicationHost.xdt en el root de la app -->
<configuration xmlns:xdt="http://schemas.microsoft.com/XML-Document-Transform">
  <system.webServer>
    <applicationInitialization 
        doAppInitAfterRestart="true" 
        skipManagedModules="false">
      <add initializationPage="/health" hostName="localhost" />
      <add initializationPage="/api/productos?limit=1" hostName="localhost" />
      <add initializationPage="/api/categorias" hostName="localhost" />
    </applicationInitialization>
  </system.webServer>
</configuration>
```

```bash
# Alternativa: App Settings
az webapp config appsettings set --name app-ventas -g rg-apps \
  --slot staging \
  --settings \
    WEBSITE_WARMUP_PATH="/health" \
    WEBSITE_SWAP_WARMUP_PING_PATH="/api/ready" \
    WEBSITE_SWAP_WARMUP_PING_STATUSES="200,202"
```

**Estrategia recomendada** para el warmup:

```
1. /health    — validación básica (app arrancada)
2. /api/ready — validación completa:
    - Cosmos DB accesible
    - Service Bus accesible
    - Redis cache conectado
    - Cachés iniciales cargadas
3. /api/productos?limit=1 — warm-up del endpoint más usado
4. /api/categorias — warm-up de otros críticos
```

Cada petición calienta conexiones pooled (Cosmos, Redis, SQL). Sin warmup, los primeros usuarios post-swap ven latencia 3-5x superior.

## Slide 30 — Auto-rollback tras smoke test fallido

Pattern profesional: si tras el swap, `/health` falla durante X minutos, **rollback automático**:

```bash
#!/bin/bash
# scripts/deploy-with-autorollback.sh

APP=app-ventas
RG=rg-apps
URL=https://app-ventas.azurewebsites.net/health

# Swap a producción
echo "Swapping staging → production..."
az webapp deployment slot swap --name $APP -g $RG --slot staging

# Verificación post-swap (5 minutos monitorizando)
TIMEOUT=300   # 5 minutos
INTERVAL=10   # checks cada 10s
ELAPSED=0
FAILURES=0
MAX_FAILURES=3   # 3 fallos consecutivos → rollback

while [ $ELAPSED -lt $TIMEOUT ]; do
  STATUS=$(curl -sf -o /dev/null -w "%{http_code}" $URL || echo "000")
  
  if [ "$STATUS" != "200" ]; then
    FAILURES=$((FAILURES + 1))
    echo "⚠ Health check failed ($FAILURES/$MAX_FAILURES): HTTP $STATUS"
    
    if [ $FAILURES -ge $MAX_FAILURES ]; then
      echo "🚨 Multiple failures. ROLLING BACK..."
      az webapp deployment slot swap --name $APP -g $RG --slot staging
      echo "✓ Rollback complete. Old version restored."
      exit 1
    fi
  else
    FAILURES=0
    echo "✓ Health OK ($ELAPSED/$TIMEOUT sec)"
  fi
  
  sleep $INTERVAL
  ELAPSED=$((ELAPSED + INTERVAL))
done

echo "✓ Deployment successful. 5 min without issues."
```

Este script como parte de vuestro pipeline → protección real contra releases malos.

## Slide 31 — Slot-specific scaling (Premium)

En SKUs Premium v3 podéis escalar slots individualmente:

```bash
# Plan Premium P1v3
az appservice plan update --name plan-ventas -g rg-apps --sku P1v3

# Configurar PerSiteScaling en el plan
az appservice plan update --name plan-ventas -g rg-apps \
  --set perSiteScaling=true

# Ahora cada slot puede tener su propio número de instancias
az webapp config set --name app-ventas -g rg-apps \
  --number-of-workers 5  # production: 5 instancias

az webapp config set --name app-ventas -g rg-apps --slot staging \
  --number-of-workers 1  # staging: 1 instancia (ahorro)
```

**Casos de uso:**
- Producción necesita 5-10 instancias (tráfico real)
- Staging solo necesita 1 (tests manuales, smoke tests)
- Sin PerSiteScaling: ambos slots usarían 5-10, desperdicio de recursos

**Precaución:** cuando se hace swap, las instancias de cada slot se mantienen. Si staging tenía 1 instancia y production 5, tras swap: lo que era staging ahora tiene 5, lo que era production tiene 1. Puede ser problema si la app necesita tiempo para recibir load.

## Slide 32 — Troubleshooting de slots

**El swap tarda mucho (>2 minutos):**
→ El warmup está tardando. Vuestra app tarda en arrancar. Optimizad el tiempo de arranque o configurad un endpoint de warmup más ligero.

**Después del swap, la app apunta a la DB equivocada:**
→ No marcaste la connection string como sticky. Verificad `--slot-settings` vs `--settings`.

**El slot de staging muestra contenido viejo:**
→ Verificad que el despliegue fue al slot correcto (`--slot staging`). Mirad en Kudu del slot: `app-ventas-staging.scm.azurewebsites.net`.

**Error 500 después del swap:**
→ El código nuevo falla con la config de producción. Probablemente una variable que falta o un valor incorrecto. Rollback con swap inverso y revisad la configuración.

**Traffic routing no funciona:**
→ El porcentaje se asigna por sesión (cookie ARRAffinity). Si probáis siempre desde el mismo navegador, puede que siempre os toque el mismo slot. Probad en incógnito o cleared cookies.

## Slide 33 — Cierre del submódulo

Los slots de despliegue transforman vuestro proceso de despliegue de "cruzar los dedos y desplegar a producción" a "probar con calma, verificar todo, y hacer swap sin downtime".

Lo esencial:
- Slots = instancias independientes con su propia URL y config
- Sticky settings para variables dependientes del entorno (DB, logs, App Insights)
- Swap intercambia punteros, no archivos — instantáneo y sin downtime
- Traffic routing para canary deployments graduales
- Rollback = un swap inverso (segundos, no minutos)
- Proteger staging con IP restrictions

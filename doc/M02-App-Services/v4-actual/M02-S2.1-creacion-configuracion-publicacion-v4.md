## Slide 3 — Qué es Azure App Service (de verdad)
App Service es un servicio PaaS de hosting para aplicaciones web, APIs REST y backends móviles. Pero esa definición se queda corta.

Lo que realmente es:
- Un **servidor web gestionado** donde Azure se ocupa del OS, el runtime, los parches, el escalado y el balanceo de carga
- Un **servicio de despliegue** con múltiples métodos (zip, Git, Docker, CI/CD)
- Una **plataforma de ejecución** que soporta .NET, Java, Node.js, Python, PHP y contenedores custom
- Un **entorno integrado** con autenticación, certificados SSL, dominios personalizados, redes virtuales y diagnóstico

No es "una VM que no ves". Es un servicio diseñado específicamente para ejecutar aplicaciones web con todo lo que necesitan en producción.

## Slide 4 — Arquitectura interna de App Service
Entender qué hay por debajo ayuda a diagnosticar problemas:

```
Internet
  ↓
Azure Front Door / Traffic Manager (opcional)
  ↓
Load Balancer (automático en planes Standard+)
  ↓
┌──────────────────────────────────┐
│         App Service Plan         │
│  ┌──────────┐  ┌──────────┐     │
│  │ Instancia │  │ Instancia │ ...│
│  │   (VM)    │  │   (VM)    │    │
│  │┌────────┐│  │┌────────┐│     │
│  ││ Tu App ││  ││ Tu App ││     │
│  │└────────┘│  │└────────┘│     │
│  └──────────┘  └──────────┘     │
└──────────────────────────────────┘
```

**App Service Plan:** El "plan de hosting". Define cuántas instancias hay, qué tamaño tienen y qué features están disponibles.

**Instancias:** Las VMs que ejecutan tu app. Azure las gestiona, las parchea y las reemplaza si fallan.

**Tu App:** Tu código, ejecutándose dentro del sandbox de cada instancia. Si hay 3 instancias, tu app corre en las 3 simultáneamente.

## Slide 5 — App Service Plan: el corazón del hosting
El App Service Plan es la decisión más importante. Define:

**Recursos de cómputo:** CPU, RAM y almacenamiento disponible para tu app.
**Features disponibles:** Slots de despliegue, escalado automático, VNet integration, certificados...
**Coste:** Pagas por el plan, no por la app. Un plan puede alojar múltiples apps.

**Concepto clave:** Múltiples Web Apps pueden compartir el mismo plan. Si tenéis una API y una app web que no consumen mucho, ponerlas en el mismo plan ahorra dinero. Pero si una de ellas es muy intensiva, puede degradar a las demás.

```bash
# Ver qué apps están en un plan
az webapp list \
  --query "[?appServicePlanId.contains(@,'plan-curso')].{nombre:name, estado:state}" \
  --output table
```

## Slide 6 — Tiers de App Service Plan: guía completa

**Free (F1) y Shared (D1) — Solo desarrollo**
- F1: 60 min CPU/día, 1 GB RAM, 1 GB disco
- Sin custom domain (F1), sin SSL personalizado, sin slots
- Comparte recursos con otros tenants
- Uso: prácticas del curso, pruebas rápidas

**Basic (B1, B2, B3) — Desarrollo y testing**
- Instancias dedicadas (no compartidas)
- Custom domain + SSL
- Sin escalado automático, sin slots
- B1: 1 core, 1.75 GB RAM (~13€/mes)
- Uso: desarrollo, apps internas con poco tráfico

**Standard (S1, S2, S3) — Producción**
- Todo lo de Basic +
- Escalado automático (hasta 10 instancias)
- 5 slots de despliegue
- VNet Integration
- S1: 1 core, 1.75 GB RAM (~70€/mes)
- Uso: producción con carga moderada


---

## Slide 7 — Tiers de App Service Plan: los de verdad

**Premium v3 (P1v3, P2v3, P3v3) — Producción exigente**
- Todo lo de Standard +
- Hasta 30 instancias de escalado
- 20 slots de despliegue
- Zone redundancy (alta disponibilidad)
- Hardware más potente (procesadores más rápidos)
- P1v3: 2 cores, 8 GB RAM (~130€/mes)
- Uso: producción con alta carga, SLA exigentes

**Isolated (I1v2, I2v2, I3v2) — Máximo aislamiento**
- App Service Environment (ASE) dedicado
- Red completamente aislada
- Cumplimiento normativo avanzado
- I1v2: desde ~350€/mes + coste del ASE
- Uso: banca, sanidad, gobierno — requisitos de aislamiento

**¿Dónde estáis vosotros?** Probablemente Standard o Premium. Si vuestra app Blazor tiene slots de staging y escalado, como mínimo S1.

## Slide 8 — Eligiendo el tier correcto: árbol de decisión

```
¿Es para producción?
├── NO → F1 o B1 (desarrollo/testing)
│
└── SÍ → ¿Necesitas slots de despliegue?
    ├── NO → B1 (producción ligera, sin downtime deploy)
    │
    └── SÍ → ¿Necesitas escalado automático?
        ├── NO → S1 (slots pero escalado manual)
        │
        └── SÍ → ¿Cuántas instancias necesitas?
            ├── ≤10 → S1/S2/S3
            │
            └── >10 → ¿Necesitas zone redundancy?
                ├── NO → P1v3
                │
                └── SÍ → P1v3 con zone redundancy habilitada
```

**Regla del formador:** Empezad con el tier más bajo que cubra vuestras necesidades. Subir es fácil (zero downtime). Bajar también. No paguéis por features que no usáis.

## Slide 11 — Windows vs Linux: la decisión
App Service puede ejecutar apps en Windows o Linux. La elección importa:

**Windows:**
- Soporte nativo para .NET Framework (versiones antiguas: 4.x)
- IIS como servidor web por debajo
- Remote Desktop para depuración avanzada (planes Premium)
- Soporte para WebJobs
- Ligeramente más caro

**Linux:**
- Más ligero y rápido en arranque
- Sin licencia de OS (ligeramente más barato)
- Soporte para contenedores Docker nativos
- SSH directo a la instancia
- No soporta .NET Framework (solo .NET Core / .NET 5+)

**¿Cuál elegir?**
- Si usáis .NET 8+: ambos valen. Linux es la tendencia.
- Si tenéis dependencias de .NET Framework 4.x: Windows obligatorio.
- Si usáis contenedores Docker: Linux.
- Si tenéis WebJobs existentes: Windows.

## Slide 12 — Configuración general de la Web App
Después de crear la app, hay que configurarla. Las settings más importantes:

**General Settings (Configuration → General):**
```bash
# Stack y versión del runtime
az webapp config set \
  --name mi-app \
  --resource-group mi-rg \
  --net-framework-version v8.0

# Always On (mantener la app cargada — requiere Basic+)
az webapp config set \
  --name mi-app \
  --resource-group mi-rg \
  --always-on true

# Tipo de plataforma (32/64 bits)
az webapp config set \
  --name mi-app \
  --resource-group mi-rg \
  --use-32bit-worker-process false
```

**Always On** es crítico en producción. Sin él, App Service descarga tu app después de 20 minutos de inactividad. La siguiente petición tarda más porque tiene que arrancar desde cero (cold start).


---

## Slide 13 — Always On: por qué importa tanto
Profundicemos en Always On porque genera confusión:

**Sin Always On (tier Free y Shared):**
- App Service descarga la app tras 20 min sin peticiones
- La primera petición después de la descarga sufre cold start (5-30 segundos)
- Ideal para desarrollo (no pagas por mantener la app viva)

**Con Always On (tier Basic+):**
- App Service envía un ping periódico a la app para mantenerla cargada
- Sin cold start: cada petición se atiende inmediatamente
- Obligatorio para producción, WebJobs y tareas en background

**Con Always On + Health Check (recomendado):**
```bash
az webapp config set \
  --name mi-app \
  --resource-group mi-rg \
  --always-on true

# Configurar health check path
az webapp config set \
  --name mi-app \
  --resource-group mi-rg \
  --generic-configurations '{"healthCheckPath": "/health"}'
```

El health check hace que App Service envíe pings al endpoint `/health` en vez de a la raíz. Si la app responde con 200, está viva. Si no, App Service la reinicia automáticamente.

## Slide 14 — Documento de la aplicación (wwwroot)
App Service sirve tu app desde un directorio raíz. Entender la estructura es útil para depuración:

**Windows (IIS):**
```
D:\home\site\wwwroot\          ← Tu app publicada va aquí
D:\home\LogFiles\              ← Logs de la aplicación
D:\home\data\                  ← Datos persistentes (WebJobs, etc.)
D:\local\Temp\                 ← Archivos temporales (no persistente)
```

**Linux:**
```
/home/site/wwwroot/            ← Tu app publicada va aquí
/home/LogFiles/                ← Logs de la aplicación
/home/                         ← Almacenamiento persistente
/tmp/                          ← Temporal (no persistente)
```

**Consola de depuración (Kudu):**
```bash
# Abrir Kudu (panel de administración avanzado)
az webapp browse --name mi-app --resource-group mi-rg
# Ir a: https://mi-app.scm.azurewebsites.net

# O desde CLI: abrir SSH directo (Linux)
az webapp ssh --name mi-app --resource-group mi-rg
```

Kudu es extremadamente útil para depuración: podéis ver los archivos desplegados, revisar variables de entorno, ejecutar comandos y descargar logs.

## Slide 16 — Zip Deploy: el método estándar
El despliegue más usado en scripts y pipelines:

```bash
# 1. Publicar la app
dotnet publish -c Release -o ./publish

# 2. Comprimir
cd publish && zip -r ../app.zip . && cd ..

# 3. Desplegar
az webapp deploy \
  --resource-group mi-rg \
  --name mi-app \
  --src-path app.zip \
  --type zip

# 4. Verificar
az webapp browse --name mi-app --resource-group mi-rg
```

**Qué pasa por detrás:**
1. El zip se sube al endpoint de Kudu (`/api/zipdeploy`)
2. Kudu extrae el contenido en `wwwroot`
3. La app se reinicia automáticamente
4. El tráfico se dirige a la nueva versión

**Tiempo de despliegue:** Depende del tamaño. Una app .NET típica (20-50 MB) tarda 30-90 segundos.


---

## Slide 17 — Run from Package: el método de producción
Run from Package es el método recomendado para producción:

```bash
# Configurar la app para ejecutar desde paquete
az webapp config appsettings set \
  --name mi-app \
  --resource-group mi-rg \
  --settings WEBSITE_RUN_FROM_PACKAGE=1

# Desplegar
az webapp deploy \
  --resource-group mi-rg \
  --name mi-app \
  --src-path app.zip \
  --type zip
```

**¿Qué cambia?**
- El zip NO se extrae. La app se ejecuta directamente desde el paquete.
- `wwwroot` es de solo lectura. La app no puede escribir en su propio directorio.
- El despliegue es atómico: funciona la versión anterior hasta que la nueva está lista al 100%.
- Arranque más rápido (no hay paso de extracción).

**Trade-off:** Tu app no puede crear archivos en `wwwroot`. Si lo necesitas (logs locales, archivos temporales), usa `/home/data/` o almacenamiento externo (Blob Storage).

## Slide 18 — Git Deploy: despliegue desde un push
App Service tiene su propio repositorio Git integrado:

```bash
# Configurar despliegue por Git local
az webapp deployment source config-local-git \
  --name mi-app \
  --resource-group mi-rg

# Resultado: devuelve una URL tipo
# https://mi-app.scm.azurewebsites.net:443/mi-app.git

# Añadir como remote
git remote add azure <url-que-devolvió>

# Desplegar con push
git push azure main
```

**Qué pasa por detrás:**
1. Push al repo de Kudu
2. Kudu detecta el tipo de proyecto (por el `.csproj`, `package.json`, etc.)
3. Ejecuta el build automáticamente (`dotnet build`, `npm install`, etc.)
4. Copia el resultado a `wwwroot`
5. Reinicia la app

**Ventaja:** Muy cómodo para desarrollo — push y listo.
**Desventaja:** El build ocurre en la instancia de App Service, consumiendo sus recursos. En producción, haced el build en un pipeline y desplegad el artefacto compilado.

## Slide 20 — Custom Domains: tu propio dominio
Por defecto, tu app vive en `mi-app.azurewebsites.net`. Para producción necesitas tu dominio:

**Configurar un custom domain:**
```bash
# 1. Añadir el hostname
az webapp config hostname add \
  --webapp-name mi-app \
  --resource-group mi-rg \
  --hostname www.midominio.com

# 2. Verificar (necesitas un registro CNAME o TXT en tu DNS)
az webapp config hostname list \
  --webapp-name mi-app \
  --resource-group mi-rg \
  --output table
```

**Registros DNS necesarios:**
- **CNAME:** `www` → `mi-app.azurewebsites.net` (para subdominios)
- **A record:** `@` → IP de App Service + TXT de verificación (para dominio raíz)

**Requiere tier Basic o superior.** El tier Free no soporta custom domains.

## Slide 21 — HTTPS y certificados SSL
En producción, HTTPS es obligatorio. App Service facilita la configuración:

**Opción 1 — Certificado gratuito gestionado por Azure:**
```bash
az webapp config ssl create \
  --name mi-app \
  --resource-group mi-rg \
  --hostname www.midominio.com
```
Gratuito, renovación automática. Solo funciona con subdominios (www.x.com, api.x.com), no con dominio raíz (x.com).

**Opción 2 — Certificado propio:**
```bash
# Subir certificado PFX
az webapp config ssl upload \
  --name mi-app \
  --resource-group mi-rg \
  --certificate-file ./certificado.pfx \
  --certificate-password "contraseña"

# Vincular al hostname
az webapp config ssl bind \
  --name mi-app \
  --resource-group mi-rg \
  --certificate-thumbprint <thumbprint> \
  --ssl-type SNI
```

**Opción 3 — App Service Certificate (comprado a través de Azure):**
Azure lo compra, lo configura, lo renueva. Todo automático. Precio: ~70€/año.

**Forzar HTTPS:**
```bash
az webapp update \
  --name mi-app \
  --resource-group mi-rg \
  --https-only true
```

## Slide 22 — Networking: cómo llega el tráfico a tu app

```
Usuario
  ↓ (HTTPS)
Azure Front Door / Application Gateway (opcional)
  ↓
App Service (load balancer interno)
  ↓
Instancia(s) de tu app
  ↓ (conexión saliente)
Cosmos DB / SQL / APIs externas
```

**Acceso entrante (inbound):**
- Por defecto, tu app es pública en internet
- Puedes restringir con IP restrictions, Private Endpoints o VNet Integration

**Acceso saliente (outbound):**
- Tu app se conecta a internet por las IPs de salida del App Service Plan
- Si necesitas acceder a recursos privados (VNet, on-premises): VNet Integration

```bash
# Ver las IPs de salida de tu app
az webapp show \
  --name mi-app \
  --resource-group mi-rg \
  --query outboundIpAddresses \
  --output tsv
```

Útil si necesitas añadir IPs a una whitelist de un servicio externo.

## Slide 23 — Restricciones de acceso (IP Restrictions)
Limitar quién puede acceder a tu app:

```bash
# Permitir solo una IP (por ejemplo, la oficina)
az webapp config access-restriction add \
  --name mi-app \
  --resource-group mi-rg \
  --rule-name "oficina" \
  --action Allow \
  --ip-address 203.0.113.50/32 \
  --priority 100

# Bloquear todo lo demás (regla por defecto)
az webapp config access-restriction set \
  --name mi-app \
  --resource-group mi-rg \
  --default-action Deny

# Ver reglas actuales
az webapp config access-restriction show \
  --name mi-app \
  --resource-group mi-rg \
  --output table
```

**Casos de uso:**
- Limitar staging a IPs de la oficina
- Proteger endpoints de administración
- Restringir acceso durante mantenimiento

**Importante:** Las restricciones de IP aplican al sitio principal (SCM/Kudu sigue accesible). Para restringir Kudu también, usad la opción `--scm-site`.

## Slide 25 — Diagnóstico avanzado: Kudu y App Service Diagnostics
Cuando los logs no bastan:

**Kudu (SCM):** `https://mi-app.scm.azurewebsites.net`
- Process explorer: ver procesos, CPU, memoria en tiempo real
- Debug console: terminal en el navegador, navegar por el sistema de archivos

**App Service Diagnostics (portal):**
1. Portal → Tu App Service → "Diagnose and solve problems"
2. Escenarios predefinidos: crashes, rendimiento, SSL, disponibilidad
3. Detector inteligente: analiza logs y métricas para sugerir causas
4. Health check reports: resultado de los health checks configurados

**Metrics (Azure Monitor):**
```bash
# Ver métricas de la app
az monitor metrics list \
  --resource /subscriptions/<id>/resourceGroups/mi-rg/providers/Microsoft.Web/sites/mi-app \
  --metric "CpuPercentage,MemoryPercentage,Http5xx" \
  --interval PT1H
```

## Slide 26 — Logging desde tu código .NET
Integrar logging en tu aplicación para que aparezca en los logs de App Service:

```csharp
var builder = WebApplication.CreateBuilder(args);

// El logging está configurado por defecto en ASP.NET Core
// Los logs van automáticamente a App Service cuando está habilitado
builder.Logging.AddAzureWebAppDiagnostics();

var app = builder.Build();

app.MapGet("/", (ILogger<Program> logger) =>
{
    logger.LogInformation("Petición recibida en el endpoint raíz");
    
    try
    {
        // Tu lógica
        return Results.Ok(new { status = "ok" });
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Error procesando la petición");
        return Results.Problem("Error interno");
    }
});
```

**Niveles de log:**
- `LogTrace` / `LogDebug`: desarrollo (no habilitéis en producción)
- `LogInformation`: eventos normales
- `LogWarning`: algo inesperado pero no crítico
- `LogError` / `LogCritical`: errores que necesitan atención

**Paquete necesario:**
```bash
dotnet add package Microsoft.Extensions.Logging.AzureAppServices
```

## Slide 27 — CORS: Cross-Origin Resource Sharing
Si vuestra API es consumida por un frontend en otro dominio:

```bash
# Permitir un origen específico
az webapp cors add \
  --name mi-api \
  --resource-group mi-rg \
  --allowed-origins "https://mi-frontend.com"

# Permitir múltiples orígenes
az webapp cors add \
  --name mi-api \
  --resource-group mi-rg \
  --allowed-origins "https://mi-frontend.com" "https://staging.mi-frontend.com"

# Ver CORS configurado
az webapp cors show \
  --name mi-api \
  --resource-group mi-rg

# Permitir todos los orígenes (SOLO desarrollo, NUNCA producción)
az webapp cors add \
  --name mi-api \
  --resource-group mi-rg \
  --allowed-origins "*"
```

**O desde código (más control):**
```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("MiFrontend", policy =>
    {
        policy.WithOrigins("https://mi-frontend.com")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});

app.UseCors("MiFrontend");
```

**Consejo:** Configurad CORS en App Service para reglas simples y en código para reglas complejas (headers específicos, credentials, métodos).

## Slide 28 — Backup y restauración
App Service incluye backup integrado (tier Standard+):

```bash
# Configurar backup automático
az webapp config backup create \
  --webapp-name mi-app \
  --resource-group mi-rg \
  --container-url "https://mistorage.blob.core.windows.net/backups?sv=..." \
  --backup-name "backup-$(date +%Y%m%d)"

# Configurar backup programado
az webapp config backup update \
  --webapp-name mi-app \
  --resource-group mi-rg \
  --container-url "https://mistorage.blob.core.windows.net/backups?sv=..." \
  --frequency 1d \
  --retain-one true \
  --retention 30

# Restaurar desde backup
az webapp config backup restore \
  --webapp-name mi-app \
  --resource-group mi-rg \
  --container-url "https://mistorage.blob.core.windows.net/backups?sv=..." \
  --backup-name "backup-20250615"
```

**¿Qué incluye el backup?**
- Configuración de la app
- Contenido del sistema de archivos (wwwroot)
- Opcionalmente: bases de datos vinculadas

**Importante:** El backup de App Service NO sustituye un backup de la base de datos. Cosmos DB y SQL tienen sus propios mecanismos de backup que debéis configurar por separado.

## Slide 29 — WebJobs: tareas en segundo plano
WebJobs ejecutan scripts o programas como tareas en segundo plano dentro de tu App Service:

**Tipos:**
- **Continuous:** Se ejecutan siempre. Ideal para colas y procesamiento en background.
- **Triggered:** Se ejecutan por schedule (CRON) o manualmente.

**¿WebJobs o Azure Functions?**

- WebJobs: si la tarea necesita acceso al mismo entorno que la app web, comparte el mismo plan

## Slide 32 — Troubleshooting: problemas comunes en producción

**Cold start lento:**
→ Activar Always On. Si persiste, revisa las dependencias en el arranque (conexiones a DB, carga de configuración).

**Error 503 intermitente:**
→ La app está crasheando y App Service la reinicia. Revisa logs. Causas comunes: out of memory, excepciones no capturadas en el arranque.

**Lentitud gradual:**
→ Memory leak. Revisa el consumo de memoria en Kudu → Process Explorer. Cada despliegue "limpia" el problema temporalmente.

**Error SNAT exhaustion:**
→ Demasiadas conexiones salientes. Usa HttpClient singleton, connection pooling en DB, y revisa si estás abriendo conexiones sin cerrarlas.

**Despliegue exitoso pero la app no cambia:**
→ Caché. Hard refresh (Ctrl+Shift+R). Si el problema persiste, verifica en Kudu que los archivos son los correctos en wwwroot.

## Slide 33 — App Service Environment (ASE v3): tier aislado enterprise

ASE (App Service Environment) es una versión **aislada** de App Service, corriendo en una VNet dedicada de vuestra suscripción:

```
App Service normal (multi-tenant):
├── Vuestro plan corre en infraestructura compartida con otros clientes
├── Limitaciones de red (IPs compartidas, SNAT ports limitados)
├── SKUs: F1, B1, S1, P1v3, P2v3, P3v3

App Service Environment v3 (single-tenant):
├── Dedicado a UN cliente (vosotros)
├── Dentro de vuestra VNet (aislamiento total de red)
├── SKUs especiales: I1v2, I2v2, I3v2 (Isolated)
├── Hasta 100 apps por ASE
├── Deploy interno o con IP pública
└── ~€2.500-3.500/mes base + coste de instancias
```

**Cuándo usar ASE:**
- Compliance estricto (PCI DSS, HIPAA, FedRAMP) que requiere aislamiento
- Apps que necesitan acceso a recursos on-premises por ExpressRoute
- Tráfico muy alto (evitar límites SNAT del multi-tenant)
- Custom hardware needs

**Cuándo NO:** para el 95% de apps, App Service normal es suficiente. ASE es caro y complejo.

## Slide 34 — Web App for Containers: deploy Docker directo

Si vuestra app está dockerizada, App Service puede correrla directamente como container:

```bash
# Crear App Service Linux configurado para container
az appservice plan create --name plan-container -g rg-apps \
  --is-linux --sku B1

az webapp create \
  --name app-miapi-container \
  --plan plan-container \
  -g rg-apps \
  --deployment-container-image-name myregistry.azurecr.io/miapi:v1.0

# Configurar autenticación a ACR (Managed Identity)
az webapp identity assign --name app-miapi-container -g rg-apps

# Asignar rol AcrPull al MI del App Service
PRINCIPAL_ID=$(az webapp identity show --name app-miapi-container -g rg-apps --query principalId -o tsv)
ACR_ID=$(az acr show --name myregistry --query id -o tsv)
az role assignment create --assignee $PRINCIPAL_ID --role AcrPull --scope $ACR_ID

# Habilitar continuous deployment (ACR webhook → App Service)
az webapp deployment container config \
  --name app-miapi-container \
  -g rg-apps \
  --enable-cd true
```

**Beneficios vs deploy tradicional:**
- Misma imagen en dev/staging/prod (reproducibilidad)
- Deploy de dependencias nativas (paquetes Linux, binarios específicos)
- Control total del runtime (versión .NET exacta, tweaks del OS)
- Más rápido escalar (imagen ya cacheada)

**Consideraciones:** ligeramente más slow cold start, requiere ACR (coste adicional).

## Slide 35 — App Service vs Container Apps vs Functions: decisión

Tres servicios de cómputo Azure, y es frecuente no saber cuál elegir:

| | App Service | Container Apps | Functions |
|---|---|---|---|
| Unidad de deploy | App/container | Container | Función |
| Runtime | .NET, Node, Python, etc. | Cualquier container | .NET, Node, Python, Java |
| Always-on | Sí (B1+) | Scale to zero opcional | Scale to zero (Consumption) |
| Escalado max | 30 instancias | Ilimitado (KEDA) | 200 (Consumption) |
| Cold start | Bajo (con Always On) | Medio (cold scale) | Alto en Consumption |
| Precio base | Fijo por plan | Por CPU-seg + mem-seg | Por ejecución + GB-seg |
| Use case | APIs REST, Blazor, web apps | Microservicios, containers | Event-driven, batch, cron |
| Managed Kubernetes | No | Sí (implícito) | No |

**Árbol de decisión simple:**
```
¿Tu workload es event-driven o con tráfico esporádico?
 └── SÍ → Functions
 └── NO → 
    ¿Necesitas microservicios con scale-to-zero?
     └── SÍ → Container Apps
     └── NO → App Service (lo más simple y maduro)
```

Este curso usa App Service como ejemplo principal. En M3-M4 veremos Functions. Container Apps es el camino si vuestra empresa abraza containers.

## Slide 37 — Private Endpoints: aislamiento de red real

Por defecto, App Service es accesible desde Internet. Para exponer la app **solo** dentro de vuestra VNet:

```bash
# 1. Crear private endpoint que expone App Service en VNet interna
az network private-endpoint create \
  --name pe-app-ventas \
  -g rg-apps \
  --vnet-name vnet-corp \
  --subnet subnet-private-endpoints \
  --private-connection-resource-id $(az webapp show --name app-ventas -g rg-apps --query id -o tsv) \
  --group-id sites \
  --connection-name app-ventas-connection

# 2. Deshabilitar acceso público a la App
az webapp update --name app-ventas -g rg-apps \
  --set publicNetworkAccess=Disabled

# 3. Configurar DNS privado para resolver el nombre
az network private-dns zone create --name "privatelink.azurewebsites.net" -g rg-apps
az network private-dns link vnet create --name "link-ventas" \
  -g rg-apps --zone-name "privatelink.azurewebsites.net" \
  --virtual-network vnet-corp --registration-enabled false
```

**Resultado:** `app-ventas.azurewebsites.net` resuelve a IP pública (accesible desde Internet). **DESDE DENTRO de la VNet**, resuelve a IP privada. Así una gateway/API Management puede exponerla controladamente sin que sea directamente accesible desde fuera.

**Service Endpoints vs Private Endpoints** (diferencia importante):

| | Service Endpoints | Private Endpoints |
|---|---|---|
| Nivel | VNet → servicio Azure | Servicio Azure → VNet |
| IP del servicio | Sigue siendo pública | IP privada en tu VNet |
| Cross-region | No (misma región) | Sí |
| Coste | Gratis | ~€0.01/hora por PE |
| Uso típico | "Mi VNet puede ver este Storage" | "Storage tiene IP privada en mi VNet" |

**Recomendación enterprise:** Private Endpoints. Más aislamiento, mejor compliance.

## Slide 38 — ARR Affinity / session affinity: sticky sessions

Cuando tenéis **múltiples instancias** de App Service, por defecto Azure usa "cookie-based affinity" para enviar al mismo usuario siempre a la misma instancia:

```bash
# Ver el estado actual
az webapp show --name app-ventas -g rg-apps --query clientAffinityEnabled

# Deshabilitar ARR Affinity (RECOMENDADO para la mayoría)
az webapp update --name app-ventas -g rg-apps \
  --client-affinity-enabled false
```

**Por qué ARR Affinity está activada por defecto:**
- Soporta apps stateful antiguas (in-memory session state)
- Histórico de App Service cuando nació

**Por qué deberíais deshabilitarla:**
- Apps modernas **deben** ser stateless (sessions en Redis/Cosmos/SQL)
- Previene distribución uniforme de carga
- Si una instancia cae, usuarios afectados pierden sesión
- ARR cookie es un bloqueo innecesario

**Regla:** deshabilitar siempre. Si vuestra app se rompe sin ARR, hay un bug — arregladlo. En M5 veréis cómo mover session state a Redis.

## Slide 43 — Deploy failures: debugging paso a paso

Un deploy falla. Así debéis diagnosticar:

```bash
# 1. Mirar el log de deploy más reciente
az webapp log deployment show \
  --name app-ventas -g rg-apps \
  --deployment-id <id-del-deploy>

# 2. Si usáis Kudu / SCM, acceder al log completo
# https://<app>.scm.azurewebsites.net/api/deployments/latest/log
#  → Basic auth con publishing credentials

# 3. Common issues y soluciones:
#
# ERROR: "Application startup failed"
#   → log de stdout en Kudu (Log Files > LogFiles/)
#   → revisar appsettings.json, env vars
#
# ERROR: "HTTP 503 Service Unavailable"
#   → App no arrancó o health check falló
#   → verificar logs startup + memoria disponible
#
# ERROR: "ENOSPC" / "no space left on device"
#   → /home está lleno (logs + deployments antiguos)
#   → Kudu Debug Console → eliminar /home/LogFiles/* viejos
#
# ERROR: "Timeout during deployment"
#   → artifact muy grande + instance pequeña
#   → Run From Package (azcopy zip a blob) en lugar de zip deploy directo
#
# ERROR: "Failed to fetch container image"
#   → ACR auth (MI + AcrPull role assignment)
```

**Tip para debugging complejo:** activar "Failed Request Tracing" temporalmente. Kudu captura request fallidos con stack traces completos. No dejarlo activo (consume espacio).

## Slide 44 — Checklist de publicación en producción

Antes de poner una app en producción en App Service:

- [ ] Tier Standard o superior (con slots y escalado)
- [ ] Always On activado
- [ ] Health Check configurado (`/health`)
- [ ] HTTPS forzado (`--https-only true`)
- [ ] Custom domain + certificado SSL
- [ ] Variables sensibles en App Settings (no en código)
- [ ] Connection strings en Key Vault (no en App Settings en texto plano)
- [ ] CORS configurado solo para los orígenes necesarios
- [ ] Logs de aplicación habilitados
- [ ] Application Insights conectado (módulo 8)
- [ ] Backup configurado
- [ ] IP restrictions en staging (solo oficina)
- [ ] Run from Package habilitado
- [ ] Resource Lock en el RG de producción

No hace falta todo el primer día. Pero cada ítem que falta es un riesgo que aceptáis.

## Slide 45 — Cierre del submódulo
App Service parece simple — "sube tu código y funciona". Y es verdad que el caso básico es así de fácil. Pero la diferencia entre un despliegue que funciona y uno que funciona bien en producción son estos 30+ detalles de configuración que hemos cubierto.

Lo esencial de este submódulo:
- El App Service Plan define los recursos y las features disponibles
- Elegid el tier más bajo que cubra vuestras necesidades y subid cuando haga falta
- Zip Deploy para scripts, Run from Package para producción
- Always On + Health Check son obligatorios en producción
- Los logs y Kudu son vuestros mejores amigos cuando algo falla

En el siguiente submódulo entramos en slots de despliegue: cómo tener staging y producción en la misma app sin downtime.

## Slide 2 — Dos tipos de escalado
Azure App Service soporta dos formas de escalar:

**Escalado vertical (scale up):** Cambiar a un plan más potente.
- De B1 (1 core, 1.75 GB) a S1 (1 core, 1.75 GB + más features)
- O de S1 a P1v3 (2 cores, 8 GB)
- Más potencia por instancia. Tiene un techo.

**Escalado horizontal (scale out):** Añadir más instancias del mismo plan.
- De 1 instancia a 3, o a 10
- Cada instancia ejecuta una copia de tu app
- El load balancer distribuye el tráfico entre instancias
- Puede ser manual o automático

```
Scale Up (vertical):                Scale Out (horizontal):
┌───────────┐                       ┌──────┐ ┌──────┐ ┌──────┐
│           │                       │ App  │ │ App  │ │ App  │
│  App      │    →                  │ (1)  │ │ (2)  │ │ (3)  │
│  (grande) │                       └──────┘ └──────┘ └──────┘
│           │                            ↑       ↑       ↑
└───────────┘                       ┌────────────────────────┐
Más CPU/RAM por                     │    Load Balancer       │
instancia                          └────────────────────────┘
                                    Más instancias iguales
```

## Slide 3 — Scale up: cuándo subir de plan

```bash
# Ver el plan actual
az appservice plan show \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --query "{nombre:name, sku:sku.name, tier:sku.tier, workers:sku.capacity}" \
  --output table

# Subir de plan (zero downtime)
az appservice plan update \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --sku S1

# Bajar de plan (también zero downtime)
az appservice plan update \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --sku B1
```

**Cuándo subir:**
- Necesitáis features que el plan actual no tiene (slots → S1+, zone redundancy → P1v3+)
- La app consume más CPU/RAM de lo que la instancia ofrece
- Necesitáis más conexiones simultáneas o WebSockets

**Cuándo bajar:**
- Después de un pico temporal (Black Friday, lanzamiento)
- Recursos infrautilizados (CPU < 20% sostenido)
- Al pasar de producción a modo mantenimiento

**El cambio es instantáneo y sin downtime.** Azure mueve tu app a instancias del nuevo tamaño de forma transparente.

## Slide 4 — Scale out manual: añadir instancias

```bash
# Ver instancias actuales
az appservice plan show \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --query "sku.capacity"
# Resultado: 1

# Escalar a 3 instancias
az appservice plan update \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --number-of-workers 3

# Verificar
az appservice plan show \
  --name plan-ventas-prod \
  --resource-group rg-ventas-prod \
  --query "sku.capacity"
# Resultado: 3
```

**Qué pasa al escalar:**
1. Azure crea 2 instancias adicionales con tu app
2. El load balancer empieza a distribuir tráfico a las 3
3. Las peticiones se reparten automáticamente (round-robin con session affinity opcional)

**Coste:** Lineal. 3 instancias S1 = 3× el precio de 1 instancia S1.

## Slide 5 — Escalado automático (autoscale): la magia

El escalado automático añade y quita instancias basándose en reglas que definís:

**Requiere tier Standard (S1) o superior.**

**Componentes de una regla de autoscale:**
1. **Métrica:** Qué medir (CPU, memoria, peticiones HTTP, longitud de cola...)
2. **Condición:** Cuándo actuar (CPU > 70% durante 5 minutos)
3. **Acción:** Qué hacer (añadir 1 instancia, o escalar a N instancias)
4. **Cooldown:** Cuánto esperar antes de volver a evaluar (evitar oscilaciones)

```
Tráfico sube → CPU > 70% durante 5 min → Añadir 1 instancia → Esperar 5 min
Tráfico baja → CPU < 30% durante 10 min → Quitar 1 instancia → Esperar 5 min
```

## Slide 6 — Configurar autoscale desde CLI

```bash
# Crear regla de escalado automático
az monitor autoscale create \
  --resource-group rg-ventas-prod \
  --resource plan-ventas-prod \
  --resource-type Microsoft.Web/serverfarms \
  --name "autoscale-ventas" \
  --min-count 1 \
  --max-count 5 \
  --count 1

# Regla: escalar UP cuando CPU > 70% durante 5 minutos
az monitor autoscale rule create \
  --resource-group rg-ventas-prod \
  --autoscale-name "autoscale-ventas" \
  --condition "Percentage CPU > 70 avg 5m" \
  --scale out 1

# Regla: escalar DOWN cuando CPU < 30% durante 10 minutos
az monitor autoscale rule create \
  --resource-group rg-ventas-prod \
  --autoscale-name "autoscale-ventas" \
  --condition "Percentage CPU < 30 avg 10m" \
  --scale in 1
```

**Parámetros clave:**
- `--min-count 1`: nunca bajar de 1 instancia
- `--max-count 5`: nunca subir de 5 (limita el coste)
- `--count 1`: empezar con 1 instancia
- `avg 5m`: media de los últimos 5 minutos (evita picos momentáneos)

## Slide 7 — Métricas disponibles para autoscale

| Métrica | Cuándo usarla | Threshold típico |
|---------|--------------|-------------------|
| **CPU Percentage** | Apps CPU-bound (procesamiento, cálculos) | Up: >70%, Down: <30% |
| **Memory Percentage** | Apps memory-bound (caché, procesamiento de archivos) | Up: >80%, Down: <40% |
| **Http Queue Length** | Peticiones esperando ser procesadas | Up: >10, Down: <2 |
| **Data In / Data Out** | Apps con mucho tráfico de red | Depende del caso |
| **Requests** | Volumen de peticiones por instancia | Up: >1000/min, Down: <100/min |
| **Custom metric** | Métricas de Application Insights | Definida por ti |

**Recomendación para la mayoría de apps web:**
Empezad con CPU Percentage. Es la métrica más universal y predecible. Añadid Http Queue Length si veis que la cola crece antes de que la CPU suba (típico de apps I/O-bound).

## Slide 9 — Patrones de escalado

**Patrón 1 — Reactivo (solo métricas):**
```
Min: 1, Max: 10
CPU > 70% → +1 instancia
CPU < 30% → -1 instancia
```
Simple y efectivo. La app escala cuando la demanda sube. Desventaja: hay un retraso de 5-10 minutos hasta que la nueva instancia está lista.

**Patrón 2 — Predictivo (horarios + métricas):**
```
Lunes-Viernes 8-20h: Min 3, Max 10
Resto: Min 1, Max 5
CPU > 70% → +1 adicional
```
Combina predicción (sabéis cuándo hay más tráfico) con reactividad. Mejor para apps con patrones regulares.

**Patrón 3 — Eventos (escalado manual pre-evento):**
```
Normal: Min 2, Max 5
Black Friday (manual): Min 10, Max 20
```
Para picos conocidos, escaláis manualmente antes del evento y volvéis después.

## Slide 10 — El load balancer: cómo se reparte el tráfico

Cuando tenéis varias instancias, Azure distribuye automáticamente:

```
Internet → Azure Load Balancer → Instancia 1 (33%)
                                → Instancia 2 (33%)
                                → Instancia 3 (33%)
```

**Session Affinity (ARR Affinity):**
Por defecto, App Service usa cookies ARRAffinity para mantener a un usuario en la misma instancia durante su sesión.

```bash
# Ver si ARR Affinity está habilitado
az webapp show --name app-ventas -g rg-ventas-prod \
  --query "clientAffinityEnabled"

# Desactivar (recomendado para APIs stateless)
az webapp update --name app-ventas -g rg-ventas-prod \
  --client-affinity-enabled false
```

**¿Desactivar o no?**
- APIs stateless (sin sesión): **desactivar**. Mejor distribución de carga.
- Apps con sesión en memoria (Blazor Server): **mantener activado** o migrar sesión a Redis.
- Apps con sesión en base de datos o Redis: **desactivar**. Cualquier instancia puede atender.

## Slide 11 — Aplicaciones stateless vs stateful

Para que el escalado funcione bien, vuestra app debería ser **stateless**:

**Stateless (escala sin problemas):**
- No guarda estado en memoria entre peticiones
- Cada petición se puede atender por cualquier instancia
- Sesión en base de datos, Redis o cookie cifrada

**Stateful (problemas al escalar):**
- Guarda datos en variables estáticas o en memoria
- La sesión vive en el proceso de la app
- Si el usuario va a otra instancia, pierde la sesión

**¿Vuestra app Blazor es stateful?**
- Blazor Server: stateful por diseño (mantiene un circuito SignalR). Necesita ARR Affinity o sticky sessions.
- Blazor WebAssembly: stateless en el servidor (el estado vive en el navegador).

**Si es Blazor Server y necesitáis escalar:**
1. Opción A: ARR Affinity activado (cada usuario siempre en la misma instancia)
2. Opción B: Azure SignalR Service (gestiona los circuitos de forma distribuida)
3. Opción C: Migrar a Blazor WASM para el frontend (el servidor se vuelve una API stateless)

## Slide 12 — Múltiples apps en un mismo plan

Un App Service Plan puede alojar varias Web Apps:

```
App Service Plan (S1, 3 instancias)
├── app-ventas-web    (Blazor frontend)
├── app-ventas-api    (API backend)
└── func-ventas       (Functions)
```

**Ventaja:** Ahorro de coste — un plan para varias apps.

**Desventaja:** Comparten recursos. Si la API consume mucha CPU, el frontend se degrada.

**Cuándo compartir plan:**
- Apps pequeñas con poco tráfico
- Apps que se complementan (frontend + API del mismo proyecto)
- Desarrollo y testing

**Cuándo separar:**
- Apps con patrones de carga muy diferentes
- Apps que necesitan escalar independientemente
- Producción crítica donde el aislamiento importa

```bash
# Ver qué apps están en un plan
az webapp list \
  --query "[?appServicePlanId.contains(@,'plan-ventas')].{nombre:name, estado:state}" \
  --output table

# Mover una app a otro plan
az webapp update --name app-ventas-api -g rg-ventas-prod \
  --set serverFarmId=/subscriptions/<id>/resourceGroups/rg-ventas-prod/providers/Microsoft.Web/serverfarms/plan-api-prod
```

## Slide 13 — Density check: ¿cuántas apps caben?

No hay un límite duro de apps por plan, pero hay límites prácticos:

**Señales de que el plan está sobrecargado:**
- CPU sostenida > 80% (no por picos, por media)
- Memory > 85% sostenido
- Http Queue Length creciendo
- Tiempos de respuesta degradándose

```bash
# Monitorizar el plan
az monitor metrics list \
  --resource "/subscriptions/<id>/resourceGroups/rg-prod/providers/Microsoft.Web/serverfarms/plan-prod" \
  --metric "CpuPercentage" "MemoryPercentage" \
  --interval PT1H \
  --output table
```

**Regla práctica:**
- Tier B1 (1 core, 1.75 GB): 2-3 apps ligeras
- Tier S1 (1 core, 1.75 GB): 3-5 apps ligeras (con autoscale)
- Tier P1v3 (2 cores, 8 GB): 5-10 apps medianas

## Slide 14 — Alertas de escalado

Configurad alertas para saber cuándo escala y cuándo se acerca al límite:

```bash
# Alerta cuando se alcanza el máximo de instancias
az monitor metrics alert create \
  --name "max-instancias-alcanzado" \
  --resource-group rg-ventas-prod \
  --scopes "/subscriptions/<id>/resourceGroups/rg-prod/providers/Microsoft.Web/serverfarms/plan-prod" \
  --condition "avg CpuPercentage > 80" \
  --window-size 15m \
  --evaluation-frequency 5m \
  --description "CPU alta sostenida — revisar si necesita más instancias o scale up"
```

**Alertas recomendadas:**
| Métrica | Condición | Severidad |
|---------|-----------|-----------|
| CPU > 80% (15 min) | El plan está al límite | Warning |
| Memory > 85% (15 min) | Posible memory leak o plan infradimensionado | Warning |
| Http 5xx > 10 (5 min) | Errores en la app | Critical |
| Http Queue > 50 | Peticiones encoladas | Warning |

## Slide 22 — Scale-in protection: evitar muertes durante deploys

Cuando el autoscale **reduce** instancias, Azure no sabe cuál está en medio de un deploy o procesando una request larga. Puede matarla. **Scale-in protection** lo previene:

```bash
# Habilitar scale-in protection en un plan
az appservice plan update \
  --name plan-ventas -g rg-apps \
  --set properties.scaleInProtectionConfig.enabled=true

# O a nivel de app específica
# Requiere preview feature flag
```

**Cómo funciona:**
1. Una instancia arranca y se registra como "protected" durante su warmup
2. Durante el warmup, Azure NO la puede quitar por scale-in
3. Al terminar warmup (2-5 min), se vuelve "scalable"
4. Si la instancia está procesando requests largas → termina antes de morir
5. Graceful shutdown con `SIGTERM` antes de kill

**Configuración recomendada:**
```bash
# App Setting
WEBSITE_GRACEFUL_SHUTDOWN_TIMEOUT=30   # segundos para drenar requests

# Application code (Program.cs)
var builder = WebApplication.CreateBuilder(args);
builder.Host.ConfigureHostOptions(options => {
    options.ShutdownTimeout = TimeSpan.FromSeconds(30);
});
```

Esto evita errores 502/503 durante scale-in. **Crítico** en producción.

## Slide 24 — Azure Front Door vs Traffic Manager: diferencias

Ambos balancean tráfico global, pero operan en capas diferentes:

| | Traffic Manager | Azure Front Door |
|---|---|---|
| Capa | DNS (Layer 4) | HTTP/S (Layer 7) |
| Decisión | Resuelve nombres | Termina conexión y reenvía |
| Latencia | Cliente → DNS → región | Cliente → edge AFD → región |
| Cacheado | No | Sí (CDN integrado) |
| WAF | No | Sí (Web Application Firewall) |
| Path-based routing | No | Sí |
| SSL offload | No | Sí |
| Coste | Bajo | Medio-alto |
| Failover | Lento (DNS TTL) | Rápido (segundos) |

**Cuándo Traffic Manager:**
- Apps no-HTTP (SQL, SMB, etc.)
- Presupuesto ajustado
- DNS-based failover es suficiente

**Cuándo Azure Front Door:**
- APIs / web apps HTTP/S (el 95% de casos)
- Necesitáis WAF (protección contra ataques)
- Queréis CDN integrado (cachear estáticos)
- Routing complejo por path (/api → backend A, /static → backend B)
- SSL offload en edge (liberar CPU de backends)

**Regla 2026:** para web apps, **Azure Front Door es la opción por defecto**. Traffic Manager se usa solo cuando AFD no aplica.

## Slide 25 — Azure CDN con App Service: cachear estáticos

Si vuestra app sirve HTML, CSS, JS, imágenes... cachearlos en CDN baja latencia y coste:

```bash
# Crear CDN profile
az cdn profile create \
  --name cdn-ventas -g rg-apps \
  --sku Standard_Microsoft

# Crear endpoint que apunta a vuestra App Service
az cdn endpoint create \
  --name ventas-cdn \
  --profile-name cdn-ventas -g rg-apps \
  --origin app-ventas.azurewebsites.net \
  --origin-host-header app-ventas.azurewebsites.net \
  --enable-compression true

# URL final: https://ventas-cdn.azureedge.net
# Custom domain posible: https://static.ventas.com → CDN → App Service
```

**Headers que controlan cacheo:**

```csharp
// En vuestra API .NET 8
app.UseStaticFiles(new StaticFileOptions
{
    OnPrepareResponse = ctx =>
    {
        // Cache 1 año para archivos con hash en el nombre
        if (ctx.File.Name.Contains(".hash."))
        {
            ctx.Context.Response.Headers.Append(
                "Cache-Control", "public, max-age=31536000, immutable");
        }
        else
        {
            // Cache 1 hora para el resto
            ctx.Context.Response.Headers.Append(
                "Cache-Control", "public, max-age=3600");
        }
    }
});
```

**Resultado típico:**
- Sin CDN: cada imagen/JS → round-trip a App Service (50-300ms por asset)
- Con CDN: primera vez al edge → cacheado → 10-30ms desde el mismo país

**AFD ya incluye CDN** — si usáis Azure Front Door, no necesitáis CDN separado.

## Slide 26 — Scale to zero: Container Apps como alternativa

App Service **NO** puede escalar a 0 (siempre hay al menos 1 instancia). Si necesitáis scale to zero:

```
Alternativa: Azure Container Apps

Características relevantes:
├── Scale to zero: 0 instancias cuando no hay tráfico
├── Cold start al primer request (~1-3s según tamaño)
├── Facturación por CPU-seg + mem-seg (muy bajo cuando inactivo)
├── Escalado basado en KEDA (HTTP, cola, eventos)
└── Runtime: container (Docker)

Cuándo reemplazar App Service con Container Apps:
├── APIs con tráfico muy esporádico (tarde/noche)
├── Servicios internos (batch, background jobs)
├── Ambientes dev/staging (no merece la pena tener always-on)
├── Microservicios con autoescala agresiva
└── Apps event-driven (procesan mensajes de cola)

Cuándo seguir con App Service:
├── Tráfico constante (el cold start molesta)
├── Stack no-container (no queréis dockerizar)
├── Queréis slots (Container Apps no los tiene)
└── Simplicidad operativa (App Service es más sencillo)
```

```bash
# Ejemplo: Container App con scale 0→10
az containerapp create \
  --name miapi -g rg-apps \
  --image myregistry.azurecr.io/miapi:v1 \
  --environment container-env-dev \
  --min-replicas 0 --max-replicas 10 \
  --scale-rule-name http-scale \
  --scale-rule-http-concurrency 50
```

## Slide 27 — Multi-region active-active: alta disponibilidad real

SLA de App Service es 99.95% (single region). Para 99.99%+ necesitáis multi-región:

```
Arquitectura típica multi-región active-active:

                 Azure Front Door
                /                \
           West Europe        North Europe
               │                    │
         App Service          App Service
               │                    │
         Cosmos DB  ←─── multi-region ───→  Cosmos DB
```

```bash
# 1. Crear App Service en 2 regiones
az appservice plan create --name plan-ventas-we -g rg-apps --location westeurope --sku P1v3
az appservice plan create --name plan-ventas-ne -g rg-apps --location northeurope --sku P1v3

az webapp create --name app-ventas-we --plan plan-ventas-we -g rg-apps
az webapp create --name app-ventas-ne --plan plan-ventas-ne -g rg-apps

# 2. Cosmos DB multi-region (account con 2 regiones)
az cosmosdb update --name cosmos-ventas -g rg-apps \
  --locations regionName=westeurope failoverPriority=0 isZoneRedundant=True \
  --locations regionName=northeurope failoverPriority=1 isZoneRedundant=True \
  --enable-multiple-write-locations true

# 3. Azure Front Door con ambas apps como backends
az afd origin create --origin-group-name ventas-og --profile-name afd-ventas \
  --resource-group rg-apps --host-name app-ventas-we.azurewebsites.net --origin-name we
az afd origin create --origin-group-name ventas-og --profile-name afd-ventas \
  --resource-group rg-apps --host-name app-ventas-ne.azurewebsites.net --origin-name ne
```

**Consideraciones:**
- Datos: Cosmos DB multi-region (sync automático), SQL con Geo-Replication
- Costes ~2x (dos sets de infraestructura)
- Complejidad operativa alta (deployments coordinados, routing)
- Solo necesario si el negocio lo exige (SLA contractual, compliance)

## Slide 28 — Autoscale con múltiples reglas combinadas

Reglas simples (solo CPU) no bastan en apps reales. Mejor combinarlas:

```json
// Autoscale con 3 reglas (OR entre ellas: si CUALQUIERA se cumple, escala)
{
  "profiles": [
    {
      "name": "Default",
      "capacity": { "minimum": 2, "maximum": 20, "default": 2 },
      "rules": [
        {
          "// Regla 1: CPU alta → escalar",
          "metricTrigger": {
            "metricName": "CpuPercentage",
            "metricResourceUri": "<plan-id>",
            "timeGrain": "PT1M",
            "statistic": "Average",
            "timeWindow": "PT5M",
            "timeAggregation": "Average",
            "operator": "GreaterThan",
            "threshold": 70
          },
          "scaleAction": {
            "direction": "Increase", "type": "ChangeCount",
            "value": "2", "cooldown": "PT5M"
          }
        },
        {
          "// Regla 2: Cola de requests HTTP → escalar",
          "metricTrigger": {
            "metricName": "HttpQueueLength",
            "threshold": 100,
            "operator": "GreaterThan"
          },
          "scaleAction": {
            "direction": "Increase", "type": "ChangeCount",
            "value": "3", "cooldown": "PT3M"
          }
        },
        {
          "// Regla 3: Memoria alta → escalar",
          "metricTrigger": {
            "metricName": "MemoryPercentage",
            "threshold": 80,
            "operator": "GreaterThan"
          },
          "scaleAction": {
            "direction": "Increase", "type": "ChangeCount",
            "value": "1", "cooldown": "PT5M"
          }
        },
        {
          "// Regla 4: TODO bajo → scale in (inversa)",
          "metricTrigger": {
            "metricName": "CpuPercentage",
            "operator": "LessThan",
            "threshold": 30,
            "timeWindow": "PT15M"
          },
          "scaleAction": {
            "direction": "Decrease", "type": "ChangeCount",
            "value": "1", "cooldown": "PT10M"
          }
        }
      ]
    }
  ]
}
```

**Buenas prácticas:**
- `cooldown` en scale-in más largo que scale-out (evitar flapping)
- Scale-out rápido (2-3 min), scale-in lento (10-15 min)
- Monitorizar el propio autoscale (alertas si alcanza max 3 veces en 1 hora)

## Slide 29 — Warmup durante scale-out: evitar requests al vacío

Cuando autoscale añade una instancia nueva, Azure empieza a enviarle tráfico **inmediatamente** aunque la app aún esté arrancando:

**Resultado:** los primeros usuarios que aterrizan en la instancia nueva ven latencia 5-10x superior o errores 502/503.

**Solución:** configurar warmup + health check:

```bash
# 1. Configurar health check path
az webapp config set \
  --name app-ventas -g rg-apps \
  --generic-configurations '{"healthCheckPath": "/health"}'

# 2. Configurar applicationInitialization (warmup antes de recibir tráfico)
az webapp config set --name app-ventas -g rg-apps \
  --generic-configurations '{
    "applicationInitialization": {
      "initializationPages": [
        { "path": "/health" },
        { "path": "/api/productos?limit=1" },
        { "path": "/api/categorias" }
      ]
    }
  }'
```

**Flujo corregido:**
1. Autoscale añade instancia N+1
2. Azure sigue enviando tráfico a N (la nueva NO recibe)
3. En la instancia nueva, IIS ejecuta las URL de warmup
4. Cuando `/health` devuelve 200 durante X checks → "healthy"
5. Azure empieza a enviar tráfico a la instancia nueva
6. Los usuarios tienen experiencia consistente

**Tiempo típico de warmup:** 30-90 segundos según complejidad. Sin warmup, los primeros 30-60s tras scale-out son malos.

## Slide 30 — Web App for Containers scaling: consideraciones

Si vuestra app es un container, el escalado tiene matices:

```
Diferencias clave vs runtime nativo:

├── Imagen pull: cada nueva instancia descarga la imagen de ACR
│   └── Imágenes pequeñas (<500MB) = pull de 10-30s
│   └── Imágenes grandes (>2GB) = pull de 1-3 min 
│   └── Recomendación: multi-stage builds, imagen final <500MB

├── Cold start mayor:
│   └── Container start + app start + warmup
│   └── Típicamente 1-2 min vs 30-60s de runtime nativo

├── Prefetch de imagen (feature):
│   └── Azure cachea la imagen en las instancias "warm pool"
│   └── Reduce pull time a casi 0 en escalados

├── Private ACR:
│   └── Usar Managed Identity (NO credenciales en app settings)
│   └── Asignar rol "AcrPull" al MI del App Service
│   └── Imagen debe estar en ACR dentro del tenant o con peering

├── Health check con containers:
│   └── El health check del App Service va al container vía HTTP
│   └── No confundir con Docker HEALTHCHECK (eso es Azure Container Apps)
```

**Tips para acelerar scale-out de containers:**
```dockerfile
# Multi-stage build: imagen final pequeña
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MiApi.dll"]

# Imagen final ~200MB en lugar de 2GB
```

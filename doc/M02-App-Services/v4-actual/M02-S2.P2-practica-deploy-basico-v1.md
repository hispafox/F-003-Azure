## Slide 2 — Qué vais a construir

Una API .NET 8 mínima desplegada a Azure App Service en plan gratuito (F1). Sin slots, sin swap, sin complicaciones — solo lo esencial para entender el flujo end-to-end.

**El recorrido:**

```
1. Crear el proyecto .NET 8 con minimal API
2. Probar en local que funciona
3. Crear Resource Group y App Service Plan F1
4. Crear Web App
5. Desplegar via az CLI
6. Verificar y probar la URL pública
7. Configurar logs y verlos en directo
8. Limpiar todo (fin de la práctica)
```

**Lo que NO hay en esta práctica** (a propósito):
- ❌ Slots (eso es la práctica anterior, M02-S2.P)
- ❌ Pipeline CI/CD (eso es M08)
- ❌ Custom domains, SSL, secretos (M06)
- ❌ Auto-escalado (escala manual al final como bonus)

**Por qué empezamos por aquí:** dominar el deploy básico es prerrequisito para todo lo demás. Si no controláis esto, slots y CI/CD os van a parecer magia.

**Tiempo estimado:** 60-75 minutos.

**Coste real:** **0€** durante toda la práctica (plan F1 gratis).

## Slide 3 — Pre-flight: requisitos antes de empezar

Validad que tenéis todo en orden antes de empezar. Cinco minutos aquí ahorran 30 después.

**Requisitos:**

```bash
# 1. .NET 8 SDK
dotnet --version
# Esperado: 8.0.x o superior

# 2. Azure CLI v2.65 o superior
az --version
# Si necesitáis actualizar:
# Mac:    brew upgrade azure-cli
# Linux:  curl -L https://aka.ms/InstallAzureCli | bash
# Win:    https://aka.ms/installazurecliwindows

# 3. Login activo en Azure
az account show --output table

# Si no estáis logueados:
az login

# 4. Suscripción correcta
az account list --output table
az account set --subscription "<nombre-de-vuestra-sub>"

# 5. Cliente HTTP para tests
which curl  # debería estar instalado por defecto
```

**Si algo falla aquí:**

- ❌ "No subscriptions found" → `az login --tenant <tenant-id>` con vuestro tenant
- ❌ "az: command not found" → instalar Azure CLI con los comandos de arriba
- ❌ "dotnet: command not found" → instalar .NET 8 SDK desde dotnet.microsoft.com

**Cuenta personal vs corporativa:** si tenéis ambas asociadas, asegurad que `az account show` devuelve la correcta. Es el error más común al empezar.

## Slide 5 — Paso 2: Personalizar Program.cs

Sustituid el contenido de `Program.cs` con esta versión simplificada que devuelve información útil:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Servicios mínimos
builder.Services.AddEndpointsApiExplorer();

var app = builder.Build();

// Endpoint raíz: información de la app
app.MapGet("/", () => new
{
    aplicacion = "Mi Primera Web App",
    version = "1.0",
    entorno = app.Environment.EnvironmentName,
    hora_servidor = DateTime.UtcNow,
    mensaje = "¡Hola desde Azure!"
});

// Endpoint de health check (lo usaremos al final)
app.MapGet("/health", () => Results.Ok(new
{
    status = "healthy",
    timestamp = DateTime.UtcNow
}));

// Endpoint con parámetro
app.MapGet("/saludo/{nombre}", (string nombre) =>
    new { mensaje = $"¡Hola, {nombre}!", hora = DateTime.UtcNow });

app.Run();
```

**Lo que hace cada endpoint:**

```
GET /                  → Información sobre la app (nombre, versión, entorno)
GET /health            → Status simple (lo usaremos para verificación)
GET /saludo/{nombre}   → Saludo personalizado
```

**Por qué esta estructura:**
- ✅ Mínimo código, fácil de entender
- ✅ Endpoints útiles para verificar que funciona
- ✅ El endpoint `/health` nos servirá para troubleshooting

## Slide 7 — Paso 4: Crear Resource Group

Todos los recursos de Azure viven dentro de un Resource Group. Creemos el nuestro:

```bash
# Variables (cambiad <tu-nombre> por algo único, sin espacios ni acentos)
RG_NAME="rg-curso-azure-<tu-nombre>"
LOCATION="westeurope"

# Crear el Resource Group
az group create \
  --name $RG_NAME \
  --location $LOCATION

# Verificar que se creó
az group show --name $RG_NAME --output table
```

**Salida esperada:**
```
Location    Name                          Status
----------  ----------------------------  ---------
westeurope  rg-curso-azure-pedro          Succeeded
```

**Conceptos clave:**

```
Resource Group:
├── Es un "contenedor lógico" para recursos relacionados
├── Tiene una región (location), pero los recursos pueden estar en otras
├── Borrar el RG → borra TODO lo que contiene (útil al limpiar)
└── No tiene coste en sí mismo (gratis)
```

**¿Por qué `westeurope`?**
- Está en Ámsterdam (cerca de España, baja latencia)
- Soporta todos los servicios que usaremos
- Otros valores válidos: `northeurope` (Irlanda), `francecentral` (París)

**Tip pro:** podéis ver todas las regiones disponibles con `az account list-locations -o table`.

## Slide 8 — Paso 5: Crear App Service Plan F1

El App Service Plan define **el hardware** donde va a correr vuestra app. F1 es el plan gratuito.

```bash
PLAN_NAME="plan-curso-<tu-nombre>"

# Crear App Service Plan F1 (gratis, Linux)
az appservice plan create \
  --name $PLAN_NAME \
  --resource-group $RG_NAME \
  --sku F1 \
  --is-linux

# Verificar
az appservice plan show \
  --name $PLAN_NAME \
  --resource-group $RG_NAME \
  --output table
```

**Salida esperada:**
```
Location    Name                  SKU
----------  --------------------  ----
westeurope  plan-curso-pedro      F1
```

**Características del plan F1:**

| Aspecto | F1 (Free) |
|---|---|
| Coste | **0€/mes** |
| RAM | 1 GB |
| Almacenamiento | 1 GB |
| CPU time | 60 min/día |
| Custom domain | ❌ |
| SSL custom | ❌ |
| Always-on | ❌ (la app se duerme tras 20 min sin tráfico) |
| Slots | ❌ |
| Auto-scale | ❌ |
| Apps por plan | Hasta 10 |

**Limitaciones a conocer:**
- 🛑 **CPU time 60 min/día**: tras superarlo, la app responde 403 hasta el siguiente día
- 🛑 **Sleep tras 20 min**: el primer request tras inactividad puede tardar 5-30 segundos (cold start)
- ✅ Para esta práctica es **más que suficiente**

## Slide 9 — Paso 6: Crear Web App

Ya tenemos el "hardware" (plan). Ahora creamos la "máquina" (Web App):

```bash
# El nombre debe ser único globalmente (forma parte de la URL)
APP_NAME="webapp-curso-<tu-nombre>-$(date +%s)"

# Crear Web App con runtime .NET 8
az webapp create \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --plan $PLAN_NAME \
  --runtime "DOTNETCORE:8.0"

# Guardar el nombre para los siguientes pasos
echo "Vuestra app: https://$APP_NAME.azurewebsites.net"
```

**¿Por qué `$(date +%s)` en el nombre?**

```
El nombre de la Web App es UNA URL única en todo Azure:
  https://webapp-curso-pedro.azurewebsites.net

Si ya existe otra "webapp-curso-pedro" en el mundo → ERROR

El timestamp asegura unicidad. Resulta en algo como:
  webapp-curso-pedro-1714298765
```

**Verificar:**

```bash
# La app ya existe pero todavía no tiene código
az webapp show --name $APP_NAME --resource-group $RG_NAME --output table

# Probar la URL (devuelve la página default de App Service)
curl https://$APP_NAME.azurewebsites.net
```

**Salida esperada:** una página HTML con el mensaje "Your web app is running and waiting for your content". Eso significa que la infraestructura está lista, falta el código.

## Slide 10 — Paso 7: Publicar la app a Azure

Ahora subimos nuestro código a la Web App. Hay varias formas; usamos la más simple para empezar.

**Método 1: ZIP deploy via az CLI**

```bash
# Volver a la carpeta del proyecto
cd MiPrimeraWebApp

# Publicar en modo Release
dotnet publish -c Release -o ./publish

# Comprimir los artifacts
cd publish
zip -r ../app.zip .
cd ..

# Desplegar el zip
az webapp deploy \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --src-path ./app.zip \
  --type zip
```

**Tiempo estimado del deploy:** 1-3 minutos.

**Output esperado:**
```
{
  "active": true,
  "complete": true,
  "deployer": "ZipDeploy",
  "is_temp": false,
  "status": 4,
  ...
}
```

**Método alternativo (más rápido si tenéis el SDK):**

```bash
# Publicar y desplegar en un solo comando
dotnet publish -c Release
az webapp up \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --runtime "DOTNETCORE:8.0" \
  --html
```

**¿Cuál usar?**
- Para esta práctica: **Método 1 (ZIP deploy)** — explícito, predecible, mejor para aprender
- Para iteración rápida: **Método alternativo** — un solo comando

## Slide 13 — Configurar logs estructurados (mejora opcional)

Los logs de framework son útiles, pero los **logs estructurados** que vosotros añadís son mucho mejores. Mejora rápida del `Program.cs`:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddEndpointsApiExplorer();

var app = builder.Build();

// Logger inyectable
var logger = app.Logger;

app.MapGet("/", () =>
{
    logger.LogInformation("Endpoint raíz invocado");
    return new
    {
        aplicacion = "Mi Primera Web App",
        version = "1.0",
        entorno = app.Environment.EnvironmentName,
        hora_servidor = DateTime.UtcNow
    };
});

app.MapGet("/saludo/{nombre}", (string nombre) =>
{
    logger.LogInformation("Saludando a {Nombre}", nombre);
    
    if (string.IsNullOrWhiteSpace(nombre) || nombre.Length > 50)
    {
        logger.LogWarning("Nombre inválido recibido: {Nombre}", nombre);
        return Results.BadRequest(new { error = "Nombre inválido" });
    }
    
    return Results.Ok(new { mensaje = $"¡Hola, {nombre}!", hora = DateTime.UtcNow });
});

app.MapGet("/health", () =>
{
    logger.LogDebug("Health check ejecutado");
    return Results.Ok(new { status = "healthy", timestamp = DateTime.UtcNow });
});

app.Run();
```

**Por qué esto es mejor:**

- ✅ Logs muestran QUÉ pasó (no solo "request finished 200")
- ✅ Estructurados con placeholders `{Nombre}` (App Insights los indexa)
- ✅ Niveles correctos (Info para éxito, Warning para input inválido)

**Re-desplegar tras el cambio:**

```bash
dotnet publish -c Release -o ./publish
cd publish && zip -r ../app.zip . && cd ..

az webapp deploy \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --src-path ./app.zip \
  --type zip
```

## Slide 14 — App Settings: configuración por entorno

Hardcodear valores en código es mala práctica. **App Settings** os permite cambiar config sin redesplegar:

```bash
# Añadir App Settings (variables de entorno)
az webapp config appsettings set \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --settings \
    SALUDO_PERSONALIZADO="¡Hola desde Azure App Service!" \
    NIVEL_LOG="Information" \
    MAX_LONGITUD_NOMBRE="50"

# Ver todas las settings
az webapp config appsettings list \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --output table
```

**Usar las settings en el código:**

```csharp
var saludoBase = builder.Configuration["SALUDO_PERSONALIZADO"] 
    ?? "¡Hola desde Azure!";

var maxLongitud = builder.Configuration.GetValue<int>("MAX_LONGITUD_NOMBRE", 50);

app.MapGet("/saludo/{nombre}", (string nombre) =>
{
    if (nombre.Length > maxLongitud)
        return Results.BadRequest(new { error = $"Máximo {maxLongitud} caracteres" });
    
    return Results.Ok(new { mensaje = $"{saludoBase} {nombre}" });
});
```

**App Settings vs hardcoded:**

| Aspecto | Hardcoded | App Settings |
|---|---|---|
| Cambio requiere redeploy | ✅ Sí | ❌ No (cambio inmediato) |
| Visible en código | ✅ Sí | ❌ No (más seguro para secretos) |
| Diferentes por entorno | ❌ Difícil | ✅ Fácil (dev/prod distintos) |

**Tras cambiar App Settings, App Service reinicia automáticamente la app** (~10-30 segundos).

**Verificar el cambio:**

```bash
# Reiniciar manualmente (no es necesario si App Settings cambió, pero por si acaso)
az webapp restart --name $APP_NAME --resource-group $RG_NAME

# Probar
curl https://$APP_NAME.azurewebsites.net/saludo/Pedro
# Ahora veréis el nuevo "saludo base" personalizado
```

## Slide 15 — Smoke tests automatizados

Validar a mano cada deploy es lento. Un script bash que valida los 3 endpoints en 5 segundos:

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

URL="${1:?Pasa la URL como primer argumento}"

echo "🔍 Smoke tests sobre $URL"

# Test 1: Endpoint raíz
echo -n "  [1/4] Endpoint raíz... "
HTTP_CODE=$(curl -o /tmp/raiz.json -s -w "%{http_code}" "$URL/")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 2: Health
echo -n "  [2/4] Health check... "
HTTP_CODE=$(curl -o /tmp/health.json -s -w "%{http_code}" "$URL/health")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 3: Saludo válido
echo -n "  [3/4] Saludo (válido)... "
HTTP_CODE=$(curl -o /tmp/saludo.json -s -w "%{http_code}" "$URL/saludo/test")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 4: Latencia P95 razonable (5 requests)
echo -n "  [4/4] Latencia... "
TOTAL=0
for i in 1 2 3 4 5; do
  T=$(curl -o /dev/null -s -w "%{time_total}" "$URL/health")
  TOTAL=$(echo "$TOTAL + $T" | bc -l)
done
AVG=$(echo "scale=3; $TOTAL / 5" | bc -l)
echo "avg ${AVG}s ✓"

echo ""
echo "✅ Todos los smoke tests pasados"
EOF

chmod +x smoke-tests.sh

# Ejecutar
./smoke-tests.sh "https://$APP_NAME.azurewebsites.net"
```

**Output esperado:**

```
🔍 Smoke tests sobre https://webapp-curso-pedro-...azurewebsites.net
  [1/4] Endpoint raíz... ✓
  [2/4] Health check... ✓
  [3/4] Saludo (válido)... ✓
  [4/4] Latencia... avg 0.245s ✓

✅ Todos los smoke tests pasados
```

**Si la latencia es alta (>3s):** probablemente cold start del F1. Ejecutad de nuevo y veréis tiempos normales (<500ms).

**En producción real (no esta práctica):** este script se ejecuta automáticamente desde el pipeline CI/CD tras cada deploy. Si falla, el pipeline alerta o hace rollback.

## Slide 16 — Troubleshooting: los 5 errores más comunes

Si algo sale mal, estas son las causas más frecuentes y cómo solucionarlas:

**1. "App returns 502 Bad Gateway o 503 Service Unavailable"**

```
Causa: la app no arrancó correctamente tras el deploy
Diagnóstico:
  az webapp log tail --name $APP_NAME -g $RG_NAME

Causas comunes:
- Error en código (excepción al arrancar)
- Falta de paquetes en publish
- Versión .NET incorrecta en el runtime

Fix:
- Ver el log y resolver el error específico
- Verificar runtime: az webapp config show --name $APP_NAME -g $RG_NAME
```

**2. "Primer request tarda mucho (10-30 seg)"**

```
Causa: cold start del plan F1 (sleep tras 20 min sin tráfico)
Síntoma: solo el primer request es lento, el resto rápidos

Es comportamiento NORMAL en F1.

Soluciones:
- Aceptar el cold start (es lo esperado en gratis)
- Pasar a B1 (~€13/mes) que tiene Always On
- Usar un servicio externo que pingee cada 5 min (NO recomendado, 
  va contra los términos del free tier)
```

**3. "503 después de muchos requests rápidos"**

```
Causa: superado el límite de 60 min CPU/día del F1
Síntoma: app va bien, pero de repente todos los requests son 503

Diagnóstico:
  az monitor metrics list \
    --resource $(az webapp show --name $APP_NAME -g $RG_NAME --query id -o tsv) \
    --metric CpuTime \
    --interval PT1H

Fix:
- Esperar a las 00:00 UTC (cuota se reinicia)
- O upgradar a B1 (~€13/mes, sin límite CPU)
```

**4. "El deploy parece funcionar pero la app no se actualiza"**

```
Causa: Azure cachea el último deploy
Síntoma: az webapp deploy devuelve OK pero el código viejo sigue corriendo

Fix:
- Forzar restart manual:
  az webapp restart --name $APP_NAME -g $RG_NAME
- Verificar que el zip incluye archivos actualizados:
  unzip -l app.zip | head -20
```

**5. "Cannot find subscription / authorization issue"**

```
Causa: az CLI no logueado o suscripción incorrecta
Síntoma: comandos fallan con "AuthorizationFailed"

Fix:
  az login
  az account list -o table
  az account set --subscription "<nombre-correcto>"
```

**Cuando nada funciona:** abrid Kudu (la consola web de App Service):

```
URL: https://$APP_NAME.scm.azurewebsites.net

Permite:
- Explorar archivos desplegados
- Ver logs en directo
- SSH a la instancia (Linux)
- Ver variables de entorno reales
```

## Slide 17 — Métricas básicas: ¿está la app sana?

Ya en producción, App Service expone métricas que conviene mirar regularmente:

```bash
# Métricas básicas de la última hora
az monitor metrics list \
  --resource $(az webapp show --name $APP_NAME -g $RG_NAME --query id -o tsv) \
  --metric "Http2xx,Http4xx,Http5xx,AverageResponseTime" \
  --interval PT5M \
  --output table
```

**Métricas clave que importan:**

| Métrica | Qué mide | Valor esperado |
|---|---|---|
| **Http2xx** | Requests con éxito | La mayoría |
| **Http4xx** | Errores cliente (404, 400, etc.) | Pocos, pero esperables |
| **Http5xx** | Errores servidor | **Cero idealmente** |
| **AverageResponseTime** | Latencia media | <500ms (>1s es preocupante) |
| **CpuTime** | Tiempo de CPU consumido | Importante en F1 (límite 60 min/día) |
| **MemoryWorkingSet** | RAM en uso | <1GB en F1 (límite del plan) |

**En el portal:**

```
1. Portal Azure → Tu Web App
2. Sección "Monitoring" → Metrics
3. Add metric → seleccionar las que interesen
4. Pin to dashboard si lo veis frecuente
```

**Alertas básicas que tendrías en producción real:**

```
- Http5xx > 5 en 5 min → email
- AverageResponseTime > 2s sostenido → email
- CpuTime > 80% del límite F1 → alerta de upgrade
```

**Para esta práctica con F1:** no configuraremos alertas (las alertas son una práctica de M05/M08). Solo necesitáis saber que existen.

## Slide 18 — Variante: escala manual (bonus)

El plan F1 no permite escalar (1 instancia fija). Pero veamos cómo sería en B1 o superior. **No ejecutéis esto** salvo que estéis en B1+:

```bash
# Para B1 o superior: escalar a 3 instancias
# COSTE: B1 cuesta ~€13/mes × 3 instancias = ~€39/mes
# NO HACER en F1 (no soportado)

# az appservice plan update \
#   --name $PLAN_NAME \
#   --resource-group $RG_NAME \
#   --number-of-workers 3
```

**Cómo funciona la escala manual:**

```
Antes (1 worker):
┌─────────────────┐
│ Worker 1        │  ← maneja todos los requests
│ (vuestra app)   │
└─────────────────┘

Después (3 workers):
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ Worker 1        │  │ Worker 2        │  │ Worker 3        │
│ (vuestra app)   │  │ (vuestra app)   │  │ (vuestra app)   │
└─────────────────┘  └─────────────────┘  └─────────────────┘
            │                │                │
            └────────────────┼────────────────┘
                             │
                  Load Balancer (transparente)
```

**Implicaciones de escalar:**

```
✅ Más capacidad para concurrencia
✅ Tolerancia a fallos (si una instancia se cae, las otras siguen)
✅ Distribución de carga automática

⚠️ Hay que pensar en:
   - Sesiones: NO usar in-memory session state (usa Redis)
   - Caches: NO en memoria local (usa Redis o similar)
   - Singleton patterns: cada instancia tiene su propio singleton
   - Files: NO escribir al filesystem local (usa Storage)
```

**Para esta práctica:** lo dejamos en F1 con 1 instancia. La escala se cubre en M02-S2.3 (escalado automático).

## Slide 2 — El principio fundamental
**Nunca hardcodees configuración que varíe entre entornos.**

Esto incluye: cadenas de conexión a bases de datos, URLs de APIs externas, claves de API, feature flags, niveles de log, nombres de colas, endpoints de servicios...

Si está en tu código fuente, está en tu repo. Si está en tu repo, cualquiera con acceso lo ve. Y si necesitas cambiarlo en producción, necesitas redesplegar.

Las variables de entorno resuelven ambos problemas: la configuración vive fuera del código y se puede cambiar sin redesplegar.


---

## Slide 3 — Dos mecanismos en App Service
App Service tiene dos tipos de configuración externa:

**Application Settings (appsettings):**
Variables de entorno generales. Se inyectan como variables de entorno del OS.
```bash
az webapp config appsettings set --name mi-app -g mi-rg \
  --settings MI_VARIABLE="valor" OTRA="otro-valor"
```

**Connection Strings:**
Específicas para cadenas de conexión a bases de datos. Se inyectan con un prefijo según el tipo.
```bash
az webapp config connection-string set --name mi-app -g mi-rg \
  --connection-string-type SQLAzure \
  --settings MiDB="Server=tcp:mi-server.database.windows.net;..."
```

**¿Cuál usar?**
- Application Settings para todo lo general (URLs, keys, flags, niveles de log)
- Connection Strings solo para conexiones a DB si usáis los helpers de .NET que las leen automáticamente

En la práctica, muchos equipos usan Application Settings para todo, incluyendo connection strings. Funciona igual.

## Slide 4 — Application Settings en detalle

```bash
# Listar todas las variables
az webapp config appsettings list --name mi-app -g mi-rg --output table

# Añadir/actualizar variables
az webapp config appsettings set --name mi-app -g mi-rg \
  --settings \
    ASPNETCORE_ENVIRONMENT=Production \
    API_BASE_URL="https://api.externa.com/v2" \
    FEATURE_NUEVA_UI=true \
    LOG_LEVEL=Warning \
    MAX_RETRY_COUNT=3

# Eliminar una variable
az webapp config appsettings delete --name mi-app -g mi-rg \
  --setting-names FEATURE_NUEVA_UI

# Marcar como sticky (no viaja con swap)
az webapp config appsettings set --name mi-app -g mi-rg \
  --slot-settings \
    ASPNETCORE_ENVIRONMENT=Production \
    DB_CONNECTION="prod-connection-string"
```

**Después de cambiar una variable, App Service reinicia la app automáticamente.** El reinicio aplica los nuevos valores. Tened esto en cuenta: cambiar una variable = mini-downtime (unos segundos de reinicio).

## Slide 5 — Leer variables desde código .NET

ASP.NET Core lee las variables de App Service automáticamente:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Opción 1: Leer directamente del entorno
var apiUrl = Environment.GetEnvironmentVariable("API_BASE_URL");

// Opción 2: A través del sistema de configuración de .NET (recomendada)
var apiUrl = builder.Configuration["API_BASE_URL"];
var maxRetry = builder.Configuration.GetValue<int>("MAX_RETRY_COUNT");

// Opción 3: Con el patrón Options (la más profesional)
builder.Services.Configure<ApiSettings>(
    builder.Configuration.GetSection("Api"));

var app = builder.Build();

app.MapGet("/config", (IOptions<ApiSettings> options) =>
{
    return Results.Json(new
    {
        url = options.Value.BaseUrl,
        retries = options.Value.MaxRetries
    });
});
```

**Precedencia de configuración en .NET:**
1. `appsettings.json` (base)
2. `appsettings.{Environment}.json` (override por entorno)
3. Variables de entorno del OS (override final — App Settings van aquí)
4. Línea de comandos (máxima prioridad)

Las variables de App Service tienen prioridad sobre lo que haya en los archivos JSON. Así podéis tener valores por defecto en `appsettings.json` y sobreescribirlos en Azure sin tocar código.

## Slide 6 — Configuración jerárquica con doble guion bajo

En `appsettings.json` tenéis secciones anidadas:
```json
{
  "Api": {
    "BaseUrl": "https://default-api.com",
    "MaxRetries": 3,
    "Timeout": 30
  },
  "Cosmos": {
    "DatabaseName": "mi-db",
    "ContainerName": "mi-container"
  }
}
```

En App Service, usáis `__` (doble guion bajo) para representar la jerarquía:
```bash
az webapp config appsettings set --name mi-app -g mi-rg \
  --settings \
    Api__BaseUrl="https://produccion-api.com" \
    Api__MaxRetries=5 \
    Cosmos__DatabaseName="prod-db"
```

En Linux, usáis `:` o `__`:
```bash
Api:BaseUrl="https://produccion-api.com"
# o
Api__BaseUrl="https://produccion-api.com"
```

El doble guion bajo funciona en ambos (Windows y Linux). Usad siempre `__`.

## Slide 7 — Connection Strings

```bash
# Añadir connection string
az webapp config connection-string set --name mi-app -g mi-rg \
  --connection-string-type SQLAzure \
  --settings \
    DefaultConnection="Server=tcp:mi-server.database.windows.net,1433;Database=mi-db;User ID=admin;Password=xxx;Encrypt=true"

# Tipos disponibles:
# SQLAzure, SQLServer, MySQL, PostgreSQL, Custom, RedisCache, ServiceBus, EventHub, DocDb (Cosmos DB), NotificationHub
```

**En código .NET:**
```csharp
var connectionString = builder.Configuration.GetConnectionString("DefaultConnection");
// Lee automáticamente de la connection string de App Service
```

**Diferencia con App Settings:**
Las connection strings se inyectan con un prefijo especial según el tipo:
- SQLAzure: `SQLAZURECONNSTR_DefaultConnection`
- Custom: `CUSTOMCONNSTR_DefaultConnection`

.NET las detecta automáticamente con `GetConnectionString()`. Otros runtimes las ven como variables de entorno con prefijo.

## Slide 8 — El problema de seguridad: secretos en App Settings

App Settings almacena valores en texto plano en la configuración de App Service. Cualquiera con acceso de lectura a la configuración (rol Contributor o superior) puede ver:
- Cadenas de conexión con passwords
- API keys
- Certificados en base64
- Tokens de acceso

**Esto es un riesgo:**
- Un desarrollador con acceso al portal puede ver la password de la DB de producción
- Si exportáis la configuración como ARM template, los secretos van en el JSON
- Los valores aparecen en logs de diagnóstico si no tenéis cuidado

**La solución: Azure Key Vault** (módulo 6 en profundidad, pero la referencia básica la vemos ahora).


---

## Slide 9 — Key Vault References: secretos sin secretos

En vez de poner el secreto directamente en App Settings, ponéis una referencia a Key Vault:

```bash
# 1. Crear Key Vault (si no existe)
az keyvault create --name kv-ventas-prod -g rg-ventas-prod --location westeurope

# 2. Guardar el secreto en Key Vault
az keyvault secret set --vault-name kv-ventas-prod \
  --name "CosmosDbConnection" \
  --value "AccountEndpoint=https://cosmos-prod.documents.azure.com:443/;AccountKey=xxx..."

# 3. Habilitar Managed Identity en la Web App
az webapp identity assign --name app-ventas -g rg-ventas-prod

# 4. Dar acceso a la identidad para leer secretos
PRINCIPAL_ID=$(az webapp identity show --name app-ventas -g rg-ventas-prod --query principalId -o tsv)
az keyvault set-policy --name kv-ventas-prod \
  --object-id $PRINCIPAL_ID \
  --secret-permissions get list

# 5. Configurar App Setting como referencia a Key Vault
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --settings \
    CosmosDbConnection="@Microsoft.KeyVault(VaultName=kv-ventas-prod;SecretName=CosmosDbConnection)"
```

**Resultado:**
- En el portal, la variable muestra "Key Vault Reference" en vez del valor real
- La app lee el valor como cualquier otra variable de entorno
- El secreto real solo está en Key Vault, no en la configuración de App Service
- Si rotáis el secreto en Key Vault, la app obtiene el nuevo valor automáticamente

## Slide 10 — Configuración por entorno en .NET

El patrón estándar de ASP.NET Core para gestionar configuración por entorno:

**Archivos en el proyecto:**
```
appsettings.json                  ← Base (valores por defecto)
appsettings.Development.json      ← Desarrollo local
appsettings.Staging.json          ← Staging (opcional)
appsettings.Production.json       ← Producción (opcional)
```

**appsettings.json (base):**
```json
{

  "Api": { "BaseUrl": "https://localhost:5001", "MaxRetries": 3 },
  "Features": { "NuevaUI": false }
}
```

**appsettings.Development.json (override local):**
```json

  "Logging": { "LogLevel": { "Default": "Debug" } },
  "Api": { "BaseUrl": "https://dev-api.internal.com" },
  "Features": { "NuevaUI": true }
}
```

**En Azure (App Settings sobreescriben todo):**
```bash

  --settings \
    Logging__LogLevel__Default=Warning \
    Api__BaseUrl="https://api.produccion.com" \

```

## Slide 11 — Feature flags con App Settings

Las variables de entorno son perfectas para feature flags simples:

```bash
# Activar feature en staging para testing
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --slot staging \
  --settings FEATURE_NUEVA_UI=true FEATURE_DARK_MODE=true

# Desactivar en producción
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --settings FEATURE_NUEVA_UI=false FEATURE_DARK_MODE=false
```

**En código:**
```csharp
app.MapGet("/", (IConfiguration config) =>
{
    var nuevaUI = config.GetValue<bool>("FEATURE_NUEVA_UI");
    
    if (nuevaUI)
        return Results.Content("<h1>Nueva UI!</h1>", "text/html");
    else
        return Results.Content("<h1>UI clásica</h1>", "text/html");
});
```

**Para feature flags más avanzados** (porcentaje de usuarios, targeting, scheduling), Azure tiene **App Configuration con Feature Management**. Pero para flags on/off simples, App Settings bastan.

## Slide 13 — Exportar e importar configuración

Útil para replicar configuración entre entornos:

```bash
# Exportar app settings a JSON
az webapp config appsettings list --name app-ventas -g rg-ventas-prod \
  --output json > config-prod.json

# Importar en otro entorno (editar valores primero)
# El JSON tiene formato [{name, value, slotSetting}]
az webapp config appsettings set --name app-ventas-dev -g rg-ventas-dev \
  --settings @config-dev.json
```

**Script para copiar configuración entre slots:**
```bash
#!/bin/bash
# copiar-config.sh — Copia app settings de un slot a otro

APP="app-ventas"
RG="rg-ventas-prod"
SOURCE="production"
TARGET="staging"

echo "Copiando configuración de $SOURCE a $TARGET..."

# Exportar (excluyendo sticky settings)
az webapp config appsettings list --name $APP -g $RG \
  --query "[?slotSetting==\`false\`].{name:name, value:value}" \
  --output json > /tmp/settings.json

# Importar al target
az webapp config appsettings set --name $APP -g $RG --slot $TARGET \
  --settings $(cat /tmp/settings.json | jq -r '.[] | "\(.name)=\(.value)"' | tr '\n' ' ')

rm /tmp/settings.json
echo "Configuración copiada."
```

## Slide 19 — IConfiguration: la cadena de prioridad completa

Cuando vuestra app lee `builder.Configuration["ClaveX"]`, .NET consulta las fuentes **en orden de prioridad**. Conocer este orden es crítico:

```
Orden de prioridad en .NET 8 (de menor a mayor = la ÚLTIMA gana):

1. appsettings.json                          (base, commiteada)
2. appsettings.{Environment}.json            (específico por env)
3. appsettings.{MachineName}.json            (por máquina, raro)
4. User Secrets                              (solo Development)
5. Environment Variables                     (producción)
6. Command-line arguments                    (override rápido)

En App Service:
├── appsettings.json ← incluido en el deploy
├── appsettings.Production.json ← si existe
├── User Secrets ← NO existen en App Service (ok)
├── Environment Variables ← las App Settings del portal
└── Azure Key Vault (cuando se configura)  ← MAX prioridad

El valor final: el último que "encuentre" la clave.
```

**Demostración práctica:**
```csharp
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// Orden visible al arrancar (debug)
foreach (var provider in ((IConfigurationRoot)builder.Configuration).Providers)
{
    Console.WriteLine($"Provider: {provider.GetType().Name}");
}

// Output típico:
// Provider: JsonConfigurationProvider (appsettings.json)
// Provider: JsonConfigurationProvider (appsettings.Production.json)  
// Provider: EnvironmentVariablesConfigurationProvider
// (cualquier ENV VAR con ese nombre gana sobre appsettings.json)
```

## Slide 20 — User Secrets: el secreto local del desarrollador

Para desarrollo local, **NUNCA pongáis secretos en appsettings.json** (aunque sea "Development"). Usar User Secrets:

```bash
# Inicializar user secrets para el proyecto
cd src/VentasApi
dotnet user-secrets init
# Añade <UserSecretsId>...</UserSecretsId> al .csproj

# Eliminar uno
dotnet user-secrets remove "ConnectionStrings:DefaultConnection"

# Eliminar todos

```

**Dónde se guardan:**
```
Windows:  %APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json
Linux:    ~/.microsoft/usersecrets/<UserSecretsId>/secrets.json
```

**Claves importantes:**
- Solo funciona en environment `Development`
- NO están en el repo (fuera del working directory del proyecto)
- Cada dev tiene los suyos (no compartidos)
- Al desplegar a Azure, IGNORADOS (usa App Settings en su lugar)
- El `.csproj` solo tiene el ID, no los valores

## Slide 21 — IOptions: IOptions vs IOptionsSnapshot vs IOptionsMonitor

Confusión clásica en .NET. Cada uno tiene su momento:

```csharp
// Strongly-typed config class
public class DatabaseOptions
{
    public string ConnectionString { get; set; } = "";
    public int MaxPoolSize { get; set; } = 100;
    public TimeSpan Timeout { get; set; } = TimeSpan.FromSeconds(30);
}

// Program.cs: registrar
builder.Services.Configure<DatabaseOptions>(
    builder.Configuration.GetSection("Database"));
```

**Las 3 formas de inyectarlo:**

```csharp
// 1. IOptions<T> — Singleton, valor fijo al arranque
public class OrderService(IOptions<DatabaseOptions> options)
{
    private readonly DatabaseOptions _opts = options.Value;
    // _opts NUNCA cambia durante la vida de la app
}

// 2. IOptionsSnapshot<T> — Scoped, se refresca por request
public class OrderService(IOptionsSnapshot<DatabaseOptions> options)
{
    // Nuevo snapshot en cada request
    // Refleja cambios en appsettings.json (file watcher)
    // Útil para reload sin reinicio
}

// 3. IOptionsMonitor<T> — Singleton con callback, detecta cambios en tiempo real
public class OrderService(IOptionsMonitor<DatabaseOptions> optionsMonitor)
{
    public OrderService(IOptionsMonitor<DatabaseOptions> optionsMonitor)
    {
        _opts = optionsMonitor.CurrentValue;  // valor actual
        
        // Callback cuando cambia
        optionsMonitor.OnChange(newOpts => {
            _opts = newOpts;
            _logger.LogInformation("Config changed, new pool size: {size}", newOpts.MaxPoolSize);
        });
    }
}
```

**Cuándo usar cada una:**

| Uso | Elige |
|---|---|
| Config del sistema (versiones, paths, constantes) | IOptions |
| Config que puede cambiar y queréis refresh por request | IOptionsSnapshot |
| Config dinámica (feature flags, rate limits) que cambia en runtime | IOptionsMonitor |

Para la mayoría de casos: **IOptions es suficiente**. No compliquéis si no hace falta.

## Slide 22 — Config binding con validación

Validar que la config sea correcta al arrancar evita sorpresas en runtime:

```csharp
public class ApiOptions
{
    [Required]
    [Url]
    public string BaseUrl { get; set; } = "";

    [Range(1, 100)]
    public int MaxRetries { get; set; } = 3;

    [Required]
    public string ApiKey { get; set; } = "";

    public TimeSpan RequestTimeout { get; set; } = TimeSpan.FromSeconds(30);
}

// Program.cs — bind con validación
builder.Services
    .AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection("Api"))
    .ValidateDataAnnotations()        // valida los [Required], [Range]...
    .ValidateOnStart();                // falla al arrancar si hay errores
```

**Validación custom más potente:**
```csharp
public class ApiOptionsValidator : IValidateOptions<ApiOptions>
{
    public ValidateOptionsResult Validate(string? name, ApiOptions opts)
    {
        var errors = new List<string>();
        
        if (!Uri.TryCreate(opts.BaseUrl, UriKind.Absolute, out _))
            errors.Add($"BaseUrl '{opts.BaseUrl}' no es una URL válida");
        
        if (opts.ApiKey.Length < 32)
            errors.Add("ApiKey debe tener al menos 32 caracteres");
        
        return errors.Count == 0
            ? ValidateOptionsResult.Success
            : ValidateOptionsResult.Fail(errors);
    }
}

// Registrar
builder.Services.AddSingleton<IValidateOptions<ApiOptions>, ApiOptionsValidator>();
```

**Resultado al arrancar con config mal:**
```
Unhandled exception. Microsoft.Extensions.Options.OptionsValidationException:
- ApiKey debe tener al menos 32 caracteres
- BaseUrl 'not-a-url' no es una URL válida

Application stopped.
```

**Mejor fallar arrancando que 2 horas después en producción** cuando un endpoint use la config.

## Slide 23 — Hot reload: cambiar config sin restart

**.NET 8** soporta reload dinámico de config cuando el archivo cambia. En App Service, los cambios de App Settings reinician la app. Pero para Key Vault / App Configuration, podéis tener reload real:

```csharp
// Program.cs — config con reload automático
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options
        .Connect(new Uri(builder.Configuration["AppConfigEndpoint"]!),
                 new DefaultAzureCredential())
        .ConfigureRefresh(refresh =>
        {
            refresh.Register("Sentinel", refreshAll: true)
                   .SetRefreshInterval(TimeSpan.FromMinutes(5));
        })
        .UseFeatureFlags();
});

// Middleware que dispara el refresh
builder.Services.AddAzureAppConfiguration();
app.UseAzureAppConfiguration();
```

**Cómo funciona:**
1. App lee config de Azure App Configuration al arrancar
2. Cada 5 min, middleware verifica la key "Sentinel"
3. Si cambió (vosotros actualizasteis Sentinel manualmente en App Config), dispara refresh
4. Valores nuevos se propagan a `IOptionsMonitor`
5. Servicios que usan IOptionsMonitor ven el cambio

**Por qué "Sentinel":** en vez de consultar todas las keys cada 5 min (caro), solo se consulta Sentinel. Cuando cambie la config, cambiáis **también** Sentinel para disparar refresh.

**Casos de uso:**
- Feature flags (activar/desactivar sin restart)
- Rate limits dinámicos
- Mensajes de mantenimiento
- Modos de operación (readonly, normal, degraded)

## Slide 25 — Key Vault: RBAC vs Access Policies

Key Vault tiene **dos modelos** de autorización. Microsoft está migrando todo a RBAC:

```
Access Policies (legacy, antes de 2020):
├── Policies específicas de Key Vault
├── Permisos: Get, List, Set, Delete sobre secrets/keys/certs
├── Hasta 1024 policies por KV
├── Asignadas por principal (user, app, SP)
└── DEPRECATED para nuevos KVs (Microsoft recomienda RBAC)

Azure RBAC (moderno, recommended desde 2022):
├── Permisos estándar de Azure (Role assignments)
├── Roles built-in:
│   ├── Key Vault Reader (lista, lee metadatos, no valores)
│   ├── Key Vault Secrets User (lee valores de secrets)
│   ├── Key Vault Secrets Officer (lee + crea secrets)
│   ├── Key Vault Administrator (todo)
│   └── Key Vault Certificates Officer (certificados)
├── Se asigna como cualquier rol Azure
└── Audit completo via Activity Log
```

```bash
# Crear KV nuevo con RBAC (recomendado)
az keyvault create \
  --name kv-ventas-prod -g rg-ventas-prod \
  --location westeurope \
  --enable-rbac-authorization true

# Asignar rol al MI del App Service
APP_MI=$(az webapp identity show --name app-ventas -g rg-ventas-prod --query principalId -o tsv)
KV_ID=$(az keyvault show --name kv-ventas-prod --query id -o tsv)

az role assignment create \
  --assignee $APP_MI \
  --role "Key Vault Secrets User" \
  --scope $KV_ID
```

**Regla 2026:** nuevos Key Vaults siempre con RBAC. Migrar los antiguos cuando sea viable.

## Slide 26 — Rotación automática de secretos

Secretos hardcoded o "puestos una vez y olvidados" son un problema de seguridad. Automatizad la rotación:

```
Patrón recomendado:

1. Secretos con expiración obligatoria:
   - API keys: rotación cada 90 días
   - Connection strings con passwords: cada 90 días
   - Client Secrets (App Registrations): cada 12 meses máx
   - Certificates: cada 12-24 meses

2. Rotación automática:
   - Azure Key Vault puede rotar certificados TLS automáticamente
   - Azure SQL puede rotar credentials sync con Key Vault
   - Cosmos DB key rotation se coordina con KV
   - Storage Account keys rotation automática vía Event Grid

3. Alertas proactivas:
   - Alert en KV cuando un secreto caduca en <30 días
   - Dashboard con todos los secretos y fechas
```

```bash
# Ejemplo: configurar expiration al añadir un secret
az keyvault secret set \
  --vault-name kv-ventas-prod \
  --name "ApiKey-Stripe" \
  --value "<secret>" \
  --expires "2026-07-22T00:00:00Z" \
  --tags rotationPolicy="90days" owner="payments-team"

# Alerta sobre secretos próximos a caducar (via Azure Monitor)
az monitor scheduled-query create \
  --name "secrets-caducando" -g rg-monitoring \
  --scopes "<kv-id>" \
  --condition "count > 0" \
  --condition-query "AzureDiagnostics | where ResourceType == 'VAULTS' | where Expires < ago(-30d)" \
  --severity 2
```

## Slide 27 — Appsettings precedencia: ejemplo end-to-end

Ejemplo completo: de dónde sale cada valor en producción:

```
Clave: Database:ConnectionString

Fuentes (orden de prioridad, de menor a mayor):

1. appsettings.json  (commiteado al repo)
   → "Database:ConnectionString" = "Data Source=localhost;..."

2. appsettings.Production.json (también commiteado)
   → "Database:ConnectionString" = "@Microsoft.KeyVault(...)"

3. App Settings del App Service (configurado en portal)
   → Database__ConnectionString = "@Microsoft.KeyVault(SecretUri=https://kv-ventas.vault.azure.net/secrets/DbConn)"
   
4. Key Vault Secret (referenciado desde arriba)
   → Secret "DbConn" = "Server=tcp:sql-ventas.database.windows.net;..."

Al arrancar la app en prod:
├── Lee appsettings.json → tiene localhost (no se usa)
├── Lee appsettings.Production.json → referencia KV
├── Lee App Settings → MISMA referencia KV (gana por precedencia)
├── Resuelve Key Vault Reference → SI MI tiene acceso → valor real
└── Final: connection string real a SQL Azure

Si algo falla:
├── MI sin rol en KV → KV ref no resuelve → value = "@Microsoft.KeyVault(..."
├── App intenta conectar a "@Microsoft.KeyVault(..." como literal
└── Error de BBDD → log con pista del problema
```

**Debugging:** Si un valor no está donde esperáis, revisad TODAS las fuentes en orden. 90% de problemas son de precedencia mal entendida.

## Slide 28 — Config scrubbing: no loguear secretos

Al loggear config para debug, podéis exponer secretos accidentalmente:

```csharp
// ❌ MAL: dump entero de config
_logger.LogInformation("Config: {config}", builder.Configuration);
// Output puede incluir "ConnectionString": "Server=...;Password=secret123"

// ✅ BIEN: scrubbing explícito
public static class ConfigExtensions
{
    private static readonly string[] SecretPatterns = 
    {
        "password", "secret", "key", "token", "connectionstring", "apikey"
    };

    public static IEnumerable<KeyValuePair<string, string?>> ToScrubbedPairs(
        this IConfiguration config)
    {
        foreach (var kv in config.AsEnumerable())
        {
            var isSecret = SecretPatterns.Any(p => 
                kv.Key.Contains(p, StringComparison.OrdinalIgnoreCase));
            yield return new KeyValuePair<string, string?>(
                kv.Key, 
                isSecret ? "***REDACTED***" : kv.Value);
        }
    }
}

// Uso seguro
var scrubbed = builder.Configuration.ToScrubbedPairs();
foreach (var kv in scrubbed)
    _logger.LogInformation("Config: {key} = {value}", kv.Key, kv.Value);
```

**Otros sitios donde revisar:**
- Exception messages (que puedan incluir conn strings)
- Stack traces que expongan rutas sensibles
- App Insights (deshabilitar telemetría de secretos)

**Tip enterprise:** configurar Application Insights con `TelemetryProcessors` que eliminen propiedades sensibles antes de enviar.

## Slide 29 — App Configuration labels: multi-entorno limpio

Azure App Configuration soporta **labels** para separar config por entorno:

```
Misma key "Database:ConnectionString" con 3 labels:

Key: Database:ConnectionString
Label: dev         → Value: "Server=dev-sql...;User=dev"
Label: staging     → Value: "Server=stg-sql...;User=stg"
Label: production  → Value: "Server=prod-sql...;User=prod"

Cuando la app arranca:
├── Identifica su entorno (ASPNETCORE_ENVIRONMENT = "Production")
├── Consulta App Configuration con label="Production"
└── Obtiene el valor correcto
```

```csharp
// Program.cs
var env = builder.Environment.EnvironmentName; // "Development", "Production", etc.

builder.Configuration.AddAzureAppConfiguration(options =>
{
    options
        .Connect(endpoint, new DefaultAzureCredential())
        // Cargar primero labels "null" (common), luego label específico del env
        .Select(KeyFilter.Any, LabelFilter.Null)
        .Select(KeyFilter.Any, env);   // override con env-specific
});
```

**Beneficios:**
- Una sola App Configuration para toda la empresa
- Keys compartidas con labels específicos para overrides
- Deploy del mismo código con diferente config por entorno
- Fácil promover config entre entornos (copiar con nuevo label)

## Slide 30 — Validación config con DataAnnotations + FluentValidation

Para validación más potente que DataAnnotations, FluentValidation + options:

```csharp
// Install: dotnet add package FluentValidation.AspNetCore

public class ApiOptions
{
    public string BaseUrl { get; set; } = "";
    public int MaxRetries { get; set; }
    public string ApiKey { get; set; } = "";
    public List<string> AllowedIps { get; set; } = new();
}

public class ApiOptionsValidator : AbstractValidator<ApiOptions>
{
    public ApiOptionsValidator()
    {
        RuleFor(x => x.BaseUrl)
            .NotEmpty()
            .Must(url => Uri.TryCreate(url, UriKind.Absolute, out _))
            .WithMessage("BaseUrl must be valid URL");

        RuleFor(x => x.MaxRetries)
            .InclusiveBetween(0, 10);

        RuleFor(x => x.ApiKey)
            .NotEmpty()
            .MinimumLength(32);

        RuleForEach(x => x.AllowedIps)
            .Must(ip => System.Net.IPAddress.TryParse(ip, out _))
            .WithMessage("Each IP must be valid");
    }
}

// Program.cs — registrar con FluentValidation
builder.Services
    .AddOptions<ApiOptions>()
    .Bind(builder.Configuration.GetSection("Api"))
    .ValidateFluentValidation()   // extensión custom (ver abajo)
    .ValidateOnStart();

// Extensión helper
public static class OptionsBuilderExtensions
{
    public static OptionsBuilder<T> ValidateFluentValidation<T>(
        this OptionsBuilder<T> builder) where T : class
    {
        builder.Services.AddSingleton<IValidateOptions<T>>(
            sp => new FluentValidationOptionsValidator<T>(
                sp.GetRequiredService<IValidator<T>>()));
        return builder;
    }
}
```

FluentValidation da mensajes más claros + composition de reglas complejas.

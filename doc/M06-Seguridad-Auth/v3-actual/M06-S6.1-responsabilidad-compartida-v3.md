## Slide 2 — Por qué un módulo de seguridad
Hasta ahora hemos mencionado la seguridad de pasada: Managed Identity en el módulo 5, HTTPS en el módulo 2, RBAC en el módulo 1. Este módulo conecta todos los puntos en un marco coherente.

La realidad es que el 80% de las brechas de seguridad en la nube son errores de configuración del cliente — no fallos de Azure. Connection strings en repos, bases de datos sin firewall, endpoints públicos sin autenticación. Azure os da las herramientas. Usarlas es vuestra responsabilidad.

**La línea que NUNCA cambia:** Tus datos, tus identidades y tus dispositivos son SIEMPRE tu responsabilidad. En cualquier modelo. Sin excepción.

## Slide 4 — Los errores más comunes (y más caros)

**1. "Está en Azure, así que está seguro"**
Azure protege el datacenter, la red física y el hipervisor. Si tu Cosmos DB tiene la connection string en un repo público, Azure no puede impedir que alguien la use.

**2. Connection strings en código fuente**
El clásico. Un `git push` con la key de producción en `appsettings.json`. Cualquiera con acceso al repo tiene acceso total a la base de datos.

**3. Storage Account público por defecto**
Antes de 2023, los Storage Accounts permitían acceso anónimo a blobs por defecto. Si tenéis cuentas antiguas, verificad `--allow-blob-public-access`.

**4. Firewall de SQL abierto a 0.0.0.0/0**
"Para que funcione desde mi casa" → toda internet puede intentar conectarse.

**5. Sin MFA para administradores**
Un admin con password filtrada y sin MFA = acceso total a la suscripción Azure.

**6. Secretos sin rotación**
La misma API key lleva 3 años en App Settings. Si se filtró en algún momento, siguen teniendo acceso.

## Slide 5 — Defense in Depth: seguridad por capas

No confiéis en una sola medida de seguridad. Usad múltiples capas:

```
┌─────────────────────────────────────────┐
│ Capa 1: IDENTIDAD (Entra ID, MFA, RBAC)│  ← Quién eres
│ ┌─────────────────────────────────────┐ │
│ │ Capa 2: RED (Firewall, NSG, VNet)  │ │  ← Desde dónde vienes
│ │ ┌─────────────────────────────────┐ │ │
│ │ │ Capa 3: APLICACIÓN (Auth, CORS) │ │ │  ← Qué puedes hacer
│ │ │ ┌─────────────────────────────┐ │ │ │
│ │ │ │ Capa 4: DATOS (Cifrado, MI) │ │ │ │  ← Qué puedes ver
│ │ │ └─────────────────────────────┘ │ │ │
│ │ └─────────────────────────────────┘ │ │
│ └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

Si el atacante pasa la capa 1 (credencial robada), la capa 2 (firewall) puede bloquearlo. Si pasa la 2, la capa 3 (autenticación de la app) lo frena. Si pasa la 3, la capa 4 (cifrado) protege los datos.

## Slide 6 — Capa 1: Identidad y acceso

**Microsoft Entra ID (antes Azure AD):**
El servicio de identidad central. Todos los usuarios, grupos y aplicaciones se gestionan aquí.

**Componentes clave:**
- **Usuarios:** Cuentas corporativas (pedro@empresa.com)
- **Grupos:** Agrupaciones para asignar permisos en bloque
- **App Registrations:** Identidades para aplicaciones (OAuth2)
- **Service Principals:** Identidades para automatización (pipelines)
- **Managed Identities:** Identidades automáticas para recursos Azure

**MFA (Multi-Factor Authentication):**
Obligatorio para administradores. Recomendado para todos. Si alguien roba la password, sin el segundo factor no entra.

**Conditional Access:**
Reglas tipo: "Si el login es desde fuera de España, requerir MFA. Si es desde un dispositivo no corporativo, bloquear."

---

## Slide 7 — Capa 2: Red y perimetral

**Network Security Groups (NSG):** Reglas de firewall para subnets y NICs.
**Azure Firewall:** Firewall centralizado para toda la VNet.
**App Service Access Restrictions:** IP whitelist por app.
**Storage Account Firewall:** `--default-action Deny` + excepciones.
**SQL Server Firewall:** Solo IPs permitidas.
**Private Endpoints:** Acceso a servicios Azure solo desde VNet (sin internet).

```bash
# Verificar que Storage no está abierto al mundo
az storage account show --name stventasprod -g mi-rg \
  --query "networkRuleSet.defaultAction"
# Debería ser "Deny"

# Verificar que SQL tiene firewall configurado
az sql server firewall-rule list --server sql-ventas-prod -g mi-rg --output table
# No debería haber regla 0.0.0.0-255.255.255.255
```

## Slide 8 — Capa 3: Aplicación

**Autenticación:** Verificar quién es el usuario (OAuth2, OpenID Connect, Entra ID).
**Autorización:** Verificar qué puede hacer (roles, claims, policies).
**CORS:** Controlar qué dominios pueden llamar a tu API.
**Input Validation:** Nunca confiar en los datos del usuario (SQL injection, XSS, path traversal).
**Rate Limiting:** Proteger contra abuso y DDoS a nivel de aplicación.
**HTTPS Only:** Forzar TLS para todo el tráfico.

```csharp
// Ejemplo: validación + autorización en una Function
[Function("GetPedido")]
public async Task<IActionResult> Get(
    [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "pedidos/{id}")] HttpRequest req,
    string id)
{
    // Autenticación: verificar token
    var user = req.HttpContext.User;
    if (!user.Identity?.IsAuthenticated ?? true)
        return new UnauthorizedResult();
    
    // Autorización: solo el cliente puede ver sus pedidos
    var userId = user.FindFirst("sub")?.Value;
    var pedido = await _db.GetPedidoAsync(id);
    if (pedido.ClienteId != userId)
        return new ForbidResult();
    
    return new OkObjectResult(pedido);
}
```

## Slide 9 — Capa 4: Datos

**Cifrado en reposo (at-rest):** AES-256 automático en todos los servicios Azure. Sin configuración.
**Cifrado en tránsito (in-transit):** TLS 1.2+ obligatorio.
**Managed Identity:** Sin passwords en connection strings (módulo 5).
**Key Vault:** Secretos centralizados, rotación automática, acceso auditado.
**Data Classification:** Marcar datos sensibles (PII, financieros) para aplicar políticas específicas.
**Customer-Managed Keys (CMK):** Si regulación lo exige, vosotros controláis las claves de cifrado.

## Slide 11 — Azure Policy para seguridad

Políticas de seguridad que se aplican automáticamente:

```bash
# HTTPS obligatorio en App Service
az policy assignment create \
  --name "force-https" \
  --policy "App Service apps should only be accessible over HTTPS" \
  --scope "/subscriptions/<id>" \
  --enforcement-mode Default

# TLS 1.2 mínimo en Storage
az policy assignment create \
  --name "force-tls12" \
  --policy "Storage accounts should have minimum TLS version" \
  --scope "/subscriptions/<id>"

# Managed Identity obligatoria en App Service
az policy assignment create \
  --name "force-mi" \
  --policy "App Service apps should use managed identity" \
  --scope "/subscriptions/<id>"
```

**Initiative (grupo de políticas):** Azure tiene un initiative "Azure Security Benchmark" con ~200 políticas de seguridad predefinidas. Asignadlo a la suscripción y tendréis una línea base completa.

## Slide 13 — Zero Trust: el principio moderno

Zero Trust = no confíes en nadie ni en nada por defecto:

**Principios:**
1. **Verificar explícitamente:** Autenticar y autorizar cada petición, siempre.
2. **Mínimo privilegio:** Dar exactamente los permisos necesarios, nada más.
3. **Asumir brecha:** Diseñar como si el atacante ya estuviera dentro. Segmentar, cifrar, monitorizar.

**En la práctica:**
- Managed Identity en vez de shared keys (verificar explícitamente)
- RBAC con roles específicos en vez de Owner (mínimo privilegio)
- Private Endpoints en vez de acceso público (asumir brecha)
- Conditional Access: MFA según contexto (verificar explícitamente)
- Micro-segmentación: cada servicio en su subnet (asumir brecha)

## Slide 15 — Compliance: GDPR y regulación

**GDPR (Reglamento General de Protección de Datos):**
- Datos de ciudadanos de la UE → obligaciones de privacidad
- Azure cumple con GDPR a nivel de infraestructura
- VOSOTROS cumplís con GDPR a nivel de aplicación y datos

**Lo que Azure os da:**
- Regiones dentro de la UE (datos no salen de Europa)
- Cifrado at-rest y in-transit
- Herramientas de auditoría y export de datos
- Data Processing Agreement (DPA) incluido

**Lo que debéis hacer vosotros:**
- Identificar qué datos personales almacenáis
- Implementar derecho de acceso (el usuario pide sus datos → se los dais)
- Implementar derecho de supresión (el usuario pide borrar → lo borráis)
- Registro de actividades de procesamiento
- Notificar brechas en 72 horas

**KQL queries esenciales para SOC:**
```kusto
// 1. Sign-ins anormales (location nueva)
SigninLogs
| where TimeGenerated > ago(7d)
| where ResultType == 0  // success
| extend Country = tostring(LocationDetails.countryOrRegion)
| summarize Countries = make_set(Country) by UserPrincipalName
| where array_length(Countries) > 2  // user signed from 3+ countries
| order by array_length(Countries) desc

// 2. Brute force attacks
SigninLogs
| where TimeGenerated > ago(1h)
| where ResultType != 0  // failed
| summarize FailedAttempts = count() by IPAddress, UserPrincipalName
| where FailedAttempts > 10

// 3. Suspicious admin activity
AuditLogs
| where TimeGenerated > ago(24h)
| where Category == "RoleManagement"
| where OperationName contains "Add member to role"
| project TimeGenerated, InitiatedBy, TargetResources, OperationName

// 4. Mass file deletion (potential ransomware)
StorageBlobLogs
| where TimeGenerated > ago(15m)
| where OperationName == "DeleteBlob"
| summarize Deletions = count() by AccountName, AuthenticationType, CallerIpAddress
| where Deletions > 100
```

## Slide 20 — Threat Modeling: STRIDE en práctica

Antes de codificar, modelad las amenazas. STRIDE es un framework simple:

```
STRIDE — 6 categorías de amenazas:

┌──────────────────────────────────────────────────────────────────┐
│  S - Spoofing       │ Someone impersonating a user/service        │
│  T - Tampering      │ Modifying data in transit or at rest        │
│  R - Repudiation    │ User denies action they took                │
│  I - Info Disclosure│ Confidential data leak                      │
│  D - DoS            │ Service unavailable                         │
│  E - Elevation      │ Gaining permissions you shouldn't have      │
└──────────────────────────────────────────────────────────────────┘
```

**Ejemplo: API REST de pedidos**

```
Componente: API Pedidos /orders endpoint

Amenazas y mitigaciones:
─────────────────────────

S - Spoofing
├── Threat: Attacker impersona usuario legítimo
└── Mitigation: 
    ├── OAuth2 + OIDC (token de Entra ID)
    ├── MFA en login
    └── Conditional Access policies

T - Tampering
├── Threat: Modificar request body para cambiar amount
└── Mitigation:
    ├── HTTPS only (TLS 1.2+)
    ├── Validate body schema en server
    └── Server-side recalc de totals

R - Repudiation
├── Threat: User dice "no hice ese pedido"
└── Mitigation:
    ├── Audit log con UserPrincipalName + timestamp
    ├── IP address + user agent capturados
    └── Logs en Log Analytics (immutable)

I - Information Disclosure
├── Threat: Otro usuario ve tus pedidos
└── Mitigation:
    ├── Row-Level Security en SQL
    ├── Authorize attribute con [Authorize(Roles="Customer")]
    └── Filter by current user en query
    
D - DoS
├── Threat: Bombardeo /orders endpoint
└── Mitigation:
    ├── Rate limiting (APIM o middleware)
    ├── Per-user quotas
    └── Auto-scaling

E - Elevation
├── Threat: Customer accede a /admin endpoint
└── Mitigation:
    ├── [Authorize(Roles="Admin")] attribute
    ├── App Roles definidos en App Registration
    └── Validate roles claim en token
```

**Microsoft Threat Modeling Tool:**
```
Free tool de Microsoft:
https://aka.ms/threatmodelingtool

Workflow:
├── 1. Diagrama de arquitectura (drag & drop)
├── 2. Tool aplica STRIDE automáticamente
├── 3. Genera lista de threats por componente
├── 4. Para cada: asignar mitigation
└── 5. Track residual risks
```

**Cuándo hacer threat modeling:**
- ✅ Inicio de proyecto (al diseñar)
- ✅ Antes de release de feature crítica
- ✅ Después de incident (para evitar repetir)
- ✅ Al integrar sistema externo
- ❌ "Cuando tengamos tiempo" → never happens

**Real-world ROI:**
```
Estudio Microsoft (2024):
├── Threat modeling temprano: €500-2000 por feature
├── Vulnerability post-deploy: €15K-100K (avg)
├── Breach por vuln no detectada: €4.5M (Cost of Data Breach 2024)
└── ROI: 100x conservador
```

## Slide 21 — Supply chain security: SBOM, scans, signed code

Tu app no es solo tu código — es **tu código + 1000 dependencias**. Cada una es vector de ataque:

```
Tu app .NET típica:
├── Tu código (10K líneas)
└── NuGet packages (50+)
    ├── Que dependen de otros (200+ transitively)
        └── Que dependen de C/C++ libs (50+)
```

## Slide 22 — Secrets scanning: prevenir leaks en git

Secrets en repositorios = #1 cause de breaches accidentales:

```
"Pero el repo es privado"
└── ❌ No importa: empleados que rotan, repos archivados, GitHub Issues, etc

"Borré el commit con el secret"
└── ❌ git history persiste; cualquier clone tiene el secret

"Solo era un dev key"
└── ❌ Many breaches: dev → prod escalation
```

**Pre-commit hooks (local, primer barrier):**
```bash
# Install gitleaks
brew install gitleaks  # mac
choco install gitleaks  # windows

# Configurar pre-commit hook
cat > .git/hooks/pre-commit << 'EOF'
#!/bin/bash
gitleaks protect --staged --verbose
if [ $? -ne 0 ]; then
    echo "❌ Secrets detected. Commit blocked."
    exit 1
fi
EOF
chmod +x .git/hooks/pre-commit
```

**Custom rules (gitleaks.toml):**
```toml
title = "Empresa custom rules"

[[rules]]
id = "azure-storage-key"
description = "Azure Storage Account Key"
regex = '''AccountKey=[A-Za-z0-9+/=]{88}'''
tags = ["azure", "secret"]

[[rules]]
id = "internal-api-key"
description = "Internal API Key"
regex = '''empresa_[a-zA-Z0-9]{32}'''
tags = ["empresa", "secret"]

[allowlist]
paths = [
    '''.*example.*''',
    '''.*test.*'''
]
```

**GitHub Advanced Security (paid):**
```yaml
# .github/workflows/security.yml
name: Security Scanning

on: [push, pull_request]

jobs:
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Need full history
      
      # GitHub native (with Advanced Security)
      - name: Run secret scanning
        uses: github/super-linter@v6
        env:
          DEFAULT_BRANCH: main
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      
      # Alternativa OSS
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GITLEAKS_LICENSE: ${{ secrets.GITLEAKS_LICENSE }}
      
      # Trufflehog (más profundo)
      - uses: trufflesecurity/trufflehog@main

          path: ./
```

**Si encontráis un secret leaked:**
```

1. INMEDIATAMENTE rotate la credential
   ├── Storage key: az storage account keys renew
   ├── App password: regenerate in App Registration
   ├── DB password: change + update KV
   └── API key: revoke + reissue

   git filter-branch --force --index-filter \

     --prune-empty --tag-name-filter cat -- --all
   git push --force --all
   
   ⚠️ Esto rompe a otros con clones. Best: just rotate.

4. Notify security team + post-mortem
```

## Slide 23 — Zero Trust en práctica: implementación real

Zero Trust = "Never trust, always verify". Pasamos del concepto a setup concreto:

```
Tradicional (Castle & Moat):
   Internet ──── Firewall ──── Trusted Internal Network
   "Si está dentro, es OK"

Zero Trust:
   Internet ──── Verify Every Request ──── Resource
                  ├── Identity?
                  ├── Device compliant?
                  ├── Location risk?
                  ├── Behavior anomaly?
                  └── Data classification?
```

**Los 6 pilares de Zero Trust (Microsoft framework):**

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. IDENTITIES                                                    │
│ ✅ Strong auth (MFA, FIDO2, passwordless)                       │
│ ✅ Conditional Access policies                                  │
│ ✅ Identity Protection (risk-based)                             │
│ ✅ Privileged Identity Management (just-in-time)                │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 2. ENDPOINTS (devices)                                           │
│ ✅ Compliant devices only (Intune)                              │
│ ✅ Endpoint Detection & Response (Defender for Endpoint)        │
│ ✅ Device-bound credentials                                     │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 3. APPLICATIONS                                                  │
│ ✅ Apps registered en Entra ID                                  │
│ ✅ App-to-app auth (Managed Identity, no shared secrets)        │
│ ✅ App permissions granular (least privilege)                   │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 4. DATA                                                          │
│ ✅ Classification (Sensitivity labels)                          │
│ ✅ Encryption at rest + in transit                              │
│ ✅ DLP policies (data loss prevention)                          │
│ ✅ Information Rights Management (IRM)                          │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 5. INFRASTRUCTURE                                                │
│ ✅ Just-in-time VM access                                       │
│ ✅ NSG / Firewall / Private Endpoints                           │
│ ✅ Bastion (no public RDP/SSH)                                  │
│ ✅ Defender for Cloud monitoring                                │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 6. NETWORK                                                       │
│ ✅ Microsegmentation (NSG por subnet)                           │
│ ✅ Encryption inter-service (TLS 1.2+)                          │
│ ✅ DDoS Protection                                              │
│ ✅ Private Link (no traffic over internet)                      │
└─────────────────────────────────────────────────────────────────┘
```

**Conditional Access típico Zero Trust:**
```
Policy 1: "Require MFA for all access"
├── Apply to: All users (excluding break-glass)
├── Conditions: Any cloud app
└── Grant: Require MFA

Policy 2: "Require compliant device for sensitive apps"
├── Apply to: All users
├── Conditions: Sensitive apps (Production environment)
└── Grant: Require compliant device + MFA

Policy 3: "Block legacy authentication"
├── Apply to: All users
├── Conditions: Legacy auth clients (POP, IMAP, etc.)
└── Grant: Block

Policy 4: "Require auth strength for admins"
├── Apply to: All admin role members
├── Conditions: Any cloud app
└── Grant: Phishing-resistant auth (FIDO2 only)

Policy 5: "Block from risky countries"
├── Apply to: All users
├── Conditions: Locations = Risky countries
└── Grant: Block
```

**Maturity model (donde estáis):**
```
Level 1 - Traditional: VPN + on-prem AD
Level 2 - Advanced: Cloud identity + MFA + some Conditional Access
Level 3 - Optimal: Zero Trust mature implementation
                   Risk-based decisions in real-time
                   All 6 pillars instrumented
```

Most enterprises (2026): aprox Level 2. Goal: Level 3 over 1-2 years.

```csharp
// ❌ MAL
[HttpGet("{userId}/orders")]
public async Task<IActionResult> GetOrders(int userId)
{
    var orders = await _db.Orders.Where(o => o.UserId == userId).ToListAsync();
    return Ok(orders);  // anyone can pass any userId!
}

// ✅ BIEN
[Authorize]
[HttpGet("orders")]
public async Task<IActionResult> GetOrders()
{
    var currentUserId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
    var orders = await _db.Orders.Where(o => o.UserId == currentUserId).ToListAsync();
    return Ok(orders);
}

// A02: Cryptographic Failures
// ❌ MD5, SHA1, hardcoded keys
// ✅ AES-256-GCM, Argon2id para passwords, KeyVault for keys

// A03: Injection
// ❌ MAL: SQL injection
var query = $"SELECT * FROM Users WHERE Email = '{email}'";

// ✅ BIEN: Parameterized
var user = await _db.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE Email = {email}")
    .FirstOrDefaultAsync();

// A05: Security Misconfiguration
// ✅ Use Production startup, disable Swagger en prod
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}
app.UseHttpsRedirection();
app.UseHsts();

// A07: Authentication Failures  
// ❌ Custom auth logic
// ✅ Use Microsoft.Identity.Web (Microsoft Entra ID)
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration);

// A09: Logging Failures
// ❌ No logging or logs without context
// ✅ Structured logging + sensitive event logging
_logger.LogInformation("User {UserId} accessed resource {Resource}",
    User.FindFirst(ClaimTypes.NameIdentifier)?.Value,
    resourceId);

// A10: SSRF
// ❌ MAL: usar URLs sin validar
var content = await _http.GetStringAsync(userInputUrl);  // can fetch internal!

// ✅ BIEN: allowlist de domains
private static readonly HashSet<string> AllowedHosts = new() 
{ "api.partner.com", "data.public.gov" };

if (!AllowedHosts.Contains(new Uri(userInputUrl).Host))
    throw new SecurityException("URL not allowed");
```

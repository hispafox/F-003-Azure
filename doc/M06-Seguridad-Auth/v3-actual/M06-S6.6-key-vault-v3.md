## Slide 2 — Por qué Key Vault es imprescindible
Hasta aquí hemos visto Managed Identity para conexiones Azure-a-Azure. Pero ¿qué pasa con las API keys de servicios externos (Stripe, SendGrid, Twilio), los client secrets de App Registrations, los certificados SSL, las claves de cifrado custom?

Key Vault es el cofre central donde viven todos los secretos. Un solo lugar, auditado, con control de acceso granular, rotación y versionado.

**La regla:** Si es un secreto y no puede ser Managed Identity, va a Key Vault. Punto.

---

## Slide 3 — Qué almacena Key Vault

**Secrets:** Strings arbitrarios (API keys, passwords, connection strings, tokens).
**Keys:** Claves criptográficas RSA/EC para cifrado y firma (CMK, JWT signing).
**Certificates:** Certificados SSL/TLS con gestión de ciclo de vida y auto-renovación.

```
Key Vault (kv-ventas-prod)
├── Secrets
│   ├── CosmosDbConnection     → "AccountEndpoint=https://..."
│   ├── StripeApiKey           → "sk_live_abc123..."
│   ├── SendGridApiKey         → "SG.xyz789..."
│   └── AzureAd-ClientSecret  → "client-secret-value"
│
├── Keys
│   ├── data-encryption-key    → RSA 2048-bit (para CMK)
│   └── jwt-signing-key        → EC P-256 (para firmar tokens)
│
└── Certificates
    ├── wildcard-empresa-com   → *.empresa.com (auto-renew)
    └── api-ventas-cert        → api.ventas.empresa.com
```

## Slide 4 — Crear Key Vault y almacenar secretos

```bash
# Crear Key Vault
az keyvault create \
  --name kv-ventas-prod \
  --resource-group rg-ventas-prod \
  --location westeurope \
  --enable-purge-protection true \
  --enable-rbac-authorization true

# Almacenar secretos
az keyvault secret set --vault-name kv-ventas-prod \
  --name "StripeApiKey" --value "sk_live_abc123def456"

az keyvault secret set --vault-name kv-ventas-prod \
  --name "SendGridApiKey" --value "SG.abcdef123456"

az keyvault secret set --vault-name kv-ventas-prod \
  --name "AzureAd-ClientSecret" --value "client-secret-here" \
  --expires "2026-06-15T00:00:00Z"  # Con expiración

# Leer un secreto
az keyvault secret show --vault-name kv-ventas-prod --name "StripeApiKey" --query value -o tsv

# Listar secretos (solo nombres, no valores)
az keyvault secret list --vault-name kv-ventas-prod --query "[].name" -o tsv
```

## Slide 5 — Access control: RBAC vs Access Policies

Key Vault tiene dos modelos de permisos:

**RBAC (recomendado, nuevo):**
```bash
# Dar permiso a un usuario para leer secretos
az role assignment create \
  --assignee pedro@empresa.com \
  --role "Key Vault Secrets User" \
  --scope "/subscriptions/<id>/.../vaults/kv-ventas-prod"

# Dar permiso a una Managed Identity
az role assignment create \
  --assignee $PRINCIPAL_ID \
  --role "Key Vault Secrets User" \
  --scope "/subscriptions/<id>/.../vaults/kv-ventas-prod"
```

**Roles de Key Vault:**
| Rol | Secretos | Keys | Certificados |
|-----|:--------:|:----:|:------------:|
| Key Vault Administrator | CRUD | CRUD | CRUD |
| Key Vault Secrets User | Read | — | — |
| Key Vault Secrets Officer | CRUD | — | — |
| Key Vault Crypto User | — | Use | — |
| Key Vault Crypto Officer | — | CRUD | — |
| Key Vault Certificates Officer | — | — | CRUD |

**Access Policies (legacy):**
```bash
az keyvault set-policy --name kv-ventas-prod \
  --object-id $PRINCIPAL_ID \
  --secret-permissions get list
```
Funciona pero es menos granular que RBAC. Microsoft recomienda migrar a RBAC.

## Slide 6 — Key Vault References en App Settings

La forma más limpia de usar secretos de Key Vault en App Service y Functions:

```bash
# Requisitos:
# 1. La app tiene Managed Identity habilitada
# 2. La MI tiene rol "Key Vault Secrets User" en el KV

# Configurar App Setting como referencia a Key Vault
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --settings \
    StripeApiKey="@Microsoft.KeyVault(VaultName=kv-ventas-prod;SecretName=StripeApiKey)" \
    SendGridApiKey="@Microsoft.KeyVault(VaultName=kv-ventas-prod;SecretName=SendGridApiKey)" \
    AzureAd__ClientSecret="@Microsoft.KeyVault(VaultName=kv-ventas-prod;SecretName=AzureAd-ClientSecret)"
```

**En tu código:** Leéis las variables normalmente, sin saber que vienen de Key Vault:
```csharp
var stripeKey = builder.Configuration["StripeApiKey"];
// Devuelve "sk_live_abc123def456" — Azure resolvió la referencia
```

**En el portal:** La variable muestra "Key Vault Reference" con un indicador verde (resuelto) o rojo (error de acceso).

## Slide 7 — Key Vault SDK: acceso desde código

```csharp
using Azure.Security.KeyVault.Secrets;
using Azure.Identity;

// Conexión con Managed Identity
var client = new SecretClient(
    new Uri("https://kv-ventas-prod.vault.azure.net"),
    new DefaultAzureCredential());

// Leer secreto
KeyVaultSecret secret = await client.GetSecretAsync("StripeApiKey");
string valor = secret.Value;

// Crear/actualizar secreto
await client.SetSecretAsync("NuevoSecreto", "valor-secreto");

// Crear con metadata y expiración
await client.SetSecretAsync(new KeyVaultSecret("ApiKey", "valor")
{
    Properties = {
        ExpiresOn = DateTimeOffset.UtcNow.AddMonths(6),
        ContentType = "application/json",
        Tags = { ["entorno"] = "produccion", ["servicio"] = "stripe" }
    }
});

// Listar secretos
await foreach (var sp in client.GetPropertiesOfSecretsAsync())
{
    Console.WriteLine($"{sp.Name} | Expira: {sp.ExpiresOn} | Habilitado: {sp.Enabled}");
}

// Eliminar (soft delete)
var deleted = await client.StartDeleteSecretAsync("NuevoSecreto");
await deleted.WaitForCompletionAsync();

// Recuperar (si soft delete está habilitado)
await client.StartRecoverDeletedSecretAsync("NuevoSecreto");
```

## Slide 8 — Versionado de secretos

Cada vez que actualizáis un secreto, Key Vault crea una nueva versión:

```bash
# Versión 1
az keyvault secret set --vault-name kv-ventas-prod --name StripeApiKey --value "sk_live_OLD"

# Versión 2 (el nombre es el mismo — se crea nueva versión)
az keyvault secret set --vault-name kv-ventas-prod --name StripeApiKey --value "sk_live_NEW"

# Ver todas las versiones
az keyvault secret list-versions --vault-name kv-ventas-prod --name StripeApiKey \
  --query "[].{version:id, created:attributes.created, enabled:attributes.enabled}" -o table
```

**Key Vault References en App Service** apuntan siempre a la versión más reciente (por defecto). Cuando actualizáis el secreto en KV, la app obtiene el nuevo valor en el próximo reinicio o en ~24 horas (polling automático).

**Para forzar refresh inmediato:**
```bash
# Reiniciar la app para que re-lea los secretos
az webapp restart --name app-ventas -g rg-ventas-prod
```

## Slide 9 — Rotación automática de secretos

Key Vault puede emitir eventos cuando un secreto está a punto de expirar:

```bash
# Crear event subscription: 30 días antes de expirar, emitir evento
az eventgrid event-subscription create \
  --name sub-secret-expiring \
  --source-resource-id "/subscriptions/<id>/.../vaults/kv-ventas-prod" \
  --endpoint "https://func-rotacion.azurewebsites.net/api/RotarSecreto" \
  --included-event-types Microsoft.KeyVault.SecretNearExpiry
```

**Flujo de rotación automática:**
1. Secreto tiene expiración: 2025-12-31
2. 30 días antes → Event Grid dispara evento `SecretNearExpiry`
3. Azure Function recibe el evento → rota el secreto en el servicio externo
4. La Function actualiza el secreto en Key Vault con el nuevo valor
5. App Service obtiene el nuevo valor automáticamente

```csharp
[Function("RotarSecretoStripe")]
public async Task Rotar([EventGridTrigger] EventGridEvent evento)
{
    var secretName = evento.Subject; // "StripeApiKey"
    
    // 1. Generar nueva key en Stripe
    var nuevaKey = await _stripeService.RotarApiKeyAsync();
    
    // 2. Actualizar en Key Vault
    await _kvClient.SetSecretAsync(secretName, nuevaKey);
    
    _logger.LogInformation("Secreto {Name} rotado", secretName);
}
```

## Slide 10 — Certificados en Key Vault

```bash
# Importar certificado PFX existente
az keyvault certificate import \
  --vault-name kv-ventas-prod \
  --name cert-api-ventas \
  --file certificado.pfx \
  --password "pfx-password"

# Crear certificado auto-firmado (para testing)
az keyvault certificate create \
  --vault-name kv-ventas-prod \
  --name cert-test \
  --policy "$(az keyvault certificate get-default-policy)"

# Crear certificado con auto-renovación de Let's Encrypt / DigiCert
# (requiere integración con CA — configurar en el portal)

# Usar certificado en App Service
az webapp config ssl import \
  --name app-ventas -g rg-ventas-prod \
  --key-vault kv-ventas-prod \
  --key-vault-certificate-name cert-api-ventas
```

**Ventajas de certificados en Key Vault:**
- Centralizado: un solo lugar para todos los certificados
- Auto-renovación: con CA integrada (DigiCert, GlobalSign)
- Versionado: cada renovación es una nueva versión
- Alertas de expiración: Event Grid notifica antes de expirar
- Permisos granulares: solo ciertas apps pueden acceder a ciertos certificados

## Slide 11 — Keys: claves criptográficas

```bash
# Crear clave RSA para cifrado
az keyvault key create \
  --vault-name kv-ventas-prod \
  --name data-encrypt-key \
  --kty RSA --size 2048

# Crear clave EC para firmas digitales
az keyvault key create \
  --vault-name kv-ventas-prod \
  --name jwt-signing-key \
  --kty EC --curve P-256
```

```csharp
using Azure.Security.KeyVault.Keys.Cryptography;

// Cifrar datos con una key de Key Vault
var cryptoClient = new CryptographyClient(
    new Uri("https://kv-ventas-prod.vault.azure.net/keys/data-encrypt-key"),
    new DefaultAzureCredential());

var cifrado = await cryptoClient.EncryptAsync(EncryptionAlgorithm.RsaOaep, datosEnClaro);
var descifrado = await cryptoClient.DecryptAsync(EncryptionAlgorithm.RsaOaep, cifrado.Ciphertext);
```

**La clave privada NUNCA sale de Key Vault.** Las operaciones criptográficas se ejecutan dentro del servicio. Tu app envía los datos a cifrar y recibe el resultado. La clave permanece protegida.

**HSM (Hardware Security Module):** Para claves ultra-sensibles, Key Vault Premium usa HSM certificado FIPS 140-2 Level 2. La clave está en hardware dedicado.

## Slide 12 — Soft Delete y Purge Protection

```bash
# Soft delete: activado por defecto desde 2020
# Los secretos/keys/certs eliminados se mantienen 90 días

# Ver secretos eliminados
az keyvault secret list-deleted --vault-name kv-ventas-prod

# Recuperar un secreto eliminado
az keyvault secret recover --vault-name kv-ventas-prod --name SecretoEliminado

# Purge protection: una vez activado, NO se puede desactivar
# Impide borrado permanente incluso por admins
az keyvault update --name kv-ventas-prod -g mi-rg --enable-purge-protection true
```

**Purge Protection es obligatorio** si usáis Key Vault para CMK (Customer-Managed Keys). Sin purge protection, si alguien elimina la clave, perdéis acceso a los datos cifrados permanentemente.

## Slide 13 — Networking: acceso privado a Key Vault

```bash
# Restringir acceso público
az keyvault update --name kv-ventas-prod -g mi-rg --default-action Deny

# Permitir IP de la oficina
az keyvault network-rule add --name kv-ventas-prod -g mi-rg --ip-address 203.0.113.50

# Permitir servicios Azure de confianza
az keyvault update --name kv-ventas-prod -g mi-rg --bypass AzureServices

# Private Endpoint (acceso solo desde VNet)
az network private-endpoint create \
  --name pe-kv-ventas \
  --resource-group rg-ventas-prod \
  --vnet-name vnet-prod --subnet subnet-endpoints \
  --private-connection-resource-id "/subscriptions/<id>/.../vaults/kv-ventas-prod" \
  --group-ids vault --connection-name conn-kv-ventas
```

## Slide 18 — Múltiples Key Vaults: estrategia

**Un KV por entorno:**
```
kv-ventas-dev       → Secretos de desarrollo
kv-ventas-staging   → Secretos de staging
kv-ventas-prod      → Secretos de producción (acceso más restringido)
```

**Ventajas de separar:**
- Permisos diferentes: desarrolladores acceden a dev, no a prod
- Networking diferente: prod con Private Endpoint, dev sin restricciones
- Lifecycle diferente: dev se puede recrear, prod tiene purge protection

**Un KV compartido para certificados:**
```
kv-certs-empresa    → Todos los certificados SSL (acceso limitado a infra team)
```

## Slide 19 — Backup y DR de Key Vault

```bash
# Backup de un secreto individual
az keyvault secret backup --vault-name kv-ventas-prod --name StripeApiKey --file stripe-backup.blob

# Restore a otro Key Vault (misma suscripción)
az keyvault secret restore --vault-name kv-ventas-dr --file stripe-backup.blob
```

**Key Vault no tiene backup automático completo.** Cada secreto/key/cert se respalda individualmente. Automatizad con un script que backup todos los objetos periódicamente.

**Geo-redundancia:** Key Vault replica automáticamente a la región par. Si West Europe cae, los secretos están disponibles en North Europe (con un breve retraso).

## Slide 20 — Checklist de Key Vault para producción

- [ ] Purge Protection habilitado (obligatorio si CMK)
- [ ] RBAC habilitado (no legacy Access Policies)
- [ ] Permisos mínimos: apps con "Secrets User", no "Administrator"
- [ ] Networking: default-action Deny + bypass AzureServices
- [ ] Diagnostic Logs habilitados (auditoría de acceso)
- [ ] Alertas: acceso denegado, secreto expirando
- [ ] Expiración configurada en todos los secretos
- [ ] Rotación automatizada para secretos críticos
- [ ] Backup periódico de secretos a otro KV o Storage Account
- [ ] Separación por entorno: dev, staging, prod
- [ ] Client secrets de App Registrations en KV (no en App Settings directo)

## Slide 22 — Key Vault: certificados con auto-renovación

```bash
# Crear certificado con auto-renovación (DigiCert como CA)
az keyvault certificate create --vault-name kv-ventas-prod \
  --name wildcard-empresa \
  --policy "$(cat cert-policy.json)"
```

```json
{
  "issuerParameters": { "name": "DigiCertCA" },
  "keyProperties": { "exportable": true, "keySize": 2048, "keyType": "RSA" },
  "lifetimeActions": [
    { "action": { "actionType": "AutoRenew" },
      "trigger": { "daysBeforeExpiry": 30 } }
  ],
  "secretProperties": { "contentType": "application/x-pkcs12" },
  "x509CertificateProperties": {
    "subject": "CN=*.empresa.com",
    "validityInMonths": 12
  }
}
```

30 días antes de expirar, Key Vault renueva automáticamente con DigiCert. El nuevo certificado se propaga a las apps que lo usan.

## Slide 24 — Key Vault: Managed HSM (para máxima seguridad)

Para claves ultra-sensibles donde incluso Microsoft no debe poder acceder:

```bash
# Crear Managed HSM (dedicado, FIPS 140-2 Level 3)
az keyvault create --hsm-name mhsm-ventas-prod -g mi-rg --location westeurope \
  --administrators $(az ad signed-in-user show --query id -o tsv)
```

**Diferencias con Key Vault Standard/Premium:**
| | Key Vault | Managed HSM |
|---|---|---|
| Certificación | FIPS 140-2 Level 2 | FIPS 140-2 Level 3 |
| Tenant aislado | Shared infra | Dedicado |
| Microsoft acceso | Puede acceder con proceso legal | NO puede acceder nunca |
| Coste | ~0.03€/10K ops | ~3.500€/mes |
| Caso de uso | Mayoría de empresas | Banca, gobierno, defensa |

Para el 99% de los casos, Key Vault Standard o Premium es suficiente.

## Slide 25 — Managed HSM deep-dive: cuándo y cómo

Managed HSM es para casos extremos de compliance — FIPS 140-2 Level 3:

```
Comparativa Standard KV vs Premium KV vs Managed HSM:

┌─────────────────────┬───────────────┬───────────────┬───────────────┐
│                     │ Standard KV   │ Premium KV    │ Managed HSM   │
├─────────────────────┼───────────────┼───────────────┼───────────────┤
│ FIPS Level          │ 140-2 Level 1 │ 140-2 Level 2 │ 140-2 Level 3 │
│ HSM-backed keys     │ ❌ Software   │ ✅ HSM        │ ✅ HSM dedicado│
│ Key isolation       │ Multi-tenant  │ Multi-tenant  │ Single-tenant │
│ Compliance          │ Most cases    │ Strict        │ Ultra-strict  │
│ Cost                │ €0.03/secret/m│ €0.03/secret/m│ ~€2500/mes ⚠️ │
│ Use case            │ App secrets   │ Encryption    │ Banks, defense│
│ Setup time          │ 1 min         │ 1 min         │ 1-2 hours     │
│ Bulk operations     │ Standard      │ Limited       │ High throughput│
└─────────────────────┴───────────────┴───────────────┴───────────────┘
```

**Crear Managed HSM:**
```bash
# Coste: ~€3.5/h = €2500+/mes
# Solo crear si REALMENTE lo necesitas

# 1. Crear el HSM (toma ~30 min)
az keyvault create --hsm-name mhsm-bank-prod \
  --resource-group rg-secure \
  --location westeurope \
  --administrators $(az ad signed-in-user show --query id -o tsv) \
  --retention-days 90

# 2. Activar (requires 3 admin certs for security ceremony)
az keyvault security-domain download \
  --hsm-name mhsm-bank-prod \
  --sd-wrapping-keys cert1.cer cert2.cer cert3.cer \
  --sd-quorum 2 \
  --security-domain-file mhsm-sd.json

# Mantener mhsm-sd.json y certs en CAJA FUERTE física
# Sin estos archivos, no se puede recuperar el HSM si falla

# 3. Crear key
az keyvault key create --hsm-name mhsm-bank-prod \
  --name banking-master-key \
  --kty RSA-HSM \
  --size 4096 \
  --ops encrypt decrypt sign verify wrapKey unwrapKey
```

**Permissions model (RBAC granular):**
```bash
# HSM tiene roles muy específicos
# - Managed HSM Administrator (full control)
# - Managed HSM Crypto Officer (manage keys, no data)
# - Managed HSM Crypto User (use keys for crypto)
# - Managed HSM Policy Administrator (manage RBAC)

# Asignar role granular
az keyvault role assignment create \
  --hsm-name mhsm-bank-prod \
  --role "Managed HSM Crypto User" \
  --assignee app-encryption-mi \
  --scope "/keys/banking-master-key"
```

**Operations support:**
- ✅ Encryption / decryption
- ✅ Signing / verification
- ✅ Wrap / unwrap keys
- ✅ Key generation hardware-backed
- ❌ Secrets (use regular KV for secrets)
- ❌ Certificates (use regular KV)

## Slide 26 — BYOK y HYOK: control extremo de keys

BYOK (Bring Your Own Key) y HYOK (Hold Your Own Key):

```
Microsoft-Managed Keys (MMK) — Default
└── Microsoft generates and manages keys
    ├── Easy: zero management
    └── Trust: must trust Microsoft

Customer-Managed Keys (CMK) — BYOK
└── You generate the key (en tu HSM o KV)
    ├── Upload to Azure Key Vault o Managed HSM
    ├── Service uses your key to encrypt
    └── You control rotation, deletion

HYOK (Hold Your Own Key)
└── Key NEVER leaves your premises
    ├── Azure service envía data to your HSM for encrypt/decrypt
    ├── Network roundtrip per operation
    └── Highest control, lowest performance
```

**BYOK setup (own key import):**
```bash
# 1. Generate key on your HSM (e.g., on-prem nCipher, Thales)
# Export as encrypted file (BYOK package)

# 2. Import to Azure KV
az keyvault key import --vault-name kv-prod \
  --name imported-master-key \
  --byok-file mykey-encrypted.byok

# Or for Managed HSM
az keyvault key import --hsm-name mhsm-prod \
  --name imported-master-key \
  --byok-file mykey-encrypted.byok

# 3. Configure Azure service to use it
# Storage example:
az storage account update --name stproduction \
  --encryption-key-vault https://kv-prod.vault.azure.net \
  --encryption-key-name imported-master-key \
  --encryption-key-source Microsoft.Keyvault
```

**HYOK with External Key Manager (preview):**
```
Architecture:
─────────────
Tu data center                    Azure
┌──────────────┐                  ┌──────────────┐
│ Your HSM     │ ◄────TLS 1.3────►│ Storage Acct │
│ (Thales,     │                  │              │
│ nCipher,     │  encrypt/decrypt │ Wraps each   │
│ Entrust)     │  for each block  │ block with   │
│              │                  │ DEK          │
└──────────────┘                  └──────────────┘

Cada read/write requiere call a tu HSM.
Latencia: +5-50ms per operation.
```

**Cuándo usar BYOK:**
- ✅ Compliance requires customer-generated keys
- ✅ Data sovereignty (key in specific country)
- ✅ Multi-cloud key management consistency
- ✅ Easier transition cuando moves de cloud

**Cuándo usar HYOK:**
- ✅ Ultra-extreme compliance (defense, intelligence)
- ✅ Zero-trust toward cloud provider
- ✅ Key escrow requirements

**Cuándo NO usar (use MMK):**
- ❌ Standard apps (overhead not justified)
- ❌ Performance-critical (BYOK adds latency)
- ❌ Complex key rotation management
- ❌ No compliance requirement

**Trade-offs:**
```
MMK:    Simple, fast, secure → 95% of cases
BYOK:   Control + performance → compliance scenarios
HYOK:   Maximum control, slower → ultra-secure cases
```

## Slide 28 — Permission models: migración Access Policies → RBAC

Microsoft recomienda RBAC sobre Access Policies (legacy). Migration:

```
Access Policies (legacy):
└── Definidas en el Key Vault itself
    ├── Por user/SP
    ├── Por permission type (Keys, Secrets, Certificates)
    └── 16 permission types granulares

RBAC for Key Vault (recomendado):
└── Roles asignados via Azure RBAC
    ├── Centralized in Azure
    ├── Built-in roles + custom
    ├── Scope flexibility (vault, secret, key)
    └── Compatible con PIM (just-in-time)
```

**Built-in RBAC roles:**
```
Data plane (use keys/secrets):
├── Key Vault Administrator (everything)
├── Key Vault Secrets User (read secrets)
├── Key Vault Secrets Officer (manage secrets)
├── Key Vault Crypto User (use keys)
├── Key Vault Crypto Officer (manage keys)
├── Key Vault Crypto Service Encryption User (specific to encryption)
├── Key Vault Certificates User (read certs)
└── Key Vault Certificates Officer (manage certs)

Management plane (resource itself):
├── Key Vault Contributor (manage vault, NOT data)
└── Key Vault Reader (view config)
```

**Migración paso a paso:**
```bash
# 1. Habilitar RBAC en Key Vault existente
az keyvault update --name kv-prod \
  --resource-group rg-prod \
  --enable-rbac-authorization true

# ⚠️ Doing this REMOVES Access Policies
# Verify nadie depende de ellas antes

# 2. Migrar permissions: ver users actuales
az keyvault show --name kv-prod \
  --query "properties.accessPolicies[].{
    UserId: objectId, 
    Permissions: permissions
  }"

# 3. Para cada user/SP, asignar role apropiado
# Example: app que solo lee secrets
APP_OBJ_ID=$(az ad sp show --id <app-id> --query id -o tsv)

az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee $APP_OBJ_ID \
  --scope $(az keyvault show -n kv-prod --query id -o tsv)

# Para granularidad: permisos solo a UN secret específico
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee $APP_OBJ_ID \
  --scope "$(az keyvault show -n kv-prod --query id -o tsv)/secrets/db-connection-string"
```

**Custom roles para casos específicos:**
```bash
# Custom role: only read+create, NO delete
cat > custom-kv-role.json << 'EOF'
{
  "Name": "Key Vault Secret Reader Creator",
  "Description": "Read and create secrets, no delete",
  "Actions": [
    "Microsoft.KeyVault/vaults/read"

  "DataActions": [
    "Microsoft.KeyVault/vaults/secrets/getSecret/action",

```

**Comparison:**

| Capability | Access Policies | RBAC |
|---|:---:|:---:|
| Granular per-secret scope | ❌ | ✅ |
| PIM (just-in-time) | ❌ | ✅ |
| Conditional Access | ❌ | ✅ (preview) |
| Custom roles | ❌ | ✅ |
| Centralized management | ❌ | ✅ |

**Cuándo NO migrate (yet):**

## Slide 29 — Cross-region replication strategy

Key Vault NO replica automatically — necesitas estrategia manual:

```
Problema:
└── Key Vault es single-region
    └── If region down, KV down
        └── Apps que dependen del KV fail

Solution patterns:
├── 1. Active-Passive con secondary KV
├── 2. Geo-replicated keys via export/import
└── 3. Use Managed HSM with multi-region (preview)
```

**Pattern 1: Active-Passive con Bicep:**
```bicep
// Primary KV en West Europe
resource kvPrimary 'Microsoft.KeyVault/vaults@2024-04-01' = {
  name: 'kv-prod-weu'
  location: 'westeurope'
  // ... config
}

// Secondary KV en North Europe
resource kvSecondary 'Microsoft.KeyVault/vaults@2024-04-01' = {
  name: 'kv-prod-neu'
  location: 'northeurope'
  // ... same config
}

// Logic App que sync secrets cada hora
resource syncLogic 'Microsoft.Logic/workflows@2019-05-01' = {
  name: 'logic-sync-secrets'
  location: 'westeurope'
  properties: {
    definition: {
      // Trigger: every hour
      // 1. Get all secrets from primary
      // 2. For each: check if exists in secondary
      // 3. If not exists or different version: sync
    }
  }
}
```

**Sync script:**
```bash
#!/bin/bash
# sync-keyvaults.sh — corre via Logic App or cron

PRIMARY_KV="kv-prod-weu"
SECONDARY_KV="kv-prod-neu"

# Get all secrets from primary
SECRETS=$(az keyvault secret list --vault-name $PRIMARY_KV \
  --query "[].name" -o tsv)

for SECRET in $SECRETS; do
  # Get latest version from primary
  PRIMARY_VALUE=$(az keyvault secret show \
    --vault-name $PRIMARY_KV --name $SECRET \
    --query "value" -o tsv)
  
  # Check if exists in secondary
  SECONDARY_VALUE=$(az keyvault secret show \
    --vault-name $SECONDARY_KV --name $SECRET \
    --query "value" -o tsv 2>/dev/null || echo "")
  
  # Sync if different
  if [ "$PRIMARY_VALUE" != "$SECONDARY_VALUE" ]; then
    az keyvault secret set \
      --vault-name $SECONDARY_KV \
      --name $SECRET \
      --value "$PRIMARY_VALUE" \
      --output none
    echo "Synced: $SECRET"
  fi
done
```

**Pattern 2: Apps con automatic failover:**
```csharp
// .NET app code que tries primary, falls back to secondary
public class FailoverSecretManager
{
    private readonly SecretClient _primary;
    private readonly SecretClient _secondary;
    
    public async Task<string> GetSecretAsync(string name)
    {
        try
        {
            // Try primary first
            var response = await _primary.GetSecretAsync(name);
            return response.Value.Value;
        }
        catch (RequestFailedException ex) when (IsTransient(ex))
        {
            _logger.LogWarning("Primary KV failed, trying secondary");
            
            // Fallback to secondary
            var response = await _secondary.GetSecretAsync(name);
            return response.Value.Value;
        }
    }
    
    private bool IsTransient(RequestFailedException ex)
    {
        return ex.Status >= 500 || ex.Status == 0;
    }
}

// Register en DI
builder.Services.AddSingleton(sp =>
{
    var primary = new SecretClient(
        new Uri("https://kv-prod-weu.vault.azure.net"),
        new DefaultAzureCredential());
    var secondary = new SecretClient(
        new Uri("https://kv-prod-neu.vault.azure.net"),
        new DefaultAzureCredential());
    return new FailoverSecretManager(primary, secondary);
});
```

**Pattern 3: Local cache + KV fallback:**
```csharp
public class CachedSecretManager
{
    private readonly IMemoryCache _cache;
    private readonly FailoverSecretManager _kvManager;
    
    public async Task<string> GetSecretAsync(string name)
    {
        return await _cache.GetOrCreateAsync(name, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(15);
            
            try
            {
                return await _kvManager.GetSecretAsync(name);
            }
            catch
            {
                // Use stale cache value if KV completely down
                if (_cache.TryGetValue($"{name}_stale", out string stale))
                    return stale;
                throw;
            }
        });
    }
}
```

**Trade-offs:**

| Pattern | Pros | Cons |
|---|---|---|
| Active-passive sync | Simple, predictable | Sync lag (1-60min) |
| App failover | Real-time | Complex code |
| Cache + fallback | Resilient | Cache staleness |

**Real-world recommendation:** combine all 3.

## Slide 31 — Auto-rotation policies con Logic Apps

Auto-rotación de secrets con Logic Apps + Key Vault Events:

```
Trigger:
├── Key Vault Event Grid event "SecretNearExpiry" (30 days before)

    ├── 1. Generate new password (random)
    ├── 2. Update target system (DB, API, etc.) con new password
    ├── 3. Test new password works

    ├── 5. Notify ops team
    └── 6. After grace period: disable old version
```

**Bicep deployment:**

```bicep
          type: 'Request'
```

## Slide 33 — Advanced KQL queries para Key Vault

Comprehensive monitoring con KQL queries para production:

```kusto
// 1. Top secrets by access (most-used in last 7 days)
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(7d)
| where OperationName == "SecretGet"
| summarize 
    AccessCount = count(),
    Callers = make_set(identity_claim_xms_mirid_s)
  by Resource_s, secretId = strcat(parse_url(requestUri_s).Path)
| top 20 by AccessCount

// 2. Anomalous access patterns
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(24h)
| where OperationName in ("SecretGet", "KeyGet")
| summarize 
    HourlyAccess = count() 
  by bin(TimeGenerated, 1h), 
     identity = identity_claim_xms_mirid_s,
     resource = Resource_s
| join kind=inner (
    AzureDiagnostics
    | where ResourceType == "VAULTS"
    | where TimeGenerated between (ago(30d) .. ago(24h))
    | where OperationName in ("SecretGet", "KeyGet")
    | summarize 
        BaselineAvg = avg(toreal(1)),
        BaselineStdev = stdev(toreal(1))
      by identity = identity_claim_xms_mirid_s, 
         resource = Resource_s
  ) on identity, resource
| where HourlyAccess > BaselineAvg + 3 * BaselineStdev
| project TimeGenerated, identity, resource, HourlyAccess, BaselineAvg

// 3. Failed authentication attempts (potential brute force)
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(1h)
| where ResultType == "Forbidden" or ResultType == "Unauthorized"
| summarize 
    FailedAttempts = count(),
    UniqueIps = dcount(CallerIPAddress),
    Identities = make_set(identity_claim_xms_mirid_s)
  by CallerIPAddress
| where FailedAttempts > 10
| order by FailedAttempts desc

// 4. Secrets created/modified outside business hours
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(7d)
| where OperationName in ("SecretSet", "KeySet", "SecretDelete", "KeyDelete")
| extend HourOfDay = datetime_part("Hour", TimeGenerated)
| extend DayOfWeek = dayofweek(TimeGenerated)
| where HourOfDay < 8 or HourOfDay > 19  // outside 8am-7pm
       or DayOfWeek == 0d                  // weekend
| project TimeGenerated, identity_claim_xms_mirid_s, OperationName, Resource_s

// 5. Service principals con KV access pero sin recent activity
let activeAssignees = AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(90d)
| distinct identity_claim_xms_mirid_s;
//
AuthorizationActivity
| where ResourceProviderValue == "MICROSOFT.KEYVAULT"
| where ActionValue contains "secrets"
| distinct PrincipalObjectID, PrincipalName
| where PrincipalObjectID !in (activeAssignees)
| project PrincipalName, PrincipalObjectID
// Estos SPs tienen acceso pero no han usado en 90 días → candidates to remove

// 6. Compliance: secrets without expiration date
AzureDiagnostics  
| where ResourceType == "VAULTS"
| where OperationName == "SecretGet"
| summarize MaxRetrieved = max(TimeGenerated) by secretName = strcat(parse_url(requestUri_s).Path)
| where MaxRetrieved < ago(180d)
| project secretName, LastUsed = MaxRetrieved
// Secrets no usados en 180 días → candidates to delete
```

**Alerting rules:**
```kusto
// Alert 1: Brute force attack
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(15m)
| where ResultType == "Forbidden"
| summarize Failures = count() by CallerIPAddress
| where Failures > 20
// Trigger if Failures > 20 in 15min from one IP

// Alert 2: Mass secret deletion
AzureDiagnostics
| where ResourceType == "VAULTS"
| where TimeGenerated > ago(5m)
| where OperationName == "SecretDelete"
| summarize Deletes = count() by identity_claim_xms_mirid_s
| where Deletes > 5
// Trigger if any identity deletes >5 secrets in 5min

// Alert 3: Configuration change (any modification)
AzureDiagnostics
| where ResourceType == "VAULTS"  
| where TimeGenerated > ago(1m)
| where OperationName contains "VaultPut" or 
        OperationName contains "AccessPolicySet" or
        OperationName contains "NetworkRuleSet"
// Trigger on ANY KV configuration change (con immediate notification)
```

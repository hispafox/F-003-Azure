## Slide 2 — El reto de auth en desktop
Las apps de escritorio no son web servers — no tienen una URL de callback accesible desde internet. Los flujos OAuth2 necesitan adaptarse.

Además, vuestro equipo trabaja con ClickOnce (que migraremos a MSIX en el módulo 7). La autenticación en apps empaquetadas tiene peculiaridades: el broker de Windows (WAM), las redirecciones nativas, y la integración con el SSO del sistema operativo.

## Slide 3 — Flujos OAuth2 disponibles para desktop

| Flujo | Cómo funciona | Recomendación |
|-------|--------------|:-------------:|
| **System browser + localhost** | Abre el navegador del sistema, callback a localhost | ✓ Recomendado |
| **Embedded browser** | WebView2 dentro de la app | ⚠ Aceptable |
| **WAM (Web Account Manager)** | Broker de Windows, SSO nativo | ✓✓ Mejor opción en Windows |
| **Device Code** | Muestra código, usuario autentica en otro dispositivo | ✓ Para kioscos/CLI |

**WAM es la mejor opción para Windows:** Aprovecha el SSO de Windows (si el usuario ya está logueado en Windows con su cuenta corporativa, no necesita introducir credenciales de nuevo). Es el método que usa Office 365 y Teams.

## Slide 4 — MSAL para aplicaciones de escritorio

```bash

dotnet add package Microsoft.Identity.Client

```

```csharp
// Crear la aplicación pública (no confidential — desktop no puede guardar secretos)
var app = PublicClientApplicationBuilder
    .Create("<client-id>")
    .WithAuthority($"https://login.microsoftonline.com/<tenant-id>")
    .WithDefaultRedirectUri()  // http://localhost para system browser
    .Build();
```

**PublicClientApplication vs ConfidentialClientApplication:**
- **Public:** Apps desktop y mobile. No tienen client secret (el usuario puede inspeccionar el código). Usan PKCE.
- **Confidential:** Apps server-side (Web Apps, APIs, Functions). Tienen client secret almacenado de forma segura.

## Slide 5 — Flujo con system browser

```csharp
public class AuthService
{
    private readonly IPublicClientApplication _app;
    private readonly string[] _scopes = { "api://api-ventas/Pedidos.Read", "User.Read" };

    public AuthService()
    {
        _app = PublicClientApplicationBuilder
            .Create("<client-id>")
            .WithAuthority("https://login.microsoftonline.com/<tenant-id>")
            .WithRedirectUri("http://localhost")
            .Build();
    }

    public async Task<AuthenticationResult> LoginAsync()
    {
        try
        {
            // Intentar token de cache primero (silent)
            var accounts = await _app.GetAccountsAsync();
            return await _app.AcquireTokenSilent(_scopes, accounts.FirstOrDefault())
                .ExecuteAsync();
        }
        catch (MsalUiRequiredException)
        {
            // No hay token en cache → abrir browser para login
            return await _app.AcquireTokenInteractive(_scopes)
                .WithUseEmbeddedWebView(false)  // System browser
                .ExecuteAsync();
        }
    }

    public async Task LogoutAsync()
    {
        var accounts = await _app.GetAccountsAsync();
        foreach (var account in accounts)
            await _app.RemoveAsync(account);
    }
}
```

**Flujo del usuario:**
1. La app llama `AcquireTokenInteractive`
2. Se abre el navegador del sistema (Chrome, Edge, Firefox)
3. El usuario se autentica en Entra ID (con MFA si aplica)
4. Entra ID redirige a `http://localhost:RANDOM_PORT/`
5. MSAL captura la redirección y obtiene el token
6. El navegador se cierra (o muestra "puedes cerrar esta ventana")

## Slide 6 — Flujo con WAM (Web Account Manager)

WAM usa el broker de autenticación de Windows para SSO nativo:

```csharp
var app = PublicClientApplicationBuilder
    .Create("<client-id>")
    .WithAuthority("https://login.microsoftonline.com/<tenant-id>")
    .WithBroker(new BrokerOptions(BrokerOptions.OperatingSystems.Windows))
    .Build();

// El login usa el broker de Windows (mismo popup que Office/Teams)
var result = await app.AcquireTokenInteractive(_scopes)
    .WithParentActivityOrWindow(windowHandle)  // Handle de la ventana WPF/WinForms
    .ExecuteAsync();
```

**Ventajas de WAM:**
- SSO con Windows: si el usuario ya está logueado en Windows con su cuenta corporativa, no necesita introducir credenciales
- Experiencia nativa: popup de Windows, no un browser
- MFA integrado: Windows Hello, PIN, biometría
- Token broker: los tokens se almacenan en el credential manager de Windows (más seguro)

**Requisito:** Windows 10+ y que el dispositivo esté joined a Entra ID o registered.

## Slide 7 — App Registration para desktop

```bash
# Crear registration para app de escritorio (public client)
az ad app create \
  --display-name "Ventas Desktop" \
  --sign-in-audience AzureADMyOrg \
  --public-client-redirect-uris \
    "http://localhost" \
    "ms-appx-web://microsoft.aad.brokerplugin/<client-id>"  # Para WAM

APP_ID=$(az ad app list --display-name "Ventas Desktop" --query "[0].appId" -o tsv)

# Habilitar public client (no client secret)
az ad app update --id $APP_ID --is-fallback-public-client true

# Añadir permisos
az ad app permission add --id $APP_ID \
  --api 00000003-0000-0000-c000-000000000000 \
  --api-permissions e1fe6dd8-ba31-4d61-89e7-88639da4683d=Scope  # User.Read

# Permisos de vuestra API
az ad app permission add --id $APP_ID \
  --api <api-app-id> \
  --api-permissions <scope-id>=Scope  # Pedidos.ReadWrite
```

**Redirect URIs para desktop:**
- `http://localhost` — para system browser flow
- `ms-appx-web://microsoft.aad.brokerplugin/<client-id>` — para WAM
- `urn:ietf:wg:oauth:2.0:oob` — legacy (no recomendado)

## Slide 8 — Token cache persistente en desktop

A diferencia de web apps, las apps desktop necesitan persistir la cache de tokens en disco para que el usuario no se re-autentique cada vez que abre la app:

```csharp
var app = PublicClientApplicationBuilder
    .Create("<client-id>")
    .WithAuthority("https://login.microsoftonline.com/<tenant-id>")
    .Build();

// Persistir cache en archivo cifrado (DPAPI en Windows)
var cacheFilePath = Path.Combine(
    Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
    "VentasDesktop", "tokencache.bin");

var cacheHelper = await MsalCacheHelper.CreateAsync(
    new StorageCreationPropertiesBuilder("tokencache.bin", Path.GetDirectoryName(cacheFilePath)!)
        .WithUnprotectedFile()  // O .WithLinuxKeyring() / .WithMacKeyChain()
        .Build());

cacheHelper.RegisterCache(app.UserTokenCache);
```

**Con WAM:** Los tokens se almacenan en el credential manager de Windows automáticamente. No necesitáis cache manual.

```csharp
        UserInfo.Text += $"\n\nPedidos: {datos}";
```

## Slide 10 — Refresh silencioso: mantener la sesión

```csharp
public async Task<string> GetAccessTokenAsync()
{
    var accounts = await _app.GetAccountsAsync();
    var account = accounts.FirstOrDefault();
    
    if (account is null)
        throw new InvalidOperationException("No hay sesión activa. Llama a LoginAsync primero.");
    
    try
    {
        // Intenta obtener token de cache (o refresh silencioso)
        var result = await _app.AcquireTokenSilent(_scopes, account).ExecuteAsync();
        return result.AccessToken;
    }
    catch (MsalUiRequiredException)
    {
        // Token expirado y refresh token también → re-login interactivo
        var result = await _app.AcquireTokenInteractive(_scopes).ExecuteAsync();
        return result.AccessToken;
    }
}
```

**Ciclo de vida típico en desktop:**
1. Primera vez: `AcquireTokenInteractive` → usuario se autentica → tokens cacheados
2. Siguiente ejecución: `AcquireTokenSilent` → token de cache (sin interacción)
3. Token expira: `AcquireTokenSilent` usa refresh token → nuevo access token (sin interacción)
4. Refresh token expira (90 días): `MsalUiRequiredException` → `AcquireTokenInteractive` → usuario re-autentica

## Slide 11 — MSIX y auth: consideraciones especiales

Cuando empaquetáis vuestra app como MSIX (módulo 7), hay diferencias en la autenticación:

**Redirect URI para MSIX:**
```
ms-appx-web://microsoft.aad.brokerplugin/<client-id>
```
Este URI es específico de apps empaquetadas Windows. Registradlo en la App Registration.

**Package Identity:** Las apps MSIX tienen una identidad de paquete que WAM usa para asociar tokens. Si cambiáis el paquete (nuevo certificado, nuevo publisher), los tokens cacheados se invalidan.

**Auto-update y auth:** Cuando se actualiza la app vía MSIX AppInstaller, la sesión del usuario se mantiene si la cache de tokens persiste entre versiones (lo hace con WAM y con cache en %LocalAppData%).

## Slide 12 — Conditional Access en desktop

Las políticas de Conditional Access aplican igual en desktop:

**Ejemplo:** Política "requiere dispositivo compliant" → si la app de escritorio se ejecuta en un dispositivo no gestionado por Intune, Entra ID rechaza el login.

```csharp
try
{
    var result = await _app.AcquireTokenInteractive(_scopes).ExecuteAsync();
}
catch (MsalServiceException ex) when (ex.Claims is not null)
{
    // Conditional Access requiere claims adicionales (ej: MFA, device compliance)
    var result = await _app.AcquireTokenInteractive(_scopes)
        .WithClaims(ex.Claims)  // Enviar los claims que pide la policy
        .ExecuteAsync();
}
```

**Claims challenge:** Cuando una Conditional Access policy requiere algo extra (MFA, device registration), Entra ID devuelve un "claims challenge" en la respuesta 401. MSAL lo maneja si capturáis la excepción y reenviáis con `.WithClaims()`.

## Slide 14 — HttpClient configurado con auth automática

```csharp
// Crear un HttpClient que añade el token automáticamente
public class AuthenticatedHttpClientHandler : DelegatingHandler
{
    private readonly AuthService _auth;

    public AuthenticatedHttpClientHandler(AuthService auth) : base(new HttpClientHandler())
    {
        _auth = auth;
    }

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        var token = await _auth.GetAccessTokenAsync();
        request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token);
        
        var response = await base.SendAsync(request, ct);
        
        // Si 401, intentar refresh y reintentar
        if (response.StatusCode == HttpStatusCode.Unauthorized)
        {
            token = await _auth.GetAccessTokenAsync();  // Forzar refresh
            request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token);
            response = await base.SendAsync(request, ct);
        }
        
        return response;
    }
}

// Uso
var client = new HttpClient(new AuthenticatedHttpClientHandler(authService));
var pedidos = await client.GetFromJsonAsync<List<Pedido>>("https://api-ventas.azurewebsites.net/api/pedidos");
```

## Slide 15 — Troubleshooting de auth en desktop

| Problema | Causa | Solución |
|----------|-------|----------|
| Browser no se abre | `WithUseEmbeddedWebView(false)` no configurado | Añadir la opción |
| "Reply address mismatch" | Redirect URI no registrada | Añadir `http://localhost` en App Registration |
| Token cache no persiste | Falta `MsalCacheHelper` | Configurar cache persistente |
| WAM falla con "device not registered" | Dispositivo no joined a Entra ID | Usar system browser en vez de WAM |
| "Consent required" | Primera vez o permisos nuevos | Admin consent o que el usuario acepte |
| Token expirado inmediatamente | Reloj del PC desfasado | Sincronizar hora del sistema |
| "AADSTS50059: No tenant" | Client ID o tenant ID incorrectos | Verificar configuración |

## Slide 17 — Token lifetime y configuración

```
Tokens por defecto de Entra ID:
├── Access Token: ~1 hora (60-90 min)
├── ID Token: ~1 hora
├── Refresh Token: 90 días (rolling window)
│   └── Si se usa cada <90 días: indefinido
│   └── Si no se usa en 90 días: expira
└── Session Token: hasta 24 horas (configurable)
```

```csharp
// Configurar políticas de token (requiere Entra ID P1+)
// Portal → Entra ID → Enterprise Applications → Token Lifetime Policies

// O por código, ajustar el comportamiento:
var options = new PublicClientApplicationBuilder.Create(clientId)
    .WithExtraQueryParameters(new Dictionary<string, string>
    {
        ["max_age"] = "3600"  // Forzar re-auth si token > 1 hora
    })
    .Build();
```

Para apps de escritorio: el refresh token de 90 días significa que el usuario solo se autentica una vez cada 3 meses (si abre la app regularmente).

## Slide 20 — WAM (Web Account Manager) deep-dive

WAM es el broker nativo de Windows para auth — la mejor experiencia desktop:

```
WAM benefits:
├── ✅ SSO integrado con Windows account
├── ✅ Token cached en Windows Credential Manager (encrypted)
├── ✅ TPM-bound credentials (hardware security)
├── ✅ Conditional Access compliant device check funciona out-of-box
├── ✅ FIDO2/Windows Hello support automático
├── ✅ No browser popups (in-app dialogs)
└── ✅ Microsoft Accounts + Work/School accounts
```

**Setup MSAL.NET con WAM:**
```csharp
using Microsoft.Identity.Client;
using Microsoft.Identity.Client.Broker;

var app = PublicClientApplicationBuilder
    .Create("<client-id>")
    .WithAuthority("https://login.microsoftonline.com/<tenant-id>")
    .WithDefaultRedirectUri()  // ms-appx-web://<package-id> for MSIX
    .WithBroker(new BrokerOptions(BrokerOptions.OperatingSystems.Windows)
    {
        ListOperatingSystemAccounts = true,  // Show Windows accounts
        Title = "MyApp Login",
        MsaPassthrough = false  // false = work/school only
    })
    .Build();

// First sign-in
var result = await app.AcquireTokenInteractive(scopes)
    .WithAccount(PublicClientApplication.OperatingSystemAccount)  // Use Windows account
    .ExecuteAsync();

// Subsequent: silent (uses Windows-cached token)
try
{
    var account = (await app.GetAccountsAsync()).First();
    var result = await app.AcquireTokenSilent(scopes, account).ExecuteAsync();
}
catch (MsalUiRequiredException)
{
    // Token expired and refresh failed; need user interaction
    var result = await app.AcquireTokenInteractive(scopes).ExecuteAsync();
}
```

**Required NuGet:**
```xml
<PackageReference Include="Microsoft.Identity.Client" Version="4.65.0" />
<PackageReference Include="Microsoft.Identity.Client.Broker" Version="4.65.0" />
```

**Para WPF apps:**
```csharp
public partial class MainWindow : Window
{
    private IPublicClientApplication _app;
    
    public MainWindow()
    {
        InitializeComponent();
        
        _app = PublicClientApplicationBuilder
            .Create("<client-id>")
            .WithAuthority("...")
            .WithBroker(new BrokerOptions(BrokerOptions.OperatingSystems.Windows))
            .WithParentActivityOrWindow(() => new WindowInteropHelper(this).Handle)
            .Build();
    }
    
    private async void LoginButton_Click(object sender, RoutedEventArgs e)
    {
        try
        {
            var result = await _app.AcquireTokenInteractive(new[] { "User.Read" })

                .ExecuteAsync();
            
            UsernameLabel.Content = result.Account.Username;
        }
        catch (MsalException ex)
        {
            MessageBox.Show($"Error: {ex.Message}");
        }
    }
}
```

**Ventajas con Conditional Access:**
```
Sin WAM:
├── User signs in en navegador
├── CA policy: "Require compliant device"
├── App tries to validate device → falla
└── User can't sign in

Con WAM:
├── WAM accede al device claim de Windows
├── CA validates compliant device automáticamente
└── Sign-in success
```

**Edge cases:**
```
Account broker fails (rare):
├── Fallback to embedded WebView2
├── Or system browser
└── Worst case: user must input credentials

CSV/MSI installations:
├── WAM might not work without proper registration
├── Test on clean install
└── Document fallback experience
```

## Slide 21 — DPAPI cache encryption: persistir tokens seguramente

Token cache files necesitan encryption — DPAPI es nativo Windows:

```csharp
using Microsoft.Identity.Client.Extensions.Msal;

var storageProperties = new StorageCreationPropertiesBuilder(
    "msal_cache.bin",  // file name
    Path.Combine(Environment.GetFolderPath(Environment.SpecialFolder.UserProfile), "MyApp"))
    .WithMacKeyChain(serviceName: "MyApp", accountName: "MSALCache")
    .WithLinuxKeyring(
        schemaName: "com.miempresa.miapp.tokencache",
        collection: MsalCacheHelper.LinuxKeyRingDefaultCollection,
        secretLabel: "MSAL token cache",
        attribute1: new KeyValuePair<string, string>("Version", "1"),
        attribute2: new KeyValuePair<string, string>("ProductGroup", "MyApp"))
    .WithUnprotectedFile()  // Last resort (NOT secure)
    .Build();

var cacheHelper = await MsalCacheHelper.CreateAsync(storageProperties);
cacheHelper.RegisterCache(app.UserTokenCache);

// Now tokens persist between app restarts, encrypted
```

**Why per-platform encryption:**

```
Windows: DPAPI
├── Encrypted with user's Windows credentials
├── Can't decrypt without user logon
└── Hardware-backed if TPM available

macOS: Keychain
├── Encrypted with Keychain master password
├── Touch ID required to access
└── Per-user, per-app scoped

Linux: Secret Service / Keyring
├── GNOME Keyring or KWallet
├── Encrypted with user session
└── Locked when user logs out
```

**Anti-pattern:**
```csharp
// ❌ Hardcoded plain text cache
File.WriteAllBytes("cache.bin", tokenBytes);
// Anyone with file access reads tokens!

// ❌ Custom AES encryption
// Hard to do right, breaks easily
// Use OS APIs instead

// ❌ No persistence at all
// User has to re-auth each app launch
// Bad UX for desktop apps
```

**Verify encryption:**
```csharp
// On Windows, the file is encrypted using DPAPI
// You can verify by:
// 1. Read the file as another user → fails to decrypt
// 2. Read as same user → reads
// 3. Boot into safe mode → fails (no DPAPI service)

// In code, verify cache encrypted
var status = cacheHelper.LastVerificationStatus;
if (status != CacheStorageType.Encrypted)
{
    _logger.LogWarning("Token cache is NOT encrypted!");
}
```

## Slide 22 — MSIX identity y package family

MSIX apps tienen identity ligada al package — different from .exe:

```
EXE traditional:
├── Identity: file path + user
├── Auth: store tokens in user profile
└── Updates: replace files

MSIX:
├── Identity: Package Family Name (PFN)
├── Auth: store tokens scoped to package
├── Updates: signed package, version-controlled
└── Containerized: limited file system access
```

**App Registration redirect URI for MSIX:**
```
Para MSIX-packaged apps, redirect URI especial:

ms-appx-web://microsoft.aad.brokerplugin/{ClientId}

Ejemplo:
ms-appx-web://microsoft.aad.brokerplugin/12345678-1234-1234-1234-123456789012
```

**MSIX manifest (Package.appxmanifest):**
```xml
<Package>
  <Identity Name="MiEmpresa.MiApp"
            Publisher="CN=MyEmpresa, O=MiEmpresa, C=ES"
            Version="1.0.0.0" />
  
  <Properties>
    <DisplayName>Mi Aplicación</DisplayName>
  </Properties>
  
  <Capabilities>
    <Capability Name="internetClient" />
    <Capability Name="enterpriseAuthentication" />  <!-- Para SSO Windows -->
    <Capability Name="privateNetworkClientServer" />
  </Capabilities>
  
  <Applications>
    <Application Id="App" Executable="MiApp.exe">
      <Extensions>
        <!-- Protocol activation for OAuth callback -->
        <uap:Extension Category="windows.protocol">
          <uap:Protocol Name="ms-appx-web">
            <uap:DisplayName>Mi App OAuth Callback</uap:DisplayName>
          </uap:Protocol>
        </uap:Extension>
      </Extensions>
    </Application>
  </Applications>
</Package>
```

**Proper redirect URI configuration:**
```csharp
// Get current package's PFN
var package = Windows.ApplicationModel.Package.Current;
var pfn = package.Id.FamilyName;
// Result: "MiEmpresa.MiApp_8wekyb3d8bbwe"

// Build redirect URI
var redirectUri = $"ms-appx-web://microsoft.aad.brokerplugin/{clientId}";

var app = PublicClientApplicationBuilder
    .Create(clientId)
    .WithAuthority(authority)
    .WithRedirectUri(redirectUri)  // MSIX-aware
    .WithBroker(new BrokerOptions(BrokerOptions.OperatingSystems.Windows))
```

## Slide 25 — Troubleshooting auth errors en desktop

Common errors and fixes:

```
ERROR: AADSTS50053 - Account locked
─────────────────────────────────────
Cause: Too many failed logins, brute-force protection
Fix: 
├── Wait 30 min for auto-unlock
├── O admin unlock: az ad user update --account-enabled false / true
└── User self-service unlock con MFA

ERROR: AADSTS65001 - User has not consented
─────────────────────────────────────────────
Cause: User hasn't approved required permissions
Fix:
├── First sign-in shows consent dialog
├── If user cancels → re-trigger AcquireToken
├── Pre-consent (admin):
    az ad app permission admin-consent --id <app-id>

ERROR: AADSTS70011 - Invalid scope
───────────────────────────────────
Cause: Scope not configured in API or wrong format
Fix:
├── For Microsoft APIs: "https://graph.microsoft.com/User.Read"
├── For your APIs: "api://<api-id>/access_as_user"
├── Check exact scope name in App Registration
└── Don't mix v1 and v2 endpoints

ERROR: WAM_E_ACCOUNT_NOT_FOUND
───────────────────────────────
Cause: Trying to use account no longer registered
Fix:
├── List accounts first: app.GetAccountsAsync()
├── Check if account still exists
└── Trigger interactive auth if not

ERROR: Cert validation failed (cust enterprise CAs)
─────────────────────────────────────────────────────
Cause: Self-signed cert in enterprise proxy
Fix:
├── Add cert to Windows trusted store
├── O config: ServicePointManager.ServerCertificateValidationCallback
└── ⚠️ NEVER bypass validation in production

ERROR: Network down during silent token refresh
────────────────────────────────────────────────
Cause: User's offline, tokens expired
Fix:
├── Cache responses with TTL
├── Show "offline mode" UI
└── Retry with backoff cuando connectivity returns

ERROR: HTTP 503 from token endpoint
────────────────────────────────────
Cause: Entra ID transient issue
Fix:
├── MSAL has built-in retry, normalmente OK
├── Increase retry attempts en config
└── Check Azure status: https://status.azure.com
```

**Debugging checklist:**
```
[ ] Check Application Insights for client-side errors
[ ] Verify network reaches login.microsoftonline.com
[ ] Check Windows Event Log for WAM errors:
     Event Viewer → Applications → Microsoft → Windows →

     PublicClientApplicationBuilder.Create(clientId)

```

## Slide 26 — Offline scenarios y token refresh strategies

Desktop apps deben funcionar offline (parcialmente):

```csharp
public class OfflineAwareAuthService
{
    private readonly IPublicClientApplication _app;
    private AuthenticationResult _cachedResult;
    
    public async Task<AuthenticationResult> GetTokenAsync(IList<string> scopes)
    {
        // 1. Check if we have valid cached token
        if (_cachedResult != null && _cachedResult.ExpiresOn > DateTimeOffset.UtcNow.AddMinutes(5))
        {
            return _cachedResult;
        }
        
        // 2. Try silent acquisition (uses MSAL cache)
        try
        {
            var account = (await _app.GetAccountsAsync()).FirstOrDefault();
            if (account != null)
            {
                _cachedResult = await _app.AcquireTokenSilent(scopes, account).ExecuteAsync();
                return _cachedResult;
            }
        }
        catch (MsalUiRequiredException)
        {
            // Need interactive auth
        }
        catch (HttpRequestException ex) when (IsOfflineError(ex))
        {
            // Network down
            _logger.LogWarning("Network unavailable, using stale token");
            
            // Try to use stale token if exists (some APIs accept slightly expired)
            if (_cachedResult != null)
            {
                return _cachedResult;
            }
            
            throw new OfflineException("Cannot authenticate offline");
        }
        
        // 3. Interactive auth (online required)
        if (!IsOnline())
        {
            throw new OfflineException("Cannot authenticate offline");
        }
        
        _cachedResult = await _app.AcquireTokenInteractive(scopes).ExecuteAsync();
        return _cachedResult;
    }
    
    private bool IsOnline()
    {
        try
        {
            using var ping = new System.Net.NetworkInformation.Ping();
            var reply = ping.Send("8.8.8.8", 1000);
            return reply.Status == System.Net.NetworkInformation.IPStatus.Success;
        }
        catch
        {
            return false;
        }
    }
    
    private bool IsOfflineError(HttpRequestException ex)
    {
        return ex.InnerException is System.Net.Sockets.SocketException ||
               ex.Message.Contains("Could not resolve", StringComparison.OrdinalIgnoreCase);
    }
}
```

**Offline-first design:**
```
App startup:
├── Show last-known data (cached)
├── Try background sync if online
└── Update UI when sync completes

Save action:
├── Save locally (SQLite)
├── Mark as "pending sync"
└── Background queue uploads

Sync queue:
├── Retry on connectivity restore
├── Conflict resolution if needed
└── Notify user of sync status
```

**Token expiry strategies:**
```csharp
// Strategy 1: Refresh proactively
// 5 min before expiry, refresh in background
private async Task ProactiveRefreshAsync()
{
    var timeToRefresh = _cachedResult.ExpiresOn.Subtract(TimeSpan.FromMinutes(5));
    var delay = timeToRefresh - DateTimeOffset.UtcNow;
    
    if (delay > TimeSpan.Zero)
    {
        await Task.Delay(delay);
    }
    
    // Refresh silently in background
    try
    {
        _cachedResult = await _app.AcquireTokenSilent(_scopes, _account)
            .WithForceRefresh(true)
            .ExecuteAsync();
    }
    catch
    {
        // Log, don't fail
    }
}

// Strategy 2: Refresh on use (lazy)
// Check on each API call, refresh if expiring
public async Task<HttpResponseMessage> CallApiAsync(string url)
{
    var token = await GetTokenAsync(_scopes);  // refreshes if needed
    // ... HTTP call
}

// Strategy 3: Reactive on 401
// Try with current token, refresh if rejected
public async Task<HttpResponseMessage> CallApiResilientAsync(string url)
{
    var response = await _http.GetAsync(url);
    if (response.StatusCode == HttpStatusCode.Unauthorized)
    {
        // Token rejected, force refresh
        var token = await ForceTokenRefreshAsync();
        // Retry
        response = await _http.GetAsync(url);
    }
    return response;
}
```

**Best practice:** combine reactive (on 401) + proactive (5 min before expiry).

## Slide 28 — Microsoft Authenticator passwordless flows

Microsoft Authenticator app supports several passwordless methods:

```
1. Phone sign-in (Authenticator)
   ├── User types email
   ├── Microsoft sends push to Authenticator
   ├── User approves with biometric
   └── Sign-in complete

2. FIDO2 security keys
   ├── User has physical key (YubiKey)
   ├── Insert + tap
   └── Sign-in complete

3. Windows Hello for Business
   ├── User on enrolled Windows device
   ├── Face/fingerprint/PIN
   └── SSO across all Microsoft

4. Certificate-based auth
   ├── Smart card or virtual smart card
   ├── PIN unlocks cert
   └── Sign-in complete
```

**Number matching (anti-phishing):**
```
Old way (push notification only):
├── User receives push: "Approve sign-in?"
├── User taps "Approve" reflexively
└── Vulnerable: attacker spams pushes until user accepts

Number matching:
├── User receives push: "Number 73 to sign in?"
├── User must enter "73" en Authenticator
├── Sign-in computer shows "73"
└── Phishing impossible: attacker doesn't see the number
```

## Slide 29 — Anti-patterns en desktop auth

Errors comunes que veo en desktop auth:

```
❌ ANTI-PATTERN 1: Embedded WebView2 sin TLS validation
   options.UseEmbeddedWebView(true);
   // Y custom cert validation bypass
   ✅ Use system browser via MSAL default
   ✅ NEVER bypass cert validation

❌ ANTI-PATTERN 2: Storing tokens en plain text file
   File.WriteAllText("token.txt", token);
   ✅ DPAPI cache via MSAL.Extensions

❌ ANTI-PATTERN 3: Hardcoded redirect URI for all envs
   .WithRedirectUri("http://localhost:5000/")
   ✅ Per-environment + dynamic for MSIX

❌ ANTI-PATTERN 4: No retry logic on transient errors
   ✅ MSAL has built-in retry, don't disable

❌ ANTI-PATTERN 5: Same client ID for desktop AND web
   ✅ Separate App Registrations per platform
   ✅ Different redirect URIs

❌ ANTI-PATTERN 6: Polling for token expiration
   while(true) { Thread.Sleep(60000); CheckExpiry(); }
   ✅ Calculate based on ExpiresOn, set Timer

❌ ANTI-PATTERN 7: No clear logout
   "Just close the window"
   ✅ app.RemoveAsync(account) + clear local data

❌ ANTI-PATTERN 8: Required network at startup
   App locks if first launch is offline
   ✅ Cached creds + offline mode

❌ ANTI-PATTERN 9: Sin Conditional Access support
   App breaks when CA requires compliant device
   ✅ Use WAM (broker) for proper CA support

❌ ANTI-PATTERN 10: Insecure token transmission
   Sending token via HTTP query string
   ✅ Always Authorization header
   ✅ Always HTTPS
```

**El más común y caro:**
```
"Cliente con WPF app en plain HTTP local server callback"
├── Insecure: anyone on network can intercept
├── Vulnerable to redirect attacks
└── Fix: use system browser + proper redirect URI

"App que store tokens en config.json plain text"
├── Anyone with file access reads tokens
├── Backups copy tokens to other locations
└── Fix: DPAPI encryption nativa (Windows)
```

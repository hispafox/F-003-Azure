## Slide 2 — Qué es Microsoft Entra ID
Entra ID (antes Azure Active Directory / Azure AD) es el servicio de identidad y acceso de Microsoft. Es el directorio central donde viven todos los usuarios, grupos, aplicaciones y permisos de vuestra organización.

**NO es Active Directory on-premises.** Son productos diferentes:
- AD on-premises: directorio LDAP para redes corporativas Windows
- Entra ID: directorio cloud para identidad y acceso a aplicaciones web/cloud

Pueden coexistir y sincronizarse (Azure AD Connect), pero son independientes.

**Todo en Azure se autentica contra Entra ID:** el portal, CLI, APIs, App Service, Functions, DevOps. Cuando hacéis `az login`, estáis autenticándoos con Entra ID.

---

## Slide 3 — Tenant: la organización

Un **Tenant** es una instancia dedicada de Entra ID para vuestra organización:

- Tiene un ID único (GUID) y un dominio: `miempresa.onmicrosoft.com`
- Opcionalmente un dominio personalizado: `miempresa.com`
- Contiene todos los usuarios, grupos, apps y configuración
- Es el límite de seguridad: datos de un tenant no son visibles desde otro

```bash
# Ver información del tenant actual
az account show --query tenantId -o tsv

# Listar tenants a los que tienes acceso
az account tenant list --output table
```

**Vuestro caso:** Tenéis un tenant de la organización. Todos los usuarios del equipo están ahí. Las apps registradas para OAuth2 se crean ahí. Los Service Principals de los pipelines viven ahí.

## Slide 4 — Usuarios: tipos y gestión

**Tipos de usuario:**
- **Miembros:** Empleados de la organización (pedro@empresa.com). Acceso completo.
- **Invitados (B2B):** Externos invitados (consultor@otra.com). Acceso limitado.

```bash
# Listar usuarios
az ad user list --query "[].{nombre:displayName, email:userPrincipalName, tipo:userType}" --output table

# Crear un usuario
az ad user create \
  --display-name "María López" \
  --user-principal-name maria@empresa.com \
  --password "TempPassword123!" \
  --force-change-password-next-sign-in true

# Invitar un externo (B2B)
az ad user create --display-name "Consultor" \
  --user-principal-name consultor_otra.com#EXT#@empresa.onmicrosoft.com \
  --user-type Guest
```

**En la práctica:** Los usuarios se gestionan desde el portal de Entra ID o se sincronizan desde Active Directory on-premises con Azure AD Connect. Raramente los creáis por CLI.

## Slide 5 — Grupos: organizar permisos

Los grupos simplifican la asignación de permisos:

**Tipos:**
- **Security groups:** Para asignar permisos (RBAC, acceso a apps)
- **Microsoft 365 groups:** Para colaboración (Teams, SharePoint, email)

```bash
# Crear grupo de seguridad
az ad group create --display-name "Desarrolladores" --mail-nickname "desarrolladores"

# Añadir miembro al grupo
USER_ID=$(az ad user show --id pedro@empresa.com --query id -o tsv)
az ad group member add --group "Desarrolladores" --member-id $USER_ID

# Listar miembros
az ad group member list --group "Desarrolladores" \
  --query "[].{nombre:displayName, email:userPrincipalName}" --output table

# Asignar rol RBAC al grupo (en vez de a cada usuario individual)
GROUP_ID=$(az ad group show --group "Desarrolladores" --query id -o tsv)
az role assignment create --assignee $GROUP_ID \
  --role "Contributor" --resource-group rg-ventas-dev
```

**Patrón recomendado:** No asignéis permisos a usuarios individuales. Cread grupos ("Desarrolladores", "QA", "Administradores") y asignad permisos a los grupos. Cuando alguien cambia de rol, movéis al usuario de grupo — los permisos se actualizan automáticamente.

## Slide 6 — RBAC de Azure vs Roles de Entra ID

Son dos sistemas de roles diferentes:

**RBAC de Azure (roles sobre recursos):**
- Owner, Contributor, Reader sobre suscripciones/RGs/recursos
- Controlan qué puedes hacer en Azure: crear VMs, desplegar apps, leer métricas
- Se asignan en Portal → Resource → Access Control (IAM)

**Roles de Entra ID (roles sobre el directorio):**
- Global Administrator, User Administrator, Application Administrator
- Controlan qué puedes hacer en Entra ID: crear usuarios, registrar apps, configurar MFA
- Se asignan en Portal → Entra ID → Roles and administrators

```
Pedro tiene:
- Contributor en rg-ventas-dev (RBAC Azure) → puede gestionar recursos Azure
- Application Developer (Entra ID) → puede registrar apps para OAuth2
No tiene:
- Owner en la suscripción → no puede cambiar permisos
- Global Administrator → no puede gestionar usuarios del directorio
```

## Slide 7 — Roles de Entra ID más comunes

| Rol | Qué puede hacer |
|-----|----------------|
| **Global Administrator** | Todo. Equivalente a root. Mínimo 2, máximo 4 personas. |
| **User Administrator** | Gestionar usuarios y grupos. Resetear passwords. |
| **Application Administrator** | Registrar y configurar apps (OAuth2, service principals). |
| **Cloud Application Administrator** | Como App Admin pero sin acceso a app proxy. |
| **Security Administrator** | Gestionar políticas de seguridad, MFA, conditional access. |
| **Privileged Role Administrator** | Asignar roles de Entra ID a otros. |
| **Billing Administrator** | Gestionar facturación y suscripciones. |

**Para vuestro equipo:**
- El formador (Pedro): Application Administrator (para registrar apps de demo)
- Los desarrolladores: Cloud Application Administrator (o nada si no registran apps)
- Admin de la organización: Global Administrator (ya lo tendrá)

## Slide 8 — App Registrations: identidad para aplicaciones

Cuando vuestra app necesita autenticar usuarios con Entra ID, necesitáis un **App Registration**:

```
App Registration = "Mi app web necesita autenticar usuarios con la cuenta corporativa"
```

```bash
# Crear app registration
az ad app create \
  --display-name "Ventas Web App" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "https://app-ventas.azurewebsites.net/signin-oidc" "http://localhost:5000/signin-oidc"

# El resultado incluye:
# appId (client ID) — identifica tu app
# objectId — ID interno del registro
```

**Conceptos clave:**
- **Client ID (appId):** Identifica tu app públicamente. No es un secreto.
- **Client Secret:** Password de la app. ES un secreto (Key Vault).
- **Redirect URI:** Donde Entra ID envía al usuario después de autenticarse.
- **Sign-in audience:** Quién puede autenticarse:
  - `AzureADMyOrg`: solo tu tenant
  - `AzureADMultipleOrgs`: cualquier tenant Entra ID
  - `AzureADandPersonalMicrosoftAccount`: corporativas + personales

## Slide 9 — Service Principals: identidad para automatización

Cuando un pipeline o script necesita autenticarse sin intervención humana:

```bash
# Crear service principal para el pipeline CI/CD
az ad sp create-for-rbac \
  --name "sp-pipeline-ventas" \
  --role Contributor \
  --scopes "/subscriptions/<id>/resourceGroups/rg-ventas-prod"

# Resultado:
# {
#   "appId": "xxx",        ← Client ID
#   "password": "yyy",     ← Client Secret (guardar en Key Vault!)
#   "tenant": "zzz"        ← Tenant ID
# }
```

**Login con Service Principal (en pipelines):**
```bash
az login --service-principal \
  --username <appId> \
  --password <password> \
  --tenant <tenant>
```

**En Azure DevOps:** Creáis una "Service Connection" que almacena el service principal. El pipeline lo usa automáticamente sin exponer las credenciales.

## Slide 10 — Managed Identity vs Service Principal vs App Registration

| | Managed Identity | Service Principal | App Registration |
|---|:---:|:---:|:---:|
| **Para qué** | Recurso Azure accede a otro recurso | Script/pipeline se autentica | App autentica usuarios |
| **Secreto** | Ninguno (gestionado por Azure) | Client Secret o Certificate | Client Secret o Certificate |
| **Rotación** | Automática | Manual (o Key Vault) | Manual (o Key Vault) |
| **Ejemplo** | App Service → Cosmos DB | Pipeline CI/CD → Azure | Web App → "Login con tu cuenta" |
| **Recomendación** | Siempre que sea posible | Pipelines y scripts | Apps que autentican usuarios |

**Prioridad de uso:**
1. Managed Identity (sin secretos — ideal)
2. Service Principal con certificado (más seguro que password)
3. Service Principal con client secret (Key Vault para el secret)

## Slide 11 — Permisos de API: lo que tu app puede hacer

Cuando registráis una app, definís qué APIs puede acceder y con qué permisos:

**Delegated permissions:** Tu app actúa EN NOMBRE del usuario. Si el usuario no tiene acceso, la app tampoco.
**Application permissions:** Tu app actúa CON SU PROPIA identidad. No necesita un usuario autenticado.

```bash
# Añadir permiso delegado: leer perfil del usuario
az ad app permission add \
  --id <app-id> \
  --api 00000003-0000-0000-c000-000000000000 \
  --api-permissions e1fe6dd8-ba31-4d61-89e7-88639da4683d=Scope
# 00000003... = Microsoft Graph
# e1fe6dd8... = User.Read (delegated)

# Conceder admin consent (para application permissions)
az ad app permission admin-consent --id <app-id>
```

**Microsoft Graph permissions comunes:**
- `User.Read` (delegated): Leer perfil del usuario autenticado
- `User.ReadAll` (application): Leer todos los usuarios del directorio
- `Mail.Send` (delegated): Enviar email en nombre del usuario
- `Directory.Read.All` (application): Leer todo el directorio

## Slide 12 — Conditional Access: políticas inteligentes

Conditional Access aplica reglas según el contexto del login:

**Ejemplos de políticas:**
| Condición | Acción |
|-----------|--------|
| Login desde fuera de España | Requerir MFA |
| Login desde dispositivo no corporativo | Bloquear o requerir MFA |
| Login a apps de producción | Siempre MFA |
| Login de administradores | Siempre MFA + dispositivo compliant |
| Login desde IP desconocida + riesgo alto | Bloquear |

**Configuración:** Portal → Entra ID → Security → Conditional Access → New Policy

**Para vuestro equipo:** Como mínimo, MFA obligatorio para Global Administrators y para acceso al portal de Azure.

## Slide 13 — MFA: Multi-Factor Authentication

**Métodos de MFA disponibles en Entra ID:**
1. Microsoft Authenticator app (push notification) — recomendado
2. FIDO2 security key (hardware) — más seguro
3. SMS (código por texto) — menos seguro, aceptable
4. Phone call — legacy
5. TOTP (Google Authenticator, etc.) — aceptable

**Habilitar MFA para todos los usuarios:**
Portal → Entra ID → Security → MFA → Getting started → Enable per-user MFA

**O mejor: con Conditional Access (más flexible):**
Crear una policy que requiera MFA para "All users" al acceder a "All cloud apps".

**Security Defaults (mínimo absoluto):**
Si no configuráis nada más, al menos activad Security Defaults: MFA para admins, bloquear legacy auth.
```
Portal → Entra ID → Properties → Manage Security defaults → Enabled
```

## Slide 15 — Privileged Identity Management (PIM)

PIM permite asignar roles de forma temporal (just-in-time):

**Sin PIM:** Pedro es Contributor 24/7. Si su cuenta se compromete, el atacante tiene Contributor 24/7.

**Con PIM:** Pedro puede ACTIVAR Contributor cuando lo necesita (máximo 8 horas). El resto del tiempo no tiene el rol.

```
Pedro necesita desplegar:
1. Portal → PIM → My Roles → Activate "Contributor"
2. Justificación: "Despliegue versión 2.4"
3. Aprobación: automática o por manager
4. Rol activo durante 4 horas
5. Expiración automática → vuelve a Reader
```

**Requiere Entra ID P2.** Para equipos que gestionan producción crítica, PIM es una de las mejores inversiones en seguridad.

## Slide 17 — App Registration: configuración completa

```bash
# Crear registration con todas las opciones relevantes
az ad app create \
  --display-name "Ventas Web App" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris \

az ad sp create --id $APP_ID

  --api-permissions e1fe6dd8-ba31-4d61-89e7-88639da4683d=Scope

# Conceder consent
az ad app permission admin-consent --id $APP_ID
```

## Slide 18 — Tokens: lo que recibe tu app

Cuando un usuario se autentica, tu app recibe tokens JWT:

**ID Token:** Identidad del usuario (quién es).
```json
{
  "aud": "client-id-de-tu-app",
  "iss": "https://login.microsoftonline.com/tenant-id/v2.0",
  "sub": "user-id-unico",
  "name": "Pedro García",
  "preferred_username": "pedro@empresa.com",
  "email": "pedro@empresa.com",
  "roles": ["Admin", "Developer"],
  "groups": ["group-id-desarrolladores"],
  "exp": 1718456789
}
```

**Access Token:** Autorización (qué puede hacer). Se envía como `Authorization: Bearer <token>` a la API.

**Refresh Token:** Para obtener nuevos tokens sin re-autenticar.

**Tu app NUNCA debe validar tokens manualmente** (salvo APIs puras). Usad las librerías de Microsoft (`Microsoft.Identity.Web`) que lo hacen automáticamente.

## Slide 20 — Proteger APIs con Entra ID (Easy Auth)

La forma más rápida de proteger una Web App o Function App:

```bash
# Habilitar Easy Auth con Entra ID
az webapp auth microsoft update \
  --name app-ventas -g rg-ventas-prod \
  --client-id $APP_ID \
  --issuer "https://login.microsoftonline.com/<tenant-id>/v2.0" \
  --yes

# Habilitar autenticación
az webapp auth update --name app-ventas -g rg-ventas-prod \
  --enabled true \
  --action LoginWithAzureActiveDirectory
```

**Resultado:** Cualquier petición sin token válido es redirigida al login de Entra ID. Sin cambiar una línea de código.

**Limitaciones de Easy Auth:**
- No permite autorización granular (solo autenticación on/off)
- Configuración limitada por CLI (mejor en portal)
- Para control fino, mejor implementar en código con `Microsoft.Identity.Web`

## Slide 24 — Emergency Access Accounts (Break Glass)

Cuentas de emergencia para cuando el Global Admin está bloqueado:

```bash
# Crear cuenta de emergencia
az ad user create --display-name "Emergency Access 1" \
  --user-principal-name emergency1@empresa.onmicrosoft.com \
  --password "SuperCompleja123!@#$%^" \
  --force-change-password-next-sign-in false

# Asignar Global Administrator
az role assignment create --assignee emergency1@empresa.onmicrosoft.com \
  --role "Global Administrator" --scope "/"
```

**Reglas para break glass accounts:**
- Mínimo 2 cuentas (redundancia)
- Password extremadamente larga (>30 chars) guardada en caja fuerte física
- SIN MFA (para poder acceder si MFA está caído)
- Excluidas de TODAS las Conditional Access policies
- Monitorizadas: alerta inmediata si alguna se usa
- Probadas trimestralmente (verificar que funcionan)

## Slide 25 — Entra ID Connect: sincronizar con AD on-premises

Si tenéis Active Directory on-premises:

```
AD on-premises                    Entra ID (cloud)
┌──────────────┐   Entra Connect  ┌──────────────┐
│ Users        │ ──────────────→  │ Users        │
│ Groups       │   sincronización │ Groups       │
│ Passwords    │   cada 30 min    │ Password hash│
└──────────────┘                  └──────────────┘
```

**Password Hash Sync:** Las passwords se sincronizan como hash. Los usuarios usan la misma password en on-prem y en cloud. Método más simple.

**Pass-through Auth:** Las passwords NO se sincronizan. Entra ID reenvía la autenticación a un agente on-premises. Para organizaciones que no quieren passwords en la nube.

**Federation (ADFS):** Todo el flujo de autenticación pasa por ADFS on-premises. Más complejo, para escenarios muy específicos.

## Slide 28 — Continuous Access Evaluation (CAE)

CAE revoca tokens al instante (no esperas a expiración):

```
ANTES (token tradicional):
├── User logs in → token válido 1 hora
├── Admin disable user → token aún válido 59 min más
└── Attacker con token robado: 1 hora de acceso

CON CAE (Continuous Access Evaluation):
├── User logs in → token con CAE
├── Admin disable user → señal a recursos
├── Token rejected next request → ~20 segundos de gap
└── Attacker rejected casi inmediatamente
```

**Cómo funciona:**
```
┌─────────────────────────────────────────────────────────────────┐
│  EVENTOS QUE TRIGGER CAE                                         │
├─────────────────────────────────────────────────────────────────┤
│ 1. User account deleted o disabled                              │
│ 2. User password changed/reset                                  │
│ 3. MFA enabled for user                                         │
│ 4. User location changed (nuevo país)                           │
│ 5. User risk detected (Identity Protection)                     │
│ 6. Admin invalidates sessions explicitly                        │
└─────────────────────────────────────────────────────────────────┘

Flow:
1. Resource (e.g. Exchange Online) registra subscriber con Entra ID
2. User authenticates → token issued with CAE claim
3. Cuando ocurre evento, Entra ID notifies resource
4. Resource invalida token cached + forces re-auth
5. User must re-login (ej. with new MFA)
```

**Servicios soportados (2026):**
- ✅ Exchange Online
- ✅ SharePoint Online + OneDrive
- ✅ Microsoft Teams
- ✅ Microsoft Graph
- ✅ Azure CLI / PowerShell
- ✅ Azure Resource Manager
- ⚠️ Tu propio API si lo configuras

```csharp

    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)

});

// Manejar claims challenges (re-auth required)
public class CaeMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        try
        {
            await next(context);
        }
        catch (MsalUiRequiredException ex) when (ex.Claims != null)
        {
            // Re-auth needed (CAE event triggered)
            context.Response.StatusCode = 401;
            context.Response.Headers["WWW-Authenticate"] =

            return;
        }
    }
}
```

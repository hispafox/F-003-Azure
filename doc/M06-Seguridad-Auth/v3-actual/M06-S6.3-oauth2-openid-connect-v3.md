## Slide 2 — Por qué necesitáis entender OAuth2
Cuando el usuario hace clic en "Iniciar sesión con cuenta corporativa", por detrás hay una coreografía de redirecciones, tokens y validaciones. Si algo falla, necesitáis entender qué pasó.

OAuth2 no es una librería — es un protocolo. OpenID Connect (OIDC) es una capa encima que añade identidad. Entender los flujos os permite depurar problemas de autenticación, configurar correctamente los App Registrations, y elegir el flujo correcto para cada tipo de aplicación.

---

## Slide 3 — OAuth2 vs OpenID Connect: la diferencia

**OAuth2:** Protocolo de AUTORIZACIÓN. "¿Puede esta app acceder a los datos del usuario?"
- Resultado: Access Token (permiso para acceder a una API)
- No dice QUIÉN es el usuario

**OpenID Connect (OIDC):** Capa de AUTENTICACIÓN sobre OAuth2. "¿QUIÉN es este usuario?"
- Resultado: ID Token (identidad del usuario) + Access Token
- Dice quién es el usuario Y qué puede hacer

**En la práctica:** Siempre usáis OIDC (que incluye OAuth2). La distinción importa cuando depuráis: si tenéis access token pero no id token, es OAuth2 puro (no tenéis identidad del usuario).

## Slide 4 — Los roles en OAuth2/OIDC

```
┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│   Resource    │     │  Authorization   │     │    Client     │
│    Owner      │     │    Server        │     │  Application  │
│  (el usuario) │     │  (Entra ID)      │     │  (vuestra app)│
└──────┬───────┘     └────────┬─────────┘     └──────┬───────┘
       │                      │                       │
       │  "Sí, permito que    │  "Aquí tienes un      │
       │   la app acceda      │   token con los       │
       │   a mis datos"       │   permisos que        │
       │                      │   el usuario aprobó"  │
       └──────────────────────┘───────────────────────┘
                              │
                     ┌────────┴────────┐
                     │  Resource Server │
                     │   (vuestra API)  │
                     │  "Token válido,  │
                     │   acceso OK"     │
                     └─────────────────┘
```

**Resource Owner:** El usuario que tiene los datos
**Authorization Server:** Entra ID (emite tokens)
**Client Application:** Vuestra app (pide tokens)
**Resource Server:** Vuestra API (valida tokens y da acceso a datos)

## Slide 6 — Flujo Authorization Code + PKCE (el estándar)

```
USUARIO          VUESTRA APP          ENTRA ID          VUESTRA API
  │                   │                   │                   │
  ├──"Login"──→       │                   │                   │
  │                   ├──Redirect──→      │                   │
  │                   │    /authorize?    │                   │
  │                   │    client_id=xxx  │                   │
  │                   │    redirect_uri=  │                   │
  │                   │    scope=openid   │                   │
  │                   │    code_challenge │                   │
  │    ←──Login page──┤                   │                   │
  ├──user+pass+MFA──→ │                   │                   │
  │                   │    ←──code──      │                   │
  │                   │    (302 redirect) │                   │
  │                   │                   │                   │
  │                   ├──POST /token──→   │                   │
  │                   │  code + verifier  │                   │
  │                   │    ←──tokens──    │                   │
  │                   │  (id_token +      │                   │
  │                   │   access_token +  │                   │
  │                   │   refresh_token)  │                   │
  │                   │                   │                   │
  │                   ├──GET /api/datos──────────────→        │
  │                   │  Authorization: Bearer <access_token> │
  │    ←──datos──     │    ←──datos──────────────────         │
```

**PKCE (Proof Key for Code Exchange):** El cliente genera un `code_verifier` random, envía su hash (`code_challenge`) en el paso 1, y el verifier original en el paso 2. Esto previene que alguien intercepte el `code` y lo use — necesitaría también el verifier.

## Slide 7 — Authorization Code en código .NET (Web App)

```bash
dotnet add package Microsoft.Identity.Web
dotnet add package Microsoft.Identity.Web.UI
```

```csharp
// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddMicrosoftIdentityWebAppAuthentication(builder.Configuration, "AzureAd")
    .EnableTokenAcquisitionToCallDownstreamApi()
    .AddInMemoryTokenCaches();

builder.Services.AddAuthorization();

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/", [Authorize] (HttpContext ctx) =>
{
    var nombre = ctx.User.FindFirst("name")?.Value;
    var email = ctx.User.FindFirst("preferred_username")?.Value;
    return Results.Json(new { nombre, email, autenticado = true });
});

app.MapGet("/login", () => Results.Challenge(new AuthenticationProperties { RedirectUri = "/" }));
app.MapGet("/logout", () => Results.SignOut());

app.Run();
```

## Slide 9 — Flujo Client Credentials (servicio a servicio)

Para cuando NO hay usuario (daemons, Functions con timer, pipelines):

```
VUESTRA FUNCTION          ENTRA ID          API PROTEGIDA
      │                      │                    │
      ├──POST /token──→      │                    │
      │  client_id=xxx       │                    │
      │  client_secret=yyy   │                    │
      │  scope=api://api-id/.default              │
      │      ←──access_token─┤                    │
      │                      │                    │
      ├──GET /api/datos──→──────────────→         │
      │  Authorization: Bearer <token>            │
      │      ←──datos────────────────────         │
```

No hay redirección, no hay usuario, no hay consentimiento. La app se autentica directamente con su client_id + client_secret.

```csharp
// En una Azure Function (timer trigger, por ejemplo)
var app = ConfidentialClientApplicationBuilder
    .Create(clientId)
    .WithClientSecret(clientSecret)
    .WithAuthority($"https://login.microsoftonline.com/{tenantId}")
    .Build();

var result = await app.AcquireTokenForClient(
    scopes: new[] { "api://api-ventas/.default" })
    .ExecuteAsync();

var httpClient = new HttpClient();
httpClient.DefaultRequestHeaders.Authorization = 
    new AuthenticationHeaderValue("Bearer", result.AccessToken);
var datos = await httpClient.GetAsync("https://api-ventas.azurewebsites.net/api/pedidos");
```

## Slide 11 — Flujo On-Behalf-Of (API → API)

Cuando vuestra API necesita llamar a otra API en nombre del usuario:

```
Usuario → Web App → API A (con access_token del user)
                        ↓
                    API A necesita llamar a API B
                    pero API B necesita saber QUIÉN es el usuario
                        ↓
                    OBO: API A pide un nuevo token para API B
                    usando el token del usuario como "prueba"
                        ↓
                    API A → API B (con nuevo access_token, mismo usuario)
```

```csharp
var app = ConfidentialClientApplicationBuilder.Create(clientId)
    .WithClientSecret(clientSecret)
    .WithAuthority($"https://login.microsoftonline.com/{tenantId}")
    .Build();

var userAssertion = new UserAssertion(incomingAccessToken);
var result = await app.AcquireTokenOnBehalfOf(
    scopes: new[] { "api://api-b/.default" },
    userAssertion: userAssertion)
    .ExecuteAsync();
```

## Slide 12 — Tokens JWT: anatomía

Un token JWT tiene 3 partes separadas por puntos: `header.payload.signature`

**Header:**
```json
{ "typ": "JWT", "alg": "RS256", "kid": "key-id-para-verificar-firma" }
```

**Payload (claims):**
```json
{
  "aud": "api://api-ventas",           // Audiencia: para quién es este token
  "iss": "https://login.microsoftonline.com/tenant-id/v2.0",  // Emisor
  "sub": "user-unique-id",             // Subject: ID único del usuario
  "name": "Pedro García",              // Nombre
  "preferred_username": "pedro@empresa.com",
  "email": "pedro@empresa.com",
  "roles": ["Admin"],                  // Roles asignados
  "groups": ["group-id-1"],            // Grupos
  "scp": "User.Read Pedidos.ReadWrite", // Scopes (delegated)
  "iat": 1718400000,                   // Issued at
  "exp": 1718403600,                   // Expires (1 hora)
  "nbf": 1718400000                    // Not before
}
```

**Signature:** HMAC o RSA firma del header+payload. Entra ID firma con su clave privada. Tu API verifica con la clave pública (auto-descubierta vía OIDC discovery endpoint).

## Slide 14 — NUNCA validéis tokens manualmente

```csharp
// MAL: validación manual (miles de cosas que pueden salir mal)
var handler = new JwtSecurityTokenHandler();
var token = handler.ReadJwtToken(bearerToken);
if (token.ValidTo < DateTime.UtcNow) throw new Exception("Expirado");
// ¿Y la firma? ¿Y el issuer? ¿Y la audiencia? ¿Y los roles?

// BIEN: usar la librería que lo hace todo
builder.Services.AddMicrosoftIdentityWebApiAuthentication(config, "AzureAd");
// Valida: firma, issuer, audiencia, expiración, nonce, claims...
```

**La librería valida automáticamente:**
1. Firma del token (descarga las claves de Entra ID y verifica)
2. Issuer (es Entra ID de vuestro tenant, no un atacante)
3. Audience (el token es para VUESTRA app, no para otra)
4. Expiración (no ha caducado)
5. Not Before (no es un token del futuro)

## Slide 15 — Scopes y permisos: definir qué puede hacer la app

**Definir scopes custom en vuestra API:**

Portal → App Registration de la API → Expose an API → Add a scope:
- `Pedidos.Read`: puede leer pedidos
- `Pedidos.ReadWrite`: puede leer y escribir pedidos
- `Admin.All`: acceso de administrador

**En la app cliente, pedir los scopes:**
```csharp
// Al autenticarse, la app pide estos scopes
var scopes = new[] { "api://api-ventas/Pedidos.Read", "api://api-ventas/Pedidos.ReadWrite" };
```

**En la API, verificar el scope:**
```csharp
app.MapPost("/api/pedidos", [Authorize] async (HttpContext ctx) =>
{
    var scopes = ctx.User.FindFirst("scp")?.Value?.Split(' ') ?? Array.Empty<string>();
    if (!scopes.Contains("Pedidos.ReadWrite"))
        return Results.Forbid();
    // Crear pedido...
});
```

## Slide 16 — Consent: el usuario acepta los permisos

Cuando una app pide permisos por primera vez, el usuario (o un admin) debe aceptar:

**User Consent:** El usuario acepta individualmente. Para permisos delegated como `User.Read`.

**Admin Consent:** Un admin acepta en nombre de toda la organización. Obligatorio para application permissions como `User.Read.All`.

```bash
# Admin consent por CLI
az ad app permission admin-consent --id $APP_ID
```

**Configurar la política de consent:**
Portal → Entra ID → Enterprise Applications → Consent and permissions:
- "Users can consent to apps": Sí (para permisos de bajo riesgo)
- "Admin consent required for all": No (demasiado restrictivo para desarrollo)
- "Custom policy": Los usuarios pueden consentir scopes de bajo riesgo, admin para el resto

## Slide 17 — MSAL: Microsoft Authentication Library

MSAL es la librería oficial para implementar OAuth2/OIDC con Entra ID:

```bash
# Para apps web y APIs
dotnet add package Microsoft.Identity.Web

# Para apps de escritorio/CLI
dotnet add package Microsoft.Identity.Client

# Para Blazor
dotnet add package Microsoft.Authentication.WebAssembly.Msal
```

**MSAL gestiona:**
- Adquisición de tokens (todos los flujos)
- Cache de tokens (no pide un token nuevo cada vez)
- Refresh automático (usa el refresh token cuando el access token expira)
- Retry con backoff (si Entra ID está lento)

**NO uséis ADAL** (Azure Active Directory Authentication Library). Está deprecada. MSAL es el reemplazo.

## Slide 18 — Token cache: no pedir tokens de más

```csharp
// MSAL gestiona la cache automáticamente
// En Web Apps:
builder.Services.AddMicrosoftIdentityWebAppAuthentication(config)
    .EnableTokenAcquisitionToCallDownstreamApi()
    .AddInMemoryTokenCaches();   // Cache en memoria (OK para 1 instancia)
    // .AddDistributedTokenCaches(); // Cache distribuida (Redis, SQL) para múltiples instancias

// En APIs/Services:
var app = ConfidentialClientApplicationBuilder.Create(clientId)
    .WithClientSecret(clientSecret)
    .Build();

// MSAL reutiliza el token de cache si no ha expirado
var result = await app.AcquireTokenForClient(scopes).ExecuteAsync();
// Primera vez: va a Entra ID, pide token, lo cachea
// Segunda vez: devuelve el token cacheado (sin ir a Entra ID)
// Cuando expira: automáticamente pide uno nuevo
```

**En producción con múltiples instancias:** Usad cache distribuida (Redis) para que todas las instancias compartan tokens. Sin esto, cada instancia pide su propio token y multiplicáis las peticiones a Entra ID.

## Slide 19 — Proteger una Azure Function con Entra ID (código)

```csharp
// Program.cs
var host = new HostBuilder()
    .ConfigureFunctionsWebApplication(worker =>
    {
        worker.UseMiddleware<AuthenticationMiddleware>();
```

```csharp
// Function con autenticación
public class PedidosSecureApi
{
    [Function("GetMisPedidos")]
    public async Task<IActionResult> GetMisPedidos(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "mis-pedidos")]
        HttpRequest req)
    {
        var user = req.HttpContext.User;
        if (!user.Identity?.IsAuthenticated ?? true)
            return new UnauthorizedResult();
        
        var userId = user.FindFirst("sub")?.Value 
            ?? user.FindFirst("oid")?.Value;
        
        var pedidos = await _service.GetPedidosByClienteAsync(userId!);
        return new OkObjectResult(pedidos);
    }
}
```

**Nota:** `AuthorizationLevel.Anonymous` para desactivar function keys — la autenticación la hace Entra ID con el token, no la function key.

## Slide 20 — OIDC Discovery: cómo descubre tu app la configuración

Tu app no necesita hardcodear URLs de Entra ID. El OIDC Discovery endpoint las provee:

```
GET https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration
```

Devuelve:
```json
{
  "authorization_endpoint": "https://login.microsoftonline.com/.../oauth2/v2.0/authorize",
  "token_endpoint": "https://login.microsoftonline.com/.../oauth2/v2.0/token",
  "jwks_uri": "https://login.microsoftonline.com/.../discovery/v2.0/keys",
  "issuer": "https://login.microsoftonline.com/{tenant-id}/v2.0",
  "scopes_supported": ["openid", "profile", "email", "offline_access"],
  "response_types_supported": ["code", "id_token", "token"],
  "claims_supported": ["sub", "iss", "aud", "exp", "name", "email", ...]
}
```

`Microsoft.Identity.Web` usa este endpoint automáticamente. No necesitáis configurar nada más que `Instance` + `TenantId`.

## Slide 21 — Logout: cerrar sesión correctamente

```csharp
// En la Web App
app.MapGet("/logout", async (HttpContext ctx) =>
{
    await ctx.SignOutAsync(OpenIdConnectDefaults.AuthenticationScheme);
    await ctx.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    // Redirige a Entra ID para cerrar la sesión también allí
});
```

**Single Logout:** Cerrar sesión en vuestra app AND en Entra ID. Si solo cerráis la cookie de vuestra app, el usuario sigue autenticado en Entra ID y podría volver a entrar sin password.

**Front-channel logout:** Entra ID notifica a todas las apps que el usuario cerró sesión. Configurar `LogoutUrl` en la App Registration.

## Slide 22 — Debuggear problemas de autenticación

**Herramientas:**
1. **jwt.ms:** Pegar un token JWT y ver su contenido decodificado. https://jwt.ms
2. **Browser DevTools → Network:** Ver las redirecciones OAuth2 y los tokens en las respuestas
3. **Fiddler/mitmproxy:** Capturar tráfico HTTPS entre tu app y Entra ID
4. **Application Insights:** Buscar errores de autenticación en los logs

**Errores comunes:**
| Error | Causa | Solución |
|-------|-------|----------|
| `AADSTS50011: Reply URL mismatch` | La redirect URI no coincide con la registrada | Verificar redirect URIs en App Registration |
| `AADSTS700016: Application not found` | Client ID incorrecto | Verificar appId |
| `AADSTS7000215: Invalid client secret` | Secret expirado o incorrecto | Rotar en App Registration, actualizar Key Vault |
| `AADSTS65001: User needs to consent` | El usuario no aceptó los permisos | Admin consent o user consent |
| `AADSTS50076: MFA required` | La policy requiere MFA | Completar MFA |
| `401 Unauthorized` en la API | Token expirado, audiencia incorrecta, scope faltante | Verificar token en jwt.ms |

## Slide 23 — Redirect URIs: las trampas más comunes

```bash
# Registrar redirect URIs
az ad app update --id $APP_ID \
  --web-redirect-uris \
    "https://app-ventas.azurewebsites.net/signin-oidc" \
    "http://localhost:5000/signin-oidc" \
    "http://localhost:5001/signin-oidc"
```

**Las trampas:**
- **HTTP vs HTTPS:** En producción, solo HTTPS. En local, HTTP está permitido para localhost.
- **Trailing slash:** `https://app.com/callback` ≠ `https://app.com/callback/`. Deben coincidir exactamente.
- **Puerto:** `http://localhost:5000` ≠ `http://localhost:5001`. Registrad todos los puertos que uséis.
- **Path:** `/signin-oidc` es el default de Microsoft.Identity.Web. Si lo cambiáis, actualizad en ambos sitios.
- **Wildcards:** No soportados en redirect URIs (por seguridad).

## Slide 24 — Multi-tenant: autenticación de cualquier organización

Si vuestra app necesita autenticar usuarios de OTROS tenants:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "common",  // "common" acepta cualquier tenant + cuentas personales
                            // "organizations" acepta cualquier tenant Entra ID
                            // "<guid>" acepta solo vuestro tenant
    "ClientId": "<app-id>"
  }
}
```

**Validación en multi-tenant:**
```csharp
builder.Services.AddMicrosoftIdentityWebApiAuthentication(config, "AzureAd")
    .EnableTokenAcquisitionToCallDownstreamApi();

// Si es multi-tenant, necesitáis validar el issuer vosotros:
builder.Services.Configure<JwtBearerOptions>(JwtBearerDefaults.AuthenticationScheme, options =>
{
    var originalValidator = options.TokenValidationParameters.IssuerValidator;
    options.TokenValidationParameters.IssuerValidator = (issuer, token, parameters) =>
    {
        // Verificar que el tenant está en vuestra lista de tenants permitidos
        var tenantId = token.Claims.First(c => c.Type == "tid").Value;
        if (!allowedTenants.Contains(tenantId))
            throw new SecurityTokenInvalidIssuerException($"Tenant {tenantId} no permitido");
        return issuer;
    };
});
```

## Slide 25 — Refresh Tokens: mantener la sesión

El access token dura ~1 hora. El refresh token permite obtener uno nuevo sin re-autenticar:

```
1. User se autentica → recibe access_token (1h) + refresh_token (90 días)
2. access_token expira
3. App usa refresh_token para pedir nuevo access_token
4. Entra ID devuelve nuevo access_token + nuevo refresh_token
5. Repeat hasta que el refresh_token expire o sea revocado
```

**MSAL gestiona esto automáticamente.** No necesitáis código para el refresh. Solo aseguraos de que la cache persiste (en memoria para dev, Redis para prod).

**Revocar sesión:**
```bash
# Revocar todos los tokens de un usuario (forzar re-login)
az ad user update --id pedro@empresa.com --force-change-password-next-sign-in
```

## Slide 29 — FIDO2 / Passkeys: el futuro sin passwords

FIDO2 (WebAuthn) elimina passwords completamente con autenticación biométrica:

```
Tradicional:
├── Server stores password hash
├── User types password (puede phishing)
├── Hash matched: success
└── Vulnerable to: phishing, breaches, weak passwords

FIDO2:
├── Server stores public key (NO secret)
├── User uses biometric (fingerprint, face) o security key
├── Device signs challenge with private key
├── Server verifies con public key
└── Vulnerable to: nothing remote (private key never leaves device)
```

**Cómo funciona en .NET:**
```csharp
// Build WebAuthn challenge
[HttpPost("webauthn/register/begin")]
public async Task<IActionResult> RegisterBegin([FromBody] string username)
{
    var user = await _userManager.FindByNameAsync(username);
    
    var options = _fido2.RequestNewCredential(
        user: new Fido2User
        {
            Id = Encoding.UTF8.GetBytes(user.Id),
            Name = user.UserName,
            DisplayName = user.UserName
        },
        excludeCredentials: new List<PublicKeyCredentialDescriptor>(),
        authenticatorSelection: AuthenticatorSelection.Default,
        attestationPreference: AttestationConveyancePreference.None);
    
    HttpContext.Session.SetString("fido2.attestationOptions", options.ToJson());
    return Ok(options);
}

// Browser does WebAuthn ceremony, devuelve la response
[HttpPost("webauthn/register/complete")]
public async Task<IActionResult> RegisterComplete([FromBody] AuthenticatorAttestationRawResponse attestationResponse)
{
    var jsonOptions = HttpContext.Session.GetString("fido2.attestationOptions");
    var options = CredentialCreateOptions.FromJson(jsonOptions);
    
    var success = await _fido2.MakeNewCredentialAsync(
        attestationResponse, options, IsCredentialIdUniqueToUser);
    
    // Store public key in DB for future authentications
    await _credentialStore.AddAsync(new StoredCredential
    {
        Id = success.Result.CredentialId,
        PublicKey = success.Result.PublicKey,
        UserHandle = success.Result.User.Id
    });
    
    return Ok();
}

// Login con FIDO2
[HttpPost("webauthn/login/begin")]
public async Task<IActionResult> LoginBegin([FromBody] string username)
{
    var user = await _userManager.FindByNameAsync(username);
    var existingCredentials = await _credentialStore.GetByUserAsync(user.Id);
    
    var options = _fido2.GetAssertionOptions(
        existingCredentials.Select(c => new PublicKeyCredentialDescriptor(c.Id)),
        UserVerificationRequirement.Required);
    
    HttpContext.Session.SetString("fido2.assertionOptions", options.ToJson());
    return Ok(options);
}
```

## Slide 30 — mTLS: autenticación bidirecional

mTLS (mutual TLS) — both client AND server present certificates:

```
Standard TLS:
├── Server presents cert
├── Client verifies server identity
└── Client identity NOT verified at TLS layer

mTLS:
├── Server presents cert (verified by client)
├── Client presents cert (verified by server)
└── Both parties cryptographically authenticated
```

**Cuándo usar mTLS:**
- ✅ Service-to-service en zero-trust networks
- ✅ B2B APIs con partners conocidos
- ✅ IoT devices conectando back to cloud
- ✅ Internal microservices (mesh)

**App Service mTLS:**
```bash

az webapp update --resource-group rg-prod \
  --name api-pedidos \
  --client-cert-mode Required

# Listas de cert exclusion paths (para health checks, etc)
az webapp update --resource-group rg-prod \
  --name api-pedidos \
  --client-cert-exclusion-paths "/health,/ping"
```

**Validar cert en .NET:**
```csharp
// Program.cs
builder.Services.Configure<KestrelServerOptions>(options =>
{
    options.ConfigureHttpsDefaults(httpsOptions =>
    {
        httpsOptions.ClientCertificateMode = ClientCertificateMode.RequireCertificate;
    });
});

builder.Services.AddAuthentication(CertificateAuthenticationDefaults.AuthenticationScheme)
    .AddCertificate(options =>
    {
        options.AllowedCertificateTypes = CertificateTypes.Chained;
        options.RevocationMode = X509RevocationMode.Online;
        
        options.Events = new CertificateAuthenticationEvents
        {
            OnCertificateValidated = ctx =>
            {
                // Validate the certificate
                var thumbprint = ctx.ClientCertificate.Thumbprint;
                var allowedThumbprints = new[] { "ABC123...", "DEF456..." };
                
                if (!allowedThumbprints.Contains(thumbprint))
                {
                    ctx.Fail("Cert not in allowed list");
                    return Task.CompletedTask;
                }
                
                // Build claims based on cert
                var claims = new[]
                {
                    new Claim(ClaimTypes.NameIdentifier, ctx.ClientCertificate.Subject),
                    new Claim(ClaimTypes.Name, ctx.ClientCertificate.Subject),
                    new Claim("CertThumbprint", thumbprint)
                };
                
                ctx.Principal = new ClaimsPrincipal(
                    new ClaimsIdentity(claims, ctx.Scheme.Name));
                ctx.Success();
                return Task.CompletedTask;
            }
        };
    });

// In controller
```

## Slide 32 — Step-up authentication patterns

Step-up = pedir auth más fuerte para operations sensitive:

```
Patrón:
├── Normal access: regular auth (token básico)
├── Sensitive operation: requires elevated auth
│   └── User does additional MFA or step-up
├── Operation completed
└── Step-up auth válida X minutes
```

**Use cases:**
- Transferir > €1000
- Cambiar password admin
- Ver datos PII de otro user
- Modify financial records
- Delete production resources

**Implementación con auth context:**
```csharp
[Authorize]
public class FinancialController : ControllerBase
{
    [HttpPost("transfer/large")]
    public async Task<IActionResult> LargeTransfer([FromBody] TransferRequest req)
    {
        // Check if user has step-up auth claim
        var authContextClaim = User.FindFirst("acrs")?.Value;
        
        if (authContextClaim != "c1")  // c1 = step-up authenticated
        {
            // Trigger step-up challenge
            return Challenge(new AuthenticationProperties
            {
                Items = 
                { 
                    ["claims"] = "{\"access_token\":{\"acrs\":{\"essential\":true,\"value\":\"c1\"}}}"
                }
            });
        }
        
        // Step-up confirmed, process transfer
        await _bankingService.TransferAsync(req);
        return Ok();
    }
}
```

**En Entra ID, configurar Authentication Context:**
```
Portal → Entra ID → Conditional Access → Authentication contexts

Nuevo Auth Context:
├── ID: c1
├── Display name: "Sensitive financial operations"
├── Description: "Required for transfers > €1000"
└── Published: ✅

Then create CA policy:
├── Apply to: Authentication context "c1"
└── Grant: Require MFA + Compliant device
```

**Frontend handling:**
```javascript

  try {
    await fetch('/api/transfer/large', {
      method: 'POST',
      body: JSON.stringify({ amount }),
      headers: { Authorization: `Bearer ${token}` }
    });
  } catch (error) {
    if (error.response.status === 401 && error.response.headers.get('WWW-Authenticate')?.includes('claims=')) {
      // Extract claims challenge

      const newToken = await msalInstance.acquireTokenPopup({

      });

      await fetch('/api/transfer/large', {
        method: 'POST',
        body: JSON.stringify({ amount }),
        headers: { Authorization: `Bearer ${newToken}` }
      });
    }
  }
}
```

- Step-up token same lifetime as regular (60 min)
- Don't store separately - reuse if "acrs" claim present
- Re-prompt only if expired or operation requires fresher auth

## Slide 33 — Token revocation y session management

Tokens son largos por design (60 min) — pero hay mecanismos de revocación:

```
Mecanismos de revocación (de menos a más rápido):

1. Token expiration (60 min default)
   └── Wait for natural expiry

2. Refresh token revocation
   ├── Admin revokes user's refresh tokens
   ├── User can no longer renew access tokens
   ├── Active access tokens still valid until expire
   └── Effective: hasta 60 min después

3. Continuous Access Evaluation (CAE)
   ├── Real-time invalidation
   ├── Critical events propagate <1 min
   └── Effective: 60 segundos típicos

4. App-level session invalidation
   ├── Your app maintains session state
   ├── Mark session "revoked" en DB
   ├── Validate cada request
   └── Effective: immediate
```

**Revocar refresh tokens (admin):**
```bash
# Force user re-auth (invalidates all refresh tokens)
az ad user revoke-sign-in-sessions --user pedro@empresa.com

# Programmatic via Graph
POST https://graph.microsoft.com/v1.0/users/pedro@empresa.com/revokeSignInSessions
```

**Server-side session validation pattern:**
```csharp
// Maintain session state independent del token
public class SessionValidator
{
    private readonly ISessionStore _sessionStore;
    
    public async Task<bool> ValidateSessionAsync(ClaimsPrincipal user)
    {
        var sessionId = user.FindFirst("sid")?.Value;
        if (string.IsNullOrEmpty(sessionId)) return false;
        
        var session = await _sessionStore.GetAsync(sessionId);
        if (session == null || session.IsRevoked)
        {
            return false;
        }
        
        // Update last activity
        session.LastActivity = DateTimeOffset.UtcNow;
        await _sessionStore.UpdateAsync(session);
        
        return true;
    }
    
    public async Task RevokeSessionAsync(string sessionId)
    {
        var session = await _sessionStore.GetAsync(sessionId);
        session.IsRevoked = true;
        await _sessionStore.UpdateAsync(session);
    }
    
    public async Task RevokeAllUserSessionsAsync(string userId)
    {
        var sessions = await _sessionStore.GetByUserAsync(userId);
        foreach (var session in sessions)
        {
            session.IsRevoked = true;
            await _sessionStore.UpdateAsync(session);
        }
    }
}

// Middleware
public class SessionValidationMiddleware
{
    public async Task InvokeAsync(HttpContext context, RequestDelegate next, SessionValidator validator)
    {
        if (context.User.Identity?.IsAuthenticated == true)
        {
            var valid = await validator.ValidateSessionAsync(context.User);
            if (!valid)
            {
                context.Response.StatusCode = 401;
                await context.Response.WriteAsync("Session revoked");
                return;
            }
        }
        
        await next(context);
    }
}
```

```csharp
public class OrderAuthorizationHandler : AuthorizationHandler<OperationAuthorizationRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        OperationAuthorizationRequirement requirement,
        Order order)
    {
        var userId = context.User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
        
        if (requirement.Name == "Read")
        {
            // Owner OR Admin
            if (order.UserId == userId || context.User.IsInRole("Admin"))
                context.Succeed(requirement);
        }
        else if (requirement.Name == "Edit")
        {
            // Solo Owner mientras no enviado
            if (order.UserId == userId && order.Status == "Draft")
                context.Succeed(requirement);
        }
        else if (requirement.Name == "Cancel")
        {
            // Owner O CustomerService role
            if (order.UserId == userId || context.User.IsInRole("CustomerService"))
                context.Succeed(requirement);
        }
        
        return Task.CompletedTask;
    }
}

// Use en controller
```

```csharp
public class AbacAuthorizationHandler : AuthorizationHandler<AbacRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        AbacRequirement requirement)
    {
        // User attributes
        var userAttributes = new Dictionary<string, string>
        {
            ["Department"] = context.User.FindFirst("Department")?.Value,
            ["ClearanceLevel"] = context.User.FindFirst("Clearance")?.Value,
            ["Country"] = context.User.FindFirst("Country")?.Value,
            ["Title"] = context.User.FindFirst("Title")?.Value
        };
        
        // Resource attributes
        var resourceAttributes = new Dictionary<string, string>
        {
            ["Classification"] = requirement.Resource.Classification,
            ["Owner"] = requirement.Resource.Owner,
            ["Region"] = requirement.Resource.Region
        };
        
        // Policy: "User can access if 
        //         their clearance >= resource classification AND
        //         they're in same region OR same department as owner"
        var clearanceOk = ClearanceLevels.Compare(
            userAttributes["ClearanceLevel"], 
            resourceAttributes["Classification"]) >= 0;
        
        var regionOk = userAttributes["Country"] == resourceAttributes["Region"];
        
        var deptOk = userAttributes["Department"] == 
                     _userService.GetDepartment(resourceAttributes["Owner"]);
        
        if (clearanceOk && (regionOk || deptOk))
        {
            context.Succeed(requirement);
        }
        
        return Task.CompletedTask;
    }
}
```

```csharp
        .ExecuteAsync();
}
```

## Slide 37 — Anti-patterns OAuth2/OIDC: errores comunes

```
❌ ANTI-PATTERN 1: Implicit Flow
   - Tokens en URL (logged everywhere)
   - No refresh tokens
   - Deprecated since 2019
   ✅ Use Authorization Code + PKCE

❌ ANTI-PATTERN 2: ROPC (Resource Owner Password Credentials)
   - User types password directamente en tu app
   - Defeats whole purpose of OAuth2
   - No supports MFA
   ✅ Use Authorization Code flow (browser-based)

❌ ANTI-PATTERN 3: Storing tokens en localStorage
   - XSS attacks pueden robar
   ✅ HTTPOnly cookies for refresh tokens
   ✅ Memory-only for access tokens

❌ ANTI-PATTERN 4: Validating tokens manually
   - JWT signing algorithms tricky
   - Missing checks (audience, issuer, expiration)
   ✅ Use Microsoft.Identity.Web library

❌ ANTI-PATTERN 5: Not validating issuer
   var tokenValidationParameters = new TokenValidationParameters
   {
       ValidateIssuer = false  // ❌ NEVER
   };
   ✅ ValidateIssuer = true + IssuerValidator

❌ ANTI-PATTERN 6: Using same token for multiple resources
   - Token for API A used to call API B
   ✅ Acquire separate token per resource (per audience)

❌ ANTI-PATTERN 7: Hardcoded redirect URIs
   redirectUri: "http://localhost:5000/signin-oidc"
   ✅ Per-environment configuration
   ✅ Validate redirect URI strictly en App Registration

❌ ANTI-PATTERN 8: Long-lived tokens
   - 24h tokens minimize re-auth pero amplify breach
   ✅ Default 60 min, refresh con CAE

❌ ANTI-PATTERN 9: Sin PKCE en SPAs/mobile
   - Code interception attacks
   ✅ Always PKCE for public clients

❌ ANTI-PATTERN 10: Not handling claims challenges
   - CAE events don't trigger re-auth
   ✅ Catch MsalUiRequiredException with claims
```

**El más caro que he visto:**
```
SPA con tokens en localStorage:
├── XSS attack (vulnerable npm package)
├── Attacker robó tokens de 50K users
├── Used tokens para download de 200GB de PII
├── Cost: €5M en regulatory fines + reputation damage
└── Fix would have been: HttpOnly cookies (10 lines of code)
```

## Slide 38 — Auth context: granular API protection

Auth contexts permiten "tagging" recursos con auth requirements específicos:

```
Concept:
├── Define auth contexts: c1, c2, c3 (custom values)
├── Resources can require specific contexts
├── Conditional Access policies map contexts to requirements
└── User must satisfy CA when accessing context-tagged resources
```

**Definir auth contexts en Entra ID:**
```
Portal → Entra ID → Conditional Access → Authentication contexts

Context 1: c1
├── Display: "Sensitive operations"
├── Description: "Required for financial transfers > €1000"

Context 2: c2  
├── Display: "Production access"
├── Description: "Required for production resources"

Context 3: c3
├── Display: "Admin operations"
├── Description: "Required for tenant configuration changes"
```

**CA policies para cada context:**
```
Policy "Sensitive ops require strong MFA":
├── Apply to: Auth context "c1"
└── Grant: Require MFA + Compliant device

Policy "Production requires MFA + named location":
├── Apply to: Auth context "c2"
├── Conditions: Locations exclude "Corporate office"
└── Grant: Require MFA + compliant device

Policy "Admin ops require phishing-resistant":
├── Apply to: Auth context "c3"
└── Grant: Require auth strength "Phishing-resistant MFA"
```

**Tu API enforce auth context:**
```csharp
[HttpPost("transfer")]
public async Task<IActionResult> Transfer([FromBody] TransferRequest req)
{
    if (req.Amount > 1000)
    {
        // Require auth context c1
        var hasC1 = User.FindAll("acrs").Any(c => c.Value == "c1");
        if (!hasC1)
        {
            return Challenge(new AuthenticationProperties
            {
                Items = { ["claims"] = "{\"access_token\":{\"acrs\":{\"essential\":true,\"value\":\"c1\"}}}" }
            });
        }
    }
    
    if (req.IsCrossBorder)
    {
        // Require additional context c2
        var hasC2 = User.FindAll("acrs").Any(c => c.Value == "c2");
        if (!hasC2)
        {
            return Challenge(...);
        }
    }
    
    await _bankingService.TransferAsync(req);
    return Ok();
}
```

## Slide 40 — Cierre del submódulo
OAuth2/OIDC son los protocolos que hacen funcionar toda la autenticación moderna. No necesitáis memorizarlos — necesitáis entender los flujos para elegir el correcto y depurar cuando algo falla.

Authorization Code + PKCE para apps con usuario. Client Credentials para servicios. MSAL gestiona tokens y cache. Microsoft.Identity.Web configura todo en ASP.NET Core con mínimo código.

Lo más importante: nunca validéis tokens manualmente, nunca guardéis client secrets en código, y siempre usad HTTPS.

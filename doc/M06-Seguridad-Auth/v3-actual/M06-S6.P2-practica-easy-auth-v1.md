## Slide 2 — Qué vais a construir

Una Web App protegida con autenticación de Microsoft Entra usando **App Service Authentication (Easy Auth)** — la solución integrada que añade login sin tocar código.

**El recorrido:**

```
1. Reutilizar (o crear) una Web App F1 sencilla
2. Habilitar Easy Auth desde el portal
3. Probar: sin login → 401, con login → tu identidad
4. Inspeccionar los headers que añade Easy Auth
5. Ver datos del usuario en /.auth/me
6. Configurar logout y redirects
7. Limpiar
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ App Registration manual (Easy Auth la crea automáticamente)
- ❌ Client secrets (Easy Auth los gestiona)
- ❌ Key Vault (eso es M06-S6.P principal)
- ❌ Validación de tokens en código (Easy Auth lo hace por ti)
- ❌ Scopes ni roles personalizados (M06-S6.P)

**Por qué Easy Auth como práctica simplificada:**

- ✅ Auth funcional en 5 minutos sin tocar código
- ✅ Modelo mental claro: el "antes y después" de habilitar
- ✅ No requiere conocer OAuth2/OIDC en profundidad
- ✅ Suficiente para un %95 de apps internas corporativas
- ✅ Sirve como base para entender qué hace OAuth2 por debajo

**Tiempo estimado:** 45-60 minutos.

**Coste real:** **0€** (Web App F1 gratis + Easy Auth gratis + Microsoft Entra incluido).


**Permisos requeridos:**

```
✅ Owner o Contributor en la suscripción → para crear Web App
✅ User en Microsoft Entra → para que Easy Auth pueda registrar la app

Si veis "Insufficient privileges to complete the operation":
- El admin del tenant debe permitir a usuarios crear App Registrations
- O pedir al admin que habilite Easy Auth manualmente
```

**Tener una Web App ya creada (o crearla rápido):**


```
- Capa de auth INTEGRADA en App Service
- Vive ANTES de tu código (request → Easy Auth → tu app)
- Soporta: Microsoft Entra, Google, Facebook, X, GitHub, Apple
- Sin escribir código C# para auth básica

Microsoft Entra (antes Azure AD):
- Servicio de identidad de Microsoft
- Tu cuenta corporativa ya está aquí
- Es el proveedor más común para Easy Auth en empresa
```

## Slide 5 — Paso 2: Habilitar Easy Auth desde el portal

Easy Auth se habilita típicamente desde el portal (más visual). Lo hacemos paso a paso:

**1. Abrir vuestra Web App en el portal:**

```
Portal Azure → Resource Groups → rg-curso-easyauth-<tu-nombre>
              → vuestra Web App (webapp-easyauth-...)
              → Settings → Authentication
```

**2. Click en "Add identity provider":**

```
Identity provider: Microsoft (Microsoft Entra)
App registration type: Create new app registration
Name: webapp-easyauth-<tu-nombre>-app  (o dejar el default)
Supported account types: 
  ☑ Current tenant - Single tenant  (recomendado para empezar)
```

**3. Configurar opciones de App Service:**

```
Restrict access: Require authentication  ✓
Unauthenticated requests: HTTP 302 Found redirect: recommended for websites
Token store: ☑ enabled  (default)
```

**4. Click "Add":**

```
Esperar 30-60 segundos a que se aplique.
Detrás de las escenas:
- Se crea una App Registration en Microsoft Entra
- Se configura como reply URL: https://<tu-app>.azurewebsites.net/.auth/login/aad/callback
- Se enlaza con vuestra Web App
- App Service inserta middleware Easy Auth ANTES de vuestro código
```

**Verificación:**

```
Portal → Identity providers
Esperado: Microsoft con estado "Configured"
```

**Importante:** todo esto pasó **sin que vosotros hayáis tocado código**. El middleware de Easy Auth vive en App Service, no en vuestra app.

## Slide 6 — Paso 3: Probar el flujo de autenticación

```bash
# Sin token, sin cookie → debería redirigir o devolver 401
curl -i https://$APP_NAME.azurewebsites.net/

# Output esperado:
# HTTP/1.1 302 Found
# Location: /.auth/login/aad?post_login_redirect_url=...
```

**Lo que pasó:**

```
Cliente → App Service Easy Auth → ¿tiene cookie/token? NO
                                  → 302 Redirect a /.auth/login/aad
                                  → Vuestra app NO recibió el request
```

**Probar en navegador:**

```
1. Abrid https://<tu-app>.azurewebsites.net/ en navegador NUEVO (modo incógnito)
2. Os redirige automáticamente a login.microsoftonline.com
3. Iniciáis sesión con vuestra cuenta corporativa
4. Os redirige de vuelta a vuestra app
5. AHORA sí veis la página HTML
```

**Diagrama del flujo OAuth/OIDC subyacente:**

```
1. GET /  
2. App Service → 302 → /.auth/login/aad
3. /.auth/login/aad → 302 → login.microsoftonline.com/<tenant>/oauth2/v2.0/authorize
4. Login en Microsoft Entra (usuario+contraseña, MFA)
5. Microsoft Entra → 302 → /.auth/login/aad/callback?code=...
6. App Service intercambia code por id_token + access_token
7. App Service guarda tokens en cookie cifrada
8. App Service → 302 → / (la URL original)
9. GET / con cookie de sesión
10. App Service → "OK, autenticado" → forward a vuestra app
11. Vuestra app responde con la página HTML
```

**Verificar la cookie en el navegador:**

```
DevTools → Application → Cookies → vuestra-app.azurewebsites.net
Veréis:
- AppServiceAuthSession (cookie cifrada con tokens)
```

## Slide 7 — Paso 4: Inspeccionar /.auth/me

Easy Auth expone un endpoint mágico que muestra TODA la info del usuario logueado:

**En el navegador (autenticado):**

```
https://<tu-app>.azurewebsites.net/.auth/me
```

**Output esperado (JSON):**

```json
[
  {
    "access_token": "eyJ0eXAiOi...",
    "expires_on": "2026-04-28T15:30:45.0000000Z",
    "id_token": "eyJ0eXAiOi...",
    "provider_name": "aad",
    "user_claims": [
      { "typ": "aud", "val": "abc-app-id-..." },
      { "typ": "iss", "val": "https://sts.windows.net/<tenant>/" },
      { "typ": "name", "val": "Pedro Pérez" },
      { "typ": "preferred_username", "val": "pedro@empresa.com" },
      { "typ": "oid", "val": "12345678-..." },
      { "typ": "tid", "val": "<tenant-id>" },
      { "typ": "groups", "val": "..." }
    ],
    "user_id": "pedro@empresa.com"
  }
]
```

**Lo que cada claim significa:**

```
aud:               audience (vuestra App ID)
iss:               issuer (Microsoft Entra de vuestro tenant)
name:              nombre completo del usuario
preferred_username: email principal del usuario
oid:               object ID único en Microsoft Entra
tid:               tenant ID
groups:            grupos a los que pertenece (si los habilitasteis)
```

**Cómo usarlo en código (si quisierais ir más allá del HTML estático):**

Si tuvierais una API .NET, podríais leer estos datos de los headers que App Service inserta:

```csharp
// En cualquier endpoint de tu API .NET
app.MapGet("/perfil", (HttpContext ctx) =>
{
    var name = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL-NAME"].ToString();
    var id = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL-ID"].ToString();
    var idp = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL-IDP"].ToString();
    
    // X-MS-CLIENT-PRINCIPAL trae el JWT decodificado en base64
    var principalHeader = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL"].ToString();
    var principalJson = Convert.FromBase64String(principalHeader);
    
    return Results.Ok(new { name, id, idp, claims = principalJson });
});
```

**Pero no necesitamos código:** Easy Auth os da `/.auth/me` listo para usar.

## Slide 8 — Paso 5: Logout y endpoints adicionales

Easy Auth añade varios endpoints útiles:

**Cerrar sesión:**

```
https://<tu-app>.azurewebsites.net/.auth/logout
```

**Lo que hace:**

```
1. Borra la cookie de sesión
2. Redirige al usuario al endpoint de logout de Microsoft Entra
3. Microsoft Entra invalida la sesión
4. Vuelve a la URL configurada (default: /)
5. Como no hay cookie, le pide login otra vez
```

**Login manual** (forzar re-autenticación):

```
https://<tu-app>.azurewebsites.net/.auth/login/aad
```

**Forzar re-login** (útil tras cambio de cuenta):

```
https://<tu-app>.azurewebsites.net/.auth/login/aad?prompt=login
```

**Refrescar tokens:**

```
https://<tu-app>.azurewebsites.net/.auth/refresh
```

**Lista completa de endpoints `/.auth/`:**

```
GET  /.auth/me                  → claims del usuario
GET  /.auth/login/aad           → iniciar login con Microsoft Entra
GET  /.auth/logout              → cerrar sesión y redirect
GET  /.auth/refresh             → refrescar tokens
GET  /.auth/token/aad           → ver tokens actuales (si está habilitado)
GET  /.auth/login/google        → si tenéis Google configurado
GET  /.auth/login/facebook      → idem
```

**Probar el flujo completo:**

```bash
# 1. Abrir incógnito → redirect a login → completar login → ver página
# 2. Verificar /.auth/me → ver claims
# 3. Visitar /.auth/logout → vuelve a "no autenticado"
# 4. Recargar / → redirect a login otra vez

# El ciclo completo en pocos clicks
```

**Configurar después-del-logout URL** (donde redirigir tras cerrar sesión):

```
Portal → Authentication → Edit (Microsoft Entra)
Sign-out URL: https://<tu-app>.azurewebsites.net/goodbye
```

## Slide 9 — Paso 6: Headers de App Service tras Easy Auth

Cuando Easy Auth deja pasar un request, **inyecta headers que tu app puede leer**. Esos headers son la "API" entre Easy Auth y tu código:

**Headers principales:**

```
X-MS-CLIENT-PRINCIPAL-NAME    → username (email del usuario)
X-MS-CLIENT-PRINCIPAL-ID      → object ID en Microsoft Entra
X-MS-CLIENT-PRINCIPAL-IDP     → identity provider ("aad", "google", etc.)
X-MS-CLIENT-PRINCIPAL         → JWT con claims completos (base64)
X-MS-TOKEN-AAD-ID-TOKEN       → id_token raw (si está habilitado)
X-MS-TOKEN-AAD-ACCESS-TOKEN   → access_token raw
X-MS-TOKEN-AAD-REFRESH-TOKEN  → refresh_token (si está habilitado)
```

**Cómo verlos:**

Si vuestra app fuera una API .NET:

```csharp
app.MapGet("/headers", (HttpContext ctx) =>
{
    var authHeaders = ctx.Request.Headers
        .Where(h => h.Key.StartsWith("X-MS-"))
        .ToDictionary(h => h.Key, h => h.Value.ToString());
    
    return Results.Ok(authHeaders);
});
```

Output esperado:

```json
{
  "X-MS-CLIENT-PRINCIPAL-NAME": "pedro@empresa.com",
  "X-MS-CLIENT-PRINCIPAL-ID": "abc-123-def-456",
  "X-MS-CLIENT-PRINCIPAL-IDP": "aad",
  "X-MS-CLIENT-PRINCIPAL": "eyJhdXRoX3R5cCI6ImFhZCIs..." (base64)
}
```

**Decodificar el header X-MS-CLIENT-PRINCIPAL:**

```bash
# El valor es base64 de un JSON con todos los claims
HEADER_VALUE="eyJhdXRoX3R5cCI6..."
echo "$HEADER_VALUE" | base64 -d | jq

# Output:
# {
#   "auth_typ": "aad",
#   "claims": [
#     { "typ": "name", "val": "Pedro Pérez" },
#     { "typ": "preferred_username", "val": "pedro@empresa.com" },
#     ...
#   ],
#   "name_typ": "name",
#   "role_typ": "..."
# }
```

**Patrón de uso en producción:**

```csharp
public class CurrentUserService
{
    public string? Email(HttpContext ctx) =>
        ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL-NAME"].FirstOrDefault();
    
    public string? UserId(HttpContext ctx) =>
        ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL-ID"].FirstOrDefault();
    
    public IDictionary<string, string> AllClaims(HttpContext ctx)
    {
        var header = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL"].FirstOrDefault();
        if (string.IsNullOrEmpty(header)) return new Dictionary<string, string>();
        
        var json = Encoding.UTF8.GetString(Convert.FromBase64String(header));
        var doc = JsonDocument.Parse(json);
        
        return doc.RootElement.GetProperty("claims")
            .EnumerateArray()
            .ToDictionary(
                c => c.GetProperty("typ").GetString()!,
                c => c.GetProperty("val").GetString()!);
    }
}
```

## Slide 10 — Paso 7: Configurar comportamiento al no-autenticar

Easy Auth puede manejar usuarios no autenticados de varias formas:

**1. HTTP 302 Redirect (recomendado para webs):**

```
Portal → Authentication → Edit Microsoft Entra
Restrict access: Require authentication
Unauthenticated requests: HTTP 302 Found redirect: <provider>
```

```
Comportamiento:
- Sin sesión → redirect a login.microsoftonline.com
- Tras login → vuelve a la URL original
- Ideal para: aplicaciones web tradicionales
```

**2. HTTP 401 Unauthorized (recomendado para APIs):**

```
Portal → Authentication → Edit Microsoft Entra
Restrict access: Require authentication
Unauthenticated requests: HTTP 401 Unauthorized: recommended for APIs
```

```
Comportamiento:
- Sin token → 401 inmediato
- El cliente debe gestionar el flujo de auth
- Ideal para: APIs REST consumidas por SPAs / mobile
```

**3. Allow unauthenticated requests:**

```
Portal → Authentication → Edit Microsoft Entra
Restrict access: Allow unauthenticated access
```

```
Comportamiento:
- Pasa todos los requests
- Tu app decide qué hacer con auth (tipo opcional)
- Ideal para: páginas mixtas (públicas + privadas)
```

**Combinaciones típicas:**

```
App tipo SPA + API en mismo App Service:
- Web: 302 redirect (login automático para usuarios)
- /api/*: configurar exclusión + manejar 401 manualmente

App pública con sección admin:
- Allow unauthenticated
- Vuestro código verifica X-MS-CLIENT-PRINCIPAL en endpoints admin
```

**Probar el cambio:**

```bash
# Cambiar a 401 desde CLI
az webapp auth update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --unauthenticated-client-action Return401

# Probar (sin cookie)
curl -i https://$APP_NAME.azurewebsites.net/

# Output esperado:
# HTTP/1.1 401 Unauthorized
```

## Slide 11 — Configurar URL exclusion paths (rutas públicas)

A veces queréis que parte de la app sea pública (login page custom, health checks, webhook):

**Excluir rutas vía Portal:**

```
Portal → Authentication → Excluded paths
Añadir:
- /health
- /api/public/*
- /static/*
```

**Excluir rutas vía CLI:**

```bash
# Excluir varias rutas
az webapp auth update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --excluded-paths "/health" "/api/public/*"

# Verificar
az webapp auth show \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --query "globalValidation.excludedPaths" -o table
```

**Probar las exclusiones:**

```bash
# /health debería ser público
curl -s https://$APP_NAME.azurewebsites.net/health
# Si vuestra app responde aquí: ✓ Easy Auth no aplicó

# / debería seguir requiriendo auth
curl -i https://$APP_NAME.azurewebsites.net/
# Esperado: 302 o 401
```

**Casos típicos:**

```
✅ /health o /healthz → para health probes de balanceadores
✅ /api/webhooks/* → para callbacks de servicios externos (Stripe, etc.)
✅ /static/* → para assets públicos (logos, css)
✅ /robots.txt → para crawlers SEO
✅ /.well-known/* → para verificaciones de dominio

❌ NO excluir /api/* completo (defeats the purpose)
❌ NO excluir /admin/* (sería catastrófico)
```

**Importante con webhooks:**

```
Si excluís un webhook (/api/webhooks/stripe), vuestra app debe validar:
- Signature del webhook (secret compartido)
- Origen (IP del proveedor, si lo permite)
- Idempotencia (mismo evento puede llegar 2 veces)

Easy Auth NO os protege ahí, vosotros sí.
```

## Slide 12 — Smoke tests automatizados

Script bash que valida el flujo de auth (sin login real, solo verifica que Easy Auth está activo):

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

BASE="${1:?Pasa la URL base como primer argumento}"

echo "🔍 Smoke tests sobre $BASE"

# Test 1: Sin auth → 302 o 401 (depende de config)
echo -n "  [1/4] Sin auth → 302/401... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/")
if [ "$HTTP_CODE" = "302" ] || [ "$HTTP_CODE" = "401" ]; then
  echo "✓ ($HTTP_CODE)"
else
  echo "✗ (esperado 302 o 401, recibido $HTTP_CODE)"
  exit 1
fi

# Test 2: Endpoint /.auth/me sin auth → 401 (siempre)
echo -n "  [2/4] /.auth/me sin auth → 401... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/.auth/me")
[ "$HTTP_CODE" = "401" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 3: Endpoint /.auth/login/aad → 302 a Microsoft
echo -n "  [3/4] /.auth/login/aad → 302... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/.auth/login/aad")
[ "$HTTP_CODE" = "302" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 4: Verificar que la redirect URL es a login.microsoftonline.com
echo -n "  [4/4] Redirect a Microsoft Entra... "
REDIRECT=$(curl -s -I "$BASE/.auth/login/aad" | grep -i "^location:" | tr -d '\r')
if echo "$REDIRECT" | grep -q "login.microsoftonline.com"; then
  echo "✓"
else
  echo "✗"
  echo "  Recibido: $REDIRECT"
  exit 1
fi

echo ""
echo "✅ Smoke tests pasados — Easy Auth está correctamente configurado"
EOF

chmod +x smoke-tests.sh
./smoke-tests.sh "https://$APP_NAME.azurewebsites.net"
```

**Output esperado:**

```
🔍 Smoke tests sobre https://webapp-easyauth-pedro.azurewebsites.net
  [1/4] Sin auth → 302/401... ✓ (302)
  [2/4] /.auth/me sin auth → 401... ✓
  [3/4] /.auth/login/aad → 302... ✓
  [4/4] Redirect a Microsoft Entra... ✓

✅ Smoke tests pasados — Easy Auth está correctamente configurado
```

**Tests interactivos (los que requieren navegador):**

```

1. Abrir / en navegador incógnito → ver redirect a Microsoft
2. Hacer login → ver la página
3. Visitar /.auth/me → ver claims
4. Visitar /.auth/logout → cerrar sesión
5. Recargar / → vuelve a pedir login
```

## Slide 13 — Comparativa: Easy Auth vs auth en código

¿Cuándo usar Easy Auth y cuándo implementar auth en vuestro código?

| Aspecto | Easy Auth | **Auth en código (M06-S6.P)** |
|---|---|---|
| **Líneas de código** | 0 | **~100-200 líneas** |
| **Tiempo de setup** | 5 min | **2-4 horas** |
| **Token validation** | Automático | **Manual con Microsoft.Identity.Web** |
| **Refresh tokens** | Automático | **Vuestra responsabilidad** |
| **Cookie management** | App Service lo hace | **Vuestra responsabilidad** |
| **Logout** | `/.auth/logout` | **Implementar custom** |
| **Custom claims logic** | Limitado | **Total control** |
| **Multi-provider** | Click & config | **Implementar manualmente** |
| **API authorization** | Headers solo | **Policies, attributes, roles** |
| **Portabilidad** | Solo App Service | **Cualquier hosting** |

**Cuándo SÍ Easy Auth:**

```
✅ App interna corporativa (intranet)
✅ MVP / prototipo rápido
✅ App donde "auth básica" es suficiente
✅ Equipo sin experiencia en OAuth2/OIDC
✅ No necesitáis lógica custom en login
```

**Cuándo NO Easy Auth (mejor en código):**

```
❌ App pública con multi-tenant complejo
❌ Custom branding del flow de login
❌ Lógica custom durante login (provisionar usuario, etc.)
❌ Necesitáis claims que no vienen del IdP
❌ App debe correr en otro hosting (no App Service)
❌ Auth muy sofisticada: scopes, roles dinámicos, etc.
```

**Patrón típico de migración:**

```
Fase 1: Easy Auth (MVP, lanzamiento rápido)
       ↓ La app crece, necesitáis más control
Fase 2: Easy Auth + código custom para algunos endpoints
       ↓ Cada vez más lógica
Fase 3: Auth completo en código (Microsoft.Identity.Web)
```

**No es "una vs otra":** muchas apps usan Easy Auth para el caso simple y código custom para flujos avanzados.

## Slide 14 — Variante: Easy Auth con APIs (no UI)

Easy Auth también funciona con APIs REST sin UI. Configuración ligeramente distinta:

**1. Cambiar a 401 (no 302):**

```bash
az webapp auth update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --unauthenticated-client-action Return401
```

**2. Cliente envía Bearer token:**

```bash
# El cliente obtiene un token de Microsoft Entra y lo manda en Authorization
TOKEN="eyJ0eXAiOiJKV1QiLCJhbGciOi..."

curl -H "Authorization: Bearer $TOKEN" \
  https://$APP_NAME.azurewebsites.net/api/data
```

**3. Easy Auth valida el token automáticamente:**

```
Cliente → App Service:
  Authorization: Bearer eyJ...

App Service Easy Auth:
  ✓ Verificar firma del token
  ✓ Verificar audience (= App ID)
  ✓ Verificar issuer (= Microsoft Entra del tenant)
  ✓ Verificar expiración
  ✓ Si todo OK → forward a vuestra API + headers X-MS-*
  ✗ Si falla → 401 Unauthorized
```

**Cómo obtener un token para tests:**

```bash
# Obtener token con az CLI (usando vuestra propia identidad)
TOKEN=$(az account get-access-token \
  --resource api://<app-id-de-easy-auth> \
  --query accessToken -o tsv)

# O para tests rápidos: usar el token de la propia API de Microsoft Graph
TOKEN=$(az account get-access-token \
  --resource https://graph.microsoft.com \
  --query accessToken -o tsv)

# IMPORTANTE: Easy Auth solo acepta tokens cuya audience sea TU APP
# Si el token es para Graph, Easy Auth lo rechaza
```

**Limitación a saber:**

```
Easy Auth con tokens (modo API) tiene limitaciones:
- Solo acepta tokens v1.0 por defecto (configurable)
- No valida scopes específicos (vosotros lo hacéis)
- No tiene authorization granular (todo o nada)
- Para API REST sería mejor: Microsoft.Identity.Web + JWT validation explícita
```

**Para esta práctica:** dejamos Easy Auth en modo "redirect" (302). Las APIs REST con Bearer token se cubren a fondo en M06-S6.P principal.

## Slide 16 — Troubleshooting: errores comunes

Los 6 errores más típicos con Easy Auth y cómo resolverlos:

**1. "AADSTS50011: Reply URL mismatch"**

```
Causa: la URL a la que Microsoft Entra debe redirigir no está en la App Registration

Diagnóstico:
- Mirar el error completo en navegador (URL devuelta)
- "redirect_uri=https://<tu-app>.azurewebsites.net/.auth/login/aad/callback"

Fix:
Portal → Microsoft Entra → App registrations → tu app → Authentication
Add redirect URI: https://<tu-app>.azurewebsites.net/.auth/login/aad/callback
Save

(Easy Auth lo configura automáticamente al crear, pero a veces falla)
```

**2. "Loop infinito de redirects"**

```
Causa: la cookie de sesión no se guarda correctamente
Síntoma: redirect a login → login OK → redirect → bucle

Causas comunes:
- HTTPS no está bien configurado
- Cookies de terceros bloqueadas en navegador
- Múltiples instancias de App Service sin sticky sessions

Fix:
- Verificar HTTPS only:
  az webapp update --name $APP_NAME -g $RG_NAME --https-only true
- Probar en otro navegador / modo incógnito
- Verificar que las cookies de tu dominio están permitidas
```

**3. "401 después de login exitoso"**

```
Causa: token llega pero Easy Auth no lo valida
Síntoma: redirect a login → login OK → vuelve con 401

Diagnóstico:
- Visitar /.auth/me → ver si hay claims
- Si /.auth/me devuelve [], el token no se procesó

Fix:
- Verificar audience del token (audience = App ID de la registration)
- Verificar issuer (debe ser Microsoft Entra del tenant correcto)
- Ver logs de Easy Auth: az webapp log tail
```

**4. "Cookie too large" (HTTP 431)**

```
Causa: la cookie AppServiceAuthSession crece demasiado (>4 KB)
Síntoma: Request Header Fields Too Large

Por qué pasa:
- Token contiene muchos grupos de Microsoft Entra (groups claim)
- Si tenéis cientos de grupos, no caben en una cookie

Fix opción A: token compresion
  - Habilitar token store con cifrado más agresivo

Fix opción B: limitar groups en el token
  - Portal → Microsoft Entra → tu App Registration
  - Token configuration → Optional claims
  - Configure groups → "Groups assigned to the application" en vez de "All"
```

**5. "/.auth/me devuelve []"**

```
Causa: estás autenticado pero no hay claims accesibles
Posibles motivos:
- Token store deshabilitado en config
- Sesión expirada (token caducó, refresh falló)
- Error temporal de Microsoft Entra

Fix:
- Verificar token store enabled:
  az webapp auth show --name $APP_NAME -g $RG_NAME \
    --query "globalValidation.tokenStore.enabled"
- Forzar logout + login: /.auth/logout → /
```

**6. "Insufficient privileges to complete the operation"**

```
Causa: vuestro usuario no tiene permisos para crear App Registration
Síntoma: al habilitar Easy Auth en el portal

Fix:
- Pedir al admin que habilite "Users can register applications"
- O pedir al admin que cree la App Registration manualmente
- O usar una cuenta con rol "Application Administrator" en Microsoft Entra
```

**Cuando nada funciona:**

```bash
# Reset completo de Easy Auth
az webapp auth update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --enabled false

# Volver a habilitarlo desde el portal
# (a veces el reset arregla configs corruptas)
```

```bash
# Borrar el Resource Group entero
az group delete \

if [ -n "$APP_REG_ID" ]; then
  az ad app delete --id $APP_REG_ID

else
```

```
App Registration:
- Vive en Microsoft Entra (otro plano)
- NO está en ningún Resource Group
- Persiste aunque borréis la sub o el RG
- Hay que borrarla manualmente
```

## Slide 18 — Buenas prácticas para producción

Si vais a llevar Easy Auth a producción de verdad:

**1. Usar HTTPS only siempre:**

```bash
az webapp update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --https-only true

az webapp config set \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --min-tls-version 1.2
```

**2. Configurar Sign-out URL específica:**

```
Portal → Authentication → Edit Microsoft Entra
Sign-out URL: https://<tu-app>.azurewebsites.net/goodbye

# Para que tras logout vayan a una página tuya, no a Microsoft
```

**3. Configurar token expiry:**

```bash
az webapp auth update \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --token-store true \
  --token-refresh-extension-hours 24

# Tokens se refrescan automáticamente durante 24h
# Tras eso, requiere re-login
```

**4. Limitar a single-tenant para apps internas:**

```
Portal → Microsoft Entra → App Registration
Authentication → Supported account types
☑ "Accounts in this organizational directory only (single tenant)"

# Esto IMPIDE que usuarios de otros tenants accedan
# Crítico para apps internas corporativas
```

**5. Configurar Conditional Access policies:**

```
Portal → Microsoft Entra → Security → Conditional Access
Add policy:
- Users: All users (o grupo específico)
- Cloud apps: tu App Registration
- Conditions: locations / device platforms / sign-in risk
- Grant: require MFA / require compliant device

# Esto da MUCHO más control:
- MFA obligatorio para acceder
- Solo desde dispositivos corporativos
- Solo desde IPs corporativas
- Bloquear países de alto riesgo
```

**6. Usar grupos para authorization (no roles fijos):**

```csharp
// En vuestro código, leer claims["groups"]
var grupos = ctx.Request.Headers["X-MS-CLIENT-PRINCIPAL"];
// Decodificar y verificar pertenencia a grupo

// Ejemplo: solo admins del grupo "App-Curso-Admins"
if (!claims.Any(c => c.Type == "groups" && c.Value == "<group-object-id>"))
{
    return Results.Forbid();
}
```

**7. Logging y auditoría:**

```bash
# Habilitar diagnostic settings → Log Analytics
az monitor diagnostic-settings create \
  --name easyauth-logs \
  --resource $(az webapp show --name $APP_NAME -g $RG_NAME --query id -o tsv) \
  --workspace <log-analytics-workspace-id> \
  --logs '[
    {"category":"AppServiceAuditLogs", "enabled":true},
    {"category":"AppServiceAuthenticationLogs", "enabled":true}
  ]'

# KQL queries útiles:
# - Logins fallidos por usuario
# - Patrones de acceso anómalos
# - Tokens revocados / expirados
```

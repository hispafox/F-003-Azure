## Slide 2 — Dos momentos de vulnerabilidad
Los datos son vulnerables en dos momentos: cuando viajan (en tránsito) y cuando están almacenados (en reposo). Una estrategia de seguridad completa protege ambos.

**En tránsito:** Datos moviéndose entre el usuario y tu app, entre tu app y la DB, entre servicios Azure. Protección: TLS/HTTPS.

**En reposo:** Datos almacenados en disco (Cosmos, SQL, Storage, Key Vault). Protección: cifrado AES-256.

Azure protege ambos por defecto, pero hay configuración que debéis verificar y opciones avanzadas para compliance.

---

## Slide 3 — Cifrado en tránsito: TLS

**TLS (Transport Layer Security)** cifra la comunicación entre dos puntos:

```bash
# Forzar HTTPS en App Service
az webapp update --name app-ventas -g mi-rg --https-only true

# Forzar TLS 1.2 mínimo en App Service
az webapp config set --name app-ventas -g mi-rg --min-tls-version 1.2

# Forzar TLS 1.2 en Storage Account
az storage account update --name stventasprod -g mi-rg --min-tls-version TLS1_2

# Forzar TLS 1.2 en SQL Server
az sql server update --name sql-ventas-prod -g mi-rg --minimal-tls-version 1.2
```

**TLS 1.0 y 1.1 están deprecados.** Si tenéis servicios que los usan, migradlos a TLS 1.2+. Azure ya bloquea TLS < 1.2 en nuevos recursos por defecto.

---

## Slide 4 — Certificados SSL/TLS para custom domains

```bash
# Opción 1: App Service Managed Certificate (gratis, auto-renovación)
az webapp config ssl create --name app-ventas -g mi-rg \
  --hostname ventas.miempresa.com

# Opción 2: Traer vuestro propio certificado (PFX)
az webapp config ssl upload --name app-ventas -g mi-rg \
  --certificate-file certificado.pfx --certificate-password "xxx"

# Bind del certificado al hostname
az webapp config ssl bind --name app-ventas -g mi-rg \
  --certificate-thumbprint <thumbprint> --ssl-type SNI
```

**Managed Certificates** son gratuitos y se renuevan automáticamente. Usadlos siempre que sea posible. Solo traed vuestro certificado si necesitáis wildcard (`*.miempresa.com`) o EV (Extended Validation).

## Slide 5 — Cifrado entre servicios Azure

**App Service → Cosmos DB:** TLS 1.2 por defecto en la connection string. `Encrypt=true` implícito.

**App Service → Azure SQL:** TLS 1.2. El parámetro `Encrypt=true` en la connection string es obligatorio (ya está por defecto en Azure SQL).

**App Service → Storage:** HTTPS obligatorio. `DefaultEndpointsProtocol=https` en la connection string.

**Function → Service Bus:** TLS 1.2 en AMQP sobre WebSocket o TCP directo.

**Todo el tráfico interno de Azure** entre servicios en la misma región viaja por la red backbone de Microsoft (no por internet público). Aun así, está cifrado.

## Slide 6 — Cifrado en reposo: lo que Azure hace por defecto

**TODOS los servicios Azure cifran datos at-rest con AES-256 automáticamente:**

| Servicio | Cifrado | Clave gestionada por |
|----------|:-------:|---------------------|
| Azure Storage | ✓ AES-256 | Microsoft (por defecto) |
| Azure SQL | ✓ TDE (Transparent Data Encryption) | Microsoft (por defecto) |
| Cosmos DB | ✓ AES-256 | Microsoft (por defecto) |
| Key Vault | ✓ HSM-protected | Microsoft (o vuestro HSM) |
| App Service | ✓ (filesystem cifrado) | Microsoft |
| Managed Disks | ✓ SSE (Server-Side Encryption) | Microsoft |

**No necesitáis configurar nada.** El cifrado at-rest está ON por defecto en todos los servicios Azure. Los datos se cifran antes de escribirse a disco y se descifran al leerlos.

## Slide 7 — Customer-Managed Keys (CMK)

Si regulación exige que VOSOTROS controléis las claves de cifrado:

```bash
# 1. Crear Key Vault con purge protection
az keyvault create --name kv-keys-prod -g mi-rg --enable-purge-protection

# 2. Crear clave RSA
az keyvault key create --vault-name kv-keys-prod --name storage-encrypt-key --kty RSA --size 2048

# 3. Habilitar Managed Identity en Storage Account
az storage account update --name stventasprod -g mi-rg --assign-identity

# 4. Dar permisos a Storage para usar la clave
STORAGE_IDENTITY=$(az storage account show --name stventasprod -g mi-rg --query identity.principalId -o tsv)
az keyvault set-policy --name kv-keys-prod \
  --object-id $STORAGE_IDENTITY \
  --key-permissions get wrapKey unwrapKey

# 5. Configurar Storage con CMK
az storage account update --name stventasprod -g mi-rg \
  --encryption-key-source Microsoft.Keyvault \
  --encryption-key-vault "https://kv-keys-prod.vault.azure.net" \
  --encryption-key-name storage-encrypt-key
```

**¿Cuándo CMK?** Banca, sanidad, gobierno, o cualquier regulación que exija "vosotros controláis las claves". Para el 90% de empresas, Microsoft-Managed Keys es suficiente.

## Slide 8 — Transparent Data Encryption (TDE) en SQL

TDE cifra la base de datos completa, backups incluidos:

```bash
# Verificar que TDE está activo (lo está por defecto)
az sql db tde show --server sql-ventas-prod -g mi-rg --database db-ventas
# Status: Enabled

# Cambiar a CMK (si regulación lo requiere)
az sql server tde-key set --server sql-ventas-prod -g mi-rg \
  --server-key-type AzureKeyVault \
  --kid "https://kv-keys-prod.vault.azure.net/keys/sql-encrypt-key/version"
```

**TDE es transparente:** La app no sabe que los datos están cifrados. Lee y escribe normalmente. El cifrado/descifrado ocurre a nivel de storage engine.

## Slide 9 — Always Encrypted en SQL: cifrado que ni Azure puede leer

Para datos ultra-sensibles (tarjetas de crédito, números de seguridad social):

**TDE:** Azure puede leer los datos descifrados (el motor SQL los descifra para procesarlos).
**Always Encrypted:** Los datos están cifrados incluso dentro de SQL Server. Solo la app cliente con la clave puede descifrarlos.

```csharp
// Connection string con Always Encrypted
var connString = "Server=tcp:sql-ventas-prod.database.windows.net;Database=db-ventas;" +
    "Column Encryption Setting=Enabled;" +
    "Authentication=Active Directory Default;";

// EF Core — la columna se descifra automáticamente en el cliente
var clientes = await _db.Clientes.ToListAsync();
// El campo "NumeroTarjeta" viene descifrado. En la DB está cifrado.
```

**Limitaciones:** No se puede hacer WHERE, ORDER BY ni cálculos sobre columnas Always Encrypted (están cifradas — SQL Server no puede procesarlas). Solo queries exactas (equality) con deterministic encryption.

## Slide 10 — Datos en tránsito: mTLS y Private Link

Para máxima seguridad, combinar TLS con private networking:

**Private Link / Private Endpoint:**
El tráfico entre tu app y los servicios Azure no sale a internet:

```
Sin Private Link:
App Service → Internet → Cosmos DB endpoint público
(tráfico cifrado con TLS, pero sale a internet)

Con Private Link:
App Service → VNet → Private Endpoint → Cosmos DB
(tráfico cifrado con TLS Y dentro de la red privada de Azure)
```

```bash
# Crear Private Endpoint para Cosmos DB
az network private-endpoint create \
  --name pe-cosmos-ventas \
  --resource-group rg-ventas-prod \
  --vnet-name vnet-prod --subnet subnet-endpoints \
  --private-connection-resource-id "/subscriptions/<id>/.../cosmosDBAccounts/cosmos-ventas-prod" \
  --group-ids Sql \
  --connection-name conn-cosmos-ventas

# Desactivar acceso público a Cosmos DB
az cosmosdb update --name cosmos-ventas-prod -g mi-rg --enable-public-network false
```

## Slide 11 — Data Classification: identificar datos sensibles

Azure SQL tiene clasificación de datos integrada:

```sql
-- Clasificar una columna como dato sensible
ADD SENSITIVITY CLASSIFICATION TO dbo.Clientes.Email
WITH (LABEL = 'Confidential', INFORMATION_TYPE = 'Contact Info');

ADD SENSITIVITY CLASSIFICATION TO dbo.Clientes.NumeroTarjeta
WITH (LABEL = 'Highly Confidential', INFORMATION_TYPE = 'Financial');

-- Ver clasificaciones
SELECT * FROM sys.sensitivity_classifications;
```

**Azure también puede descubrir automáticamente** columnas con datos sensibles:
Portal → SQL Database → Data Discovery & Classification → muestra recomendaciones automáticas de clasificación.

**¿Para qué?** Auditoría (saber quién accede a datos sensibles), compliance (GDPR requiere conocer dónde están los datos personales), y políticas de acceso (limitar quién puede ver columnas sensibles).

## Slide 12 — Proteger datos en la aplicación

Más allá del cifrado de infraestructura, proteged datos en vuestro código:

```csharp
// Data Protection API (.NET) para cifrar datos en la app
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(new Uri("https://stventasprod.blob.core.windows.net/keys/dataprotection"))
    .ProtectKeysWithAzureKeyVault(
        new Uri("https://kv-ventas-prod.vault.azure.net/keys/dataprotection-key"),
        new DefaultAzureCredential());

// Cifrar un dato
var protector = app.Services.GetRequiredService<IDataProtectionProvider>()
    .CreateProtector("PII");
var cifrado = protector.Protect("4111-1111-1111-1111");
var original = protector.Unprotect(cifrado);
```

**Casos de uso:** Cifrar PII antes de almacenarla en Cosmos DB (defense in depth: incluso si alguien accede a la DB, los datos PII están cifrados con clave que solo tu app tiene).

## Slide 13 — CORS: proteger contra peticiones no autorizadas

```bash
# Configurar CORS en App Service
az webapp cors add --name api-ventas -g mi-rg \
  --allowed-origins "https://app-ventas.azurewebsites.net" "http://localhost:3000"

# En Azure Functions
az functionapp cors add --name func-ventas -g mi-rg \
  --allowed-origins "https://app-ventas.azurewebsites.net"
```

```csharp
// En código ASP.NET Core (más control)
builder.Services.AddCors(options =>
{
    options.AddPolicy("produccion", policy =>
    {
        policy.WithOrigins("https://app-ventas.azurewebsites.net")
              .AllowAnyMethod()
              .AllowAnyHeader()
              .AllowCredentials();
    });
});
app.UseCors("produccion");
```

**NUNCA `AllowAnyOrigin()` con `AllowCredentials()`** en producción. Es una vulnerabilidad que permite a cualquier sitio hacer peticiones autenticadas a tu API.

## Slide 15 — Dynamic Data Masking en Azure SQL

Ocultar datos sensibles para usuarios no privilegiados:

```sql
-- Máscara en email: pe***@empresa.com
ALTER TABLE Clientes ALTER COLUMN Email ADD MASKED WITH (FUNCTION = 'email()');

-- Máscara parcial: XXXX-XXXX-XXXX-1234
ALTER TABLE Clientes ALTER COLUMN NumeroTarjeta ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');

-- Máscara total: 0
ALTER TABLE Clientes ALTER COLUMN Salario ADD MASKED WITH (FUNCTION = 'default()');

-- Dar permiso para ver datos sin máscara
GRANT UNMASK TO [pedro@empresa.com];
```

Los usuarios con permiso UNMASK ven los datos reales. El resto ve las máscaras. Sin cambiar código de la app — es transparente a nivel de SQL Server.

## Slide 16 — Row-Level Security en Azure SQL

Restringir qué filas puede ver cada usuario:

```sql
-- Función de filtro: cada usuario solo ve los pedidos de su región
CREATE FUNCTION dbo.fn_SecurityPredicate(@Region nvarchar(50))
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS result WHERE @Region = SESSION_CONTEXT(N'UserRegion');

-- Aplicar el filtro a la tabla
CREATE SECURITY POLICY RegionFilter
ADD FILTER PREDICATE dbo.fn_SecurityPredicate(Region) ON dbo.Pedidos
WITH (STATE = ON);

-- En la app, al conectar, establecer la región del usuario
-- EXEC sp_set_session_context @key = N'UserRegion', @value = 'Europa';
```

Pedro de Europa solo ve pedidos de Europa. María de Asia solo ve pedidos de Asia. Sin filtros WHERE en la app — SQL Server lo hace automáticamente.

## Slide 17 — Proteger datos en Cosmos DB: field-level encryption

```csharp
// Cifrar campos sensibles antes de guardar en Cosmos
var protector = _dataProtection.CreateProtector("PII-fields");

var documento = new Cliente
{
    Id = "CLI-001",
    Nombre = "Pedro García",  // No cifrado (necesario para display)
    Email = protector.Protect("pedro@empresa.com"),  // Cifrado
    Telefono = protector.Protect("+34666123456"),     // Cifrado
    NumeroTarjeta = protector.Protect("4111111111111111")  // Cifrado
};

await container.CreateItemAsync(documento);

// Al leer: descifrar
var cliente = await container.ReadItemAsync<Cliente>("CLI-001", partition);
var emailReal = protector.Unprotect(cliente.Resource.Email);
```

Defense in depth: incluso si alguien accede a Cosmos DB directamente (MI comprometida, export), los campos PII están cifrados con una clave que solo vuestra app tiene (en Key Vault).

## Slide 19 — Confidential Computing: cifrado en uso

Hasta ahora hablamos de cifrado at-rest e in-transit. Falta el tercero: **in-use**:

```
3 estados de los datos:
├── At rest: en disco/storage (Azure cifra siempre)
├── In transit: viajando por red (TLS)
└── In use: en memoria RAM mientras se procesan ⚠️
              └── Aquí estaba la brecha hasta ahora
```

**Confidential VMs (AMD SEV-SNP / Intel TDX):**
```bash
# Crear Confidential VM
az vm create \
  --resource-group rg-confidential \
  --name vm-secure \
  --size Standard_DC4as_v5 \
  --image Ubuntu2204 \
  --security-type ConfidentialVM \
  --enable-secure-boot true \
  --enable-vtpm true \
  --os-disk-security-encryption-type DiskWithVMGuestState \
  --confidential-compute-encryption-type DiskWithVMGuestState
```

**Características:**
```
Confidential VMs:
├── Memory encrypted con keys hardware
├── Microsoft NO puede ver memory contents
├── Hypervisor itself can't access guest memory
├── Attestation: prove it's actually confidential
└── Use cases:
    ├── Process highly sensitive data
    ├── Multi-party computation
    ├── Bank fraud detection con shared models
    └── Healthcare research con PHI
```

**Confidential Containers (AKS):**
```yaml
# Pod en confidential containers
apiVersion: v1
kind: Pod
metadata:
  name: confidential-app
  annotations:
    io.katacontainers.config.hypervisor.path: /usr/bin/qemu-system-x86_64
spec:
  runtimeClassName: kata-cc-isolation  # Confidential runtime
  containers:
  - name: secure-app
    image: mi-empresa/secure-processor:1.0
    resources:
      limits:
        kata.peerpods.io/vm: "1"
    env:
    - name: ATTESTATION_REQUIRED
      value: "true"
```

**Attestation (probar que es confidential):**
```csharp
// Tu app verifica que está corriendo en confidential VM
var attestationClient = new AttestationClient(
    new Uri("https://sharedweu.weu.attest.azure.net"),
    new DefaultAzureCredential());

var attestationResult = await attestationClient.AttestSgxEnclaveAsync(
    quote: GetEnclaveQuote(),
    runtimeData: new AttestationData(BinaryData.FromString("my-data")));

// Si attestation falla → no estamos en confidential, abort
if (!attestationResult.Value.IsValidated)
{
    throw new SecurityException("Not running in confidential environment");
}
```

**Comparativa:**

| | Standard VM | Confidential VM |
|---|:---:|:---:|
| Coste | 1.0x | 1.5-2.0x |
| Memory encryption | ❌ | ✅ |
| Microsoft access | Possible (logged) | Impossible |
| Hypervisor access | Yes | Blocked |
| Hardware required | Any | AMD EPYC / Intel Xeon nuevo |
| Attestation | No | Yes |
| Use case | 99% workloads | Datos ultra-sensitive |

**Real-world: salud sector**
- Hospital procesa imágenes médicas con AI en cloud
- Confidential VMs garantizan que ni Microsoft ve los datos
- Compliance HIPAA + paciente confidence
- Coste extra justificado por privacy guarantees

## Slide 20 — Customer Lockbox: control de acceso de Microsoft

Para datos críticos, control granular de cuándo Microsoft puede acceder:

```
Sin Customer Lockbox:
└── Microsoft Engineer accede a tu data para troubleshoot
    └── Logged but already happened

Con Customer Lockbox:
└── Engineer requires YOUR explicit approval
    ├── You receive notification
    ├── You see: who, why, what scope, duration
    ├── You APPROVE or DENY
    ├── Auto-revoke after duration
    └── Full audit trail
```

**Habilitar:**
```bash
# Requires Premier/Unified Support contract
# Habilitar en subscription level
az feature register --name lockbox \
  --namespace Microsoft.Authorization

# Configurar approvers (recomendado: 2+ personas)
az role assignment create \
  --role "Customer Lockbox Approver" \
  --assignee security@empresa.com \
  --scope /subscriptions/<sub-id>

# Email notifications
az lockbox notification email add \
  --subscription <sub-id> \
  --email-address security-team@empresa.com
```

**Servicios cubiertos (2026):**
```
✅ Virtual Machines
✅ Azure SQL Database / Managed Instance
✅ Azure Storage (blob, files)
✅ App Service / Web Apps
✅ Azure Kubernetes Service
✅ Azure Synapse Analytics
⚠️ Key Vault (limited scope)
✅ Azure Functions
```

**Workflow real:**
```
T+0:  Subes ticket Premier por SQL DB issue
T+0h: MS engineer assigned
T+2h: Engineer determines necesita ver data → triggers Lockbox

Tu equipo recibe:
┌─────────────────────────────────────────────────────────┐
│ 🔒 Customer Lockbox Approval Request                    │
│                                                         │
│ Engineer: john.doe@microsoft.com                        │
│ Service: Azure SQL Database                             │
│ Resource: prod-customers-db                             │
│ Reason: "Investigating slow query in ticket #12345"    │

Tú APRUEBAS:
├── Engineer gets access for 4 hours
├── All actions logged
├── Auto-revoke at 4h
└── You receive activity report

Tú DENIEGAS:
├── Engineer notified

└── Possibly slower resolution but more control
```

**Compliance value:**
- HIPAA: required en muchos cases ("audit trail of MS access")

**Costs:**

## Slide 22 — mTLS termination en Application Gateway

App Gateway WAF + mTLS para zero-trust API access:

```
Architecture:

External Client (mTLS cert)
    │
    │ HTTPS + Client Cert
```

```csharp
public IActionResult SecureEndpoint()
{
```

## Slide 24 — Dynamic Data Masking deep-dive

DDM en Azure SQL: cifrado lógico para usuarios sin permisos:

```sql
-- Enable masking on sensitive columns
CREATE TABLE Customers (
    Id INT PRIMARY KEY,
    Name NVARCHAR(100),
    Email NVARCHAR(100) MASKED WITH (FUNCTION = 'email()'),
    SSN VARCHAR(11) MASKED WITH (FUNCTION = 'partial(0,"XXX-XX-",4)'),
    CreditCard VARCHAR(19) MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)'),
    Phone VARCHAR(15) MASKED WITH (FUNCTION = 'default()'),
    Salary DECIMAL(10,2) MASKED WITH (FUNCTION = 'random(50000, 80000)')
);

-- DDM functions:
-- default():       0 / xxxx
-- email():         aXXX@XXXX.com
-- random(low,hi):  random number in range
-- partial(p,s,t):  custom mask (prefix, suffix, total)

-- Insertar datos
INSERT INTO Customers VALUES (1, 'Pedro García', 'pedro@empresa.com', 
    '123-45-6789', '4532-1234-5678-9012', '+34666777888', 65000);

-- Query as admin (has UNMASK permission)
SELECT * FROM Customers;
-- Email: pedro@empresa.com  (unmasked)
-- SSN: 123-45-6789

-- Query as regular user (NO UNMASK)
SELECT * FROM Customers;
-- Email: pXXX@XXXX.com
-- SSN: XXX-XX-6789
-- CreditCard: XXXX-XXXX-XXXX-9012
```

**Granular permissions:**
```sql
-- Grant unmask para data analyst
GRANT UNMASK ON Customers TO data_analyst_role;

-- Solo unmask de email para reporting
GRANT UNMASK ON Customers(Email) TO reporting_role;

-- Revoke
REVOKE UNMASK ON Customers FROM marketing_role;
```

**Trade-offs:**
- ✅ Easy to implement (column-level)
- ✅ No app code changes
- ✅ Compliance-friendly (PII protection by default)
- ❌ NOT cryptographic (DBA con SQL access can bypass)
- ❌ User with WHERE clause sobre masked column ve fragments (info leakage)

**Anti-pattern:**
```sql
-- User without UNMASK queries:
SELECT COUNT(*) FROM Customers WHERE SSN = '123-45-6789';
-- Returns 1 → user knows the SSN exists
-- Attack: brute force iteración

-- Solution: combine DDM con RLS para evitar
```

**Usar con RLS para defense in depth:**
```sql
-- DDM: enmascara columnas
-- RLS: filtra rows visibles
-- Together: user solo ve "their" rows + masked columns

CREATE FUNCTION dbo.fn_RowFilter(@TenantId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS Result
       WHERE @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT);

CREATE SECURITY POLICY dbo.TenantPolicy
ADD FILTER PREDICATE dbo.fn_RowFilter(TenantId) ON dbo.Customers,
ADD BLOCK PREDICATE dbo.fn_RowFilter(TenantId) ON dbo.Customers
WITH (STATE = ON);
```

## Slide 25 — Row-Level Security: filtros transparentes

RLS en Azure SQL — filtra rows automáticamente sin cambiar queries:

```sql
-- Schema multi-tenant clásico
CREATE TABLE Orders (
    Id INT PRIMARY KEY,
    TenantId INT NOT NULL,
    CustomerName NVARCHAR(100),
    Amount DECIMAL(10,2),
    OrderDate DATETIME
);

-- Filter function: returns 1 if row is visible
CREATE FUNCTION dbo.fn_TenantFilter(@TenantId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
WHERE 
    @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT)
    OR IS_MEMBER('SuperAdmin') = 1;  -- Admins see all

-- Security policy
CREATE SECURITY POLICY OrderTenantPolicy
ADD FILTER PREDICATE dbo.fn_TenantFilter(TenantId) ON dbo.Orders,
ADD BLOCK PREDICATE dbo.fn_TenantFilter(TenantId) ON dbo.Orders 
                                                   AFTER INSERT,
ADD BLOCK PREDICATE dbo.fn_TenantFilter(TenantId) ON dbo.Orders 
                                                   AFTER UPDATE
WITH (STATE = ON);
```

**Configurar SESSION_CONTEXT desde .NET:**
```csharp
public class TenantAwareDbContext : DbContext
{
    private readonly ICurrentUserService _currentUser;
    
    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        await SetTenantContextAsync();
        return await base.SaveChangesAsync(ct);
    }
    
    private async Task SetTenantContextAsync()
    {
        await Database.ExecuteSqlRawAsync(
            "EXEC sp_set_session_context @key = N'TenantId', @value = {0}",
            _currentUser.TenantId);
    }
    
    // Override Query methods too
    public override IQueryable<TEntity> Set<TEntity>()
    {
        SetTenantContextAsync().GetAwaiter().GetResult();
        return base.Set<TEntity>();
    }
}
```

**Patterns avanzados:**

```sql
-- Pattern 1: Multi-attribute filter (TenantId + Region)
CREATE FUNCTION dbo.fn_AccessFilter(@TenantId INT, @Region NVARCHAR(10))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
WHERE 
    @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS INT)
    AND (@Region = CAST(SESSION_CONTEXT(N'UserRegion') AS NVARCHAR(10))
         OR @Region = 'GLOBAL'
         OR IS_MEMBER('GlobalReader') = 1);

-- Pattern 2: Time-based access (data only accessible after grace period)
CREATE FUNCTION dbo.fn_TimeFilter(@CreatedDate DATETIME)
RETURNS TABLE  
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
WHERE 
    @CreatedDate < DATEADD(MINUTE, -5, GETUTCDATE())  -- Hide newest rows
    OR IS_MEMBER('RealtimeAccess') = 1;

-- Pattern 3: Hierarchy-based (manager sees own + reports)
CREATE FUNCTION dbo.fn_HierarchyFilter(@OwnerId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
FROM dbo.UserHierarchy h
WHERE 
    h.UserId = CAST(SESSION_CONTEXT(N'UserId') AS INT)
    AND (@OwnerId = h.UserId 
         OR @OwnerId IN (SELECT ChildUserId FROM h.Subordinates));
```

**Performance tips:**
- Filter function debe ser **inline TVF**, NOT scalar
- Use indexes on filter columns (TenantId)
- BLOCK predicates can affect insert performance
- Test queries con execution plans

**Audit:**
```sql

-- Disable for emergency (admin only)
ALTER SECURITY POLICY OrderTenantPolicy WITH (STATE = OFF);
-- ⚠️ Use with caution - removes all filtering
```

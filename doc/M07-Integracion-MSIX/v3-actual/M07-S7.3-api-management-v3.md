## Slide 2 — Qué problema resuelve API Management
Tenéis múltiples APIs: la Web App en App Service, las Functions HTTP, quizá algún servicio legacy. Cada una con su propia URL, su propia autenticación, su propio formato de errores.

API Management (APIM) es un gateway que pone orden: una URL de entrada, autenticación centralizada, rate limiting, versionado, transformaciones, analytics. Los clientes (frontend, apps móviles, partners) hablan con APIM. APIM habla con vuestros backends.

```
Clientes → APIM (apim-ventas.azure-api.net)
              ├─ /api/v1/productos → App Service (api-ventas)
              ├─ /api/v1/pedidos   → Azure Functions (func-pedidos)
              ├─ /api/v1/facturas  → Legacy API (on-premises)
              └─ /api/v2/productos → App Service v2 (api-ventas-v2)
```

## Slide 5 — Policies: el poder de APIM

Las policies son reglas que se ejecutan en cada petición. Son XML (o C# expressions):

```xml
<policies>
  <inbound>
    <!-- Rate limiting: max 100 calls/min por subscription key -->
    <rate-limit calls="100" renewal-period="60" />
    
    <!-- CORS -->
    <cors allow-credentials="true">
      <allowed-origins><origin>https://app-ventas.azurewebsites.net</origin></allowed-origins>
      <allowed-methods><method>*</method></allowed-methods>
      <allowed-headers><header>*</header></allowed-headers>
    </cors>
    
    <!-- Validar JWT token -->
    <validate-jwt header-name="Authorization" require-scheme="Bearer">
      <openid-config url="https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration" />
      <required-claims>
        <claim name="aud" match="all"><value>{client-id}</value></claim>
      </required-claims>
    </validate-jwt>
    
    <!-- Añadir header al backend -->
    <set-header name="X-Forwarded-For" exists-action="override">
      <value>@(context.Request.IpAddress)</value>
    </set-header>
  </inbound>
  
  <backend>
    <forward-request />
  </backend>
  
  <outbound>
    <!-- Cachear respuestas 5 minutos -->
    <cache-store duration="300" />
    
    <!-- Eliminar headers internos -->
    <set-header name="X-Powered-By" exists-action="delete" />
  </outbound>
  
  <on-error>
    <return-response>
      <set-status code="500" reason="Internal Error" />
      <set-body>{"error": "Error interno del gateway"}</set-body>
    </return-response>
  </on-error>
</policies>
```

## Slide 6 — Policies más útiles

| Policy | Para qué |
|--------|----------|
| `rate-limit` | Limitar llamadas por tiempo |
| `quota` | Limitar llamadas por período (diario/mensual) |
| `validate-jwt` | Validar token OAuth2 |
| `ip-filter` | Whitelist/blacklist de IPs |
| `cache-lookup` / `cache-store` | Cachear respuestas |
| `set-header` / `remove-header` | Manipular headers |
| `rewrite-uri` | Cambiar la URL antes de enviar al backend |
| `set-body` | Transformar el body (request o response) |
| `log-to-eventhub` | Enviar logs a Event Hub |
| `mock-response` | Devolver respuesta mock (sin backend) |
| `retry` | Reintentar si el backend falla |
| `send-request` | Llamar a otro servicio dentro de la policy |

## Slide 7 — Versionado de APIs

```bash
# Crear versión set
az apim api versionset create \
  --resource-group rg-ventas-prod \
  --service-name apim-ventas-prod \
  --version-set-id "productos-versions" \
  --display-name "Productos API Versions" \
  --versioning-scheme "Segment"  # /v1/productos, /v2/productos

# Crear v1
az apim api create --service-name apim-ventas-prod -g rg-ventas-prod \
  --api-id "productos-v1" --path "v1/productos" \
  --display-name "Productos v1" \
  --service-url "https://api-ventas-v1.azurewebsites.net/api" \
  --api-version "v1" --api-version-set-id "productos-versions"

# Crear v2
az apim api create --service-name apim-ventas-prod -g rg-ventas-prod \
  --api-id "productos-v2" --path "v2/productos" \
  --display-name "Productos v2" \
  --service-url "https://api-ventas-v2.azurewebsites.net/api" \
  --api-version "v2" --api-version-set-id "productos-versions"
```

**Esquemas de versionado:**
- **Segment:** `/v1/productos` (recomendado, más claro)
- **Query:** `/productos?api-version=v1`
- **Header:** `Api-Version: v1`

## Slide 8 — Subscription Keys: proteger APIs

APIM usa subscription keys para controlar acceso:

```bash
# Crear producto (agrupación de APIs)
az apim product create --service-name apim-ventas-prod -g rg-ventas-prod \
  --product-id "standard" --display-name "Standard Access" \
  --subscription-required true --approval-required false

# Crear suscripción
az apim subscription create --service-name apim-ventas-prod -g rg-ventas-prod \
  --subscription-id "sub-frontend" --display-name "Frontend App" \
  --product-id "standard" --state active
```

**Los clientes envían la key en un header:**
```
GET https://apim-ventas.azure-api.net/v1/productos
Ocp-Apim-Subscription-Key: abc123def456
```

**Subscription keys + OAuth2:** Usad ambos. La subscription key identifica LA APP. El token OAuth2 identifica AL USUARIO. APIM valida ambos.

## Slide 9 — Rate Limiting y Quotas

```xml
<!-- Rate limit: 100 llamadas por minuto por subscription key -->
<rate-limit-by-key calls="100" renewal-period="60" 
  counter-key="@(context.Subscription?.Key ?? context.Request.IpAddress)" />

<!-- Quota: 10.000 llamadas por día por subscription key -->
<quota-by-key calls="10000" renewal-period="86400" 
  counter-key="@(context.Subscription?.Key ?? "anonymous")" />

<!-- Rate limit diferente para usuarios premium -->
<choose>
  <when condition="@(context.Request.Headers.GetValueOrDefault("X-User-Tier") == "premium")">
    <rate-limit calls="1000" renewal-period="60" />
  </when>
  <otherwise>
    <rate-limit calls="100" renewal-period="60" />
  </otherwise>
</choose>
```

**Cuando se excede el rate limit:** APIM devuelve `429 Too Many Requests` con un header `Retry-After` indicando cuándo reintentar.

## Slide 10 — Caching en APIM

```xml
<!-- Buscar en cache -->
<inbound>
  <cache-lookup vary-by-developer="false" vary-by-developer-groups="false" 
    downstream-caching-type="none">
    <vary-by-query-parameter>categoria</vary-by-query-parameter>
  </cache-lookup>
</inbound>

<!-- Guardar en cache (5 minutos) -->
<outbound>
  <cache-store duration="300" />
</outbound>
```

**Resultado:** La primera petición a `GET /productos?categoria=electronica` va al backend. Las siguientes 5 minutos se sirven desde la cache de APIM. El backend no recibe la petición.

Ideal para endpoints que no cambian frecuentemente (catálogos, configuración, listas de referencia).

## Slide 11 — Transformaciones de request/response

```xml
<!-- Transformar request antes de enviar al backend -->
<inbound>
  <!-- Cambiar la URL -->
  <rewrite-uri template="/api/v2/products" />
  
  <!-- Añadir header de autenticación para el backend -->
  <set-header name="Authorization" exists-action="override">
    <value>@("Bearer " + context.Variables["backend-token"])</value>
  </set-header>
</inbound>

<!-- Transformar response antes de devolver al cliente -->
<outbound>
  <!-- Quitar campos internos del response -->
  <set-body>@{
    var body = context.Response.Body.As<JObject>();
    body.Remove("internalId");
    body.Remove("debugInfo");
    return body.ToString();
  }</set-body>
</outbound>
```

## Slide 16 — Cuándo usar APIM y cuándo no

**Usa APIM cuando:**
- Tenéis múltiples APIs y queréis una URL de entrada única
- Necesitáis rate limiting, caching, o transformaciones
- Exponéis APIs a terceros (partners, clientes)
- Necesitáis versionado centralizado
- Queréis analytics de uso de APIs

**NO uses APIM cuando:**
- Solo tenéis una API simple (el overhead no se justifica)
- No exponéis APIs externamente
- El tráfico es exclusivamente interno (service-to-service)
- El presupuesto no lo permite (tiers no-Consumption cuestan €€)

## Slide 17 — APIM: backend con múltiples servicios (load balancing)

```xml
<backend>
  <!-- Load balancing entre dos backends -->
  <set-backend-service base-url="@{
    var random = new Random();
    return random.Next(2) == 0 
      ? "https://api-ventas-1.azurewebsites.net"
      : "https://api-ventas-2.azurewebsites.net";
  }" />
  <forward-request />
</backend>
```

Útil para canary deployments: enviar un porcentaje del tráfico al nuevo backend. O para distribuir carga entre múltiples instancias.

## Slide 18 — APIM: circuit breaker con retry

```xml
<backend>
  <retry condition="@(context.Response.StatusCode >= 500)" count="3" interval="1" 
         max-interval="10" delta="2" first-fast-retry="true">
    <forward-request />
  </retry>
</backend>
```

Si el backend responde 5xx, APIM reintenta automáticamente hasta 3 veces con backoff exponencial. El cliente no sabe que hubo reintentos — solo ve la respuesta final.

## Slide 19 — APIM: respuestas custom para errores

```xml
<on-error>
  <choose>
    <when condition="@(context.Response.StatusCode == 429)">
      <return-response>
        <set-status code="429" reason="Rate Limit Exceeded" />
        <set-header name="Retry-After"><value>60</value></set-header>
        <set-body>{"error":"Has superado el límite de peticiones. Espera 60 segundos."}</set-body>
      </return-response>
    </when>
    <when condition="@(context.Response.StatusCode >= 500)">
      <return-response>
        <set-status code="502" reason="Backend Error" />
        <set-body>{"error":"Servicio temporalmente no disponible. Reintentar en unos minutos."}</set-body>
      </return-response>
    </when>
  </choose>
</on-error>
```

## Slide 23 — APIM AI Gateway: Token tracking y quotas

Configurar token tracking per subscription/user:

```xml
<!-- Inbound policy: track tokens -->
<policies>
    <inbound>
        <base />
        
        <!-- Authenticate -->
        <validate-jwt header-name="Authorization" failed-validation-httpcode="401">
            <openid-config url="https://login.microsoftonline.com/<tenant>/.well-known/openid-configuration" />
            <required-claims>
                <claim name="aud" match="any">
                    <value>api://your-app-id</value>
                </claim>
            </required-claims>
        </validate-jwt>
        
        <!-- Get user from token -->
        <set-variable name="userId" value="@(context.User.Id)" />
        
        <!-- Token quota: limit per user per day -->
        <azure-openai-token-limit
            counter-key="@(context.Variables.GetValueOrDefault<string>("userId"))"
            tokens-per-minute="1000"
            estimate-prompt-tokens="false"
            tokens-consumed-header-name="x-tokens-consumed"
            remaining-tokens-header-name="x-tokens-remaining"
            tokens-quota-period="Hourly" />
    </inbound>
    
    <backend>
        <base />
    </backend>
    
    <outbound>
        <base />
        
        <!-- Emit metrics with token counts -->
        <azure-openai-emit-token-metric
            namespace="OpenAI"
            metric-name="TokensConsumed">
            <dimension name="UserId" value="@(context.Variables.GetValueOrDefault<string>("userId"))" />
            <dimension name="Model" value="@(context.Response.Headers.GetValueOrDefault("openai-model", ""))" />
            <dimension name="ApiName" value="@(context.Api.Name)" />
        </azure-openai-emit-token-metric>
    </outbound>
</policies>
```

**Resultado en Azure Monitor:**
```kusto
// Tokens consumed by user
customMetrics
| where name == "TokensConsumed"
| where timestamp > ago(7d)
| summarize TotalTokens = sum(value) 
  by UserId = tostring(customDimensions.UserId)
| order by TotalTokens desc
| top 20 by TotalTokens

// Cost per user (assuming €0.005/1K input + €0.015/1K output GPT-4o)
customMetrics
| where name == "TokensConsumed"
| where timestamp > ago(30d)
| extend Cost = (value / 1000) * 0.01  // simplified
| summarize TotalCost = sum(Cost) 
  by UserId = tostring(customDimensions.UserId)
| top 10 by TotalCost desc
```

**Quota enforcement:**
```
User exceeded 1000 tokens/min:
├── APIM returns 429 Too Many Requests
├── Header: x-tokens-remaining: 0
├── Header: x-retry-after: 60
└── Client should backoff y retry

Per-customer quotas (B2B):
├── Customer A: 100K tokens/month (premium)
├── Customer B: 10K tokens/month (basic)
├── Customer C: unlimited (enterprise)
└── Configured via subscription products
```

## Slide 24 — APIM Load Balancing for OpenAI

Distribute traffic intelligently across multiple OpenAI deployments:

```xml
<!-- Backend pool con multiple OpenAI deployments -->
<policies>
    <inbound>
        <base />
        
        <!-- Choose backend based on load balancing strategy -->
        <set-backend-service backend-id="openai-pool" />
        
        <!-- Or manual: weighted random -->
        <choose>
            <when condition="@(new Random().Next(0,100) < 70)">
                <set-backend-service base-url="https://openai-prod-weu.openai.azure.com" />
            </when>
            <when condition="@(new Random().Next(0,100) < 90)">
                <set-backend-service base-url="https://openai-prod-neu.openai.azure.com" />
            </when>
            <otherwise>
                <set-backend-service base-url="https://openai-prod-eus.openai.azure.com" />
            </otherwise>
        </choose>
    </inbound>
</policies>
```

**Backend pool con health checks:**
```bash
# Crear backend pool con multiple OpenAI deployments

  --service-name apim-ai-prod \
  --backend-id openai-weu \

  --protocol http

az apim backend create \
  --resource-group rg-ai \
  --service-name apim-ai-prod \
  --backend-id openai-neu \
  --url "https://openai-prod-neu.openai.azure.com" \
  --protocol http

# Pool: priority + weight based load balancing
cat > pool.json << EOF
{
  "type": "Pool",
```

## Slide 25 — Semantic caching para LLMs

Cache responses por similarity semántica — not exact match:

```
Without semantic cache:
├── User1: "What's the capital of France?"
├── User2: "Tell me the capital city of France"
└── 2 OpenAI calls (same answer, paid twice)

With semantic cache:
├── User1: "What's the capital of France?" → call OpenAI, cache
├── User2: "Tell me the capital city of France"
│   └── Embedding similarity > 0.95 → cache hit ✅
└── 1 OpenAI call, 1 cached response
```

**Habilitar semantic caching:**
```xml
<!-- Inbound policy -->
<policies>
    <inbound>
        <base />
        
        <!-- Lookup en semantic cache -->
        <azure-openai-semantic-cache-lookup 
            score-threshold="0.05"
            embeddings-backend-id="embeddings-backend"
            embeddings-backend-auth="system-assigned"
            ignore-system-messages="true"
            max-message-count="10">
            <vary-by>@(context.Subscription.Id)</vary-by>
        </azure-openai-semantic-cache-lookup>
    </inbound>
    
    <backend>
        <base />
    </backend>
    
    <outbound>
        <base />
        
        <!-- Store en semantic cache si fue miss -->
        <azure-openai-semantic-cache-store duration="3600" />
    </outbound>
</policies>
```

**Score threshold tuning:**
```
score-threshold = "cosine distance threshold for cache hit"

0.01: Very strict (basically only exact matches)
├── Cache hit rate: 5-10%
├── False positives: very low
└── Use case: facts that must be precise

0.05: Recommended default
├── Cache hit rate: 20-40%
├── False positives: low
└── Use case: most chat scenarios

0.10: Moderate
├── Cache hit rate: 40-60%
├── Some semantic drift
└── Use case: brainstorming, FAQs

0.20: Aggressive  
├── Cache hit rate: 60-80%
├── Higher false positive risk
└── Use case: cost-sensitive scenarios
```

**Vary by subscription/user:**
```xml
<!-- Cache different per consumer (privacy) -->
<vary-by>@(context.Subscription.Id)</vary-by>

<!-- Or per user (more privacy) -->
<vary-by>@(context.User.Id)</vary-by>

<!-- Or shared cache (más cost savings, less privacy) -->
<!-- omit vary-by -->
```

## Slide 26 — Content Safety integration

APIM puede filter prompts/responses con Azure AI Content Safety:

```xml
<!-- Inbound: filter user prompts -->
<policies>
    <inbound>
        <base />
        
        <!-- Send prompt to Content Safety API -->
        <send-request mode="new" 
                      response-variable-name="contentSafetyResponse" 
                      timeout="20" 
                      ignore-error="false">
            <set-url>https://content-safety-prod.cognitiveservices.azure.com/contentsafety/text:analyze?api-version=2024-09-01</set-url>
            <set-method>POST</set-method>
            <set-header name="Ocp-Apim-Subscription-Key" exists-action="override">
                <value>{{content-safety-key}}</value>
            </set-header>
            <set-header name="Content-Type" exists-action="override">
                <value>application/json</value>
            </set-header>
            <set-body>@{
                var body = context.Request.Body.As<JObject>(true);
                var userMessage = body["messages"]
                    .Where(m => m["role"].ToString() == "user")
                    .LastOrDefault()?["content"]?.ToString() ?? "";
                
                return new JObject
                {
                    ["text"] = userMessage,
                    ["categories"] = new JArray("Hate", "SelfHarm", "Sexual", "Violence"),
                    ["outputType"] = "FourSeverityLevels"
                }.ToString();
            }</set-body>
        </send-request>
        
        <!-- Block if any category > severity 4 -->
        <choose>
            <when condition="@{
                var response = ((IResponse)context.Variables["contentSafetyResponse"]).Body.As<JObject>();
                var categories = response["categoriesAnalysis"] as JArray;
                return categories.Any(c => (int)c["severity"] >= 4);
            }">
                <return-response>
                    <set-status code="400" reason="Content blocked" />
                    <set-body>@{
                        return new JObject 
                        { 
                            ["error"] = "Content blocked due to safety policy",
                            ["details"] = "Your prompt contains inappropriate content"
                        }.ToString();
                    }</set-body>
                </return-response>
            </when>
        </choose>
    </inbound>
    
    <outbound>
        <base />
        
        <!-- Optionally filter response too -->
        <!-- Similar logic but on context.Response.Body -->
    </outbound>
</policies>
```

**Severity levels (Content Safety API):**
```
Level 0: Safe
Level 2: Low (mild reference)
Level 4: Medium (clear concerning content)
Level 6: High (explicit harmful content)
```

**Categories detected:**
```
Hate:      Discrimination, hate speech
SelfHarm:  Self-harm, suicide content
Sexual:    Sexual content
Violence:  Violence, weapons
```

**Configurable thresholds per use case:**
```
Chatbot for customers (strict):
├── Block at severity 2+
└── No tolerance for offensive content

Internal coding assistant (lenient):
├── Block at severity 6 only
└── Allow technical discussions

Education platform (very strict):
├── Block at severity 2+
├── Plus: PII detection, prompt injection
└── Plus: protected content scanner
```

**Prompt Shields (newer 2024):**
```xml
<!-- Detect prompt injection attempts -->
<send-request mode="new" 
              response-variable-name="promptShieldResponse" 
              ignore-error="false">
    <set-url>https://content-safety.cognitiveservices.azure.com/contentsafety/text:shieldPrompt?api-version=2024-09-01</set-url>

        return new JObject
```

```graphql
type Product {
```

```
✅ Schema validation

✅ WebSocket support for subscriptions
✅ Schema federation (combine multiple GraphQL APIs)
```

**Field-level authorization:**
```xml
<!-- Different policies per query/mutation -->
<inbound>
    <validate-graphql-request error-variable-name="graphqlError">

            <rule action="reject">
                <path>/Mutation/*</path>

                    <claim name="role" value="admin" />
                </not>
            </rule>
            
            <!-- Hide internal fields from non-admin -->
            <rule action="redact">
                <path>/Product/internalNotes</path>
                <not>
                    <claim name="role" value="admin" />
                </not>
            </rule>
        </authorize>
    </validate-graphql-request>
</inbound>
```

**Query complexity limiting (DDoS protection):**
```xml
<!-- Reject queries con too much depth/complexity -->

</validate-graphql-request>
```

**Caching resolvers:**


**Synthetic GraphQL (compose REST APIs):**

**Comparison REST vs GraphQL en APIM:**

| | REST | GraphQL |
|---|:---:|:---:|
| Multiple endpoints | ✅ | One endpoint |
| Over-fetching | Common | Eliminated |
| Under-fetching | Common | Eliminated |
| Caching | Easy (URL) | Complex (field-level) |
| Versioning | URL/header | Schema evolution |
| Tooling | Mature | Improving |
| Best for | Simple CRUD | Complex relationships |

**Cuándo usar GraphQL:**
- ✅ Mobile apps (bandwidth-sensitive)
- ✅ Multiple data sources (federation)
- ✅ Frontend has complex data needs
- ✅ Rapid iteration without backend changes
- ❌ File uploads (REST better)
- ❌ Simple CRUD (overkill)
- ❌ Public APIs (REST more universal)

```
   ├── Each customer = workspace
```

```bash
apiVersion: apps/v1
```

## Slide 31 — Anti-patterns APIM

Errores comunes en producción:

```
❌ ANTI-PATTERN 1: Developer tier in production
   "It's cheaper" → no SLA, single instance
   ✅ Standard or Premium for prod

❌ ANTI-PATTERN 2: All APIs en single product
   No granular subscriptions
   ✅ Products by tier/customer

❌ ANTI-PATTERN 3: Hardcoded subscription keys in code
   ✅ Key Vault references

❌ ANTI-PATTERN 4: Sin rate limiting
   APIs vulnerable to DDoS/abuse
   ✅ Per-subscription o per-IP rate limits

❌ ANTI-PATTERN 5: Logging full request/response bodies
   PII exposed in logs, expensive
   ✅ Log only headers + small body samples

❌ ANTI-PATTERN 6: Single backend per API
   No failover or load balancing
   ✅ Backend pools

❌ ANTI-PATTERN 7: Tight coupling con backend
   Same paths, same payloads as backend
   ✅ APIM transforms to abstract backend

❌ ANTI-PATTERN 8: APIM as "just a proxy"
   Not using policies, transformations, etc
   ✅ Use APIM as full API gateway

❌ ANTI-PATTERN 9: Sin VNet integration en prod
   APIs publicly accessible directly
   ✅ Internal VNet mode

❌ ANTI-PATTERN 10: Manual changes en Portal
   Configuration drift, no version control
   ✅ Bicep + GitOps

❌ ANTI-PATTERN 11: Sin caching strategy
   Backend hit on every request
   ✅ Cache appropriate responses

❌ ANTI-PATTERN 12: Sin developer portal
   API consumers can't self-service
   ✅ Use developer portal o equivalent
```

**El más caro:**
```
Cliente con 50 APIs todos en Developer tier "para ahorrar":
├── Cost: €40/mes (cheap)
├── No SLA, single instance
├── Region down → 4 horas downtime
├── Lost revenue: €100K
├── Fix: migrate to Standard
├── New cost: €600/mes (+€560)
├── Annual save: €100K avoided incident
└── ROI: instant
```

**Decision matrix:**

```
¿VNet integration mandatory?
   SÍ → Premium (full) o StandardV2 (limited)
   NO → Any tier

¿Multi-region active-active?
   SÍ → Premium only
   NO → Any tier

¿Compliance requires CMK?
   SÍ → Premium only
   NO → Any tier

¿APIs > 1000 calls/sec?
   SÍ → Premium (4+ units)
   NO → Standard tier OK

¿Dev/Test environment?
   SÍ → Developer (no SLA but full features)
   NO → Real production tier

¿Self-hosted gateway needed?
   SÍ → Premium only
   NO → Any tier
```

**Cost optimization:**
```
Reserved Instances:
├── 1-year commitment: 30% discount
├── 3-year commitment: 50% discount
└── Available for Standard, Premium

Multi-environment savings:
├── Use single APIM with workspaces (instead of N APIMs)
├── Dev/Staging/Prod = workspaces in shared APIM Premium
└── Saves €1000s/mo for big orgs

Auto-scaling:
├── Standard, StandardV2 auto-scale
├── Premium: manual unit allocation (HA improvement)
└── Set min/max units carefully
```

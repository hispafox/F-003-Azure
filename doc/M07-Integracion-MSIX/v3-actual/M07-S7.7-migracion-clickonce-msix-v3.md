## Slide 2 — Estrategia de migración
La migración no tiene que ser big-bang. Podéis hacerla gradual:

**Fase 1 (2 semanas):** Empaquetar la app ACTUAL como MSIX (sin cambiar código). Probar internamente.
**Fase 2 (1 semana):** Distribuir MSIX a un grupo piloto. ClickOnce sigue activo para el resto.
**Fase 3 (2 semanas):** Migrar a todos los usuarios a MSIX. Desactivar ClickOnce.
**Fase 4 (opcional):** Migrar la app a .NET 8 (mejoras de rendimiento, nuevas APIs).

**Duración total estimada:** 4-6 semanas si dedicáis una persona a ello.

## Slide 3 — Pre-requisitos antes de empezar

**Verificar compatibilidad:**
```powershell
# Instalar MSIX Packaging Tool (desde Microsoft Store — gratis)

# Verificar que la app no usa features incompatibles con MSIX:
# ✗ Drivers de kernel
# ✗ Servicios de Windows (se pueden añadir con PSF pero es complejo)
# ✗ COM servers no registrados en manifest
# ✗ Escritura directa en C:\Windows o C:\Program Files

# ✓ Acceso a filesystem del usuario — compatible
```

**Preparar certificado:**
```powershell
# Desarrollo: self-signed

  -CertStoreLocation "Cert:\CurrentUser\My" -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3","2.5.29.19={text}")

# Producción: usar Enterprise CA o comprar a CA pública
```

## Slide 4 — Método 1: MSIX Packaging Tool (sin tocar código)

Para empaquetar la app ClickOnce TAL CUAL como MSIX:

```
1. Instalar MSIX Packaging Tool (Microsoft Store)
2. Abrir → "Application package"
3. Seleccionar el instalador ClickOnce (.application o .exe generado)
4. La herramienta ejecuta el instalador en una VM limpia
5. Captura todos los cambios (archivos, registry)
6. Genera el .msix

Resultado: un .msix que contiene exactamente lo mismo que el ClickOnce
pero en formato MSIX moderno.
```

**Ventaja:** Cero cambios en el código fuente. Funciona con apps .NET Framework.
**Desventaja:** Es una "captura" — si la app tiene dependencias complejas, puede no captarlas todas.

## Slide 5 — Método 2: Windows Application Packaging Project (recomendado)

Añadir un proyecto de empaquetado a la solución existente:

```
1. Visual Studio → Solution → Add New Project
2. "Windows Application Packaging Project"
3. Target: Windows 10 1809+
4. References → Add Reference → seleccionar proyecto WPF/WinForms
5. Set as Startup Project
6. Build → genera .msix
```

**Cambios en la solución:**
```
MiApp.sln
├── MiApp.WPF/            ← Proyecto existente (NO se toca)
│   ├── MainWindow.xaml
│   └── MiApp.WPF.csproj
│
└── MiApp.Package/         ← NUEVO proyecto de empaquetado
    ├── Package.appxmanifest
    ├── Images/
    └── MiApp.Package.wapproj
```

**El proyecto WPF NO cambia.** Solo añadís el wrapper de empaquetado. Podéis seguir publicando con ClickOnce Y con MSIX simultáneamente durante la transición.

## Slide 8 — Migrar la autenticación

Si vuestra app ClickOnce usa autenticación:

**ClickOnce con Forms Auth / Basic Auth:**
→ Migrar a MSAL con Entra ID (submódulo 6.4)

**ClickOnce con Windows Integrated Auth:**
→ Funciona igual en MSIX (no necesita cambios)

**ClickOnce con custom token:**
→ Evaluar migrar a MSAL o mantener (funciona igual en MSIX)

```csharp
// Si migráis a MSAL, el cambio principal:
// ANTES (ClickOnce): custom auth
var token = await _customAuth.LoginAsync(username, password);

// DESPUÉS (MSIX + MSAL): OAuth2 con Entra ID
var result = await _msalApp.AcquireTokenInteractive(scopes).ExecuteAsync();
var token = result.AccessToken;
```

## Slide 9 — Migrar la configuración y datos de usuario

**ClickOnce guarda datos en:**
`%LocalAppData%\Apps\2.0\Data\{hash}\{hash}\{app}.exe_Url_{hash}\Data\`

**MSIX guarda datos en:**
`%LocalAppData%\Packages\{package-family}\LocalState\`

**Para migrar datos del usuario:**
```csharp
public class DataMigrationService
{
    public void MigrateFromClickOnce()
    {
        // Detectar si hay datos de ClickOnce
        var clickOncePath = FindClickOnceDataPath();
        if (clickOncePath == null || !Directory.Exists(clickOncePath))
            return;
        
        // Copiar datos al path de MSIX
        var msixPath = ApplicationData.Current.LocalFolder.Path;
        
        foreach (var file in Directory.GetFiles(clickOncePath))
        {
            var dest = Path.Combine(msixPath, Path.GetFileName(file));
            if (!File.Exists(dest))
                File.Copy(file, dest);
        }
        
        // Marcar migración como completada
        File.WriteAllText(Path.Combine(msixPath, ".migrated"), DateTime.UtcNow.ToString());
    }
}
```

**Ejecutar al primer arranque de la versión MSIX.**

## Slide 12 — PSF: Package Support Framework (para apps problemáticas)

Si la app tiene comportamientos incompatibles con el contenedor MSIX:

```
App escribe en C:\ProgramData\ → MSIX virtualiza → la app no encuentra el archivo
App lee registry HKLM → MSIX virtualiza → claves no visibles
App busca DLLs en PATH global → MSIX no tiene PATH global
```

**PSF (Package Support Framework)** intercepta estas llamadas y las redirige:

```xml
<!-- config.json del PSF -->
{
  "applications": [{
    "id": "VentasDesktop",
    "executable": "MiApp.WPF.exe"
  }],
  "processes": [{
    "executable": "MiApp.WPF.exe",
    "fixups": [{
      "dll": "FileRedirectionFixup.dll",
      "config": {
        "redirectedPaths": {
          "packageRelative": [{ "base": "VFS/Common AppData/MiApp", "patterns": ["*"] }]
        }
      }
    }]
  }]
}
```

**En la mayoría de apps WPF/WinForms modernas, PSF no es necesario.** Solo para apps legacy que escriben en ubicaciones del sistema.

## Slide 14 — Script de migración de datos completo

```csharp
public class ClickOnceMigration
{
    private readonly ILogger _logger;

    public bool NeedsMigration()
    {
        var msixDataPath = ApplicationData.Current.LocalFolder.Path;
        var migrationMarker = Path.Combine(msixDataPath, ".clickonce-migrated");
        return !File.Exists(migrationMarker);
    }

    public async Task MigrateAsync()
    {
        if (!NeedsMigration()) return;

        _logger.LogInformation("Detectada primera ejecución post-migración. Migrando datos...");

        // Buscar datos de ClickOnce
        var clickOncePaths = FindClickOnceDataPaths();
        var msixPath = ApplicationData.Current.LocalFolder.Path;

        foreach (var sourcePath in clickOncePaths)
        {
            _logger.LogInformation("Migrando desde: {Path}", sourcePath);

            // Copiar archivos de configuración
            MigrateFiles(sourcePath, msixPath, "*.config");
            MigrateFiles(sourcePath, msixPath, "*.json");
            MigrateFiles(sourcePath, msixPath, "*.db");
            MigrateFiles(sourcePath, msixPath, "*.xml");

            // Migrar user.config (settings de la app)
            var userConfig = FindUserConfig(sourcePath);
            if (userConfig != null)
                MigrateUserConfig(userConfig, msixPath);
        }

        // Marcar como migrado
        await File.WriteAllTextAsync(
            Path.Combine(msixPath, ".clickonce-migrated"),
            $"Migrated at {DateTime.UtcNow:O}");

        _logger.LogInformation("Migración completada");
    }

    private List<string> FindClickOnceDataPaths()
    {
        var appData = Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData);
        var apps20 = Path.Combine(appData, "Apps", "2.0");

        if (!Directory.Exists(apps20)) return new List<string>();

        return Directory.GetDirectories(apps20, "Data", SearchOption.AllDirectories).ToList();
    }
}
```

## Slide 18 — Rollback plan si la migración falla

Si MSIX tiene problemas y necesitáis volver a ClickOnce:

```
1. Mantener el file share de ClickOnce activo durante al menos 4 semanas
2. Si MSIX falla para un usuario:
   a. Desinstalar MSIX: Remove-AppxPackage ...
   b. Re-instalar ClickOnce desde el file share
   c. Verificar que funciona
   d. Reportar el problema al equipo de desarrollo
3. No eliminar el pipeline de ClickOnce hasta que el 100% esté en MSIX
   y haya pasado al menos 1 semana sin incidencias
```

**La regla:** Nunca queméis el puente de ClickOnce hasta que estéis seguros de que MSIX funciona para todos.

## Slide 19 — Migración a ARM64 + multi-arch builds

Apps modernas necesitan soportar x64 + ARM64 (Surface Pro X, Snapdragon laptops):

```
Architecture support landscape 2026:
├── x64: 80% of Windows installs
├── ARM64: ~15% (creciendo rápido con Snapdragon X / Copilot+ PCs)
├── x86 (32-bit): ~5% (legacy)
└── ARM32: deprecated

Estrategia recomendada: x64 + ARM64 bundle único
```

**Modificar .csproj para multi-arch:**
```xml
<PropertyGroup>
  <OutputType>WinExe</OutputType>
  <TargetFramework>net8.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>
  
  <!-- Multi-platform support -->
  <Platforms>x64;ARM64</Platforms>
  <RuntimeIdentifiers>win-x64;win-arm64</RuntimeIdentifiers>
  
  <!-- Para que single-file funcione cross-arch -->
  <PublishSingleFile>true</PublishSingleFile>
  <SelfContained>true</SelfContained>
  <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
</PropertyGroup>
```

**Build script multi-arch:**
```powershell
# build-multiarch.ps1
$ErrorActionPreference = "Stop"

$Version = "2.0.0"
$Platforms = @("x64", "ARM64")
$OutputDir = ".\publish"

# Limpiar
Remove-Item -Recurse -Force $OutputDir -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Path $OutputDir | Out-Null

# Build per arquitectura
foreach ($platform in $Platforms) {
    $rid = $platform -eq "x64" ? "win-x64" : "win-arm64"
    
    Write-Host "Building $platform..." -ForegroundColor Cyan
    
    dotnet publish .\MiApp\MiApp.csproj `
        --configuration Release `
        --runtime $rid `
        --self-contained true `
        --output "$OutputDir\$platform" `
        /p:PublishSingleFile=true `
        /p:PublishReadyToRun=true
    
    # Empaquetar MSIX por arquitectura
    & "C:\Program Files (x86)\Windows Kits\10\bin\10.0.22621.0\$($platform.ToLower())\makeappx.exe" `
        pack /d "$OutputDir\$platform" `
        /p "$OutputDir\MiApp_$Version`_$platform.msix" `
        /o
    
    # Firmar
    & signtool sign /fd SHA256 /a /f cert.pfx /p $env:CERT_PWD `
        "$OutputDir\MiApp_$Version`_$platform.msix"
}

# Crear bundle (combina ambos en un .msixbundle único)
& "C:\Program Files (x86)\Windows Kits\10\bin\10.0.22621.0\x64\makeappx.exe" `
    bundle /d $OutputDir `
    /p "$OutputDir\MiApp_$Version.msixbundle" `
    /bv $Version

# Firmar el bundle
& signtool sign /fd SHA256 /a /f cert.pfx /p $env:CERT_PWD `
    "$OutputDir\MiApp_$Version.msixbundle"

Write-Host "✅ Bundle ready: $OutputDir\MiApp_$Version.msixbundle"
```

**El bundle "smart-install":**
```
MiApp_2.0.0.msixbundle
├── MiApp_2.0.0_x64.msix
├── MiApp_2.0.0_ARM64.msix
└── AppxMetadata/

Cuando user instala:
├── ARM64 device → instala solo paquete ARM64 (NO descarga x64)
├── x64 device → instala solo paquete x64
└── Ahorro de bandwidth: 50% típicamente
```

**Native AOT consideration (.NET 8/9):**
```xml
<!-- AOT compilation: faster startup, smaller binary -->
<!-- ⚠️ Requires careful testing — algunas libs no compatibles -->
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
```

**Pros AOT:**
- ✅ Startup ~10x más rápido
- ✅ Binary ~50% más pequeño
- ✅ Sin runtime dependency

**Contras AOT:**
- ❌ No reflection support (dynamic code)
- ❌ Algunas dependencies fallan
- ❌ Build time mucho mayor
- ❌ Debug más complejo

**Verificar funciona en ARM64:**
```powershell
# En máquina ARM64 (o emulator)
Add-AppxPackage -Path "MiApp_2.0.0_ARM64.msix"

# Verificar arquitectura instalada
Get-AppxPackage MiEmpresa.MiApp | Select-Object Name, Architecture, Version

# Output esperado en ARM64:
# Name: MiEmpresa.MiApp
# Architecture: Arm64
# Version: 2.0.0.0
```

**Costes vs beneficios:**
- ARM64 build CI extra time: ~3-5 min
- Bundle size: 2x (both archs incluidos)
- Smart-install ahorra para usuarios
- Future-proof para dispositivos Copilot+ PC

## Slide 20 — Edge case: Win32 services migration

Services Win32 son MUY tricky para MSIX migration:

```
Servicios Windows tradicionales:
├── Run en background (sin UI)
├── Configuración en registry HKLM
├── Need elevation (admin)
└── Lifecycle gestionado por Service Control Manager (SCM)

Problema con MSIX:
├── MSIX apps run as user, not as service
├── No HKLM access (limited registry)
├── No elevation por defecto
└── Auto-start patterns differ
```

**Estrategias migration:**

```
Strategy 1: Convert service to UWP background task
├── Limited but works
├── Lose: arbitrary code, low-level access
└── Gain: store distribution

Strategy 2: Keep service separately (hybrid approach)
├── MSIX app for UI
├── Traditional service for background work
└── IPC entre ambos

Strategy 3: Use Win32 IL5 (Isolation Level 5) - 2026
├── Sandboxed but more capable
├── Can run as restricted user
└── Newer feature, careful with compatibility
```

**Hybrid approach example:**
```xml
<!-- Package.appxmanifest -->
<Package>
  <Applications>
    <Application Id="App" Executable="MiApp.exe" EntryPoint="Windows.FullTrustApplication">
      <Extensions>
        <!-- Lanzar service helper al startup -->
        <desktop:Extension Category="windows.fullTrustProcess" 
                          Executable="ServiceHelper.exe">
          <desktop:FullTrustProcess>
            <desktop:ParameterGroup GroupId="install" Parameters="--install" />
          </desktop:FullTrustProcess>
        </desktop:Extension>
        
        <!-- Service heartbeat extension -->
        <desktop6:Extension Category="windows.service">
          <desktop6:Service Name="MiAppService" 
                           StartupType="auto"
                           StartAccount="localSystem"
                           Executable="MiAppService.exe" />
        </desktop6:Extension>
      </Extensions>
    </Application>
  </Applications>
</Package>
```

**Service registration en install:**
```csharp
// ServiceHelper.exe — runs at MSIX install
public class ServiceInstaller
{
    public static void Install()
    {
        // Get path within MSIX package
        var packagePath = Package.Current.InstalledLocation.Path;
        var serviceExe = Path.Combine(packagePath, "MiAppService.exe");
        
        // Use sc.exe (need elevation)
        var psi = new ProcessStartInfo
        {
            FileName = "sc.exe",
            Arguments = $"create MiAppService binPath=\"{serviceExe}\" start= auto",
            Verb = "runas",  // elevation
            UseShellExecute = true
        };
        
        Process.Start(psi).WaitForExit();
        
        // Start the service
        var startPsi = new ProcessStartInfo
        {
            FileName = "sc.exe",
            Arguments = "start MiAppService",
            UseShellExecute = true
        };
        Process.Start(startPsi);
    }
    
    public static void Uninstall()
    {
        var stopPsi = new ProcessStartInfo
        {
            FileName = "sc.exe",
            Arguments = "stop MiAppService",
            UseShellExecute = true
        };
        Process.Start(stopPsi).WaitForExit();
        
        var deletePsi = new ProcessStartInfo
        {
            FileName = "sc.exe",
            Arguments = "delete MiAppService",
            Verb = "runas",
            UseShellExecute = true
        };
        Process.Start(deletePsi);
    }
}
```

**Limitations a documentar:**
```
Service en MSIX hybrid:
├── ⚠️ Requires elevation at install
├── ⚠️ Service NO se actualiza automáticamente con MSIX update
├── ⚠️ Service se queda si user uninstall MSIX (a menos lo gestiones)
├── ⚠️ Startup order tricky
└── ⚠️ Settings deben sync entre service y MSIX app
```

**Better alternative: Background task UWP**
```csharp
// Si el "service" puede ser un background task más simple
public sealed class BackgroundProcessor : IBackgroundTask
{
    public async void Run(IBackgroundTaskInstance taskInstance)
    {
        var deferral = taskInstance.GetDeferral();
        
        try
        {
            // Periodic work
            await ProcessQueueAsync();
        }
        finally
        {
            deferral.Complete();
        }
    }
}

// Registrar en App startup
var builder = new BackgroundTaskBuilder
{
    Name = "MiAppBackgroundTask",
    TaskEntryPoint = "MiApp.BackgroundProcessor"
};
builder.SetTrigger(new TimeTrigger(15, false));  // every 15 min
builder.Register();
```

**Decision tree:**
```
¿Necesitáis tarea background?
├── Sí, sigue UI activa → Background thread en MSIX (simple)
├── Sí, app cerrada → Background task (Windows scheduler)
├── Sí, todo el tiempo → Service (hybrid approach)
└── Sí, requiere admin → Service como antes (no MSIX)
```

```csharp
        await localFolder.CreateFolderAsync("Cache", CreationCollisionOption.OpenIfExists);
        await localFolder.CreateFolderAsync("Logs", CreationCollisionOption.OpenIfExists);
        
        // 4. Copy bundled templates
        var packageRoot = Package.Current.InstalledLocation;
```

## Slide 27 — Cierre del submódulo
La migración de ClickOnce a MSIX es más un proyecto de distribución que de desarrollo. El código de la app no cambia (o cambia mínimamente). Lo que cambia es cómo se empaqueta, firma, distribuye y actualiza.

Hacedlo gradual: ambos canales en paralelo, grupo piloto, migración progresiva, y no eliminéis ClickOnce hasta que estéis 100% seguros. Con el plan de 5 semanas que hemos visto, la migración es controlada y reversible.

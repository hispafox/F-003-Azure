# Submódulo 7.4 — ClickOnce vs MSIX: por qué migrar y qué cambia

## Slide 1 — Portada
**Módulo 7 · Submódulo 7.4**
ClickOnce vs MSIX
Por qué migrar, qué se gana, qué cambia, y el roadmap de Microsoft

---

## Slide 2 — Contexto: vuestro equipo usa ClickOnce
Vuestro equipo distribuye aplicaciones WPF/WinForms con ClickOnce. Funciona, pero tiene limitaciones que cada vez pesan más: firma con Authenticode, publicación en un file share o IIS, auto-update que a veces falla silenciosamente, y un formato de paquete que Microsoft ha dejado de evolucionar.

MSIX es el formato moderno de empaquetado para Windows. No es solo un reemplazo de ClickOnce — es una arquitectura diferente que resuelve problemas que ClickOnce ni siquiera intenta abordar.

---

## Slide 3 — ClickOnce: lo que tenéis hoy

**Cómo funciona ClickOnce:**
1. Compiláis la app en Visual Studio
2. Publish → genera un `.application` (manifest) + archivos de la app
3. Copiáis a un file share, IIS, o Azure Blob Storage
4. El usuario accede a la URL del `.application` → descarga e instala
5. Al abrir la app, ClickOnce comprueba si hay nueva versión → actualiza

**Lo que funciona bien:**
- Simple para el desarrollador (publish desde Visual Studio)
- Auto-update integrado (sin código adicional)
- No requiere permisos de administrador para instalar

**Lo que NO funciona bien:**
- Firma con Authenticode: certificados caros, warnings de SmartScreen
- Sin control del ciclo de vida: no se puede desinstalar limpiamente
- Sin sandbox: la app tiene acceso completo al sistema del usuario
- Formato propietario: no funciona con Intune, SCCM ni MDM moderno
- Dependencias: .NET Framework hardcoded, no funciona con .NET 8
- Microsoft ha parado la evolución de ClickOnce

---

## Slide 4 — MSIX: qué es y por qué importa

MSIX es el formato moderno de empaquetado de aplicaciones Windows:

```
Archivo .msix (o .msixbundle)
├── Manifest (AppxManifest.xml)    ← Identidad, versión, capabilities
├── Código de la app               ← Tu WPF/WinForms/Console
├── Recursos (imágenes, config)    ← Assets
├── Firma digital                  ← Certificado de confianza
└── Metadata de actualización      ← AppInstaller para auto-update
```

**Ventajas sobre ClickOnce:**
| | ClickOnce | MSIX |
|---|:---:|:---:|
| Formato estándar de Windows | No | Sí (igual que apps Store) |
| Instalación limpia | Parcial | Completa (sandbox + cleanup) |
| Desinstalación limpia | No (deja residuos) | Sí (elimina todo) |
| Compatible con Intune/MDM | No | Sí |
| Auto-update con auth | No | Sí (con AppInstaller) |
| Firma | Authenticode (warnings) | App signing cert (confianza) |
| .NET 8+ | No (.NET Framework only) | Sí |
| Sideloading empresarial | Limitado | Completo |
| CI/CD pipeline | Limitado | Completo (MSBuild, Azure DevOps) |

## Slide 5 — MSIX: cómo funciona la instalación

```
1. Usuario recibe el .msix (descarga, MDM, o AppInstaller)
2. Windows verifica la firma digital
3. Windows instala en un contenedor virtualizado:
   - Archivos en C:\Program Files\WindowsApps\{package}\
   - Registry en VReg (virtualizado)
   - No toca el resto del sistema
4. Acceso directo en Start Menu
5. La app ejecuta en un sandbox ligero (acceso al filesystem limitado)

Desinstalación:
1. Settings → Apps → Desinstalar
2. Windows elimina TODOS los archivos, registry, cache
3. Sin residuos. Limpio.
```

**El concepto clave: contenedor.** La app vive en su propio espacio. No contamina el sistema. No deja residuos. Si algo falla, desinstaláis y el sistema queda exactamente como antes.

## Slide 6 — MSIX: modelo de distribución

```
Distribución MSIX:
├── Microsoft Store (apps públicas)
├── Microsoft Store for Business (apps corporativas privadas)
├── Sideloading (sin Store)
│   ├── AppInstaller (.appinstaller) → URL web con auto-update
│   ├── PowerShell (Add-AppxPackage)
│   ├── Intune / SCCM / MDM
│   └── Descarga directa del .msix
└── Azure Blob + CDN (distribución web con AppInstaller)
```

**Para vuestro equipo (distribución interna):**
La opción más relevante es **Sideloading con AppInstaller**. El `.appinstaller` es un XML que apunta a la URL donde está el `.msix`. Cuando el usuario lo abre, Windows descarga, instala y configura auto-update.

## Slide 7 — Requisitos para MSIX

**Desarrollo:**
- Visual Studio 2022+ con workload "Desktop development with .NET"
- Windows Application Packaging Project (o SDK de MSIX)
- Certificado de firma (self-signed para desarrollo, CA o corporativo para producción)

**Usuario final:**
- Windows 10 1809+ (October 2018) o Windows 11
- Sideloading habilitado (por defecto en Windows 10 2004+)
- Certificado de firma de la empresa instalado (para sideloading corporativo)

**Infraestructura:**
- Servidor web o Azure Blob Storage para hospedar el .msix y .appinstaller
- Pipeline CI/CD para build, sign y publicar automáticamente

## Slide 8 — Certificado de firma: tipos

| Tipo | Para qué | Coste | SmartScreen |
|------|----------|:-----:|:-----------:|
| Self-signed | Desarrollo y testing | Gratis | Warning |
| Enterprise CA (AD CS) | Distribución corporativa interna | Incluido en AD | Sin warning (si CA trusted) |
| Public CA (DigiCert, etc.) | Distribución externa | ~200-500€/año | Sin warning |
| Microsoft Store | Publicación en Store | Gratis (con dev account) | Sin warning |

**Para vuestro equipo (distribución interna):** Enterprise CA es la opción ideal. Si vuestra organización tiene Active Directory con Certificate Authority, ya tenéis la infraestructura. El certificado es de confianza en todos los PCs del dominio.

```powershell
# Crear certificado self-signed (para desarrollo)
New-SelfSignedCertificate -Type Custom -Subject "CN=MiEmpresa, O=MiOrg" `
  -KeyUsage DigitalSignature -FriendlyName "MSIX Dev Signing" `
  -CertStoreLocation "Cert:\CurrentUser\My" `
  -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3", "2.5.29.19={text}")
```

## Slide 9 — ClickOnce → MSIX: qué cambia para el usuario

| Aspecto | ClickOnce (ahora) | MSIX (después) |
|---------|:-----------------:|:--------------:|
| **Instalar** | Clic en .application → instala | Clic en .appinstaller → instala |
| **Actualizar** | Al abrir la app (check automático) | Al abrir la app (check automático) |
| **Desinstalar** | Panel de control (deja residuos) | Settings → Apps (limpio) |
| **Ubicación** | %LocalAppData%\Apps\ | C:\Program Files\WindowsApps\ |
| **Permisos** | Full trust | Full trust o sandbox (configurable) |
| **Experiencia** | Similar | Ligeramente diferente (popup de Windows) |

**Para el usuario final:** La experiencia es casi idéntica. La diferencia más visible es el diálogo de instalación (el de MSIX es el estándar de Windows, con el logo de vuestra empresa).

## Slide 10 — ClickOnce → MSIX: qué cambia para el desarrollador

| Aspecto | ClickOnce | MSIX |
|---------|:---------:|:----:|
| **Build** | Visual Studio Publish | MSBuild + packaging project |
| **Firma** | Authenticode (signtool) | MSIX signing (makemsix/signtool) |
| **Distribución** | File share / IIS | Azure Blob / CDN / AppInstaller |
| **Auto-update** | Built-in (limitado) | AppInstaller XML (flexible) |
| **CI/CD** | Publicar a file share | Pipeline: build → sign → upload → update .appinstaller |
| **Framework** | .NET Framework 4.x | .NET 8+ (o .NET Framework) |
| **Proyecto** | Proyecto WPF/WinForms directo | + Windows Application Packaging Project |

**El cambio más grande:** Necesitáis un proyecto de empaquetado adicional (WAP) o usar el MSIX SDK directamente. El build es ligeramente más complejo pero mucho más automatizable.

## Slide 11 — El roadmap de Microsoft: por qué ahora

**ClickOnce:**
- Sin nuevas features desde 2019
- Solo .NET Framework (no .NET 8+)
- No integrado con MDM moderno
- Microsoft lo mantiene pero no lo evoluciona

**MSIX:**
- Actualización continua con cada versión de Windows
- Integrado con Intune, SCCM, Windows Package Manager (winget)
- Soporte completo de .NET 8+
- AppInstaller con auto-update cada vez más potente
- MSIX Core para Windows 7/8.1 (legacy support)

**Conclusión:** ClickOnce no va a desaparecer mañana, pero cualquier inversión nueva debería ser en MSIX. Y migrar las apps existentes no es tan difícil como parece.

## Slide 12 — Escenarios de migración

**Escenario A: App WPF .NET Framework → MSIX (sin reescribir)**
MSIX Packaging Tool puede empaquetar la app tal cual. No necesitáis migrar a .NET 8. Solo empaquetáis el instalador existente como MSIX.

**Escenario B: App WPF → .NET 8 + MSIX (modernización)**
Migráis la app a .NET 8 (dotnet upgrade assistant) y empaquetáis con MSIX. Obtenéis todas las ventajas de .NET 8 (rendimiento, ARM64, etc.) + MSIX.

**Escenario C: App nueva → directamente con MSIX**
Para apps nuevas, usáis la plantilla de Visual Studio con packaging project desde el inicio.

**Para vuestro equipo:** Probablemente escenario A primero (empaquetar sin reescribir) y después escenario B (migrar a .NET 8) cuando tengáis tiempo.

## Slide 13 — MSIX Packaging Tool: empaquetar sin código

Para apps legacy (EXE/MSI installers) que no podéis recompilar:

```
1. Instalar MSIX Packaging Tool (Microsoft Store, gratis)
2. Preparar: VM limpia o Hyper-V sandbox
3. Abrir la herramienta → "Application package"
4. Seleccionar el instalador (.exe, .msi)
5. La herramienta ejecuta el instalador y captura cambios:
   - Archivos creados
   - Registry keys añadidas
   - Servicios registrados
6. Genera un .msix con todo capturado
```

Útil para empaquetar software de terceros o apps legacy sin acceso al código fuente.

```
  MSIX Packaging Tool → captura → .msix (legacy)

  Get-AppxPackage (listar instalados)
  Remove-AppxPackage (desinstalar)
```

## Slide 18 — Decisión: ¿Migrar ahora o esperar?

| Factor | Migrar ahora | Esperar |
|---|---|---|
| ClickOnce funciona bien | Si no hay problemas urgentes, OK esperar | Si hay problemas de actualización, migrar |
| Intune/MDM planeado | Migrar (ClickOnce no funciona con Intune) | — |
| Migración a .NET 8 | Migrar (ClickOnce no soporta .NET 8) | — |
| Nuevas apps | Directamente MSIX | — |
| Equipo pequeño | Esperar si no hay bandwidth | — |
| Certificado Authenticode expira pronto | Migrar (certificado MSIX es diferente) | — |

**Recomendación para vuestro equipo:** Empezad por las apps nuevas (directamente MSIX) y migrad las existentes gradualmente, empezando por las que tienen más problemas con ClickOnce.

## Slide 19 — Windows 11 24H2: cambios que afectan a MSIX

Windows 11 24H2 (lanzado Q4 2024) trae cambios importantes para MSIX:

```
Cambios relevantes 2024-2025:
├── ✅ Improved MSIX install performance (50% faster típica)
├── ✅ Background updates más eficientes
├── ✅ Better progress UI durante installs
├── ⚠️ AppInstaller deprecation roadmap clarified
├── ✅ Trusted Signing Service preview → GA
├── ✅ Identity Provider Locker (IDC) integration
└── ⚠️ Some legacy AppInstaller features removed
```

**Trusted Signing Service (GA 2024-2025):**
```
Antes: necesitabas comprar EV Code Signing Cert (€300-700/año)
       ├── Hardware token físico
       ├── Setup complejo
       └── Renewal cada 1-3 años

Ahora: Microsoft Trusted Signing
       ├── PaaS — service en Azure
       ├── No hardware token
       ├── Pay per signature (~€0.01)
       └── Auto-renewal de certs
```

**Setup Trusted Signing:**
```bash
# 1. Crear Trusted Signing account
az trustedsigning account create \
  --name ts-empresa \
  --resource-group rg-signing \
  --location westeurope \
  --sku-name Basic

# 2. Crear certificate profile
az trustedsigning certificate-profile create \
  --account-name ts-empresa \
  --resource-group rg-signing \
  --name MSIX-Signing-Profile \
  --profile-type PublicTrust \
  --include-country "ES" \
  --include-state-or-province "Madrid" \
  --identity-validation-id <validation-id>

# 3. Use to sign MSIX en CI/CD
# (replaces SignTool with TrustedSigningCli)
```

**CI/CD example:**
```yaml
# .github/workflows/build-msix.yml
- name: Build MSIX
  run: msbuild MyApp.wapproj /p:Configuration=Release /p:UapAppxPackageBuildMode=SideloadOnly

- name: Sign with Trusted Signing
  uses: azure/trusted-signing-action@v0
  with:
    azure-tenant-id: ${{ secrets.AZURE_TENANT_ID }}
    azure-client-id: ${{ secrets.AZURE_CLIENT_ID }}
    azure-client-secret: ${{ secrets.AZURE_CLIENT_SECRET }}
    endpoint: https://weu.codesigning.azure.net
    trusted-signing-account-name: ts-empresa
    certificate-profile-name: MSIX-Signing-Profile
    files-folder: AppPackages
    files-folder-filter: msix,appx,msi,exe
```

**Beneficios cliente:**
```
Pequeña empresa antes:
├── EV cert: €700/año
├── Hardware token: €100
├── Renewal hassle
└── Total: €800+/año

Con Trusted Signing:
├── Account fee: €60/año (~€5/mes Basic)
├── Sign cost: €0.01/sig × 100 sigs = €1/mes
├── No hardware
└── Total: ~€100/año (-87%)
```

**Identity Provider Locker (IDC):**
```
Windows 11 24H2 introduces IDC for MSIX apps
└── App can request "lock" on identity provider
    ├── Prevents user changing IDP from app
    ├── Useful for enterprise SSO compliance
    └── User opens Settings → Identity Locker
```

**Deprecations to watch:**
```
2024: AppInstaller deprecated for new development
   └── Microsoft pushing winget as preferred
2025: Some MSIX legacy APIs removed
2026: AppInstaller removed completely (announced)
   └── Migrate to winget OR Microsoft Store

Implications:
├── New projects: use winget
├── Existing: plan migration before 2026
└── Enterprise: Intune still primary deployment
```

## Slide 21 — MSIX Core: extensiones y APIs

MSIX no es solo packaging — tiene APIs runtime poderosas:

```csharp
// Runtime APIs disponibles en MSIX apps

using Windows.ApplicationModel;
using Windows.Storage;
using Windows.Management.Deployment;

public class MsixServices
{
    // Get current package info
    public Package GetCurrentPackage()
    {
        var package = Package.Current;
        return new Package
        {
            DisplayName = package.DisplayName,
            Version = $"{package.Id.Version.Major}.{package.Id.Version.Minor}.{package.Id.Version.Build}.{package.Id.Version.Revision}",
            FamilyName = package.Id.FamilyName,  // ⭐ unique identifier
            FullName = package.Id.FullName,
            Publisher = package.Id.Publisher,
            InstalledLocation = package.InstalledLocation.Path,
            IsDevelopmentMode = package.IsDevelopmentMode,
            SignatureKind = package.SignatureKind  // Store, Enterprise, etc.
        };
    }
    
    // App data folders
    public Dictionary<string, string> GetAppFolders()
    {
        return new Dictionary<string, string>
        {
            // Persistent across updates
            ["LocalState"] = ApplicationData.Current.LocalFolder.Path,
            
            // Per-user, syncs between devices via OneDrive (deprecated)
            ["RoamingState"] = ApplicationData.Current.RoamingFolder.Path,
            
            // Cleared by user
            ["LocalCache"] = ApplicationData.Current.LocalCacheFolder.Path,
            
            // Temp files
            ["TempState"] = ApplicationData.Current.TemporaryFolder.Path,
            
            // App settings (registry-like)
            ["Settings"] = ApplicationData.Current.LocalSettings.ToString(),
            
            // App install location (read-only)
            ["InstallLocation"] = Package.Current.InstalledLocation.Path
        };
    }
    
    // App restart
    public async Task RestartAppAsync()
    {
        await CoreApplication.RequestRestartAsync("Update applied");
    }
    
    // Check for updates programmatically
    public async Task<PackageUpdateAvailabilityResult> CheckForUpdatesAsync()
    {
        var package = Package.Current;
        var result = await package.CheckUpdateAvailabilityAsync();
        return result;  // Result.Availability: NoUpdates / Available / Required / Error
    }
}
```

## Slide 22 — Single-file MSIX con .NET 8/9

.NET 8+ permite single-file deployment dentro de MSIX:

```xml
<!-- MyApp.csproj — single-file deployment -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    
    <!-- Single-file settings -->
    <PublishSingleFile>true</PublishSingleFile>
    <SelfContained>true</SelfContained>
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
    <PublishTrimmed>false</PublishTrimmed>  <!-- Trimming WPF problemático -->
    <IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>
    
    <!-- Optimizations -->
    <PublishReadyToRun>true</PublishReadyToRun>  <!-- Faster startup -->
    <DebugType>embedded</DebugType>
  </PropertyGroup>
</Project>
```

**Build single-file:**
```bash
dotnet publish -c Release -r win-x64 \
  -p:PublishSingleFile=true \
  -p:SelfContained=true \
  --output ./publish

# Result: MyApp.exe (single file, ~80MB con runtime)
```

**Wrap en MSIX:**
```xml
<!-- Windows Application Packaging Project (.wapproj) -->
<Project>
  <PropertyGroup>
    <ProjectCapability Include="Msix" />
  </PropertyGroup>
  
  <ItemGroup>
    <ProjectReference Include="..\MyApp\MyApp.csproj">
      <PublishProfile>win-x64</PublishProfile>
    </ProjectReference>
  </ItemGroup>
</Project>
```

**Comparison:**

| | Traditional MSIX | Single-file MSIX |
|---|:---:|:---:|
| Package size | 30 MB (without runtime) | 80 MB (con runtime self-contained) |
| Install time | Fast | Slower (más datos) |
| User has .NET | Must install separately | Not needed |
| Update efficiency | Differential possible | Full re-download |
| Dependency hell | Possible | Avoided |
| Best for | Office IT-managed | Public distribution |

**Trimming considerations:**
```xml
<!-- .NET 8+ AOT compilation (advanced) -->
<PropertyGroup>
  <PublishAot>true</PublishAot>  <!-- Native AOT -->
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

<!-- Resultado: 
- Smaller binary (~20MB)
- Faster startup
- BUT: incompatible con WPF, EF Core, reflection-heavy code -->
```

**Real-world choice:**
```
Console apps / CLIs: 
└── Native AOT (smallest, fastest)

WPF apps:
└── Single-file self-contained (no AOT - reflection issues)

WinUI 3 apps:
└── Single-file self-contained (modern UI)

Server apps:
└── Containerized (Docker), not MSIX
```

**Tamaño optimizado:**
```bash
# Optimize MSIX size con compression
makeappx pack /d publish /p MyApp.msix /h SHA256 /l

# Bundle múltiples architectures (x64 + arm64)
makeappx bundle /d packages /p MyApp.msixbundle

# Total size: ~50MB con bundle (vs 80MB single arch)
```

## Slide 23 — Win32 Isolation Level 5 (IL5)

Windows 11 introduce mayor sandboxing para MSIX:

```
Isolation Levels (Windows 11):
├── Level 0: No isolation (legacy desktop)
├── Level 1: Per-user data isolation
├── Level 2: + Registry virtualization
├── Level 3: + File system virtualization
├── Level 4: + Network restrictions
└── Level 5: ⭐ Full sandboxing (similar to UWP)
```

**Configurar IL5 en manifest:**
```xml
<Package>
  <Properties>
    <!-- Request high isolation level -->
    <uap10:HostRuntimeDependency>
      <uap10:UAP6IsolationLevel>5</uap10:UAP6IsolationLevel>
    </uap10:HostRuntimeDependency>
  </Properties>
  
  <!-- Limit capabilities estrictamente -->
  <Capabilities>
    <Capability Name="internetClient" />  <!-- Only what needed -->
  </Capabilities>
</Package>
```

**Restrictions en IL5:**
```
✅ Permitido:
├── Acceso a propio LocalState, RoamingState
├── Network calls (si capability granted)
├── Acceso a propias APIs registradas
└── Reading propio package contents

❌ Restringido:
├── Reading other apps' data
├── Modifying registry directly
├── Executing other processes
├── COM activation outside package
└── Direct file system access (only WinRT FilePicker)
```

**Migration considerations:**
```csharp
// Code que NO funciona en IL5:
// ❌ Direct registry access
Registry.LocalMachine.CreateSubKey("Software\\MyApp");

// ✅ Use ApplicationData settings instead
ApplicationData.Current.LocalSettings.Values["MyKey"] = "value";

// ❌ Direct file system access
File.WriteAllText(@"C:\MyApp\data.txt", content);

// ✅ Use ApplicationData folders
var folder = ApplicationData.Current.LocalFolder;
var file = await folder.CreateFileAsync("data.txt");
await FileIO.WriteTextAsync(file, content);

// ❌ Process.Start to launch other apps directly  
Process.Start("C:\\Windows\\System32\\notepad.exe");

// ✅ Launcher.LaunchUriAsync for inter-app communication
await Launcher.LaunchUriAsync(new Uri("ms-paint:"));
```

**Use cases para IL5:**
- ✅ Consumer apps from Microsoft Store
- ✅ Education/restricted devices
- ✅ Public-facing apps (high security)
- ❌ IT admin tools (need broader access)
- ❌ Legacy apps con direct registry/file access

**Detect runtime context:**
```csharp
public bool IsRunningInSandbox()
{
    try
    {
        // En sandbox, accessing some APIs throws
        var temp = Environment.GetEnvironmentVariable("TEMP");
        var systemRoot = Environment.GetFolderPath(Environment.SpecialFolder.SystemX86);
        
        return Package.Current.SignatureKind != PackageSignatureKind.None;
    }
    catch
    {
        return true;  // Probably restricted
    }
}
```

**Adoption status:**
- IL5 still rolling out (2024-2026)
- Most apps run en Level 0-1 (default)
- Microsoft recommending IL5 for new apps
- Legacy apps gradual migration

**PSF (Package Support Framework) for problematic apps:**
```
Some apps have issues con MSIX containerization:
├── Hardcoded paths (C:\MyApp\config.ini)
├── Direct registry HKLM writes
├── Files written to Program Files
└── Solution: PSF runtime fixes

PSF features:
├── File redirection (intercept paths)
├── Registry redirection
├── Working directory fixing
├── Dynamic library injection
└── Open source: github.com/microsoft/MSIX-PackageSupportFramework
```

**Configure PSF:**
```json
// config.json en MSIX package

  "applications": [{
    "id": "MyApp",
    "executable": "MyApp.exe",

  "processes": [{
    "executable": ".*",
    "fixups": [{
      "dll": "FileRedirectionFixup.dll",
      "config": {
        "redirectedPaths": {
          "packageRelative": [{

      }
    }]
  }]
}
```

**When MSIX Packaging Tool falla:**
```
Common issues:
├── App requires Admin privileges (run packaging tool as admin)
├── App writes a HKLM (use PSF registry fixup)
├── App has driver/kernel components (NOT compatible con MSIX)
├── App requires running services (limited support)
└── App has shell extensions (special handling needed)

Decision tree:
├── Standard installer? → MSIX Packaging Tool works
├── Complex setup? → Try MSIX + PSF
├── Drivers/services? → Stay con MSI/legacy
└── New development? → Build MSIX-native
```

```

MSI → MSIX:
├── Recommended for desktop apps
├── Keep MSI for drivers/services

├── Quick win for distribution

```

## Slide 27 — Cierre del submódulo
MSIX es el presente y el futuro de la distribución de apps Windows. ClickOnce fue su momento, pero las limitaciones de firma, distribución y gestión hacen que la migración sea cuestión de cuándo, no de si.

La decisión: empaquetar primero (MSIX Packaging Tool, sin cambios de código) o modernizar primero (.NET 8 + packaging project). Para vuestro equipo, empaquetar primero es el camino más rápido.

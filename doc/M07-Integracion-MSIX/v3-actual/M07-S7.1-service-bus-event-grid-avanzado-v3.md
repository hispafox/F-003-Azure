## Slide 3 — Service Bus: arquitectura de topics y subscriptions

```
Publicador                Topic                    Suscripciones
┌──────────┐          ┌─────────────┐         ┌──────────────────┐
│ API      │─mensaje─→│             │────────→ │ sub-emails       │→ Func: enviar email
│ Pedidos  │          │  pedidos    │────────→ │ sub-facturacion  │→ Func: generar factura
│          │          │  -eventos   │────────→ │ sub-inventario   │→ Func: reservar stock
│          │          │             │────────→ │ sub-analytics    │→ Func: actualizar KPIs
└──────────┘          └─────────────┘         └──────────────────┘
```

**Cada suscripción recibe una COPIA del mensaje.** Si publicáis un evento "PedidoCreado", las 4 funciones lo reciben y lo procesan independientemente. Si una falla, las otras no se ven afectadas.

**Cada suscripción tiene su propia dead-letter queue.** Si la función de emails falla 10 veces, el mensaje va a la DLQ de emails — no afecta a facturación ni inventario.

## Slide 4 — Filtros SQL en suscripciones

Las suscripciones pueden filtrar qué mensajes reciben:

```bash
# Crear suscripción que solo recibe pedidos > 100€
az servicebus topic subscription create \
  --namespace-name sb-ventas-prod -g mi-rg \
  --topic-name pedidos-eventos --name sub-pedidos-grandes

az servicebus topic subscription rule create \
  --namespace-name sb-ventas-prod -g mi-rg \
  --topic-name pedidos-eventos --subscription-name sub-pedidos-grandes \
  --name filtro-importe \
  --filter-sql-expression "total > 100"

# Solo pedidos de España
az servicebus topic subscription rule create \
  --namespace-name sb-ventas-prod -g mi-rg \
  --topic-name pedidos-eventos --subscription-name sub-spain \
  --name filtro-pais \
  --filter-sql-expression "pais = 'ES'"

# Solo pedidos urgentes de electrónica
az servicebus topic subscription rule create ... \
  --filter-sql-expression "prioridad = 'urgente' AND categoria = 'electronica'"
```

**Los filtros se evalúan en el broker** — no en tu código. Service Bus descarta mensajes que no cumplen el filtro antes de entregarlos a la suscripción. Menos tráfico, menos procesamiento.

## Slide 5 — Publicar mensajes con propiedades para filtrado

```csharp
public class PedidoEventPublisher
{
    private readonly ServiceBusSender _sender;

    public async Task PublicarPedidoCreadoAsync(Pedido pedido)
    {
        var mensaje = new ServiceBusMessage(JsonSerializer.Serialize(pedido))
        {
            ContentType = "application/json",
            Subject = "pedido-creado",
            MessageId = pedido.Id,
            CorrelationId = Activity.Current?.Id ?? Guid.NewGuid().ToString(),
            ApplicationProperties =
            {
                ["total"] = pedido.Total,
                ["pais"] = pedido.Cliente.Pais,
                ["categoria"] = pedido.Items.First().Categoria,
                ["prioridad"] = pedido.Total > 500 ? "urgente" : "normal",
                ["clienteTipo"] = pedido.Cliente.EsPremium ? "premium" : "standard",
                ["version"] = "2.0"
            }
        };

        await _sender.SendMessageAsync(mensaje);
    }
}
```

**Las ApplicationProperties son la clave del filtrado.** Poned toda la información que pueda necesitarse para filtrar en las propiedades, no en el body. Service Bus puede filtrar propiedades sin deserializar el body.

## Slide 6 — Patrón: Competing Consumers

Múltiples instancias de la misma función procesando la misma cola:

```
Cola: pedidos-a-procesar
  ┌─ Mensaje 1 ──→ Instancia A (procesa)
  ├─ Mensaje 2 ──→ Instancia B (procesa)
  ├─ Mensaje 3 ──→ Instancia A (procesa)
  ├─ Mensaje 4 ──→ Instancia C (procesa)
  └─ Mensaje 5 ──→ Instancia B (procesa)
```

**Cada mensaje es procesado por exactamente UNA instancia.** Service Bus usa Peek Lock: la instancia "bloquea" el mensaje, lo procesa, y lo completa. Ninguna otra instancia lo ve mientras está bloqueado.

**Escalar:** Añadir más instancias de la función = más throughput. Azure Functions lo hace automáticamente.

## Slide 7 — Patrón: Request/Reply con Service Bus

Cuando necesitáis respuesta asíncrona:

```csharp
// EMISOR: enviar petición y esperar respuesta
var requestMessage = new ServiceBusMessage(JsonSerializer.Serialize(request))
{
    ReplyTo = "respuestas-validacion",  // Cola donde espero la respuesta
    MessageId = correlationId,
    SessionId = correlationId  // Para correlacionar request/reply
};
await _requestSender.SendMessageAsync(requestMessage);

// Esperar respuesta en la cola de respuestas
var receiver = _client.AcceptSessionAsync("respuestas-validacion", correlationId);
var reply = await receiver.ReceiveMessageAsync(TimeSpan.FromSeconds(30));

// RECEPTOR: procesar y responder
[Function("ValidarPedido")]
public async Task Validar(
    [ServiceBusTrigger("peticiones-validacion")] ServiceBusReceivedMessage msg,
    ServiceBusMessageActions actions)
{
    var pedido = msg.Body.ToObjectFromJson<Pedido>();
    var resultado = await _validador.ValidarAsync(pedido);
    
    // Responder en la cola indicada por ReplyTo
    var replySender = _client.CreateSender(msg.ReplyTo);
    await replySender.SendMessageAsync(new ServiceBusMessage(JsonSerializer.Serialize(resultado))
    {
        SessionId = msg.MessageId,  // Correlación
        CorrelationId = msg.MessageId
    });
}
```

## Slide 9 — Patrón: Dead-Letter processing workflow

```
Cola principal              DLQ                     Proceso de revisión
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│ Msg procesados│         │ Msg fallidos │         │ Dashboard    │
│ normalmente   │         │ (max retries)│────────→│ + alertas    │
└──────────────┘         └──────────────┘         │ + re-submit  │
                                                   └──────────────┘
```

```csharp
// Función que monitoriza la DLQ
[Function("MonitorizarDLQ")]
public async Task MonitorizarDLQ(
    [TimerTrigger("0 */5 * * * *")] TimerInfo timer)
{
    var receiver = _client.CreateReceiver("pedidos-a-procesar",
        new ServiceBusReceiverOptions { SubQueue = SubQueue.DeadLetter });
    
    var mensajes = await receiver.PeekMessagesAsync(maxMessages: 100);
    
    if (mensajes.Count > 0)
    {
        _logger.LogWarning("DLQ tiene {Count} mensajes", mensajes.Count);
        
        foreach (var msg in mensajes)
        {
            _logger.LogWarning("  DLQ msg {Id}: reason={Reason}, error={Error}",
                msg.MessageId, msg.DeadLetterReason, msg.DeadLetterErrorDescription);
        }
        
        // Alertar al equipo
        await _alertas.EnviarAsync($"DLQ pedidos: {mensajes.Count} mensajes pendientes");
    }
}

// Re-submit: mover mensajes de DLQ de vuelta a la cola principal
[Function("ResubmitDLQ")]
public async Task Resubmit(
    [HttpTrigger(AuthorizationLevel.Admin, "post", Route = "admin/dlq/resubmit")] HttpRequest req)
{
    var dlqReceiver = _client.CreateReceiver("pedidos-a-procesar",
        new ServiceBusReceiverOptions { SubQueue = SubQueue.DeadLetter });
    var sender = _client.CreateSender("pedidos-a-procesar");
    
    var msg = await dlqReceiver.ReceiveMessageAsync();
    if (msg is not null)
    {
        await sender.SendMessageAsync(new ServiceBusMessage(msg));
        await dlqReceiver.CompleteMessageAsync(msg);
    }
}
```

## Slide 10 — Patrón: Message Deduplication

Service Bus puede detectar y descartar mensajes duplicados:

```bash
# Crear cola con deduplicación
az servicebus queue create \
  --namespace-name sb-ventas-prod -g mi-rg \
  --name pedidos-dedup \
  --enable-duplicate-detection true \
  --duplicate-detection-history-time-window P1D  # 1 día de ventana
```

```csharp
// Si envías el mismo MessageId dos veces, el segundo se descarta
var msg1 = new ServiceBusMessage("Pedido PED-001") { MessageId = "PED-001-v1" };
var msg2 = new ServiceBusMessage("Pedido PED-001") { MessageId = "PED-001-v1" };  // Duplicado

await sender.SendMessageAsync(msg1);  // ✓ Entregado
await sender.SendMessageAsync(msg2);  // ✗ Descartado (mismo MessageId en la ventana)
```

**Cuándo usarlo:** Cuando el publicador puede enviar el mismo mensaje más de una vez (retries, failover, at-least-once delivery). La deduplicación garantiza que el consumidor no lo procesa dos veces.

## Slide 11 — Patrón: Batch processing con Service Bus

```csharp
// Enviar batch de mensajes (más eficiente que uno a uno)
var batch = await sender.CreateMessageBatchAsync();
foreach (var pedido in pedidos)
{
    var msg = new ServiceBusMessage(JsonSerializer.Serialize(pedido))
    {
        MessageId = pedido.Id,
        ApplicationProperties = { ["total"] = pedido.Total }
    };
    
    if (!batch.TryAddMessage(msg))
    {
        // Batch lleno → enviar lo que hay y crear nuevo batch
        await sender.SendMessagesAsync(batch);
        batch = await sender.CreateMessageBatchAsync();
        batch.TryAddMessage(msg);
    }
}
await sender.SendMessagesAsync(batch);  // Enviar el último batch
```

**Recibir batch en Function:**
```json
// host.json — procesar hasta 50 mensajes por invocación
{
  "extensions": {
    "serviceBus": {
      "maxMessageBatchSize": 50,
      "prefetchCount": 100,
      "maxConcurrentCalls": 16
    }
  }
}
```

## Slide 14 — Event Grid: dead-letter y retry

```bash
# Configurar dead-letter en blob storage
az eventgrid event-subscription update \
  --name sub-pedidos-grandes \
  --source-resource-id "..." \
  --deadletter-endpoint "/subscriptions/<id>/.../storageAccounts/stventas/blobServices/default/containers/deadletter-events"
```

**Política de retry de Event Grid:**
- 24 horas de reintentos
- Backoff exponencial
- Si después de 24h no se entrega → dead-letter (si configurado) o se pierde

**Diferencia con Service Bus:** Event Grid tiene retry limitado (24h). Service Bus mantiene el mensaje indefinidamente en la DLQ. Para procesamiento crítico donde no podéis perder mensajes, usad Service Bus.

## Slide 16 — Event Grid vs Service Bus: decisión por escenario

| Escenario | Recomendación |
|-----------|:------------:|
| Blob creado → procesar archivo | **Event Grid** |
| Pedido creado → enviar email | **Service Bus** (fiabilidad) |
| Notificar a N suscriptores | **Event Grid** (fan-out nativo) |
| Encolar trabajo pesado | **Service Bus** (dead-letter, FIFO) |
| Reaccionar a cambios en Azure | **Event Grid** (eventos nativos) |
| Comunicación entre microservicios | **Service Bus** (garantías de entrega) |
| Pipeline de datos (transform) | **Service Bus** (sessions, orden) |
| Webhook de servicio externo | **Event Grid** (HTTP push) |

**Combinación:** Event Grid detecta el evento → publica en un Service Bus Topic → Functions procesan con garantías de entrega.

## Slide 20 — Service Bus: message lock renewal
Para procesamiento largo que excede el lock timeout (default 30s):

```csharp
[Function("ProcesarPedidoLargo")]
public async Task Procesar(
    [ServiceBusTrigger("pedidos-largos")] ServiceBusReceivedMessage msg,
    ServiceBusMessageActions actions)
{
    // Renovar el lock periódicamente durante procesamiento largo
    using var cts = new CancellationTokenSource();
    var renewTask = RenewLockPeriodically(msg, actions, cts.Token);
    
    try
    {
        await ProcesamientoLargoAsync(msg);  // Tarda 5 minutos
        await actions.CompleteMessageAsync(msg);
    }
    finally
    {
        cts.Cancel();
    }
}

private async Task RenewLockPeriodically(ServiceBusReceivedMessage msg,
    ServiceBusMessageActions actions, CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        await Task.Delay(TimeSpan.FromSeconds(20), ct);
        await actions.RenewMessageLockAsync(msg, ct);
    }
}
```

Sin lock renewal, Service Bus asume que el consumidor falló y reentrega el mensaje a otra instancia (duplicando el procesamiento).

## Slide 24 — Geo-disaster recovery (Geo-DR)

Premium tier permite geo-DR con automatic failover:

```
Architecture:
─────────────
West Europe (PRIMARY)            North Europe (SECONDARY)
┌────────────────────┐           ┌────────────────────┐
│ sb-prod-weu        │           │ sb-prod-neu        │
│ Premium Namespace  │           │ Premium Namespace  │
│                    │           │                    │
│ ✅ Active          │ ────►     │ ⏸️ Standby         │
│ Receiving messages │  metadata │ Empty messages     │
│                    │   sync    │                    │
└────────────────────┘           └────────────────────┘
        │
        │ Alias: sb-prod.servicebus.windows.net
        └─── (transparent endpoint que no cambia con failover)
```

**Setup Geo-DR:**
```bash
# 1. Crear secondary namespace en otra region
az servicebus namespace create \
  --resource-group rg-prod-neu \
  --name sb-prod-neu \
  --location northeurope \
  --sku Premium \
  --capacity 1

# 2. Pair primary y secondary con alias
az servicebus georecovery-alias create \
  --resource-group rg-prod \
  --namespace-name sb-prod-weu \
  --alias sb-prod-alias \
  --partner-namespace $(az servicebus namespace show \
    -n sb-prod-neu -g rg-prod-neu --query id -o tsv)

# 3. Verificar pairing
az servicebus georecovery-alias show \
  --resource-group rg-prod \
  --namespace-name sb-prod-weu \
  --alias sb-prod-alias
```

```csharp
// Apps connect to alias endpoint

var client = new ServiceBusClient(connectionString);

// Antes failover: connects to West EU
// Después failover: connects to North EU automáticamente
```

**Failover scenarios:**
```
1. Manual failover (planned, e.g. for testing):
   az servicebus georecovery-alias fail-over \
     --resource-group rg-prod-neu \
     --namespace-name sb-prod-neu \
     --alias sb-prod-alias
   
   Time: 30-60 segundos
   Impact: 5-10 sec downtime

2. Disaster failover (region down):
   Mismo command, ejecutado por equipo de ops
   Tiempo: < 1 minuto

3. Failback (después de restoration):
   Re-pair primary, run failover hacia primary
   Datos: solo metadata sync, NO messages in flight
```

**Important caveats:**
- ⚠️ **Solo metadata replicates** (queues, topics, subscriptions, filters)
- ⚠️ **Messages NO replicate** — los in-flight pueden perderse
- ⚠️ **Apps must handle duplicates** — same message puede llegar twice
- ⚠️ **RPO ~0 minutos pero RTO ~1 min**

**Mitigation para messages no replicados:**
```csharp
// Pattern: Outbox + idempotent receivers
public class IdempotentMessageHandler
{
    public async Task ProcessAsync(ServiceBusReceivedMessage msg)
    {
        var messageId = msg.MessageId;
        
        // Check dedup table en SQL/Cosmos
        if (await _dedupStore.HasProcessedAsync(messageId))
        {
            await msg.CompleteMessageAsync();  // ya procesado, just complete
            return;
        }
        
        // Process
        await DoBusinessLogicAsync(msg);
        
        // Mark as processed (atomic con business logic ideally)
        await _dedupStore.MarkProcessedAsync(messageId);
        await msg.CompleteMessageAsync();
    }
}
```

**Cost:** Geo-DR pairing duplica el coste (2x Premium namespaces) pero garantiza zero data loss en metadata + 1 min RTO.

```
Para mensajes muy grandes, mejor referenciar storage:

┌──────────────┐                    ┌──────────────┐
│  Producer    │                    │  Consumer    │
│              │                    │              │
│ 1. Upload    │                    │ 4. Receive   │
│    blob to   │ ───────────────► Storage          │
│    storage   │   (50MB JSON)      │              │
│              │                    │              │
│ 2. Send msg  │ ──── Service Bus ─►│ 5. Read URL  │
│    with URL  │   ("ref": URL)     │              │
│              │                    │ 6. Download  │
│              │                    │    blob      │
└──────────────┘                    └──────────────┘
```

**Implementation:**
```csharp
// Producer
public async Task SendLargeEventAsync(MyLargeEvent evt)
{
    // 1. Upload payload to blob storage
    var blobName = $"events/{Guid.NewGuid()}.json";
    var blobClient = _containerClient.GetBlobClient(blobName);
    await blobClient.UploadAsync(BinaryData.FromObjectAsJson(evt));
    
    // 2. Send small message with reference (NOT full data)
    var message = new ServiceBusMessage(JsonSerializer.Serialize(new
    {
        EventType = "LargeEventCreated",
        BlobUri = blobClient.Uri.ToString(),
        EventId = evt.Id
    }));
    
    await _sender.SendMessageAsync(message);
}

// Consumer
[Function(nameof(ProcessLargeEvent))]
public async Task ProcessLargeEvent(
    [ServiceBusTrigger("events", Connection = "ServiceBus")] 
    ServiceBusReceivedMessage msg)
{
    // 1. Parse small message
    var reference = msg.Body.ToObjectFromJson<EventReference>();
    
    // 2. Download large payload
    var blobClient = new BlobClient(new Uri(reference.BlobUri), 
        new DefaultAzureCredential());
    var blob = await blobClient.DownloadContentAsync();
    var fullEvent = blob.Value.Content.ToObjectFromJson<MyLargeEvent>();
    
    // 3. Process
    await ProcessAsync(fullEvent);
}
```

**Cuándo direct large message vs claim check:**

| | Direct (>1MB) | Claim Check |
|---|:---:|:---:|
| Setup complexity | Low | Medium |
| Network usage | Per message | Initial upload |
| Idempotency | Built-in | Per blob |
| Lifecycle mgmt | Auto cleanup | Manual blob cleanup |
| Cost | High msg ops | Low msg ops + storage |
| Multiple consumers | Replays cost | Each downloads (free reads) |
| Best for | <5MB messages | >5MB or replay scenarios |

## Slide 26 — Sessions y FIFO ordering

Service Bus Sessions garantiza ordering FIFO **por session key**:

```
Sin sessions:
Queue:  [msg1, msg2, msg3, msg4]
        ▼     ▼     ▼     ▼
        Worker1  Worker2  Worker3  Worker4
        (parallelizado, NO ordering guarantee)

Con sessions:
Queue:  [order-A:msg1, order-B:msg1, order-A:msg2, order-A:msg3]
        ▼                ▼                ▼            ▼
        Session lock     Session lock     Session lock Session lock
        for "order-A"    for "order-B"    for "order-A" for "order-A"
        Worker1 ─────────── (procesa A en orden) ─────────────►
                            Worker2 ───────► (procesa B en orden)
```

**Habilitar sessions en queue:**
```bash
# Required: enable sessions al crear (NO se puede cambiar después)
az servicebus queue create \
  --resource-group rg-prod \
  --namespace-name sb-prod \
  --name orders-queued \
  --enable-session true \
  --max-size 1024
```

**Producer con session ID:**
```csharp

{
    SessionId = "order-12345",  // session key
    MessageId = "msg-1"

{
    SessionId = "order-12345",
    MessageId = "msg-2"
});

await sender.SendMessageAsync(new ServiceBusMessage("Order shipped")
{
    SessionId = "order-12345",
    MessageId = "msg-3"
});

// Different session = parallel processing
await sender.SendMessageAsync(new ServiceBusMessage("Other order")
{
    SessionId = "order-67890"  // different session
});
```

**Consumer con session processor:**
```csharp
// Session processor — handles one session at a time
var processor = client.CreateSessionProcessor("orders-queued",
    new ServiceBusSessionProcessorOptions
    {
        MaxConcurrentSessions = 5,  // process 5 sessions in parallel
        MaxConcurrentCallsPerSession = 1,  // FIFO within session
        SessionIdleTimeout = TimeSpan.FromMinutes(1)
    });

processor.ProcessMessageAsync += async args =>
{
    var sessionId = args.SessionId;
    var message = args.Message;
    
    Console.WriteLine($"[{sessionId}] Processing: {message.Body}");
    
    // All messages with same SessionId process IN ORDER
    await ProcessOrderEventAsync(sessionId, message.Body);
    
    await args.CompleteMessageAsync(message);
};

processor.SessionInitializingAsync += async args =>
{
    Console.WriteLine($"Locked session: {args.SessionId}");
    
    // Load session state (e.g., from DB)
    var state = await _stateStore.GetAsync(args.SessionId);
    await args.SetSessionStateAsync(BinaryData.FromObjectAsJson(state));
};

processor.SessionClosingAsync += async args =>
{
    Console.WriteLine($"Released session: {args.SessionId}");
    
    // Save session state
    var stateData = await args.GetSessionStateAsync();
    if (stateData != null)
    {
        var state = stateData.ToObjectFromJson<SessionState>();
        await _stateStore.SaveAsync(args.SessionId, state);
    }
};

await processor.StartProcessingAsync();
```

**Use cases reales:**

```
1. Order processing pipeline (ordering matters within order):
   ├── Order Created → Order Paid → Order Shipped
   ├── Different orders process in parallel
   └── Same order steps in sequence

2. Conversation/chat threads:
   ├── Each conversation = session
   ├── Messages within conversation in order
   └── Multiple conversations parallel

3. Workflow per entity:
   ├── User onboarding: ID verify → email verify → profile complete
   └── Sequence guaranteed per user

4. Stock trading per symbol:
   ├── BUY 100 AAPL → SELL 50 AAPL → BUY 200 AAPL
   ├── Same symbol = same session = correct order
   └── Different symbols = parallel
```

**Session state management:**
```csharp

{
    LastProcessedAt = DateTime.UtcNow,
    MessagesProcessed = 42,
    ErrorCount = 0
}));

// Useful for tracking progress without external DB
```

**Anti-patterns:**
- ❌ Single session for all messages (loses parallelism)
- ❌ Sessions with millions of unique keys (overhead)
- ❌ Heavy state per session (use external store for >100KB)

## Slide 28 — Cross-region active-active patterns

Para apps mission-critical, traffic split entre regiones simultáneamente:

```
Traditional Geo-DR:
└── Primary: 100% traffic
└── Secondary: 0% traffic (standby)
   Failover: ~1 min downtime

Active-Active:
└── Region 1: 50% traffic
└── Region 2: 50% traffic
   Failover: 0 sec downtime (just route 100% to surviving)
```

**Implementation con Front Door + dos namespaces:**
```bash
# Front Door routes a 2 regions
# Apps en cada region usan SB local namespace

# Region 1 setup
az servicebus namespace create \
  --resource-group rg-prod-weu \
  --name sb-prod-weu-active \
  --location westeurope --sku Premium

# Region 2 setup
az servicebus namespace create \
  --resource-group rg-prod-neu \
  --name sb-prod-neu-active \
  --location northeurope --sku Premium

# Both active simultaneously
# Apps connect to local SB based on which region they're in
```

**App-level routing:**
```csharp
// App detecta region y conecta al local SB
public class RegionAwareServiceBus
{
    private readonly string _region;
    private readonly ServiceBusClient _localClient;
    
    public RegionAwareServiceBus(IConfiguration config)
    {
        // Detect region (via Azure metadata, env var, etc.)
        _region = Environment.GetEnvironmentVariable("AZURE_REGION") ?? "westeurope";
        
        var sbNamespace = _region == "westeurope" 
            ? "sb-prod-weu-active.servicebus.windows.net"
            : "sb-prod-neu-active.servicebus.windows.net";
        
        _localClient = new ServiceBusClient(sbNamespace, new DefaultAzureCredential());
    }
    
    public ServiceBusSender CreateSender(string queueName)
    {
        return _localClient.CreateSender(queueName);
    }
}
```

**Cross-region replication entre namespaces:**
```csharp
// Function que replica messages from one region to other
// (for shared visibility)

[Function(nameof(ReplicateToOtherRegion))]
public async Task ReplicateToOtherRegion(
    [ServiceBusTrigger("orders", Connection = "ServiceBus")]
    ServiceBusReceivedMessage msg,
    FunctionContext context)
{
    // If message originated locally, replicate to other region
    var originRegion = msg.ApplicationProperties["OriginRegion"]?.ToString();
    var currentRegion = Environment.GetEnvironmentVariable("AZURE_REGION");
    
    if (originRegion == currentRegion)
    {
        // Replicate to other region
        var otherRegion = currentRegion == "westeurope" ? "northeurope" : "westeurope";
        var otherClient = GetClientForRegion(otherRegion);
        var otherSender = otherClient.CreateSender("orders");
        
        var replicaMsg = new ServiceBusMessage(msg.Body)
        {
            MessageId = msg.MessageId,  // same ID for dedup
            ApplicationProperties = 
            {
                ["OriginRegion"] = originRegion,
                ["ReplicatedFrom"] = currentRegion,
                ["ReplicatedAt"] = DateTimeOffset.UtcNow
            }
        };
        
        await otherSender.SendMessageAsync(replicaMsg);
    }
    
    // Process locally
    await ProcessOrderAsync(msg);
}
```

**Dedup strategy:**
```
Both regions process same message after replication
Need to prevent double-processing:

Option 1: Idempotent receivers
├── Use MessageId for dedup table
├── First region wins, second sees "already processed"

Option 2: Region-specific routing
├── Header: TargetRegion = "westeurope"
├── Other region replicates but ignores
└── Useful for region-pinned data
```

**Cost analysis:**
```
Active-Active 2 regions:
├── 2x Premium namespaces: €1200/mes
├── 2x app deployments: €X
├── Cross-region bandwidth: €Y
└── Total overhead: ~2x base cost

Active-Active 3 regions:
├── 3x setup
├── More complex consistency (last-write-wins)
└── 3x base cost

Traditional Geo-DR:
├── 2x Premium namespaces (one standby)
├── ~1.5x base cost (some idle)
└── < 1 min RTO

Decision matrix:
├── < 1 min downtime acceptable: Geo-DR
├── 0 downtime required: Active-Active 2 regions
├── Global distribution + low latency: 3+ regions
```

## Slide 29 — Schema Registry para events

Schema Registry para eventos versionados (preview/GA 2024):

```
Problem:
├── Producer envía evento v1
├── Consumer parsea como v1
├── Producer evolves to v2 (breaking change)
└── Consumer crashes parsing v2 ❌

Solution: Schema Registry
├── Schemas versionados centralmente
├── Producer publica schema version with event
├── Consumer reads schema for proper parsing
└── Compatibility validation prevents breaking
```

**Setup Schema Registry en Event Hubs (también funciona con SB):**
```bash
az eventhubs namespace schema-registry create \
  --resource-group rg-prod \
  --namespace-name eh-prod \
  --name OrderEvents \
  --schema-compatibility Backward
```

**Compatibility modes:**
```
NONE:        Cualquier change permitted (no protection)
BACKWARD:    Consumer with new schema can read old data
FORWARD:     Producer with new schema, old consumer can read
FULL:        Backward AND Forward
```

**Define schema (Avro):**

```json
        "type": "array",
        "items": {
          "type": "record",
          "name": "OrderItem",
          "fields": [
            { "name": "productId", "type": "string" },
            { "name": "quantity", "type": "int" },
            { "name": "price", "type": "double" }
          ]
        }
    }},
    { "name": "createdAt", "type": "long", "logicalType": "timestamp-millis" }
```

```csharp
// Util script: re-process dead-lettered messages
public async Task ResubmitDeadLetterAsync(string queueName)
{
    var dlqReceiver = _client.CreateReceiver(queueName, new ServiceBusReceiverOptions
    {
        SubQueue = SubQueue.DeadLetter
    });
    
    var sender = _client.CreateSender(queueName);
    
    while (true)
    {
        var dlqMessage = await dlqReceiver.ReceiveMessageAsync(TimeSpan.FromSeconds(5));
        if (dlqMessage == null) break;
        
        Console.WriteLine($"Resubmitting: {dlqMessage.MessageId}");
        Console.WriteLine($"  Reason: {dlqMessage.DeadLetterReason}");
        Console.WriteLine($"  Description: {dlqMessage.DeadLetterErrorDescription}");
        
        // Recreate as new message
        var newMessage = new ServiceBusMessage(dlqMessage.Body)
        {
            MessageId = dlqMessage.MessageId,
            ContentType = dlqMessage.ContentType,
            CorrelationId = dlqMessage.CorrelationId
        };
        
        // Copy properties
        foreach (var prop in dlqMessage.ApplicationProperties)
        {
            newMessage.ApplicationProperties[prop.Key] = prop.Value;
        }
        
        await sender.SendMessageAsync(newMessage);
        await dlqReceiver.CompleteMessageAsync(dlqMessage);
    }
}
```

## Slide 31 — Anti-patterns Service Bus + Event Grid

Errors comunes que veo en producción:

```
❌ ANTI-PATTERN 1: ServiceBusClient new instance per request
   var client = new ServiceBusClient(cs); // each request
   ✅ Singleton DI registration

❌ ANTI-PATTERN 2: Storage Queues para algo más complex que FIFO
   ✅ Service Bus para anything beyond simple queue

❌ ANTI-PATTERN 3: Sin DLQ monitoring
   Messages accumulate, no one notices
   ✅ Alert if DLQ count > 10

❌ ANTI-PATTERN 4: Sin retry policy
   First failure = permanent failure
   ✅ Built-in retry + dead-lettering after N attempts

❌ ANTI-PATTERN 5: Hardcoded connection strings
   appsettings.json: "Endpoint=sb://...;SharedAccessKey=..."
   ✅ Managed Identity + RBAC

❌ ANTI-PATTERN 6: Lock duration < processing time
   Message lock expires, message redelivered, double processing
   ✅ Lock duration = max processing time + safety margin
   ✅ Or: AutoLockRenewal con SDK

❌ ANTI-PATTERN 7: Synchronous processing en async-first SDK
   message.Receive() blocking
   ✅ async/await everywhere

❌ ANTI-PATTERN 8: Sin idempotency
   Network blip = duplicate processing
   ✅ Dedupe with MessageId + state store

❌ ANTI-PATTERN 9: Event Grid in subscription per consumer
   N consumers = N subscriptions cada con same filter
   ✅ Single subscription + routing logic

❌ ANTI-PATTERN 10: Send + Process en single transaction
   Messages sent BEFORE business logic confirmed
   ✅ Outbox pattern

❌ ANTI-PATTERN 11: Standard tier para mission-critical
   Compliance fail
   ✅ Premium with VNet, Geo-DR

❌ ANTI-PATTERN 12: Polling Event Hubs en lugar de subscription
   Wasted resources
   ✅ Event-driven trigger
```

**Real-world cost issue:**
```
Cliente con SB Standard, 1B operations/mes:
├── Cost: €100/mes (Standard volume pricing)
├── Latency p99: 800ms (multi-tenant noisy)
├── No VNet integration

Migration to Premium 1MU:
├── Cost: €600/mes (+€500 increase)
├── Latency p99: 50ms (-94%)
├── VNet integrated, Private Endpoint
├── Customer Lockbox compliance
└── ROI justified by SLA improvement + compliance value
```

**El más caro:**
```
Sin idempotency en payments processing:
├── Network blip
├── Duplicate "Charge €1000" message
├── Customer charged €2000
├── Refund issued, customer support cost
└── Damaged reputation

Cost: 1 incident = thousands of euros + brand damage
Fix: idempotency keys + dedup table = 50 lines of code
ROI: priceless (literally avoided business risk)
```

## Slide 32 — Decision tree: qué messaging usar

Cheat sheet final para elegir messaging correcto:

```
                    ¿Qué tipo de mensaje?
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
    Comando             Evento de             Streaming
    (do this)           negocio               (high volume)
        │                   │                   │
        ▼                   ▼                   ▼
    Service Bus         Event Grid o          Event Hubs o
    Queue               Service Bus Topic     Kafka

¿Necesitas FIFO ordering?
   SÍ → Sessions en SB
   NO → Standard queue

¿Mensaje > 256KB?
   SÍ → Service Bus Premium (100MB)
       O Claim Check pattern con blob storage
   NO → Cualquier queue

¿Simple workflow, low volume?
   SÍ → Storage Queue (cheap)
   NO → Service Bus

¿Multi-tenant SaaS con muchos suscribers?
   SÍ → Event Grid (escalable, 24M events/sec)
   NO → Service Bus Topic

¿Replay events?
   SÍ → Event Hubs (retains 7-90 days)
   NO → Service Bus (consumed once)

¿Push to webhooks?
   SÍ → Event Grid (HTTP push)
   NO → Service Bus (poll-based)

¿Pricing-sensitive, low volume?
   ├── Storage Queue: €0.36/M ops
   ├── Service Bus Std: €0.05/M ops
   ├── Event Grid: €0.60/M ops
   └── Event Hubs: capped at TU (€11/TU/mes)

¿VNet integration mandatory?
   SÍ → Service Bus Premium (only one with native VNet)
   NO → Cualquiera con Private Endpoint
```

|---|---|

Combinad Event Grid para eventos (notificaciones) con Service Bus para mensajes (trabajo). Logic Apps para integraciones SaaS sin código.

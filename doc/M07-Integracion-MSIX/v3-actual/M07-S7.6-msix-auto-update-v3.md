## Slide 2 — AppInstaller: el motor de auto-update
AppInstaller es el protocolo de Windows para gestionar instalación y actualización de paquetes MSIX. El archivo `.appinstaller` es un XML que indica a Windows: dónde descargar el paquete, con qué frecuencia comprobar actualizaciones, y qué hacer cuando hay una disponible.

A diferencia de ClickOnce (que comprueba al arrancar y bloquea), AppInstaller puede comprobar en background, descargar en background, y aplicar cuando el usuario cierra la app.

## Slide 3 — Configuración completa de UpdateSettings

```xml
<AppInstaller Uri="https://stventasprod.blob.core.windows.net/msix/MiApp.appinstaller"
              Version="2.4.1.0"
              xmlns="http://schemas.microsoft.com/appx/appinstaller/2018">

  <MainPackage Name="MiEmpresa.VentasDesktop" Version="2.4.1.0"
    Publisher="CN=MiEmpresa, O=MiOrg, C=ES" ProcessorArchitecture="x64"
    Uri="https://stventasprod.blob.core.windows.net/msix/MiApp_2.4.1.0_x64.msix" />

  <UpdateSettings>
    <!-- Comprobar al abrir la app (cada 1 hora max) -->
    <OnLaunch HoursBetweenUpdateChecks="1"
              ShowPrompt="true"
              UpdateBlocksActivation="false" />
    
    <!-- Comprobar en background (sin abrir la app) -->
    <AutomaticBackgroundTask />
    
    <!-- Permitir actualizar desde cualquier versión (no solo secuencial) -->
    <ForceUpdateFromAnyVersion>true</ForceUpdateFromAnyVersion>
  </UpdateSettings>
</AppInstaller>
```

**Opciones de UpdateSettings:**
- `ShowPrompt="true"`: Muestra diálogo al usuario: "Hay una actualización disponible"
- `UpdateBlocksActivation="true"`: La app NO abre hasta que se actualice (forzado)
- `HoursBetweenUpdateChecks`: Mínimo tiempo entre checks (evitar saturar el servidor)
- `AutomaticBackgroundTask`: Windows comprueba en segundo plano, sin que el usuario abra la app

## Slide 4 — Flujo de actualización

```
USUARIO ABRE LA APP
       ↓
Windows: ¿Han pasado >1h desde último check?
  │
  NO → Abrir la app normalmente
  │
  SÍ → Descargar .appinstaller → comparar versión
         │
         ¿Nueva versión disponible?
         │
         NO → Abrir la app normalmente
         │
         SÍ → ShowPrompt=true: "Hay una actualización. ¿Actualizar ahora?"
              │
              USUARIO dice SÍ → Descargar .msix → Instalar → Abrir nueva versión
              USUARIO dice NO → Abrir la versión actual (recordar más tarde)
              
              UpdateBlocksActivation=true → Actualizar OBLIGATORIAMENTE antes de abrir
```

## Slide 5 — Auto-update con endpoint autenticado

Si el .msix está en un endpoint que requiere autenticación (no público):

**Opción 1: SAS Token en la URL (más simple)**
```xml
<MainPackage Uri="https://stventasprod.blob.core.windows.net/msix/MiApp_2.4.1.0_x64.msix?sv=2023-01-03&se=2026-12-31&sr=b&sp=r&sig=xxx" />
```
Problema: el SAS token expira. Tendréis que regenerar y actualizar el .appinstaller periódicamente.

**Opción 2: Azure CDN con token de acceso**
Configurar Azure CDN con reglas de acceso que requieran un token en la URL o un header.

**Opción 3: API proxy con autenticación**
El .appinstaller apunta a una API vuestra que verifica la identidad del usuario y redirige al blob:
```xml
<MainPackage Uri="https://api-ventas.azurewebsites.net/api/msix/download/latest" />
```
```csharp
[Authorize]
[Function("DownloadMSIX")]
public async Task<IActionResult> Download(HttpRequest req)
{
    var blobUri = GenerateSASForBlob("MiApp_latest.msix", TimeSpan.FromMinutes(5));
    return new RedirectResult(blobUri.ToString());
}
```

**Opción 4: Blob Storage con acceso restringido por IP/VNet**
Si todos los usuarios están en la red corporativa, restringid el Storage Account por IP.

## Slide 6 — Actualización programática desde la app

Además de AppInstaller, podéis controlar las actualizaciones desde código:

```csharp
using Windows.Management.Deployment;

public class UpdateService
{
    public async Task<bool> CheckForUpdateAsync()
    {
        var pm = new PackageManager();
        var current = Package.Current;
        
        var result = await current.CheckUpdateAvailabilityAsync();
        
        switch (result.Availability)
        {
            case PackageUpdateAvailability.Available:
                // Hay actualización disponible (no obligatoria)
                return true;
            case PackageUpdateAvailability.Required:
                // Actualización obligatoria (ForceUpdate)
                return true;
            case PackageUpdateAvailability.NoUpdates:
                return false;
            case PackageUpdateAvailability.Error:
                // Error al comprobar
                return false;
        }
        return false;
    }
}
```

**API de PackageManager (más control):**
```csharp
// Registrar la actualización manualmente
var pm = new PackageManager();
var updateUri = new Uri("https://stventasprod.blob.core.windows.net/msix/MiApp.appinstaller");
var options = new AddPackageByAppInstallerOptions();
await pm.AddPackageByAppInstallerFileAsync(updateUri, options, pm.GetCurrentPackage());
```

## Slide 7 — Versionado: reglas de actualización

**Regla fundamental:** La versión nueva DEBE ser mayor que la actual.

```
Instalado: 2.4.1.0
Actualización: 2.4.2.0 → ✓ OK
Actualización: 2.5.0.0 → ✓ OK
Actualización: 2.4.1.0 → ✗ FALLA (misma versión)
Actualización: 2.3.0.0 → ✗ FALLA (versión anterior)
                         → ✓ OK si ForceUpdateFromAnyVersion=true
```

**Estrategia de versionado recomendada:**
```
Major.Minor.Build.0
  │     │     │
  │     │     └── Build number del pipeline (auto-incremental)
  │     └──────── Feature release (sprint/milestone)
  └────────────── Breaking change / major release
```

Ejemplo: `2.4.147.0` → versión 2.4, build 147.

## Slide 8 — Rollback: volver a una versión anterior

MSIX no tiene rollback automático integrado. Opciones:

**Opción 1: Publicar la versión anterior con número mayor**
```
v2.4.147.0 → tiene un bug
v2.4.148.0 → es el código de v2.4.146.0 con build number +1
```
Truco: el build number sube pero el código es el de la versión buena.

**Opción 2: Reinstalar manualmente**
```powershell
# Desinstalar la versión con bug
Remove-AppxPackage -Package "MiEmpresa.VentasDesktop_2.4.147.0_x64__abc123"

# Instalar la versión anterior (si la tenéis disponible)
Add-AppxPackage -Path .\MiApp_2.4.146.0_x64.msix
```

**Opción 3: Actualizar el .appinstaller para apuntar a la versión buena**
```xml
<!-- Cambiar la URI y versión para que apunte al .msix bueno -->
<MainPackage Version="2.4.148.0"
  Uri="https://stventasprod.blob.core.windows.net/msix/MiApp_2.4.146.0_x64.msix" />
```

**Recomendación:** Opción 1 (publicar la versión buena con build number +1). Es la más limpia y funciona con auto-update.

## Slide 9 — Notificar actualizaciones a los usuarios

Dentro de vuestra app WPF, informad al usuario cuando hay actualización:

```csharp
public partial class MainWindow : Window
{
    private readonly UpdateService _updates = new();

    private async void Window_Loaded(object sender, RoutedEventArgs e)
    {
        // Comprobar actualizaciones al arrancar
        var available = await _updates.CheckForUpdateAsync();
        
        if (available)
        {
            var result = MessageBox.Show(
                "Hay una nueva versión disponible. ¿Actualizar ahora?\n\n" +
                "La app se cerrará y se actualizará.",
                "Actualización disponible",
                MessageBoxButton.YesNo, MessageBoxImage.Information);
            
            if (result == MessageBoxResult.Yes)
            {
                // Cerrar la app — Windows aplicará la actualización al reabrir
                Application.Current.Shutdown();
            }
        }
        
        // Mostrar versión actual en la barra de estado
        var version = Package.Current.Id.Version;
        StatusBar.Text = $"v{version.Major}.{version.Minor}.{version.Build}";
    }
}
```

## Slide 11 — Differential updates: ahorro de ancho de banda

MSIX soporta actualizaciones diferenciales: solo descarga los bloques que cambiaron.

Si vuestra app pesa 100 MB y la nueva versión cambia 5 MB de código, Windows solo descarga ~5 MB (no los 100 MB completos).

**Requisitos:**
- El paquete anterior y el nuevo deben estar firmados con el mismo certificado
- El servidor debe soportar HTTP Range requests (Azure Blob Storage lo soporta)
- AppInstaller gestiona esto automáticamente

**Resultado práctico:** Actualizaciones mucho más rápidas y menos consumo de ancho de banda. Especialmente relevante para actualizaciones frecuentes en equipos con conexión limitada.

## Slide 13 — Forzar actualización obligatoria

Para actualizaciones de seguridad o bugs críticos:

```xml
<UpdateSettings>
  <OnLaunch HoursBetweenUpdateChecks="0"
            ShowPrompt="true"
            UpdateBlocksActivation="true" />  <!-- La app NO abre hasta actualizar -->
  <ForceUpdateFromAnyVersion>true</ForceUpdateFromAnyVersion>
</UpdateSettings>
```

Con `UpdateBlocksActivation="true"`: el usuario ve "Hay una actualización obligatoria" y no puede usar la app hasta que se instale. Usadlo solo para actualizaciones críticas — los usuarios se frustran si cada versión es "obligatoria".

## Slide 14 — Streaming install: usar la app mientras se descarga

MSIX soporta streaming install: el usuario puede empezar a usar la app antes de que termine de descargarse por completo.

```xml
<!-- ContentGroupMap.xml — definir qué se descarga primero -->
<ContentGroupMap xmlns="http://schemas.microsoft.com/msix/2018/45/contentgroupmap">
  <Automatic>
    <ContentGroup Name="Essential">
      <File Name="MiApp.exe" />
      <File Name="*.dll" />
    </ContentGroup>
  </Automatic>
  <ContentGroup Name="Assets">
    <File Name="Images\*" />
    <File Name="Data\*" />
  </ContentGroup>
</ContentGroupMap>
```

El grupo "Essential" se descarga primero (la app arranca). "Assets" se descarga en background.

## Slide 16 — Troubleshooting de auto-update

| Problema | Causa | Solución |
|---|---|---|
| No comprueba actualizaciones | HoursBetweenUpdateChecks > 0 y no ha pasado el tiempo | Reducir a 0 para testing |
| Descarga pero no instala | La app está abierta | Cerrar la app para que Windows aplique |
| "Package not found" al actualizar | URL del .msix incorrecta en .appinstaller | Verificar que la URL es accesible |
| Vuelve a pedir certificado | Certificado diferente en la nueva versión | Firmar con el MISMO certificado |
| No actualiza en background | AutomaticBackgroundTask no configurado | Añadir al .appinstaller |
| HTTP 403 al descargar | SAS token expirado o acceso denegado | Generar nuevo SAS o verificar permisos |

## Slide 17 — Patrón: Health check post-update

Verificar que la actualización se aplicó correctamente:

```csharp
public class StartupHealthCheck
{
    public async Task<bool> VerifyAsync()
    {
        var checks = new List<(string Name, Func<Task<bool>> Check)>
        {
            ("API connectivity", CheckApiAsync),
            ("Database access", CheckDbAsync),
            ("Configuration loaded", CheckConfigAsync),
            ("Auth working", CheckAuthAsync)
        };
        
        foreach (var (name, check) in checks)
        {
            try
            {
                var ok = await check();
                if (!ok)
                {
                    _logger.LogError("Health check failed: {Check}", name);
                    _telemetry.TrackEvent("UpdateHealthCheckFailed", 
                        new Dictionary<string, string> { ["check"] = name });
                    return false;
                }
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Health check exception: {Check}", name);
                return false;
            }
        }
        
        _telemetry.TrackEvent("UpdateHealthCheckPassed");
        return true;
    }
}
```

Si el health check falla post-update, notificad al equipo (puede ser un bug en la nueva versión).

## Slide 19 — winget update patterns + private sources

winget update workflow es similar a npm/apt — pero con MSIX:

```bash
# Update single app
winget upgrade Empresa.MyApp

# Update all apps
winget upgrade --all

# Update from specific source
winget upgrade Empresa.MyApp --source empresa-private

# Skip optional dependencies
winget upgrade Empresa.MyApp --skip-dependencies

# Force re-install (if corrupted)
winget upgrade Empresa.MyApp --force

# Pinning (don't auto-update)
winget pin add Empresa.MyApp --version 1.5.0
```

**Configurar private winget source:**
```bash
# Use Azure Container Registry como winget source
# (storage option en lugar of REST API)

# 1. Create ACR

  --name acrwingetempresa \
  --sku Standard \
  --admin-enabled true

# 2. Push manifests to ACR
oras push acrwingetempresa.azurecr.io/empresa.myapp:1.5.0 \

  ./manifests/Empresa.MyApp/1.5.0/Empresa.MyApp.locale.en-US.yaml \
  ./manifests/Empresa.MyApp/1.5.0/Empresa.MyApp.yaml

# 3. Add as winget source en client machines

  --type Microsoft.Rest \
  --arg "https://acrwingetempresa.azurecr.io/winget"
```

## Slide 20 — A/B rollout strategies (staged release)

Para apps críticas, no actualices al 100% inmediatamente:

```
Staged release pattern:
├── Phase 1: 5% (canary) — early adopters
├── Phase 2: 25% — wider validation
├── Phase 3: 50% — half of users
├── Phase 4: 100% — full rollout
└── Each phase: 24-48h monitoring before next
```

**Server-side staged distribution:**
```csharp
[ApiController]
[Route("api/[controller]")]
public class UpdateController : ControllerBase
{
    private readonly IFeatureManager _featureManager;
    
    [HttpGet("check")]
    public async Task<IActionResult> CheckForUpdate(
        [FromQuery] string currentVersion,
        [FromQuery] string userId,
        [FromQuery] string ringName = null)
    {
        // 1. Get available version
        var latestVersion = await _versionService.GetLatestAsync();
        
        // 2. Determine if user is in rollout group
        var rollout = await _versionService.GetRolloutAsync(latestVersion);
        if (!IsUserInRollout(userId, rollout))
        {
            return Ok(new { updateAvailable = false });
        }
        
        // 3. User is in rollout - return new version
        return Ok(new
        {
            updateAvailable = true,
            version = latestVersion,
            url = GetMsixUrl(latestVersion),
            mandatory = false
        });
    }
    
    private bool IsUserInRollout(string userId, RolloutInfo rollout)
    {
        // Determinant: deterministic but distributed
        var hash = ComputeStableHash(userId);
        var bucket = hash % 100;
        
        return bucket < rollout.PercentageRolledOut;
    }
    
    private int ComputeStableHash(string input)
    {
        // SHA256 hash for stable distribution
        var bytes = Encoding.UTF8.GetBytes(input);
        var hash = SHA256.HashData(bytes);
        return Math.Abs(BitConverter.ToInt32(hash, 0));
    }
}
```

**Update rings (Microsoft style):**
```
Define rings based on risk tolerance:

Insider Ring (1%):
├── Internal team
├── Receives daily/weekly builds
├── Mostly bugs OK
└── Tolerance: very high

Beta Ring (10%):
├── Power users, opt-in
├── Receives weekly stable builds
├── Some bugs OK
└── Tolerance: medium

Stable Ring (89%):
├── All users default
├── Receives validated builds
├── Bug-free expectation
└── Tolerance: very low
```

## Slide 22 — Differential updates con block hashing

Para apps grandes, differential updates ahorran bandwidth significativamente:

```
Traditional update:
└── Re-download full 100MB MSIX

Differential update:
├── BlockMap analysis: identify changed blocks
├── Download only changed blocks (~2-10%)
└── Apply patch to existing install
```

**BlockMap analysis:**
```xml
<!-- AppxBlockMap.xml inside MSIX -->
<BlockMap xmlns="http://schemas.microsoft.com/appx/2010/blockmap">
    <File Name="MyApp.exe" Size="65536" LfhSize="38">
        <Block Hash="abc123..." />
    </File>
    <File Name="resources\image1.png" Size="200000" LfhSize="50">
        <Block Hash="def456..." />
        <Block Hash="ghi789..." />
        <Block Hash="jkl012..." />  <!-- Each block 64KB -->
    </File>
    <!-- ... más archivos -->
</BlockMap>
```

**Cómo funciona el delta calculation:**
```csharp
public class DifferentialUpdateService
{
    public async Task<DeltaPackage> CalculateDeltaAsync(
        string installedPackagePath,
        string newPackagePath)
    {
        // 1. Read both BlockMaps
        var oldBlocks = ParseBlockMap(installedPackagePath);
        var newBlocks = ParseBlockMap(newPackagePath);
        
        // 2. Identify changed blocks
        var changedBlocks = newBlocks
            .Where(nb => !oldBlocks.Any(ob => ob.Hash == nb.Hash))
            .ToList();
        
        // 3. Build delta
        var delta = new DeltaPackage
        {
            FromVersion = GetVersionFromPackage(installedPackagePath),
            ToVersion = GetVersionFromPackage(newPackagePath),
            ChangedBlocks = changedBlocks,
            UnchangedBlockReferences = newBlocks
                .Where(nb => oldBlocks.Any(ob => ob.Hash == nb.Hash))
                .Select(nb => new BlockReference 
                { 
                    Hash = nb.Hash, 
                    SourceFile = oldBlocks.First(ob => ob.Hash == nb.Hash).FileName 
                })
                .ToList()
        };
        
        // 4. Calculate savings
        var totalSize = newBlocks.Sum(b => b.Size);
        var deltaSize = changedBlocks.Sum(b => b.Size);
        var savingsPercent = (1 - (double)deltaSize / totalSize) * 100;
        
        _logger.LogInformation(
            "Delta calculated: {savings}% savings ({size} MB → {deltaSize} MB)",
            savingsPercent, totalSize / 1_000_000, deltaSize / 1_000_000);
        
        return delta;
    }
}
```

**Server-side delta serving:**
```csharp
[ApiController]
[Route("api/[controller]")]
public class DistributionController : ControllerBase
{
    [HttpGet("delta")]
    public async Task<IActionResult> GetDelta(
        [FromQuery] string fromVersion,
        [FromQuery] string toVersion,
        [FromQuery] string architecture = "x64")
    {
        // Try to find pre-computed delta
        var cachedDelta = await _deltaCache.GetAsync($"{fromVersion}-{toVersion}-{architecture}");
        if (cachedDelta != null)
        {
            return File(cachedDelta, "application/octet-stream", 
                       $"MyApp-{fromVersion}-to-{toVersion}.delta");
        }
        
        // Compute delta on-the-fly
        var delta = await _deltaService.ComputeDeltaAsync(fromVersion, toVersion, architecture);
        
        // Cache for next request
        await _deltaCache.SetAsync($"{fromVersion}-{toVersion}-{architecture}", 
                                   delta, 
                                   TimeSpan.FromDays(7));
        
        return File(delta.ToStream(), "application/octet-stream",
                   $"MyApp-{fromVersion}-to-{toVersion}.delta");
    }
}
```

## Slide 24 — Anti-patterns en update strategies

```
❌ ANTI-PATTERN 1: Force-update en horarios laborables
   "User needs to install ahora mismo"
   ✅ Schedule outside business hours
   
❌ ANTI-PATTERN 2: Big-bang releases (100% al instante)
   "If it works en dev, it'll work en prod"
   ✅ Staged rollout 5% → 25% → 50% → 100%

❌ ANTI-PATTERN 3: No rollback plan
   "Update will succeed, no need backup"
   ✅ Always have rollback procedure tested

❌ ANTI-PATTERN 4: Updates sin telemetry
   "We'll know if there are issues"
   ✅ Crash reports, performance metrics, success rate

❌ ANTI-PATTERN 5: Mandatory updates con < 24h notice
   Forces user disruption
   ✅ 7-day rolling window con countdown

❌ ANTI-PATTERN 6: Skip testing en realistic environment
   "Tested en clean VM"
   ✅ Test con realistic user data, common configs

❌ ANTI-PATTERN 7: Sin migration plan para data
   New version expects new data format
   ✅ Migration logic en startup

❌ ANTI-PATTERN 8: Updates rompen plugins/extensions
   Third-party integrations break
   ✅ Maintain plugin compatibility o communicate breaking changes

❌ ANTI-PATTERN 9: No monitoring post-deployment
   "Released, done"
   ✅ Monitor for 7-30 days post-rollout

❌ ANTI-PATTERN 10: User-hostile messages
   "An update has been installed. Restart now."
   ✅ Friendly, choice-respecting communications
```

**El más caro:**
```
Cliente forzó update mandatory durante working hours:
├── 5000 users using app simultaneously
├── App restarts forced at 2pm
├── Users lose work in progress
├── Massive complaints + support tickets
├── Revenue lost: estimated €50K
├── User trust damaged
├── Better approach:
│   ├── Schedule restart outside hours
│   ├── Save user work automatically
│   ├── Show notification, allow defer
│   └── Restart only with user permission
└── Lesson: respect user time
```

```

├── Code signed (Microsoft cert)
├── Sandboxed (App Container)

Private winget:
├── Code signed (your cert)
├── Customizable security model
├── Internal users only
└── Best for: enterprise apps, restricted

AppInstaller (legacy):
├── Code signed (your cert)
├── Direct from your servers
├── Subject to deprecation
└── Best for: existing customers transition

Custom auto-updater:
├── Direct embedded en app
├── Programmatic control
├── Custom UX/UI
└── Best for: licensed software, B2B
```

**Dual maintenance approach:**

```
For each channel:
├── Same MSIX package (signed)
├── Different distribution metadata
├── Same auto-update mechanism
└── Telemetry differentiated

Pipeline:
├── Build: One MSIX
├── Sign: One signature
├── Distribute:
│   ├── Microsoft Store submission API
│   ├── winget-pkgs PR (public)
│   ├── ACR push (private winget)
│   ├── Azure Storage upload (AppInstaller)
│   └── Intune upload (enterprise)
```

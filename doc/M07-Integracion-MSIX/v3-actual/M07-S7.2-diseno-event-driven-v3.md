## Slide 2 — De monolito síncrono a event-driven
La mayoría de aplicaciones empiezan como monolitos síncronos: el usuario crea un pedido → la API valida → cobra → reserva inventario → envía email → devuelve 200 OK. Todo en una sola petición. Si el email tarda 5 segundos, el usuario espera 5 segundos.

En event-driven, la API crea el pedido y publica un evento "PedidoCreado". Otros servicios reaccionan al evento de forma asíncrona. La API devuelve 200 inmediatamente. El email se envía cuando toca, sin bloquear al usuario.

---

## Slide 3 — Monolito síncrono vs Event-driven

**Síncrono:**
```
POST /pedidos
  ├─ ValidarPedido() ──── 50ms
  ├─ CobrarTarjeta()  ─── 2000ms  ← API de banco
  ├─ ReservarStock()  ─── 100ms
  ├─ EnviarEmail()    ─── 3000ms  ← SMTP lento
  └─ Response 200     ─── 5150ms total  ← usuario espera TODO
```

**Event-driven:**
```
POST /pedidos
  ├─ ValidarPedido()  ─── 50ms
  ├─ GuardarEnDB()    ─── 20ms
  ├─ PublicarEvento()  ── 10ms
  └─ Response 202     ─── 80ms  ← usuario NO espera

Async (en paralelo):
  ├─ CobrarTarjeta()  ── 2000ms  (Service Bus → Function)
  ├─ ReservarStock()   ── 100ms   (Service Bus → Function)
  └─ EnviarEmail()    ── 3000ms  (Service Bus → Function)
```

**Resultado:** Latencia de 5 segundos → 80ms. Los procesos pesados ocurren en background.

---

## Slide 4 — Beneficios de event-driven

**1. Desacoplamiento:** El publicador no conoce a los consumidores. Podéis añadir un nuevo consumidor (ej: analytics) sin tocar el publicador.

**2. Escalabilidad independiente:** Si el email es lento, escalar la función de email no afecta a la API ni a facturación.

**3. Resiliencia:** Si el servicio de email cae, los mensajes esperan en la cola. Cuando vuelve, procesa el backlog.

**4. Latencia de usuario:** La API responde inmediatamente. Lo pesado ocurre async.

**5. Audit trail natural:** Los eventos son un log de todo lo que pasó.

---

## Slide 5 — Riesgos y trade-offs

**1. Complejidad:** Más piezas móviles (colas, topics, funciones). Más difícil de depurar.

**2. Consistencia eventual:** Los datos no están sincronizados inmediatamente. El pedido existe en la DB antes de que el cobro se procese.

**3. Orden:** Los eventos pueden llegar desordenados (sin sessions). A → B no garantiza que se procesen en ese orden.

**4. Idempotencia obligatoria:** Cada consumidor debe manejar duplicados.

**5. Observabilidad:** Trazar una petición a través de 5 funciones y 3 colas es más complejo que depurar un monolito.

**6. Testing:** Probar flujos async end-to-end es más difícil que probar un endpoint síncrono.

## Slide 6 — Patrones de event-driven architecture

**Patrón 1 — Event Notification:**
```
Evento: "PedidoCreado" (solo ID, sin datos)
Consumidor: lee el ID → consulta la API para obtener detalles
Ventaja: Eventos pequeños, desacoplado del schema
Desventaja: N consumidores × 1 query cada uno = N+1 queries
```

**Patrón 2 — Event-Carried State Transfer:**
```
Evento: "PedidoCreado" (con todos los datos del pedido)
Consumidor: usa los datos del evento directamente, sin consultar
Ventaja: Sin queries adicionales, consumidor autónomo
Desventaja: Eventos grandes, posible inconsistencia si los datos cambian
```

**Patrón 3 — Event Sourcing:**
```
En vez de guardar el estado actual, guarda todos los eventos:
PedidoCreado → ItemAñadido → ItemEliminado → PedidoConfirmado
El estado actual se reconstruye "replay-ando" los eventos.
Ventaja: Audit trail perfecto, time travel
Desventaja: Complejidad, eventual consistency
```

**Para vuestro equipo:** Empezad con Event-Carried State Transfer (patrón 2). Es el más práctico.

## Slide 7 — CQRS: Command Query Responsibility Segregation

Separar el modelo de escritura del de lectura:

```
WRITES (Commands)                    READS (Queries)
┌──────────────┐                    ┌──────────────┐
│ POST /pedidos│                    │ GET /pedidos  │
│ PUT /pedidos │                    │ GET /stats    │
└──────┬───────┘                    └──────┬───────┘
       ↓                                   ↓
┌──────────────┐   Change Feed     ┌──────────────┐
│ Cosmos DB    │──────────────────→│ Cosmos DB    │
│ (write model)│   Event / Trigger │ (read model)  │
│ Normalizado  │                   │ Desnormalizado│
│ por clienteId│                   │ por consulta  │
└──────────────┘                   └──────────────┘
```

**Write model:** Optimizado para validación y transacciones. Normalizado.
**Read model:** Optimizado para queries frecuentes. Desnormalizado, precalculado.

**Caso práctico:** El dashboard de ventas necesita "total por región, por día, top productos". En vez de hacer queries complejas en la DB transaccional, un trigger de Change Feed precalcula estas vistas y las guarda en un contenedor optimizado para lectura.

## Slide 8 — Saga Pattern: transacciones distribuidas

Cuando un flujo de negocio involucra múltiples servicios y necesitáis consistencia:

```
Crear pedido
  ├─ 1. Reservar inventario ──→ OK
  ├─ 2. Cobrar tarjeta ──────→ OK
  └─ 3. Programar envío ─────→ FALLA
      ↓
  COMPENSACIÓN:
  ├─ Revertir cobro (2)
  └─ Liberar inventario (1)
  └─ Marcar pedido como fallido
```

**Choreography Saga:** Cada servicio publica un evento al completar. El siguiente servicio reacciona al evento. Sin coordinador central.

**Orchestration Saga:** Un Durable Function orquesta los pasos. Si uno falla, ejecuta compensación. El Orchestrator es el coordinador.

**Recomendación:** Para flujos simples (3-4 pasos), choreography. Para flujos complejos (5+ pasos con lógica condicional), orchestration con Durable Functions.

## Slide 9 — Correlation ID: trazabilidad end-to-end

Cuando un evento pasa por 5 funciones y 3 colas, necesitáis rastrear todo el flujo:

```csharp
// Al crear el pedido, generar correlation ID
var correlationId = Activity.Current?.Id ?? Guid.NewGuid().ToString();

// Incluirlo en el mensaje de Service Bus
var msg = new ServiceBusMessage(body)
{
    CorrelationId = correlationId
};

// En cada función consumidora, incluir en los logs
[Function("ProcesarPedido")]
public async Task Procesar(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg, ILogger logger)
{
    using var scope = logger.BeginScope(new Dictionary<string, object>
    {
        ["CorrelationId"] = msg.CorrelationId,
        ["MessageId"] = msg.MessageId
    });
    
    logger.LogInformation("Procesando pedido...");
    
    // Si publicáis otro evento downstream, pasar el correlationId
    var nextMsg = new ServiceBusMessage(result)
    {
        CorrelationId = msg.CorrelationId  // Propagar
    };
}
```

**En Application Insights:** Buscad por CorrelationId para ver el trace completo del pedido a través de todos los servicios.

## Slide 11 — Outbox Pattern: publicar eventos de forma fiable

El problema: guardáis el pedido en la DB y publicáis un evento. Si la DB se guarda pero el evento falla, el sistema queda inconsistente.

```csharp
// MAL: puede fallar entre los dos pasos
await _db.Pedidos.AddAsync(pedido);
await _db.SaveChangesAsync();
// ← Si la app se cae AQUÍ, el pedido existe pero el evento no se publicó
await _serviceBus.SendAsync(new ServiceBusMessage(evento));

// BIEN: Outbox Pattern con Cosmos DB Change Feed
await _db.Pedidos.AddAsync(pedido);  // El pedido va a Cosmos DB
await _db.SaveChangesAsync();
// El Change Feed detecta el nuevo documento → Function publica el evento
// Garantía: si el documento existe, el Change Feed lo procesará
```

**Cosmos DB Change Feed es un Outbox natural.** Todo lo que se escribe en Cosmos aparece en el Change Feed. Si la función que publica eventos falla, el Change Feed reintenta. No se pierde ningún evento.

## Slide 13 — Cuándo usar event-driven y cuándo NO

**Usa event-driven cuando:**
- Múltiples servicios necesitan reaccionar al mismo evento
- El procesamiento es pesado y no puede bloquear al usuario
- Necesitáis escalar servicios independientemente
- La disponibilidad es más importante que la consistencia inmediata
- Tenéis un equipo que puede manejar la complejidad

**NO uses event-driven cuando:**
- Es un CRUD simple (un solo servicio, lectura/escritura directa)
- Necesitáis consistencia fuerte inmediata (transacción bancaria atómica)
- El equipo es pequeño y la complejidad no se justifica
- El volumen es bajo y un monolito funciona perfectamente

## Slide 15 — Event Sourcing: implementación con Cosmos DB

```csharp
public class EventStore
{
    private readonly Container _container;

    public async Task AppendAsync(string streamId, DomainEvent evento)
    {
        var entry = new EventEntry
        {
            Id = $"{streamId}-{evento.Version}",
            StreamId = streamId,
            Version = evento.Version,
            EventType = evento.GetType().Name,
            Data = JsonSerializer.Serialize(evento),
            Timestamp = DateTime.UtcNow
        };

        await _container.CreateItemAsync(entry, new PartitionKey(streamId));
    }

    public async Task<List<DomainEvent>> GetEventsAsync(string streamId)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.streamId = @id ORDER BY c.version")
            .WithParameter("@id", streamId);

        var events = new List<DomainEvent>();
        var iterator = _container.GetItemQueryIterator<EventEntry>(query,
            requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey(streamId) });

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync();
            events.AddRange(page.Select(e => DeserializeEvent(e)));
        }
        return events;
    }
}
```

## Slide 16 — Eventual Consistency: cómo gestionarlo

En un sistema event-driven, los datos no están sincronizados inmediatamente:

```
T=0ms:  API guarda pedido en Cosmos DB → responde 202 al usuario
T=50ms: Change Feed detecta el nuevo documento
T=100ms: Function publica evento en Event Grid
T=200ms: Function de email recibe el evento
T=3000ms: Email enviado al cliente

El usuario ve "Pedido creado" a T=0ms
Pero el email llega a T=3000ms
Y el dashboard de analytics se actualiza a T=5000ms
```

**Estrategias para el usuario:**
1. **Optimistic UI:** Mostrar "Pedido creado" inmediatamente, sin esperar confirmación de email
2. **Polling:** El frontend hace polling a un endpoint de estado cada 2 segundos
3. **WebSocket/SignalR:** Notificación push cuando el procesamiento completa
4. **Inbox pattern:** Guardar un "mensaje pendiente" que se resuelve cuando el proceso completa

## Slide 17 — Error handling en event-driven

Cuando un consumidor falla en un sistema event-driven:

```
Evento "PedidoCreado" publicado
  ↓
Consumidor A (email): ✓ OK
Consumidor B (inventario): ✗ FALLA
Consumidor C (factura): ✓ OK
```

**El fallo de B no afecta a A ni C.** Cada suscripción procesa independientemente.

**B reintenta automáticamente:** Service Bus reintenta el mensaje hasta maxDeliveryCount. Si sigue fallando → dead-letter.

**Compensación si B es crítico:** Si el inventario no se reserva, ¿qué pasa? Depende del negocio:
- Opción A: Alertar y reservar manualmente
- Opción B: Saga — si inventario falla, cancelar el pedido y revertir el cobro
- Opción C: Aceptar el riesgo — procesad más tarde desde la DLQ

## Slide 20 — Anti-patterns: lo que NO hacer

**1. Event chain demasiado larga:**
```
A → B → C → D → E → F → G
Si G falla, ¿cómo se entera A? La trazabilidad se pierde.
```
Máximo 3-4 saltos. Si necesitáis más, usad un Orchestrator (Durable Functions).

**2. Eventos como comandos disfrazados:**
```
// MAL: esto es un comando, no un evento
{ "type": "EnviarEmailAlCliente", "email": "pedro@..." }

// BIEN: esto es un evento
{ "type": "PedidoCreado", "pedidoId": "PED-001" }
// El consumidor DECIDE si enviar email o no
```

**3. Datos sensibles en eventos:**
```
// MAL: password en el evento
{ "type": "UsuarioCreado", "password": "abc123" }

// BIEN: solo referencia
{ "type": "UsuarioCreado", "userId": "USR-001" }
// El consumidor consulta la API si necesita más datos
```

**4. Sin versionado de eventos:**
Si cambiáis el schema de un evento, los consumidores antiguos rompen. Versionad.

## Slide 21 — Event Sourcing avanzado: snapshotting y proyecciones

Event Sourcing puro acumula eventos infinitamente — patterns para gestionarlo:

```
Problema sin snapshots:
├── Order tiene 5000 events después de 2 años
├── Para cargar Order: replay all 5000 events
├── Latencia: 2-5 segundos
└── Performance: 🚨

Solución: snapshots periódicos
├── Cada 100 events: tomar snapshot del estado
├── Cargar Order: read snapshot + replay últimos 50 events
├── Latencia: 50-100ms
└── Performance: ✅
```

**Implementación con Cosmos DB:**
```csharp
public class OrderRepository
{
    private readonly Container _eventsContainer;
    private readonly Container _snapshotsContainer;
    
    // Save event (append-only)
    public async Task AppendEventAsync(Guid aggregateId, IDomainEvent evt)
    {
        var sequenceNumber = await GetNextSequenceAsync(aggregateId);
        
        var eventDoc = new EventDocument
        {
            Id = Guid.NewGuid().ToString(),
            AggregateId = aggregateId.ToString(),
            SequenceNumber = sequenceNumber,
            EventType = evt.GetType().Name,
            EventData = JsonSerializer.Serialize(evt),
            Timestamp = DateTimeOffset.UtcNow
        };
        
        await _eventsContainer.CreateItemAsync(eventDoc, 
            new PartitionKey(aggregateId.ToString()));
        
        // Take snapshot every 100 events
        if (sequenceNumber % 100 == 0)
        {
            await TakeSnapshotAsync(aggregateId);
        }
    }
    
    // Load aggregate
    public async Task<Order> GetOrderAsync(Guid orderId)
    {
        // 1. Load latest snapshot (if exists)
        var snapshot = await GetLatestSnapshotAsync(orderId);
        
        Order order;
        long fromSequence = 0;
        
        if (snapshot != null)
        {
            order = JsonSerializer.Deserialize<Order>(snapshot.State);
            fromSequence = snapshot.SequenceNumber;
        }
        else
        {
            order = new Order { Id = orderId };
        }
        
        // 2. Replay events since snapshot
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.aggregateId = @id AND c.sequenceNumber > @seq ORDER BY c.sequenceNumber")
            .WithParameter("@id", orderId.ToString())
            .WithParameter("@seq", fromSequence);
        
        await foreach (var eventDoc in _eventsContainer.GetItemQueryIterator<EventDocument>(query)
                                                       .ReadAllAsync())
        {
            var evt = DeserializeEvent(eventDoc);
            order.Apply(evt);
        }
        
        return order;
    }
    
    private async Task TakeSnapshotAsync(Guid aggregateId)
    {
        var order = await GetOrderAsync(aggregateId);
        var lastSeq = order.Events.LastOrDefault()?.SequenceNumber ?? 0;
        
        var snapshot = new SnapshotDocument
        {
            Id = $"snapshot-{aggregateId}-{lastSeq}",
            AggregateId = aggregateId.ToString(),
            SequenceNumber = lastSeq,
            State = JsonSerializer.Serialize(order),
            CreatedAt = DateTimeOffset.UtcNow
        };
        
        await _snapshotsContainer.UpsertItemAsync(snapshot,
            new PartitionKey(aggregateId.ToString()));
    }
}
```

**Proyecciones para queries:**
```csharp
// Event Sourcing: writes via events
// Reads: optimized via projections (read models)

public class OrderProjectionHandler
{
    private readonly IOrderReadStore _readStore;
    
    // Listen to events, build read models
    public async Task HandleAsync(IDomainEvent evt)
    {
        switch (evt)
        {
            case OrderCreated created:
                await _readStore.UpsertAsync(new OrderSummary
                {
                    OrderId = created.OrderId,
                    CustomerId = created.CustomerId,
                    Total = 0,
                    Status = "Created",
                    CreatedAt = created.Timestamp
                });
                break;
                
            case OrderItemAdded itemAdded:
                var order = await _readStore.GetAsync(itemAdded.OrderId);
                order.Total += itemAdded.Price * itemAdded.Quantity;
                order.ItemCount++;
                await _readStore.UpsertAsync(order);
                break;
                
            case OrderShipped shipped:
                var order2 = await _readStore.GetAsync(shipped.OrderId);
                order2.Status = "Shipped";
                order2.ShippedAt = shipped.Timestamp;
                await _readStore.UpsertAsync(order2);
                break;
        }
    }
}
```

**Multiple projections desde mismos events:**
```
Events stream:
├── OrderCreated, OrderPaid, OrderShipped...
│
├──► Projection 1: OrderSummary (for customer dashboard)
├──► Projection 2: SalesReport (for analytics)
├──► Projection 3: CustomerInsights (for ML features)
└──► Projection 4: AuditTrail (for compliance)

Each projection optimized for its query pattern
```

**Replay scenarios:**
- Add new projection: replay all events from start, build read model
- Bug fix: replay events into corrected logic
- Compliance audit: full event history available
- A/B testing: replay events through alternate logic

**Trade-offs:**
- ✅ Audit trail completo (immutable)
- ✅ Time-travel queries
- ✅ Multiple read models from same events
- ❌ Complex (eventual consistency)
- ❌ Storage cost (events accumulate)
- ❌ Steep learning curve

## Slide 22 — Saga compensation patterns

Sagas distribuyen transacciones — cuando algo falla, hay que **compensar**:

```
Choreographed Saga:
├── Service A executes step
├── Publishes event
├── Service B executes next step on event
├── Publishes event
└── ... cada service decides qué hacer

Orchestrated Saga:
├── Orchestrator (Durable Function) coordina
├── Llama Service A
├── Llama Service B
├── Si algo falla: ejecuta compensations
```

**Orchestrated Saga con Durable Functions:**
```csharp
[Function(nameof(OrderProcessingSaga))]
public async Task OrderProcessingSaga(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var input = context.GetInput<OrderRequest>();
    var compensations = new List<Func<Task>>();
    
    try
    {
        // Step 1: Reserve inventory
        var reservationId = await context.CallActivityAsync<string>(
            nameof(ReserveInventory), input);
        compensations.Add(async () => await context.CallActivityAsync(
            nameof(ReleaseInventory), reservationId));
        
        // Step 2: Charge payment
        var paymentId = await context.CallActivityAsync<string>(
            nameof(ChargePayment), input);
        compensations.Add(async () => await context.CallActivityAsync(
            nameof(RefundPayment), paymentId));
        
        // Step 3: Schedule shipping
        var shipmentId = await context.CallActivityAsync<string>(
            nameof(ScheduleShipping), input);
        compensations.Add(async () => await context.CallActivityAsync(
            nameof(CancelShipping), shipmentId));
        
        // Step 4: Notify customer
        await context.CallActivityAsync(nameof(NotifyCustomer), input);
        
        // All success — commit
        await context.CallActivityAsync(nameof(MarkOrderComplete), input.OrderId);
    }
    catch (Exception)
    {
        // Compensate in reverse order
        for (int i = compensations.Count - 1; i >= 0; i--)
        {
            try
            {
                await compensations[i]();
            }
            catch (Exception compEx)
            {
                // Log compensation failure (manual intervention needed)
                _logger.LogError(compEx, "Compensation failed at step {step}", i);
            }
        }
        
        await context.CallActivityAsync(nameof(MarkOrderFailed), input.OrderId);
        throw;
    }
}
```

## Slide 23 — Microservices boundaries: cómo dividir bien

Wrong service boundaries = distributed monolith. Patterns for getting it right:

```
Bounded Context (DDD):
└── Cada microservicio = one bounded context
    ├── Owns its data
    ├── Owns its language (ubiquitous language)
    ├── Communicates via events
    └── No shared DB schemas
```

**Decomposition strategies:**

```
1. By business capability
   ├── Order Management Service
   ├── Customer Service
   ├── Inventory Service
   ├── Payment Service
   └── Shipping Service

2. By subdomain
   ├── Sales (orders, quotes)
   ├── Operations (fulfillment, logistics)
   ├── Finance (invoicing, payments)
   └── Support (tickets, refunds)

3. By data lifecycle
   ├── Hot data: real-time orders (Cosmos DB)
   ├── Warm data: recent transactions (SQL)
   └── Cold data: archive (ADLS)

4. By transactional boundaries
   ├── Atomic: same service
   ├── Eventually consistent: separate services
   └── Manual reconciliation OK: separate services
```

**Anti-pattern: Distributed Monolith**
```
Symptom: services that must deploy together
├── Service A change requires Service B change
├── Service A failure causes Service B failure
├── Tests require all services running
└── This is a monolith with extra steps

Causes:
├── Shared database (services querying same tables)
├── Synchronous calls (Service A waits for B waits for C)
├── Tight schema coupling
└── Premature decomposition

Fix:
├── Each service: own database
├── Async communication via events
├── Versioned event contracts
└── Strangler fig pattern para migrar
```

**Decomposing monolith — Strangler Fig:**
```
Initial state:
[Monolith with all features]

Step 1: Identify boundary (e.g., notifications)
├── Extract notification logic to new service
├── Monolith calls notification service via API
├── Both running in parallel

Step 2: Route reads to new service
├── New service has its own DB
├── Sync data with monolith DB
└── Reads progressively shift to new service

Step 3: Route writes
├── Writes go to new service
├── Sync back to monolith for backward compat
└── Monolith no longer modifies notifications data

Step 4: Cut cord
├── Monolith no longer needs notifications data
├── Remove notification logic from monolith
└── New service fully independent

Repeat for each boundary
```

**Right-sizing services:**
```
Too small (microservice mania):
├── Each function = its own service
├── Network overhead dominates
├── Operational complexity
└── Anti-pattern

Too big (modular monolith):
├── Services with too many responsibilities
├── Hard to scale independently
├── Tight coupling
└── Anti-pattern

Just right (signs):
├── Service can be understood by one team
├── Owns its data
├── Independent deploy lifecycle
├── Has clear API/event contract
└── Can fail without bringing down others
```

**Real-world example:**
```
E-commerce platform decomposition:

Bad:
├── ProductService (read products)
├── ProductCreatorService (create products)
├── ProductUpdaterService (update products)
├── ProductSearchService (search products)
└── ProductImageService (manage images)

Better:
├── ProductCatalog (CRUD products + search)
├── ProductImages (specialized for image storage/CDN)
└── If search becomes bottleneck → split later
```

**Communication patterns by relation:**
```
Same bounded context:
└── Direct method calls (inside service)

Different bounded context (related):
└── Async events

Different bounded context (unrelated):
└── Loose coupling via shared infrastructure (Event Grid)

External (third party):
└── Anti-corruption layer + sync API
```

## Slide 25 — Outbox pattern: reliability cross-service

Outbox pattern garantiza que eventos no se pierden si el servicio falla:

```
Sin Outbox:
├── 1. Update DB (commit)
├── 2. Publish event
└── 3. CRASH ANTES de step 2 → DB updated, no event ❌

Con Outbox:
├── 1. Update DB + Insert event en outbox table (mismo transaction)
├── 2. Worker periodic reads outbox, publishes events
├── 3. Worker marks event as published
└── 4. CRASH at any point → recovery garantizada ✅
```

**Implementación:**
```csharp
// Outbox table (same DB que tu domain)
public class OutboxEvent
{
    public Guid Id { get; set; }
    public string EventType { get; set; }
    public string Payload { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset? ProcessedAt { get; set; }
    public string TraceContext { get; set; }
}

// Repository — events stored TRANSACTIONALLY with domain changes
public class OrderRepository
{
    private readonly ApplicationDbContext _db;
    
    public async Task CreateOrderAsync(Order order, IEnumerable<IDomainEvent> events)
    {
        using var transaction = await _db.Database.BeginTransactionAsync();
        
        try
        {
            // 1. Save domain
            _db.Orders.Add(order);
            
            // 2. Save events to outbox (en mismo transaction)
            foreach (var evt in events)
            {
                _db.OutboxEvents.Add(new OutboxEvent
                {
                    Id = Guid.NewGuid(),
                    EventType = evt.GetType().Name,
                    Payload = JsonSerializer.Serialize(evt),
                    CreatedAt = DateTimeOffset.UtcNow,
                    TraceContext = Activity.Current?.Id
                });
            }
            
            await _db.SaveChangesAsync();
            await transaction.CommitAsync();
            
            // Domain + events saved atomically
        }
        catch
        {
            await transaction.RollbackAsync();
            throw;
        }
    }
}

// Background worker — publish events periodically
public class OutboxPublisher : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly ILogger<OutboxPublisher> _logger;
    
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                await ProcessOutboxBatchAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Error processing outbox");
            }
            
            await Task.Delay(TimeSpan.FromSeconds(5), ct);
        }
    }
    
    private async Task ProcessOutboxBatchAsync()
    {
        using var scope = _services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
        var sender = scope.ServiceProvider.GetRequiredService<ServiceBusSender>();
        
        // Get unpublished events
        var pending = await db.OutboxEvents
            .Where(e => e.ProcessedAt == null)
            .OrderBy(e => e.CreatedAt)
            .Take(100)
            .ToListAsync();
        
        foreach (var evt in pending)
        {
            try
            {
                var message = new ServiceBusMessage(evt.Payload)
                {
                    MessageId = evt.Id.ToString(),  // dedup key
                    ContentType = "application/json",
                    ApplicationProperties =
                    {
                        ["EventType"] = evt.EventType,
                        ["traceparent"] = evt.TraceContext
                    }
                };
                
                await sender.SendMessageAsync(message);
                
                // Mark processed
                evt.ProcessedAt = DateTimeOffset.UtcNow;
                await db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Failed to publish event {id}", evt.Id);
                // Will retry next iteration
            }
        }
    }
}
```

**Optimization: SQL change tracking + Service Bus:**
```sql
-- Enable Change Tracking en outbox table

  (CHANGE_RETENTION = 2 DAYS);

ALTER TABLE OutboxEvents ENABLE CHANGE_TRACKING;

-- Function trigger reacts to inserts
[Function(nameof(OutboxPublisher))]
public async Task OutboxPublisher(
    [SqlTrigger("[dbo].[OutboxEvents]", "SqlConnection")]
    IReadOnlyList<SqlChange<OutboxEvent>> changes,
    FunctionContext context)
{
    foreach (var change in changes.Where(c => c.Operation == SqlChangeOperation.Insert))
    {
        var evt = change.Item;
        await _sender.SendMessageAsync(new ServiceBusMessage(evt.Payload)
        {
            MessageId = evt.Id.ToString()
        });
        
        // Mark as processed
        await UpdateProcessedAtAsync(evt.Id);
    }
}
```

**Alternativas:**
- **Change Data Capture (CDC):** SQL CDC + Debezium for Cosmos DB Change Feed
- **Event Sourcing:** events ARE source of truth, no separate outbox
- **Transactional Outbox via Marten:** PostgreSQL with built-in support
- **MassTransit:** built-in outbox pattern

**Real-world impact:**
```
Sin outbox (typical):
├── 99.9% reliability (DB ok, but events fail occasionally)
├── 1 event lost per 1000
├── 1B events/year = 1M lost
└── Catastrophic in financial systems

Con outbox:
├── 99.99% reliability (transactional guarantee)
├── 1 event delayed ≠ lost
├── Recoverable at any time
└── Mission-critical safe
```

## Slide 26 — Idempotency en práctica

Idempotency = same operation N times has same result as 1 time:

```csharp
// Idempotency key pattern
public class IdempotentApiController : ControllerBase
{
    [HttpPost("orders")]
    public async Task<IActionResult> CreateOrder(
        [FromHeader(Name = "Idempotency-Key")] string idempotencyKey,
        [FromBody] OrderRequest request)
    {
        if (string.IsNullOrEmpty(idempotencyKey))
            return BadRequest("Idempotency-Key header required");
        
        // Check if we've seen this key before
        var existing = await _idempotencyStore.GetAsync(idempotencyKey);
        if (existing != null)
        {
            // Return cached response (avoid duplicate processing)
            return new ObjectResult(existing.ResponseBody)
            {
                StatusCode = existing.StatusCode
            };
        }
        
        // Reserve idempotency key (atomic with TTL)
        if (!await _idempotencyStore.TryReserveAsync(idempotencyKey, TimeSpan.FromHours(24)))
        {
            // Another request is processing same key
            return Conflict(new { error = "Duplicate request in progress" });
        }
        
        try
        {
            // Process request
            var order = await _orderService.CreateAsync(request);
            
            // Store response for future duplicate requests
            await _idempotencyStore.SaveResponseAsync(idempotencyKey, new IdempotentResponse
            {
                StatusCode = 201,
                ResponseBody = JsonSerializer.Serialize(order),
                CreatedAt = DateTimeOffset.UtcNow
            });
            
            return Created($"/orders/{order.Id}", order);
        }
        catch
        {
            // Release reservation on error
            await _idempotencyStore.ReleaseAsync(idempotencyKey);
            throw;
        }
    }
}
```

**Idempotency store en Redis:**
```csharp
public class RedisIdempotencyStore : IIdempotencyStore
{
    private readonly IDistributedCache _cache;
    
    public async Task<bool> TryReserveAsync(string key, TimeSpan ttl)
    {
        // Atomic reservation con SETNX
        return await _cache.SetAsync(
            $"idempotency:{key}",
            "RESERVED",
            new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = ttl })
            == true;  // returns true if key didn't exist
    }
    
    public async Task<IdempotentResponse> GetAsync(string key)
    {
        var data = await _cache.GetStringAsync($"idempotency:{key}");
        if (data == null || data == "RESERVED") return null;
        
        return JsonSerializer.Deserialize<IdempotentResponse>(data);
    }
    
    public async Task SaveResponseAsync(string key, IdempotentResponse response)
    {
        await _cache.SetStringAsync(
            $"idempotency:{key}",
            JsonSerializer.Serialize(response),
            new DistributedCacheEntryOptions 
            { 
                AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(24) 
            });
    }
}
```

**Different idempotency strategies:**

```
1. Idempotency Key (header-based)
   ├── Client provides unique ID per logical operation
   ├── Server caches response by key
   ├── Used by Stripe, AWS, etc.
   └── Best for: public APIs

2. Conditional updates (ETag / version)
   ├── Client provides version of expected resource
   ├── Server rejects if version mismatch
   └── Best for: optimistic locking

3. Domain-based dedup
   ├── Use business identifier (e.g., order_number)
   ├── Server checks if exists before creating
   └── Best for: business uniqueness rules

4. Message ID dedup (Service Bus)
   ├── MessageId set en client
   ├── SB built-in dedup window
   └── Best for: async messaging
```

**Idempotency en eventos:**

## Slide 29 — Cierre del submódulo
Event-driven architecture es potente pero no es gratis. Requiere pensar en eventual consistency, idempotencia, observabilidad y testing distribuido. Usadlo donde el desacoplamiento y la escala lo justifiquen. Para CRUD simple, un monolito es más simple y más fácil de mantener.

Lo esencial: Outbox con Change Feed, Saga para transacciones distribuidas, Correlation ID para trazabilidad, contract tests para compatibilidad, y no más de 3-4 saltos en event chains.

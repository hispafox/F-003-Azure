## Slide 2 — Estructura de un proyecto MSIX
Para empaquetar una app WPF/WinForms como MSIX, añadís un proyecto de empaquetado:

```
Solution

│   ├── MainWindow.xaml

│
└── MiApp.Package/           ← Proyecto de empaquetado MSIX (nuevo)
    ├── Package.appxmanifest  ← Identidad, versión, capabilities
    ├── Images/               ← Iconos y logos (múltiples tamaños)
    │   ├── LockScreenLogo.png

    │   ├── Square44x44Logo.png
    │   ├── Square150x150Logo.png
    │   └── StoreLogo.png
    └── MiApp.Package.wapproj
```

```bash

dotnet new msix -n MiApp.Package
# O en Visual Studio: Add → New Project → Windows Application Packaging Project
```

## Slide 3 — Package.appxmanifest: la identidad del paquete

```xml
<?xml version="1.0" encoding="utf-8"?>
<Package xmlns="http://schemas.microsoft.com/appx/manifest/foundation/windows10"
         xmlns:uap="http://schemas.microsoft.com/appx/manifest/uap/windows10"
         xmlns:rescap="http://schemas.microsoft.com/appx/manifest/foundation/windows10/restrictedcapabilities">

  <Identity Name="MiEmpresa.VentasDesktop"
            Publisher="CN=MiEmpresa, O=MiOrg, C=ES"
            Version="2.4.1.0"
            ProcessorArchitecture="x64" />

  <Properties>
    <DisplayName>Ventas Desktop</DisplayName>
    <PublisherDisplayName>MiEmpresa</PublisherDisplayName>
    <Description>Aplicación de gestión de ventas</Description>
    <Logo>Images\StoreLogo.png</Logo>
  </Properties>

  <Dependencies>
    <TargetDeviceFamily Name="Windows.Desktop" MinVersion="10.0.17763.0" MaxVersionTested="10.0.22621.0" />
  </Dependencies>

  <Resources>
    <Resource Language="es-ES" />
  </Resources>

  <Applications>
    <Application Id="VentasDesktop" Executable="MiApp.WPF.exe" EntryPoint="Windows.FullTrustApplication">
      <uap:VisualElements DisplayName="Ventas Desktop" Description="Gestión de ventas"
        Square150x150Logo="Images\Square150x150Logo.png" Square44x44Logo="Images\Square44x44Logo.png"
        BackgroundColor="transparent">
        <uap:DefaultTile Wide310x150Logo="Images\Wide310x150Logo.png" />
        <uap:SplashScreen Image="Images\SplashScreen.png" />
      </uap:VisualElements>
    </Application>
  </Applications>

  <Capabilities>
    <rescap:Capability Name="runFullTrust" />
    <Capability Name="internetClient" />
  </Capabilities>
</Package>
```

**Campos críticos:**
- **Identity Name:** Único globalmente. Formato: `Empresa.NombreApp`
- **Publisher:** DEBE coincidir exactamente con el Subject del certificado de firma
- **Version:** Formato `Major.Minor.Build.Revision` (siempre incremental)
- **Capabilities:** Qué puede hacer la app (internet, filesystem, bluetooth, etc.)

## Slide 5 — Firmar el paquete

**Sin firma, Windows rechaza la instalación.** Hay que firmar con un certificado de confianza.

```powershell
# Desarrollo: crear certificado self-signed
$cert = New-SelfSignedCertificate -Type Custom `
  -Subject "CN=MiEmpresa, O=MiOrg, C=ES" `
  -KeyUsage DigitalSignature `
  -FriendlyName "MSIX Dev Signing Cert" `
  -CertStoreLocation "Cert:\CurrentUser\My" `
  -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3", "2.5.29.19={text}")

# Exportar a PFX (para CI/CD)
$password = ConvertTo-SecureString -String "CertPassword123!" -Force -AsPlainText
Export-PfxCertificate -cert $cert -FilePath ./signing-cert.pfx -Password $password

# Firmar el paquete
& "C:\Program Files (x86)\Windows Kits\10\bin\10.0.22621.0\x64\signtool.exe" sign `
  /fd SHA256 /a /f signing-cert.pfx /p "CertPassword123!" `
  ./output/MiApp.Package_2.4.1.0_x64.msix
```

**En producción:** Usad un certificado de vuestra Enterprise CA (AD Certificate Services) o uno comprado a una CA pública (DigiCert, Sectigo). Almacenad la clave privada en Azure Key Vault.

## Slide 6 — Firmar con certificado de Azure Key Vault

```bash
# Firmar directamente desde Key Vault (la clave privada nunca sale del KV)
# Herramienta: Azure SignTool (NuGet: AzureSignTool)

dotnet tool install --global AzureSignTool

AzureSignTool sign \
  --azure-key-vault-url "https://kv-ventas-prod.vault.azure.net" \
  --azure-key-vault-certificate "msix-signing-cert" \
  --azure-key-vault-client-id "<app-id>" \
  --azure-key-vault-client-secret "<secret>" \
  --azure-key-vault-tenant-id "<tenant-id>" \
  --timestamp-rfc3161 "http://timestamp.digicert.com" \
  --file-digest sha256 \
  ./output/MiApp.Package_2.4.1.0_x64.msix
```

**Ventaja:** La clave privada del certificado NUNCA sale de Key Vault. La firma se hace usando el API de Key Vault. Incluso si el pipeline se compromete, la clave está segura.

## Slide 7 — Distribuir: AppInstaller

El archivo `.appinstaller` es un XML que define dónde descargar el MSIX y cómo auto-actualizarse:

```xml
<?xml version="1.0" encoding="utf-8"?>
<AppInstaller Uri="https://stventasprod.blob.core.windows.net/msix/MiApp.appinstaller"
              Version="2.4.1.0"
              xmlns="http://schemas.microsoft.com/appx/appinstaller/2018">

  <MainPackage Name="MiEmpresa.VentasDesktop"
               Version="2.4.1.0"
               Publisher="CN=MiEmpresa, O=MiOrg, C=ES"
               ProcessorArchitecture="x64"
               Uri="https://stventasprod.blob.core.windows.net/msix/MiApp_2.4.1.0_x64.msix" />

  <UpdateSettings>
    <OnLaunch HoursBetweenUpdateChecks="1" ShowPrompt="true"
              UpdateBlocksActivation="false" />
    <AutomaticBackgroundTask />
    <ForceUpdateFromAnyVersion>true</ForceUpdateFromAnyVersion>
  </UpdateSettings>
</AppInstaller>
```

**Flujo del usuario:**
1. Abre `https://stventasprod.blob.core.windows.net/msix/MiApp.appinstaller`
2. Windows muestra diálogo de instalación con logo de la empresa
3. Descarga el .msix y lo instala
4. Cada vez que abre la app, Windows comprueba si hay nueva versión
5. Si hay actualización, la descarga en background y la aplica

## Slide 8 — Hospedar en Azure Blob Storage

```bash
# Crear contenedor público para MSIX
az storage container create --name msix --account-name stventasprod --public-access blob

# Subir el .msix
az storage blob upload --account-name stventasprod --container-name msix \
  --file ./output/MiApp.Package_2.4.1.0_x64.msix \
  --name MiApp_2.4.1.0_x64.msix \
  --content-type "application/msix"

# Subir el .appinstaller
az storage blob upload --account-name stventasprod --container-name msix \
  --file ./MiApp.appinstaller \
  --name MiApp.appinstaller \
  --content-type "application/appinstaller"

# URL de instalación:
# https://stventasprod.blob.core.windows.net/msix/MiApp.appinstaller
```

**Con CDN:** Para distribución a muchos usuarios, poned un Azure CDN delante del Storage Account. Mejor rendimiento y menor coste de egress.

## Slide 9 — Sideloading: instalación sin Store

Para distribución corporativa (no pasa por Microsoft Store):

**Requisitos en el PC del usuario:**
1. Sideloading habilitado (Windows 10 2004+: habilitado por defecto)
2. Certificado de firma instalado como "Trusted People" o "Trusted Root"

```powershell
# Instalar certificado en el PC del usuario (una sola vez)
# Si usáis Enterprise CA: ya estará trusted vía Group Policy

# Si usáis self-signed (desarrollo):
Import-Certificate -FilePath .\MiApp.Package_2.4.1.0_x64.cer `
  -CertStoreLocation Cert:\LocalMachine\TrustedPeople

# Instalar el MSIX
Add-AppxPackage -Path .\MiApp.Package_2.4.1.0_x64.msix

# O con AppInstaller (preferido):
# El usuario simplemente abre la URL del .appinstaller
```

**Con Group Policy (para despliegue masivo):**
```
Computer Configuration → Admin Templates → Windows Components → App Package Deployment
→ "Allow all trusted apps to install" = Enabled
```

## Slide 11 — Pipeline CI/CD para MSIX

```yaml
# Azure DevOps Pipeline
trigger:
  branches: [main]

variables:
  version: '2.4.$(Build.BuildId).0'

stages:
- stage: Build
  jobs:
  - job: BuildMSIX
    pool:
      vmImage: 'windows-latest'
    steps:
    - task: UseDotNet@2
      inputs: { version: '8.x' }
    
    # Actualizar versión en manifest
    - powershell: |
        $manifest = Get-Content MiApp.Package/Package.appxmanifest
        $manifest = $manifest -replace 'Version="[\d.]+"', "Version=`"$(version)`""
        Set-Content MiApp.Package/Package.appxmanifest $manifest
    
    # Build
    - task: MSBuild@1
      inputs:
        solution: MiApp.Package.wapproj
        platform: x64
        configuration: Release
        msbuildArguments: '/p:AppxPackageDir="$(Build.ArtifactStagingDirectory)/" /p:UapAppxPackageBuildMode=SideLoadOnly'
    
    # Firmar con Key Vault
    - task: DotNetCoreCLI@2
      inputs:
        command: 'custom'
        custom: 'tool'
        arguments: 'install --global AzureSignTool'
    - script: |
        AzureSignTool sign \
          --azure-key-vault-url "$(KeyVaultUrl)" \
          --azure-key-vault-certificate "msix-signing-cert" \
          --azure-key-vault-managed-identity true \
          --timestamp-rfc3161 "http://timestamp.digicert.com" \
          --file-digest sha256 \
          "$(Build.ArtifactStagingDirectory)/*.msix"
    
    - publish: $(Build.ArtifactStagingDirectory)
      artifact: msix

- stage: Publish
  jobs:
  - deployment: PublishToBlob
    environment: msix-production
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureCLI@2
            inputs:
              azureSubscription: 'mi-conexion'
              scriptType: bash
              scriptLocation: inlineScript
              inlineScript: |
                az storage blob upload-batch \
                  --account-name stventasprod \
                  --destination msix \
                  --source $(Pipeline.Workspace)/msix \
                  --overwrite
                
                # Actualizar .appinstaller con nueva versión
                sed -i "s/Version=\"[0-9.]*\"/Version=\"$(version)\"/" appinstaller.xml
                az storage blob upload --account-name stventasprod --container-name msix \
                  --file appinstaller.xml --name MiApp.appinstaller --overwrite
```

## Slide 13 — Troubleshooting de MSIX

| Problema | Causa probable | Solución |
|----------|---------------|----------|
| "Publisher doesn't match" | Publisher en manifest ≠ Subject del certificado | Verificar que coinciden exactamente |
| "This app package is not signed" | No se firmó o firma inválida | Firmar con signtool/AzureSignTool |
| "Untrusted certificate" | Certificado no en Trusted People/Root | Instalar certificado o usar Enterprise CA |
| "Version must be higher" | Intentáis instalar versión ≤ actual | Incrementar versión |
| "Sideloading not enabled" | Policy de Windows bloquea sideloading | Habilitar en Settings o Group Policy |
| Ícono no aparece | Imágenes faltantes o tamaño incorrecto | Generar todos los tamaños requeridos |
| App se cierra inmediatamente | Crash al arrancar (dependencias, config) | Revisar Event Viewer → Application |

## Slide 14 — MSIX con .NET 8: single-file + self-contained

```xml
<!-- En el .csproj del proyecto WPF -->
<PropertyGroup>
  <PublishSingleFile>true</PublishSingleFile>
  <SelfContained>true</SelfContained>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>
</PropertyGroup>
```

Ventaja: el MSIX incluye el runtime .NET. El usuario no necesita tener .NET instalado. El paquete es más grande (~80 MB) pero la instalación es independiente.

Para apps internas donde controláis los PCs: framework-dependent (más ligero). Para distribución amplia: self-contained.

## Slide 17 — Modification Packages: personalización por empresa

Si distribuís la misma app a varias empresas con configuración diferente:

```xml
<!-- Modification Package: sobreescribe configuración sin tocar el MSIX principal -->
<Package xmlns="http://schemas.microsoft.com/appx/manifest/foundation/windows10"
         xmlns:uap4="http://schemas.microsoft.com/appx/manifest/uap/windows10/4">
  <Identity Name="MiEmpresa.VentasDesktop.ConfigEmpresaA" Version="1.0.0.0" />
  <Properties>
    <uap4:MainPackageDependency Name="MiEmpresa.VentasDesktop" />
  </Properties>
</Package>
```

El modification package contiene solo los archivos de configuración (appsettings, logos, etc.) que difieren. El paquete principal es el mismo para todos.

## Slide 18 — Shared Package Container: apps que comparten datos

Si tenéis múltiples apps MSIX que necesitan compartir archivos entre ellas:

```xml
<Properties>
  <uap15:SharedPackageContainer Name="VentasSuite">
    <uap15:PackageFamily Name="MiEmpresa.VentasDesktop_abc123" />
    <uap15:PackageFamily Name="MiEmpresa.VentasReporting_abc123" />
  </uap15:SharedPackageContainer>
</Properties>
```

Sin shared container, cada app MSIX tiene su filesystem aislado. Con él, las apps del mismo grupo pueden leer/escribir en un espacio compartido.

## Slide 20 — Event Viewer: diagnosticar problemas de instalación

Cuando una instalación MSIX falla, los detalles están en Event Viewer:

```
Event Viewer → Applications and Services Logs → Microsoft → Windows → AppxDeployment → Operational
```

Errores comunes:
- `0x80073CFB`: Publisher mismatch (certificado ≠ manifest)
- `0x80073CF9`: Dependency not found (VCLibs, etc.)
- `0x80073D05`: Can't update because app is running
- `0x80073CF3`: Package already exists with same or higher version

## Slide 21 — MSIX Core APIs: deeper management

Más allá del manifest, runtime APIs poderosas para gestión:

```csharp
using Windows.Management.Deployment;

public class MsixDeploymentManager
{
    private readonly PackageManager _pkgMgr = new();
    
    // Listar todos los packages instalados
    public IEnumerable<Package> GetInstalledPackages()
    {
        return _pkgMgr.FindPackages()
                      .Where(p => !p.IsResourcePackage 
                                  && !p.IsBundle 
                                  && !p.IsFramework);
    }
    
    // Install package
    public async Task InstallAsync(string msixUri)
    {
        var deployment = await _pkgMgr.AddPackageAsync(
            new Uri(msixUri),
            null,
            DeploymentOptions.None);
        
        if (deployment.IsRegistered)
        {
            Console.WriteLine($"Installed: {deployment.PackageFullName}");
        }
    }
    
    // Update con downgrade allowed (rollback)
    public async Task UpdateAsync(string msixUri, bool allowDowngrade = false)
    {
        var options = DeploymentOptions.ForceApplicationShutdown;
        if (allowDowngrade) options |= DeploymentOptions.ForceTargetApplicationShutdown;
        
        var deployment = await _pkgMgr.UpdatePackageAsync(
            new Uri(msixUri), 
            null, 
            options);
    }
    
    // Remove package
    public async Task UninstallAsync(string packageFullName)
    {
        await _pkgMgr.RemovePackageAsync(packageFullName, RemovalOptions.None);
    }
    
    // Check signing info
    public PackageSignatureKind GetSignatureType(Package pkg)
    {
        return pkg.SignatureKind;
        // Store, Enterprise, Developer, Unsigned, etc.
    }
}
```

**PackageDeploymentManager (Windows 11+):**
```csharp
// Newer API con better progress reporting

var deploymentManager = PackageDeploymentManager.GetDefault();

var pkgSet = new PackageSet
{
    PackageSetItems = 
    {
        new PackageSetItem { PackageUri = new Uri("https://app.example.com/MyApp.msix") },
        new PackageSetItem { PackageUri = new Uri("https://app.example.com/MyAppFramework.msix") }
    }
};

// Install set with progress
var operation = deploymentManager.AddPackageSetAsync(pkgSet, null);

operation.Progress = (op, progress) =>
{
    Console.WriteLine($"Progress: {progress.Progress}%");
    if (progress.Status == PackageDeploymentProgressStatus.PackageInstalling)
    {
        Console.WriteLine($"  Installing {progress.PackageFullName}");
    }
};

var result = await operation;
if (result.Status == PackageDeploymentStatus.CompletedSuccess)
{
    Console.WriteLine("All packages installed!");
}
```

## Slide 22 — VFS (Virtual File System) deep-dive

MSIX usa VFS para hacer packages compatibles con Win32 paths:

```
Tu app espera archivos en:
├── C:\Program Files\MyCompany\MyApp\
├── C:\ProgramData\MyApp\
├── %APPDATA%\MyApp\
└── C:\Windows\System32\

MSIX redirige automáticamente vía VFS:
├── VFS\ProgramFilesX64\MyCompany\MyApp\ → C:\Program Files\...
├── VFS\AppData\MyApp\ → %APPDATA%\MyApp\
└── VFS\SystemX86\ → C:\Windows\System32
```

**VFS structure en package:**
```
MyApp.msix contents:
├── AppxManifest.xml
├── MyApp.exe
├── (resources, etc.)
└── VFS\
    ├── AppData\Roaming\MyApp\config.xml
    ├── AppData\Local\MyApp\cache\
    ├── ProgramFilesX64\MyCompany\Shared\library.dll
    ├── ProgramFilesX86\Common Files\Shared\runtime.dll
    ├── SystemX64\someSystemDll.dll
    ├── Windows\Fonts\customfont.ttf
    └── Local AppData\MyApp\settings.json
```

**VFS folder mapping table:**
```
VFS Path                    Maps to
───────────────────────────────────────────────
ProgramFilesX64             C:\Program Files
ProgramFilesX86             C:\Program Files (x86)
SystemX64                   C:\Windows\System32
SystemX86                   C:\Windows\SysWOW64
Common Programs             C:\ProgramData\Microsoft\Windows\Start Menu\Programs
Local AppData               %LOCALAPPDATA%
AppData                     %APPDATA%
Local AppData Low           %LOCALAPPDATA%Low
```

**Migration legacy app (PSF + VFS):**
```json
// config.json en MSIX package
{
  "applications": [{
    "id": "MyApp",
    "executable": "VFS\\ProgramFilesX64\\MyCompany\\MyApp\\app.exe",
    "workingDirectory": "VFS\\ProgramFilesX64\\MyCompany\\MyApp"
  }],
  "processes": [{
    "executable": ".*",
    "fixups": [{
      "dll": "FileRedirectionFixup.dll",
      "config": {
        "redirectedPaths": {
          "packageRelative": [{
            "base": "VFS\\AppData\\MyApp",
            "patterns": [".*\\.ini", ".*\\.config"]
          }]
        }
      }
    }, {
      "dll": "RegLegacyFixups.dll",
      "config": {
        "remediation": [{
          "type": "ModifyKeyAccess",
          "hive": "HKCU",

```

**BlockMap (para optimization):**
```
BlockMap.xml inside MSIX:
├── Lista de blocks (chunks de 64KB típicamente)
├── Hash SHA256 por block
├── Used para differential updates
└── Auto-generated por makeappx

Differential update funciona así:
├── Server has BlockMap of new package
├── Client sends BlockMap of installed package
├── Server returns ONLY changed blocks
└── Bandwidth saved: 60-95% típico
```

```csharp
public async Task<bool> HasCameraAccessAsync()
{
    var camera = AppCapability.Create("webcam");
    var status = camera.CheckAccess();
    
    if (status == AppCapabilityAccessStatus.Allowed)
    {
        return true;
```

## Slide 25 — Bundle creation (msixbundle): multi-arch

MSIX bundles unen múltiples arquitecturas en un solo archivo:

```
Architectures soportadas (2026):
├── x86 (32-bit, legacy)
├── x64 (most common)
├── arm64 (Surface Pro, ARM laptops)
└── neutral (no arch-specific code)

├── MyApp_x64.msix
├── MyApp_arm64.msix

├── MyApp.msixbundle (contains all)
└── Windows auto-selects correct arch
```

**Build multi-arch:**
```bash
# 1. Build cada arquitectura separadamente
dotnet publish -r win-x64 -c Release \
  -p:UapAppxPackageBuildMode=SideloadOnly \

dotnet publish -r win-arm64 -c Release \
  -p:UapAppxPackageBuildMode=SideloadOnly \
  -p:AppxPackageDir=./packages/arm64/

# 2. Merge en bundle
makeappx bundle /d ./packages /p MyApp.msixbundle

# Result: MyApp.msixbundle (~150MB con both archs)

# 3. Sign bundle
SignTool sign /fd SHA256 /a /f cert.pfx /p $PASSWORD MyApp.msixbundle
```

## Slide 28 — Anti-patterns en MSIX packaging

Errores comunes que veo en producción:

```
❌ ANTI-PATTERN 1: Hardcoded paths C:\Program Files
   File.WriteAllText(@"C:\Program Files\MyApp\config.ini")
   ✅ ApplicationData.Current.LocalFolder.Path

❌ ANTI-PATTERN 2: Direct registry HKLM writes
   Registry.LocalMachine.CreateSubKey(...)
   ✅ ApplicationData.Current.LocalSettings

❌ ANTI-PATTERN 3: Skipping signing en dev
   "We'll sign en production" → tests fall en signed scenarios
   ✅ Always sign con dev cert

❌ ANTI-PATTERN 4: Single-arch packages para distribution
   Only x64.msix → arm64 users can't install
   ✅ Bundle x64+arm64 con .msixbundle

❌ ANTI-PATTERN 5: Invalid manifest changes
   Modify manifest sin testing
   ✅ Always rebuild + test on clean VM

❌ ANTI-PATTERN 6: Including unnecessary files
   100MB package porque unused libraries incluidas
   ✅ Trim unused references

❌ ANTI-PATTERN 7: Custom installers en MSIX
   "Run setup.exe inside MSIX"
   ✅ MSIX itself IS the installer

❌ ANTI-PATTERN 8: Sharing data via ProgramData
   Apps esperan compartir data en C:\ProgramData
   ✅ Use Shared Package Container o explicit file picker

❌ ANTI-PATTERN 9: Failing first launch porque cert untrusted
   Self-signed dev cert → SmartScreen blocks
   ✅ Use EV cert o Microsoft Trusted Signing

❌ ANTI-PATTERN 10: No update strategy planned
   Ship MSIX 1.0, then how update?
   ✅ Plan AppInstaller/winget desde día 1

❌ ANTI-PATTERN 11: Ignoring App Container restrictions
   Code que assumes full filesystem access
   ✅ Test en restricted environment

❌ ANTI-PATTERN 12: Sin telemetry de installs
   Don't know if installs failing
   ✅ App Insights integration desde primer día
```

**El más caro:**
```
Cliente con app que escribe en HKLM:
├── Worked en MSI installer
├── MSIX install: silent failure (HKLM blocked)
├── User: app installs but doesn't work
├── Support tickets: massive
├── Fix: rewrite to use ApplicationData.Settings
├── Time: 3 weeks development
└── Cost: lost users + support overhead
```

**Mejor diagnóstico:**

```yaml
name: MSIX Build & Deploy

on:
  push:
    tags: ['v*.*.*']

jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '9.0.x'
      
      - name: Restore + Build x64
        run: dotnet publish ./src/MyApp/MyApp.csproj 
              -c Release 
              -r win-x64 
              -p:PublishSingleFile=true
              -p:SelfContained=true
              -o ./publish/x64
      
      - name: Restore + Build arm64
        run: dotnet publish ./src/MyApp/MyApp.csproj 
              -c Release 
              -r win-arm64 
              -p:PublishSingleFile=true
              -p:SelfContained=true
              -o ./publish/arm64
      
      - name: Build MSIX x64
        run: msbuild ./src/MyApp.Package/MyApp.Package.wapproj 
              /p:Configuration=Release 
              /p:Platform=x64
              /p:UapAppxPackageBuildMode=SideloadOnly
      
      - name: Build MSIX arm64
        run: msbuild ./src/MyApp.Package/MyApp.Package.wapproj 
              /p:Configuration=Release 
              /p:Platform=arm64
              /p:UapAppxPackageBuildMode=SideloadOnly
      
      - name: Create bundle
        run: |
          New-Item -ItemType Directory -Force -Path ./bundle
          Copy-Item ./AppPackages/*.msix ./bundle/
          & 'C:\Program Files (x86)\Windows Kits\10\bin\10.0.22621.0\x64\makeappx.exe' bundle 
            /d ./bundle /p ./MyApp.msixbundle
      
      - name: Sign with Trusted Signing
        uses: azure/trusted-signing-action@v0
        with:
          azure-tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          azure-client-id: ${{ secrets.AZURE_CLIENT_ID }}
          azure-client-secret: ${{ secrets.AZURE_CLIENT_SECRET }}
          endpoint: https://weu.codesigning.azure.net
          trusted-signing-account-name: ts-empresa
          certificate-profile-name: MSIX-Profile
          files: MyApp.msixbundle
      
      - name: Upload to Azure Storage
        uses: azure/CLI@v1
        with:
          inlineScript: |
            az storage blob upload \
              --container distribution \
              --account-name stempresa \
              --file MyApp.msixbundle \
              --name "MyApp_${{ github.ref_name }}.msixbundle" \
              --overwrite
      
      - name: Update AppInstaller manifest
        run: |
          ./scripts/update-appinstaller.sh ${{ github.ref_name }}
      
      - name: Submit to winget
        run: |
          # Trigger winget-pkgs PR via wingetcreate
          wingetcreate update --version ${{ github.ref_name }} \
            --urls "https://stempresa.blob.core.windows.net/distribution/MyApp_${{ github.ref_name }}.msixbundle" \
            Empresa.MyApp
```

## Slide 30 — Cierre del submódulo
MSIX packaging tiene más opciones de las que parece: self-contained, trimming, modification packages, shared containers. Pero para el 90% de los casos, un packaging project estándar + firma + Blob Storage es suficiente.

Lo importante: firma correcta (Publisher = Subject del cert), versión siempre incremental, y pipeline CI/CD para automatizar todo el flujo.

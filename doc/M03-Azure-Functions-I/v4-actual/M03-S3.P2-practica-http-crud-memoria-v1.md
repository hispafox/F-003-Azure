## Slide 2 — Qué vais a construir

Una Azure Function con HTTP Triggers que implementan un CRUD completo (Create/Read/Update/Delete) **manteniendo los datos en memoria**. Sin Cosmos, sin Storage, sin emuladores complicados.

**El recorrido:**

```
1. Crear el proyecto Functions (.NET 8 isolated)
2. Implementar 5 endpoints HTTP en una clase
3. Probar en local con func start
4. Desplegar a Azure (Consumption Plan)
5. Probar la API real
6. Configurar logging básico
7. Limpiar recursos
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ Timer Trigger (eso es la práctica principal M03-S3.P)
- ❌ Blob Trigger ni Cosmos Trigger (también principal)
- ❌ Persistencia real en BBDD (eso es M05)
- ❌ Pipeline CI/CD (M08)
- ❌ Auth ni Key Vault (M06)

**Por qué empezar por HTTP CRUD en memoria:**

- ✅ Solo UN tipo de trigger → menos confusión
- ✅ Sin emuladores → arranca con un solo comando
- ✅ Cualquier alumno entiende un CRUD (modelo mental conocido)
- ✅ Aprenden el ciclo Functions sin preocuparse por persistencia

**Tiempo estimado:** 45-60 minutos.

**Coste real:** **0€** (Consumption Plan, primeras 1M ejecuciones gratis).

## Slide 5 — Paso 2: Crear el modelo y storage en memoria

Antes de las funciones, definimos qué van a manejar. Un modelo simple `Producto` y una "BBDD" en memoria:

```bash
# Crear archivo del modelo
cat > Producto.cs << 'EOF'
namespace MiPrimeraFunction;

public record Producto(
    string Id,
    string Nombre,
    decimal Precio,
    int Stock);
EOF

# Crear archivo del repositorio en memoria
cat > ProductosRepository.cs << 'EOF'
using System.Collections.Concurrent;

namespace MiPrimeraFunction;

public interface IProductosRepository
{
    IReadOnlyList<Producto> GetAll();
    Producto? GetById(string id);
    Producto Create(Producto producto);
    Producto? Update(string id, Producto producto);
    bool Delete(string id);
}

public class ProductosRepository : IProductosRepository
{
    // ConcurrentDictionary porque Functions puede ejecutar varios threads
    private readonly ConcurrentDictionary<string, Producto> _productos = new();

    public ProductosRepository()
    {
        // Datos de ejemplo al arrancar
        Seed();
    }

    private void Seed()
    {
        var ejemplos = new[]
        {
            new Producto("p001", "Laptop Dell", 1299.00m, 5),
            new Producto("p002", "Monitor 27\"", 349.00m, 12),
            new Producto("p003", "Teclado mecánico", 89.90m, 30)
        };
        foreach (var p in ejemplos) _productos[p.Id] = p;
    }

    public IReadOnlyList<Producto> GetAll() => _productos.Values.ToList();

    public Producto? GetById(string id) =>
        _productos.TryGetValue(id, out var p) ? p : null;

    public Producto Create(Producto producto)
    {
        var nuevo = producto with { Id = $"p{Guid.NewGuid().ToString("N")[..6]}" };
        _productos[nuevo.Id] = nuevo;
        return nuevo;
    }

    public Producto? Update(string id, Producto producto)
    {
        if (!_productos.ContainsKey(id)) return null;
        var actualizado = producto with { Id = id };
        _productos[id] = actualizado;
        return actualizado;
    }

    public bool Delete(string id) => _productos.TryRemove(id, out _);
}
EOF
```

**Importante: `static` o `singleton`**

Como queremos que los datos persistan entre invocaciones (mientras la function está caliente), registraremos el repositorio como **Singleton** en DI.

**Limitación a saber:** los datos se pierden cuando:
- La instancia se reinicia
- Cambia de instancia (escalado)
- Pasa el tiempo de inactividad y la function se duerme

Para esta práctica está perfecto. Para producción real → usar Cosmos / SQL.

## Slide 6 — Paso 3: Registrar el servicio en DI

Modificad `Program.cs` para inyectar el repositorio:

```bash
cat > Program.cs << 'EOF'
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using MiPrimeraFunction;

var builder = FunctionsApplication.CreateBuilder(args);

builder.ConfigureFunctionsWebApplication();

// El repositorio en memoria es Singleton → único en toda la app
builder.Services.AddSingleton<IProductosRepository, ProductosRepository>();

builder.Build().Run();
EOF
```

**Por qué Singleton:**

```
Singleton:  una única instancia compartida
            → datos persisten entre invocaciones ✓
            → necesario para nuestro repo en memoria

Scoped:     una instancia por request HTTP
            → datos se pierden entre requests ✗
            → no nos sirve

Transient:  nueva instancia cada inyección
            → datos se pierden constantemente ✗
            → no nos sirve
```

## Slide 7 — Paso 4: Crear la function con los 5 endpoints

Ahora la function principal con todos los endpoints CRUD:

```bash
cat > ProductosFunctions.cs << 'EOF'
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Mvc;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;
using System.Text.Json;

namespace MiPrimeraFunction;

public class ProductosFunctions
{
    private readonly IProductosRepository _repo;
    private readonly ILogger<ProductosFunctions> _logger;

    public ProductosFunctions(
        IProductosRepository repo,
        ILogger<ProductosFunctions> logger)
    {
        _repo = repo;
        _logger = logger;
    }

    // GET /api/productos — listar todos
    [Function("ListarProductos")]
    public IActionResult Listar(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "productos")]
        HttpRequest req)
    {
        _logger.LogInformation("Listando todos los productos");
        var productos = _repo.GetAll();
        return new OkObjectResult(new
        {
            total = productos.Count,
            productos
        });
    }

    // GET /api/productos/{id} — obtener uno
    [Function("ObtenerProducto")]
    public IActionResult Obtener(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "productos/{id}")]
        HttpRequest req,
        string id)
    {
        _logger.LogInformation("Obteniendo producto {Id}", id);
        var producto = _repo.GetById(id);
        return producto is null
            ? new NotFoundObjectResult(new { error = $"Producto {id} no encontrado" })
            : new OkObjectResult(producto);
    }

    // POST /api/productos — crear nuevo
    [Function("CrearProducto")]
    public async Task<IActionResult> Crear(
        [HttpTrigger(AuthorizationLevel.Anonymous, "post", Route = "productos")]
        HttpRequest req)
    {
        var producto = await JsonSerializer.DeserializeAsync<Producto>(
            req.Body,
            new JsonSerializerOptions { PropertyNameCaseInsensitive = true });

        if (producto is null || string.IsNullOrWhiteSpace(producto.Nombre))
        {
            return new BadRequestObjectResult(new { error = "Nombre obligatorio" });
        }

        var nuevo = _repo.Create(producto);
        _logger.LogInformation("Producto creado: {Id} - {Nombre}", nuevo.Id, nuevo.Nombre);
        return new CreatedResult($"/api/productos/{nuevo.Id}", nuevo);
    }

    // PUT /api/productos/{id} — actualizar
    [Function("ActualizarProducto")]
    public async Task<IActionResult> Actualizar(
        [HttpTrigger(AuthorizationLevel.Anonymous, "put", Route = "productos/{id}")]
        HttpRequest req,
        string id)
    {
        var producto = await JsonSerializer.DeserializeAsync<Producto>(
            req.Body,
            new JsonSerializerOptions { PropertyNameCaseInsensitive = true });

        if (producto is null) return new BadRequestObjectResult(new { error = "Body inválido" });

        var actualizado = _repo.Update(id, producto);
        if (actualizado is null)
        {
            return new NotFoundObjectResult(new { error = $"Producto {id} no encontrado" });
        }

        _logger.LogInformation("Producto actualizado: {Id}", id);
        return new OkObjectResult(actualizado);
    }

    // DELETE /api/productos/{id} — borrar
    [Function("BorrarProducto")]
    public IActionResult Borrar(
        [HttpTrigger(AuthorizationLevel.Anonymous, "delete", Route = "productos/{id}")]
        HttpRequest req,
        string id)
    {
        if (!_repo.Delete(id))
        {
            return new NotFoundObjectResult(new { error = $"Producto {id} no encontrado" });
        }

        _logger.LogInformation("Producto borrado: {Id}", id);
        return new NoContentResult();  // 204
    }
}
EOF
```

**Compilar:**

```bash
dotnet build
```

Esperado: build correcto, sin errores.

## Slide 9 — Troubleshooting local

Errores comunes durante el desarrollo y cómo resolverlos:

**1. "Could not load file or assembly..."**

```
Causa: paquetes NuGet desactualizados o conflicto
Fix:
  dotnet clean
  dotnet restore
  dotnet build
```

**2. "Port 7071 is already in use"**

```
Causa: otra function o app usando ese puerto
Fix opción A: matar el proceso anterior
  lsof -i :7071  # ver el PID
  kill <PID>

Fix opción B: usar otro puerto
  func start --port 7072
```

**3. "Functions:" aparece vacío**

```
Causa: no se detectó ningún [Function] en el código
Posibles motivos:
- Falta atributo [Function("Nombre")]
- Build falló sin que os dieseis cuenta
- El archivo .cs no está en el proyecto

Fix:
  dotnet build  # ver errores
  ls *.cs       # confirmar archivos presentes
```

**4. "Curl devuelve 404 Not Found"**

```
Causa común: ruta incorrecta
Verificar:
- ¿Está incluido /api/ en la URL?
- Default route prefix es "api" (en host.json)
- Si quitáis el prefix: añadir "extensions": { "http": { "routePrefix": "" } } a host.json

Otra causa:
- El método HTTP no coincide (POST vs GET, etc.)
```

**5. "JSON deserialization error"**

```
Causa: body del request no coincide con el modelo
Fix:
- Verificar que enviáis Content-Type: application/json
- Los nombres de campo coinciden (case-insensitive con PropertyNameCaseInsensitive)
- record types necesitan los nombres exactos en orden o nombre

Tip pro: añadir try/catch en deserialize y devolver mensaje claro
```

**6. "Logs no aparecen en la terminal"**

```
Causa: nivel de log filtrado
Verificar host.json:
  "logLevel": {
    "default": "Information",
    "Function": "Information"
  }

Si el nivel es Warning o más alto, los Information no se ven.
```

## Slide 10 — Paso 6: Crear recursos en Azure

Vamos a desplegar a Azure. Primero los recursos necesarios:

```bash
# Variables (cambiad <tu-nombre>)
RG_NAME="rg-curso-functions-<tu-nombre>"
LOCATION="westeurope"
STORAGE_NAME="stfunc<tu-nombre>$(date +%s | tail -c 5)"
APP_NAME="func-productos-<tu-nombre>-$(date +%s | tail -c 5)"

# 1. Resource Group
az group create --name $RG_NAME --location $LOCATION

# 2. Storage Account (Functions LO REQUIERE, aunque no usemos blobs)
az storage account create \
  --name $STORAGE_NAME \
  --resource-group $RG_NAME \
  --location $LOCATION \
  --sku Standard_LRS

# 3. Function App (Consumption Plan, .NET 8 isolated)
az functionapp create \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --consumption-plan-location $LOCATION \
  --runtime dotnet-isolated \
  --runtime-version 8 \
  --functions-version 4 \
  --storage-account $STORAGE_NAME \
  --os-type Linux

echo "URL: https://$APP_NAME.azurewebsites.net"
```

**Tiempo estimado:** 2-3 minutos para crear todo.

**Output esperado al final:**

```
URL: https://func-productos-pedro-12345.azurewebsites.net
```

**Por qué Functions necesita Storage Account:**

```
Aunque vuestro código no use blobs:
- Functions almacena estado interno en Storage (locks, lease, etc.)
- Triggers como Timer y Blob lo necesitan obligatoriamente
- HTTP-only podría funcionar sin él, pero sigue siendo recomendado
- En Consumption Plan ES OBLIGATORIO

Coste del Storage Account vacío: ~€0.02/mes (despreciable)
```

**Verificar la Function App creada:**

```bash
az functionapp show \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --query "{Name:name, State:state, Runtime:siteConfig.linuxFxVersion}" \
  -o table
```

## Slide 12 — Paso 8: Probar la API en Azure

Mismo CRUD pero contra el endpoint público:

```bash
BASE="https://$APP_NAME.azurewebsites.net/api"

# 1. Listar
curl -s $BASE/productos | jq

# 2. Crear
curl -s -X POST $BASE/productos \
  -H "Content-Type: application/json" \
  -d '{"nombre":"Webcam HD","precio":79.50,"stock":20}' | jq

# 3. Obtener uno (usad un id devuelto en el listar)
curl -s $BASE/productos/p001 | jq

# 4. Actualizar
curl -s -X PUT $BASE/productos/p001 \
  -H "Content-Type: application/json" \
  -d '{"nombre":"Laptop Premium","precio":1799,"stock":2}' | jq

# 5. Borrar
curl -s -X DELETE -w "Status: %{http_code}\n" $BASE/productos/p003
```

**El primer request puede tardar 5-15 segundos.** Es **cold start** del Consumption Plan: la function lleva tiempo "dormida" y se levanta solo cuando llega tráfico. Los siguientes requests son rápidos (<200 ms).

**Comportamiento esperado tras unos minutos:**

```
- La function se duerme tras ~20 min sin tráfico
- Al volver a llamarla, cold start de nuevo
- TAMBIÉN: como tenemos datos EN MEMORIA, ¡los productos creados se pierden!
- Los datos seed (p001, p002, p003) se restauran cada vez que la function arranca
```

**Esta limitación es parte del aprendizaje:**

> "Si vuestra app necesita persistir datos entre cold starts → necesitáis BBDD real (Cosmos en M05)."

## Slide 14 — Smoke tests automatizados

Script bash que valida los 5 endpoints en 30 segundos:

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

BASE="${1:?Pasa la URL base como primer argumento}"

echo "🔍 Smoke tests sobre $BASE"

# Test 1: GET listar
echo -n "  [1/5] GET /productos... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/productos")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 2: POST crear
echo -n "  [2/5] POST /productos... "
RESP=$(curl -s -X POST "$BASE/productos" \
  -H "Content-Type: application/json" \
  -d '{"nombre":"SmokeTest","precio":1,"stock":1}')
NEW_ID=$(echo $RESP | jq -r '.id')
[ -n "$NEW_ID" ] && [ "$NEW_ID" != "null" ] && echo "✓ (id=$NEW_ID)" || { echo "✗"; exit 1; }

# Test 3: GET por id (el creado)
echo -n "  [3/5] GET /productos/$NEW_ID... "
```

## Slide 16 — Comparativa: Functions vs Web App

Ahora que tenéis una function corriendo, conviene comparar con la Web App del M02:

| Aspecto | Web App (M02) | **Function (M03)** |
|---|---|---|
| **Modelo de pago** | Por instancia siempre on | **Por ejecución (gratis hasta 1M/mes)** |
| **Cold start** | Solo en F1 | **Siempre en Consumption** |
| **Always on** | Sí desde B1 | **Solo en Premium** |
| **Latency mínima** | <100 ms | **200-500 ms warm; 5-15s cold** |
| **State** | Cualquiera (memoria, cookies, etc.) | **No state entre invocations** |
| **Triggers** | HTTP only | **HTTP, Timer, Blob, Cosmos, etc.** |
| **Casos uso ideal** | Webs, APIs constantes | **APIs esporádicas, jobs, eventos** |
| **Coste con bajo tráfico** | ~€13/mes mínimo (B1) | **€0** |
| **Coste con alto tráfico** | Predecible | **Crece con uso** |

**Cuándo Function en lugar de Web App:**

```
✅ APIs con tráfico esporádico (no 24/7)
✅ Tareas event-driven (Timer, Queue, Blob upload)
✅ Workloads de bajo coste donde scale-to-zero importa
✅ Microservicios pequeños y especializados
```

**Cuándo Web App en lugar de Function:**

```
✅ APIs con tráfico constante (Web App es más barato a alto volumen)
✅ Aplicaciones web tradicionales (SPA, MVC, Razor)
✅ Latencia crítica (no queréis cold starts)
✅ Necesitáis WebSockets / SignalR persistente
```

**Para esta práctica:** una function HTTP es **excesivo** para un CRUD constante en producción. Pero es **perfecto** para APIs ocasionales, webhooks, o como "backend para forms".

## Slide 18 — Troubleshooting Azure deployment

Los 5 errores más típicos al desplegar la function:

**1. "Function host is not running"**

```
Causa: el deploy falló silenciosamente, runtime mal configurado
Diagnóstico:
  az webapp log tail --name $APP_NAME -g $RG_NAME

Causas comunes:
- Runtime version mismatch (.NET 7 vs 8)
- Falta paquete en publish
- Excepción en Program.cs

Fix:
- Verificar: az functionapp show --name $APP_NAME -g $RG_NAME --query "siteConfig.linuxFxVersion"
- Esperado: "DOTNET-ISOLATED|8.0"
```

**2. "404 Not Found" al llamar el endpoint**

```
Causa: la función no se registró
Verificar:
  az functionapp function list --name $APP_NAME -g $RG_NAME -o table

Si la lista está vacía:
- El deploy no incluyó el código compilado
- Reintentar: func azure functionapp publish $APP_NAME --dotnet-isolated
```

**3. "503 Service Unavailable" durante cold start**

```
Causa: la function está iniciándose
Síntoma: primer request tras varios minutos sin uso devuelve 503

Es comportamiento normal en Consumption Plan. Reintentad después de 5-10 segundos.

Si queréis evitarlo:
- Pasar a Premium Plan (~€155/mes) → siempre warm
- O Flex Consumption (más nuevo, mejor balance)
- Para esta práctica: aceptar el cold start
```

**4. "Storage account not accessible"**

```
Causa: Storage Account borrado o connection string mal
Verificar:
  az functionapp config appsettings list \
    --name $APP_NAME -g $RG_NAME \
    --query "[?name=='AzureWebJobsStorage'].value" -o tsv

Si está vacío o apunta a un Storage que no existe:
- Reconfigurar:
  STORAGE_KEY=$(az storage account keys list -n $STORAGE_NAME -g $RG_NAME --query "[0].value" -o tsv)
  CONN="DefaultEndpointsProtocol=https;AccountName=$STORAGE_NAME;AccountKey=$STORAGE_KEY"
  az functionapp config appsettings set --name $APP_NAME -g $RG_NAME \
    --settings AzureWebJobsStorage="$CONN"
```

**5. "Datos creados se pierden al cabo de un rato"**

```
Causa: NO ES UN BUG, es así por diseño
Síntoma: creáis productos, los listáis, pasan 20 min, vuelven a aparecer solo los seed

Por qué:
- Repositorio está EN MEMORIA
- Cuando la function se duerme y rearrancan, memoria se resetea
- Solo persisten los datos del Seed() en el constructor

Fix (para producción):
- Usar Cosmos DB (M05)
- O Azure SQL
- O Storage Tables
```

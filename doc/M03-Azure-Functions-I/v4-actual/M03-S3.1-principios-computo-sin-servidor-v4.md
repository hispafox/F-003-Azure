## Slide 3 — Qué es serverless (de verdad)
El nombre engaña. "Serverless" no significa "sin servidores". Significa que tú no los ves, no los gestionas, y no te importa cuántos hay.

**Lo que tú haces:**
- Escribes una función (un trozo de código con un propósito específico)
- Defines qué evento la dispara (una petición HTTP, un timer, un cambio en la DB...)
- La subes a Azure

**Lo que Azure hace:**
- Asigna recursos cuando llega un evento
- Ejecuta tu función
- Escala automáticamente si llegan muchos eventos a la vez
- Apaga todo cuando no hay nada que hacer
- Te cobra solo por el tiempo de ejecución

No hay App Service Plan que mantener encendido (en plan de consumo). No hay VM que parchear. No hay instancias que dimensionar. Azure se encarga.

## Slide 4 — Azure Functions vs App Service: la diferencia clave

```
App Service (PaaS):
┌─────────────────────────────────┐
│  App Service Plan (siempre ON)  │
│  ┌───────────────────────────┐  │
│  │     Tu aplicación         │  │
│  │     (siempre corriendo)   │  │
│  └───────────────────────────┘  │
│  Pagas 24/7 aunque nadie use   │
└─────────────────────────────────┘

Azure Functions (Serverless):
         ┌──────┐
Evento → │ func │ → Resultado
         └──────┘
         ↑ solo existe mientras se ejecuta
         Pagas solo por ejecución (~0.20€ / millón)
```

**App Service:** Tu app está siempre corriendo, esperando peticiones. Pagas el plan completo. Ideal para aplicaciones con tráfico constante.

**Functions (consumo):** Tu función solo existe cuando hay un evento. Sin eventos, no hay función, no hay coste. Ideal para eventos esporádicos, procesamiento reactivo, tareas programadas.

## Slide 5 — El modelo de ejecución

```
1. EVENTO ocurre
   (HTTP request, timer tick, nuevo blob, cambio en Cosmos DB)
                    ↓
2. Azure Functions RUNTIME detecta el evento
                    ↓
3. Asigna una INSTANCIA (o reutiliza una "caliente")
                    ↓
4. Ejecuta tu FUNCIÓN
                    ↓
5. Devuelve el RESULTADO
   (response HTTP, mensaje en cola, documento en DB)
                    ↓
6. Si no hay más eventos → instancia se apaga (tras ~20 min)
```

**Cold start:** Si no hay instancia disponible, Azure necesita crear una. Esto tarda 1-10 segundos según el runtime y las dependencias. Es el trade-off principal de serverless.

**Warm instance:** Si la función se ha ejecutado recientemente, la instancia sigue viva. La siguiente ejecución es instantánea (~100ms).

## Slide 6 — Planes de hosting de Azure Functions

La decisión de plan afecta coste, rendimiento y features. Hay 4 planes principales en 2026:

| | Consumption | Flex Consumption | Premium (EP) | Dedicated (App Service) |
|---|---|---|---|---|
| **Modelo de pricing** | Por ejecución + GB-s | Por ejecución + GB-s | Fijo (VM dedicada) | Fijo (App Service Plan) |
| **Scale to zero** | ✓ | ✓ | ✗ | ✗ |
| **Max duración ejecución** | 10 min | 60 min | Sin límite | Sin límite |
| **Max scale-out** | 200 instancias | 1000 instancias | 100-200 | Según plan |
| **VNet integration** | ✗ | ✓ | ✓ | ✓ |
| **Private Endpoints** | ✗ | ✓ | ✓ | ✓ |
| **Pre-warmed instances** | ✗ | Configurable | Sí (0-20) | N/A (always on) |
| **Max memoria por instancia** | 1.5 GB | 4 GB | 14 GB | Según plan |
| **Cold start** | Sí (1-10s) | Sí (mejor que Consumption) | No | No |
| **Durable Functions** | ✓ (limitado) | ✓ | ✓ (recomendado) | ✓ |
| **Linux/Windows** | Linux | Linux | Ambos | Ambos |
| **Precio base mensual** | €0 | €0 | ~€150+ | ~€45+ |

**Árbol de decisión 2026:**

```
¿Tráfico esporádico, workload simple, sin VNet?
  └── Consumption (sigue siendo válido y prácticamente gratis)

¿Necesitas VNet o pre-warmed pero sigue siendo esporádico?
  └── Flex Consumption (GA 2024, recomendado por defecto)

¿Tráfico constante 24/7, latencia crítica, Durable complejo?
  └── Premium (EP1/EP2/EP3)

¿Ya tienes un App Service Plan con capacidad libre?
  └── Dedicated (reutilizáis infra, coste adicional 0)
```

**Recomendación práctica:**
- Desarrollo y pruebas: **Consumption** (prácticamente gratis)
- Producción nueva 2026: **Flex Consumption** (GA 2024)
- Producción legacy con Premium: mantener si funciona, considerar Flex en próxima migración
- Ya tenéis App Service Plan: **Dedicated** (reutilizáis recursos)

## Slide 7 — Coste real del plan de consumo

El plan de consumo cobra por dos cosas:

**1. Ejecuciones:** 0.17€ por millón de ejecuciones (primeras 1M/mes gratis)

**2. Consumo de recursos (GB-segundo):**
- Memoria usada × tiempo de ejecución
- 0.000014€ por GB-segundo
- Primeras 400.000 GB-s/mes gratis

**Ejemplo real:**
- Función que tarda 500ms y usa 256 MB de RAM
- Se ejecuta 100.000 veces al mes
- Consumo: 100.000 × 0.5s × 0.25 GB = 12.500 GB-s
- Coste de ejecuciones: dentro del tier gratis (< 1M)
- Coste de GB-s: dentro del tier gratis (< 400K)
- **Total: 0€**

Tendríais que ejecutar millones de veces al mes para que el coste sea significativo. Para los triggers que usáis, el plan de consumo es prácticamente gratis.

## Slide 8 — Cold start: el trade-off que hay que entender

**¿Qué es?**
Cuando no hay instancia caliente, Azure necesita: asignar una VM → cargar el runtime → cargar tu código → inicializar dependencias → ejecutar. Eso tarda.

**Tiempos típicos de cold start:**

| Runtime | Cold start típico | Con dependencias pesadas |
|---------|:-----------------:|:------------------------:|
| .NET (in-process) | 1-3 s | 3-8 s |
| .NET (isolated) | 2-5 s | 5-12 s |
| Node.js | 1-3 s | 3-10 s |
| Python | 2-5 s | 5-15 s |
| Java | 5-15 s | 10-30 s |

**Cómo reducir cold start:**
1. Menos dependencias = arranque más rápido
2. .NET in-process es más rápido que isolated (pero isolated es el futuro)
3. Plan Premium elimina el cold start (always warm)
4. Usar ReadyToRun publishing: `dotnet publish -c Release -p:PublishReadyToRun=true`

**¿Cuándo importa?**
- Trigger HTTP de cara al usuario: importa mucho (el usuario espera)
- Trigger Timer que se ejecuta cada hora: no importa (nadie espera)
- Trigger de Cosmos DB Change Feed: no importa (procesamiento asíncrono)

## Slide 9 — Anatomía de una Azure Function

Una Function tiene tres partes:

```
TRIGGER          →     FUNCIÓN          →     BINDINGS DE SALIDA
(qué la dispara)       (tu código)            (dónde escribe)

HTTP request           public static async    Blob Storage
Timer (CRON)           Task<IActionResult>     Cosmos DB
Blob nuevo             Run(...)               Queue
Cosmos DB change       {                      HTTP response
Queue message            // tu lógica         Event Grid
Event Grid               return result;       Service Bus
Service Bus            }                      Table Storage
                                              SendGrid (email)
```

**Trigger:** Exactamente uno. Cada función tiene un solo trigger que la dispara.
**Input Bindings:** Cero o más. Datos que la función lee al ejecutarse.
**Output Bindings:** Cero o más. Donde la función escribe el resultado.

Los bindings son declarativos — defines la conexión en configuración, no en código. Azure inyecta los datos automáticamente.

## Slide 11 — In-process vs Isolated Worker

Azure Functions en .NET tiene dos modos de ejecución:

**In-process (clásico):**
- Tu código corre dentro del mismo proceso que el runtime de Functions
- Más rápido (sin serialización entre procesos)
- Limitado a la versión de .NET del runtime (actualmente .NET 8)
- En camino a ser deprecado

**Isolated Worker (recomendado):**
- Tu código corre en un proceso separado del runtime
- Más flexible: puedes usar cualquier versión de .NET
- Soporta middleware, dependency injection completa
- Es el modelo que Microsoft recomienda para nuevo desarrollo
- Ligeramente más lento que in-process (comunicación entre procesos)

```bash
# Crear proyecto isolated worker (recomendado)
func init --worker-runtime dotnet-isolated --target-framework net8.0

# Crear proyecto in-process (legacy)
func init --worker-runtime dotnet
```

**Para este curso:** Usaremos **isolated worker**. Es el futuro y soporta todas las features que necesitáis.

## Slide 12 — Program.cs en Isolated Worker

```csharp
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var host = new HostBuilder()
    .ConfigureFunctionsWebApplication()  // Habilita HTTP triggers
    .ConfigureServices(services =>
    {
        // Dependency Injection — igual que en ASP.NET Core
        services.AddApplicationInsightsTelemetryWorkerService();
        services.ConfigureFunctionsApplicationInsights();
        
        // Tus servicios
        services.AddSingleton<IProcesadorService, ProcesadorService>();
        services.AddHttpClient("ApiExterna", c => {
            c.BaseAddress = new Uri("https://api.externa.com");
        });
    })
    .Build();

host.Run();
```

**La ventaja de isolated:** Tenéis el mismo patrón de DI que en ASP.NET Core. Podéis registrar servicios, HttpClients, middleware, y todo lo que ya conocéis.

## Slide 16 — Cuándo usar Functions y cuándo no

**Usa Functions cuando:**
- Reaccionas a eventos (algo cambia → procesa → guarda resultado)
- Tareas programadas (cada hora, cada noche, los lunes a las 8)
- Procesamiento de archivos (llega un blob → transformar → guardar)
- APIs con tráfico esporádico o impredecible
- Integraciones entre servicios (Cosmos DB → procesar → Service Bus)
- Webhooks y callbacks

**NO uses Functions cuando:**
- Necesitas conexiones persistentes (WebSockets, SignalR → App Service)
- Procesamiento que tarda más de 10 minutos (→ Durable Functions o Container Apps)
- Aplicaciones con estado complejo (→ App Service)
- Tráfico constante y alto (→ App Service sale más barato)
- Necesitas control total del entorno (→ Contenedores)

**La pregunta rápida:** ¿Tu código reacciona a un evento y termina en menos de 5 minutos? → Functions. ¿Tu código necesita estar siempre corriendo esperando conexiones? → App Service.

## Slide 18 — Bindings: la conexión declarativa

Los bindings son la forma de conectar tu función con otros servicios sin escribir código de conexión:

**Sin bindings (manual):**
```csharp
// Tienes que crear el cliente, conectar, leer, cerrar
var client = new CosmosClient(connectionString);
var container = client.GetContainer("db", "container");
var response = await container.ReadItemAsync<Documento>(id, partition);
```

**Con input binding (declarativo):**
```csharp
[Function("GetDocumento")]
public async Task<IActionResult> Run(
    [HttpTrigger(AuthorizationLevel.Function, "get")] HttpRequest req,
    [CosmosDBInput("db", "container", 
        Connection = "CosmosDbConnection",
        Id = "{Query.id}", 
        PartitionKey = "{Query.pk}")] Documento documento)
{
    // documento ya está cargado — Azure lo hizo por ti
    return new OkObjectResult(documento);
}
```

Menos código, menos errores, menos configuración. Los bindings son una de las ventajas más potentes de Azure Functions.

## Slide 20 — Escalado de Functions: cómo funciona

En plan de consumo, Azure escala automáticamente:

```
0 eventos    → 0 instancias (no pagas nada)
1 evento     → 1 instancia
100 eventos  → Azure decide cuántas instancias (5? 10? 50?)
1000 eventos → Azure escala hasta 200 instancias máximo
0 eventos    → ~20 min después, 0 instancias otra vez
```

**El Scale Controller:**
Azure tiene un componente llamado Scale Controller que monitoriza la tasa de eventos y decide cuántas instancias crear. Para HTTP triggers, mira las peticiones en cola. Para Cosmos DB, mira los cambios pendientes en el Change Feed. Para Blob, mira los blobs nuevos no procesados.

**Límites de escalado:**

| Plan | Máx instancias | Escala a cero |
|------|:--------------:|:-------------:|
| Consumption | 200 | Sí |
| Premium EP1 | 100 | No (min 1) |
| Premium EP2/EP3 | 100 | No (min 1) |
| Dedicated | Según plan | No |

## Slide 24 — Seguridad en Azure Functions

**Niveles de autorización para HTTP triggers:**

| Nivel | Quién puede llamar | Cómo |
|-------|--------------------|----|
| Anonymous | Cualquiera | Sin restricción |
| Function | Con function key | `?code=<function-key>` en la URL |
| Admin | Con master key | Solo administración |

```csharp
// Anonymous — cualquiera puede llamar (proteger con otro mecanismo)
[HttpTrigger(AuthorizationLevel.Anonymous, "get")]

// Function — requiere function key
[HttpTrigger(AuthorizationLevel.Function, "get")]
```

**Function keys NO son autenticación real.** Son un mecanismo básico de protección. Para autenticación de usuarios, usad OAuth2/Entra ID (módulo 6).

**Para triggers que no son HTTP** (Timer, Blob, Cosmos DB), la seguridad la da la cadena de conexión al servicio. Si alguien tiene la connection string de vuestro Storage Account, puede disparar funciones. Proteded las connection strings con Key Vault.

## Slide 25 — Buenas prácticas generales

**1. Una función = una responsabilidad**
No metáis lógica de 5 tareas diferentes en una función. Dividid en funciones pequeñas y específicas.

**2. Funciones rápidas**
La duración máxima en consumo es 5-10 minutos. Pero las buenas funciones tardan segundos, no minutos. Si tarda más, probablemente debería ser un Durable Function o un App Service.

**3. Idempotencia**
Los triggers pueden ejecutar tu función más de una vez (at-least-once delivery). Tu función debe producir el mismo resultado aunque se ejecute dos veces con los mismos datos.

**4. Connection pooling**
Nunca creéis un `CosmosClient` o `HttpClient` dentro de la función. Usad dependency injection para que se reutilice entre ejecuciones.

**5. Evitad estado local**
Las variables estáticas se pierden cuando la instancia se recicla. Usad Cosmos DB, Redis o Table Storage para estado persistente.

**6. Logs estructurados**
`logger.LogInformation("Procesando documento {DocumentId} de {Container}", docId, container)` — no string concatenation.

## Slide 26 — Errores comunes (y cómo evitarlos)

**"Mi función no se ejecuta"**
→ Verificad la connection string en App Settings. El 90% de las veces es una connection string mal configurada.

**"Funciona en local pero no en Azure"**
→ local.settings.json no se despliega. Las variables tienen que estar en App Settings de Azure.

**"La función se ejecuta dos veces"**
→ Es normal en at-least-once triggers (Blob, Queue). Haced la función idempotente.

**"Timeout después de 5 minutos"**
→ Plan de consumo tiene límite de 5 min (configurable a 10). Si necesitáis más, usad Premium o Durable Functions.

**"Memory leak — la función cada vez tarda más"**
→ Probablemente estáis creando objetos pesados (HttpClient, CosmosClient) dentro de la función en vez de inyectarlos por DI.

## Slide 29 — Warmup de Functions en Premium

En Premium (y Flex Consumption), configuráis **pre-warmed instances** para evitar cold starts:

```bash
# Configurar 5 instancias pre-calentadas siempre
az functionapp plan update \
  --name plan-func-premium \
  --resource-group rg-ventas-prod \
  --min-instances 5

# O desde Bicep
resource functionPlan 'Microsoft.Web/serverfarms@2024-04-01' = {
  name: 'plan-func-premium'
  location: location
  sku: { name: 'EP1', tier: 'ElasticPremium' }
  properties: {
    maximumElasticWorkerCount: 20
    // 5 siempre encendidas + hasta 15 adicionales bajo demanda
  }
}

resource functionApp 'Microsoft.Web/sites@2024-04-01' = {
  name: 'func-ventas'
  // ...
  properties: {
    serverFarmId: functionPlan.id
    siteConfig: {
      minimumElasticInstanceCount: 5  // pre-warmed
      functionAppScaleLimit: 20
    }
  }
}
```

**Además, configurar warmup trigger:**
```csharp
public class WarmupFunction
{
    [Function(nameof(WarmUp))]
    public void WarmUp([WarmupTrigger] object warmupContext)
    {
        // Este código se ejecuta al añadir una nueva instancia
        // Inicializar conexiones pool, cachear datos, etc.
        _ = CosmosClient.GetContainer("db", "col");
        _ = ServiceBusClient.CreateSender("queue");
    }
}
```

Sin este warmup, cuando autoscale añade instancia N+1, los primeros requests en esa instancia experimentan latencia 3-5x superior hasta que las conexiones pool se llenen.

## Slide 30 — Escalado: límites y burst capacity

Conocer los límites de escalado evita sorpresas en picos:

```
LÍMITES POR PLAN (abril 2026):

Consumption:
├── Max instances: 200
├── Scale-out rate: ~1 instancia/seg
├── Burst hasta límite en ~3 min
├── Cold start: 1-3 seg en .NET
└── Max execution per instance: 10 min

Flex Consumption:
├── Max instances: 1000 (GA 2024)
├── Scale-out rate: más rápido que Consumption
├── Burst hasta límite en ~1-2 min
├── Max execution per instance: 60 min
└── Memoria configurable: 2GB o 4GB

Premium (Elastic):
├── Max instances: 100 (EP1), 100 (EP2), 100 (EP3)
├── Pre-warmed: configurable 1-20
├── Scale-out rate: muy rápido
├── Max execution: sin límite teórico
└── Memoria: 3.5GB / 7GB / 14GB según SKU

Dedicated (App Service Plan):
├── Max instances: según SKU del plan (10 en S1, 30 en P1v3)
├── Manual scale o autoscale (tipo App Service)
├── No scale to zero
└── Max execution: sin límite
```

**Throttling en triggers:**
- HTTP: cada instancia procesa N concurrent requests (`maxConcurrentRequests`)
- Service Bus: cada instancia hasta 32 mensajes concurrentes (`maxConcurrentCalls`)
- Blob: cada instancia N blobs paralelos (`maxDegreeOfParallelism`)

Si al escalar llegáis al límite y el tráfico sigue, empezáis a encolar (Service Bus) o recibir 429 (HTTP).

## Slide 32 — Cost optimization específico de Functions

Factores de coste de Functions y cómo optimizarlos:

```
Modelo Consumption / Flex Consumption:
├── Por ejecución: ~$0.20 por millón de ejecuciones
├── Por GB-s: ~$0.000016 por GB-segundo consumido
├── Primeras 1 millón ejecuciones al mes: GRATIS
└── Primeros 400,000 GB-s al mes: GRATIS

Ejemplo real:
Function que ejecuta 1M veces/mes, 500ms promedio, 0.5GB memory:
├── Ejecuciones: 1M = 1M × $0.20 = $0.20 (1er millón gratis = $0)
├── GB-seg: 1M × 0.5s × 0.5GB = 250,000 GB-s (gratis primeros 400K = $0)
└── Coste total: $0

Otra: 100M ejecuciones/mes, 2s promedio, 1GB memory:
├── Ejecuciones: 100M - 1M free = 99M × $0.20 = $19.80
├── GB-seg: 100M × 2s × 1GB = 200M (200M - 400K = 199.6M) × $0.000016 = $3,193
└── Total: ~$3,213/mes

En este ejemplo: GB-s >> coste por ejecución (función larga + mucha memoria)
```

**Optimizaciones típicas:**

| Técnica | Ahorro |
|---|---|
| Reducir memoria allocated (menor GB) | Proporcional |
| Reducir tiempo ejecución (async/await bien) | Significativo |
| Batching: procesar varios items por ejecución | Muy alto |
| Cache resultados que se reusan | Alto |
| Pasar a Premium si hay patrón constante | Variable |

**Regla:** Consumption es ideal para tráfico esporádico. Si una función ejecuta >10M veces/mes con tiempos largos, evaluad Premium con pre-warmed instances (puede salir más barato que Consumption).

## Slide 34 — Cierre del submódulo

Serverless no es magia — es un modelo de ejecución donde Azure gestiona la infraestructura y tú te centras en el código. Las ventajas son enormes (coste, escalado, simplicidad) pero hay trade-offs reales (cold start, duración máxima, debugging más complejo).

Lo esencial:
- Functions = código que reacciona a eventos
- Plan de consumo para desarrollo y cargas esporádicas (prácticamente gratis)
- Plan Premium para producción sin cold start
- Un trigger, múltiples bindings, aislamiento por función
- Isolated worker para nuevo desarrollo en .NET
- Idempotencia, connection pooling, funciones rápidas

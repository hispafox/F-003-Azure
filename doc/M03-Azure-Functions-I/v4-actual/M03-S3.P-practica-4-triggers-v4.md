## Slide 2 — Qué vais a construir
Un Function App con 4 funciones, una por cada tipo de trigger:

1. **HTTP Trigger:** API de productos (GET por ID, POST para crear)
2. **Timer Trigger:** Limpieza nocturna de registros temporales
3. **Blob Trigger:** Procesar un CSV subido y generar un JSON con el resumen
4. **Cosmos DB Trigger:** Reaccionar a cambios en pedidos y loguear notificaciones

**Tiempo estimado:** 25-30 minutos
**Entregable:** Function App corriendo en local con las 4 funciones operativas

## Slide 6 — Paso 3: HTTP Trigger — API de productos

Cread `Functions/ProductosApi.cs`:

```csharp
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Mvc;
using Microsoft.Azure.Functions.Worker;

public class ProductosApi
{
    private static readonly List<Producto> _productos = new()
    {
        new("1", "Laptop", 999.99m),
        new("2", "Monitor", 349.99m),
        new("3", "Teclado", 79.99m)
    };

    [Function("ListarProductos")]
    public IActionResult Listar(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "productos")] 
        HttpRequest req)
    {
        return new OkObjectResult(_productos);
    }

    [Function("GetProducto")]
    public IActionResult Get(
        [HttpTrigger(AuthorizationLevel.Anonymous, "get", Route = "productos/{id}")] 
        HttpRequest req, string id)
    {
        var producto = _productos.FirstOrDefault(p => p.Id == id);
        return producto is null ? new NotFoundResult() : new OkObjectResult(producto);
    }

    [Function("CrearProducto")]
    public async Task<IActionResult> Crear(
        [HttpTrigger(AuthorizationLevel.Anonymous, "post", Route = "productos")] 
        HttpRequest req)
    {
        var dto = await req.ReadFromJsonAsync<Producto>();
        if (dto is null) return new BadRequestResult();
        
        var producto = dto with { Id = Guid.NewGuid().ToString()[..8] };
        _productos.Add(producto);
        return new CreatedResult($"/api/productos/{producto.Id}", producto);
    }
}

public record Producto(string Id, string Nombre, decimal Precio);
```

## Slide 7 — Paso 4: Timer Trigger — Limpieza nocturna

Cread `Functions/TareasAutomaticas.cs`:

```csharp
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class TareasAutomaticas
{
    private readonly ILogger<TareasAutomaticas> _logger;

    public TareasAutomaticas(ILogger<TareasAutomaticas> logger) => _logger = logger;

    [Function("LimpiezaProgramada")]
    public void Limpieza(
        [TimerTrigger("0 */1 * * * *")] TimerInfo timer)  // Cada minuto para testing
    {
        _logger.LogInformation("=== LIMPIEZA INICIADA === {Hora}", DateTime.UtcNow);
        
        if (timer.IsPastDue)
            _logger.LogWarning("Ejecución retrasada");
        
        // Simulación de limpieza
        var registrosEliminados = Random.Shared.Next(10, 100);
        _logger.LogInformation("Eliminados {Count} registros temporales", registrosEliminados);
        
        _logger.LogInformation("Próxima ejecución: {Next}", timer.ScheduleStatus?.Next);
    }
}
```

**Nota:** Usamos `*/1` (cada minuto) para testing. En producción sería `0 0 3 * * *` (3 AM).

**Verificar:** Al ejecutar `func start`, deberíais ver el log de limpieza cada minuto.

## Slide 8 — Paso 5: Blob Trigger — Procesar CSV

Cread `Functions/ProcesadorCSV.cs`:

```csharp
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;
using System.Text.Json;

public class ProcesadorCSV
{
    private readonly ILogger<ProcesadorCSV> _logger;

    public ProcesadorCSV(ILogger<ProcesadorCSV> logger) => _logger = logger;

    [Function("ProcesarCSV")]
    [BlobOutput("resultados/{nombre}-resumen.json", Connection = "StorageConnection")]
    public string Procesar(
        [BlobTrigger("uploads/{nombre}.csv", Connection = "StorageConnection")] 
        string csvContent,
        string nombre)
    {
        _logger.LogInformation("Procesando CSV: {Nombre}", nombre);
        
        var lineas = csvContent.Split('\n', StringSplitOptions.RemoveEmptyEntries);
        var headers = lineas.FirstOrDefault()?.Split(',') ?? Array.Empty<string>();
        var dataLines = lineas.Skip(1).ToList();
        
        var resumen = new
        {
            archivo = $"{nombre}.csv",
            columnas = headers.Select(h => h.Trim()).ToArray(),
            total_filas = dataLines.Count,
            procesado_en = DateTime.UtcNow,
            preview = dataLines.Take(3).Select(l => l.Trim()).ToArray()
        };
        
        _logger.LogInformation("CSV procesado: {Filas} filas, {Columnas} columnas", 
            dataLines.Count, headers.Length);
        
        return JsonSerializer.Serialize(resumen, new JsonSerializerOptions { WriteIndented = true });
    }
}
```

**Probar:** Subid un archivo CSV al contenedor `uploads` en Azurite:

## Slide 9 — Paso 6: Cosmos DB Trigger — Reaccionar a cambios

Cread `Functions/ReaccionPedidos.cs`:

```csharp
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;
using System.Text.Json.Serialization;

public class ReaccionPedidos
{
    private readonly ILogger<ReaccionPedidos> _logger;

    public ReaccionPedidos(ILogger<ReaccionPedidos> logger) => _logger = logger;

    [Function("ReaccionarCambiosPedidos")]
    public void Reaccionar(
        [CosmosDBTrigger(
            databaseName: "tienda",
            containerName: "pedidos",
            Connection = "CosmosDbConnection",
            LeaseContainerName = "leases",
            CreateLeaseContainerIfNotExists = true)]
        IReadOnlyList<PedidoDoc> cambios)
    {
        if (cambios is null || cambios.Count == 0) return;
        
        _logger.LogInformation("*** {Count} cambios detectados en pedidos ***", cambios.Count);
        
        foreach (var pedido in cambios)
        {
            _logger.LogInformation(
                "  Pedido {Id}: cliente={Cliente}, total={Total:C}, estado={Estado}",
                pedido.Id, pedido.ClienteId, pedido.Total, pedido.Estado);
        }
    }
}

public class PedidoDoc
{
    [JsonPropertyName("id")]
    public string Id { get; set; } = "";
    
    [JsonPropertyName("clienteId")]
    public string ClienteId { get; set; } = "";
    
    [JsonPropertyName("total")]
    public decimal Total { get; set; }
    
    [JsonPropertyName("estado")]
    public string Estado { get; set; } = "nuevo";
}
```

**Probar:** Cread un documento en Cosmos DB (emulador o real):

## Slide 12 — Troubleshooting específico por tipo de trigger

Los 4 triggers tienen modos de fallo distintos. Esta tabla os ahorrará horas:

**HTTP Trigger:**
```
❌ "Could not load file or assembly 'Microsoft.AspNetCore.App'"
   → Falta paquete Functions.Worker.Extensions.Http.AspNetCore
   → dotnet add package Microsoft.Azure.Functions.Worker.Extensions.Http.AspNetCore

❌ Endpoint no responde (404)
   → Verificar que el binding [HttpTrigger] tiene authLevel correcto
   → Verificar route en el atributo (default: nombre de la función)

❌ "Function host is not running"
   → Otro proceso usa el puerto 7071
   → func start --port 7072 (o matar el otro proceso)
```

**Timer Trigger:**
```
❌ Timer no ejecuta nunca
   → Verificar formato CRON (6 campos, no 5 estilo Linux)
   → "0 */5 * * * *" = cada 5 min (correcto)
   → "*/5 * * * *" = ERROR (formato Linux)

❌ Timer ejecuta dos veces al mismo tiempo
   → Singleton attribute si es crítico que solo corra una instancia
   → AzureWebJobsStorage debe ser único por entorno

❌ "useMonitor: false" warning
   → En desarrollo está bien
   → En producción: configurar Storage para tracking
```

**Blob Trigger:**
```
❌ Blob trigger nunca dispara
   → Verificar que el contenedor existe ANTES de arrancar Functions
   → Path en binding debe coincidir: "uploads/{name}" no "/uploads/{name}"
   → Latencia inicial puede ser 1-10 minutos (polling)

❌ Mismo blob procesado múltiples veces
   → Check del lease/lock no funcionó
   → Solución: idempotencia en tu código (verificar si ya procesado)

❌ Demasiada latencia para procesar
   → Para producción: usar Event Grid Source en vez de polling
   → Cambiar Source = BlobTriggerSource.EventGrid en el binding
```

**Cosmos DB Trigger (Change Feed):**
```
❌ Trigger no recibe cambios
   → Verificar que CreateLeaseContainerIfNotExists = true
   → Verificar nombre database y container
   → El container 'leases' debe existir o auto-crearse

❌ "Throttled (429)" durante procesamiento
   → Cosmos RU/s insuficientes para Change Feed
   → Aumentar throughput temporalmente
   → Revisar batch size del trigger (MaxItemsPerInvocation)

❌ Trigger procesa cambios antiguos al reiniciar
   → Comportamiento normal: re-procesa desde último checkpoint
   → Para ignorar histórico: borrar lease container antes de iniciar
```

## Slide 13 — Observabilidad: ver los triggers en acción

Sin observabilidad, las Functions son una caja negra. En local podéis ver logs, en producción necesitáis Application Insights.

**1. Verificar Application Insights conectado** (al desplegar):
```bash
az functionapp show \
  --name func-cuatro-triggers \
  --resource-group rg-curso \
  --query "siteConfig.appSettings[?name=='APPLICATIONINSIGHTS_CONNECTION_STRING'].value" \
  --output tsv
# Debe devolver una connection string
```

**2. Live metrics** (lo más útil durante desarrollo):
```
Portal → Function App → Application Insights → Live Metrics
```
Veréis en tiempo real:
- Requests/segundo por función
- Failed requests (fallos)
- CPU y memoria
- Servidores activos

**3. KQL queries útiles para los 4 triggers:**

```kusto
// ¿Cuántas veces ejecutó cada trigger en la última hora?
requests
| where timestamp > ago(1h)
| where cloud_RoleName contains "func-cuatro-triggers"
| summarize Count = count() by name, success
| order by Count desc

// Latencia P95 por función
requests
| where timestamp > ago(24h)
| summarize 
    P50 = percentile(duration, 50),
    P95 = percentile(duration, 95),
    P99 = percentile(duration, 99)
  by name
| order by P95 desc

// Errores con stack trace
exceptions
| where timestamp > ago(24h)
| where cloud_RoleName contains "func-cuatro-triggers"
| project timestamp, operation_Name, type, outerMessage, details[0].rawStack
| order by timestamp desc

// Cosmos Change Feed: cuántos items procesados por invocación
traces
| where timestamp > ago(1h)
| where cloud_RoleName contains "func-cuatro-triggers"
| where message contains "Procesando"
| extend ItemsProcessed = toint(extract(@"(\d+) items", 1, message))
| summarize TotalItems = sum(ItemsProcessed), Invocations = count() by bin(timestamp, 5m)
```

**4. Métricas que importan en producción:**
- Function execution count (total invocaciones)
- Function execution units (consumo facturable)
- Server response time (latencia)
- Failed requests % (debe ser <1%)
- Cosmos RU consumption (si usáis Cosmos trigger)

**5. Configurar alertas** (lo mínimo en producción):
- Error rate > 5% en 5 min → email
- Latencia P95 > 5s sostenida → email
- Cosmos RU > 80% throughput → escalar

## Slide 14 — Costes: Consumption vs Premium vs Flex Consumption

Antes de desplegar a producción, entended qué váis a pagar:

**Consumption Plan (lo que probablemente usaréis):**
```
Coste:
- Primeras 1M ejecuciones/mes: GRATIS
- Después: ~€0.18 por millón
- Memoria: ~€0.000014/GB-segundo

Ejemplo: 5M ejecuciones/mes, 200ms cada una, 256MB
- Ejecuciones: (5M - 1M) × €0.18/M = €0.72
- Compute: 5M × 0.2s × 0.25GB × €0.000014 = €3.50
- TOTAL: ~€4.22/mes

✅ Ideal para: APIs intermitentes, procesos batch, tareas event-driven
❌ NO ideal para: workloads con cold start crítico, traffic constante
```

**Premium Plan:**
```
Coste:
- Plan EP1 (1 vCPU, 3.5GB RAM): ~€155/mes baseline
- Pre-warmed instances: -90% cold starts
- VNet integration nativa

✅ Ideal para: workloads de producción con SLA, latencia crítica, VNet
❌ NO ideal para: workloads esporádicos (gastáis aunque no uséis)
```

**Flex Consumption (lo más nuevo, recomendado para 2026):**
```
Coste:
- Pay per request similar a Consumption
- Pre-warmed instances opcionales (€/instancia/hora)
- Sin cold start si tenéis pre-warmed

Ejemplo: 5M ejecuciones/mes + 1 instance pre-warmed
- Ejecuciones: ~€4 (similar a Consumption)
- Pre-warmed: €0.05/h × 720h = €36/mes
- TOTAL: ~€40/mes (sin cold starts)

✅ Ideal para: producción moderna, balance precio/performance
✅ Replaces: Consumption + Premium en muchos casos
```

**Para esta práctica (4 triggers en local + tests):**
- Coste real: **€0** (Azurite + Cosmos emulator local)
- Si despliegan a Azure: Consumption Plan = **<€1/mes** mientras desarrollan

## Slide 19 — Variante: Function App con MI + Key Vault

Convertir la práctica a setup "production-ready":

```bash
# 1. Habilitar Managed Identity en la Function App
az functionapp identity assign --name func-practica-<tu-nombre> -g rg-practica-<tu-nombre>

# 2. Crear Key Vault
az keyvault create --name kv-practica-<tu-nombre> -g rg-practica-<tu-nombre> \
  --location westeurope --enable-rbac-authorization true

# 3. Asignar rol al MI de la Function App
PRINCIPAL=$(az functionapp identity show --name func-practica-<tu-nombre> \
  -g rg-practica-<tu-nombre> --query principalId -o tsv)
KV_ID=$(az keyvault show --name kv-practica-<tu-nombre> --query id -o tsv)

az role assignment create --assignee $PRINCIPAL \
  --role "Key Vault Secrets User" --scope $KV_ID

# 4. Guardar secretos en KV (en lugar de App Settings)
az keyvault secret set --vault-name kv-practica-<tu-nombre> \
  --name "CosmosConnection" --value "<connection-string>"

# 5. Configurar la Function App para usar Key Vault reference
az functionapp config appsettings set --name func-practica-<tu-nombre> \
  -g rg-practica-<tu-nombre> \
  --settings "CosmosConnection=@Microsoft.KeyVault(SecretUri=https://kv-practica-<tu-nombre>.vault.azure.net/secrets/CosmosConnection)"

# 6. Migrar conexiones a Managed Identity (sin password)
# En lugar de connection string:
# "CosmosConnection": "AccountEndpoint=https://...;AccountKey=xxx"
# Usar:
# "CosmosConnection__accountEndpoint": "https://cosmos.documents.azure.com:443/"
# + MI con rol "Cosmos DB Data Contributor"
```

**Comparativa:**

| Setup | Seguridad | Complejidad |
|---|:---:|:---:|
| Connection strings en app settings | 🟡 Media | 🟢 Baja |
| Key Vault references | 🟢 Alta | 🟡 Media |
| Managed Identity + RBAC | 🟢 Máxima | 🟠 Alta |

La configuración production es la tercera. Lo veréis a fondo en M6.

## Slide 20 — Variante: deploy via GitHub Actions

Automatizar deploys con workflow completo:

```yaml
# .github/workflows/deploy-functions.yml
name: Deploy Functions

on:
  push:
    branches: [main]
    paths:
      - 'src/Functions/**'
      - '.github/workflows/deploy-functions.yml'

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      
      - name: Build
        run: dotnet build src/Functions -c Release
      
      - name: Test
        run: dotnet test src/Functions.Tests -c Release --no-build
      
      - name: Publish
        run: dotnet publish src/Functions -c Release -o publish --no-build
      
      - name: Login to Azure (OIDC, sin passwords)
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      - name: Deploy to Function App
        uses: Azure/functions-action@v1
        with:
          app-name: 'func-practica-<tu-nombre>'
          package: 'publish'
          
      - name: Smoke test
        run: |
          sleep 30
          curl -sf https://func-practica-<tu-nombre>.azurewebsites.net/api/productos \
            -H "x-functions-key: ${{ secrets.FUNCTION_KEY }}"
```

**Setup necesario:**
1. Crear App Registration en Entra ID con federated credentials (para OIDC)
2. Asignar rol Contributor al Function App
3. Añadir secrets al repo: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID
4. Push a main → deploy automático

**Sin passwords almacenados** (OIDC federation). Más seguro que service principal con client secret.

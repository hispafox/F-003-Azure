## Slide 2 — Qué es el Change Feed
Cosmos DB mantiene un log ordenado cronológicamente de todos los cambios (inserciones y actualizaciones) en un contenedor. Ese log es el **Change Feed**.

El Cosmos DB trigger de Azure Functions lee ese Change Feed y ejecuta tu función cada vez que hay documentos nuevos o modificados.

**Qué detecta:** Inserciones y actualizaciones de documentos.
**Qué NO detecta:** Eliminaciones (por diseño — Cosmos DB no las registra en el Change Feed. Workaround: soft delete con un campo `eliminado: true`).

**Vuestro caso:** Ya usáis este trigger en producción. Este submódulo profundiza en cómo funciona internamente, cómo configurarlo bien y cómo evitar los errores más comunes.

## Slide 3 — Change Feed: cómo funciona internamente

```
Contenedor "pedidos" (particionado por clienteId)
┌──────────────┬──────────────┬──────────────┐
│ Partición A  │ Partición B  │ Partición C  │
│ (cliente-1)  │ (cliente-2)  │ (cliente-3)  │
│              │              │              │
│ doc1 (nuevo) │              │ doc5 (upd)   │
│ doc2 (upd)   │ doc3 (nuevo) │              │
└──────┬───────┴──────┬───────┴──────┬───────┘
       ↓              ↓              ↓
   Change Feed (log ordenado por partición)
       ↓              ↓              ↓
   ┌─────────────────────────────────────┐
   │   Azure Functions Cosmos Trigger     │
   │   (lee el Change Feed en batch)      │
   │                                      │
   │   [doc1, doc2, doc3, doc5]           │
   │   → tu función recibe el batch       │
   └─────────────────────────────────────┘
```

**El trigger lee en batches:** No recibe un documento a la vez, sino un lote de cambios. Tu función procesa el lote completo.

## Slide 4 — Cosmos DB Trigger mínimo

```csharp
public class ReaccionCambios
{
    private readonly ILogger<ReaccionCambios> _logger;

    public ReaccionCambios(ILogger<ReaccionCambios> logger) => _logger = logger;

    [Function("ProcesarCambiosPedidos")]
    public void Procesar(
        [CosmosDBTrigger(
            databaseName: "tienda",
            containerName: "pedidos",
            Connection = "CosmosDbConnection",
            LeaseContainerName = "leases",
            CreateLeaseContainerIfNotExists = true)] 
        IReadOnlyList<Pedido> cambios)
    {
        if (cambios is null || cambios.Count == 0) return;
        
        _logger.LogInformation("Recibidos {Count} cambios en pedidos", cambios.Count);
        
        foreach (var pedido in cambios)
        {
            _logger.LogInformation("Pedido {Id}: estado={Estado}, total={Total}", 
                pedido.Id, pedido.Estado, pedido.Total);
            
            // Procesar cada cambio...
        }
    }
}

public class Pedido
{
    [JsonPropertyName("id")]
    public string Id { get; set; } = "";
    
    [JsonPropertyName("clienteId")]
    public string ClienteId { get; set; } = "";
    
    [JsonPropertyName("estado")]
    public string Estado { get; set; } = "";
    
    [JsonPropertyName("total")]
    public decimal Total { get; set; }
    
    [JsonPropertyName("_ts")]
    public long Timestamp { get; set; }
}
```

## Slide 5 — El contenedor de leases

El contenedor de **leases** es clave para entender cómo funciona:

**¿Qué es?** Un contenedor auxiliar en Cosmos DB donde el trigger guarda su progreso: qué cambios ya ha procesado, en qué partición va, qué instancia procesa qué.

**¿Por qué lo necesita?**
- Si la función se reinicia, sabe por dónde continuar (no reprocesa todo)
- Si hay múltiples instancias, se reparten las particiones (cada instancia procesa particiones diferentes)
- Si una instancia falla, otra toma sus particiones

```
CreateLeaseContainerIfNotExists = true  → Azure lo crea solo
LeaseContainerName = "leases"           → Nombre del contenedor de leases
```

**Recomendación:** Un contenedor de leases por cada trigger. Si tenéis dos funciones leyendo el mismo contenedor, dadles lease containers diferentes:

```csharp
LeaseContainerName = "leases-notificaciones"   // Para la función de notificaciones
LeaseContainerName = "leases-analytics"         // Para la función de analytics
```

## Slide 6 — Configuración avanzada

```csharp
[CosmosDBTrigger(
    databaseName: "tienda",
    containerName: "pedidos",
    Connection = "CosmosDbConnection",
    LeaseContainerName = "leases",
    CreateLeaseContainerIfNotExists = true,
    MaxItemsPerInvocation = 100,          // Máx documentos por batch
    StartFromBeginning = false,           // true = reprocesar todo desde el inicio
    FeedPollDelay = 5000,                 // Milisegundos entre polls (default: 5000)
    LeaseExpirationInterval = 60000,      // Tiempo antes de considerar un lease expirado
    LeaseRenewInterval = 17000            // Frecuencia de renovación de leases
)]
```

**`MaxItemsPerInvocation`:** Controla el tamaño del batch. Más pequeño = más invocaciones pero más rápido por invocación. Más grande = menos invocaciones pero puede tardar más.

**`StartFromBeginning`:** Si es `true`, la primera vez que se ejecuta, procesa TODOS los documentos existentes. Útil para migración o reconstrucción de índices. Cuidado: puede ser millones de documentos.

**`FeedPollDelay`:** Cada cuánto el trigger pregunta "¿hay cambios nuevos?". 5 segundos por defecto. Reducidlo para menor latencia, aumentadlo para menor coste de RU.

## Slide 8 — Ejemplo: notificación cuando cambia estado de pedido

```csharp
public class NotificacionesPedidos
{
    private readonly INotificacionService _notificaciones;
    private readonly ILogger<NotificacionesPedidos> _logger;

    public NotificacionesPedidos(
        INotificacionService notificaciones, 
        ILogger<NotificacionesPedidos> logger)
    {
        _notificaciones = notificaciones;
        _logger = logger;
    }

    [Function("NotificarCambioPedido")]
    public async Task Notificar(
        [CosmosDBTrigger("tienda", "pedidos",
            Connection = "CosmosDbConnection",
            LeaseContainerName = "leases-notificaciones",
            CreateLeaseContainerIfNotExists = true)]
        IReadOnlyList<Pedido> cambios)
    {
        foreach (var pedido in cambios)
        {
            switch (pedido.Estado)
            {
                case "confirmado":
                    await _notificaciones.EnviarAsync(pedido.ClienteId,
                        $"Tu pedido {pedido.Id} ha sido confirmado. Total: {pedido.Total:C}");
                    break;
                    
                case "enviado":
                    await _notificaciones.EnviarAsync(pedido.ClienteId,
                        $"Tu pedido {pedido.Id} está en camino");
                    break;
                    
                case "entregado":
                    await _notificaciones.EnviarAsync(pedido.ClienteId,
                        $"Tu pedido {pedido.Id} ha sido entregado. ¡Gracias!");
                    break;
            }
            
            _logger.LogInformation("Notificación enviada: pedido {Id}, estado {Estado}", 
                pedido.Id, pedido.Estado);
        }
    }
}
```

## Slide 9 — Ejemplo: materializar vista desnormalizada

```csharp
[Function("MaterializarResumenCliente")]
[CosmosDBOutput("tienda", "resumenes-clientes", Connection = "CosmosDbConnection")]
public List<ResumenCliente> Materializar(
    [CosmosDBTrigger("tienda", "pedidos",
        Connection = "CosmosDbConnection",
        LeaseContainerName = "leases-resumenes",
        CreateLeaseContainerIfNotExists = true)]
    IReadOnlyList<Pedido> cambios)
{
    // Agrupar cambios por cliente
    var porCliente = cambios.GroupBy(p => p.ClienteId);
    
    var resumenes = new List<ResumenCliente>();
    foreach (var grupo in porCliente)
    {
        resumenes.Add(new ResumenCliente
        {
            Id = $"resumen-{grupo.Key}",
            ClienteId = grupo.Key,
            UltimoPedido = grupo.Max(p => p.Timestamp),
            TotalPedidos = grupo.Count(),
            ActualizadoEn = DateTime.UtcNow
        });
    }
    
    // Output binding: se escriben automáticamente en "resumenes-clientes"
    return resumenes;
}
```

**¿Por qué materializar?** En vez de hacer un query complejo cada vez que necesitáis el resumen de un cliente (JOIN, GROUP BY, etc.), el trigger precalcula el resumen y lo guarda en un contenedor optimizado para lectura. La consulta se convierte en un simple `ReadItem` por ID.

## Slide 10 — Idempotencia: el requisito más importante

**El Change Feed garantiza at-least-once delivery.** Esto significa que tu función puede recibir el mismo documento más de una vez.

**¿Cuándo pasa?**
- La función falla a mitad del batch → reintento desde el inicio del batch
- Una instancia pierde el lease → otra instancia reprocesa
- Reinicio del Function App

**Tu función DEBE ser idempotente:**
```csharp
// MAL: duplica la notificación
await _email.EnviarAsync(pedido.ClienteId, "Pedido confirmado");

// BIEN: verifica si ya se envió
var yaEnviado = await _registro.ExisteNotificacionAsync(pedido.Id, "confirmado");
if (!yaEnviado)
{
    await _email.EnviarAsync(pedido.ClienteId, "Pedido confirmado");
    await _registro.MarcarComoEnviadaAsync(pedido.Id, "confirmado");
}
```

**Estrategias de idempotencia:**
1. Verificar en DB si la acción ya se ejecutó (más seguro, más lento)
2. Usar `_ts` del documento para descartar cambios ya procesados
3. Operaciones naturalmente idempotentes (upsert en vez de insert)

## Slide 11 — Escalado del Cosmos DB trigger

El trigger escala basándose en las particiones del contenedor monitoreado:

```
Contenedor con 10 particiones lógicas
→ El trigger puede crear hasta 10 instancias (1 por partición)
→ Cada instancia procesa los cambios de "sus" particiones
```

**Regla:** El número máximo de instancias del trigger = número de particiones físicas del contenedor. No podéis tener más paralelismo que particiones.

**Implicación:** Si vuestro contenedor tiene pocas particiones (por ejemplo, 1 partición con pocos datos), el trigger no escalará más allá de 1 instancia. Si necesitáis más paralelismo, necesitáis más datos o una partition key que distribuya mejor.

## Slide 12 — Manejo de errores

```csharp
[Function("ProcesarCambios")]
public async Task Procesar(
    [CosmosDBTrigger("tienda", "pedidos",
        Connection = "CosmosDbConnection",
        LeaseContainerName = "leases")]
    IReadOnlyList<Pedido> cambios,
    ILogger logger)
{
    var errores = new List<string>();
    
    foreach (var pedido in cambios)
    {
        try
        {
            await ProcesarPedidoAsync(pedido);
        }
        catch (Exception ex)
        {
            // Loguear pero NO relanzar — si relanzáis, TODO el batch se reintenta
            logger.LogError(ex, "Error procesando pedido {Id}", pedido.Id);
            errores.Add(pedido.Id);
        }
    }
    
    if (errores.Any())
    {
        // Guardar IDs fallidos para reprocesar después
        logger.LogWarning("Pedidos con error: {Ids}", string.Join(", ", errores));
        await _deadLetterService.GuardarAsync(errores);
    }
    
    // Si NO lanzáis excepción, el checkpoint avanza — los cambios se marcan como procesados
    // Si lanzáis excepción, todo el batch se reintenta desde el inicio
}
```

**Decisión clave:** ¿Relanzar la excepción o tragarla?
- Relanzar → el batch entero se reintenta (seguro pero puede ser ineficiente)
- Tragar → los fallidos se pierden si no los guardáis en un dead-letter
- **Recomendación:** Tragar + dead-letter para errores individuales. Relanzar solo si el error afecta a todo el batch.

## Slide 15 — Troubleshooting

**"El trigger no se ejecuta":**
→ Verificad la connection string `CosmosDbConnection` en App Settings
→ Verificad que la base de datos y el contenedor existen con esos nombres exactos
→ Verificad que el contenedor de leases se creó (`CreateLeaseContainerIfNotExists = true`)

**"Procesa documentos viejos al desplegar":**
→ `StartFromBeginning = false` (por defecto). Si está en `true`, reprocesa todo.
→ Si borrasteis el contenedor de leases, perdió el checkpoint y empieza de cero.

**"Recibe el mismo documento dos veces":**
→ Normal. At-least-once delivery. Haced la función idempotente.

**"Tarda mucho en detectar cambios (>30 seg)":**
→ Reducid `FeedPollDelay` en la configuración del trigger.
→ En producción alta, considerad Event Grid como intermediario.

**"Eliminaciones no se detectan":**
→ Por diseño. Usad soft delete (campo `deleted: true`) y reaccionad a la actualización.

## Slide 16 — Change Feed: procesamiento con backpressure

```json
// host.json: controlar el ritmo de procesamiento
{
  "extensions": {
    "cosmosDB": {
      "maxItemsPerInvocation": 50,    // Máximo 50 docs por batch
      "feedPollDelay": 5000,           // 5 seg entre polls
      "leaseAcquireInterval": 13000,
      "leaseExpirationInterval": 60000
    }
  }
}
```

Si el Change Feed genera más cambios de los que podéis procesar, ajustad `maxItemsPerInvocation` y `feedPollDelay`. Batches más pequeños = más invocaciones pero más manejables. Poll delay mayor = menos presión en Cosmos (menos RU de lectura del feed).

## Slide 19 — Change Feed: all versions and deletes mode

Desde 2024, Change Feed soporta detectar eliminaciones:

```csharp
[CosmosDBTrigger("tienda", "pedidos", 
    Connection = "CosmosDb", 
    LeaseContainerName = "leases",
    FeedRange = "FullRange")]
public void HandleAllChanges(IReadOnlyList<ChangeFeedItem> changes)
{
    foreach (var change in changes)
    {
        if (change.Metadata.OperationType == ChangeFeedOperationType.Delete)
            _logger.LogInformation("Documento ELIMINADO: {Id}", change.Previous.Id);
        else
            _logger.LogInformation("Documento modificado: {Id}", change.Current.Id);
    }
}
```

**Requiere:** Cosmos DB API version 2024+, continuous backup mode habilitado. Resuelve el problema histórico de que Change Feed no detectaba deletes.

## Slide 20 — Change Feed vs Event Sourcing: diferencias conceptuales

Change Feed y Event Sourcing se confunden, pero son patterns distintos:

```
Change Feed (lo que nos da Cosmos):
├── Registro automático de cambios en documentos
├── El documento "actual" está siempre en la colección
├── Consumidores leen cambios incrementales
├── Change Feed NO es la fuente de verdad (lo son los docs)
└── Uso: sync, materialized views, eventos downstream

Event Sourcing (arquitectura que vosotros diseñáis):
├── CADA cambio es un evento en una "event store"
├── El estado actual se RECONSTRUYE leyendo eventos
├── La event store ES la fuente de verdad
├── Snapshots periódicos para acelerar lectura
└── Uso: audit total, time-travel debugging, CQRS

Comparativa:
                      Change Feed    Event Sourcing
                      ─────────────────────────────
Fuente verdad         Docs actuales  Stream de eventos
Historial completo    No (solo delta) Sí (para siempre)
Retention             30 días        Para siempre
Complejidad           Baja           Alta
Useful para           Sync + views   Audit + replay
```

**Combinación pragmática:** usar **Cosmos DB con Change Feed como event store "lite"**. Los cambios en la colección se exportan a Event Grid/Service Bus, y tienen retention configurable.



## Slide 21 — Service Bus vs Change Feed: cuándo usar cada uno

Both son patrones event-driven, pero resuelven problemas distintos. Confundirlos es un error común:

| Aspecto | Cosmos Change Feed | Service Bus |
|---|---|---|
| **Origen del evento** | Cambios en una BBDD existente | Mensajes explícitamente publicados |
| **Source of truth** | La BBDD (Cosmos) | El productor de mensajes |
| **Garantías de orden** | Por partition key | FIFO con sessions |
| **Retención** | Los datos siguen en Cosmos | TTL configurable (días) |
| **Replay** | Sí, desde cualquier punto | No (mensajes se consumen) |
| **Coste** | RUs del Cosmos | €/mensaje + base namespace |
| **Latencia** | <1 seg típico | <100 ms típico |
| **Acoplamiento** | Acoplado a Cosmos | Cualquier productor |

**Cuándo Change Feed:**

```csharp
// ✅ Reaccionar a cambios EN tu BBDD operacional
[Function("ProyectarPedidoEnBusqueda")]
public async Task Run(
    [CosmosDBTrigger(
        databaseName: "Ventas",
        containerName: "pedidos",
        Connection = "Cosmos",
        LeaseContainerName = "leases")]
    IReadOnlyList<Pedido> changes,
    [CosmosDBOutput(
        databaseName: "Search",
        containerName: "pedidos-index")]
    IAsyncCollector<PedidoIndexEntry> indexedItems)
{
    foreach (var pedido in changes)
    {
        // Materializar vista para búsqueda
        await indexedItems.AddAsync(new PedidoIndexEntry
        {
            Id = pedido.Id,
            ClienteName = pedido.ClienteName,
            // Campos que queremos indexar
        });
    }
}
```

**Cuándo Service Bus:**

```csharp
// ✅ Comunicación entre microservicios desacoplados
[Function("ProcesarPagoConfirmado")]
public async Task Run(
    [ServiceBusTrigger("pagos-confirmados", Connection = "ServiceBus")]
    PagoConfirmadoMessage message)
{
    // Reaccionar a evento publicado por otro microservicio
    await UpdatePedidoStateAsync(message.PedidoId, "pagado");
}
```

**Patrón híbrido (típico en producción):**

```
┌─────────────┐   Change      ┌──────────────┐
│  Cosmos     │  ───feed──>  │  Function:    │
│  Pedidos    │              │  ProyectarToSB│
└─────────────┘              └──────┬───────┘
                                    │
                                    │ publish
                                    ▼
                             ┌──────────────┐
                             │ Service Bus  │
                             │ Topic        │
                             └──────┬───────┘
                                    │
                          ┌─────────┼─────────┐
                          ▼         ▼         ▼
                     [Servicio A][Servicio B][Servicio C]
```

**Reglas decisión:**

```
¿Necesitáis reaccionar a cambios en VUESTRA BBDD?
  → Change Feed

¿Necesitáis comunicar entre microservicios?
  → Service Bus

¿Necesitáis lo dos?
  → Patrón híbrido: Change Feed → publica a Service Bus
  
¿Workflow con humanos en el loop?
  → Logic Apps + Service Bus (no Change Feed)
```

## Slide 22 — Performance y RU consumption del Change Feed

Change Feed consume RUs como cualquier operación de Cosmos. Sin monitoring, vuestra factura sorprende.

**Cómo se cobran las RUs del Change Feed:**

```
1. Lectura del feed (cada poll del listener):
   - 1 RU por documento leído (aprox)
   - Mínimo 2 RU por poll aunque no haya cambios

2. Lease container operations:
   - Read lease: ~1 RU
   - Update lease checkpoint: ~10 RU (escritura)
   - Frecuencia: ~1 update cada minuto por partición física

3. Si tu trigger procesa el documento y vuelve a Cosmos:
   - Updates / Reads adicionales se cobran normalmente
```

**Estimación realista:**

```
Container con 10 millones documentos, 1000 cambios/segundo:
- Lectura del feed: ~3.6M RUs/hora consumidas
- Lease updates: ~36K RUs/hora (60 min × 60 partitions × 10 RU)
- Total Change Feed: ~3.6M RUs/hora

Si Cosmos tiene 5000 RU/s provisionados:
- Total: 18M RUs/hora capacidad
- Change Feed consume: 20% del throughput
- Resto: queries, writes, reads de la app

Si fueras Serverless: ~€0.90/hora solo por Change Feed
```

**Optimizaciones:**

**1. Configurar `MaxItemsPerInvocation` para batching:**

```csharp
[CosmosDBTrigger(
    databaseName: "Ventas",
    containerName: "pedidos",
    LeaseContainerName = "leases",
    MaxItemsPerInvocation = 100,  // Default 100, ajustar según latencia tolerable
    StartFromBeginning = false)]
IReadOnlyList<Pedido> changes
```

**2. Configurar `FeedPollDelay` para reducir polling:**

```csharp
// En host.json
{
  "extensions": {
    "cosmosDB": {
      "leaseRenewInterval": "00:00:17",
      "leaseAcquireInterval": "00:00:13",
      "leaseExpirationInterval": "00:01:00",
      "feedPollDelay": "00:00:05"  // Poll cada 5 seg en vez de 1
    }
  }
}
```

**Trade-off:**
- `feedPollDelay: 1s` → cambios casi en tiempo real, más RUs consumidas
- `feedPollDelay: 5s` → 80% menos polls, latencia hasta 5 seg

**3. Filtrar en el código (no consumir RUs procesando lo que no interesa):**

```csharp
foreach (var pedido in changes)
{
    // Skip rápido si no relevante (no hace nuevas queries)
    if (pedido.Estado != "Confirmado") continue;
    if (pedido.Total < 100) continue;
    
    // Solo procesar los que importan
    await ProcesarPedidoConfirmadoAsync(pedido);
}
```

## Slide 25 — Filtros y projection en el Change Feed

Por defecto, Change Feed entrega TODO el documento. En 2026 hay opciones para optimizar:

**Filtrado en código (lo más simple):**

```csharp
[Function("ProcesarSoloConfirmados")]
public async Task Run(
    [CosmosDBTrigger(...)] IReadOnlyList<Pedido> pedidos,
    FunctionContext ctx)
{
    // Filtro inline: solo procesar lo relevante
    var confirmados = pedidos.Where(p => p.Estado == "Confirmado").ToList();
    
    if (!confirmados.Any())
    {
        _logger.LogDebug("Sin pedidos confirmados en este batch. Skip.");
        return;
    }
    
    _logger.LogInformation(
        "Procesando {Confirmed} de {Total} pedidos",
        confirmados.Count, pedidos.Count);
    
    foreach (var pedido in confirmados)
        await ProcesarConfirmadoAsync(pedido);
}
```

**Pro:** Simple, sin configuración extra
**Contra:** Cosmos sigue cargando TODOS los documentos, los filtras después

**Projection (transformar antes de procesar):**

```csharp
public class PedidoSummary  // DTO con solo lo necesario
{
    public string Id { get; set; } = "";
    public string Estado { get; set; } = "";
    public decimal Total { get; set; }
    public string ClienteId { get; set; } = "";
}

[Function("ProcesarSummaries")]
public async Task Run(
    [CosmosDBTrigger(...)] IReadOnlyList<PedidoSummary> summaries)
{
    // Cosmos serializa a PedidoSummary directamente
    // Reduce memoria si Pedido completo es grande (con muchos campos)
    foreach (var summary in summaries)
        await ProcesarSummaryAsync(summary);
}
```

**Pro:** Menos memoria si el documento original es grande
**Contra:** Cosmos lee el documento entero igual; solo ahorra memoria en proceso

**All Versions and Deletes mode (preview en 2026):**

```csharp
// Capturar también borrados (no solo creates/updates)
[Function("AuditChangeFeed")]
public async Task Run(
    [CosmosDBTrigger(
        databaseName: "Ventas",
        containerName: "pedidos",
        LeaseContainerName = "leases-audit",
        FeedPollDelay = "00:00:05",
        ChangeFeedMode = ChangeFeedMode.AllVersionsAndDeletes)]  // ← preview
    IReadOnlyList<dynamic> changes)
{
    foreach (var change in changes)
    {
        var operationType = change.metadata?.operationType?.ToString();
        // operationType: "create" | "replace" | "delete"
        
        if (operationType == "delete")
        {
            await AuditDeleteAsync(change.metadata.previousImage);
        }
    }
}
```

**Cuándo usar All Versions:**
- ✅ Audit logs completos (compliance)
- ✅ Replicación/backup de cambios
- ✅ Detección de patrones de borrado

**Limitaciones (Apr 2026):**
- Solo containers nuevos (no se puede activar en existentes)
- Retención limitada (default 5 minutos, configurable hasta 7 días)
- RU consumption mayor

**Patrón pro-tip: indexes específicos para filtros frecuentes**

```bash
# Si filtráis siempre por estado, indexar ese campo
az cosmosdb sql container update \
  --account-name cosmos-ventas \
  --database-name Ventas \
  --resource-group rg-ventas \
  --name pedidos \
  --idx '[
    {
      "path": "/estado/?",
      "indexes": [{ "kind": "Range", "dataType": "String", "precision": -1 }]
    }
  ]'
```

**Decisión final:**

```
Filtrado simple, mensajes de cualquier tamaño → filtrar en código
Documento original muy grande → projection con DTO
Necesitáis capturar deletes → AllVersionsAndDeletes mode
Filtros muy específicos a alto volumen → considerar Synapse Link
```

## Slide 26 — Migration patterns: SQL → Cosmos via Change Feed

Change Feed es la herramienta perfecta para migrar de SQL Server a Cosmos sin downtime. Patrón que se ve mucho en producción:

**Estrategia: Strangler Fig pattern aplicado a BBDD:**

```
FASE 1: Doble escritura
┌────────┐   write    ┌─────────┐
│  App   │ ─────────> │ SQL     │ (origen)
│        │            └─────────┘
│        │   write    ┌─────────┐
│        │ ─────────> │ Cosmos  │ (destino, en construcción)
└────────┘            └─────────┘

FASE 2: Reads desde Cosmos, writes a ambos
┌────────┐   write    ┌─────────┐
│  App   │ ─────────> │ SQL     │
│        │   write    ┌─────────┐
│        │ ─────────> │ Cosmos  │
│        │   read     │         │
│        │ <──────────│         │
└────────┘            └─────────┘

FASE 3: Solo Cosmos
┌────────┐            ┌─────────┐
│  App   │ <────────> │ Cosmos  │
└────────┘            └─────────┘
                      
                      SQL: archivado o eliminado
```

**Implementación de la fase 1 con Change Feed inverso:**

```csharp
// Function: detectar cambios en SQL (mediante CDC) y replicar a Cosmos
[Function("ReplicarPedidoSqlACosmos")]
public async Task Run(
    [SqlTrigger("[dbo].[Pedidos]", "SqlConnection")]
    IReadOnlyList<SqlChange<PedidoSqlRow>> sqlChanges,
    [CosmosDBOutput(
        databaseName: "Ventas",
        containerName: "pedidos",
        Connection = "Cosmos",
        PartitionKey = "/clienteId")]
    IAsyncCollector<PedidoCosmosDoc> output)
{
    foreach (var change in sqlChanges)
    {
        var pedidoSql = change.Item;
        
        if (change.Operation == SqlChangeOperation.Delete)
        {
            // Borrar de Cosmos también
            await DeleteFromCosmosAsync(pedidoSql.Id, pedidoSql.ClienteId);
            continue;
        }
        
        // Mapear schema SQL → schema Cosmos
        var doc = new PedidoCosmosDoc
        {
            Id = pedidoSql.Id.ToString(),
            ClienteId = pedidoSql.ClienteId.ToString(),
            Total = pedidoSql.Total,
            Estado = pedidoSql.Estado,
            FechaCreacion = pedidoSql.CreatedAt,
            // Desnormalización: meter datos del cliente en el documento
            ClienteName = await _clienteService.GetNameAsync(pedidoSql.ClienteId),
            
            // Metadata para tracking de migración
            _migrationSource = "sql-server",
            _migrationDate = DateTime.UtcNow,
            _sqlVersion = pedidoSql.RowVersion
        };
        
        await output.AddAsync(doc);
    }
    
    _logger.LogInformation("Replicados {Count} cambios desde SQL", sqlChanges.Count);
}
```

**Verificación de consistencia (Function de auditoría):**

```csharp
[Function("AuditarConsistenciaSqlCosmos")]
public async Task Run(
    [TimerTrigger("0 */15 * * * *")] TimerInfo timer,  // Cada 15 min
    [SqlInput("SELECT COUNT(*) AS Total FROM Pedidos WHERE CreatedAt > DATEADD(hour,-1,GETUTCDATE())")]
    IEnumerable<CountRow> sqlCounts)
{
    var sqlCount = sqlCounts.First().Total;
    
    // Contar en Cosmos
    var cosmosCount = await _cosmosClient
        .GetContainer("Ventas", "pedidos")
        .GetItemQueryIterator<int>(
            "SELECT VALUE COUNT(1) FROM c WHERE c._migrationSource = 'sql-server' AND c._migrationDate > GetCurrentDateTime() - 60*60*1000")
        .ReadNextAsync();
    
    var diff = Math.Abs(sqlCount - cosmosCount.First());
    var diffPercent = sqlCount > 0 ? diff * 100.0 / sqlCount : 0;
    
    if (diffPercent > 1)
    {
        _logger.LogError(
            "Inconsistencia detectada: SQL={Sql}, Cosmos={Cosmos}, diff={Diff}%",
            sqlCount, cosmosCount.First(), diffPercent);
        
        await SendAlertAsync(new MigrationAlert { Difference = diff });
    }
}
```

**Cutover (paso final, fase 3):**

```csharp
// Feature flag para alternar fuente de reads
public class PedidoRepository : IPedidoRepository
{
    private readonly IFeatureManager _features;
    private readonly SqlConnection _sql;
    private readonly CosmosClient _cosmos;
    
    public async Task<Pedido> GetAsync(string id)
    {
        if (await _features.IsEnabledAsync("ReadFromCosmos"))
        {
            return await ReadFromCosmosAsync(id);
        }
        return await ReadFromSqlAsync(id);
    }
}
```

**Timeline típico de migración:**

```
Semana 1-2: Schema en Cosmos + doble escritura activada
Semana 3-4: Verificación consistencia + alertas
Semana 5-6: Reads desde Cosmos para % gradual de usuarios (canary)
Semana 7-8: 100% reads desde Cosmos, SQL solo para reads de auditoría
Semana 9+: SQL en read-only mode, planificar deprecación
```

**Riesgos típicos:**

```
❌ Schema mismatch: Cosmos espera string, SQL devuelve int
   → Tests de mapping exhaustivos antes de cutover

❌ Performance regression: queries que SQL hacía bien, Cosmos costoso (sin partition key)
   → Diseñar partition key correctamente ANTES, no después

❌ Cost overrun: Cosmos cobra por RU, lecturas mal diseñadas explotan factura
   → Monitoring durante migración (alertas de RU)

❌ Inconsistencia eventual: Change Feed tarda 1-5 seg en replicar
   → No hacer reads inmediatos tras writes en período de coexistencia
```

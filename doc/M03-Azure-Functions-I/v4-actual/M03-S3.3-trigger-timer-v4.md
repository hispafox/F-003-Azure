## Slide 2 — Qué es un Timer Trigger

Un **Timer Trigger** ejecuta una función según una expresión CRON. Es el equivalente serverless de un cron job de Linux o un Scheduled Task de Windows.

**Cuándo lo usaréis:**

- Limpiezas nocturnas de datos antiguos
- Health checks periódicos a APIs externas
- Generación de informes diarios/semanales
- Renovación de tokens y certificados
- Sincronizaciones programadas con sistemas legacy
- Pre-cargar caches antes del horario laboral

**Ventajas sobre alternativas (cron en VM, Logic Apps Schedule):**

- ✅ No mantenéis VMs ni servidores
- ✅ Pago por ejecución (Consumption Plan)
- ✅ Escalado automático y alta disponibilidad
- ✅ Logs y métricas integrados con Application Insights
- ✅ Deploy con el resto del código (versionado en git)

**Lo que un Timer Trigger NO debe hacer:**

- ❌ Procesos largos (>10 min en Consumption, ajustar timeout)
- ❌ Tareas que dependen del orden de otras (usad Durable Functions)
- ❌ Tareas que requieren ejecución exactamente una vez (Singleton ayuda pero no garantiza)

## Slide 3 — Timer Trigger mínimo

```csharp
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class LimpiezaNocturna
{
    private readonly ILogger<LimpiezaNocturna> _logger;

    public LimpiezaNocturna(ILogger<LimpiezaNocturna> logger)
    {
        _logger = logger;
    }

    [Function("LimpiezaNocturna")]
    public void Run([TimerTrigger("0 0 3 * * *")] TimerInfo timer)
    {
        _logger.LogInformation(
            "Limpieza ejecutada a las {Time} (próxima: {Next})",
            DateTime.UtcNow,
            timer.ScheduleStatus?.Next);
        
        // Lógica de limpieza aquí
    }
}
```

**Anatomía del atributo `[TimerTrigger]`:**

```
[TimerTrigger("0 0 3 * * *")]
                │
                └── Expresión CRON (6 campos)
                    Significa: "todos los días a las 03:00 UTC"
```

**Lo que recibe la función:**

```csharp
TimerInfo timer
├── timer.ScheduleStatus.Last      → última ejecución
├── timer.ScheduleStatus.Next      → próxima ejecución programada
├── timer.IsPastDue                → ¿se perdió alguna ejecución?
└── timer.Schedule                 → configuración del schedule
```

## Slide 4 — Expresiones CRON: la sintaxis

Azure Functions usa **NCRONTAB**, una variante con 6 campos (incluye segundos):

```
 ┌──────────── segundo (0-59)
 │ ┌────────── minuto (0-59)
 │ │ ┌──────── hora (0-23)
 │ │ │ ┌────── día del mes (1-31)
 │ │ │ │ ┌──── mes (1-12)
 │ │ │ │ │ ┌── día de la semana (0-6, 0=domingo)
 │ │ │ │ │ │
 0 0 3 * * *
```

**Operadores soportados:**

```
*       → cualquier valor (wildcard)
,       → lista de valores: "0,15,30,45"
-       → rango: "9-17" (de las 9 a las 17)
/       → step: "*/5" (cada 5 unidades)
1-5     → de lunes a viernes (en el último campo)
```

**⚠️ Diferencia con cron de Linux:**

```
Linux cron (5 campos):     "*/5 * * * *"        cada 5 min
NCRONTAB (6 campos):       "0 */5 * * * *"      cada 5 min

Si copiáis CRON de Linux a Functions sin añadir el campo de segundos,
NO os ejecutará y tampoco os dará error claro.
```

**Herramienta útil:** [crontab.guru](https://crontab.guru) sirve para validar lógica, pero recordad que tiene 5 campos. Para NCRONTAB añadid `0 ` al principio.

## Slide 5 — Expresiones CRON: ejemplos prácticos

Los 12 patrones más comunes que vais a necesitar:

```csharp
// Cada minuto (testing)
[TimerTrigger("0 * * * * *")]

// Cada 5 minutos
[TimerTrigger("0 */5 * * * *")]

// Cada hora en punto
[TimerTrigger("0 0 * * * *")]

// Diariamente a las 03:00 UTC
[TimerTrigger("0 0 3 * * *")]

// Solo días laborables a las 09:00
[TimerTrigger("0 0 9 * * 1-5")]

// Lunes a las 08:00
[TimerTrigger("0 0 8 * * 1")]

// Día 1 de cada mes a las 02:00
[TimerTrigger("0 0 2 1 * *")]

// Cada 30 minutos en horario laboral (9-18)
[TimerTrigger("0 */30 9-18 * * 1-5")]

// Cada 2 horas durante el día (06-22)
[TimerTrigger("0 0 6-22/2 * * *")]

// Al minuto 0 y 30 de cada hora
[TimerTrigger("0 0,30 * * * *")]

// Domingos a medianoche
[TimerTrigger("0 0 0 * * 0")]

// Una vez al año (1 de enero a las 00:00)
[TimerTrigger("0 0 0 1 1 *")]
```

**Tip pro: expresión desde configuración**

```csharp
// Útil para cambiar schedule sin redeploy
[TimerTrigger("%CronExpression%")]

// En local.settings.json:
"CronExpression": "0 0 3 * * *"
```

## Slide 6 — Zona horaria: cuidado con los UTC

**Por defecto, todos los timers se ejecutan en UTC.** Esto es la fuente de bugs número uno con Timer Triggers.

**Ejemplo del problema:**

```csharp
// Pretende ser "diario a las 9 AM hora de Madrid"
[TimerTrigger("0 0 9 * * *")]
public void EnviarInforme(...)
```

En UTC, esto se ejecuta a las 9:00 UTC = **10:00 Madrid en invierno** y **11:00 Madrid en verano**.

**Solución: configurar `WEBSITE_TIME_ZONE`:**

```bash
# Configurar la app setting
az functionapp config appsettings set \
  --name func-tareas-prod \
  --resource-group rg-prod \
  --settings WEBSITE_TIME_ZONE="Romance Standard Time"

# Linux: usa formato IANA
WEBSITE_TIME_ZONE="Europe/Madrid"

# Windows: usa formato Windows
WEBSITE_TIME_ZONE="Romance Standard Time"
```

**Tras configurar:**

```csharp
[TimerTrigger("0 0 9 * * *")]
// Ahora se ejecuta a las 9:00 hora de Madrid
// El cambio horario se respeta automáticamente
```

**Trampa común con Linux:** algunos planes Consumption en Linux no soportan `WEBSITE_TIME_ZONE`. Verificad la documentación según vuestro plan.

**Plan B sin timezone configurada:** calculad manualmente:

```csharp
[TimerTrigger("0 0 8 * * *")]  // 8:00 UTC = 9:00 Madrid invierno
public void Tarea(...)
{
    var madridTime = TimeZoneInfo.ConvertTimeFromUtc(
        DateTime.UtcNow,
        TimeZoneInfo.FindSystemTimeZoneById("Europe/Madrid"));
    
    _logger.LogInformation("Hora local: {Time}", madridTime);
}
```

## Slide 7 — IsPastDue: ejecuciones perdidas

Si la Function App estuvo apagada (deploy, mantenimiento, fallo) cuando tocaba ejecutar el timer, podéis decidir qué hacer al volver:

```csharp
[Function("InformeDiario")]
public async Task Run([TimerTrigger("0 0 9 * * *")] TimerInfo timer)
{
    if (timer.IsPastDue)
    {
        _logger.LogWarning(
            "Ejecución perdida detectada. Última: {Last}",
            timer.ScheduleStatus?.Last);
        
        // Decisión 1: ejecutar igualmente (catch-up)
        await GenerarInformeAsync();
        
        // Decisión 2: ejecutar solo si la pérdida fue reciente
        var lastRun = timer.ScheduleStatus?.Last ?? DateTime.MinValue;
        if (DateTime.UtcNow - lastRun < TimeSpan.FromHours(2))
        {
            await GenerarInformeAsync();
        }
        
        // Decisión 3: ignorar y esperar la próxima
        return;
    }
    
    // Ejecución normal
    await GenerarInformeAsync();
}
```

**Cuándo cada estrategia:**

| Estrategia | Caso de uso |
|---|---|
| Siempre catch-up | Cleanup nocturno (es OK ejecutarlo "tarde") |
| Catch-up con ventana | Informes diarios (no tiene sentido el de ayer hoy) |
| Ignorar | Renovación de tokens (la próxima refrescará) |
| Doble check (idempotencia) | Cualquier producción real |

**Detalles importantes:**

- `IsPastDue` solo funciona si `useMonitor: true` en el binding (default)
- El estado se persiste en `AzureWebJobsStorage` → mismo storage para todas las instancias
- En desarrollo local NO se respeta entre arranques (cada `func start` empieza limpio)

## Slide 8 — Singleton: evitar ejecuciones simultáneas

Si vuestra Function App tiene múltiples instancias (escalado horizontal), un timer **se ejecutará en TODAS las instancias** salvo que useis Singleton.

**Sin Singleton (problema):**

```
Instance 1 → Timer ejecuta a las 03:00 → Eliminar 1000 records
Instance 2 → Timer ejecuta a las 03:00 → Eliminar los mismos 1000 records
Instance 3 → Timer ejecuta a las 03:00 → Race condition + double processing
```

**Con Singleton (solución):**

```csharp
using Microsoft.Azure.WebJobs;

public class LimpiezaSemanal
{
    [Singleton]  // ← Solo UNA instancia ejecuta a la vez
    [Function("LimpiezaSemanal")]
    public async Task Run(
        [TimerTrigger("0 0 4 * * 0")] TimerInfo timer,  // Domingo 4:00
        FunctionContext context)
    {
        _logger.LogInformation("Iniciando limpieza semanal en instancia {InstanceId}",
            context.InvocationId);
        
        // Tarea pesada - solo se ejecuta en una instancia
        await EliminarRegistrosAntiguosAsync();
    }
}
```

**Cómo funciona:**

```
Singleton usa un blob lock en AzureWebJobsStorage:
1. Instance 1 intenta adquirir lock → ✅ lo consigue → ejecuta
2. Instance 2 intenta adquirir lock → ❌ ya está tomado → skip
3. Instance 3 intenta adquirir lock → ❌ ya está tomado → skip
4. Cuando Instance 1 termina → libera lock
```

**Cuándo usarlo siempre:**

- Tareas que escriben en BBDD compartida
- Tareas que mandan notificaciones (evitar duplicados)
- Tareas que mueven/eliminan archivos
- Cualquier operación con side-effects no idempotentes

**Cuándo NO necesitáis Singleton:**

- Tarea pura de lectura (idempotente por naturaleza)
- Función ya idempotente por diseño
- Plan de Consumption con auto-scale a 1 (raro)

## Slide 9 — Timer + Output Bindings: ejemplo real

Combinar Timer con output bindings reduce código boilerplate:

```csharp
public class GenerarInformeDiario
{
    private readonly ILogger _logger;
    private readonly IInformeService _informeService;

    public GenerarInformeDiario(
        ILogger<GenerarInformeDiario> logger,
        IInformeService informeService)
    {
        _logger = logger;
        _informeService = informeService;
    }

    // Output binding: el return se escribe a Cosmos automáticamente
    [Function("GenerarInformeDiario")]
    [CosmosDBOutput(
        databaseName: "analytics",
        containerName: "informes",
        Connection = "CosmosDb")]
    public async Task<Informe> Run(
        [TimerTrigger("0 0 6 * * *")] TimerInfo timer)  // Diario 06:00 UTC
    {
        var ayer = DateTime.UtcNow.Date.AddDays(-1);
        
        _logger.LogInformation("Generando informe para {Fecha}", ayer);
        
        var informe = new Informe
        {
            Id = $"informe-{ayer:yyyy-MM-dd}",
            Fecha = ayer,
            TotalPedidos = await _informeService.ContarPedidosAsync(ayer),
            FacturacionTotal = await _informeService.SumarFacturacionAsync(ayer),
            ClientesActivos = await _informeService.ContarClientesAsync(ayer),
            GeneradoEn = DateTime.UtcNow
        };
        
        _logger.LogInformation(
            "Informe {Id}: {Pedidos} pedidos, {Total}€",
            informe.Id, informe.TotalPedidos, informe.FacturacionTotal);
        
        return informe;  // Se persiste automáticamente en Cosmos
    }
}
```


## Slide 10 — Timer + HTTP Client: sincronización con API externa

Patrón común: cada N tiempo, llamar a una API externa y procesar resultado:

```csharp
public class SincronizarPrecios
{
    private readonly HttpClient _http;
    private readonly ILogger _logger;

    public SincronizarPrecios(IHttpClientFactory factory, ILogger<SincronizarPrecios> logger)
    {
        _http = factory.CreateClient("preciosApi");
        _logger = logger;
    }

    [Function("SincronizarPrecios")]
    public async Task Run(
        [TimerTrigger("0 0 */2 * * *")] TimerInfo timer)  // Cada 2 horas
    {
        try
        {
            using var response = await _http.GetAsync("/api/precios?desde=last-sync");
            response.EnsureSuccessStatusCode();
            
            var precios = await response.Content.ReadFromJsonAsync<List<Precio>>();
            
            if (precios is null || !precios.Any())
            {
                _logger.LogInformation("No hay precios nuevos para sincronizar");
                return;
            }
            
            await _precioService.ActualizarBatchAsync(precios);
            
            _logger.LogInformation(
                "Sincronizados {Count} precios. Próxima ejecución: {Next}",
                precios.Count,
                timer.ScheduleStatus?.Next);
        }
        catch (HttpRequestException ex)
        {
            _logger.LogError(ex, "API externa no disponible. Reintentar en próxima ejecución");
            // No lanzamos: el timer seguirá funcionando en próxima cita
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Error inesperado durante sincronización");
            throw;  // Lanzamos para que aparezca como ejecución fallida en métricas
        }
    }
}
```

**Configuración de `HttpClient` con resiliencia (en `Program.cs`):**

```csharp
builder.Services.AddHttpClient("preciosApi", client =>
{
    client.BaseAddress = new Uri(builder.Configuration["PreciosApi:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(30);
})
.AddStandardResilienceHandler();  // Retry, circuit breaker, timeout (built-in .NET 8)
```

**Decisiones de diseño aquí:**

- ✅ Catch específico de `HttpRequestException` → no fallar la ejecución
- ✅ Catch general → fallar para que se vea en métricas
- ✅ Resilience built-in en lugar de Polly manual
- ✅ Log con próxima ejecución para context

## Slide 11 — 5 patrones de timer en producción

Los casos de uso típicos en empresas reales:

**Patrón 1 — Cleanup nocturno**
```
CRON:    "0 0 3 * * *"  (3:00 UTC, baja carga)
Acción:  DELETE FROM logs WHERE created < NOW() - 90 days
         DELETE FROM blobs WHERE container = 'temp' AND created < NOW() - 7 days
Singleton: ✅ obligatorio
```

**Patrón 2 — Health check de dependencias externas**
```
CRON:    "0 */5 * * * *"  (cada 5 min)
Acción:  Pingear APIs externas, alertar si responden 5xx o timeout
         Reportar disponibilidad a App Insights como custom metric
Singleton: ❌ no necesario (idempotente)
```

**Patrón 3 — Informe semanal a stakeholders**
```
CRON:    "0 0 8 * * 1"  (lunes 08:00 UTC)
Acción:  Calcular KPIs de la semana anterior
         Generar PDF
         Enviar email a la lista
Singleton: ✅ obligatorio (evitar duplicados de email)
```

**Patrón 4 — Renovación de tokens / certificados**
```
CRON:    "0 0 */12 * * *"  (cada 12 horas)
Acción:  Refresh token de API externa antes que caduque
         Guardar nueva versión en Key Vault
         Notificar si falla (compliance crítico)
Singleton: ✅ obligatorio
```

**Patrón 5 — Cache warming**
```
CRON:    "0 50 7 * * 1-5"  (L-V 7:50, 10 min antes de abrir)
Acción:  Pre-cargar Redis con datos frecuentes
         Evita cold queries en hora punta de los usuarios
Singleton: ❌ no necesario (idempotente, refrescar cache es OK)
```

**Patrón 6 (bonus) — Reconciliación de datos**
```
CRON:    "0 30 2 * * *"  (diario 02:30)
Acción:  Comparar nuestra BBDD con sistema legacy
         Detectar desincronizaciones
         Generar tickets automáticos para cada divergencia
Singleton: ✅ obligatorio
```

## Slide 12 — Idempotencia: la regla del Timer en producción

**Asumid siempre que un Timer puede ejecutarse 2 veces** (por crash, retry, race condition). Vuestro código debe soportar esto sin causar daño.

**Patrón de idempotencia con marcador en BBDD:**

```csharp
[Function("EnviarInformeDiario")]
public async Task Run(
    [TimerTrigger("0 0 8 * * *")] TimerInfo timer,
    [CosmosDBInput(...)] CosmosClient cosmos)
{
    var fecha = DateTime.UtcNow.Date;
    var marcadorId = $"informe-enviado-{fecha:yyyy-MM-dd}";
    
    var container = cosmos.GetContainer("operations", "marcadores");
    
    // 1. Verificar si ya se ejecutó hoy
    try
    {
        var existing = await container.ReadItemAsync<Marcador>(
            marcadorId, new PartitionKey("informes"));
        
        _logger.LogInformation(
            "Informe ya enviado a las {Hora}. Skip.",
            existing.Resource.EjecutadoEn);
        return;  // Idempotente: si ya se hizo, no repetir
    }
    catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
    {
        // No existe → continuar con la ejecución
    }
    
    // 2. Ejecutar la tarea
    await EnviarInformeAsync(fecha);
    
    // 3. Marcar como completado (intento de evitar duplicados)
    await container.CreateItemAsync(new Marcador
    {
        Id = marcadorId,
        Tipo = "informes",
        EjecutadoEn = DateTime.UtcNow,
        Detalles = $"Informe del {fecha:yyyy-MM-dd}"
    }, new PartitionKey("informes"));
}
```

**Patrón alternativo con lock distribuido (Storage):**

```csharp
public async Task Run([TimerTrigger("0 0 3 * * *")] TimerInfo timer)
{
    var leaseClient = blobContainer
        .GetBlobClient("limpieza-nocturna.lock")
        .GetBlobLeaseClient();
    
    try
    {
        // Adquirir lease 60 segundos (auto-libera si crashea)
        var lease = await leaseClient.AcquireAsync(TimeSpan.FromSeconds(60));
        
        // Tarea aquí (renueva el lease cada 30s si dura más)
        await DoCleanupAsync();
        
        await leaseClient.ReleaseAsync();
    }
    catch (RequestFailedException ex) when (ex.Status == 409)
    {
        _logger.LogInformation("Otra instancia tiene el lock. Skip.");
    }
}
```

**Regla:** Singleton resuelve el caso "múltiples instancias", pero **no** resuelve "el timer falló y reintenta". Para producción real, idempotencia + Singleton es la combinación segura.

## Slide 13 — Output a Cosmos: caso real de informes

Ejemplo completo de patrón "generar informe semanal y persistirlo":

```csharp
public class InformeSemanal
{
    private readonly IPedidoRepository _pedidos;
    private readonly ILogger<InformeSemanal> _logger;

    public InformeSemanal(IPedidoRepository pedidos, ILogger<InformeSemanal> logger)
    {
        _pedidos = pedidos;
        _logger = logger;
    }

    [Function("GenerarInformeSemanal")]
    [CosmosDBOutput(
        databaseName: "analytics",
        containerName: "informes-semanales",
        Connection = "CosmosDb",
        CreateIfNotExists = true,
        PartitionKey = "/anio")]
    public async Task<InformeSemanalDoc?> Run(
        [TimerTrigger("0 0 8 * * 1")] TimerInfo timer,  // Lunes 08:00 UTC
        FunctionContext ctx)
    {
        var hoy = DateTime.UtcNow.Date;
        var lunesAnterior = hoy.AddDays(-7);
        var domingoAnterior = hoy.AddDays(-1);
        
        var idInforme = $"semana-{lunesAnterior:yyyy-MM-dd}";
        var anio = lunesAnterior.Year;
        
        _logger.LogInformation(
            "Generando informe semana {Inicio} a {Fin}",
            lunesAnterior, domingoAnterior);
        
        var pedidos = await _pedidos.GetByDateRangeAsync(lunesAnterior, domingoAnterior);
        
        if (!pedidos.Any())
        {
            _logger.LogWarning("No hay pedidos en la semana. Skip informe.");
            return null;  // No persiste si return es null
        }
        
        var informe = new InformeSemanalDoc
        {
            Id = idInforme,
            Anio = anio.ToString(),
            SemanaInicio = lunesAnterior,
            SemanaFin = domingoAnterior,
            TotalPedidos = pedidos.Count,
            FacturacionTotal = pedidos.Sum(p => p.Total),
            TicketMedio = pedidos.Average(p => p.Total),
            ClientesUnicos = pedidos.Select(p => p.ClienteId).Distinct().Count(),
            ProductosMasVendidos = pedidos
                .SelectMany(p => p.Items)
                .GroupBy(i => i.ProductoId)
                .Select(g => new TopProducto
                {
                    ProductoId = g.Key,
                    Cantidad = g.Sum(i => i.Cantidad)
                })
                .OrderByDescending(p => p.Cantidad)
                .Take(10)
                .ToList(),
            GeneradoEn = DateTime.UtcNow
        };
        
        _logger.LogInformation(
            "Informe {Id}: {Pedidos} pedidos, {Total:C} facturación",
            idInforme, informe.TotalPedidos, informe.FacturacionTotal);
        
        return informe;
    }
}
```

**Tip:** retornar `null` cuando no hay datos evita persistir documentos vacíos en Cosmos (ahorra RUs).

## Slide 14 — Monitorización: ¿se está ejecutando bien?

Sin observabilidad, los timers son una caja negra: o funcionan o no.

**1. KQL queries para Application Insights:**

```kusto
// ¿Se ejecutaron todos los timers que tocaban?
requests
| where timestamp > ago(7d)
| where operation_Name startswith "TimerTrigger"
| summarize 
    Ejecuciones = count(),
    Failed = countif(success == false),
    LastRun = max(timestamp)
  by operation_Name
| order by Ejecuciones desc

// Tarea diaria que NO se ejecutó hoy
requests
| where timestamp > ago(2d)
| where operation_Name == "InformeDiario"
| summarize Last = max(timestamp)
| extend NoEjecutadoUltimas = datetime_diff('hour', now(), Last)
| where NoEjecutadoUltimas > 25  // Esperaba ejecutarse hace <25h

// Duración de timer triggers (buscar regresiones)
requests
| where timestamp > ago(7d)
| where operation_Name startswith "TimerTrigger"
| summarize 
    P50 = percentile(duration, 50),
    P95 = percentile(duration, 95),
    P99 = percentile(duration, 99),
    Max = max(duration)
  by operation_Name, bin(timestamp, 1d)
| render timechart
```

**2. Métricas custom desde el código:**

```csharp
private static readonly Counter<long> _ejecuciones = 
    new Meter("MisTimers", "1.0").CreateCounter<long>("timer.ejecuciones");

private static readonly Histogram<double> _duracion = 
    new Meter("MisTimers", "1.0").CreateHistogram<double>("timer.duracion.ms");

[Function("LimpiezaNocturna")]
public async Task Run([TimerTrigger("0 0 3 * * *")] TimerInfo timer)
{
    var sw = Stopwatch.StartNew();
    var status = "success";
    
    try
    {
        await DoCleanupAsync();
    }
    catch
    {
        status = "failure";
        throw;
    }
    finally
    {
        sw.Stop();
        _ejecuciones.Add(1, new("function", "LimpiezaNocturna"), new("status", status));
        _duracion.Record(sw.Elapsed.TotalMilliseconds, new("function", "LimpiezaNocturna"));
    }
}
```

**3. Alertas básicas que deberíais configurar:**

```bash
# Alerta: tarea diaria que no se ejecutó
az monitor scheduled-query create \
  --name "alert-informe-diario-missing" \
  --condition-query "requests | where operation_Name == 'InformeDiario' | summarize last=max(timestamp) | where datetime_diff('hour', now(), last) > 25" \
  --severity 2 \
  --evaluation-frequency PT1H \
  --window-size PT1H
```

## Slide 16 — Errores comunes y cómo resolverlos

Los 8 errores que veo más frecuentemente con Timer Triggers:

**1. "El timer no se ejecuta nunca"**
```
Causa: CRON con 5 campos (Linux-style)
Síntoma: deploy correcto pero no aparecen ejecuciones en logs
Fix: añadir el campo de segundos al inicio
  ❌ "*/5 * * * *"     (5 campos)
  ✅ "0 */5 * * * *"   (6 campos)
```

**2. "Se ejecuta a hora distinta de la esperada"**
```
Causa: UTC por defecto, no hora local
Fix: configurar WEBSITE_TIME_ZONE
  Linux:   "Europe/Madrid"
  Windows: "Romance Standard Time"
```

**3. "Se ejecuta dos veces simultáneamente"**
```
Causa: múltiples instancias de Function App
Fix: añadir [Singleton] al método
  Verificar: AzureWebJobsStorage compartido entre instancias
```

**4. "No se ejecuta en plan Consumption sin tráfico"**
```
Causa: plan Consumption desactiva instancias sin tráfico
Síntoma: timer cada hora se ejecuta a veces, otras no
Fix opción A: cambiar a Premium (siempre warm) — ~€155/mes
Fix opción B: cambiar a Flex Consumption (mejor balance 2026)
Fix opción C: añadir Always On si está disponible en vuestro plan
```

**5. "Funciona en local pero no en producción"**
```
Causa: AzureWebJobsStorage no configurado en producción
Fix: verificar que App Setting "AzureWebJobsStorage" apunta a un storage real
  En local usa UseDevelopmentStorage=true (Azurite)
  En producción debe ser una connection string a Storage Account real
```

**6. "Timer expira con timeout"**
```
Causa: tarea dura más que el timeout de Functions
Síntoma: ejecución cortada a los 5/10 minutos
Fix opción A: aumentar functionTimeout en host.json
Fix opción B: dividir tarea en chunks y usar Durable Functions (M04)
Fix opción C: usar Premium plan (timeout configurable hasta 1h)
```

**7. "IsPastDue siempre es false aunque debería ser true"**
```
Causa: useMonitor: false en el binding
Fix: useMonitor: true (default, verificar no lo deshabilitasteis)
  Con useMonitor: true, el estado se persiste en AzureWebJobsStorage
```

**8. "Timer dispara pero la lógica falla en silencio"**
```
Causa: excepción capturada y tragada en el código
Síntoma: el request aparece como success en App Insights
Fix: NO hagais catch genérico sin log + rethrow
  Mejor: catch específico → log + decisión + rethrow si crítico
```

## Slide 18 — Timer vs Logic Apps Schedule: cuándo cada uno

A veces no necesitáis un Timer Trigger: Logic Apps tiene un trigger Schedule integrado. ¿Cuándo conviene cada uno?

| Aspecto | Timer Trigger | Logic Apps Schedule |
|---|---|---|
| **Lenguaje** | C# / Python / Node.js | Visual designer (low-code) |
| **Coste base** | €0 (Consumption) | €0.000019/ejecución (Consumption) |
| **Lógica compleja** | ✅ Cualquier código .NET | ⚠️ Limitado a connectors + expresiones |
| **Conectores managed** | ❌ Tienes que codificar todo | ✅ 400+ conectores (SAP, Salesforce, etc.) |
| **Curva de aprendizaje** | C# senior | PM/business analyst |
| **Versionado en git** | ✅ Natural | ⚠️ Posible pero menos cómodo |
| **Tests unitarios** | ✅ Estándar xUnit | ❌ No nativos |
| **Debugging** | ✅ VS Code, breakpoints | ⚠️ Run history en portal |
| **Stateful workflows** | ❌ (necesitas Durable) | ✅ Built-in |
| **Triggers manuales** | API admin | Visual + parámetros |

**Reglas de decisión:**

```
Timer Trigger cuando:
✅ Lógica de procesamiento no trivial
✅ El equipo es .NET (no PM/integration)
✅ Necesitáis tests unitarios sólidos
✅ Procesos de datos masivos (CSVs, BBDD, etc.)
✅ Alta frecuencia (cada minuto o más)

Logic Apps Schedule cuando:
✅ Integraciones con SaaS (Salesforce, Dynamics, M365)
✅ Workflow visual entendible por business
✅ Múltiples sistemas externos en cadena
✅ Aprobaciones humanas en medio (Logic Apps soporta nativamente)
✅ Frecuencia baja (diaria/semanal) y lógica simple
```

**Patrón híbrido común:** Timer Trigger orquesta tareas internas (BBDD, Cosmos, internas), Logic Apps maneja la "última milla" hacia sistemas SaaS.

```
✅ SLA estricto (clientes notarían ejecución tardía)
✅ Tareas con timeout corto (los 1-3s de cold start importan)
✅ Tareas en cadena (cold start se acumula)

❌ Timer diario/semanal (pre-warmed = €€€ desperdiciado)
❌ Tareas que toleran 1-3s de latencia
❌ Workload de testing/desarrollo
```

**Coste vs beneficio:**

```
Premium plan EP1 con 2 instancias min:
- Baseline: ~€155/mes × 2 instances = €310/mes
```

## Slide 20 — Slot deployment con Timer Triggers

Slots son la mejor práctica para deploy sin downtime, pero con timers tienen un comportamiento que conviene entender:

**Comportamiento por defecto:**

```
Slot "production":
├── Timer "LimpiezaNocturna" → ejecuta a las 03:00 ✓
├── Timer "InformeDiario"   → ejecuta a las 06:00 ✓
└── Timer "HealthCheck"     → ejecuta cada 5 min ✓

Slot "staging":
├── Timer "LimpiezaNocturna" → ¿ejecuta? → SÍ por defecto
├── Timer "InformeDiario"   → ¿ejecuta? → SÍ por defecto
└── Timer "HealthCheck"     → ¿ejecuta? → SÍ por defecto

⚠️ PROBLEMA: ambos slots ejecutan los mismos timers en paralelo
  → Cleanup se ejecuta 2 veces
  → Informe se envía 2 veces
  → Tickets duplicados, emails repetidos, etc.
```

**Solución: deshabilitar timers en staging slot:**

```bash
# Opción 1: deshabilitar timers específicos en staging
az functionapp config appsettings set \
  --name func-tareas-prod \
  --resource-group rg-tareas-prod \
  --slot staging \
  --settings AzureWebJobs.LimpiezaNocturna.Disabled=true \
            AzureWebJobs.InformeDiario.Disabled=true \
            AzureWebJobs.HealthCheck.Disabled=true

# Opción 2: marcar como sticky (slot setting)
# Para que la config viaje con el slot al hacer swap
az functionapp config appsettings set \
  --name func-tareas-prod \
  --resource-group rg-tareas-prod \
  --slot staging \
  --slot-settings AzureWebJobs.LimpiezaNocturna.Disabled=true
```

**Tras swap, el comportamiento es:**

```
ANTES DEL SWAP:
- Production slot: timers ENABLED ✓
- Staging slot: timers DISABLED (sticky setting) ✓

DESPUÉS DEL SWAP:
- Production slot (era staging): timers ENABLED ✓ (sticky se quedó)
- Staging slot (era production): timers DISABLED ✓ (sticky se quedó)

Resultado correcto: timers solo ejecutan en producción.
```

**Strategy completa con código condicional:**

```csharp
[Function("LimpiezaNocturna")]
public async Task Run(
    [TimerTrigger("0 0 3 * * *")] TimerInfo timer,
    FunctionContext context)
{
    // Validar que estamos en production slot
    var slotName = Environment.GetEnvironmentVariable("WEBSITE_SLOT_NAME") ?? "Production";
    
    if (slotName != "Production")
    {
        _logger.LogWarning(
            "Timer ejecutándose en slot {Slot}. Skip por seguridad.",
            slotName);
        return;
    }
    
    // Lógica normal
    await DoCleanupAsync();
}
```

**Recomendación:** combinar ambos enfoques (config + código defensivo) para evitar accidentes.

## Slide 21 — Migración desde Hangfire / Quartz.NET

Si venís de aplicaciones .NET tradicionales con Hangfire o Quartz.NET, conviene saber cómo migrar a Functions:

**Comparativa Hangfire vs Functions Timer:**

| Aspecto | Hangfire | Functions Timer |
|---|---|---|
| **Hosting** | Self-hosted (en tu app) | Serverless (Azure managed) |
| **Persistencia** | SQL Server / Redis (tu BBDD) | AzureWebJobsStorage |
| **Dashboard** | UI integrada (`/hangfire`) | Application Insights + portal |
| **Recurring jobs** | `RecurringJob.AddOrUpdate(...)` | `[TimerTrigger("CRON")]` |
| **One-time jobs** | `BackgroundJob.Schedule(...)` | Service Bus scheduled messages |
| **Retry** | Configurable per-job | Configurable en `host.json` |
| **Coste** | Coste de tu app + BBDD | Por ejecución (Consumption) |
| **Escalado** | Manual (auto si tu app escala) | Automático |

**Patrón de migración:**

```csharp
// ANTES (Hangfire en ASP.NET Core)
public class TareasService
{
    public TareasService(IRecurringJobManager mgr)
    {
        mgr.AddOrUpdate<TareasService>(
            "limpieza-nocturna",
            x => x.LimpiarRegistrosAntiguos(),
            "0 3 * * *");  // CRON 5 campos
    }
    
    public async Task LimpiarRegistrosAntiguos()
    {
        await _repo.DeleteOlderThan(DateTime.UtcNow.AddDays(-90));
    }
}

// DESPUÉS (Azure Functions)
public class LimpiezaNocturna
{
    private readonly IRepository _repo;
    
    public LimpiezaNocturna(IRepository repo) => _repo = repo;
    
    [Function("LimpiezaNocturna")]
    public async Task Run([TimerTrigger("0 0 3 * * *")] TimerInfo timer)
    {
        // CRON 6 campos (con segundos al inicio)
        await _repo.DeleteOlderThan(DateTime.UtcNow.AddDays(-90));
    }
}
```

**Comparativa Quartz.NET:**

```csharp
// ANTES (Quartz.NET)
public class LimpiezaJob : IJob
{
    public async Task Execute(IJobExecutionContext context)
    {
        await _repo.DeleteOlderThan(...);
    }
}

// Configuración en Startup
services.AddQuartz(q => 
{
    var jobKey = new JobKey("limpieza");
    q.AddJob<LimpiezaJob>(opts => opts.WithIdentity(jobKey));
    q.AddTrigger(opts => opts
        .ForJob(jobKey)
        .WithCronSchedule("0 0 3 * * ?"));  // Quartz CRON con ? para día semana
});

// DESPUÉS (Functions)
[Function("LimpiezaNocturna")]
public async Task Run([TimerTrigger("0 0 3 * * *")] TimerInfo timer)
{
    await _repo.DeleteOlderThan(...);
}
```

**Diferencias importantes a manejar:**

```
1. CRON syntax:
   Hangfire: 5 campos (Linux-style)
   Quartz:   7 campos (con segundos + año)
   Functions: 6 campos (segundos + 5 estándar)

2. Timezone:
   Hangfire: TimeZoneInfo configurable per-job
   Quartz:   ScheduleBuilder.InTimeZone(...)
   Functions: WEBSITE_TIME_ZONE app setting

3. Persistence:
   Hangfire: tu BBDD (SQL Server, Redis, etc.)
   Quartz: tu BBDD (configurable)
   Functions: AzureWebJobsStorage (Azure Storage Account)

4. Distributed locking:
   Hangfire: built-in con [DisableConcurrentExecution]
   Quartz: @DisallowConcurrentExecution attribute
   Functions: [Singleton] attribute
```

**Cuándo NO migrar:**

- Si tu app es un monolito y el coste de Azure Functions sería más alto
- Si necesitáis dashboards visuales muy personalizados (Hangfire UI)
- Si tenéis lógica de jobs muy entrelazada con código de la app

**Cuándo SÍ migrar:**

- App ya en Azure y queréis quitar componentes self-hosted
- Múltiples timer jobs y mantenimiento de BBDD pesa
- Buscáis pago-por-uso vs hosting fijo
- Vais hacia arquitectura serverless general

## Slide 23 — Coordinación entre múltiples Timer Triggers

Si tenéis varios timers que dependen entre sí (orden de ejecución importa), evitad anti-patterns y usad el patrón correcto:

**❌ Anti-pattern: timers anidados con sleeps**

```csharp
// MAL: confiar en que el timer de las 03:00 termina antes de las 03:30
[TimerTrigger("0 0 3 * * *")]
public async Task LimpiezaPaso1() { /* dura 25 min */ }

[TimerTrigger("0 30 3 * * *")]
public async Task LimpiezaPaso2()
{
    // Asume que Paso1 terminó hace 5 min
    // Si Paso1 tarda más → Paso2 corre con datos incompletos
}
```

**✅ Patrón correcto: marcadores en BBDD + condicional**

```csharp
[Function("LimpiezaPaso2")]
public async Task LimpiezaPaso2(
    [TimerTrigger("0 30 3 * * *")] TimerInfo timer,
    [CosmosDBInput(...)] CosmosClient cosmos)
{
    // Verificar que Paso1 ha completado
    var marcador = await cosmos
        .GetContainer("ops", "marcadores")
        .ReadItemAsync<Marcador>(
            $"limpieza-paso1-{DateTime.UtcNow:yyyy-MM-dd}",
            new PartitionKey("limpieza"));
    
    if (marcador.Resource.Estado != "Completado")
    {
        _logger.LogWarning(
            "Paso1 no completado todavía. Re-encolar Paso2 para reintento.");
        return;  // El próximo trigger reintentará
    }
    
    // Ejecutar Paso2
    await DoLimpiezaPaso2Async();
    
    // Registrar completado
    await cosmos.GetContainer("ops", "marcadores").CreateItemAsync(new Marcador
    {
        Id = $"limpieza-paso2-{DateTime.UtcNow:yyyy-MM-dd}",
        Tipo = "limpieza",
        Estado = "Completado",
        EjecutadoEn = DateTime.UtcNow
    });
}
```

**✅ Patrón mejor (para flujos complejos): Durable Functions Orchestrator**

Para 3+ pasos coordinados, Timer Triggers individuales se complican. **Durable Functions** (M04) es la herramienta adecuada:

```csharp
// Timer dispara orchestrator UNA vez
[Function("Iniciar")]
public async Task Iniciar(
    [TimerTrigger("0 0 3 * * *")] TimerInfo timer,
    [DurableClient] DurableTaskClient client)
{
    await client.ScheduleNewOrchestrationInstanceAsync(
        nameof(LimpiezaOrchestrator),
        new { Fecha = DateTime.UtcNow.Date });
}

// Orchestrator coordina los pasos (esto es M04)
// → ver módulo 4 para detalles completos
```

**Patrón avanzado: timers con offset condicional**

```csharp
[Function("ReporteSemanal")]
public async Task ReporteSemanal(
    [TimerTrigger("0 0 8 * * 1")] TimerInfo timer)  // Lunes 08:00
{
    // Solo ejecutar si la limpieza dominical terminó
    var ultimoCleanup = await GetUltimoCleanupAsync();
    
    if (ultimoCleanup is null || ultimoCleanup < DateTime.UtcNow.AddDays(-2))
    {
        _logger.LogError("Cleanup dominical no se ejecutó. Skip reporte.");
        // Crear ticket / alerta
        await CreateAlertAsync("Cleanup no ejecutado");
        return;
    }
    
    await GenerarReporteSemanalAsync();
}
```

**Decisión de arquitectura:**

```
1-2 timers, sin dependencias entre sí
  → Timer Triggers separados ✓

2-3 timers con dependencias simples
  → Timer Triggers + marcadores en BBDD ✓

3+ timers coordinados, lógica compleja
  → Durable Functions Orchestrator (M04) ✓✓

Workflows con humanos en el loop, aprobaciones, etc.
  → Logic Apps (no Functions) ✓✓
```

## Slide 24 — Cierre del submódulo

Habéis cubierto los Timer Triggers en profundidad: desde el ejemplo mínimo hasta producción.

**Lo esencial de Timer Triggers:**

- ✅ NCRONTAB con 6 campos (¡atención al campo de segundos!)
- ✅ Por defecto UTC; configurar `WEBSITE_TIME_ZONE` para hora local
- ✅ `[Singleton]` para evitar ejecuciones simultáneas en múltiples instancias
- ✅ `IsPastDue` para decidir qué hacer con ejecuciones perdidas
- ✅ Output bindings reducen código (Cosmos, Service Bus, Storage Queue)
- ✅ Idempotencia siempre asumir ejecución duplicada como caso real
- ✅ Plan adecuado: Consumption para timers no críticos, Premium/Flex para alta frecuencia
- ✅ Monitorización con KQL y alertas para tareas que NO se ejecutan
- ✅ Forzar ejecución manual con `/admin/functions/<nombre>` para testing

**Patrones de producción más comunes:**

- Cleanup nocturno
- Health check de dependencias externas
- Informes diarios/semanales
- Renovación de tokens y certificados
- Cache warming antes de horas punta
- Reconciliación de datos con sistemas legacy

**Cuándo NO usar Timer Trigger:**

- Tareas con coordinación compleja → Durable Functions (M04)
- Tareas que disparan en respuesta a eventos → Event Grid o Service Bus (M04)
- Tareas que necesitan ejecutarse exactamente una vez en futuro → Scheduled Messages (M07)

## Slide 2 — Qué son los bindings
Los bindings son la forma de conectar tu función con servicios Azure sin escribir código de conexión. Declaras QUÉ quieres leer o dónde quieres escribir, y Azure Functions se encarga del CÓMO.

**Sin bindings:**
- Creas un cliente (CosmosClient, BlobServiceClient...)
- Gestionas la conexión (connection string, autenticación)
- Haces la operación (read, write)
- Manejas errores de conexión
- 15-25 líneas de código por operación

**Con bindings:**
- Declaras un atributo en el parámetro de la función
- Azure inyecta el dato o el destino automáticamente
- 1-2 líneas de declaración

Los bindings ya los habéis visto en acción en los submódulos anteriores. Aquí los consolidamos y vemos el catálogo completo.

## Slide 3 — Tres tipos de bindings

**1. Trigger (uno por función, obligatorio):**
```csharp
[HttpTrigger(...)] HttpRequest req           // HTTP dispara la función
[TimerTrigger("0 0 3 * * *")] TimerInfo t    // Timer dispara la función
[BlobTrigger("uploads/{name}")] Stream blob   // Blob nuevo dispara la función
[CosmosDBTrigger(...)] IReadOnlyList<Doc> d   // Change Feed dispara la función
```

**2. Input Binding (cero o más, datos que LEES):**
```csharp
[CosmosDBInput("db", "container", Id = "{id}")] Documento doc  // Lee un documento
[BlobInput("datos/{name}")] string contenido                    // Lee un blob
[TableInput("tabla", "{pk}", "{rk}")] Entidad entity            // Lee de Table Storage
```

**3. Output Binding (cero o más, donde ESCRIBES):**
```csharp
[CosmosDBOutput("db", "container")] → return documento         // Escribe en Cosmos
[BlobOutput("resultados/{name}")] → return contenido           // Escribe un blob
[QueueOutput("mi-cola")] → return mensaje                      // Envía a una cola
[TableOutput("tabla")] → return entidad                        // Escribe en Table
```

## Slide 6 — Output Binding como return value

La forma más limpia de usar output bindings:

```csharp
// Output binding en el return — se escribe automáticamente
[Function("CrearPedido")]
[CosmosDBOutput("tienda", "pedidos", Connection = "CosmosDb")]
public Pedido Crear(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "pedidos")] 
    HttpRequest req)
{
    var pedido = req.ReadFromJsonAsync<Pedido>().Result;
    pedido!.Id = Guid.NewGuid().ToString();
    pedido.CreadoEn = DateTime.UtcNow;
    
    return pedido;  // ← esto se escribe directamente en Cosmos DB
}
```

**¿Y si necesito TAMBIÉN devolver HTTP response?** Usad un tipo con múltiples outputs:

```csharp
public class CrearPedidoResult
{
    [CosmosDBOutput("tienda", "pedidos", Connection = "CosmosDb")]
    public Pedido DocumentoCosmos { get; set; }
    
    [QueueOutput("pedidos-nuevos", Connection = "StorageConnection")]
    public string MensajeCola { get; set; }
    
    public HttpResponseData HttpResponse { get; set; }
}

[Function("CrearPedido")]
public CrearPedidoResult Crear(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
{
    var pedido = new Pedido { Id = Guid.NewGuid().ToString() };
    
    return new CrearPedidoResult
    {
        DocumentoCosmos = pedido,                           // → Cosmos DB
        MensajeCola = $"Nuevo pedido: {pedido.Id}",        // → Queue
        HttpResponse = req.CreateResponse(HttpStatusCode.Created) // → HTTP
    };
}
```

## Slide 7 — Combinaciones potentes

**HTTP → lee de Cosmos → escribe en Blob:**
```csharp
[Function("ExportarPedido")]
[BlobOutput("exports/pedido-{id}.json", Connection = "Storage")]
public string Exportar(
    [HttpTrigger(AuthorizationLevel.Function, "get", Route = "exportar/{id}")] HttpRequest req,
    [CosmosDBInput("tienda", "pedidos", Connection = "CosmosDb", Id = "{id}", PartitionKey = "{id}")] 
    Pedido pedido,
    string id)
{
    return JsonSerializer.Serialize(pedido);
    // HTTP trigger → lee de Cosmos (input) → escribe blob (output)
}
```

**Timer → lee de Cosmos → escribe en Queue:**
```csharp
[Function("ProcesarPendientes")]
[QueueOutput("pedidos-a-procesar", Connection = "Storage")]
public List<string> ProcesarPendientes(
    [TimerTrigger("0 */15 * * * *")] TimerInfo timer,
    [CosmosDBInput("tienda", "pedidos", Connection = "CosmosDb",
        SqlQuery = "SELECT * FROM c WHERE c.estado = 'pendiente'")] 
    IReadOnlyList<Pedido> pendientes)
{
    return pendientes.Select(p => JsonSerializer.Serialize(p)).ToList();
    // Timer cada 15 min → query Cosmos (input) → mensajes a cola (output)
}
```

## Slide 8 — Bindings vs SDK: cuándo usar cada uno

**Usa bindings cuando:**
- Lectura simple por ID o query fijo
- Escritura simple (un documento, un blob, un mensaje)
- No necesitas lógica condicional en la conexión
- Quieres el código más corto posible

**Usa el SDK cuando:**
- Operaciones complejas (transacciones, queries dinámicos, batch operations)
- Necesitas control sobre retry policies y timeouts
- Operaciones condicionales (upsert solo si X, delete si Y)
- Paginación de resultados

```csharp
// Binding: simple, declarativo, 0 líneas de conexión
[CosmosDBInput("db", "c", Id = "{id}")] Documento doc

// SDK: flexible, más código, más control
var client = _cosmosService.GetContainer("db", "c");
var response = await client.ReadItemAsync<Documento>(id, new PartitionKey(id));
if (response.StatusCode == HttpStatusCode.NotFound) { ... }
```

**Regla práctica:** Empezad con bindings. Si necesitáis más control, cambiad a SDK. Los bindings cubren el 70% de los casos.

## Slide 9 — Connection strings en los bindings

Todos los bindings usan `Connection` para referenciar un App Setting:

```csharp
[CosmosDBInput(... Connection = "CosmosDbConnection")]
[BlobInput(... Connection = "StorageConnection")]
[QueueOutput(... Connection = "StorageConnection")]
[ServiceBusOutput(... Connection = "ServiceBusConnection")]
```

**En local (local.settings.json):**
```json
{
  "Values": {
    "CosmosDbConnection": "AccountEndpoint=https://localhost:8081/;AccountKey=...",
    "StorageConnection": "UseDevelopmentStorage=true",
    "ServiceBusConnection": "Endpoint=sb://mi-sb.servicebus.windows.net/;SharedAccessKeyName=..."
  }
}
```

**En Azure (App Settings):**
```bash
az functionapp config appsettings set --name mi-func -g mi-rg \
  --settings \
    CosmosDbConnection="AccountEndpoint=https://cosmos-prod.documents.azure.com:443/;AccountKey=..." \
    StorageConnection="DefaultEndpointsProtocol=https;AccountName=..." \
    ServiceBusConnection="Endpoint=sb://..."
```

**En producción, usad Key Vault references** en vez de valores en texto plano.

## Slide 10 — Bindings con expresiones dinámicas

Los bindings soportan expresiones entre llaves `{...}` que se resuelven en runtime:

```csharp
// Del trigger: {id} viene del path de la URL
[BlobOutput("exports/{id}.json")]

// Del sistema: fecha y hora actual
[BlobOutput("logs/{DateTime:yyyy-MM-dd}/{rand-guid}.json")]

// Del trigger: {nombre} viene del nombre del blob
[BlobOutput("procesados/{nombre}-resultado.json")]

// De query params: {Query.clienteId}
[CosmosDBInput("db", "c", SqlQuery = "SELECT * FROM c WHERE c.clienteId = {Query.clienteId}")]

// De route params
[CosmosDBInput("db", "c", Id = "{id}", PartitionKey = "{id}")]
```

**Expresiones disponibles:**
- `{parametro}` — del trigger (route params, blob name)
- `{Query.xxx}` — de query parameters HTTP
- `{Headers.xxx}` — de headers HTTP
- `{DateTime}` — fecha/hora actual (formatos .NET)
- `{rand-guid}` — GUID aleatorio

## Slide 13 — Bindings: SignalR para notificaciones en tiempo real

```csharp
// Negociar conexión SignalR (el frontend llama a este endpoint)
[Function("Negotiate")]
public HttpResponseData Negotiate(
    [HttpTrigger(AuthorizationLevel.Anonymous, "post")] HttpRequestData req,
    [SignalRConnectionInfoInput(HubName = "ventas")] SignalRConnectionInfo connectionInfo)
{
    var response = req.CreateResponse(HttpStatusCode.OK);
    response.WriteAsJsonAsync(connectionInfo);
    return response;
}

// Enviar notificación cuando un pedido cambia
[Function("NotificarCambio")]
[SignalROutput(HubName = "ventas")]
public SignalRMessageAction Notificar(
    [CosmosDBTrigger("tienda", "pedidos", Connection = "CosmosDb", LeaseContainerName = "leases-signalr")]
    IReadOnlyList<Pedido> cambios)
{
    return new SignalRMessageAction("pedidoActualizado")
    {
        Arguments = new object[] { cambios.Select(p => new { p.Id, p.Estado, p.Total }) }
    };
}
```

Cosmos Change Feed → SignalR → Frontend recibe actualización en tiempo real. Sin polling.

## Slide 15 — Custom bindings: crear uno propio

Si los bindings built-in no cubren vuestro caso, podéis crear uno custom. Ejemplo: binding que lee datos de una API interna:

```csharp
// 1. Attribute que identifica el binding
[AttributeUsage(AttributeTargets.Parameter)]
public class MiApiInternaAttribute : InputBindingAttribute
{
    public string Endpoint { get; set; } = "";
    public string Method { get; set; } = "GET";
}

// 2. Extension para registrar el binding
public class MiApiBindingExtension : IExtensionConfigProvider
{
    public void Initialize(ExtensionConfigContext context)
    {
        var rule = context.AddBindingRule<MiApiInternaAttribute>();
        rule.BindToInput<MiApiData>(BuildResultAsync);
    }

    private async Task<MiApiData> BuildResultAsync(MiApiInternaAttribute attr, ValueBindingContext ctx)
    {
        using var httpClient = new HttpClient();
        var response = await httpClient.GetAsync(attr.Endpoint);
        return await response.Content.ReadFromJsonAsync<MiApiData>();
    }
}

// 3. Registrar en Program.cs
builder.Services.AddSingleton<IExtensionConfigProvider, MiApiBindingExtension>();

// 4. Uso
[Function(nameof(Run))]
public async Task Run(
    [HttpTrigger(...)] HttpRequestData req,
    [MiApiInterna(Endpoint = "https://api-interna/productos")] MiApiData datos)
{
    // Usar 'datos' como si fuera cualquier otro binding
}
```

**Cuándo vale la pena crear custom binding:**
- Acceso repetitivo a un sistema interno (API corporate, LDAP, mainframe)
- Queréis que "parezca" nativo de Functions para el resto del equipo
- Configuración compleja que prefieres abstraer

**Cuándo NO:** un HttpClient tipado con DI es más simple y igual de efectivo en el 95% de casos.

## Slide 16 — Binding expressions avanzadas

Los bindings soportan expresiones dinámicas que se resuelven en tiempo de ejecución:

```csharp
// {name} — del trigger (ej: nombre del blob)
[BlobTrigger("uploads/{name}")] Stream blob,
[BlobOutput("procesados/{name}")] Stream output   // mismo nombre en otro container

// {rand-guid} — GUID aleatorio
[BlobOutput("logs/{rand-guid}.json")] Stream log

// {DateTime} — fecha/hora de ejecución
[BlobOutput("archivo/{DateTime:yyyy-MM-dd}/{rand-guid}.log")] Stream

// %AppSetting% — valor de App Settings
[BlobOutput("container-%OutputPath%/{name}")] Stream
// Requiere App Setting "OutputPath" = "procesados" (o similar)

// Combinaciones
[BlobOutput("archivo/{DateTime:yyyy}/{DateTime:MM}/{DateTime:dd}/{name}")] Stream

// Propiedades del input (requiere trigger con POCO)
[QueueTrigger("pedidos")] PedidoDto pedido,
[CosmosDBOutput("ventas", "pedidos/{pedido.ClienteId}", ...)] // partition key dinámico

// Bindings a través de configuración
[TimerTrigger("%ScheduleCron%")] TimerInfo timer
// Permite cambiar el CRON vía App Setting sin redeployar
```

**Expresiones custom con Trigger Metadata:**
```csharp
[Function(nameof(Run))]
public async Task Run(
    [ServiceBusTrigger("pedidos", Connection = "SB")] ServiceBusReceivedMessage msg,
    [CosmosDBOutput("ventas", "pedidos", Id = "{MessageId}", PartitionKey = "{CorrelationId}")] 
    object docOutput)
{
    // MessageId y CorrelationId vienen del mensaje SB
    // Se usan como id y partition key del output
}
```

## Slide 17 — Bindings + retry strategies

Functions tiene retry policies automáticas configurables:

```csharp
// Retry a nivel de función (host.json)
// Aplica a todas las funciones del app
{
  "version": "2.0",
  "extensions": {
    "queues": {
      "maxDequeueCount": 5      // queue-specific retry
    },
    "serviceBus": {
      "maxAutoLockRenewalDuration": "00:05:00"
    }
  },
  "retry": {
    "strategy": "exponentialBackoff",
    "maxRetryCount": 5,
    "minimumInterval": "00:00:02",
    "maximumInterval": "00:15:00"
  }
}
```

```csharp
// Retry per-function con attribute
[Function(nameof(Run))]
[ExponentialBackoffRetry(
    maxRetryCount: 5,
    minimumInterval: "00:00:10",
    maximumInterval: "00:05:00")]
public async Task Run(
    [ServiceBusTrigger("pedidos", Connection = "SB")] string message)
{
    // Si falla, Azure reintenta según la policy
    // Tras 5 fallos → Dead Letter Queue
}

// Retry fijo
[Function(nameof(RunConRetryFijo))]
[FixedDelayRetry(
    maxRetryCount: 3,
    delayInterval: "00:00:30")]
public async Task RunConRetryFijo(...)
{
    // 3 intentos con 30s entre cada uno
}
```

**Strategies disponibles:**

| Strategy | Cuándo usarla |
|---|---|
| Fixed Delay | Transient fails cortos (latencia temporal) |
| Exponential Backoff | Servicios externos rate-limited (respetar ventana) |
| Sin retry | Idempotencia no garantizada → fallar rápido |

**Precaución:** más retries = más tiempo procesando mensajes problemáticos. Si cada retry tarda 1 min y hay 5 retries, un mensaje tóxico bloquea un consumer 5 min.

## Slide 18 — Table Storage bindings: casos de uso

Table Storage es barato y simple. Bindings hacen su uso trivial:

```csharp
// Input binding: leer una entidad específica
[Function(nameof(GetConfig))]
public HttpResponseData GetConfig(
    [HttpTrigger(...)] HttpRequestData req,
    [TableInput("Configuration", "Feature", "{id}", Connection = "Storage")] 
    ConfigEntity config)
{
    if (config == null) return req.CreateResponse(HttpStatusCode.NotFound);
    var response = req.CreateResponse(HttpStatusCode.OK);
    response.WriteAsJsonAsync(new { config.Feature, config.Enabled, config.RolloutPercent });
    return response;
}

// Input binding: listar con filter
[Function(nameof(ListActive))]
public HttpResponseData ListActive(
    [HttpTrigger(...)] HttpRequestData req,
    [TableInput("Configuration", Filter = "Enabled eq true", Connection = "Storage")] 
    IEnumerable<ConfigEntity> configs)
{
    // configs contiene TODAS las filas que cumplen el filter
}

// Output binding: insertar/actualizar
[Function(nameof(SaveConfig))]
[TableOutput("Configuration", Connection = "Storage")]
public ConfigEntity SaveConfig(
    [HttpTrigger(AuthorizationLevel.Function, "post")] ConfigDto dto)
{
    return new ConfigEntity
    {
        PartitionKey = "Feature",
        RowKey = dto.Id,
        Feature = dto.Feature,
        Enabled = dto.Enabled,
        RolloutPercent = dto.RolloutPercent
    };
}

// Entidad (debe implementar ITableEntity)
public class ConfigEntity : ITableEntity
{
    public string PartitionKey { get; set; } = "";
    public string RowKey { get; set; } = "";
    public DateTimeOffset? Timestamp { get; set; }
    public ETag ETag { get; set; }
    
    public string Feature { get; set; } = "";
    public bool Enabled { get; set; }
    public int RolloutPercent { get; set; }
}
```

**Cuándo Table Storage es buena idea:**
- Datos clave-valor muy simples
- Mucho volumen, pocas consultas complejas
- Coste crítico (~€0.04/GB vs Cosmos €25/GB)
- Feature flags, audit logs, session state

**Cuándo NO:** queries complejas, joins, alta consistencia multi-región → Cosmos DB.

## Slide 19 — Queue Storage bindings: procesamiento simple

Queue Storage es el hermano simple de Service Bus. Para colas básicas, es suficiente:

```csharp
// Queue trigger
[Function(nameof(ProcesarPedido))]
public async Task ProcesarPedido(
    [QueueTrigger("pedidos-pendientes", Connection = "Storage")] 
    PedidoDto pedido)
{
    // Deserialización automática de JSON → PedidoDto
    await GuardarEnBBDDAsync(pedido);
}

// Queue output (envío desde otra función)
[Function(nameof(RecibirPedido))]
[QueueOutput("pedidos-pendientes", Connection = "Storage")]
public PedidoDto RecibirPedido(
    [HttpTrigger(AuthorizationLevel.Function, "post")] PedidoDto pedido)
{
    // El return value se enqueue automáticamente
    return pedido;
}

// Multiple messages output
[Function(nameof(EnvioBatch))]
public async Task<MultipleOutput> EnvioBatch([TimerTrigger("0 0 * * * *")] TimerInfo timer)
{
    var pedidos = await GetPedidosPendientes();
    return new MultipleOutput 
    { 
        Queue = pedidos.Select(p => new QueueMessage { Body = JsonSerializer.Serialize(p) }).ToArray(),
        HttpResponse = null
    };
}

public class MultipleOutput
{
    [QueueOutput("pedidos-pendientes", Connection = "Storage")]
    public QueueMessage[] Queue { get; set; } = Array.Empty<QueueMessage>();
    
    public HttpResponseData? HttpResponse { get; set; }
}
```

**Queue Storage vs Service Bus:**

| | Queue Storage | Service Bus |
|---|---|---|
| Precio | ~€0.0004 / 10K ops | ~€0.05 / 10K ops (Standard) |
| Max message size | 64 KB | 256 KB (Standard), 100 MB (Premium) |
| FIFO | No | Sí (con sessions) |
| Dead letter | Manual | Built-in |
| Topics/Subs | No | Sí |
| Duplicates | Manual | Built-in detection |
| Transacciones | No | Sí |

**Regla:** Queue Storage para colas simples (high volume, low complexity). Service Bus para patterns avanzados (pub/sub, FIFO, transactions).

## Slide 20 — Event Hub bindings: ingesta masiva

Event Hub es el servicio para ingesta de eventos de alto throughput (IoT, telemetría, logs masivos):

```csharp
// Input: procesar lotes grandes (hasta 10K eventos por invocación)
[Function(nameof(ProcesarEventos))]
public async Task ProcesarEventos(
    [EventHubTrigger("telemetria", Connection = "EventHubConnection",
                     ConsumerGroup = "procesador-principal")]
    EventData[] events,  // batch, no uno solo
    FunctionContext ctx)
{
    _logger.LogInformation("Procesando {count} eventos", events.Length);

    // Procesamiento en batch (mucho más eficiente)
    var tareas = events.Select(async e =>
    {
        var telemetria = JsonSerializer.Deserialize<TelemetriaDto>(e.Body.ToArray());
        await GuardarEnTimeSeriesAsync(telemetria);
    });
    
    await Task.WhenAll(tareas);
}

// Output: publicar eventos a un Event Hub
[Function(nameof(GenerarMetricas))]
[EventHubOutput("metricas", Connection = "EventHubConnection")]
public object[] GenerarMetricas([TimerTrigger("0 */5 * * * *")] TimerInfo timer)
{
    return new[]
    {
        new { metric = "cpu", value = GetCpu(), timestamp = DateTime.UtcNow },
        new { metric = "memory", value = GetMemory(), timestamp = DateTime.UtcNow },
        new { metric = "disk", value = GetDisk(), timestamp = DateTime.UtcNow }
    };
}
```

**Throughput escalas:**

| | Event Hub | Service Bus | Queue Storage |
|---|---|---|---|
| Messages/sec | Millones | Miles | Cientos |
| Max retention | 7-90 días | 14 días | 7 días |
| Replay capability | Sí (desde inicio) | No | No |
| Use case | Telemetría, logs | Messaging transaccional | Colas simples |

**Consumer groups** son una feature clave: permiten múltiples consumers independientes leer los mismos eventos sin interferir:

```
Event Hub "telemetria"
       │
       ├── Consumer Group "analytics" → Function A (time series DB)
       ├── Consumer Group "alertas"   → Function B (detecta anomalías)
       └── Consumer Group "archivo"   → Function C (backup a Storage)

Cada grupo tiene su propio puntero de lectura.
```

## Slide 21 — Bindings: anti-patterns a evitar

Bindings son poderosos pero mal usados generan código frágil. Anti-patterns comunes:

**1. Binding a tipos complejos sin validación**
```csharp
// ❌ MAL
[Function(nameof(Run))]
public void Run([QueueTrigger("pedidos")] Pedido pedido)
{
    // Si la queue tiene JSON malformado, Azure Functions FALLA
    // Tras 5 retries → Dead Letter
    // Perdéis visibilidad del payload problemático
}

// ✅ BIEN
[Function(nameof(Run))]
public async Task Run([QueueTrigger("pedidos")] string rawMessage)
{
    try
    {
        var pedido = JsonSerializer.Deserialize<Pedido>(rawMessage);
        if (pedido == null) throw new InvalidDataException("Null after deserialization");
        await ValidateAsync(pedido);
        await ProcessAsync(pedido);
    }
    catch (JsonException ex)
    {
        _logger.LogError(ex, "Mensaje inválido: {raw}", rawMessage);
        // Podéis enviar a dead-letter queue con detalles
        throw;
    }
}
```

**2. Demasiados bindings en una sola función**
```csharp
// ❌ MAL: binding soup
[Function(nameof(Mega))]
[BlobOutput("out1/{name}")] // 1
[QueueOutput("queue1")]      // 2
[TableOutput("t1")]          // 3
[CosmosDBOutput("db", "c")]  // 4
public async Task<MultipleOutput> Mega(...)
{
    // Función que hace 5 cosas → difícil de testear, debug, entender
}

// ✅ BIEN: función pequeña + fan-out
// Una función por responsabilidad, comunicadas vía Service Bus o Durable Functions
```

**3. Output bindings con side effects sincrónicos**
```csharp
// ❌ MAL: output binding que bloquea
[BlobOutput("slow-container")] 
public Stream Run([HttpTrigger(...)] HttpRequestData req)
{
    // Si Storage está lento, la Function tarda mucho en responder HTTP
    // El cliente espera el upload completo
}

// ✅ BIEN: fire-and-forget con Queue
// HTTP responde rápido, otra Function hace el work pesado
```

**Regla:** bindings son útiles, pero no todo es clavo. A veces un SDK client bien inyectado es más claro.

## Slide 23 — Bindings vs Dependency Injection: cuándo cada uno

Tanto bindings como DI permiten acceder a recursos externos. La elección impacta en testabilidad y flexibilidad:

```csharp
// OPCIÓN 1: con binding declarativo
[Function("CrearPedidoConBinding")]
public async Task<IActionResult> Run(
    [HttpTrigger(AuthorizationLevel.Anonymous, "post")] HttpRequest req,
    [CosmosDBOutput("Ventas", "pedidos", Connection = "Cosmos",
                    PartitionKey = "/clienteId")]
    IAsyncCollector<Pedido> output)
{
    var pedido = await req.ReadFromJsonAsync<Pedido>();
    await output.AddAsync(pedido);
    return new OkObjectResult(pedido);
}

// OPCIÓN 2: con DI explícito
[Function("CrearPedidoConDI")]
public async Task<IActionResult> RunWithDI(
    [HttpTrigger(AuthorizationLevel.Anonymous, "post")] HttpRequest req)
{
    var pedido = await req.ReadFromJsonAsync<Pedido>();
    await _pedidoRepository.CreateAsync(pedido);  // _pedidoRepository inyectado en constructor
    return new OkObjectResult(pedido);
}
```

**Tabla comparativa:**

| Aspecto | Bindings | Dependency Injection |
|---|---|---|
| **Cantidad de código** | Menos | Más (configuración + clase) |
| **Testabilidad** | Difícil mock de bindings | Fácil con interfaces |
| **Lógica compleja** | Limitada (1 operación) | Cualquier flujo |
| **Reutilización** | Per-función | Compartido entre funciones |
| **Connection management** | Auto-managed | Manual (pool, lifecycle) |
| **Telemetría** | Built-in | Configurable |
| **Validación previa** | No | Sí (en repository) |

**Reglas de decisión:**

```
Usad BINDINGS cuando:
✅ Operación simple (1 read o 1 write a un servicio)
✅ La lógica cabe en el método de la function
✅ No necesitáis mockear el servicio en tests
✅ Conexión por función está bien (no shared state)

Ejemplos: Timer → Cosmos write, Queue → Blob output

Usad DI cuando:
✅ Necesitáis transactions multi-operación
✅ Lógica de negocio compleja (validación, mappings, etc.)
✅ Tests unitarios con mocks
✅ Reutilización de lógica entre funciones
✅ Pooling de conexiones eficiente

Ejemplos: APIs REST con múltiples operaciones, microservicios
```

**Patrón híbrido (recomendado para producción):**


## Slide 24 — Validación de inputs: bindings + FluentValidation

Los bindings traen el dato, pero **validar es tu responsabilidad**. Patrón limpio con FluentValidation:

```bash
# Añadir paquete
dotnet add package FluentValidation
dotnet add package FluentValidation.DependencyInjectionExtensions
```

**Validador del DTO:**

```csharp
public class CrearPedidoDto
{
    public string ClienteId { get; set; } = "";
    public List<ItemDto> Items { get; set; } = new();
    public string? CodigoPromocion { get; set; }
    public string? Notas { get; set; }
}

public class CrearPedidoDtoValidator : AbstractValidator<CrearPedidoDto>
{
    public CrearPedidoDtoValidator()
    {
        RuleFor(x => x.ClienteId)
            .NotEmpty().WithMessage("ClienteId es obligatorio")
            .Matches(@"^[A-Z0-9]{8,12}$")
            .WithMessage("ClienteId debe ser 8-12 alfanuméricos");
        
        RuleFor(x => x.Items)
            .NotEmpty().WithMessage("El pedido debe tener al menos 1 item")
            .Must(items => items.Count <= 50)
            .WithMessage("Máximo 50 items por pedido");
        
        RuleForEach(x => x.Items).SetValidator(new ItemDtoValidator());
        
        RuleFor(x => x.CodigoPromocion)
            .MaximumLength(20)
            .Matches(@"^[A-Z0-9-]+$").When(x => x.CodigoPromocion is not null)
            .WithMessage("Código promoción inválido");
        
        RuleFor(x => x.Notas)
            .MaximumLength(500);
    }
}

public class ItemDtoValidator : AbstractValidator<ItemDto>
{
    public ItemDtoValidator()
    {
        RuleFor(x => x.ProductoId).NotEmpty();
        RuleFor(x => x.Cantidad).GreaterThan(0).LessThanOrEqualTo(100);
        RuleFor(x => x.PrecioUnitario).GreaterThanOrEqualTo(0);
    }
}
```

**Function que valida antes del binding output:**

```csharp
[Function("CrearPedidoValidado")]
public async Task<MultiResponse> CrearPedidoValidado(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "pedidos")]
    HttpRequest req,
    [CosmosDBOutput(...)] IAsyncCollector<Pedido> output)
{
    // 1. Deserializar
    CrearPedidoDto? dto;
    try
    {
        dto = await req.ReadFromJsonAsync<CrearPedidoDto>();
    }
    catch (JsonException ex)
    {
        return new MultiResponse
        {
            HttpResponse = new BadRequestObjectResult(new ProblemDetails
            {
                Title = "JSON inválido",
                Detail = ex.Message,
                Status = 400
            })
        };
    }
    
    if (dto is null)
        return new MultiResponse 
        { 
            HttpResponse = new BadRequestObjectResult("Body vacío") 
        };
    
    // 2. Validar con FluentValidation
    var validator = new CrearPedidoDtoValidator();
    var validationResult = await validator.ValidateAsync(dto);
    
    if (!validationResult.IsValid)
    {
        return new MultiResponse
        {
            HttpResponse = new BadRequestObjectResult(new
            {
                title = "Errores de validación",
                status = 400,
                errors = validationResult.Errors
                    .GroupBy(e => e.PropertyName)
                    .ToDictionary(
                        g => g.Key,
                        g => g.Select(e => e.ErrorMessage).ToArray())
            })
        };
    }
    
    // 3. Si todo OK, mapear y persistir vía binding
    var pedido = new Pedido
    {
        Id = Guid.NewGuid().ToString(),
        ClienteId = dto.ClienteId,
        Items = dto.Items.Select(i => new PedidoItem { /* mapeo */ }).ToList(),
        Total = dto.Items.Sum(i => i.Cantidad * i.PrecioUnitario),
        Estado = "Nuevo",
        FechaCreacion = DateTime.UtcNow
    };
    
    return new MultiResponse
    {
        HttpResponse = new CreatedResult($"/pedidos/{pedido.Id}", pedido),
        PedidoToSave = pedido
    };
}

public class MultiResponse
{
    [HttpResult]
    public IActionResult HttpResponse { get; set; } = null!;
    
    [CosmosDBOutput("Ventas", "pedidos", Connection = "Cosmos",
                    PartitionKey = "/clienteId")]
    public Pedido? PedidoToSave { get; set; }
}
```

**Patrón con DI (más testeable):**

```csharp

{

    public CrearPedidoFunction(IValidator<CrearPedidoDto> validator) 
        => _validator = validator;

    public async Task<IActionResult> Run(/* ... */) { /* usa _validator */ }
}

// Program.cs

```

**Reglas de validación a tener:**

```
✅ Validar ANTES del binding output (no escribir basura)
✅ Devolver Problem Details (RFC 7807) en errores
✅ Loguear validation failures (detectar patrones de abuso)
✅ Tests unitarios para cada regla del validator
✅ Validation rules en código, no en SQL constraints
```

## Slide 26 — Testing strategies para bindings

Los bindings son notoriamente difíciles de testear. Estrategias prácticas:

**Estrategia 1: Test del handler, no del trigger**

```csharp
// Separar lógica de la function
public class CrearPedidoHandler
{
    private readonly IPedidoRepository _repo;
    
    public CrearPedidoHandler(IPedidoRepository repo) => _repo = repo;
    
    public async Task<Result<Pedido>> HandleAsync(CrearPedidoDto dto)
    {
        // Lógica pura, testeable
        if (string.IsNullOrEmpty(dto.ClienteId))
            return Result<Pedido>.Fail("ClienteId requerido");
        
        var pedido = new Pedido { /* ... */ };
        await _repo.SaveAsync(pedido);
        
        return Result<Pedido>.Ok(pedido);
    }
}

// La function solo orquesta
public class CrearPedidoFunction
{
    private readonly CrearPedidoHandler _handler;
    
    public CrearPedidoFunction(CrearPedidoHandler handler) => _handler = handler;
    
    [Function("CrearPedido")]
    public async Task<IActionResult> Run(
        [HttpTrigger("post")] HttpRequest req,
        [CosmosDBOutput(...)] IAsyncCollector<Pedido> output)
    {
        var dto = await req.ReadFromJsonAsync<CrearPedidoDto>();
        var result = await _handler.HandleAsync(dto);
        
        if (!result.Success)
            return new BadRequestObjectResult(result.Error);
        
        await output.AddAsync(result.Value);
        return new CreatedResult($"/pedidos/{result.Value.Id}", result.Value);
    }
}

// Test: solo testeas el handler, no necesitas mocks de bindings
public class CrearPedidoHandlerTests
{
    [Fact]
    public async Task HandleAsync_ConDtoValido_CreaPedido()
    {
        // Arrange
        var repoMock = new Mock<IPedidoRepository>();
        var handler = new CrearPedidoHandler(repoMock.Object);
        var dto = new CrearPedidoDto { ClienteId = "C001", Items = [/* ... */] };
        
        // Act
        var result = await handler.HandleAsync(dto);
        
        // Assert
        Assert.True(result.Success);
        repoMock.Verify(r => r.SaveAsync(It.IsAny<Pedido>()), Times.Once);
    }
}
```

**Estrategia 2: Mock de IAsyncCollector / output bindings**

```csharp
public class CrearPedidoFunctionTests
{
    [Fact]
```

**Pirámide de tests recomendada:**

```
        Integration tests (5-10%)
        ├── End-to-end con emuladores
        └── Tests de bindings reales

       Function tests (20-30%)
       ├── Mock de bindings (collectors, etc.)
       ├── Validación HTTP request/response
       └── Verificación de side effects

      Handler/Service tests (60-70%)
      ├── Lógica de negocio pura
      ├── Validación de inputs
      ├── Mappings y transformaciones
      └── Manejo de errores
```

**Anti-patterns en testing:**

```
❌ Testear el SDK (es responsabilidad de Microsoft)
   No testees CosmosClient.CreateItemAsync funciona

❌ Tests de Azure Function que necesitan Azure real
   Si tu CI/CD requiere conexión a Azure, no es test unitario

❌ Mockear DateTime.UtcNow inline
   Mejor: inyectar IClock interface y mockear
```

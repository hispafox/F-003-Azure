## Slide 2 — Qué es un Blob Trigger
El Blob trigger ejecuta una función cuando se crea o modifica un archivo (blob) en Azure Blob Storage. La función recibe el contenido del blob y puede procesarlo.

**Casos de uso:**
- Procesamiento de imágenes (redimensionar, crear thumbnails)
- Conversión de formatos (CSV a JSON, XML a Parquet)
- Extracción de texto de documentos (OCR, PDFs)
- Validación de archivos subidos por usuarios
- Copia/sincronización entre contenedores
- Generación de metadatos o índices

## Slide 3 — Blob Trigger mínimo

```csharp
public class ProcesadorArchivos
{
    private readonly ILogger<ProcesadorArchivos> _logger;

    public ProcesadorArchivos(ILogger<ProcesadorArchivos> logger)
        => _logger = logger;

    [Function("ProcesarArchivo")]
    public void Procesar(
        [BlobTrigger("uploads/{nombre}", Connection = "StorageConnection")] 
        Stream contenido,
        string nombre)
    {
        _logger.LogInformation("Nuevo archivo detectado: {Nombre}, tamaño: {Bytes} bytes", 
            nombre, contenido.Length);
        
        // Procesar el contenido del blob...
    }
}
```

**Parámetros:**
- `"uploads/{nombre}"`: contenedor `uploads`, el nombre del blob se captura en `{nombre}`
- `Connection`: nombre del App Setting con la connection string del Storage Account
- `Stream contenido`: el contenido del blob como stream (también puede ser `string`, `byte[]`, o un tipo custom)

## Slide 4 — Cómo detecta nuevos blobs

El Blob trigger tiene **dos mecanismos de detección:**

**1. Polling (por defecto en consumo):**
- Azure Functions escanea el contenedor periódicamente (cada 10 segundos a 10 minutos)
- Compara timestamps de blobs con un registro de lo ya procesado
- Más lento: puede tardar hasta 10 minutos en detectar un blob nuevo
- Menos fiable con grandes volúmenes

**2. Event Grid (recomendado):**
- Azure Storage emite un evento inmediatamente cuando se crea un blob
- Event Grid lo captura y dispara la función
- Latencia de ~1 segundo
- Más fiable y escalable

```json
// host.json — usar Event Grid en vez de polling
{
  "extensions": {
    "blobs": {
      "maxDegreeOfParallelism": 8
    }
  }
}
```

**Recomendación:** Para producción, usad Event Grid trigger en vez de Blob trigger puro. La latencia pasa de minutos a segundos.

## Slide 6 — Ejemplo: procesamiento de CSV

```csharp
[Function("ProcesarCSV")]
[BlobOutput("procesados/{nombre}-resultado.json", Connection = "StorageConnection")]
public async Task<string> ProcesarCSV(
    [BlobTrigger("uploads/{nombre}.csv", Connection = "StorageConnection")] 
    string csvContent,
    string nombre,
    ILogger logger)
{
    logger.LogInformation("Procesando CSV: {Nombre}", nombre);
    
    var lineas = csvContent.Split('\n', StringSplitOptions.RemoveEmptyEntries);
    var headers = lineas[0].Split(',');
    
    var registros = lineas.Skip(1).Select(linea =>
    {
        var valores = linea.Split(',');
        var registro = new Dictionary<string, string>();
        for (int i = 0; i < headers.Length && i < valores.Length; i++)
            registro[headers[i].Trim()] = valores[i].Trim();
        return registro;
    }).ToList();
    
    var resultado = new
    {
        archivo_origen = $"{nombre}.csv",
        total_registros = registros.Count,
        procesado_en = DateTime.UtcNow,
        datos = registros
    };
    
    logger.LogInformation("CSV procesado: {Count} registros", registros.Count);
    
    // Output binding: se guarda automáticamente como JSON en el contenedor "procesados"
    return JsonSerializer.Serialize(resultado, new JsonSerializerOptions { WriteIndented = true });
}
```

**Flujo:** Alguien sube `ventas-junio.csv` a `uploads/` → la función lo lee → lo transforma a JSON → lo guarda como `ventas-junio-resultado.json` en `procesados/`.

## Slide 9 — Poison blobs: archivos que fallan

Si la función falla al procesar un blob, Azure Functions lo reintenta:

**Comportamiento por defecto:**
1. Primer intento falla → reintento inmediato
2. Segundo intento falla → reintento tras breve pausa
3. Tercer intento falla → reintento final
4. Cuarto intento falla → blob marcado como "poison"
5. Se crea un blob en el contenedor `{contenedor-origen}-poison` con el nombre del blob fallido

```bash
# Después de 5 fallos:
# uploads/factura-corrupta.pdf → blob original (no se toca)
# uploads-poison/factura-corrupta.pdf → registro del poison blob
```

**Manejar poison blobs:**
- Monitorizar el contenedor `-poison`
- Alertar cuando aparece un blob ahí
- Investigar y corregir (archivo corrupto, formato inesperado, error en tu código)

## Slide 10 — Evitar loops infinitos

**El peligro:** Si tu función lee de un contenedor y escribe en EL MISMO contenedor, se dispara a sí misma infinitamente.

```
uploads/foto.jpg → Function → uploads/foto-processed.jpg → Function → ...
```

**Soluciones:**
1. **Contenedores separados** (recomendado): leer de `uploads/`, escribir en `procesados/`
2. **Filtro por nombre**: solo procesar blobs que NO contengan "-processed"
3. **Metadata check**: marcar el blob como procesado y verificar antes de procesar

```csharp
[Function("ProcesarImagen")]
public async Task Procesar(
    [BlobTrigger("imagenes/{nombre}", Connection = "StorageConnection")] 
    BlobClient blob, string nombre)
{
    var props = await blob.GetPropertiesAsync();
    
    // Si ya tiene metadata "procesado=true", saltar
    if (props.Value.Metadata.ContainsKey("procesado"))
        return;
    
    // Procesar...
    
    // Marcar como procesado
    await blob.SetMetadataAsync(new Dictionary<string, string> { ["procesado"] = "true" });
}
```

## Slide 11 — Blob Trigger vs Event Grid Trigger

| Característica | Blob Trigger | Event Grid Trigger |
|----------------|:------------:|:------------------:|
| Latencia de detección | 1-10 minutos | ~1 segundo |
| Fiabilidad en alto volumen | Media | Alta |
| Configuración | Simple | Requiere Event Grid subscription |
| Coste | Incluido | Event Grid cobra por evento (~0.50€/M) |
| Información disponible | Contenido del blob | Evento (URL, metadata, tipo) |
| Ideal para | Desarrollo, bajo volumen | Producción, alto volumen |

**Para producción recomendamos Event Grid trigger.** Lo veremos en el módulo 4.

Para las prácticas y desarrollo, Blob trigger es suficiente y más simple de configurar.

## Slide 13 — Ejemplo completo: pipeline de procesamiento de documentos

```csharp
public class PipelineDocumentos
{
    private readonly ILogger<PipelineDocumentos> _logger;

    public PipelineDocumentos(ILogger<PipelineDocumentos> logger) => _logger = logger;

    [Function("ValidarDocumento")]
    [BlobOutput("validados/{nombre}", Connection = "StorageConnection")]
    [QueueOutput("documentos-validados", Connection = "StorageConnection")]
    public async Task<ValidacionResult> Validar(
        [BlobTrigger("uploads/{nombre}", Connection = "StorageConnection")] 
        BlobClient blob, string nombre)
    {
        var props = await blob.GetPropertiesAsync();
        var tamaño = props.Value.ContentLength;
        var tipo = props.Value.ContentType;
        
        _logger.LogInformation("Validando: {Nombre} ({Tipo}, {Tamaño} bytes)", nombre, tipo, tamaño);

        // Validaciones
        if (tamaño > 50 * 1024 * 1024) // 50 MB máximo
            throw new Exception($"Archivo demasiado grande: {tamaño} bytes");
        
        var extensionesPermitidas = new[] { ".pdf", ".csv", ".xlsx", ".json" };
        if (!extensionesPermitidas.Any(e => nombre.EndsWith(e, StringComparison.OrdinalIgnoreCase)))
            throw new Exception($"Extensión no permitida: {nombre}");

        // Copiar al contenedor de validados + poner mensaje en cola
        return new ValidacionResult
        {
            BlobContent = await blob.OpenReadAsync(),     // → va al blob output
            QueueMessage = $"Documento validado: {nombre}" // → va a la cola
        };
    }
}
```

## Slide 18 — Event Grid filters: procesar solo lo que interesa

Los filters en Event Grid subscription ahorran invocaciones innecesarias:

```bash
# Filter por extensión de archivo
az eventgrid system-topic event-subscription create \
  --name to-func-procesarcsv \
  --system-topic-name st-storage-events -g rg-ventas \
  --endpoint-type azurefunction --endpoint "..." \
  --included-event-types Microsoft.Storage.BlobCreated \
  --subject-begins-with "/blobServices/default/containers/uploads/" \
  --subject-ends-with ".csv"

# Filter por size (blobs >1MB)
--advanced-filter data.contentLength NumberGreaterThan 1048576

# Filter por content type
--advanced-filter data.contentType StringContains "csv"

# Filter por tags del blob
--advanced-filter data.metadata.prioridad StringIn alta critica
```

```json
// Advanced filters en JSON (para subscriptions complejas)
{
  "advancedFilters": [
    {
      "operatorType": "NumberGreaterThan",
      "key": "data.contentLength",
      "value": 1048576
    },
    {
      "operatorType": "StringBeginsWith",
      "key": "subject",
      "values": ["/blobServices/default/containers/uploads/2026/"]
    },
    {
      "operatorType": "StringEndsWith",
      "key": "subject",
      "values": [".csv", ".xlsx"]
    }
  ]
}
```

**Beneficio:** si 90% de los blobs no son relevantes, el 90% de las invocations no ocurren = 10x ahorro en coste.

## Slide 19 — Procesamiento de archivos grandes con streaming

Para CSVs/JSONs de GB, NO cargarlos en memoria:

```csharp
public class ProcesarCsvGrande
{
    [Function(nameof(Run))]
    public async Task Run(
        [BlobTrigger("uploads/{name}.csv", Source = BlobTriggerSource.EventGrid,
                     Connection = "StorageConnection")]
        Stream blobStream,  // ← Stream, NO byte[]
        string name,
        FunctionContext ctx)
    {
        // Lectura streaming: no carga todo en memoria
        using var reader = new StreamReader(blobStream);
        using var csv = new CsvReader(reader, CultureInfo.InvariantCulture);

        int procesados = 0;
        var batch = new List<PedidoDto>(1000);

        while (await csv.ReadAsync())
        {
            var pedido = csv.GetRecord<PedidoDto>();
            batch.Add(pedido);

            // Procesar en batches (bulk insert a Cosmos)
            if (batch.Count == 1000)
            {
                await InsertBatchAsync(batch);
                procesados += batch.Count;
                batch.Clear();
                
                _logger.LogInformation("Procesados {n} items", procesados);
            }
        }

        // Último batch
        if (batch.Count > 0)
        {
            await InsertBatchAsync(batch);
            procesados += batch.Count;
        }

        _logger.LogInformation("Completado. Total: {n}", procesados);
    }
}
```

**Memoria usada:**
- Sin streaming: CSV de 2GB → 2GB+ memoria → **OutOfMemoryException** en Consumption (1.5GB límite)
- Con streaming: ~50-100MB constante → procesable en cualquier plan

**Otras técnicas para archivos masivos:**
- Chunked processing (leer rangos del blob): `BlockBlobClient.DownloadStreamingAsync(range)`
- Paralelismo controlado (N tareas procesando partes distintas)
- Durable Functions para coordinar fan-out/fan-in sobre el archivo

## Slide 20 — Dead-letter para blobs problemáticos

Blobs que fallan repetidamente deben irse a una "quarantine" para análisis manual:

```csharp
public class ProcesarConDLQ
{
    private readonly BlobServiceClient _blobService;

    [Function(nameof(Run))]
    public async Task Run(
        [BlobTrigger("uploads/{name}", Source = BlobTriggerSource.EventGrid,
                     Connection = "StorageConnection")]
        Stream blobStream,
        string name,
        FunctionContext ctx)
    {
        try
        {
            await ProcesarAsync(blobStream);
            
            // Éxito: mover a procesados
            await MoverBlobAsync(
                sourceContainer: "uploads",
                sourceBlob: name,
                targetContainer: "procesados",
                targetBlob: $"{DateTime.UtcNow:yyyy-MM-dd}/{name}");
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Error procesando {blob}", name);
            
            // Azure retry automático: 5 intentos por defecto
            // Tras 5 fallos → Azure mueve a webjobs-blobtrigger-poison container
            // 
            // Pero nosotros podemos hacerlo más elegante:
            await MoverBlobAsync(
                sourceContainer: "uploads",
                sourceBlob: name,
                targetContainer: "quarantine",
                targetBlob: $"{DateTime.UtcNow:yyyy-MM-dd}/{name}",
                metadata: new Dictionary<string, string>
                {
                    ["error"] = ex.GetType().Name,
                    ["errorMessage"] = ex.Message.Substring(0, Math.Min(200, ex.Message.Length)),
                    ["attemptedAt"] = DateTime.UtcNow.ToString("O"),
                    ["invocationId"] = ctx.InvocationId.ToString()
                });
            
            throw; // dejar que Functions haga sus retries también
        }
    }
}
```

**Monitorización:**
- Alerta cuando `quarantine` container tenga > 0 blobs durante > 1 hora
- Dashboard con conteo de blobs quarantine por día (tendencia de problemas)
- Review manual semanal: ¿qué blobs están en quarantine? ¿patrones?

## Slide 21 — Blob versioning y soft delete: consideraciones

Si vuestro Storage Account tiene **versioning** o **soft delete**, el Blob Trigger recibe eventos que quizá no esperáis:

```bash
# Ver si versioning está habilitado
az storage account blob-service-properties show \
  --account-name stventas \
  --resource-group rg-ventas \
  --query isVersioningEnabled

# Con versioning habilitado:
# - Cada SOBRESCRITURA crea una versión nueva
# - Blob Trigger dispara con CADA versión nueva
# - Evento BlobCreated se lanza tanto en create como update
```

**Problema típico:** app actualiza `config.json` cada 5 min → Blob Trigger ejecuta cada 5 min aunque no cambiéis nada.

**Soluciones:**
```csharp
// 1. Filter en Event Grid: solo versiones "current" (no históricas)
// En la subscription:
// advancedFilter: data.isCurrentVersion EqualTo true

// 2. Filter por el event type específico
// Subscribirse solo a BlobCreated, NO a BlobUpdated
// (aunque en práctica, Storage genera BlobCreated para ambos)

// 3. Check en el código si es una versión "nueva" interesante
public async Task Run(
    [BlobTrigger("config/{name}", Source = BlobTriggerSource.EventGrid)]
    Stream blob, string name, BlobProperties props)
{
    // Saltar si es una versión vieja (soft deleted restore, etc.)
    if (props.VersionId != null && !props.IsLatestVersion)
    {
        _logger.LogDebug("Skipping old version {v}", props.VersionId);
        return;
    }
    
    // Procesar la versión actual
}
```

**Soft delete también genera eventos:**
- Cuando un blob soft-deleted vuelve a crearse → `BlobCreated`
- Cuando se restaura de soft delete → `BlobCreated` de nuevo
- Patterns de deduplication son importantes

## Slide 22 — Metadata-driven routing

El metadata del blob puede dirigir el procesamiento:

```csharp
// Al subir el blob, añadir metadata
var client = containerClient.GetBlobClient($"pedido-{id}.xml");
await client.UploadAsync(stream, new BlobUploadOptions
{
    Metadata = new Dictionary<string, string>
    {
        ["prioridad"] = "alta",
        ["tipo"] = "pedido-urgente",
        ["cliente"] = "ACME-Corp",
        ["version"] = "2"
    }
});
```

```csharp
// En Blob Trigger, leer metadata para decidir routing
public class ProcesarConRouting
{
    [Function(nameof(Run))]
    public async Task Run(
        [BlobTrigger("incoming/{name}")] Stream blob,
        string name,
        BlobProperties properties,  // ← esto incluye metadata
        FunctionContext ctx)
    {
        var prioridad = properties.Metadata.GetValueOrDefault("prioridad", "normal");
        var tipo = properties.Metadata.GetValueOrDefault("tipo", "");
        
        // Routing según metadata
        switch (prioridad)
        {
            case "alta":
                await ProcesarRapidoAsync(blob);  // SLA agresivo
                break;
            case "normal":
                await ProcesarNormalAsync(blob);
                break;
            case "baja":
                // Delegar a otra Function con plan más barato
                await QueueForBatchAsync(name);
                break;
        }

        // Métricas diferenciadas por tipo
        _meter.RecordProcessed(1, new("tipo", tipo), new("prioridad", prioridad));
    }
}
```

**Uso típico:**
- Tenant multi-cliente: metadata `cliente=X` → procesamiento con data de ese cliente
- SLA tiering: metadata `prioridad=alta` → prioridad en la cola
- Routing a diferentes pipelines: metadata `tipo=factura` vs `tipo=albarán`
- Versioning: metadata `schema-version=v2` → deserializer v2

## Slide 23 — Stream vs byte[] vs string: la decisión que define el rendimiento

El binding `[BlobTrigger]` puede recibir el blob en distintos tipos. La elección impacta directamente en memoria y latencia:

```csharp
// Opción 1: Stream (recomendado para >5 MB)
[BlobTrigger("uploads/{name}", Connection = "Storage")]
Stream blobStream

// Opción 2: byte[] (para procesado binario completo)
[BlobTrigger("uploads/{name}", Connection = "Storage")]
byte[] blobBytes

// Opción 3: string (solo para archivos texto pequeños <1 MB)
[BlobTrigger("uploads/{name}", Connection = "Storage")]
string blobText
```

**Tabla de impacto en memoria:**

| Tipo | Memoria usada | Cuándo usar | Cuándo NO |
|---|---|---|---|
| `Stream` | ~50-100 KB constante | Archivos grandes, procesamiento secuencial | Si necesitáis acceso aleatorio |
| `byte[]` | Tamaño del blob completo | Imágenes, binarios pequeños | Archivos >50 MB (riesgo OOM) |
| `string` | 2× tamaño (UTF-16 en memoria) | Textos pequeños conocidos | Archivos binarios, archivos grandes |

**Benchmark real** (procesamiento de CSV de 500 MB):

```
Con string:
- Memoria peak: 1.2 GB (ratio 2.4× por encoding)
- Tiempo: OutOfMemoryException en Consumption Plan ❌

Con byte[]:
- Memoria peak: 520 MB
- Tiempo: 8.5 segundos
- ⚠️ Funciona pero come casi todo el plan Consumption (1.5 GB)

Con Stream:
- Memoria peak: 80 MB constante
- Tiempo: 7.2 segundos
- ✅ Procesa en cualquier plan, incluso si el archivo crece a GB
```

**Patrón pro: detectar tipo y elegir tratamiento:**

```csharp
[Function("ProcesarArchivo")]
public async Task Procesar(
    [BlobTrigger("uploads/{name}", Connection = "Storage")]
    Stream blobStream,
    string name,
    Uri uri)
{
    var extension = Path.GetExtension(name).ToLower();
    
    switch (extension)
    {
        case ".csv":
        case ".log":
        case ".txt":
            // Procesamiento línea a línea con StreamReader
            await ProcessTextStreamAsync(blobStream, name);
            break;
            
        case ".jpg":
        case ".png":
            // Decodificar imagen completa (necesita byte[])
            using (var ms = new MemoryStream())
            {
                await blobStream.CopyToAsync(ms);
                await ProcessImageAsync(ms.ToArray(), name);
            }
            break;
            
        case ".pdf":
            // Stream → librería PDF que lo lee progresivamente
            await ProcessPdfStreamAsync(blobStream, name);
            break;
    }
}
```

**Regla de oro:** **siempre `Stream`** salvo que tengáis un caso muy claro de necesitar el archivo entero en memoria.

## Slide 24 — Container vs Path-based filtering: dos formas de filtrar

Hay dos enfoques para que un Blob Trigger procese solo ciertos blobs. Cada uno tiene trade-offs:

**Opción 1: Filtering por path pattern en el binding**

```csharp
// Solo procesa blobs en /uploads/csvs/
[BlobTrigger("uploads/csvs/{name}.csv", Connection = "Storage")]
Stream blobStream

// Captura subcarpetas y nombre
[BlobTrigger("uploads/{categoria}/{name}.{ext}", Connection = "Storage")]
public async Task Run(Stream blob, string categoria, string name, string ext)
{
    // Acceso a las partes del path como parámetros
    if (categoria == "imagenes" && (ext == "jpg" || ext == "png"))
    {
        await ProcessImageAsync(blob, name);
    }
}
```

**Pros:** Simple, sin código extra
**Contras:** Functions polling sigue mirando TODO el container, solo filtra después → ineficiente en containers con miles de blobs/min

**Opción 2: Containers separados por tipo**

```csharp
// Function 1: solo escucha /imagenes/
[Function("ProcesarImagenes")]
public async Task ProcesarImagenes(
    [BlobTrigger("imagenes/{name}", Connection = "Storage")] Stream blob,
    string name) { /* ... */ }

// Function 2: solo escucha /csvs/
[Function("ProcesarCsvs")]
public async Task ProcesarCsvs(
    [BlobTrigger("csvs/{name}", Connection = "Storage")] Stream blob,
    string name) { /* ... */ }
```

**Pros:** Cada container tiene su polling propio, más eficiente
**Contras:** Mayor coste de gestión (más containers, más permisos)

**Opción 3 (la mejor para producción): Event Grid + filters**

```bash
# Solo dispara para .pdf en cualquier subcarpeta
az eventgrid event-subscription create \
  --name proceso-pdfs \
  --source-resource-id $STORAGE_ID \
  --endpoint $FUNCTION_WEBHOOK \
  --included-event-types Microsoft.Storage.BlobCreated \
  --subject-ends-with ".pdf" \
  --advanced-filter data.contentType StringContains application/pdf
```

```csharp
[Function("ProcesarPdfs")]
public async Task Run(
    [EventGridTrigger] EventGridEvent eventGridEvent)
{
    // Solo se dispara para .pdf, sin polling
    var data = eventGridEvent.Data.ToObjectFromJson<StorageBlobCreatedEventData>();
    var blobUri = new Uri(data.Url);
    
    var blobClient = new BlobClient(blobUri, new DefaultAzureCredential());
    using var stream = await blobClient.OpenReadAsync();
    
    await ProcessPdfAsync(stream, data.Url);
}
```

**Comparativa decisional:**

```
Containers separados:
✅ Aislamiento claro entre tipos de proceso
✅ Permisos RBAC granulares
❌ Más infraestructura
→ Para arquitecturas muy moduladas

Path filtering:
✅ Simple, sin gestión extra
❌ Polling ineficiente con muchos blobs
→ Para apps simples, MVP

Event Grid + filters:
✅ Máxima eficiencia (no polling)
✅ Filtros avanzados (size, content-type, etc.)
✅ Escalable a miles de blobs/seg
❌ Setup más complejo
→ Para producción seria
```

## Slide 26 — Blob retention y lifecycle policies

Las Functions procesan blobs, pero **¿qué pasa con los blobs ya procesados?** Sin lifecycle policies, vuestro Storage crece sin límites y os come la factura.

**Estrategia 1: Mover blob procesado a otro container**

```csharp
[Function("ProcesarYArchivar")]
public async Task Run(
    [BlobTrigger("uploads/{name}", Connection = "Storage")] 
    Stream blob,
    string name,
    Uri uri,
    [BlobOutput("processed/{name}", Connection = "Storage")] Stream output)
{
    // Procesar
    await DoProcessAsync(blob);
    
    // Copiar al container "processed"
    blob.Position = 0;
    await blob.CopyToAsync(output);
    
    // El blob original sigue en /uploads/, hay que limpiarlo aparte
    // (el binding NO permite delete del input directamente)
}
```

**Estrategia 2: Lifecycle Management Policies (lo más limpio)**

```bash
# Política: borrar blobs en /processed/ después de 30 días
az storage account management-policy create \
  --account-name stcurso \
  --resource-group rg-curso \
  --policy '{
    "rules": [
      {
        "name": "delete-processed-after-30-days",
        "enabled": true,
        "type": "Lifecycle",
        "definition": {
          "actions": {
            "baseBlob": {
              "delete": { "daysAfterModificationGreaterThan": 30 }
            }
          },
          "filters": {
            "blobTypes": ["blockBlob"],
            "prefixMatch": ["processed/"]
          }
        }
      },
      {
        "name": "tier-old-uploads-to-cool",
        "enabled": true,
        "type": "Lifecycle",
        "definition": {
          "actions": {
            "baseBlob": {
              "tierToCool": { "daysAfterModificationGreaterThan": 7 },
              "tierToArchive": { "daysAfterModificationGreaterThan": 90 },
              "delete": { "daysAfterModificationGreaterThan": 365 }
            }
          },
          "filters": {
            "blobTypes": ["blockBlob"],
            "prefixMatch": ["uploads/"]
          }
        }
      }
    ]
  }'
```

**Storage tiers y coste (Apr 2026):**

| Tier | Precio storage | Precio acceso | Cuándo |
|---|---|---|---|
| **Hot** | ~€0.018/GB/mes | Bajo | Acceso frecuente |
| **Cool** | ~€0.010/GB/mes | Medio | <1 acceso/mes |
| **Cold** | ~€0.0036/GB/mes | Alto | <1 acceso/3 meses |
| **Archive** | ~€0.001/GB/mes | Muy alto + delay | Archivado long-term |

**Patrón producción común:**

```
/uploads/ (Hot, 7 días)
   ↓ lifecycle
/processed/ (Cool, 90 días)  
   ↓ lifecycle
/archive/ (Archive, 7 años por compliance)
```

**Estrategia 3: Borrar tras procesar (con marcador)**

```csharp
[Function("ProcesarYBorrar")]
public async Task Run(
    [BlobTrigger("uploads/{name}", Connection = "Storage")] 
    Stream blob,
    string name,
    Uri uri)
{
    try
    {
        await DoProcessAsync(blob);
        
        // Marcar como procesado en Cosmos (idempotencia)
        await MarkProcessedAsync(name);
        
        // Borrar blob original
        var blobClient = new BlobClient(uri, new DefaultAzureCredential());
        await blobClient.DeleteIfExistsAsync();
    }
    catch
    {
        // Si falla el procesamiento, dejar el blob para reintento
        // No borrar
        throw;
    }
}
```

**Best practices producción:**

- ✅ Habilitar **soft delete** en Storage Account (recovery 7-90 días)
- ✅ Habilitar **versioning** para blobs críticos
- ✅ Lifecycle policies según tipo de container
- ✅ Monitoring: alertar si Storage crece >X GB/día (indica que no se está limpiando)

## Slide 27 — Best practices: imágenes y PDFs

Los dos casos más comunes de Blob Trigger son procesamiento de imágenes y PDFs. Patrones específicos:

**Procesamiento de imágenes con SkiaSharp:**

```csharp
[Function("GenerarThumbnails")]
public async Task GenerarThumbnails(
    [BlobTrigger("imagenes/{name}", Source = BlobTriggerSource.EventGrid,
                 Connection = "Storage")] Stream imagen,
    string name,
    [BlobOutput("thumbnails/sm/{name}", Connection = "Storage")] Stream outputSm,
    [BlobOutput("thumbnails/md/{name}", Connection = "Storage")] Stream outputMd,
    [BlobOutput("thumbnails/lg/{name}", Connection = "Storage")] Stream outputLg)
{
    // Validar que es imagen procesable
    if (!IsImageExtension(Path.GetExtension(name)))
    {
        _logger.LogWarning("Archivo {Name} no es imagen. Skip.", name);
        return;
    }
    
    using var bitmap = SKBitmap.Decode(imagen);
    if (bitmap is null)
    {
        _logger.LogError("No se pudo decodificar imagen {Name}", name);
        throw new InvalidOperationException($"Imagen inválida: {name}");
    }
    
    // Generar 3 tamaños en paralelo
    var formatos = new[]
    {
        (Width: 150,  Stream: outputSm),
        (Width: 400,  Stream: outputMd),
        (Width: 1200, Stream: outputLg)
    };
    
    foreach (var formato in formatos)
    {
        var ratio = (float)formato.Width / bitmap.Width;
        var newHeight = (int)(bitmap.Height * ratio);
        
        using var resized = bitmap.Resize(
            new SKImageInfo(formato.Width, newHeight),
            SKFilterQuality.High);
        
        using var encoded = SKImage.FromBitmap(resized).Encode(SKEncodedImageFormat.Jpeg, 85);
        encoded.SaveTo(formato.Stream);
    }
    
    _logger.LogInformation("Thumbnails generados para {Name}: 3 formatos", name);
}

private static bool IsImageExtension(string ext) =>
    ext is ".jpg" or ".jpeg" or ".png" or ".webp" or ".gif";
```

**Best practices imágenes:**

```
✅ Validar extensión y magic bytes (no solo extensión del archivo)
✅ Limitar tamaño (rechazar >50 MB en función)
✅ Generar múltiples tamaños en paralelo (más rápido que secuencial)
✅ Usar JPEG quality 80-85 (balance calidad/tamaño)
✅ Strip EXIF metadata (privacidad: GPS, dispositivo)
✅ Detectar y manejar formatos animados (GIF, WebP animado)

❌ NO procesar imágenes >100 MB en Consumption Plan (OOM)
❌ NO confiar en MIME type del header (puede mentir)
❌ NO permitir SVG sin sanear (XSS injection)
```

**Procesamiento de PDFs con PdfPig:**

```csharp
using UglyToad.PdfPig;

[Function("ExtraerTextoDePdf")]
public async Task Run(
    [BlobTrigger("pdfs/{name}", Source = BlobTriggerSource.EventGrid,
                 Connection = "Storage")] Stream pdfStream,
    string name,
    [CosmosDBOutput("docs", "extracted",
                    Connection = "Cosmos",
                    PartitionKey = "/source")]
    IAsyncCollector<DocumentoExtraido> output)
{
    using var document = PdfDocument.Open(pdfStream);
    
    var paginas = new List<PaginaExtraida>();
    
    foreach (var page in document.GetPages())
    {
        paginas.Add(new PaginaExtraida
        {
            Numero = page.Number,
            Texto = page.Text,
            Palabras = page.GetWords().Select(w => w.Text).ToList(),
            CharCount = page.Text.Length
        });
    }
    
    var doc = new DocumentoExtraido
    {
        Id = Path.GetFileNameWithoutExtension(name),
        Source = "pdf",
        Nombre = name,
        TotalPaginas = document.NumberOfPages,
        TotalCaracteres = paginas.Sum(p => p.CharCount),
        Paginas = paginas,
        ProcesadoEn = DateTime.UtcNow
    };
    
    await output.AddAsync(doc);
    
    _logger.LogInformation(
        "PDF {Name} extraído: {Pages} páginas, {Chars} caracteres",
        name, doc.TotalPaginas, doc.TotalCaracteres);
}
```

**Best practices PDFs:**

```
✅ Validar que es PDF real (header %PDF-1.x)
✅ Limitar páginas máximas (rechazar >500 páginas)
✅ Extraer texto + metadata (no solo texto)
✅ Detectar PDFs encriptados (PdfPig lanza si no tienes pwd)
✅ Manejar PDFs con OCR necesario (no tienen texto real)

⚠️ Consideraciones:
- PDFs escaneados: solo OCR puede extraer texto (Azure Document Intelligence)
- PDFs con formularios: extraer fields aparte del texto
- PDFs firmados: validar firma si es relevante
```

**Si vuestro caso es OCR + estructura compleja, considerad Azure Document Intelligence** (servicio managed con modelos pre-entrenados). Más caro pero ahorra desarrollar OCR desde cero.

## Slide 28 — Cierre del submódulo
El Blob trigger convierte Azure Functions en un procesador reactivo de archivos. Para producción usad Event Grid trigger (instantáneo), para desarrollo Blob trigger polling (más simple). Stream para archivos grandes, múltiples outputs para pipelines, y control de concurrencia para no saturar.

## Slide 3 — Autenticación: 3 opciones

```bash
# Opción 1: OAuth (por defecto)
claude auth login
# Abre navegador, te autentica con tu cuenta Anthropic
# Guarda credenciales en ~/.claude/

# Opción 2: API key vía variable de entorno
export ANTHROPIC_API_KEY="sk-ant-..."
claude
# Útil en CI/CD, Docker, servidores sin navegador

# Opción 3: Claude en Azure AI Foundry (enterprise)
export ANTHROPIC_BASE_URL="https://<foundry-resource>.services.ai.azure.com/models"
export ANTHROPIC_API_KEY="<foundry-key>"
claude --model claude-sonnet-4-6
```

Para equipos: **opción 1 para devs, opción 2 para CI/CD, opción 3 para workloads con datos sensibles**.

## Slide 5 — CLAUDE.md: el contexto del proyecto

`CLAUDE.md` es un archivo en la raíz del proyecto que Claude Code lee al arrancar. Es donde pones el contexto que todo el equipo necesita que Claude sepa.

```markdown
# Proyecto Ventas — Contexto para Claude Code

## Stack
- .NET 8 (App Service + Azure Functions)
- Cosmos DB serverless (database: tienda, containers: pedidos, productos)
- Service Bus Standard (topic: pedido-eventos)
- Entra ID para auth (OAuth2)
- Key Vault + Managed Identity (cero connection strings con password)
- Azure DevOps para CI/CD (pipelines YAML)
- Bicep para IaC (en infrastructure/)

## Convenciones
- async/await en TODAS las operaciones I/O
- records para DTOs (no clases)
- ILogger con logging estructurado (no Console.Write)
- CancellationToken en todos los métodos públicos
- Tests con xUnit + FluentAssertions + Moq
- Nombres de clases/métodos en inglés, comentarios en español

## Reglas de infraestructura
- Managed Identity SIEMPRE (nunca connection strings con password)
- Bicep modular en infrastructure/modules/
- What-if obligatorio antes de cualquier deploy a producción
- App Service con slots staging+production

## No tocar sin preguntar
- infrastructure/modules/rbac.bicep (contiene asignaciones críticas)
- src/Api/Program.cs línea 15-30 (config MI sensible)
- azure-pipelines.yml (cambios requieren review del lead)
```

## Slide 6 — CLAUDE.md: buenas prácticas

```
DO:
✓ Stack técnico (versiones, servicios Azure usados)
✓ Convenciones del equipo (no-negociables)
✓ Comandos del proyecto (build, test, deploy local)
✓ Arquitectura general (2-3 líneas, link a docs/)
✓ Glosario del dominio (si usáis términos específicos)
✓ Zonas "frágiles" donde hay que tener cuidado

DON'T:
✗ Manual completo del proyecto (queda obsoleto)
✗ Secretos o credenciales
✗ Documentación de features (eso va en docs/)
✗ Cosas que Claude Code puede averiguar solo leyendo el código
```

**Regla:** CLAUDE.md debería caber en 1 pantalla. Si crece, partidlo en archivos y referenciadlos:
```markdown
## Más contexto
- Arquitectura detallada: [docs/architecture.md](docs/architecture.md)
- Runbooks operativos: [docs/runbooks/](docs/runbooks/)
- Decisiones (ADRs): [docs/adr/](docs/adr/)
```

## Slide 7 — settings.json del proyecto

```json
// .claude/settings.json — config compartida del equipo
{
  "model": "claude-sonnet-4-6",
  "permissions": {
    "allow": [
      "Bash(dotnet *)",
      "Bash(az *)",
      "Bash(bicep *)",
      "Bash(git *)",
      "Bash(npm *)",
      "Read(**)",
      "Write(src/**)",
      "Write(infrastructure/**)",
      "Write(tests/**)",
      "Edit(*.md)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(az group delete *)",
      "Write(infrastructure/modules/rbac.bicep)",
      "Read(**/*.env)",
      "Read(**/*.pfx)",
      "Read(**/local.settings.json)"
    ]
  },
  "env": {
    "ANTHROPIC_MODEL": "claude-sonnet-4-6"
  },
  "hooks": {
    "PreToolUse": ".claude/hooks/pre-tool-use.sh"
  }
}
```

**`allow`:** Lo que Claude Code puede hacer sin preguntar. **`deny`:** Lo que NUNCA puede hacer, incluso si parece razonable.

## Slide 9 — Permissions: entender los patrones

```
Patrones permitidos:
├── Bash(comando)          → ejecutar ese comando exacto
├── Bash(comando *)        → ejecutar ese comando con cualquier arg
├── Bash(comando arg *)    → comando + arg fijo + cualquier sufijo
├── Read(path)             → leer ese archivo
├── Read(path/**)          → leer cualquier archivo bajo path/
├── Write(path)            → escribir/crear ese archivo
├── Edit(path)             → modificar archivo existente (no crear)
└── WebFetch(domain)       → fetch a ese dominio

Precedencia: deny > allow
Si algo está en deny, no se permite aunque esté en allow.

Modos de ejecución:
├── --permission-mode default    (pregunta antes de cada acción)
├── --permission-mode acceptAll  (acepta todo sin preguntar — PELIGRO)
├── --permission-mode bypassAll  (ignora permissions — TESTING)
└── --permission-mode dontAsk    (deniega todo lo no explícito)
```

## Slide 13 — MCP configuration: arquitectura

```
~/.claude/                              (config global del usuario)
├── claude_desktop_config.json          (MCP servers globales)
│
Proyecto/
├── .claude/
│   └── settings.json                   (config proyecto)
└── .mcp.json                           (MCP servers del proyecto)

Jerarquía de MCP:
1. MCP del proyecto (.mcp.json)         → siempre cargado
2. MCP personal global (~/.claude/...)  → si habilitado
3. Plugins instalados                    → según plugin

Recomendación:
- MCP proyecto: los que todo el equipo necesita (ADO, Azure)
- MCP global: los personales (tu Notion, tu Gmail)
```

## Slide 18 — Hooks: ejecutar código antes/después de acciones

```bash
# .claude/hooks/pre-tool-use.sh
#!/bin/bash
# Se ejecuta ANTES de que Claude Code use cualquier tool
# Útil para: logging, validaciones, bloqueos por política

TOOL=$1
ACTION=$2

# Log de todas las acciones
echo "$(date) | $TOOL | $ACTION" >> ~/.claude-audit.log

# Bloqueo: no permitir deploy a prod en viernes tarde
if [[ "$ACTION" == *"az deployment"*"--subscription"*"prod"* ]]; then
  DOW=$(date +%u)
  HOUR=$(date +%H)
  if [[ $DOW -eq 5 && $HOUR -gt 14 ]]; then
    echo "❌ Deploy a prod bloqueado los viernes después de las 15h" >&2
    exit 1
  fi
fi

exit 0
```

```json
// settings.json
{
  "hooks": {
    "PreToolUse": ".claude/hooks/pre-tool-use.sh",
    "PostToolUse": ".claude/hooks/post-tool-use.sh"
  }
}
```

## Slide 21 — /commands: deploy con checks

```markdown
# .claude/commands/deploy-staging.md
# Comando: /deploy-staging

Deploy controlado a staging con estos pasos:

1. Verifica que estamos en rama `main` y está limpia (git status)
2. Ejecuta tests: `dotnet test`
3. Si tests pasan, haz build y publish
4. Valida Bicep: `az deployment group validate`
5. Ejecuta what-if contra rg-ventas-staging
6. Muestra el what-if y pide mi confirmación
7. Si confirmo, ejecuta el deploy a staging slot
8. Smoke test en staging (curl /health)
9. Reporta resultado

Si cualquier paso falla, para y dime qué pasó.
NO continúes si un paso falla.
```

Convertís el flujo repetitivo del deploy en una conversación de 1 línea.

## Slide 22 — MCP toolsets y read-only: seguridad

```json
// .mcp.json — ADO MCP restringido a read-only por defecto
{
  "mcpServers": {
    "azure-devops": {
      "type": "http",
      "url": "https://mcp.dev.azure.com/mi-org",
      "headers": {
        "X-MCP-Toolsets": "wit",       // Solo work items
        "X-MCP-Readonly": "true"        // Solo lectura
      }
    }
  }
}
```

Para producción, CC puede leer de ADO pero no puede cerrar work items ni mergear PRs. Humano en el loop para acciones con impacto.

Para entornos dev, quitáis readonly y añadís más toolsets (`repos,pipelines,wit`).

## Slide 24 — Checklist de setup para un proyecto Azure nuevo


## Slide 2 — Skill vs Agent: la diferencia
```
SKILL:
- "Cómo se hace X"
- Procedural, instrucciones
- Se ejecuta en la conversación principal
- Comparte el context window

AGENT (subagent):
- "Quién hace X"
- Configuración de subagente con tools propios
- Se ejecuta en un contexto separado (fork)
- Context window independiente
```

Analogía: un skill es un manual. Un agent es un especialista que ha leído ese manual (entre otros) y sabe cuándo aplicarlo.

## Slide 3 — Tipos de agentes en Claude Code
```
Built-in agents:
├── Explore       → optimizado para explorar código (read-only tools)
├── Plan          → optimizado para planificar (thinking extendido)
└── general-purpose → agent estándar con todos los tools

Custom agents (.claude/agents/):
├── Frontmatter define: nombre, description, tools, model
├── Contenido: system prompt del agent
└── Invocación: por nombre o auto-detectada por Claude
```

Los custom agents viven en `.claude/agents/` y se commitean con el proyecto.

## Slide 4 — Anatomía de un agent: estructura

```markdown
---
name: bicep-reviewer
description: "Use this agent when Bicep infrastructure files have been modified. Reviews for consistency, best practices, and Azure Verified Modules (AVM) opportunities."
tools: Glob, Grep, Read, WebFetch, WebSearch, Edit, Write, Bash(az *), TodoWrite
model: sonnet
---

# Bicep Reviewer Agent

You are a senior Azure infrastructure engineer specialized in Bicep.

Your job is to review Bicep files for:

1. **Correctness**
   - Syntax (run `az bicep build` to catch errors)
   - Resource dependencies (explicit vs implicit)
   - Parameter validation

2. **Best practices**
   - Module organization
   - Naming conventions (check against CLAUDE.md)
   - Managed Identity usage (prefer over keys)
   - Tags completeness

3. **Azure Verified Modules (AVM)**
   - If a custom module exists that AVM already provides, flag it
   - Lookup AVM registry: `br/public:avm/res/...`
   - Suggest migration path

4. **Security**
   - No hardcoded secrets
   - Key Vault references where appropriate
   - RBAC following least privilege
   - Network restrictions (no public access by default)

5. **Cost**
   - SKUs appropriate for env (dev ≠ prod)
   - Delete vs retain policies
   - Lifecycle rules

## Output format
Markdown report with sections:
- Summary (1 paragraph, high level assessment)
- Findings by severity (Critical, High, Medium, Low)
- Recommendations (actionable, with code examples)
- AVM migration opportunities (if any)
```

## Slide 6 — Built-in agents: Explore

**Explore** está diseñado para investigar código sin modificarlo.

```
Tools disponibles:
├── Glob       (buscar archivos por patrón)
├── Grep       (buscar contenido)
├── Read       (leer archivos)
├── WebFetch   (docs externas)
└── WebSearch  (búsqueda web)

Tools NO disponibles:
├── Write, Edit (read-only!)
├── Bash (por defecto)
└── Tools que modifiquen estado
```

Uso típico:
```bash
> Antes de implementar nada, usa el Explore agent para entender
  cómo funciona el módulo de autenticación actual
```

## Slide 7 — Built-in agents: Plan

**Plan** está diseñado para planificar antes de ejecutar. Usa extended thinking.

```
Características:
├── Extended thinking activado por defecto
├── Produce plans detallados antes de actuar
├── Identifica riesgos, dependencies, orden de pasos
└── Puede invocar Explore como sub-paso
```

Uso típico:
```bash
> Usa el Plan agent para diseñar la migración de la app 
  LegacyOrders de ClickOnce a MSIX.
  Necesito un plan con fases, tiempos estimados, y riesgos.

# El agent:
# 1. Analiza el proyecto (invoca Explore internamente)
# 2. Piensa (extended thinking)
# 3. Genera un plan por fases con checklists
# 4. Devuelve al thread principal
```

## Slide 8 — Cuándo crear un custom agent
Creáis un custom agent cuando:

✓ Hay una tarea recurrente que requiere especialización
✓ La tarea se beneficia de un contexto separado (no contamina el principal)
✓ Queréis restringir tools para seguridad (ej: reviewer sin write)
✓ Queréis un system prompt detallado solo para esa tarea
✓ Queréis usar un modelo diferente (Sonnet para review, Opus para arquitectura)

NO creáis un custom agent para:
✗ Tareas one-shot simples (un skill es suficiente)
✗ Cosas que ya hace el general-purpose bien
✗ Overengineering (empezad sin custom agents)

## Slide 9 — Custom agent #1: bicep-reviewer (completo)

```markdown
---
name: bicep-reviewer
description: "Review Bicep infrastructure files for correctness, best practices, AVM opportunities, security and cost. Invoke when Bicep files are modified or before deploying infrastructure changes."
tools: Glob, Grep, Read, WebFetch, WebSearch, Bash(az bicep *), TodoWrite
model: sonnet
---

You are a senior Azure infrastructure engineer.

# Process
1. Discover all Bicep files changed (git diff or user-specified)
2. For each file:
   a. Run `az bicep build` to catch syntax issues
   b. Read the file thoroughly
   c. Cross-reference with CLAUDE.md for team conventions
3. Build a findings list categorized by severity
4. Check if any of the recursos could use Azure Verified Modules (AVM)
5. Generate a structured report

# Team conventions to enforce (from CLAUDE.md)
- Managed Identity ALWAYS (never connection strings)
- Modular structure: main.bicep + modules/
- Naming: `<tipo>-<proyecto>-<entorno>`
- Tags: environment, project, managedBy, costCenter
- No hardcoded secrets — use Key Vault references

# Severity guidance
- Critical: exposed secrets, public access to sensitive resources
- High: missing MI, overly permissive RBAC, no monitoring
- Medium: wrong SKU for env, missing tags, old API versions
- Low: style, optional improvements, AVM opportunities

# Output
Use this exact structure:
## Bicep Review: [file or "PR changes"]

### Summary
<1-paragraph overall assessment>

### Critical Findings
<list, or "None">

### High Findings
<list with file:line references>

### Medium Findings
<list>

### Low Findings / Suggestions
<list>

### AVM Migration Opportunities
<if any, with example code>

### Overall Recommendation
<approve / approve-with-changes / reject>
```

## Slide 10 — Custom agent #2: security-auditor

```markdown
---
name: security-auditor
description: "Security audit of Azure infrastructure and code. Finds secrets in code, missing MI, public endpoints, weak RBAC, expired certs. Invoke manually or before releases."
tools: Glob, Grep, Read, Bash(az *), Bash(grep *)
model: sonnet
---

You are a security engineer specialized in Azure.

# Audit checklist

## 1. Secrets in code
Search patterns (case-insensitive):
- password[:=]
- apikey[:=]
- secret[:=]
- connectionstring.*password
- Bearer token patterns
- Azure SAS tokens (sv=, sig=)

Exclude:
- appsettings.Development.json (ok for dev values)
- comments with // TODO or // example
- test files with obvious mock values

Flag: any plausible secret in prod code.

## 2. Infrastructure checks (Bicep or Azure CLI queries)
- Storage: `allowBlobPublicAccess` should be `false`
- SQL: `publicNetworkAccess` should be `Disabled` or restricted
- Web Apps: `httpsOnly: true` required
- Recursos sin `identity: SystemAssigned` cuando aplica → FLAG

## 3. Entra ID / RBAC
- App registrations con owners = 0 → FLAG
- Client secrets con expiration > 24 meses → FLAG
- Role assignments en scope `/subscriptions/...` → REVIEW
- Usuarios con rol `Owner` → REVIEW (debería ser Contributor + PIM)

## 4. Certificates
- Certs en Key Vault con expiration < 30 días → FLAG
- Apps con certs custom sin auto-renewal → FLAG

## 5. Monitoring / Audit
- Resources sin Diagnostic Settings → FLAG
- Azure Activity Log sin retention > 90 días → REVIEW

# Output
Structured report with severity + recommended commands to fix.
Include `az` commands the user can run to remediate each finding.
```

## Slide 11 — Custom agent #3: cost-analyzer

```markdown
---
name: cost-analyzer
description: "Analyze Azure costs and find optimization opportunities. Invoke monthly or when cost alerts fire."
tools: Read, Bash(az *), TodoWrite
model: sonnet
---

You are an Azure FinOps specialist.

# Process
1. Ask user: subscription ID or resource group to analyze
2. Gather data:
   - `az consumption usage list` (last 30 days)
   - `az resource list` (all resources)
   - For each compute resource, get metrics (CPU, memory utilization)
   - For storage, get blob size + access tier
   - For databases, get DTU/RU consumption

3. Identify optimizations:
   - Compute underutilized (avg CPU < 20%)
   - Storage in wrong tier
   - Provisioned DBs that should be serverless
   - Orphaned resources (public IPs without binding, disks without VM)
   - Reserved instances opportunities (if predictable workload)

4. Estimate savings per optimization

# Output
| Resource | Current cost/mo | Optimized cost/mo | Savings | Action | Risk |
|----------|---:|---:|---:|---|---|
...

Sort by savings descending.
Include `az` commands to apply optimizations (but don't execute them).
Present the report and ask if user wants to apply any.
```

## Slide 12 — Custom agent #4: test-writer

```markdown
---
name: test-writer
description: "Write comprehensive unit tests for existing code using xUnit, Moq, FluentAssertions. Invoke when a service/class needs test coverage."
tools: Glob, Grep, Read, Write, Edit, Bash(dotnet test *)
model: sonnet
---

You are a QA engineer specialized in .NET testing.

# Process
1. Read the class/service to test
2. Identify:
   - Public methods to test
   - Dependencies to mock (constructor params)
   - Edge cases (null, empty, invalid, boundary values)
   - Error paths (exceptions thrown)

3. Generate test file following team conventions:
   - Location: `tests/<Project>.Tests/<Class>Tests.cs`
   - Framework: xUnit
   - Mocking: Moq
   - Assertions: FluentAssertions (`.Should().Be(...)`)
   - Naming: `MethodName_Condition_ExpectedResult`
   - Arrange/Act/Assert with comments

4. Run tests and report:
   - Total tests generated
   - Pass/fail count
   - Coverage estimate

5. If any test fails, analyze why (bug in code? bug in test?) and ask user

# Template
```csharp
public class [Service]Tests
{
    private readonly Mock<[Dep1]> _dep1Mock = new();
    private readonly Mock<ILogger<[Service]>> _loggerMock = new();
    private readonly [Service] _sut;

    public [Service]Tests()
    {
        _sut = new [Service](_dep1Mock.Object, _loggerMock.Object);
    }

    [Fact]
    public async Task MethodName_Condition_ExpectedResult()
    {
        // Arrange
        _dep1Mock.Setup(...).ReturnsAsync(...);

        // Act
        var result = await _sut.MethodName(...);

        // Assert
        result.Should().Be(expected);
        _dep1Mock.Verify(..., Times.Once);
    }
}
```
```

## Slide 13 — Custom agent #5: deploy-orchestrator

```markdown
---
name: deploy-orchestrator
description: "Orchestrate a full Azure deployment: validate, what-if, deploy infra, deploy app, smoke test. Use for complex multi-service deployments."
tools: Read, Bash(az *), Bash(azd *), Bash(dotnet *), Bash(curl *), TodoWrite
model: sonnet
---

You are a DevOps engineer orchestrating Azure deployments.

# Deployment workflow

## Pre-checks
1. Verify git is clean (no uncommitted changes on main)
2. Verify tests pass: `dotnet test`
3. Read CLAUDE.md for project-specific deployment rules
4. Check if any "frágil" files were changed — if yes, STOP and escalate

## Infrastructure (Bicep)
5. Validate: `az deployment group validate`
6. What-if: `az deployment group what-if`
7. Present what-if to user
8. Wait for explicit confirmation ("proceed" / "deploy" / "yes")
9. If confirmed: `az deployment group create`
10. Verify all resources provisioned correctly

## Application (App Service)
11. Build: `dotnet publish`
12. Deploy to staging slot
13. Smoke test staging: `curl -sf .../health`
14. If staging OK, swap to production
15. Post-swap smoke test

## Verification
16. Check App Insights for errors in last 5min
17. Report summary to user

# Rollback triggers
If any step fails, STOP and ask user:
- Rollback infrastructure? (az deployment group delete)
- Swap back to previous version?
- Ignore and continue?

NEVER rollback without user confirmation.
NEVER continue past a failed step silently.
```

## Slide 14 — Agent tool restrictions: defensa en profundidad

```yaml
# Reviewer agent: solo lectura, sin ejecución
---
name: code-reviewer
tools: Glob, Grep, Read, WebFetch   # ← sin Write, sin Bash
---

# Deployer agent: puede ejecutar az pero con alcance limitado
---
name: deployer-staging
tools: Read, Bash(az deployment group * --resource-group rg-staging *), Bash(dotnet publish *)
# Nota: el glob limita az a staging RG. No puede tocar prod.
---

# Orchestrator agent: muchos tools pero confirmación requerida
---
name: orchestrator
tools: Read, Write, Bash(az *), Bash(azd *), TodoWrite
# System prompt obliga a pedir confirmación antes de acciones destructivas
---
```

**Principio:** cada agent solo tiene los tools estrictamente necesarios. Los daños por errores o prompt injections se contienen.

## Slide 15 — Agentes en paralelo: workflows complejos

Claude Code puede ejecutar múltiples subagents en paralelo cuando hay partes independientes.

```bash
claude

> Haz un análisis completo pre-release del proyecto:
  - Seguridad
  - Costes
  - Calidad de código
  
  Todo en paralelo, reporta resultados cuando terminen.
```

Claude Code detecta que son tareas independientes y puede lanzar:
- `security-auditor` agent (fork 1)
- `cost-analyzer` agent (fork 2)
- `code-quality-reviewer` agent (fork 3)

Corren en paralelo. Cada uno devuelve su reporte. Claude Code los sintetiza en un resumen ejecutivo.

## Slide 16 — Orchestrator pattern: agente que coordina agentes

```markdown
---
name: release-gate
description: "Run full release gate: invoke security-auditor, cost-analyzer, test-coverage agents and decide if release can proceed"
tools: TodoWrite   # Solo orquesta, no ejecuta tools bajos
---

# Release Gate

Cuando el usuario pida "release gate":

1. Invoca en paralelo:
   - security-auditor (analizar cambios de esta release)
   - cost-analyzer (estimar impacto en costes)
   - test-writer (verificar cobertura en archivos nuevos/modificados)
   - bicep-reviewer (si hay cambios de infra)

2. Espera a que todos terminen y recoge sus reportes

3. Decisión:
   - Si algún Critical en security → BLOQUEAR release
   - Si cobertura nueva < 70% → BLOQUEAR release
   - Si increase de costes > 20% → REVIEW (no auto-bloquear)
   - Si Bicep review tiene High → REVIEW

4. Output final:
   - Resumen de cada agent
   - Decisión: PROCEED / HOLD / BLOCK
   - Acciones requeridas antes de proceder (si HOLD o BLOCK)
```

Uso:
```bash
> /release-gate   (o invocación por description)
```

## Slide 17 — Multi-agent chains: pipelines de agentes

Un patrón común: agente A produce output → agente B lo consume → etc.

```
Workflow: "feature ticket → código"

ticket-analyzer agent
    ↓ (produce: specs técnicas)
architect agent
    ↓ (produce: plan detallado con diseño)
test-writer agent
    ↓ (produce: tests fallando)
implementer agent
    ↓ (produce: código que pasa los tests)
bicep-reviewer agent
    ↓ (produce: review de infra)
deploy-orchestrator agent
    ↓ (produce: deploy a staging)
```

Cada agent hace su pedazo. El orquestador principal pasa contexto entre ellos.

**En la práctica:** no siempre funciona tan limpio. Humano en el loop entre agentes en fases tempranas.

## Slide 19 — Debugging agents: qué hacer si no funciona

**Problema 1: agent no se auto-invoca**
```
Causa: description vaga o demasiado genérica
Solución: añadir keywords específicos relacionados con cuándo activar
```

**Problema 2: agent se queda corto (no completa la tarea)**
```
Causa: faltan tools en el frontmatter
Solución: verificar que tiene todos los tools que necesita
Debug: añadir TodoWrite para que liste qué está haciendo
```

**Problema 3: agent hace cosas que no debería**
```
Causa: tools demasiado permisivos, system prompt ambiguo
Solución: restringir tools + refinar system prompt con "NEVER do X"
```

**Problema 4: agent tarda demasiado**
```
Causa: modelo Opus cuando Sonnet sería suficiente
Solución: bajar a Sonnet, o a Haiku para tareas simples
```

## Slide 21 — Coste de agents: optimizar el gasto

Cada invocación de agent consume tokens. Estrategias para optimizar:

```
Token budget por agent:
├── Modelo: sonnet es ~5x más barato que opus
├── Context: pasar solo archivos relevantes (no el repo entero)
├── Output: pedir resumen ejecutivo + detalles bajo demanda
└── Paralelización: agents simples en Haiku

Ejemplo de costes (abril 2026, aprox):
├── Claude Haiku: $1-3/M tokens input, $4-15/M output
├── Claude Sonnet: $3/M tokens input, $15/M output
├── Claude Opus: $15/M input, $75/M output

Agent bicep-reviewer con 500 líneas de Bicep:
├── Con Opus: ~$0.30 por invocación
├── Con Sonnet: ~$0.06 por invocación
├── Con Haiku: ~$0.015 por invocación
```

Regla: **empezad con el modelo más barato que dé calidad aceptable**. Subid de modelo si el output no es suficiente.

## Slide 22 — Agents en CI/CD: automatización

```yaml
# En un pipeline ADO, podéis invocar Claude Code con un agent específico
- task: Bash@3
  inputs:
    targetType: inline
    script: |
      # Instalar Claude Code
      npm install -g @anthropic-ai/claude-code

      # Invocar bicep-reviewer agent sobre los cambios de la PR
      git diff origin/main...HEAD -- 'infrastructure/**/*.bicep' > bicep-changes.diff

      if [ -s bicep-changes.diff ]; then
        claude --no-interactive --headless \
          --agent bicep-reviewer \
          --prompt "Review these Bicep changes: $(cat bicep-changes.diff)" \
          > review.md

        # Publicar review como comentario en la PR
        az repos pr comment create \
          --pull-request-id $(System.PullRequest.PullRequestId) \
          --content "$(cat review.md)"
      fi
  env:
    ANTHROPIC_API_KEY: $(ANTHROPIC_API_KEY)
```

El resultado: cada PR con cambios de Bicep recibe automáticamente review por IA.

## Slide 24 — Anti-patterns de agents

**1. Un agent para todo**
No creéis un "super-agent" que hace de todo. Fragmentad en agents especializados.

**2. Agents sin system prompt claro**
Si el system prompt es ambiguo, el agent hace cosas impredecibles. Seed clear + rules + constraints.

**3. Agents con acceso total (`Bash(*)`)**
Demasiado permisivo. Restringid a los comandos que el agent realmente necesita.

**4. Agents que se llaman a sí mismos en loop**
Si agent A invoca B, y B puede invocar A, cuidado con infinite loops.

**5. Demasiados agents (>20)**
Claude necesita elegir cuál invocar. Con muchos agents similares, confusión. Máx 5-10 agents diferenciados.

**6. No actualizar agents con lecciones**
Cuando un agent falla, añadid la lección al system prompt. "Si encuentras X, haz Y".

- Del proyecto → procesos del equipo (review, deploy, security)
- Personales → productividad individual (emails, calendarios, notas)

## Slide 27 — Roadmap de adopción de agents

```
Fase 1 (semanas 1-2): ningún agent custom
- Usar built-in (Explore, Plan) + Azure Skills Plugin
- Observar qué tareas se repiten manualmente

Fase 2 (mes 1): primer agent de reviewer
- Crear bicep-reviewer o code-reviewer
- Probar en algunas PRs
- Iterar el system prompt con lecciones aprendidas

Fase 3 (mes 2-3): agentes operativos
- security-auditor
- cost-analyzer
- deploy-orchestrator

Fase 4 (mes 4+): orquestación
- release-gate agent que combina varios
- Automatización en CI/CD
- Workflows multi-agent

Fase 5 (mes 6+): reflexión
- ¿Qué agents aportan valor real?
- ¿Cuáles podemos simplificar o eliminar?
- ¿Podemos compartir agents entre equipos de la empresa?
```

Los agents convierten Claude Code de "asistente interactivo" en "plataforma de especialistas". Cada agent tiene foco, tools propios, y system prompt optimizado. Pueden correr en paralelo, encadenarse, e integrarse en CI/CD.

La regla: **empezad simples, medid valor, iterad**. Un bicep-reviewer bien hecho vale por diez agents mediocres. Y combinados con los skills del submódulo anterior, construyen una plataforma de productividad potente.

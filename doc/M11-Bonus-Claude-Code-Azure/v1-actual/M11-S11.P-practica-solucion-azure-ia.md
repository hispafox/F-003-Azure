## Slide 3 — El caso: Gestión de incidencias
Vuestra solución: sistema simple de gestión de incidencias para IT.

```
Funcionalidad:
├── POST /api/incidencias     → crear incidencia
├── GET  /api/incidencias/{id} → leer
├── GET  /api/incidencias      → listar (filtros: estado, prioridad)
├── PATCH /api/incidencias/{id} → actualizar estado
│
├── Cosmos DB: container "incidencias"
├── Auth: Entra ID (JWT)
├── Event-driven:
│   ├── Al crear incidencia de prioridad "critical" → mensaje a SB
│   └── Function consume SB → notifica por Slack/Teams (simulado con log)
│
└── Observability: App Insights con eventos custom y métricas
```


## Slide 16 — Validación de calidad del código generado por IA

IA acelera, pero la calidad del código generado depende de cómo le pidáis y cómo lo verifiquéis. **No aceptéis código a ciegas.**

**Checklist de revisión antes de aceptar código generado:**

```
✅ FUNCIONAL:
[ ] El código compila sin warnings
[ ] Los tests del propio código pasan
[ ] Los tests existentes del proyecto siguen verdes
[ ] Coverage no bajó
[ ] Smoke tests E2E pasan

✅ ARQUITECTÓNICO:
[ ] Sigue el patrón del proyecto (CQRS, DDD, etc.)
[ ] Layers correctos (Domain en Domain/, no en Infrastructure/)
[ ] Dependencias inyectadas vía DI (no new()s salvajes)
[ ] Async donde corresponde (no .Result, no .Wait())
[ ] No introduce dependencias nuevas sin justificar

✅ SEGURIDAD:
[ ] Sin secretos hardcoded
[ ] Input validation en endpoints públicos
[ ] Sin SQL injection (usar parameterized queries)
[ ] Sin path traversal en file operations
[ ] Auth/authorization correctos en endpoints

✅ MANTENIBILIDAD:
[ ] Naming descriptivo (no var x, var foo)
[ ] Comentarios donde el "por qué" no sea obvio
[ ] Funciones <50 líneas, complexity razonable
[ ] No duplicación con código existente
[ ] Logging apropiado para debugging futuro

✅ PERFORMANCE:
[ ] No queries N+1 en EF Core / Cosmos
[ ] No allocations innecesarias en hot paths
[ ] Async streaming donde tenga sentido (no ToList() todo)
[ ] Caching donde aplique
```

**Ejecución del checklist en automation** (CI):

```bash
# Generar reporte de calidad post-código IA
dotnet build --warnaserror  # Compila SIN warnings
dotnet test --collect:"XPlat Code Coverage" --logger trx
dotnet format --verify-no-changes  # Style consistency
dotnet roslyn-analyzers  # Static analysis

# SonarQube si está configurado
sonar-scanner -Dsonar.qualitygate.wait=true
```

**Métricas de calidad antes vs después:**

```kusto
// Comparar bug rate antes/después de adoptar IA
let preIA = 
    Bugs
    | where created between (datetime(2025-01-01) .. datetime(2025-06-30))
    | summarize Count = count(), AvgSeverity = avg(severity);

let postIA = 
    Bugs
    | where created between (datetime(2025-09-01) .. datetime(2026-04-01))
    | summarize Count = count(), AvgSeverity = avg(severity);

print 
    PreIA_Bugs = toscalar(preIA | project Count),
    PostIA_Bugs = toscalar(postIA | project Count),
    Improvement = round(
        (toscalar(preIA | project Count) - toscalar(postIA | project Count)) 
        * 100.0 / toscalar(preIA | project Count), 2)
```

**Red flags en código IA:**

```
🚩 "TODO: implement" o "TODO: validate" sin contexto
   → IA dejó algo a medias, completar antes de mergear

🚩 Comentarios excesivos explicando lo obvio
   → IA llena espacio, no añade valor

🚩 Naming inglés cuando el resto del proyecto es español
   → IA no leyó CLAUDE.md o convenciones del proyecto

🚩 Try/catch que tragan excepciones (catch sin re-throw ni log)
   → IA sigue patrón "que parezca robusto" pero hace código frágil

🚩 Versiones fijas muy antiguas en NuGet
   → IA usó datos del training, no la última versión

🚩 Patterns over-engineered para lo que se pide
   → IA tiende a complicar; pedid simplicidad explícita
```

**Mantra para revisión:**
> "Sería un buen code review aunque viniera de un colega humano experimentado."
> 
> Si la respuesta es no, refactorizad o re-pedid.

## Slide 17 — Lessons learned: dónde IA aceleró y dónde no

Tras completar la práctica, reflexionad en grupo o individual:

**Donde la IA típicamente acelera 5-10x:**

```
✅ Boilerplate / scaffolding
   - Crear estructura de proyectos
   - DTOs, mappers, handlers vacíos
   - Configuración de servicios DI
   - Generación de Bicep desde descripción

✅ Migración de patterns conocidos
   - .NET Framework → .NET 8
   - Sync → Async
   - Tests legacy → tests modernos
   - JSON → DTOs strongly-typed

✅ Generación de tests
   - Unit tests para clases existentes
   - Integration tests con TestContainers
   - Performance tests con k6
   - Mock data realista

✅ Documentación
   - README, ARCHITECTURE.md, RUNBOOK
   - Comentarios XML para APIs públicas
   - Diagramas Mermaid desde código
   - Postman collections desde OpenAPI

✅ Debugging guiado
   - "Lee este stack trace y propón hipótesis"
   - "Genera KQL para investigar este síntoma"
   - "Dime qué configuración chequear primero"

✅ Code review preliminar
   - Identificar patterns problemáticos
   - Sugerir refactors evidentes
   - Detectar code smells
```

**Donde la IA NO acelera (o frena):**

```
❌ Decisiones arquitectónicas críticas
   - "¿Cosmos vs SQL?" → necesita contexto que IA no tiene
   - "¿Microservicios o monolito?" → trade-offs largos
   - "¿Build o buy?" → política organizacional

❌ Debugging con state distribuido complejo
   - 12 microservicios + Kafka + 3 DBs + CDN
   - IA no tiene visibilidad full-stack en runtime
   - Senior debugging real con telemetría sigue siendo humano

❌ Performance optimization extrema
   - IA conoce patterns generales
   - No conoce vuestro hardware específico, cache L1/L2/L3
   - Para "extraer último 5%" → profiling humano

❌ Compliance crítico sin review
   - GDPR/HIPAA/SOX requieren interpretation legal
   - IA aproxima pero NO sustituye legal counsel

❌ Innovación real (algoritmos novedosos)
   - IA replica patterns existentes
   - No hace research científica genuina (al menos en 2026)

❌ Negociación con stakeholders
   - Soft skills puramente humanos
   - IA puede ayudar con drafts pero no con la conversación
```

**Métrica de valor real en esta práctica:**

```
┌──────────────────────────────────────────────────┐
│ TIEMPO TOTAL DE LA PRÁCTICA                     │
├──────────────────────────────────────────────────┤
│ Esperado (sin IA, manual):  ~6-8 horas           │
│ Con Claude Code:            ~45-90 minutos       │
│ Aceleración:                ~5-8x                │
└──────────────────────────────────────────────────┘

¿Por qué el rango ancho?
- Quien sabe pedir bien (prompts estructurados): 45 min
- Quien itera mucho con IA (prompts vagos): 90 min
- Quien revisa código generado a fondo: 90 min
- Quien acepta sin revisar: 45 min pero genera tech debt
```

**Las 3 lecciones que típicamente emergen del debrief:**

```
1. "Sin CLAUDE.md robusto, IA inventa convenciones"
   → Inversión inicial en docs paga 100x

2. "Verificar lo generado es tan importante como pedirlo"
   → Tiempo de revisión > 0 siempre

3. "IA es force multiplier, no reemplazo"
   → Senior con IA: 10x productivo
   → Junior con IA: 2-3x productivo (necesita criterio aún)
```

**Para llevarse:**
> "El developer del 2026 no es 'el que escribe más código'.
>  Es 'el que dirige IA hacia outcomes valiosos con criterio'."

## Slide 2 — Qué vais a hacer

Configurar **CLAUDE.md** con contexto de un proyecto Azure y resolver **una sola task realista** con Claude Code: añadir un endpoint nuevo a una API .NET, desplegarlo a Azure y validar que funciona.

**El recorrido:**

```
1. Reutilizar (o crear) un proyecto .NET 8 simple
2. Crear un CLAUDE.md específico para Azure
3. Pedirle a Claude UNA task concreta:
   "Añade endpoint POST /productos a la API y despliega a Azure"
4. Revisar lo que Claude propone (no aceptar a ciegas)
5. Aprobar paso a paso
6. Validar el resultado
7. Iterar 1-2 veces si hay issues
8. Limpiar
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ MCP servers conectados a Azure (M11-S11.5)
- ❌ Sub-agentes especializados (M11-S11.4)
- ❌ Skills personalizadas (M11-S11.3)
- ❌ Pipeline IA-augmented (M11-S11.P principal)
- ❌ Cowork (M11-S11.7)
- ❌ Workflows avanzados (M11-S11.8)
- ❌ "Resuelvo todo el proyecto con IA" (M11-S11.P)

**Por qué esta práctica:**

- ✅ Primer contacto con Claude Code aplicado a Azure
- ✅ Modelo mental claro: "task → plan → review → execute → validate"
- ✅ Aprender a pedir (no a "delegar todo")
- ✅ Aprender a revisar lo que Claude propone
- ✅ Base mental antes de saltar a sub-agentes / pipelines IA

**Tiempo estimado:** 45-60 minutos.

**Coste real:** ~€0 en Azure (F1) + uso de plan Claude Pro o ~€0.05-0.20 en API.

cat > Program.cs << 'EOF'
var builder = WebApplication.CreateBuilder(args);

{
    new(1, "Laptop", 1299.00m),
    new(2, "Monitor", 349.00m)

app.MapGet("/health", () => Results.Ok(new { status = "healthy", time = DateTime.UtcNow }));

record Producto(int Id, string Nombre, decimal Precio);
EOF

# Verificar build
dotnet build
```

**Crear la Web App F1 si no tenéis una:**

## Slide 5 — Paso 2: Crear CLAUDE.md específico para Azure

Aquí está la diferencia clave: vuestro CLAUDE.md NO es genérico, debe darle a Claude todo el contexto Azure que necesita.

```bash
cat > CLAUDE.md << 'EOF'
# Project: ApiProductos

## Overview
API REST .NET 8 minimal API que gestiona un catálogo de productos.
Desplegada en Azure App Service (Linux Consumption F1).

## Stack
- Runtime: .NET 8.0 (LTS)
- Framework: ASP.NET Core minimal API
- Hosting: Azure App Service Plan F1 Linux
- BBDD: actualmente in-memory List<T> (a migrar)
- Region: West Europe
- IDE: VS Code o Visual Studio 2022

## Azure Resources
- Subscription: <vuestra-sub>
- Resource Group: rg-claude-azure-<tu-nombre>
- App Service Plan: plan-claude-<tu-nombre> (F1 Linux)
- Web App: webapp-claude-<tu-nombre>-XXXXX
- URL: https://webapp-claude-<tu-nombre>-XXXXX.azurewebsites.net

## Conventions
### Code style
- Records para DTOs (preferido sobre clases)
- async/await para I/O
- PascalCase para types y propiedades
- camelCase para variables locales
- Endpoints en formato REST: /productos, /productos/{id}

### Error handling
- 200/201/204 según operación exitosa
- 400 para inputs inválidos con problema details
- 404 si no existe
- 500 solo para errores no controlados (no propagar excepciones internas)

### Validation
- Validación inline en endpoints (esta app es simple)
- Title: no vacío, max 200 chars
- Precio: > 0
- Stock: >= 0

## Common Tasks
### Build & Test
```bash
dotnet build
dotnet test  # si hay proyecto de tests
```

### Local run
```bash
dotnet run
# Puerto: 5xxx (varía)
```

### Deploy a Azure
```bash
dotnet publish -c Release -o ./publish
cd publish && zip -rq ../app.zip . && cd ..
az webapp deploy \
  --name webapp-claude-<tu-nombre>-XXXXX \
  --resource-group rg-claude-azure-<tu-nombre> \
  --src-path ./app.zip --type zip
```

### Verificar deploy
```bash
curl -s https://<app>.azurewebsites.net/health | jq
curl -s https://<app>.azurewebsites.net/productos | jq
```

### Logs
```bash
az webapp log tail --name <app> --resource-group <rg>
```

## Lessons learned / Constraints
- Plan F1 tiene cold start (5-15s tras 20 min sin tráfico) — aceptable
- F1 tiene límite 60 min CPU/día — suficiente para esta app
- Storage in-memory NO persiste entre deploys (próximo paso: Cosmos o Table Storage)
- NO commitear connection strings ni secretos al repo

## What I'd like Claude to do
- ANTES de modificar archivos: mostrarme el plan
- ANTES de ejecutar comandos shell: pedir aprobación explícita
- Sugerir mejoras pero NO aplicarlas sin pedir permiso
- Validar que mis cambios siguen las convenciones de arriba
EOF
```

**IMPORTANTE: editar el CLAUDE.md** sustituyendo `<tu-nombre>` y los nombres reales de vuestros recursos.

```bash
# Reemplazar variables con valores reales
sed -i.bak "s/<tu-nombre>/$(echo $APP_NAME | sed 's/webapp-claude-//' | sed 's/-.*//')/g" CLAUDE.md
sed -i.bak "s/webapp-claude-<tu-nombre>-XXXXX/$APP_NAME/g" CLAUDE.md
rm CLAUDE.md.bak

# Verificar
head -30 CLAUDE.md
```

**Por qué este CLAUDE.md es importante:**

```
Sin esto, Claude:
- Inventa nombres de recursos
- Sugiere comandos genéricos sin contexto
- Pierde tiempo preguntando

Con esto, Claude:
- Conoce tu app exacta
- Usa los comandos que tienen sentido
- Sigue tus convenciones
- Va directamente al grano
```

## Slide 11 — Patrones útiles para tareas Azure

Algunos patrones de prompts que funcionan especialmente bien con Azure:

**Patrón 1: el plan antes de tocar nada**

```
> "Quiero hacer X. Antes, el plan: qué tocas, qué riesgos, qué tests."
```

**Patrón 2: validar cambio sin desplegar**

```
> "Implementa el cambio en local. NO despliegues todavía. 
> Valida que funciona en local primero."

(Después, en una segunda iteración, le pedís el deploy.)
```

**Patrón 3: Claude usa az CLI con vuestras variables**

```
> "Despliega a la Web App de mi CLAUDE.md. 
> Si hace falta cualquier dato adicional, pregúntalo."
```

**Patrón 4: explicar antes de modificar**

```
> "Antes de tocar nada, explícame cómo funciona el flow actual 
> de auth en este proyecto. Solo después haremos el cambio."
```

**Patrón 5: limitar el scope explícitamente**

```
> "Solo modifica Program.cs. NO toques otros archivos.
> NO modifiques infrastructure (los recursos en Azure)."
```

**Patrón 6: pedirle hacer lo opuesto (validar)**

```
> "Lee el código actual y dime qué bugs ves antes de añadir features. 
> Solo análisis, sin modificar nada."
```

**Patrón 7: dual-check con Azure CLI**

```
> "Verifica con az webapp show que la app esté en el plan F1 
> y la región correcta antes de hacer deploy."
```

**Patrón 8: pedir explicación de comandos antes de ejecutar**

```
> "Antes de ejecutar el comando az que propones, explícame 
> exactamente qué hace cada flag."
```

**Anti-patterns típicos a evitar:**

```
❌ "Dame el código completo de mi app entera"
   → demasiado scope, mucho rework

❌ "Resuelve todos los problemas"
   → no sabéis qué problemas detectó

❌ "Hazlo y dime cuando termines"
   → sin review, perdéis aprendizaje

❌ "Adivina qué quiero"
   → Claude inventa, vosotros corregís

✅ El patrón ganador:
   1. Una task concreta
   2. Plan ANTES
   3. Review del plan
   4. Aprobar diff
   5. Ejecutar
   6. Validar
```

## Slide 13 — Smoke tests con Claude

Pedirle a Claude que cree y ejecute un smoke test completo:

```
> Crea un script bash smoke-tests.sh que valide los siguientes endpoints 
> en mi Web App de Azure:
> 
> - GET /health → 200
> - GET /productos → 200 + array
> - POST /productos con datos válidos → 201
> - POST /productos con nombre vacío → 400
> 
> Después ejecuta el script contra mi Web App.
```

**Claude crea el script (similar al que veis en M02-S2.P2 / otras prácticas):**

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

BASE="${1:?Pasa la URL como primer argumento}"

echo "🔍 Smoke tests sobre $BASE"

# Test 1: Health
echo -n "  [1/4] GET /health... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/health")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 2: GET productos
echo -n "  [2/4] GET /productos... "
RESP=$(curl -s "$BASE/productos")
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$BASE/productos")
ARRAY_TYPE=$(echo $RESP | jq 'type')
if [ "$HTTP_CODE" = "200" ] && [ "$ARRAY_TYPE" = '"array"' ]; then
  echo "✓"
else
  echo "✗"
  exit 1
fi

# Test 3: POST válido
echo -n "  [3/4] POST /productos válido... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" -X POST "$BASE/productos" \
  -H "Content-Type: application/json" \
  -d '{"nombre":"SmokeTest","precio":1.0}')
[ "$HTTP_CODE" = "201" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 4: POST inválido
echo -n "  [4/4] POST /productos inválido... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" -X POST "$BASE/productos" \
  -H "Content-Type: application/json" \
  -d '{"nombre":"","precio":1.0}')
[ "$HTTP_CODE" = "400" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

echo ""
echo "✅ Smoke tests pasados"
EOF

chmod +x smoke-tests.sh
```

**Claude lo ejecuta:**

```
$ ./smoke-tests.sh "https://webapp-claude-pedro-12345.azurewebsites.net"

🔍 Smoke tests sobre https://webapp-claude-pedro-12345.azurewebsites.net
  [1/4] GET /health... ✓
  [2/4] GET /productos... ✓
  [3/4] POST /productos válido... ✓
  [4/4] POST /productos inválido... ✓

✅ Smoke tests pasados
```

**Patrón típico para futuras tareas:**

```
1. Hacer cambio
2. "Crea un smoke test que valide el cambio"
3. "Ejecuta el smoke test contra producción"
4. Si verde: ✓
5. Si rojo: pedir diagnóstico

## Slide 15 — Cuando Claude se equivoca

No siempre Claude tiene razón. Casos comunes:

**1. Inventa nombres de recursos**

```
Vosotros: "Despliega a mi web app"
Claude: "$ az webapp deploy --name mi-webapp --resource-group mi-rg ..."

❌ Esos nombres no son reales

Solución:
- CLAUDE.md específico (lo hicimos en paso 2)
- O en el prompt: "usa el nombre exacto de mi CLAUDE.md"
```

**2. Sugiere comandos peligrosos**

```
Claude: "Voy a ejecutar: az group delete --name <todo-mi-rg> --yes"

⚠️ Si pide eso por error → DECID NO

Cuándo desconfiar:
- rm -rf /
- az group delete sin confirmación
- Editar archivos del sistema (~/.bashrc, /etc/...)
- Modificar producción cuando deberías estar en dev
```

**3. Asume tecnología equivocada**

```
Claude: "Como es una app .NET 6..."
Vosotros: pero es .NET 8

Solución:
- CLAUDE.md actualizado
- Corregir en el prompt: "es .NET 8, ten en cuenta diferencias con minimal API"
```

**4. Aplica patrón sin entender contexto**

```
Vosotros: "Refactoriza para mejor performance"
Claude: implementa caching con Redis

Pero... vuestra app tiene 10 usuarios. Redis es overkill.

Solución:
- Pedir EL PLAN antes
- En el plan veríais "añadir Redis" → decir "no, demasiado complejo, busca algo más simple"
```

**5. No tiene contexto de runtime**

```
Vosotros: "Mi app está lenta"
Claude: "Probablemente es N+1 queries en EF Core"

Pero vosotros NO usáis EF Core. Claude está adivinando.

Solución:
- Dar más contexto: "uso Dapper, no EF Core"
- Pedirle inspeccionar primero: "lee Program.cs y dime cómo se hacen queries"
```

**Cómo detectar errores tempranos:**

```
1. Plan ANTES de modificar (siempre)
2. Review del plan con cuidado
3. Diff antes de aplicar
4. Validar tras cada cambio
5. Tests automáticos (smoke tests)
6. Git commits frecuentes (rollback fácil)
```

**Mantra:**

```
"Claude es un par de programación, no un junior que ejecuta sin pensar.
 Vosotros sois el senior que decide.
 Confiad pero verificad."
```

## Slide 17 — Troubleshooting

Errores comunes específicos de esta combinación:

**1. "Claude dice que mi CLAUDE.md no existe"**

```
Causa: directorio de Claude != directorio del proyecto
Diagnóstico:
> /pwd
   o
> Ejecuta pwd y muéstrame el resultado.

Si no es vuestra carpeta:
- /exit
- cd /ruta/correcta
- claude
```

**2. "Claude no aplica las convenciones del CLAUDE.md"**

```
Causa: CLAUDE.md mal escrito o muy genérico
Diagnóstico:
> Resúmeme las convenciones de mi CLAUDE.md.

Si Claude responde algo distinto a lo que pusisteis:
- Editar CLAUDE.md para ser MÁS explícito
- Especificar reglas como "MUST", "ALWAYS", "NEVER"

Ejemplo MAL: "usar buenas prácticas"
Ejemplo BIEN: "ALWAYS use record types for DTOs, NEVER use class for input models"
```

**3. "Claude ejecuta comandos pero falla az login"**

```
Síntoma: az command devuelve "Please run 'az login'"
Causa: la sesión az tiene un timeout

Fix:
> Necesito hacer az login. ¿Puedes ejecutarlo o lo hago yo?

Claude detecta que az login requiere browser interactivo
y os pide hacerlo manualmente.
```

**4. "El deploy con `az webapp deploy` tarda mucho"**

```
Tiempos normales:
- Primer deploy: 60-90 segundos
- Subsecuentes: 30-45 segundos

Si tarda >3 min:
- Problema de red
- Web App reiniciándose
- Storage Account lento (raro)

Claude reportará al final si timeout o error.
```

**5. "Claude propone cambios pero no los aplica"**

```
Causa: estáis en modo "plan" o el permiso lo bloqueó
Diagnóstico:
> /permissions
   o
> ¿Estás en modo plan?

Fix:
- /permissions → cambiar a default o acceptEdits
- Pedir explícitamente: "aplica los cambios ahora"
```

**6. "Tests tardan mucho en ejecutarse"**

```
Causa común: dotnet restore en cada test run
Síntoma: cada `dotnet test` tarda 30-60 seg

Fix:
> Ejecuta los tests con --no-build para que vaya más rápido.

Claude sabe usar el flag y os ahorra esos segundos.
```

**Cuando la sesión está "pegada":**

```
- /clear (limpia pantalla, mantiene contexto)
- /compact (compacta el contexto)
- /exit y volver a empezar
```

- Lee el diff antes de aceptar

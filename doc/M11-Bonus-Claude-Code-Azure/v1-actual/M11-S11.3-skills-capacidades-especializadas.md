## Slide 2 — Qué es un skill
Un skill es una carpeta con un archivo `SKILL.md` y opcionalmente archivos de apoyo (scripts, templates, docs). Claude Code los carga dinámicamente cuando la descripción del skill coincide con la tarea.

```
Analogía útil:
- Un CLAUDE.md es "lo que sabe el equipo".
- Un skill es "cómo el equipo hace X cosa concreta".

Ejemplo:
- CLAUDE.md dice: "Usamos Bicep para IaC".
- Skill "deploy-bicep-to-prod" dice: "Para desplegar a prod, estos son
  los pasos exactos: validar, what-if, pedir aprobación, deploy, verificar".
```

El skill es **procedural** y **auto-cargable**. Claude lo invoca cuando detecta que aplica.

## Slide 3 — Estándar abierto SKILL.md

Los skills siguen un estándar abierto (agentskills.io) compatible con Claude Code, Cursor, Gemini CLI, Codex CLI, Antigravity IDE, GitHub Copilot.

```markdown
---
name: deploy-to-azure
description: "Deploy a .NET app to Azure App Service with validation, what-if, and smoke tests"
allowed-tools: Bash, Read, Write
---

# Deploy to Azure App Service

When the user asks to deploy, follow these steps:

1. Run `dotnet test` first
2. Run `az bicep build` to validate IaC
3. Run `az deployment group what-if`
4. Show the what-if output and ask for confirmation
5. If confirmed, run `az deployment group create`
6. Run smoke test: `curl -sf $(APP_URL)/health`

Never skip step 4. Always show what-if to the user.
```

## Slide 5 — Cómo se carga un skill
Claude Code usa "progressive disclosure":

```
1. Arranque:
   - Claude lee todos los SKILL.md disponibles
   - Solo carga el FRONTMATTER (name + description)
   - No carga el contenido completo aún

2. Durante la conversación:
   - Claude analiza tu petición
   - Si la description de un skill coincide con la petición,
     Claude carga el contenido COMPLETO del SKILL.md
   - Sigue las instrucciones del skill

3. Archivos de apoyo:
   - Claude solo lee los archivos del skill si el SKILL.md los menciona
   - Ej: "Ver examples.md" → lo lee bajo demanda
```

Esto mantiene el context window eficiente. Un skill largo no consume tokens si no se invoca.

## Slide 6 — Frontmatter de un skill: todos los campos

```yaml
---
name: my-skill                     # Nombre (usado con /my-skill)
description: "Lo que hace el skill" # CRUCIAL: Claude decide cargarlo por esto
context: fork                       # fork = ejecuta en subagent (opcional)
agent: Explore                      # Qué agent usa si context=fork
allowed-tools: Bash, Read, Write   # Tools permitidos en este skill
model: sonnet                       # Modelo a usar (opcional)
---
```

**Campo más importante: `description`.** Si es vago, Claude nunca cargará el skill. Si es específico y con keywords, Claude lo cargará cuando aplique.

**Mal:** `description: "Helps with deployments"`
**Bien:** `description: "Deploy a .NET app to Azure App Service with validation, what-if preview, and post-deploy smoke tests"`

## Slide 7 — `!` syntax: ejecutar comandos antes del prompt

Los skills pueden ejecutar comandos shell antes de enviar el prompt al modelo. El output reemplaza el placeholder.

```markdown
---
name: pr-summary
description: Summarize the current pull request
allowed-tools: Bash(gh *)
---

## Pull request context
- PR diff: !`gh pr diff`
- PR comments: !`gh pr view --comments`
- Changed files: !`gh pr diff --name-only`

## Your task
Summarize this pull request:
- What changed (high level)
- Risks to watch for
- Files that need careful review
```

Cuando invocas `/pr-summary`, Claude Code ejecuta los `!` commands primero, inserta su output en el prompt, y envía todo al modelo. El modelo recibe **datos reales**, no el comando.

## Slide 9 — Skill útil #1: "convenciones-equipo"

Un skill que codifica las convenciones específicas del equipo:

```markdown
---
name: convenciones-equipo
description: "Apply our team's .NET + Azure coding conventions when generating or reviewing code"
---

# Convenciones del equipo Ventas

## C# / .NET 8
- async/await OBLIGATORIO en operaciones I/O
- records para DTOs (no clases con propiedades)
- Primary constructors donde sea posible
- CancellationToken en TODOS los métodos públicos async
- ILogger<T> con logging estructurado (no Console, no string.Format)
- ConfigureAwait(false) en librerías, no en apps

## Naming
- Clases/métodos: PascalCase, en inglés
- Variables: camelCase
- Constantes: PascalCase
- Archivos: PascalCase.cs (igual que la clase principal)
- Comentarios: ESPAÑOL (convención del equipo)

## Azure
- Managed Identity SIEMPRE. Nunca connection strings con password.
- Variables con sufijo __accountEndpoint, __fullyQualifiedNamespace
- DefaultAzureCredential en Program.cs
- RBAC asignaciones en Bicep, nunca a mano en portal

## Tests
- xUnit + FluentAssertions + Moq (no NUnit, no MSTest)
- Naming: MethodName_Condition_ExpectedResult
- Arrange/Act/Assert con comentarios
- 1 test = 1 assertion principal

## Git / PRs
- Conventional Commits (feat:, fix:, refactor:, etc.)
- PRs con description que vincule work item (Fixes #1234)
- Squash merge a main
```

Cuando pidáis a CC "genera un servicio", automáticamente cargará este skill y aplicará las convenciones.

## Slide 10 — Skill útil #2: "bicep-modular-pattern"

```markdown
---
name: bicep-modular-pattern
description: "Generate Bicep following our modular pattern with modules in infrastructure/modules/ and parameters per environment"
---

# Bicep modular pattern

Cuando generes Bicep para este proyecto, sigue este patrón:

## Estructura
```
infrastructure/
├── main.bicep              (orquestador, llama a módulos)
├── params.dev.json
├── params.staging.json
├── params.prod.json
└── modules/
    ├── app-service.bicep
    ├── cosmos-db.bicep
    ├── functions.bicep
    ├── service-bus.bicep
    ├── key-vault.bicep
    ├── app-insights.bicep
    └── rbac.bicep
```

## Convenciones
- Cada recurso de nivel superior va en su propio módulo
- main.bicep solo orquesta, no declara recursos directamente
- Parámetros críticos: `environment`, `location`, `appName`
- Outputs: cada módulo expone `name`, `id`, y `principalId` (si aplica)
- Managed Identity siempre: `identity: { type: 'SystemAssigned' }`
- Sin secretos hardcoded — usar Key Vault references

## Nombres de recursos
- Patrón: `<tipo>-<proyecto>-<entorno>`
- Ej: app-ventas-prod, func-ventas-staging, cosmos-ventas-dev
- Storage Accounts: sin guiones, minúsculas → `stventasprod`
- Key Vault: `kv-<proyecto>-<entorno>` (máx 24 chars)

## Tags obligatorios
Todos los recursos deben tener:
- environment: dev/staging/prod
- project: ventas
- managedBy: bicep
- costCenter: (leer de params)
```

## Slide 11 — Skill útil #3: "azure-cost-review"

```markdown
---
name: azure-cost-review
description: "Review Azure resources for cost optimization opportunities — unused resources, wrong SKUs, idle spend"
allowed-tools: Bash(az *), Read
---

# Azure Cost Review

Realiza una auditoría de costes sobre el resource group indicado.

## Pasos
1. Lista recursos: !`az resource list -g $RG -o table`
2. Para cada recurso, analiza:
   - ¿Tiene tráfico/uso reciente? (métricas de los últimos 30 días)
   - ¿El SKU es apropiado para el uso real?
   - ¿Hay alternativas más baratas que cumplan los mismos SLOs?

## Red flags a buscar
- App Service Plan Premium con <20% CPU promedio → bajar a Standard
- Cosmos DB provisioned con <20% RU usadas → cambiar a Serverless
- Storage Account con cientos de GB en Hot tier sin accesos → pasar a Cool/Archive
- VMs encendidas 24/7 que solo se usan en horario laboral → auto-shutdown
- Public IPs asignadas a recursos borrados (huérfanas)
- Log Analytics con retención de 90 días cuando nadie consulta >30 días
- Application Insights con sampling desactivado ingiriendo >5GB/día

## Output
Tabla con columnas:
| Recurso | Coste/mes actual | Coste/mes optimizado | Ahorro | Acción |

Al final, orden priorizado por ahorro y comando az exacto para cada optimización.
```

## Slide 12 — Skill útil #4: "security-review-azure"

```markdown
---
name: security-review-azure
description: "Security audit of Azure infrastructure and code — secrets in code, public endpoints, missing Managed Identity, weak RBAC"
allowed-tools: Bash(az *), Bash(grep *), Read
---

# Security review para Azure

Auditoría de seguridad completa. Analiza:

## 1. Secrets en código
- Busca patrones: password, apikey, connectionstring, secret
- Excluye: appsettings.Development.json, comentarios con TODO
- Flag: cualquier valor con aspecto de secret en código commiteado

## 2. Infraestructura
- Storage Accounts con `allowBlobPublicAccess: true` → FLAG
- SQL Servers sin firewall (`publicNetworkAccess: Enabled` sin restricciones) → FLAG
- Web Apps sin `httpsOnly: true` → FLAG
- Recursos sin Managed Identity cuando podrían tenerla → FLAG
- Key Vault con `publicNetworkAccess: Enabled` sin Private Endpoint → FLAG

## 3. RBAC
- Asignaciones con scope `subscription` (muy amplio) → REVIEW
- Principals con rol `Owner` o `Contributor` → REVIEW
- Service Principals sin rotación en >1 año → FLAG

## 4. Entra ID
- App Registrations con `allowPublicClient: true` → REVIEW
- Client Secrets con expiración >2 años → FLAG
- App Registrations sin owners → FLAG

## Output
Reporte en 3 severidades:
🔴 Critical — fix inmediato
🟡 Medium — plan de corrección
🟢 Info — mejora recomendada
```

## Slide 17 — Skills anti-patterns: qué evitar

**1. Skills que duplican CLAUDE.md**
CLAUDE.md se carga siempre. Si algo aplica a todo el proyecto, va en CLAUDE.md. Los skills son para procedimientos específicos.

**2. Skills enormes (>500 líneas)**
Partidlo en varios skills o usad archivos de apoyo. Un skill largo consume más tokens cuando se carga.

**3. Skills que solicitan credenciales**
Nunca. Credenciales van en variables de entorno o Key Vault.

**4. Skills que se contradicen**
Si tenéis "deploy-aggressive" y "deploy-conservative" con criterios opuestos, Claude no sabe cuál aplicar. Unificad.

**5. Skills sin tools restringidos**
Si el skill solo necesita leer, no le deis `Write` ni `Bash(*)`. Principio de menor privilegio.

## Slide 20 — Skill propio completo: "migrate-clickonce-to-msix"

Contexto vuestro: tenéis apps ClickOnce y queréis migrar a MSIX (viene del M7).

```markdown
---
name: migrate-clickonce-to-msix
description: "Guide the migration of a ClickOnce app to MSIX packaging with AppInstaller for auto-update"
allowed-tools: Bash, Read, Write, Edit
---

# Migración ClickOnce → MSIX

Cuando el usuario pida migrar una app de ClickOnce a MSIX, sigue este proceso:

## Fase 1: Análisis
1. Identifica el proyecto WPF/WinForms que estaba en ClickOnce
2. Lee el .csproj y detecta:
   - Framework actual (.NET Framework 4.x vs .NET 8)
   - Publish profile de ClickOnce existente
   - Dependencias (VCLibs, etc.)
3. Genera reporte del estado actual

## Fase 2: Preparación
1. Si es .NET Framework, pregunta si van a migrar a .NET 8 primero
2. Añade Windows Application Packaging Project (.wapproj)
3. Configura Package.appxmanifest con:
   - Identity (Name, Version, Publisher del cert)
   - Visual elements (logos, colores)
   - Capabilities mínimas necesarias
   - Dependencies

## Fase 3: Firma
1. Genera el certificado para dev (makecert/New-SelfSignedCertificate)
2. Configura AzureSignTool para prod (Key Vault)
3. Añade al pipeline:
   ```yaml
   - task: MSBuild@1
     inputs:
       solution: Package.wapproj
       msbuildArguments: '/p:AppxPackageSigningEnabled=true /p:PackageCertificateKeyFile=$(certPath)'
   ```

## Fase 4: AppInstaller
1. Genera el archivo .appinstaller con auto-update
2. Sube a Blob Storage (contenedor público o SAS)
3. Configura OnLaunch con HoursBetweenUpdateChecks

## Fase 5: Migración de datos
1. Detecta paths de datos de usuario en ClickOnce
2. Genera script de migración (copiar datos ClickOnce → MSIX storage)
3. Añade llamada al script en primer arranque

## Fase 6: Distribución
1. Documenta cómo desinstalar ClickOnce (los usuarios deben hacerlo)
2. Prepara email al grupo piloto con link de instalación
3. Checklist de verificación post-instalación

En cada fase, ejecuta lo necesario y reporta. Si encuentras problemas específicos
del proyecto del usuario, adapta las instrucciones.
```

Este skill es ORO para vuestro equipo: codifica la experiencia de un ingeniero senior en el proceso de migración.

## Slide 21 — Skill propio completo: "generate-azure-function"

```markdown
---
name: generate-azure-function
description: "Generate a new Azure Function with .NET 8 isolated worker, bindings, tests, and Bicep infrastructure"
allowed-tools: Read, Write, Edit
---

# Generar nueva Azure Function

Para generar una nueva Azure Function, sigue estos pasos:

## 1. Información necesaria
Pregunta al usuario (si no está claro en el prompt):
- Nombre de la función
- Trigger: HTTP / Timer / Blob / Cosmos / Service Bus / Event Grid
- Bindings de input/output necesarios
- Datos que procesa (DTOs)

## 2. Generación del código
Usa estas convenciones (del equipo):
- .NET 8 isolated worker (no in-process)
- [Function] attribute con nombre explícito
- ILogger<NombreFunction> inyectado
- Managed Identity para conexiones (NUNCA connection strings)
- Variables con sufijos __accountEndpoint, __blobServiceUri
- CancellationToken en métodos async

Ejemplo para Cosmos DB Change Feed trigger:
```csharp
public class DetectarPedido
{
    private readonly ILogger<DetectarPedido> _logger;
    public DetectarPedido(ILogger<DetectarPedido> logger) => _logger = logger;

    [Function(nameof(DetectarPedido))]
    [ServiceBusOutput("pedido-eventos", Connection = "ServiceBus")]
    public string Run(
        [CosmosDBTrigger("tienda", "pedidos", Connection = "CosmosDb",
            LeaseContainerName = "leases", CreateLeaseContainerIfNotExists = true)]
        IReadOnlyList<Pedido> cambios)
    {
        _logger.LogInformation("Procesando {Count} pedidos", cambios.Count);
        return JsonSerializer.Serialize(cambios.Select(p => new { p.Id, tipo = "PedidoCreado" }));
    }
}
```

## 3. Tests unitarios
Genera tests con xUnit + Moq + FluentAssertions que cubran:
- Caso feliz
- Input vacío
- Input con datos inválidos
- Excepción inesperada (debería loggearse, no silenciarse)

## 4. Infraestructura Bicep
Actualiza `infrastructure/modules/functions.bicep` para añadir:
- La app setting necesaria para conexiones (MI sufijos)
- Permisos (RBAC) para acceder a recursos referenciados

## 5. Actualiza pipeline si hace falta
Si la función añade nueva dependencia a otro servicio, actualiza azure-pipelines.yml.

## 6. Documenta
Añade entrada a docs/functions-reference.md con el trigger, inputs, outputs, y comportamiento.
```

## Slide 22 — Skills compartidos vs personales: gobierno

**Skills del proyecto (commiteados):**
- Requieren review como cualquier código
- PR, aprobación, merge
- Cambios los ve todo el equipo

**Skills personales (en `~/.claude/skills/`):**
- Cada uno con los suyos
- No se revisan
- Riesgo: cada dev trabaja diferente

**Recomendación:**
- Todo skill que defina proceso del equipo → versionado en el repo
- Skills personales solo para workflow individual (ej: "summarize my emails")
- El lead revisa periódicamente los skills del proyecto y los refina

## Slide 25 — Compartir skills entre equipos
Si vuestra organización tiene varios equipos con Claude Code:

```
Monorepo de skills corporativos:
├── company-skills/
│   ├── .claude/skills/
│   │   ├── conventions-company/
│   │   ├── security-review-company/
│   │   └── cost-review-company/
│   └── README.md

Cada equipo hace symlink o git submodule a este repo.

O publicáis como plugin interno:
# .claude/plugins/
#   └── company-plugin/ → skills + MCP custom internos

/plugin install company@https://azuredevops/company/plugin.git
```

Resultado: convenciones corporativas en todos los proyectos automáticamente.

## Slide 26 — Skills + Cowork: reutilización
**Importante:** Los skills funcionan en Claude Code Y Cowork. Un skill bien escrito vale en los dos productos.

```
.claude/skills/
└── azure-cost-report/
    └── SKILL.md

# Desde Claude Code (terminal, para devs):
claude
> Ejecuta el skill azure-cost-report para rg-ventas-prod

# Desde Cowork (desktop, para managers):
Cowork > "Use the azure-cost-report skill for rg-ventas-prod and save as report.xlsx"
```

Mismo skill, dos audiencias. Codificáis la experiencia una vez, todos se benefician.

## Slide 28 — Cierre del submódulo
Los skills son el mecanismo para codificar la experiencia del equipo en algo que Claude Code usa automáticamente. No "prompts guardados" — procedimientos ejecutables con contexto y buenas prácticas.

Microsoft publica 20 skills oficiales para Azure. La comunidad tiene >1000. Pero los más valiosos son los vuestros: los que codifican cómo VUESTRO equipo trabaja con Azure específicamente.

Siguiente: agentes y subagentes — el siguiente nivel de especialización.

## Slide 3 — ¿Por qué VS Code y no Visual Studio?
No es una decisión contra Visual Studio. Es a favor del denominador común:

**Para los desarrolladores .NET:**
C# Dev Kit tiene IntelliSense, depuración, refactorización y explorador de tests. No es Visual Studio completo, pero para proyectos de App Service y Functions es más que suficiente.

**Para el equipo de sistemas:**
Terminal integrada, extensiones Azure, edición de YAML y Bicep con validación en tiempo real. No necesitáis instalar Visual Studio para editar un pipeline.

**Para todos:**
- Arranca en 2-3 segundos (VS puede tardar 30+)
- Consume 200-400 MB de RAM (VS consume 1-4 GB)
- Funciona en Windows, macOS y Linux
- Extensiones para literalmente cualquier cosa

**Visual Studio sigue siendo válido** para soluciones grandes, WPF/MAUI, y debugging avanzado con profiler. Pero para este curso, VS Code es donde todos partimos igual.

## Slide 8 — Instalar todas las extensiones por script

```bash
#!/bin/bash
# setup-extensiones.sh — Ejecutar una vez en cada máquina

# .NET

# Productividad
code --install-extension humao.rest-client
code --install-extension eamodio.gitlens
code --install-extension usernamehw.errorlens

# Verificar
echo "Extensiones instaladas:"

```

**Compartid este script con el equipo.** Cada persona lo ejecuta una vez y tiene el mismo entorno. Cero diferencias entre máquinas, cero "a mí me funciona".

## Slide 9 — .NET 8 SDK: instalación y verificación

```bash
# Windows
winget install Microsoft.DotNet.SDK.8

# macOS
brew install dotnet@8

# Linux (Ubuntu)
sudo apt install dotnet-sdk-8.0

# Verificar
dotnet --version           # 8.0.x

dotnet --list-runtimes     # Todos los runtimes
```

**¿.NET 8 o .NET 9?**
- .NET 8: LTS (Long Term Support) — soporte hasta noviembre 2026
- .NET 9: Current — más features pero soporte hasta mayo 2026

Para el curso y para producción: **LTS siempre.** Las empresas no quieren migrar cada 6 meses.

**Si ya tenéis .NET 9:** No hay conflicto. Ambos SDKs coexisten. Para forzar .NET 8 en un proyecto, el `.csproj` tiene `<TargetFramework>net8.0</TargetFramework>`. O usáis `global.json`:
```json
{
  "sdk": {
    "version": "8.0.300",
    "rollForward": "latestFeature"
  }
}
```

## Slide 10 — Azure Functions Core Tools

Core Tools permite crear, ejecutar y depurar Azure Functions en local:

```bash
# Windows
winget install Microsoft.Azure.FunctionsCoreTools

# macOS
brew tap azure/functions
brew install azure-functions-core-tools@4

# npm (multiplataforma)
npm install -g azure-functions-core-tools@4 --unsafe-perm true

# Verificar
func --version    # 4.x
```

**¿Por qué es imprescindible?**
Sin Core Tools, cada cambio en una Function requiere desplegar a Azure, esperar, probar, ver el error, corregir, volver a desplegar. Con Core Tools: `func start`, pruebas en 2 segundos, iteras rápido.

**Verificación rápida:**
```bash
mkdir test-func && cd test-func
func init --worker-runtime dotnet-isolated --target-framework net8.0
func new --name Test --template "HTTP trigger"
func start
# Debería arrancar en http://localhost:7071
```

## Slide 15 — Configuración de debugging en VS Code

Para depurar proyectos .NET, VS Code necesita un archivo `launch.json`:

**Creación automática:**
1. Abrid un proyecto .NET
2. Pulsad F5
3. VS Code detecta el proyecto y crea `.vscode/launch.json`

**Configuración manual (`.vscode/launch.json`):**
```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": ".NET Core Launch (web)",
      "type": "coreclr",
      "request": "launch",
      "preLaunchTask": "build",
      "program": "${workspaceFolder}/bin/Debug/net8.0/MiApp.dll",
      "args": [],
      "cwd": "${workspaceFolder}",
      "stopAtEntry": false,
      "env": {
        "ASPNETCORE_ENVIRONMENT": "Development"
      }
    }
  ]
}
```

**Para Azure Functions (`.vscode/launch.json`):**
```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Attach to .NET Functions",
      "type": "coreclr",
      "request": "attach",
      "processId": "${command:azureFunctions.pickProcess}"
    }
  ]
}
```

## Slide 16 — Tasks: automatizar builds en VS Code

El archivo `.vscode/tasks.json` define tareas que VS Code ejecuta al depurar o con atajos:

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build",
      "command": "dotnet",
      "type": "process",
      "args": ["build", "${workspaceFolder}/MiApp.csproj"],
      "problemMatcher": "$msCompile"
    },
    {
      "label": "publish",
      "command": "dotnet",
      "type": "process",
      "args": ["publish", "-c", "Release", "-o", "./publish"],
      "problemMatcher": "$msCompile"
    },
    {
      "label": "test",
      "command": "dotnet",
      "type": "process",
      "args": ["test", "--verbosity", "normal"],
      "problemMatcher": "$msCompile"
    }
  ]
}
```

**Atajos:**
- `Ctrl+Shift+B` → Ejecutar tarea de build por defecto
- `Ctrl+Shift+P` → "Tasks: Run Task" → elegir tarea

## Slide 24 — Dev Containers: reproducibilidad del entorno

Que todos los devs tengan el mismo entorno es una pelea continua. **Dev Containers** lo resuelven: tu entorno de desarrollo vive en un contenedor Docker, declarado en el repo:

```json
// .devcontainer/devcontainer.json
{
  "name": "Ventas Azure Dev",
  "image": "mcr.microsoft.com/devcontainers/dotnet:8.0",
  "features": {
    "ghcr.io/devcontainers/features/azure-cli:1": {},
    "ghcr.io/devcontainers/features/node:1": {"version": "20"},
    "ghcr.io/devcontainers/features/docker-in-docker:2": {},
    "ghcr.io/azure/azure-dev/azd:latest": {},
    "ghcr.io/devcontainers/features/github-cli:1": {}
  },
  "customizations": {
    "vscode": {
      "extensions": [
        "ms-azuretools.vscode-azureresourcegroups",
        "ms-azuretools.vscode-bicep",
        "ms-dotnettools.csdevkit",
        "humao.rest-client",
        "eamodio.gitlens"
      ],
      "settings": {
        "editor.formatOnSave": true,
        "terminal.integrated.defaultProfile.linux": "bash"
      }
    }
  },
  "postCreateCommand": "dotnet tool install -g dotnet-ef && dotnet tool install -g dotnet-outdated-tool",
  "remoteUser": "vscode"
}
```

**Ventajas:**
- Nuevo dev clona el repo → VS Code abre en dev container → todo funciona
- Sin "a mí me funciona pero a ti no" (todos tienen el mismo entorno)
- Versiones pinneadas de SDK, herramientas, extensiones
- Funciona en macOS, Windows (con WSL), Linux, Codespaces idéntico

**Requisito:** Docker Desktop (o equivalente) instalado localmente. Para equipos sin Docker local, Codespaces es la alternativa.

## Slide 25 — GitHub Codespaces: VS Code en el navegador

Si vuestra empresa usa GitHub y queréis eliminar la fricción de setup:

```
¿Qué es?
├── Un Dev Container corriendo en GitHub Cloud
├── VS Code renderizado en navegador (o desktop via VS Code)
├── Acceso SSH / terminal / puertos forwarded
└── Estado persistente: puedes volver al mismo Codespace días después

Casos de uso ideales:
✓ Onboarding: día 1, nuevo dev productivo en 5 min
✓ Pair programming entre ubicaciones
✓ Demos (link temporal, sin setup)
✓ Trabajar desde máquinas no-dev (iPad, Chromebook)
✓ Contextos aislados (cliente A / cliente B sin contaminación)

Cómo arrancar:
1. En GitHub repo → Code → Codespaces → Create codespace
2. Se despliega en ~30s (ya con .devcontainer/ aplicado)
3. VS Code abre en navegador
4. Trabajas normal: commits, push, debug...

Precios (2026):
├── Gratuito: 60h/mes para 2-core (personal accounts)
├── Team: ~$0.18/h por 2-core
├── Pro: 4-core, 8-core, 16-core disponibles
```

**Patrón típico:** `.devcontainer/` bien cuidado → ambos entornos (local Docker + Codespaces) son idénticos. Los devs eligen cuál prefieren.

## Slide 26 — WSL: desarrollo Linux desde Windows

Si estáis en Windows y trabajáis con .NET 8 / Azure, **WSL2** (Windows Subsystem for Linux) es prácticamente obligatorio en 2026:

```powershell

```


## Slide 29 — Live Share: pair programming remoto

VS Code Live Share permite que dos (o más) devs trabajen en el **mismo archivo** en tiempo real:

## Slide 30 — .editorconfig y .gitattributes: consistencia del equipo

Diferencias sutiles entre devs (tabs vs spaces, line endings, encoding) se vuelven guerra fratricida. Dos archivos los resuelven:

```ini
# .editorconfig (raíz del repo)
# https://editorconfig.org
root = true

[*]
indent_style = space
indent_size = 4
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true

[*.{json,yml,yaml,md}]
indent_size = 2

[*.cs]
# Reglas específicas C# (naming, var, etc.)
csharp_style_var_when_type_is_apparent = true:suggestion
csharp_new_line_before_open_brace = all
```

```gitattributes
# .gitattributes (raíz del repo)
# Normaliza line endings cross-platform
* text=auto eol=lf

# Archivos binarios (no convertir)
*.png binary
*.jpg binary
*.pdf binary
*.pfx binary

# Archivos Windows-específicos (mantener CRLF)
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

# Linguist overrides (GitHub language detection)
*.razor linguist-language=HTML
```

**Impacto inmediato:** no más PRs con 1000 cambios que solo son espacios. Los editores respetan .editorconfig automáticamente. Git normaliza line endings en cada commit.

## Slide 31 — Profiles de VS Code: separar contextos

Si trabajáis en múltiples stacks (Azure .NET + frontend React + data Python), tener todas las extensiones cargadas siempre ralentiza VS Code. **Profiles** lo resuelven:

```
VS Code Profiles (File → Preferences → Profiles):

Crear profiles específicos:
├── "Azure .NET" — extensiones Azure + C# Dev Kit + Bicep
├── "Frontend" — ESLint + Prettier + React snippets + Tailwind
├── "Data" — Python + Jupyter + Polyglot notebooks

Switch entre profiles:
├── Click nombre del profile (barra inferior izquierda)
├── O: Ctrl+Shift+P → "Profiles: Switch Profile"
└── VS Code recarga con las extensiones/settings del profile elegido

Cada profile tiene:
├── Extensiones instaladas
├── Settings (settings.json)
├── Keybindings
├── Snippets
├── UI state (workspaces, layouts)

Exportar/importar profiles:
└── Ctrl+Shift+P → "Profiles: Export Profile" → .code-profile
# Compartir con el equipo
```

**Ventaja:** VS Code más rápido (solo las extensiones necesarias activas), contextos mentalmente separados.

## Slide 35 — Problemas comunes en la configuración

**IntelliSense no funciona en C#:**
→ Verificad que C# Dev Kit está instalado y habilitado
→ `Ctrl+Shift+P` → "OmniSharp: Restart" (o ".NET: Restart Language Server")
→ Verificad que `dotnet --version` devuelve resultado

**La extensión de Azure no muestra recursos:**
→ `Ctrl+Shift+P` → "Azure: Sign In" (re-autenticad)
→ Verificad el filtro de suscripción en settings.json
→ `Ctrl+Shift+P` → "Azure: Refresh"

**`code` no funciona desde la terminal:**
→ Windows: reinstalad VS Code marcando "Add to PATH"
→ macOS: `Ctrl+Shift+P` → "Shell Command: Install 'code' command in PATH"

**`az login` falla con error de tenant:**
→ Verificad que estáis en la red correcta (no VPN a otro tenant)
→ Usad `az login --tenant <id>` para especificar

**`func start` no arranca:**
→ Verificad Core Tools: `func --version`
→ Si es un proyecto .NET: `dotnet build` primero
→ Verificad que el puerto 7071 no está ocupado

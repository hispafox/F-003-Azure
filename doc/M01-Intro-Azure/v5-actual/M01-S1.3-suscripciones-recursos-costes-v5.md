## Slide 2 — Por qué importa la organización
Azure hace que crear recursos sea extremadamente fácil. Demasiado fácil. Tres clics y tienes una base de datos. Cinco comandos y tienes un cluster entero.

El problema no es crear. El problema es que seis meses después nadie sabe quién creó qué, para qué proyecto, si sigue siendo necesario, y por qué la factura subió un 40%.

La organización en Azure no es burocracia. Es la diferencia entre una cuenta controlada y un caos con factura sorpresa.

## Slide 3 — Jerarquía de gestión en Azure

```
Tenant (Entra ID / Azure AD)
│   └── Tu organización. Identidades, usuarios, grupos.
│
├── Management Groups (opcionales)
│   └── Agrupan suscripciones. Políticas a nivel organizativo.
│       Ejemplo: "MG-Europa" con políticas de GDPR.
│
├── Subscriptions (contratos de facturación)
│   └── Cada suscripción = una factura separada.
│       Ejemplo: "Sub-Produccion", "Sub-Desarrollo".
│
├── Resource Groups (contenedores lógicos)
│   └── Agrupan recursos relacionados. Unidad de gestión diaria.
│       Ejemplo: "rg-miapp-prod", "rg-miapp-dev".
│
└── Resources (servicios individuales)
    └── App Service, Function App, Cosmos DB, Key Vault...
```

Cada nivel hereda las políticas y permisos del nivel superior. Si asignáis una política al Management Group, aplica a todas las suscripciones dentro. Si asignáis permisos a un Resource Group, todos los recursos dentro los heredan.

## Slide 4 — Tenant: la raíz de todo

El Tenant es vuestra organización en Microsoft Entra ID (antes Azure AD):

**Qué contiene:**
- Todos los usuarios y grupos de la organización
- Aplicaciones registradas (OAuth2, service principals)
- Políticas de acceso condicional
- Configuración de MFA

**Identificación:**
- Cada tenant tiene un ID único (GUID)
- Y un nombre de dominio: `miempresa.onmicrosoft.com` (o vuestro dominio personalizado)

**¿Por qué importa?**
Si tenéis acceso a varios tenants (por ejemplo, el de vuestra empresa y el de un cliente), cada `az login` opera en un tenant específico. Si creáis recursos "en el tenant equivocado", los estáis creando en la cuenta de otro.

```bash
# Ver en qué tenant estáis
az account show --query tenantId --output tsv

# Login en un tenant específico
az login --tenant miempresa.onmicrosoft.com
```

## Slide 5 — Management Groups: gobernanza a escala

Los Management Groups organizan suscripciones en una jerarquía:

```
Root Management Group (automático)
├── MG-Producción
│   ├── Sub-Produccion-App1
│   └── Sub-Produccion-App2
├── MG-Desarrollo
│   ├── Sub-Desarrollo
│   └── Sub-Testing
└── MG-Sandbox
    └── Sub-Sandbox-Equipo
```

**¿Para qué sirven?**
- Aplicar políticas a todas las suscripciones de un grupo
- Ejemplo: "En MG-Producción, obligar que todos los recursos tengan etiquetas y estén en regiones de la UE"
- Ejemplo: "En MG-Sandbox, limitar los tipos de VM a los más baratos"

**¿Los necesitáis ahora?**
Para un equipo con una o dos suscripciones, no. Los Management Groups son para organizaciones grandes con decenas de suscripciones. Pero es bueno saber que existen para cuando la organización crezca.

## Slide 6 — Subscriptions: la unidad de facturación

Una suscripción es un contrato con Microsoft que define:

**Facturación:** Todos los recursos dentro generan coste en la misma factura. Una factura por suscripción.

**Límites (cuotas):** Cada suscripción tiene cuotas por defecto:
- Máximo de vCPUs por región (~20 por defecto, ampliable)
- Máximo de cuentas de almacenamiento (~250)
- Máximo de Resource Groups (~980)
- Máximo de recursos por RG (~800)

**Aislamiento:** Los recursos de una suscripción no ven los de otra por defecto. Necesitáis VNet Peering o Private Endpoints para comunicar recursos entre suscripciones.

```bash
# Ver tu suscripción activa
az account show --output table

# Listar todas las suscripciones a las que tienes acceso
az account list --output table

# Ver cuotas de una suscripción
az vm list-usage --location westeurope --output table
```

## Slide 7 — Estrategias de organización de suscripciones

**Estrategia 1 — Por entorno:**
```
Sub-Desarrollo    → dev, testing, sandbox
Sub-Staging       → pre-producción, QA
Sub-Producción    → producción real
```
Ventaja: aislamiento de costes y permisos por entorno. El equipo de QA no puede tocar producción accidentalmente.

**Estrategia 2 — Por departamento/equipo:**
```
Sub-Ingeniería    → todos los proyectos de desarrollo
Sub-Data          → pipelines de datos, analytics
Sub-Infraestructura → networking, VMs compartidas
```
Ventaja: cada departamento controla su presupuesto.

**Estrategia 3 — Por proyecto (grandes organizaciones):**
```
Sub-Proyecto-X    → toda la infra del proyecto X
Sub-Proyecto-Y    → toda la infra del proyecto Y
```
Ventaja: coste asignado al 100% a cada proyecto.

**Vuestro caso:** Una suscripción de la organización con Resource Groups individuales por asistente. Más adelante, lo ideal sería al menos separar desarrollo de producción en suscripciones distintas.

## Slide 8 — Resource Groups: las reglas fundamentales

Un Resource Group (RG) es el contenedor lógico del día a día. Las reglas que no podéis saltaros:

**1. Un recurso pertenece a exactamente un RG.**
No puede estar en dos. No puede "compartirse" entre RGs.

**2. Si eliminas un RG, se elimina TODO lo que contiene.**
Sin excepción. Sin confirmación adicional. Sin papelera de reciclaje. Esto es a la vez la forma más limpia de limpiar y la más peligrosa si os equivocáis.

**3. La ubicación del RG es solo metadatos.**
Los recursos dentro pueden estar en cualquier región. El RG en West Europe puede contener una base de datos en East US. La ubicación del RG solo indica dónde se almacenan los metadatos.

**4. Los permisos se heredan.**
Contributor en el RG = Contributor en todos los recursos dentro.

**5. Los recursos se pueden mover entre RGs.**
Pero no todos los tipos lo soportan, y hay limitaciones.

```bash
# Verificar si un tipo de recurso se puede mover
az provider show --namespace Microsoft.Web \
  --query "resourceTypes[?resourceType=='sites'].capabilities[?name=='supportsMoveReasonDetails']"
```

## Slide 9 — Convenciones de nombres: el estándar que deberíais adoptar

Un buen sistema de nombres evita confusiones y facilita la automatización:

**Patrón recomendado:** `<tipo>-<proyecto>-<entorno>-<región>-<instancia>`

| Recurso | Ejemplo | Patrón |
|---------|---------|--------|
| Resource Group | `rg-ventas-prod-we` | rg-{proyecto}-{entorno}-{región} |
| App Service Plan | `plan-ventas-prod-we` | plan-{proyecto}-{entorno}-{región} |
| Web App | `app-ventas-prod-we` | app-{proyecto}-{entorno}-{región} |
| Function App | `func-procesar-prod-we` | func-{función}-{entorno}-{región} |
| Cosmos DB | `cosmos-ventas-prod-we` | cosmos-{proyecto}-{entorno}-{región} |
| Storage Account | `stventasprodwe` | st{proyecto}{entorno}{región}* |
| Key Vault | `kv-ventas-prod-we` | kv-{proyecto}-{entorno}-{región} |

*Storage Accounts no permiten guiones ni mayúsculas (3-24 chars, solo minúsculas y números).

**Abreviaturas estándar:**
- Entornos: `dev`, `stg`, `prod`
- Regiones: `we` (West Europe), `ne` (North Europe), `sc` (Spain Central)

## Slide 10 — Estrategias de agrupación de Resource Groups

**Por entorno + proyecto (la más común):**
```
rg-ventas-dev         → App Service, Functions, Cosmos DB de desarrollo
rg-ventas-stg         → Los mismos recursos, configuración staging
rg-ventas-prod        → Los mismos recursos, configuración producción
```
Ventaja: eliminar `rg-ventas-dev` no afecta a staging ni producción.

**Por ciclo de vida (avanzado):**
```
rg-compartido-prod    → Key Vault, DNS, certificados (no cambian)
rg-ventas-v2-prod     → La versión actual de la app
rg-ventas-v3-beta     → La nueva versión en desarrollo
```
Ventaja: los recursos de larga vida (Key Vault, DNS) no se tocan al desplegar una nueva versión.

**Por tipo de recurso (no recomendado):**
```
rg-bases-datos        → Todas las DB de todos los proyectos
rg-web-apps           → Todas las Web Apps
```
Problema: no podéis eliminar un proyecto sin eliminar recursos de otros.

**Regla de oro:** Agrupa en el mismo RG los recursos que comparten ciclo de vida. Lo que se crea junto, se elimina junto.

## Slide 11 — Crear y gestionar Resource Groups

```bash
# Crear con tags desde el inicio (buena práctica)
az group create \
  --name rg-ventas-dev \
  --location westeurope \
  --tags entorno=dev proyecto=ventas responsable=pedro fecha-creacion=2025-06-15

# Listar todos los RGs con tags
az group list \
  --query "[].{nombre:name, ubicacion:location, entorno:tags.entorno, proyecto:tags.proyecto}" \
  --output table

# Ver detalle de un RG
az group show --name rg-ventas-dev

# Listar recursos dentro con su tipo y coste estimado
az resource list --resource-group rg-ventas-dev \
  --query "[].{nombre:name, tipo:type, sku:sku.name}" \
  --output table

# Exportar la configuración del RG como ARM template
az group export --name rg-ventas-dev > rg-ventas-dev-template.json

# Eliminar RG (y TODO dentro — IRREVERSIBLE)
az group delete --name rg-ventas-dev --yes --no-wait
```

## Slide 12 — Etiquetas (Tags): la base del orden

Las etiquetas son pares clave-valor libres que asignáis a cualquier recurso:

```bash
# Etiquetar un Resource Group
az group update --name rg-ventas-dev \
  --tags entorno=dev proyecto=ventas responsable=pedro centro-coste=IT

# Etiquetar un recurso individual
az resource tag --tags entorno=dev proyecto=ventas \
  --resource-group rg-ventas-dev \
  --name app-ventas-dev \
  --resource-type Microsoft.Web/sites

# Ver tags de un recurso
az resource show --resource-group rg-ventas-dev \
  --name app-ventas-dev \
  --resource-type Microsoft.Web/sites \
  --query tags

# Buscar recursos por tag
az resource list --tag entorno=prod --output table

# Buscar todos los recursos sin tag "responsable"
az resource list \
  --query "[?tags.responsable==null].{nombre:name, tipo:type, rg:resourceGroup}" \
  --output table
```


---

## Slide 13 — Taxonomía de etiquetas recomendada

| Etiqueta | Ejemplo | Obligatoria | Para qué |
|----------|---------|:-----------:|----------|
| `entorno` | dev / stg / prod | ✓ | Saber qué se puede tocar |
| `proyecto` | ventas / curso-azure | ✓ | Filtrar costes por proyecto |
| `responsable` | pedro / equipo-backend | ✓ | Saber a quién preguntar |
| `centro-coste` | IT / formacion / producto | ✓ | Asignación de costes |
| `fecha-creacion` | 2025-06-15 | Recomendada | Detectar recursos huérfanos |
| `fecha-revision` | 2025-09-15 | Recomendada | Revisar si sigue necesario |
| `automatizable` | si / no | Opcional | Apagado fuera de horario |
| `criticidad` | alta / media / baja | Opcional | Priorizar soporte |
| `backup` | diario / semanal / no | Opcional | Política de backup |
| `iac` | bicep / manual | Opcional | Si se gestiona con código |

**Las primeras cuatro deberían ser obligatorias.** Con Azure Policy podéis forzar que un recurso no se cree sin ellas.

## Slide 14 — Herencia de tags desde el Resource Group

Las etiquetas NO se heredan automáticamente del RG a los recursos. Pero podéis configurarlo con Azure Policy:

**Opción 1 — Policy "Inherit a tag from the resource group":**
Asignad la policy built-in "Inherit a tag from the resource group if missing". Si un recurso no tiene la etiqueta `entorno`, la hereda del RG.

**Opción 2 — Script de propagación:**
```bash
#!/bin/bash
# propagar-tags.sh — Copia tags del RG a todos los recursos dentro

RG="rg-ventas-dev"
RG_TAGS=$(az group show --name $RG --query "tags" --output json)

for id in $(az resource list --resource-group $RG --query "[].id" --output tsv); do
  echo "Actualizando tags en: $(basename $id)"
  az resource update --ids $id --set tags="$RG_TAGS" 2>/dev/null
done
```

**Opción 3 — Bicep (al crear):**
```bicep
resource webApp 'Microsoft.Web/sites@2023-12-01' = {
  name: 'app-ventas-dev'
  location: resourceGroup().location
  tags: resourceGroup().tags  // Hereda todos los tags del RG
  properties: { ... }
}
```

## Slide 15 — Azure Policy: gobernanza automática

Azure Policy evalúa automáticamente todos los recursos contra reglas que definís:

**Modos de acción:**
| Modo | Efecto | Cuándo |
|------|--------|--------|
| **Audit** | Solo marca como "no conforme". No bloquea. | Empezar a ver qué incumple |
| **Deny** | Bloquea la creación si no cumple | Cuando las reglas estén claras |
| **Modify** | Modifica el recurso para que cumpla | Auto-corregir (añadir tags, etc.) |
| **DeployIfNotExists** | Despliega recursos adicionales | Añadir diagnósticos automáticamente |
| **Append** | Añade propiedades | Forzar configuración |

**Consejo:** Empezad SIEMPRE con Audit. Cuando veáis que las reglas son correctas y no hay falsos positivos, pasad las críticas a Deny.

## Slide 16 — Políticas útiles para vuestro equipo

**1. Obligar etiquetas al crear recursos:**
Policy built-in: "Require a tag and its value on resources"
```
Etiqueta: entorno
Valores permitidos: dev, stg, prod
Efecto: Deny
```

**2. Restringir regiones permitidas:**
Policy built-in: "Allowed locations"
```
Regiones: westeurope, northeurope, francecentral, spaincentral
Efecto: Deny
```

**3. Prohibir VMs grandes en desarrollo:**
Policy built-in: "Allowed virtual machine size SKUs"
```
SKUs permitidos en dev: Standard_B1s, Standard_B2s
Efecto: Deny (solo en suscripción de desarrollo)
```

**4. Auditar recursos sin diagnósticos:**
Policy built-in: "Audit diagnostic setting"
```
Efecto: Audit (avisa pero no bloquea)
```

**5. Forzar HTTPS en App Service:**
Policy built-in: "App Service apps should only be accessible over HTTPS"
```
Efecto: Deny o Audit
```

## Slide 17 — Asignar una policy desde CLI

```bash
# Listar policies built-in disponibles
az policy definition list \
  --query "[?policyType=='BuiltIn'].{nombre:displayName, id:name}" \
  --output table | head -30

# Asignar policy de etiqueta obligatoria al RG
az policy assignment create \
  --name "obligar-tag-entorno" \
  --display-name "Obligar etiqueta entorno" \
  --policy "require-tag" \
  --params '{"tagName": {"value": "entorno"}}' \
  --scope "/subscriptions/<sub-id>/resourceGroups/rg-ventas-prod" \
  --enforcement-mode Default

# Ver compliance (después de unas horas)
az policy state list \
  --resource-group rg-ventas-prod \
  --query "[?complianceState=='NonCompliant'].{recurso:resourceId, policy:policyDefinitionName}" \
  --output table
```

**Nota:** Las policies tardan hasta 30 minutos en evaluarse la primera vez. Las nuevas creaciones se evalúan en tiempo real si la policy usa modo Deny.

## Slide 18 — RBAC: Role-Based Access Control

RBAC define quién puede hacer qué en Azure:

**Tres conceptos clave:**
1. **Security Principal:** Quién (usuario, grupo, service principal, managed identity)
2. **Role:** Qué puede hacer (Owner, Contributor, Reader, roles custom)
3. **Scope:** Dónde aplica (Management Group, Subscription, RG, Resource)

```
          ┌─ Owner (control total + gestión de permisos)
Roles ────┼─ Contributor (todo menos gestionar permisos)
          ├─ Reader (solo lectura)
          └─ Roles específicos (Website Contributor, SQL DB Contributor, etc.)

          ┌─ Management Group (máximo alcance)
Scope ────┼─ Subscription
          ├─ Resource Group
          └─ Resource (mínimo alcance)
```

Los permisos se heredan hacia abajo. Contributor en la suscripción = Contributor en TODOS los RGs de esa suscripción.


---

## Slide 19 — RBAC: principio de mínimo privilegio

**La regla de oro:** Asigna el rol más restrictivo que permita hacer el trabajo.

| Necesita | Rol correcto | NO asignéis |
|----------|:------------:|:-----------:|
| Ver recursos (dashboards, reportes) | Reader | Contributor |
| Crear y gestionar recursos | Contributor | Owner |
| Gestionar permisos de otros | Owner | - |
| Solo desplegar código | Website Contributor | Contributor |
| Solo leer datos de Cosmos | Cosmos DB Account Reader | Contributor |
| Ejecutar pipelines | DevOps específico | Owner |

**¿Por qué importa?**
- Un usuario con Owner en la suscripción puede eliminar todos los recursos de producción
- Un usuario con Contributor en un RG solo puede afectar a ese RG
- Un usuario con Reader no puede romper nada

## Slide 20 — RBAC en la práctica

```bash

  --resource-group rg-curso-azure-pedro \

```

## Slide 21 — Roles custom: cuando los built-in no bastan

Si ningún rol predefinido encaja, podéis crear uno custom:

```json
{
  "Name": "App Deployer",
  "Description": "Puede desplegar código pero no cambiar configuración",
  "Actions": [
    "Microsoft.Web/sites/publish/Action",
    "Microsoft.Web/sites/restart/Action",
    "Microsoft.Web/sites/Read",
    "Microsoft.Web/sites/config/Read"
  ],
  "NotActions": [
    "Microsoft.Web/sites/Delete",
    "Microsoft.Web/sites/config/Write"
  ],
  "AssignableScopes": [
    "/subscriptions/<sub-id>"
  ]
}
```

```bash
az role definition create --role-definition @rol-deployer.json
az role assignment create --assignee cicd@empresa.com --role "App Deployer" --resource-group rg-ventas-prod
```

**Caso de uso real:** Tenéis un service principal que solo debe desplegar código en producción — no cambiar la configuración ni eliminar recursos. Un rol custom es la solución.

## Slide 24 — Cost Analysis: lectura de gráficos

Cómo interpretar el dashboard de Cost Analysis:

**Gráfico de barras diario:**
Cada barra es un día. Si una barra sube de repente, algo cambió: un recurso nuevo, un cambio de tier, o una VM que se quedó encendida.

**Forecast (previsión):**
Azure extrapola el gasto del mes basándose en los días anteriores. Si el forecast supera el presupuesto, actuad antes de que termine el mes.

**Desglose por servicio:**
Muestra qué porcentaje del coste es App Service, Cosmos DB, Storage, etc. Si un servicio domina, ahí es donde debéis optimizar.

**Desglose por tag:**
Si habéis etiquetado bien, podéis ver el coste exacto de cada proyecto, cada entorno, cada equipo. Sin tags, este desglose no funciona — otro motivo para etiquetar todo.

**Amortized cost vs Actual cost:**
- Actual: lo que pagaréis este mes
- Amortized: coste real distribuido (si tenéis reservas, el pago anual se divide entre 12 meses)

## Slide 25 — Azure Advisor: recomendaciones automáticas

Azure Advisor analiza vuestros recursos y sugiere optimizaciones en 5 categorías:

**Cost (Coste):**
- "Esta VM lleva 30 días con 5% CPU — bájala de tamaño o elimínala"
- "Si reserváis esta VM por 1 año, ahorraréis 40%"
- "Este disco no está adjunto a ninguna VM — podéis eliminarlo"

**Security (Seguridad):**
- "Este Storage Account permite acceso público — restringidlo"
- "Esta App Service no fuerza HTTPS"

**Reliability (Fiabilidad):**
- "Esta base de datos no tiene backup configurado"
- "Este App Service Plan tiene una sola instancia — sin redundancia"

**Performance (Rendimiento):**
- "Esta base de datos está al 90% de DTU — subidla de tier"

**Operational Excellence:**
- "Este recurso no tiene diagnósticos habilitados"

```bash
# Ver recomendaciones de coste
az advisor recommendation list --category cost --output table
```

**Revisad Advisor una vez por semana.** Cinco minutos que pueden ahorrar cientos de euros al mes.

## Slide 26 — Trucos para no llevarse sustos en la factura

**1. Calculadora de precios ANTES de crear:**
https://azure.microsoft.com/pricing/calculator/
Simulad el coste mensual. Compartid la estimación con el equipo antes de crear el recurso.

**2. Tiers gratuitos para desarrollo:**
App Service F1, Cosmos DB free tier, Functions consumption. Si no necesitáis features de producción, no paguéis por ellas.

**3. Apagad lo que no uséis:**
VMs de desarrollo encendidas 24/7 = dinero quemado en las 128 horas del fin de semana mensual. App Service y Functions en consumo no tienen este problema.

**4. Alertas de presupuesto en TODO:**
Cada RG de desarrollo y cada suscripción debería tener un presupuesto con alertas. Es una red de seguridad de 5 minutos de configuración.

**5. Reservas para producción estable:**
Si un recurso va a existir más de 12 meses, la reserva ahorra un 30-40%. Evaluadlo para App Service Plans y bases de datos.

**6. Eliminad recursos huérfanos:**
Discos no adjuntos, IPs públicas sin asignar, RGs vacíos. Se acumulan silenciosamente.

## Slide 27 — Script: detector de recursos huérfanos

```bash
#!/bin/bash
# huerfanos.sh — Detecta recursos que probablemente sobran

echo "=== DETECTOR DE RECURSOS HUÉRFANOS ==="
echo ""

echo "--- Discos no adjuntos a ninguna VM ---"
az disk list \
  --query "[?managedBy==null].{nombre:name, tamaño_gb:diskSizeGb, rg:resourceGroup}" \
  --output table

echo ""
echo "--- IPs públicas sin asignar ---"
az network public-ip list \
  --query "[?ipConfiguration==null].{nombre:name, ip:ipAddress, rg:resourceGroup}" \
  --output table

echo ""
echo "--- Network Security Groups sin asociar ---"
az network nsg list \
  --query "[?subnets==null && networkInterfaces==null].{nombre:name, rg:resourceGroup}" \
  --output table

echo ""
echo "--- Recursos sin tag 'proyecto' ---"
az resource list \
  --query "[?tags.proyecto==null].{nombre:name, tipo:type, rg:resourceGroup}" \
  --output table

echo ""
echo "--- Resource Groups vacíos ---"
for rg in $(az group list --query "[].name" -o tsv); do
  count=$(az resource list --resource-group $rg --query "length(@)")
  if [ "$count" -eq 0 ]; then
    echo "RG vacío: $rg"
  fi
done
```

Ejecutad esto una vez al mes. Os sorprenderá lo que encontráis.

## Slide 28 — Resource Locks: proteger lo que importa

Los bloqueos protegen recursos contra eliminación o modificación accidental:

**Tipos:**
| Lock | Permite modificar | Permite eliminar |
|------|:-----------------:|:----------------:|
| **CanNotDelete** | ✓ | ✗ |
| **ReadOnly** | ✗ | ✗ |

```bash
# Bloquear un RG contra eliminación
az lock create \
  --name "proteccion-produccion" \
  --resource-group rg-ventas-prod \
  --lock-type CanNotDelete \
  --notes "Protección contra eliminación accidental — contactar Pedro"

# Bloquear un recurso específico (Key Vault, por ejemplo)
az lock create \
  --name "proteger-keyvault" \
  --resource-group rg-ventas-prod \
  --resource-name kv-ventas-prod \
  --resource-type Microsoft.KeyVault/vaults \
  --lock-type CanNotDelete

# Ver bloqueos
az lock list --resource-group rg-ventas-prod --output table

# Eliminar bloqueo (requiere Owner)
az lock delete --name "proteccion-produccion" --resource-group rg-ventas-prod
```

**Cuándo usarlos:**
- ✓ Siempre en Resource Groups de producción
- ✓ En recursos compartidos (Key Vault, DNS zones, bases de datos)
- ✗ Nunca en entornos de desarrollo (molestan más de lo que protegen)

## Slide 30 — EA vs MCA vs Pay-as-you-go: tipos de contrato

El tipo de contrato que tenga vuestra empresa con Microsoft determina precios, descuentos disponibles y gestión:


## Slide 34 — Azure Deployment Stacks: el nuevo estándar

**Contexto importante:** Azure Blueprints está en **deprecación** (discontinuado 2026-2027). El reemplazo es **Azure Deployment Stacks** (GA desde 2024, estándar en 2026).

```bash
# Un deployment stack gestiona el LIFECYCLE COMPLETO de un set de recursos
az stack group create \
  --name stack-ventas-prod \
  --resource-group rg-ventas-prod \
  --template-file main.bicep \
  --parameters @params.prod.json \
  --action-on-unmanage deleteAll \
  --deny-settings-mode denyDelete
```

**Diferencia con un deployment normal:**

| | Deployment normal | Deployment Stack |
|---|---|---|
| Recursos se crean | ✓ | ✓ |
| Recursos eliminados del template | Persisten | Se eliminan automáticamente |
| Protección contra delete manual | No | Sí (denySettings) |
| Tracking | Solo histórico | Stack posee los recursos |

**Para qué:** gobernanza de infraestructura donde el equipo A declara qué recursos existen y el equipo B no puede modificarlos. Se verá a fondo en **M8**, pero conviene que sepáis que existe porque reemplaza a Blueprints que estaba en todos los temarios antes de 2024.

## Slide 35 — PIM: Privileged Identity Management

**RBAC + PIM = el modelo real de seguridad en empresas**. PIM (parte de Entra ID P2) convierte roles de "permanentes" a "just-in-time":

```
Flujo PIM:
1. Admin asigna rol ELEGIBLE (no activo) a María:
   - "Puedes activar el rol Contributor cuando lo necesites"
2. María trabaja normal sin permisos (mínimo privilegio real)
3. Cuando María necesita el rol:
   - Entra a portal PIM
   - "Activate role Contributor"
   - Especifica justificación + duración (ej: 2 horas)
   - Puede requerir aprobación de un manager
   - Puede requerir MFA
4. Activa el rol durante 2h, luego expira automáticamente
5. Audit log completo: quién activó qué y cuándo
```

**Beneficios:**
- Reduce superficie de ataque (roles activos solo cuando se usan)
- Audit completo para compliance
- Obliga a justificar acciones sensibles
- MFA + aprobación para roles críticos (Owner, User Access Admin)

**Requiere:** Entra ID Premium P2 o Microsoft Entra Suite (~€9-12/usuario/mes).

## Slide 36 — Resource Providers: qué registrar en una suscripción nueva

Cada servicio de Azure vive en un "Resource Provider" (namespace). Una suscripción recién creada tiene muchos **no registrados** — el primer deploy de ese servicio los registra, pero a veces queréis adelantar:

```bash
# Ver estado de todos los providers
az provider list -o table

# Registrar providers típicos para desarrollo Azure-first
for p in \
  Microsoft.Web \
  Microsoft.Storage \
  Microsoft.Compute \
  Microsoft.Network \
  Microsoft.DocumentDB \
  Microsoft.KeyVault \
  Microsoft.ServiceBus \
  Microsoft.Insights \
  Microsoft.OperationalInsights \
  Microsoft.Sql \
  Microsoft.ContainerRegistry \
  Microsoft.ContainerInstance \
  Microsoft.App \
  Microsoft.ManagedIdentity; do
  az provider register --namespace $p
done

# Verificar uno concreto
az provider show -n Microsoft.Web --query registrationState
```

**Para sub nueva:** ejecutad este script al crear la suscripción. Os ahorra errores del tipo "The subscription is not registered to use namespace 'Microsoft.X'" cuando intentéis desplegar algo nuevo.

## Slide 40 — Showback vs chargeback: FinOps en tu empresa

Cuando una empresa crece, contabilizar el coste cloud por equipo se vuelve crítico:

```
Showback (reporte):
├── "Tu equipo gastó €3.400 en Azure este mes"
├── Visibilidad sin impacto financiero
├── Primera etapa de madurez FinOps
└── Se hace con tags (project, team, costCenter) + Cost Analysis

Chargeback (facturación interna):
├── "Tu equipo es facturado €3.400 internamente"
├── Coste se descuenta del budget del equipo
├── Responsabilidad real del gasto
└── Requiere madurez FinOps + contabilidad que lo soporte
```

**Implementación práctica:**

```bash
# 1. Taxonomía de tags obligatoria (Azure Policy lo enforza):
#    team=ventas, project=facturas, costCenter=CC-1234, environment=prod

# 2. Export de costes diario a Storage (slide anterior)

# 3. Power BI dashboard con filtros por tag:
#    Total €, por equipo, por proyecto, por entorno, tendencia 90 días

# 4. Meeting FinOps mensual:
#    - Review del mes anterior
#    - Anomalías (subidas >20%)
#    - Acciones: optimizar, reservar, apagar
```

**Clave:** sin tags bien puestos, no hay FinOps. Por eso **S1.3 slide 12-13 (tags)** es tan importante.

## Slide 43 — Cierre del submódulo

La organización en Azure no es glamurosa. Nadie se levanta por la mañana con ganas de configurar policies y presupuestos. Pero es lo que separa un equipo que controla su infraestructura de uno que reza para que la factura no se dispare y que nadie elimine producción por accidente.

Lo esencial:
- Resource Groups como unidad de gestión — lo que se crea junto, se elimina junto
- Etiquetas en todo — sin ellas, Cost Management es inútil
- Presupuestos y alertas — la red de seguridad que todos necesitan
- RBAC con mínimo privilegio — cada persona tiene exactamente los permisos que necesita
- Locks en producción — porque los accidentes pasan

Siguiente submódulo: preparamos el entorno de trabajo — VS Code, SDK, extensiones y todo lo necesario para empezar a escribir código.

## Slide 4 — Convenciones y nombres

Usaremos estos nombres durante TODA la práctica. Reemplazad `<tu-nombre>` por el vuestro (minúsculas, sin espacios, sin eñe):

```
Resource Group:      rg-curso-azure-<tu-nombre>
App Service Plan:    plan-curso-<tu-nombre>
Web App:             app-curso-<tu-nombre>
Directorio local:    ~/curso-azure/modulo-01/hello-world
Región Azure:        westeurope (o la que use vuestra empresa)
```

**Ejemplos válidos:**
- `pedro` → `rg-curso-azure-pedro`, `app-curso-pedro`
- `maria-g` → `rg-curso-azure-maria-g`, `app-curso-maria-g`

**Ejemplos inválidos:**
- ❌ `Pedro Martínez` (espacios, tilde)
- ❌ `MariáGarcía` (tildes, mayúsculas en nombre DNS)
- ❌ `peña` (eñe no válida en DNS)

**Consideraciones del naming en Azure:**
- El nombre de la Web App es **globalmente único** en todo Azure
- Si `app-curso-pedro` ya existe (otro Pedro), usad `app-curso-pedro-23` o similar
- Máximo 60 caracteres, solo letras/números/guiones

## Slide 5 — Mental model antes de empezar

Antes de teclear comandos, aseguraos de entender QUÉ estáis creando:

```
Jerarquía de lo que montaréis:

  Suscripción Azure (ya existe, os la han dado)
          │
          ▼
  Resource Group "rg-curso-azure-<tu-nombre>"  (contenedor lógico)
          │
          ├── App Service Plan "plan-curso-<tu-nombre>" (la "VM" que cuesta)
          │        │
          │        └── Web App "app-curso-<tu-nombre>" (el hosting de tu código)
          │               │
          │               └── https://app-curso-<tu-nombre>.azurewebsites.net
          │                   (la URL pública final)
          │
          └── (opcional) Storage Account, App Insights, etc.
```

**Relaciones clave:**
- El **Resource Group** no cuesta nada (es solo un contenedor)
- El **App Service Plan** es lo que se factura (incluso vacío, si no es F1)
- Múltiples **Web Apps** pueden compartir un mismo **Plan**
- Si borráis el Resource Group, se borra TODO lo que contiene (tier "nuclear" de limpieza)

**Regla mental:** si no entendéis por qué algo es un recurso vs una configuración, preguntad. No memoricéis comandos a ciegas.

## Slide 8 — Pre-flight: login con Azure CLI (casos reales)

El login de Azure CLI tiene más variantes de las que parece. Elegid la que aplica a vuestro caso:

**Caso A — Máquina personal con navegador (lo más habitual):**
```bash
az login
# Abre navegador automáticamente
# Autenticáis con vuestra cuenta Entra ID (corporativa)
# MFA si procede
# Vuelve al terminal: lista de suscripciones disponibles
```

**Caso B — Servidor sin navegador (WSL remoto, SSH, Docker):**
```bash
az login --use-device-code
# Devuelve: "To sign in, use a web browser to open
#           https://microsoft.com/devicelogin
#           and enter the code ABC123XYZ"
# Abrís esa URL en OTRA máquina (portátil)
# Introducís el código → autenticáis
# El terminal original completa el login
```

**Caso C — Service Principal (CI/CD, producción):**
```bash
az login --service-principal \
  --username <app-id> \
  --password <client-secret> \
  --tenant <tenant-id>
# NO uséis esto para la práctica manual; es para pipelines
```

**Caso D — Managed Identity (si ejecutáis desde una VM de Azure):**
```bash
az login --identity
# Usa la MI asignada a la VM
# No veréis esto hasta M6
```

**Verificación común:**
```bash
az account show --output table
# Debe devolver vuestra cuenta y suscripción activas
```

## Slide 9 — Pre-flight: múltiples tenants y suscripciones

Muchos entornos corporativos tienen varias suscripciones. Escenarios reales:

```bash
# Ver TODOS los tenants a los que podéis acceder
az account tenant list --output table
# TenantId                              DisplayName
# ------------------------------------  ------------------
# aaa-aaa-aaa-aaa                       MiEmpresa
# bbb-bbb-bbb-bbb                       ClienteX (guest)

# Ver TODAS las suscripciones disponibles
az account list --output table
# Name                      IsDefault    State     TenantId
# ------------------------ -----------  --------  -------------
# Curso-Dev                 True         Enabled   aaa-aaa-aaa
# Produccion                False        Enabled   aaa-aaa-aaa
# Cliente-X-Sandbox         False        Enabled   bbb-bbb-bbb

# Cambiar la activa
az account set --subscription "Curso-Dev"

# O por ID (más fiable si hay nombres duplicados)
az account set --subscription "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"

# Forzar re-login contra un tenant específico
az login --tenant bbb-bbb-bbb-bbb

# Ver el tenant activo actual
az account show --query tenantId -o tsv
```

**Gotcha real:** podéis tener `az account show` apuntando a la suscripción correcta PERO el tenant incorrecto si sois guest en varios. Verificad siempre `tenantId` + `name`.

**Guest accounts:** si os invitan a un tenant externo, `az login --tenant <external-tenant>` es obligatorio antes de `az account set`.

## Slide 10 — Pre-flight: proxy corporativo y firewalls

Si estáis detrás de un proxy corporativo (muy común en empresas grandes), Azure CLI puede fallar silenciosamente. Debugging:

```bash
# 1. ¿Tengo proxy configurado?
echo $HTTPS_PROXY $HTTP_PROXY
# Si ambos están vacíos y tu red lo requiere → aquí está el problema

# 2. Configurar proxy (Linux/Mac):
export HTTPS_PROXY=http://proxy.miempresa.com:8080
export HTTP_PROXY=http://proxy.miempresa.com:8080
export NO_PROXY=localhost,127.0.0.1,.miempresa.com

# 2. Windows PowerShell:
$env:HTTPS_PROXY = "http://proxy.miempresa.com:8080"
$env:HTTP_PROXY = "http://proxy.miempresa.com:8080"

# 3. Certificado corporativo (empresas que inspeccionan SSL)
export REQUESTS_CA_BUNDLE=/path/to/corp-ca-bundle.pem
export AZURE_CLI_DISABLE_CONNECTION_VERIFICATION=0  # NO bypasear SSL

# 4. Persistente: añadir al .bashrc / .zshrc / $PROFILE
```

**URLs que deben estar en whitelist:**
```
*.azure.com
*.microsoftonline.com
login.microsoftonline.com
management.azure.com
*.azurewebsites.net
*.scm.azurewebsites.net       ← Kudu, muy importante para deploy
*.vault.azure.net              ← Key Vault (lo veréis en M6)
*.blob.core.windows.net        ← Storage
```

**Síntoma típico:** `az login` funciona pero `az webapp deploy` falla con timeout → el puerto 443 del SCM está bloqueado. Hablad con networking de vuestra empresa.

## Slide 15 — Paso 1.3: Verificar tu rol

¿Tenéis permisos de Contributor en el RG? Este comando os lo confirma:

```bash
az role assignment list \
  --resource-group rg-curso-azure-<tu-nombre> \
  --assignee <tu-email> \
  --query "[].{Role:roleDefinitionName, Scope:scope}" \
  --output table

# Output esperado:
# Role          Scope
# ------------  ----------------------------------------------------
# Contributor   /subscriptions/xxx/resourceGroups/rg-curso-azure-...
```

**Roles típicos y qué permiten:**
- **Owner:** todo + gestionar accesos
- **Contributor:** crear, modificar, eliminar recursos (lo que necesitáis)
- **Reader:** solo lectura (NO podéis hacer la práctica)
- **User Access Administrator:** gestionar accesos, no recursos

**Si solo tenéis Reader**, no podréis crear la Web App. Pedid un upgrade temporal a Contributor.

**Truco útil** — alias shell para tecleo rápido:
```bash
# Añadir a vuestro .bashrc / .zshrc
export RG=rg-curso-azure-<tu-nombre>
export APP=app-curso-<tu-nombre>
export PLAN=plan-curso-<tu-nombre>
export LOC=westeurope
```

Desde aquí podéis usar `$RG`, `$APP`, etc. en vez de repetir los nombres. Ahorra errores.

## Slide 17 — Planning: ¿qué región elegir?

La región afecta a latencia, precio, features disponibles y residencia de datos:

```
Europa (para usuarios en España):

┌─────────────────────────┬──────────┬──────────────────────────────────┐
│      Región             │ Latencia │ Notas                            │
├─────────────────────────┼──────────┼──────────────────────────────────┤
│ Spain Central           │  ~10 ms  │ GA 2024 · DC nuevo · precios     │
│                         │          │ ligeramente más altos            │
│ West Europe (Amsterdam) │  ~25 ms  │ ⭐ Madurez · features primero     │
│                         │          │ Feature parity casi total        │
│ North Europe (Dublin)   │  ~40 ms  │ Segunda opción habitual          │
│ France Central          │  ~30 ms  │ Compliance FR, precios medios    │
│ Germany West Central    │  ~40 ms  │ Compliance DE                    │
│ Italy North             │  ~35 ms  │ Más nuevo · algunos GAPs         │
│ UK South                │  ~45 ms  │ GBP pricing, post-Brexit         │
│ Sweden Central          │  ~50 ms  │ Green energy · sostenibilidad    │
│ Switzerland North       │  ~40 ms  │ Compliance CH, más caro          │
└─────────────────────────┴──────────┴──────────────────────────────────┘
```

**Para esta práctica: `westeurope`** (o `spaincentral` si el formador lo indica).

**Criterios reales de selección en proyectos:**
1. **Usuarios**: ¿dónde están los usuarios? (proximidad = baja latencia)
2. **Compliance**: ¿hay requisitos de residencia de datos? (RGPD, sectores regulados)
3. **Feature set**: ¿el servicio que necesitamos está en esa región?

app.MapGet("/", () => Results.Json(new
{

## Slide 30 — Paso 3.6: appsettings.json — el corazón de la configuración

Abrid `appsettings.json`:

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*"
}
```

**Jerarquía de configuración en .NET (orden de precedencia, de menor a mayor):**

```
┌─ 1. appsettings.json (base)
├─ 2. appsettings.{Environment}.json     ← Development, Staging, Production
├─ 3. User Secrets                        ← solo en desarrollo (dotnet user-secrets)
├─ 4. Environment Variables               ← TypiCase ASPNETCORE_<Section>__<Key>
├─ 5. Command-line arguments              ← dotnet run --MyKey=value
└─ 6. (En Azure) App Settings del Portal  ← inyectadas como env vars
```

**En Azure — App Settings se inyectan como variables de entorno con formato especial:**
```
Portal (App Settings):        En código (IConfiguration):
──────────────────────        ──────────────────────────
MyKey                          builder.Configuration["MyKey"]
ConnectionStrings__Default     builder.Configuration.GetConnectionString("Default")
Nested__Key                    builder.Configuration["Nested:Key"]
```

**Importante:** en Azure, el doble underscore `__` es el separador de sección (porque `:` no es válido en nombres de variables de entorno).

**Leer configuración en código:**
```csharp
var value = app.Configuration["AllowedHosts"];
var logLevel = app.Configuration["Logging:LogLevel:Default"];
```

Esto lo usaréis en el **Reto 1** más adelante.

│     + web.config (si es IIS) o Dockerfile (si es container)   │
│     Tamaño típico: 5-50 MB                                    │
└────────────────────────┬──────────────────────────────────────┘
                         │ zip + upload al SCM de App Service
                         ▼
┌───────────────────────────────────────────────────────────────┐
│  4. DEPLOYED APP                                              │
│     /home/site/wwwroot/ en el App Service                     │
│     + Runtime .NET 8 gestionado por Azure                     │
│     + Process supervisado por Kudu                            │
└───────────────────────────────────────────────────────────────┘
```

**Diferencias clave:**

| | Build | Publish |
|---|---|---|
| Destino | `bin/` | `./publish/` (o donde digáis) |
| Config | Debug por defecto | Release por defecto para deploy |
| Optimizaciones | No | Sí (JIT info, trimming opcional) |
| Dependencias | Referencias a NuGet cache | **Copias físicas** de todas las DLLs |
| Se usa para | `dotnet run` local | Deploy a servidor |

**Regla simple:** `dotnet build` para dev local, `dotnet publish` para deploy. En los próximos slides los veréis en acción.

## Slide 40 — Paso 4.7: Hot reload y iteración rápida

`dotnet watch` es un superpoder de productividad en desarrollo:

```bash
# En lugar de dotnet run (requiere reinicio manual)
dotnet watch run

# Salida esperada:
# watch : File changed: /Users/pedro/Program.cs
# watch : Hot reload of changes succeeded.
# watch : Restarting
```

**Qué hace:**
1. Ejecuta `dotnet run`
2. Observa cambios en `.cs`, `.csproj`, `.json`
3. Al detectar cambio:
   - Si es "pequeño" (método interno) → **Hot Reload** (mantiene estado)
   - Si es "grande" (nuevo endpoint, cambio de Program.cs estructural) → **Restart**

**Ejemplos de cambios que hacen hot reload sin reiniciar:**
- Cambiar el cuerpo de un método
- Cambiar un string literal
- Añadir nuevo endpoint simple

**Ejemplos que fuerzan restart:**
- Cambios en `Program.cs` fuera de un método
- Cambios en `appsettings.json`
- Añadir nuevos paquetes NuGet
- Cambios en `.csproj`

**Flags útiles:**
```bash
# Desactivar hot reload (solo restart al detectar cambio)
dotnet watch run --no-hot-reload

# Browser refresh automático
dotnet watch run --browser

# Monitorizar archivos específicos
dotnet watch --project ./HelloWorldCurso.csproj run
```

**Comparativa mental:**

| Modo | Caso de uso |
|---|---|
| `dotnet run` | Ejecución one-shot |
| `dotnet watch run` | Desarrollo activo, cambios frecuentes ⭐ |
| F5 (debugger VS Code) | Necesito breakpoints, inspeccionar estado |
| `dotnet test --watch` | TDD con tests |

**Regla del pulgar:** siempre `dotnet watch run` en desarrollo activo. Cambiáis código → recarga → probáis en browser / REST Client.

## Slide 41 — Paso 4.8: confiar el certificado HTTPS local

Si `https://localhost:5001` da error de certificado, arreglar una sola vez:

```bash
# Ver estado actual
dotnet dev-certs https --check --verbose

# Generar certificado si no existe
dotnet dev-certs https

# Confiar el certificado (Linux necesita extensión manual)
dotnet dev-certs https --trust

# Linux específico (Ubuntu)
dotnet dev-certs https --export-path ~/aspnet-cert.pfx --format PFX
# Luego confiad el .pfx en el keychain del sistema

# Reset completo si algo falla
dotnet dev-certs https --clean
dotnet dev-certs https
dotnet dev-certs https --trust
```

**Tras hacer trust:**
- Chrome/Edge/Firefox confían en el certificado de localhost
- No veréis "Your connection is not private"
- curl funciona sin `-k`

**En Azure esto NO aplica:** las apps en Azure reciben un certificado real de `*.azurewebsites.net` gestionado por Microsoft. El dev cert es solo para local.

**En dev containers o WSL:** a veces hay que regenerar el cert cuando saltáis entre entornos. Si el flow se rompe, `dotnet dev-certs https --clean && dotnet dev-certs https --trust`.

## Slide 43 — Paso 5.1a: Zip Deploy vs Git Deploy vs Run From Package

Los 3 "sabores" de entrega física de código en App Service:

**1. Zip Deploy (el más común hoy):**
```bash
# Empaquetas la publish como zip
# Subes a https://<app>.scm.azurewebsites.net/api/zipdeploy
# Kudu extrae en /home/site/wwwroot/
# App se reinicia automáticamente
```
- ⚡ Rápido (la build la hacéis local)
- Deploy "mutable" → se sobrescribe wwwroot
- Gotcha: si hay archivos del deploy anterior que ya no están en el zip → **quedan en el filesystem**
- Solución: `--clean true` o la nueva flag `SCM_DO_BUILD_DURING_DEPLOYMENT`

**2. Git Deploy:**
```bash
git remote add azure https://<user>@<app>.scm.azurewebsites.net/<app>.git
git push azure main
# Kudu hace build EN EL SERVER (lento) + deploy
```
- 🐌 Más lento porque build se ejecuta en App Service
- Útil si no podéis build localmente (sin SDK)
- Desuso en favor de CI/CD moderno

**3. Run From Package (producción real):**
```bash
# Subes el zip a Storage o mismo servidor
# Configuras: WEBSITE_RUN_FROM_PACKAGE = <URL del zip>
# App Service monta el zip como filesystem read-only
```
- ⚡ **Deploy atómico** (todo-o-nada)
- Filesystem read-only (más seguro)
- Fácil rollback: cambia la URL del paquete
- Lo veréis en M2 con más detalle

**Para esta práctica: Zip Deploy (método 1)** porque es lo que VS Code y `az webapp deploy` hacen por defecto.

## Slide 48 — Paso 5.4: Qué ocurre durante el deploy (internals)

Conocer el flujo interno os ayuda a debuggear:

```
Vuestra máquina                 Azure (Kudu + App Service)
──────────────                  ──────────────────────────

deploy.zip
    │
    │ HTTPS POST
    ▼
┌──────────────────────┐    
│ Kudu SCM endpoint    │    https://app-curso-<tu-nombre>.scm.azurewebsites.net
│ /api/zipdeploy       │
└──────────────────────┘
    │
    ▼
1. Recibe el ZIP en /tmp
2. Valida autenticación
3. Extrae a /home/site/wwwroot
4. Detecta runtime (dotnet:8)
5. Ejecuta script post-deploy (si existe)
6. Reinicia el App Service worker
    │
    ▼
┌──────────────────────┐
│ Kestrel arranca el   │
│ hello-world.dll      │
│ en el worker process │
└──────────────────────┘
    │
    ▼
App responde en puerto interno → HTTPS outer layer
    │
    ▼
https://app-curso-<tu-nombre>.azurewebsites.net está "Running"
```

**Tiempo típico:**
- Upload ZIP: 5-30 seg (según tamaño y red)
- Extract + detect: 10-20 seg
- Restart + warmup: 30-60 seg
- **Total: 45-110 segundos** desde que ejecutáis el comando

**Si el deploy tarda >3 minutos, algo va mal.** Logs en Kudu muestran por qué.

## Slide 59 — Paso 7.6: Seguridad por defecto — lo que deberíais activar YA

Con la app desplegada, hay security defaults que Azure NO activa por vosotros. Configuradlos antes de abrir la app al mundo:

```bash
# 1. HTTPS only (rechaza HTTP → redirige a HTTPS)
az webapp update \
  -n app-curso-<tu-nombre> \
  -g rg-curso-azure-<tu-nombre> \
  --https-only true

# 2. Minimum TLS version 1.2 (1.0/1.1 son inseguras)
az webapp config set \
  -n app-curso-<tu-nombre> \
  -g rg-curso-azure-<tu-nombre> \
  --min-tls-version 1.2

# 3. Desactivar FTP/FTPS de deploy (deploy solo por HTTPS)
az webapp config set \
  -n app-curso-<tu-nombre> \
  -g rg-curso-azure-<tu-nombre> \
  --ftps-state Disabled

# 4. Desactivar Basic Auth en SCM (Kudu) — usar OAuth
az resource update --resource-type Microsoft.Web/sites/basicPublishingCredentialsPolicies \
  --name scm --parent "sites/app-curso-<tu-nombre>" \
  -g rg-curso-azure-<tu-nombre> \
  --set properties.allow=false

# 5. Desactivar Basic Auth en FTP
az resource update --resource-type Microsoft.Web/sites/basicPublishingCredentialsPolicies \
  --name ftp --parent "sites/app-curso-<tu-nombre>" \
  -g rg-curso-azure-<tu-nombre> \
  --set properties.allow=false

# 6. Ver estado de seguridad completo
az webapp config show \
  -n app-curso-<tu-nombre> \
  -g rg-curso-azure-<tu-nombre> \
  --query "{httpsOnly:httpsOnly, minTls:minTlsVersion, ftpsState:ftpsState, http20Enabled:http20Enabled}" \
  --output table
```

**Gotcha del paso 4:** si desactiváis Basic Auth en SCM, algunos métodos de deploy dejan de funcionar (VS Code puede seguir OK con token OAuth). Si rompéis el deploy, reactivadlo temporal y configurad Managed Identity + OIDC (M8).

**Checklist mínimo security:**
- [x] HTTPS only = true
- [x] Min TLS = 1.2 (idealmente 1.3)
- [x] FTP state = Disabled (o FtpsOnly si necesitáis FTP)
- [x] No secretos en App Settings (usar Key Vault refs)
- [x] Managed Identity asignada (lo veremos en M6)

## Slide 61 — Troubleshooting: errores durante el deploy

Los errores más comunes en esta práctica y cómo resolverlos:

```
❌ ERROR: "No such app exists in resource group"
CAUSA: Typo en nombre o RG incorrecto
SOLUCIÓN:
  az webapp list -g <rg> --query "[].name" -o tsv
  → Verificad que el nombre exacto coincide

❌ ERROR: "401 Unauthorized" durante az webapp deploy
CAUSA: Token de auth expirado
SOLUCIÓN:
  az logout && az login
  # Re-intentad el deploy

❌ ERROR: HTTP 500 después del deploy (app no arranca)
CAUSA: Error en código o configuración
SOLUCIÓN:
  az webapp log tail --name <app> -g <rg>
  # Leed la excepción y corregid
  # Causa típica: versión .NET no coincide (Program.cs requiere 8.0, plan tiene 6.0)

❌ ERROR: HTTP 503 Service Unavailable
CAUSA: App aún arrancando (cold start)
SOLUCIÓN:
  Esperad 60-90 segundos. Refrescad.
  Si persiste >3 min: revisar logs

❌ ERROR: "La app no responde con el código nuevo"
CAUSA: Cache del navegador, o deploy incompleto
SOLUCIÓN:
  Ctrl+Shift+R (hard refresh)
  curl <url> (bypasea cache del navegador)

❌ ERROR: "entorno" aparece como "Development" en Azure
CAUSA: Variable ASPNETCORE_ENVIRONMENT hardcoded
SOLUCIÓN:
  az webapp config appsettings list --name <app> -g <rg>
  # Verificar que ASPNETCORE_ENVIRONMENT = "Production"
  # Si NO está: Azure la añade por defecto, algo la está sobrescribiendo
```

## Slide 62 — Troubleshooting: errores persistentes

Si los problemas persisten tras los intentos básicos:

```
🔧 RESET COMPLETO DE LA APP:
  # Detiene la app, la reinicia (limpia memoria/cache)
  az webapp restart --name <app> -g <rg>
  # Esperad 60s y re-probad

🔧 RE-DEPLOY LIMPIO:
  # A veces hay conflictos de archivos antiguos
  az webapp deployment source delete --name <app> -g <rg>
  # Luego hacer deploy normal de nuevo

🔧 HABILITAR LOGS DETALLADOS:
  az webapp config set \
    --name <app> -g <rg> \
    --generic-configurations '{"detailedErrorLoggingEnabled": true}'
  # Re-desplegar
  # Los errores ahora muestran stack trace completo
  # DESACTIVAR después (seguridad)

🔧 VER ÚLTIMO DEPLOY:
  az webapp deployment list \
    --name <app> -g <rg> \
    --query "[0].{Status:status, Author:author, Start:startTime, Active:active}" \
    -o table
  # Si "Status: Failed", mirar en Kudu el log de deploy

🔧 VERIFICAR ARCHIVOS EN WWWROOT:
  # Vía Kudu: https://<app>.scm.azurewebsites.net
  # Debug Console → CMD → D:\home\site\wwwroot
  # Debería haber: hello-world.dll, web.config, etc.
  # Si está vacío: deploy falló silenciosamente

🔧 FACTORY RESET (extremo):
  # Borrar la Web App completa y recrear desde cero
  az webapp delete --name <app> -g <rg>
  # Repetir desde Paso 2.2
```

**Reglas de oro del debugging:**
1. **Siempre leer logs primero** — la respuesta suele estar ahí
2. **Cambiar una cosa a la vez** — si cambiáis 5 cosas, no sabéis cuál arregló
3. **No tener miedo de borrar y recrear** — 5 min perdidos vs 1h debuggeando

## Slide 63 — Troubleshooting: errores 4xx (de cliente)

Errores que indican que el cliente pide algo mal (o la app rechaza):

**400 Bad Request:**
```
Causa: request malformado (JSON inválido, parameter faltante)
Debug:
  curl -v <url>/<endpoint>     # ver qué envía el cliente
  tail logs de la app          # ver qué ve el servidor
Fix: validar payload del cliente, revisar FluentValidation
```

**401 Unauthorized:**
```
Causa: requiere autenticación (Easy Auth activado, o JWT middleware)
Debug:
  Portal → Authentication → ¿hay provider configurado?
  ¿La app tiene [Authorize] attribute?
Fix: login primero, o hacer endpoint público (solo si procede)
```

**403 Forbidden:**
```
Causas típicas en Azure App Service:
  a) F1 ha agotado 60 min CPU/día → devuelve 403 hasta reset UTC 00:00
  b) IP restrictions configuradas → vuestra IP no está en whitelist
  c) Easy Auth activo + rol no asignado
Debug:
  az webapp show -n <app> -g <rg> --query hostNameSslStates
  Portal → Access restrictions → ver reglas
Fix: escalar a B1, abrir IP, asignar rol
```

**404 Not Found:**
```
Causas:
  a) Ruta mal escrita (/api/Users vs /api/users)
  b) App no desplegada (wwwroot vacío)
  c) Routing no configurado en Program.cs
Debug:
  SSH: ls /home/site/wwwroot/
  ¿Está el DLL ahí? ¿Falta algo?
  curl <app>.scm.azurewebsites.net/DebugConsole → revisar filesystem
Fix: redeploy, revisar endpoints en Program.cs
```

**405 Method Not Allowed:**
```
Causa: usas POST contra endpoint GET (o viceversa)
Fix: verificar método HTTP
```

**408 Request Timeout:**
```
Causa: Kestrel timeout (por defecto 30s)
Fix: revisar si la request tarda mucho o hay bucle infinito
```

**429 Too Many Requests:**
```
Causa: rate limiting configurado o throttling de plataforma
Fix: revisar rate limit policy o escalar
```

## Slide 64 — Troubleshooting: errores 5xx (de servidor)

Estos son vuestros dolores de cabeza reales. Siempre empezad mirando **Log Stream**:

**500 Internal Server Error:**
```
Causa: excepción no manejada en vuestro código

  1. az webapp log tail -n <app> -g <rg>
  2. Portal → Log stream
  3. AppInsights → Failures → ver stack trace

  - Config missing: App Setting no configurado

**502 Bad Gateway:**
```
Causa: el front-end de Azure (ARR) no puede hablar con vuestro proceso
Debug:
  - ¿La app ha arrancado? (revisar wwwroot y startup logs)
  - ¿Escucha en el puerto correcto? (Azure pone PORT env var)
  - ¿Crashea en startup?
Comandos:
  az webapp log tail -n <app> -g <rg>
  # Buscar "Application startup" seguido de error
Fix: revisar Program.cs, configuración mínima
```

**503 Service Unavailable:**
```
La más frustrante. Varias causas:
  a) App Service Plan saturado (CPU/RAM al 100%)
  b) Instancia reiniciando tras crash
  c) Cold start (F1 tras idle de 20min) — espera 30s
  d) Deployment in progress (momentáneo durante deploy)
  e) Mantenimiento de plataforma (raro, Azure avisa)
  
Debug:
  az webapp show -n <app> -g <rg> --query state
  Metrics → CPU/RAM en los últimos 30 min
  Advisor → recomendaciones
Fix:
  - Esperad 1-2 min si fue cold start
  - Escalar si es saturación persistente
  - Restart: az webapp restart -n <app> -g <rg>
```

**504 Gateway Timeout:**
```
Causa: vuestra app responde pero tarda más de 230s (límite de App Service)
Fix:
  - Reducir tiempo de respuesta
  - Usar Durable Functions o colas para work largo
  - Streaming responses si tiene sentido
```

## Slide 65 — Troubleshooting: errores específicos de deploy

Errores que veréis al ejecutar `az webapp deploy` o desde VS Code:

**"Conflict - Another operation is in progress":**
```
Causa: ya hay un deploy ejecutándose
Debug:
  az webapp deployment list -n <app> -g <rg> --query "[].status"
Fix:
  - Esperar a que termine (~1-2 min)
  - O cancelar: az webapp deployment cancel -n <app> -g <rg>
```

**"Unauthorized - The client 'xxx' with object id 'yyy' does not have authorization":**
```
Causa: vuestro usuario no tiene rol de deploy en el App Service
Debug:
  az role assignment list --assignee <vuestro-email> \
    --scope $(az webapp show -n <app> -g <rg> --query id -o tsv)
Fix: pedir a un admin que os asigne "Website Contributor" o "Contributor"
```

**"Package deployment was marked as cancelled":**
```
Causa: timeout del deploy (zip muy grande o conexión lenta)
Debug: tamaño del zip, ping a scm.azurewebsites.net
Fix:
  - Reducir tamaño del publish (quitar archivos innecesarios)
  - --timeout 300 para dar más margen
  - Usar Run From Package + Storage (M2)
```

**"Could not find a valid ASP.NET Core runtime":**
```
Causa: la app está configurada para runtime diferente
Debug:
  az webapp config show -n <app> -g <rg> --query "{netFxVer:netFrameworkVersion, linuxFx:linuxFxVersion}"
Fix:
  # Forzar runtime .NET 8
  az webapp config set -n <app> -g <rg> --linux-fx-version "DOTNETCORE|8.0"
```

**"The zip file is not a valid zip file":**
```
Causa: tar.gz en lugar de zip, o zip corrupto
Fix:
  # Comprimir correctamente
  cd ./publish
  zip -r ../deploy.zip .
  # NO hacer zip deploy.zip publish (mete la carpeta)
```

## Slide 67 — Troubleshooting: cuándo reiniciar, cuándo redeploy, cuándo recrear

Decisión crítica: ¿qué acción tomar?

```
┌───────────────────────────────────────────────────────────────┐
│  RESTART (30 segundos)                                        │
│  az webapp restart -n <app> -g <rg>                           │
├───────────────────────────────────────────────────────────────┤
│  Usar cuando:                                                 │
│  - App Settings cambiados, la app no los ha recogido         │
│  - Leak de memoria evidente                                   │
│  - Crash reciente que debe haber resuelto la causa raíz      │
│  - Problema momentáneo que queréis "resetear"                │
│                                                               │
│  NO resuelve:                                                 │
│  - Bugs de código                                             │
│  - Config mal puesta                                          │
│  - DLLs corruptas                                             │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│  REDEPLOY (1-2 minutos)                                       │
│  dotnet publish + az webapp deploy                            │
├───────────────────────────────────────────────────────────────┤
│  Usar cuando:                                                 │
│  - Bugs en código                                             │
│  - Cambios en appsettings.json                                │
│  - Dependencias actualizadas                                  │
│  - Filesystem corrupto / archivos zombie del deploy anterior │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│  RECREATE (5-10 minutos)                                      │
│  az webapp delete + az webapp create                          │
├───────────────────────────────────────────────────────────────┤
│  Usar cuando:                                                 │
│  - Nada más funciona                                          │
│  - Queréis cambiar SKU del Plan (mejor: cambiar el plan)      │
│  - Config corrupta a nivel plataforma (raro)                  │
│  - Queréis empezar "desde cero"                               │
│                                                               │
│  ADVERTENCIA: perderéis logs, metrics y configuración       │
│  si no las tenéis en IaC (Bicep/ARM)                          │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│  SCALE UP / SCALE OUT (varios minutos)                        │

├───────────────────────────────────────────────────────────────┤
│  Usar cuando:                                                 │
│  - CPU/RAM consistentemente al tope                           │
│  - Demasiado tráfico para instancias actuales                │

└───────────────────────────────────────────────────────────────┘
```

**Regla práctica:** probad en este orden: restart → redeploy → recreate. No saltéis al "recreate" sin antes investigar.

## Slide 68 — Troubleshooting: lo que NO debéis hacer nunca

Anti-patterns frecuentes que empeoran la situación:

```
❌ "Voy a borrar todo y empezar de cero" SIN INVESTIGAR
   → Perderéis la pista del problema real
   → Probablemente se repetirá en el siguiente deploy
   ✅ Investigad primero (30 min), recreate solo si no hay alternativa

❌ Ignorar errores en logs porque "la app funciona"
   → Hoy funciona, mañana rompe en producción
   ✅ Cualquier ERROR level en logs debe investigarse

❌ Desactivar HTTPS o bajar TLS para "arreglar" un problema
   → Os exponéis a MITM attacks
   ✅ Solucionad el error de verdad (cert, CORS, etc.)

❌ Poner secrets en App Settings en texto plano
   → Visible para cualquiera con acceso de lectura al RG
   ✅ Key Vault references (M6)

❌ Desactivar Application Insights para "reducir coste"
   → Os quedáis sin diagnóstico cuando falla
   ✅ Ajustad sampling (50%) antes de desactivar

❌ Usar F1 para cargas serias ("total, es gratis")
   → 60 min CPU/día → 403s aleatorios en producción
   ✅ B1 o superior para cualquier cosa seria

❌ Dejar recursos corriendo "por si acaso"
   → Factura inesperada a fin de mes
   ✅ Limpieza disciplinada + budget alerts

❌ Hacer cambios en producción desde Portal sin IaC
   → Configuration drift: nadie sabe qué está configurado
   ✅ Bicep/Terraform para todo en producción

❌ Compartir credenciales SCM o FTP con el equipo
   → No auditable, difícil de rotar
   ✅ RBAC con Entra ID (cada dev tiene sus permisos)
```

**Regla de oro:** si vuestro primer instinto es "apagar monitoring" o "saltarse validación", **es exactamente lo contrario** de lo que deberíais hacer.

## Slide 72 — Reto 4: Logging estructurado con ILogger

Añadid logs útiles a vuestros endpoints:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Configurar logging (aunque es el default, explícito es mejor)
builder.Logging.AddConsole();
builder.Logging.SetMinimumLevel(LogLevel.Information);

var app = builder.Build();

// Inject ILogger en cada endpoint
app.MapGet("/", (ILogger<Program> logger) =>
{
    logger.LogInformation("Root endpoint called at {Time}", DateTime.UtcNow);
    
    return Results.Json(new
    {
        mensaje = "Hello Azure — Curso AZ-204",
        // ... resto del JSON
    });
});

app.MapGet("/api/echo", (string? msg, ILogger<Program> logger) =>
{
    logger.LogInformation("Echo request with msg={Msg} length={Len}", 
        msg, msg?.Length ?? 0);
    
    if (string.IsNullOrWhiteSpace(msg))
    {
        logger.LogWarning("Echo called without msg parameter");
        return Results.BadRequest(new { error = "msg es obligatorio" });
    }
    
    return Results.Ok(new { recibido = msg, eco = $"Has dicho: {msg}" });
});
```

**Tras redeploy, generad tráfico y observad:**
```bash
# Terminal 1: streaming de logs
az webapp log tail --name app-curso-<tu-nombre> -g rg-curso-azure-<tu-nombre>

# Terminal 2: peticiones
curl https://app-curso-<tu-nombre>.azurewebsites.net/api/echo?msg=test
curl https://app-curso-<tu-nombre>.azurewebsites.net/api/echo
```

**Output esperado en el tail:**
```
[Information] Program: Echo request with msg=test length=4
[Information] Program: Echo request with msg= length=0
[Warning] Program: Echo called without msg parameter
```

**Logging estructurado** (placeholders `{Msg}`, `{Len}`) permite búsquedas:
- En App Insights: `traces | where customDimensions.Msg == "test"`
- Cada campo es queryable separadamente
- Vs string formatting: solo texto búsqueda por substring

## Slide 73 — Reto 5: Script de deploy unificado

Convirtiendo el proceso manual en un script:

```bash
# scripts/deploy.sh
#!/bin/bash
set -e  # fallar en cualquier error

# Variables
APP_NAME="app-curso-<tu-nombre>"
RG_NAME="rg-curso-azure-<tu-nombre>"
PUBLISH_DIR="./publish"
ZIP_FILE="deploy.zip"

echo "🚀 Iniciando deploy de $APP_NAME..."

# Paso 1: Build
echo "📦 [1/4] Publishing..."
dotnet publish -c Release -o "$PUBLISH_DIR"

# Paso 2: Empaquetar
echo "📦 [2/4] Creating ZIP..."
cd "$PUBLISH_DIR"
zip -rq "../$ZIP_FILE" .
cd ..

# Paso 3: Deploy
echo "☁️  [3/4] Deploying to Azure..."
az webapp deploy \
    --resource-group "$RG_NAME" \
    --name "$APP_NAME" \
    --src-path "$ZIP_FILE" \
    --type zip \
    --timeout 300

# Paso 4: Verificar
echo "✅ [4/4] Verifying..."
sleep 10  # esperar warmup
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "https://$APP_NAME.azurewebsites.net")

if [ "$HTTP_CODE" = "200" ]; then
    echo "✅ Deploy exitoso! URL: https://$APP_NAME.azurewebsites.net"
else
    echo "❌ Deploy completado pero la app responde HTTP $HTTP_CODE"
    echo "Revisad los logs: az webapp log tail --name $APP_NAME -g $RG_NAME"
    exit 1
fi

# Cleanup
rm -rf "$PUBLISH_DIR" "$ZIP_FILE"
echo "🧹 Cleanup completado"
```

**Uso:**
```bash
chmod +x scripts/deploy.sh
./scripts/deploy.sh
```

**Mejora:** versión PowerShell equivalente para Windows en `scripts/deploy.ps1`. Ambos scripts versionados en Git → cualquiera puede desplegar igual.

## Slide 79 — Colaboración: compartir un script de onboarding

Si vuestro equipo va a repetir este setup, automatizadlo con un script:

```bash
#!/bin/bash
# onboarding.sh — setup inicial para nuevo dev del equipo

set -euo pipefail

# Pedir datos
read -p "Tu nombre (para nombres de recursos): " USER_NAME
USER_NAME=$(echo "$USER_NAME" | tr '[:upper:]' '[:lower:]' | tr -d ' ')

# Constantes
LOCATION="westeurope"
RG="rg-curso-azure-${USER_NAME}"
ASP="asp-curso-${USER_NAME}"
APP="app-curso-${USER_NAME}"
APPI="appi-curso-${USER_NAME}"
LAW="law-curso-${USER_NAME}"
TAGS="owner=${USER_NAME}@miempresa.com curso=AZ-204 sesion=M01 expira=2026-05-31"

echo "═══════════════════════════════════════════"
echo "  Setup curso Azure AZ-204"
echo "═══════════════════════════════════════════"
echo "Dev:      $USER_NAME"
echo "Region:   $LOCATION"
echo "RG:       $RG"
echo "═══════════════════════════════════════════"
read -p "¿Continuar? (y/n): " CONFIRM
[ "$CONFIRM" = "y" ] || exit 0

# Create all resources
echo "1/6 Creating Resource Group..."
az group create -n "$RG" -l "$LOCATION" --tags $TAGS -o none

echo "2/6 Creating Log Analytics..."
az monitor log-analytics workspace create \
  -g "$RG" -n "$LAW" -l "$LOCATION" -o none

echo "3/6 Creating Application Insights..."
az monitor app-insights component create \
  --app "$APPI" -l "$LOCATION" -g "$RG" \
  --workspace "$LAW" --application-type web -o none

echo "4/6 Creating App Service Plan..."
az appservice plan create \
  -n "$ASP" -g "$RG" --is-linux --sku F1 -o none

echo "5/6 Creating Web App..."
az webapp create \
  -n "$APP" -g "$RG" -p "$ASP" \
  --runtime "DOTNETCORE:8.0" -o none

echo "6/6 Configuring Application Insights..."
APPI_CONN=$(az monitor app-insights component show \
  --app "$APPI" -g "$RG" --query connectionString -o tsv)
az webapp config appsettings set \
  -n "$APP" -g "$RG" \
  --settings "APPLICATIONINSIGHTS_CONNECTION_STRING=$APPI_CONN" -o none

echo ""
echo "✅ Setup completo"
echo "   URL: https://${APP}.azurewebsites.net"
echo ""
echo "   Limpieza cuando termines:"
echo "   az group delete -n $RG --yes --no-wait"
```

**Ventajas:**
- Nuevo miembro del equipo → `./onboarding.sh` → 5 min y listo
- Mismos nombres + tags en todo el equipo → governance fácil
- Documentación ejecutable

## Slide 82 — Limpieza: CRÍTICO (no os olvidéis)

```bash
# OPCIÓN 1: Borrar solo la Web App (mantener plan)

  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre>

  --name plan-curso-<tu-nombre> \

  --name rg-curso-azure-<tu-nombre> \

## Slide 90 — Gotchas que no olvidaréis

Lecciones aprendidas que os servirán toda la vida Azure:

```
🔑 "ASPNETCORE_ENVIRONMENT es Production por defecto en Azure"
   No tenéis que setearla — Azure la pone sola.
   Si aparece Development en Azure, algo la está sobrescribiendo.

🔑 "Los nombres de Web Apps son globales"
   app-curso-pedro puede estar tomada por otro Pedro.
   Estrategia: incluid sufijo empresa o año.

🔑 "El RG es un contenedor, no un recurso"
   Borrar el RG borra TODO lo que contiene.
   Superpoder: limpieza total con un comando.

🔑 "Un plan puede hostear múltiples Web Apps"
   Escalado: 1 plan con 3 instancias = 3 apps x 3 instancias.
   Ahorro: agrupad apps relacionadas en el mismo plan.

🔑 "F1 (Free) tiene límites brutales"
   60 min CPU/día, sin SSL custom, sin Always On, sin slots.
   Solo para aprender. Nunca para "producción".

🔑 "Cold start es real"
   Tras minutos sin tráfico, la primera request tarda 3-10s.
   B1 y superiores con Always On evitan esto.

🔑 "Kudu es el superpoder oculto"
   Cuando algo falla y Azure no dice por qué, Kudu sí.
   URL: https://<app>.scm.azurewebsites.net

🔑 "Logs siempre primero"
   Antes de teorías mágicas sobre qué falla, leed los logs.
   90% de los misterios se resuelven así.

🔑 "Limpiar es tan importante como crear"
   Habituaos: crear → usar → limpiar. Cada ejercicio.
```

if [ -z "$1" ]; then
    echo "Suscripción actual:"
    az account show --query "{Name:name, Id:id}" -o table

    echo "Suscripciones disponibles:"

```bash
#!/bin/bash
# Uso: ./rg-stats.sh <rg-name>

RG="${1:-rg-curso-azure-$(whoami)}"
echo "📊 Estadísticas del RG: $RG"
echo ""
echo "Total recursos:"
az resource list -g "$RG" --query "length(@)"
echo ""
echo "Recursos por tipo:"
az resource list -g "$RG" --query "[].type" -o tsv | sort | uniq -c | sort -rn
```

**scripts/cleanup-rg.sh** (limpieza segura):
```bash
#!/bin/bash
# Uso: ./cleanup-rg.sh <rg-name>

RG="$1"
if [ -z "$RG" ]; then
    echo "❌ Usage: $0 <rg-name>"
    exit 1
fi

echo "⚠️  Vas a borrar el RG: $RG"
echo "Contenido actual:"
az resource list -g "$RG" -o table
echo ""
read -p "¿Confirmar borrado? (escribe 'YES' para confirmar): " confirm

if [ "$confirm" = "YES" ]; then
    az group delete --name "$RG" --yes
    echo "✅ RG $RG borrado"
else
    echo "❌ Cancelado"
fi
```

## Slide 3 — Verificar el Resource Group individual

```bash
# 1. Confirmar que estáis en la suscripción correcta
az account show --query "{suscripcion:name, tenant:tenantId}" --output table

# 2. Ver vuestro Resource Group
az group show --name rg-curso-azure-<tu-nombre> --output table

# 3. Ver qué hay dentro (debería estar vacío o casi)
az resource list --resource-group rg-curso-azure-<tu-nombre> --output table

# 4. Verificar permisos
az role assignment list \
  --resource-group rg-curso-azure-<tu-nombre> \
  --assignee <tu-email> \

  --output table
```

**Esperado:**
- RG existe en West Europe (o la región asignada)
- Rol: Contributor (o superior)
- Vacío o con recursos base preconfigurados

Si no veis el RG o no tenéis permisos, parad y avisad. Sin esto, nada de lo que viene funciona.

## Slide 4 — Crear un App Service Plan

```bash
az appservice plan create \
  --name plan-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --sku F1 \
  --is-linux false \
  --tags entorno=dev proyecto=curso responsable=<tu-nombre>
```

**Parámetros explicados:**
- `--sku F1`: tier gratuito, perfecto para prácticas
- `--is-linux false`: Windows (por defecto para .NET)
- `--tags`: etiquetamos desde el primer recurso

**Verificar:**
```bash
az appservice plan show \
  --name plan-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --query "{nombre:name, sku:sku.name, tier:sku.tier, workers:sku.capacity}" \
  --output table
```

Deberíais ver: SKU = F1, Tier = Free, Workers = 0 (bajo demanda en tier gratuito).

## Slide 8 — El código: Hello World informativo

Reemplazad el contenido de `Program.cs`:

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => Results.Json(new
{
    mensaje = "Hello Azure — Curso AZ-204",
    asistente = "<tu-nombre>",
    entorno = app.Environment.EnvironmentName,
    servidor = Environment.MachineName,
    hora_utc = DateTime.UtcNow.ToString("yyyy-MM-dd HH:mm:ss"),
    runtime = System.Runtime.InteropServices
                .RuntimeInformation.FrameworkDescription,
    os = System.Runtime.InteropServices
                .RuntimeInformation.OSDescription,
    arquitectura = System.Runtime.InteropServices
                .RuntimeInformation.OSArchitecture.ToString(),
    procesadores = Environment.ProcessorCount
}));

app.MapGet("/health", () => Results.Ok(new { status = "healthy" }));

app.MapGet("/info", () => Results.Json(new
{
    variables_entorno = Environment.GetEnvironmentVariables()
        .Cast<System.Collections.DictionaryEntry>()
        .Where(e => e.Key.ToString()!.StartsWith("WEBSITE_") || 
                     e.Key.ToString()!.StartsWith("ASPNETCORE_"))
        .ToDictionary(e => e.Key.ToString(), e => e.Value?.ToString())
}));

app.Run();
```

**Tres endpoints:**
- `/` → Info general de la app (entorno, servidor, OS)
- `/health` → Health check simple
- `/info` → Variables de entorno de Azure (WEBSITE_*, ASPNETCORE_*)

El endpoint `/info` es solo para desarrollo — en producción NUNCA expongáis variables de entorno.

## Slide 15 — Variables de entorno en App Service

Las variables de entorno son fundamentales para configurar tu app sin cambiar código:

```bash
# Ver todas las app settings
az webapp config appsettings list \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --output table

# Añadir una variable
az webapp config appsettings set \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --settings MI_VARIABLE="mi-valor" OTRA_VARIABLE="otro-valor"

# Eliminar una variable
az webapp config appsettings delete \
  --name app-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --setting-names MI_VARIABLE
```

**Variables que Azure crea automáticamente:**
- `WEBSITE_SITE_NAME` → nombre de la app
- `WEBSITE_HOSTNAME` → hostname completo
- `WEBSITE_INSTANCE_ID` → ID de la instancia actual
- `ASPNETCORE_ENVIRONMENT` → no se define por defecto (→ Production)

**Cuándo usar app settings:**
- Cadenas de conexión a bases de datos
- URLs de APIs externas
- Feature flags
- Cualquier configuración que varíe entre entornos

En el módulo 6 veremos cómo proteger las variables sensibles con Key Vault.

## Slide 16 — Troubleshooting: los problemas más comunes

**Error 503 — Service Unavailable:**
La app está arrancando. Esperad 30 segundos. Si persiste: logs → probablemente un error en el arranque (dependencia faltante, configuración incorrecta).

**Error 500 — Internal Server Error:**
Tu código lanza una excepción. `az webapp log tail` muestra el stack trace. Corregid y redesplega.

**Error 404 — Not Found:**
La ruta no existe. Verificad que el endpoint está definido en el código y que la app está desplegada correctamente (Kudu → wwwroot).

**La app muestra contenido viejo después de desplegar:**
1. Hard refresh: `Ctrl+Shift+R`
2. Verificad en Kudu que los archivos en wwwroot son los correctos
3. Si usáis Run from Package, verificad que el flag está activo

**"az webapp deploy" devuelve error:**
1. Verificad nombre de la app y RG (case sensitive)
2. Verificad que el zip contiene el resultado de `dotnet publish`, no el código fuente
3. Verificad que estáis logueados: `az account show`

**Logs vacíos:**
Los logs no están habilitados por defecto. Ejecutad el comando de `az webapp log config` del slide 14.

## Slide 17 — Script completo de despliegue

Juntemos todo en un script reutilizable:

```bash
#!/bin/bash
# deploy.sh — Despliegue completo a App Service
# Uso: ./deploy.sh <nombre-app> <resource-group>

APP_NAME=${1:?"Uso: ./deploy.sh <app-name> <resource-group>"}
RG=${2:?"Uso: ./deploy.sh <app-name> <resource-group>"}

echo "=== Desplegando $APP_NAME en $RG ==="

# 1. Build
echo "→ Compilando..."
dotnet publish -c Release -o ./publish --verbosity quiet

# 2. Empaquetar
echo "→ Empaquetando..."
cd publish && zip -r -q ../deploy.zip . && cd ..

# 3. Desplegar
echo "→ Desplegando a Azure..."
az webapp deploy \
  --resource-group $RG \
  --name $APP_NAME \
  --src-path deploy.zip \
  --type zip \
  --output none

# 4. Verificar
echo "→ Verificando..."
URL="https://$APP_NAME.azurewebsites.net"
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" $URL)

if [ "$HTTP_CODE" == "200" ]; then
  echo "✓ Despliegue exitoso — $URL (HTTP $HTTP_CODE)"
else
  echo "✗ Error — HTTP $HTTP_CODE. Revisad logs:"
  echo "  az webapp log tail --name $APP_NAME --resource-group $RG"
fi

# 5. Limpiar
rm -rf publish deploy.zip

echo "=== Fin ==="
```

Guardadlo en `curso-azure/scripts/deploy.sh`. Lo usaréis durante todo el curso.

## Slide 18 — Windows vs Linux App Service: qué elegir

Al crear un App Service Plan, elegís el sistema operativo. Afecta a qué podéis ejecutar, el precio y algunas features:

```
Windows App Service:
├── Runtime: .NET Framework (4.x), .NET (Core/5/6/7/8), Node, PHP, Java, Python
├── IIS como host
├── Soporta Web Jobs clásicos
├── Support para .NET Framework (único sitio)
├── Un poco más caro (mismo SKU)
└── No requiere Docker/container

Linux App Service:
├── Runtime: .NET 6+, Node, PHP, Java, Python, Ruby, Go, contenedores Docker
├── Sin IIS (Kestrel direct, Nginx, etc.)
├── ~10-15% más barato para mismo SKU
├── Mejor para Docker custom (code-less deploys)
├── Required para algunas features modernas
└── NO soporta .NET Framework

Para este curso (.NET 8):
az appservice plan create ... --is-linux   # RECOMENDADO
# Misma experiencia de deploy, más barato, mejor alineado con Docker moderno
```

Si tenéis apps .NET Framework 4.x legacy, Windows. Para todo lo nuevo, Linux es la opción por defecto.

## Slide 19 — Deploy ZIP vs Git vs FTP vs Container: comparativa

Hay múltiples formas de subir el código a App Service. En el curso usamos `az webapp deploy` (ZIP), pero conviene conocer las alternativas:

| Método | Velocidad | Reproducibilidad | Uso típico |
|---|---|---|---|
| **ZIP (`az webapp deploy`)** | Rápida | Alta (scripteable) | CI/CD, despliegue manual puntual |
| **Git local** | Media | Media | Prototipado, iteración rápida |
| **GitHub Actions** | Media | Alta (versionada) | Proyectos en GitHub |
| **Azure DevOps Pipelines** | Media | Alta | Proyectos en ADO |
| **FTP/FTPS** | Lenta | Baja | Solo emergencias, apps legacy |
| **Docker container** | Media | Muy alta | Apps Docker, estandarización |
| **WebDeploy (msdeploy)** | Media | Alta | Stack Visual Studio clásico |

**Regla del curso:** ZIP deploy para manual, GitHub Actions o ADO Pipelines para automático. FTP solo si no queda otra.

## Slide 20 — Deployment Center: configurar deploy continuo desde el portal

Para proyectos reales, queréis que cada push a `main` despliegue solo. Lo podéis configurar desde el portal:

```
Portal Azure → tu App Service → Deployment Center

Opciones de origen:
├── Azure Repos (ADO)
├── GitHub
├── Bitbucket
├── Local Git
├── External Git
├── OneDrive / Dropbox
└── Container Registry (para Docker)

Al conectarlo con GitHub:
1. Autorizas el OAuth (una vez)
2. Eliges repo + rama (típicamente main)
3. Azure genera un .github/workflows/main_<appname>.yml automáticamente
4. El workflow hace build + deploy en cada push
5. Azure añade el secret AZUREAPPSERVICE_PUBLISHPROFILE_<id> al repo
```

**Útil saber:** Deployment Center NO es obligatorio. Podéis escribir vuestro propio workflow/pipeline desde cero y tener más control. El Center solo acelera el setup inicial.

## Slide 21 — Publish profile: las credenciales en un XML

Cuando Deployment Center conecta con GitHub, descarga un "publish profile". Podéis verlo/descargarlo manualmente:

```bash
# Descargar publish profile
az webapp deployment list-publishing-profiles \
  --name appsvc-aprende-$(whoami) \
  -g rg-aprendizaje-$(whoami) \
  --xml > publish-profile.xml

# El XML contiene credenciales (publicUrl, userName, userPWD)
# para varias formas de deploy:
#   - MSDeploy (WebDeploy)
#   - FTP
#   - ZIP Deploy
```

**Advertencia de seguridad:** este XML es un secret. No lo commiteéis. Para CI/CD modernos, es mejor usar **federated credentials (OIDC)** con Managed Identity — evita secretos en secretos de GitHub. Lo veréis en M8.

**Resetear credenciales** si sospecháis leak:
```bash
az webapp deployment list-publishing-credentials --name ... -g ...
# o desde portal: Overview → Reset publish profile
```

## Slide 22 — Deploy desde GitHub Actions: el workflow básico

Si trabajáis con GitHub, este es el workflow más simple que funciona (lo generáis sustituyendo valores):

```yaml
# .github/workflows/deploy-appservice.yml
name: Deploy to App Service

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      
      - name: Build
        run: dotnet publish -c Release -o publish
      
      - name: Deploy
        uses: azure/webapps-deploy@v3
        with:
          app-name: 'appsvc-aprende-pedro'
          publish-profile: ${{ secrets.AZURE_PUBLISH_PROFILE }}
          package: publish
```

Añadís el secret `AZURE_PUBLISH_PROFILE` en Settings → Secrets con el contenido del XML descargado. En cada push a main, GitHub construye y despliega. Primer paso hacia CI/CD real.

## Slide 23 — Always On, Startup Command y configuración HTTP

App Service tiene varias opciones de configuración que conviene conocer desde el día uno:

```bash
# Always On (para SKUs B1+): mantiene el sitio "caliente"
# Sin esto, después de 20min sin tráfico, el sitio se "duerme" y tarda
# segundos en responder la primera request.
az webapp config set --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --always-on true

# Startup command (para Linux): qué ejecutar al arrancar
# Útil si vuestro contenedor o app necesita comandos custom
az webapp config set --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --startup-file "dotnet MiApp.dll"

# HTTPS only: redirecciona HTTP → HTTPS automáticamente
az webapp update --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --https-only true

# Min TLS version (1.2 recomendado por compliance)
az webapp config set --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --min-tls-version 1.2

# HTTP 2.0 habilitado
az webapp config set --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --http20-enabled true
```

**Para producción siempre:** `--always-on true --https-only true --min-tls-version 1.2 --http20-enabled true`.

## Slide 24 — Health check: probes que mantienen la app sana

App Service puede monitorizar un endpoint de vuestra app periódicamente y, si falla, marcar esa instancia como no saludable (reemplaza automáticamente en SKUs con multi-instancia):

```csharp
// En vuestra app .NET 8, añadís un endpoint /health
app.MapGet("/health", () => Results.Ok(new 
{ 
    status = "healthy", 
    timestamp = DateTime.UtcNow 
}));
```

```bash
# Configurar que App Service monitorice /health cada 2 min
az webapp config set --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --generic-configurations '{"healthCheckPath": "/health"}'
```

**Cómo funciona:** App Service llama `GET /health` cada ~2 min. Si la respuesta NO es 2xx durante varios intentos consecutivos, marca la instancia como unhealthy y deja de enviarle tráfico. En SKUs B1+ con múltiples instancias, una instancia sana sigue sirviendo tráfico.

Para un health check útil, añadid checks reales (Cosmos DB accesible, etc.) — lo veremos en M2 con `AddHealthChecks()`.

## Slide 25 — App Settings vs Connection Strings: cuándo usar cada uno

Ya vimos `--settings`. App Service tiene DOS tipos de configuración diferentes, y conviene entender la diferencia:

```bash
# App Settings: key-value simples (variables de entorno)
az webapp config appsettings set ... --settings KEY=VALUE

# Connection Strings: cadenas de conexión a BBDD, especiales
az webapp config connection-string set \
  --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --connection-string-type SQLAzure \
  --settings MiBBDD="Server=tcp:...;Database=..."
```

**Diferencias prácticas:**

| | App Settings | Connection Strings |
|---|---|---|
| Tipo | KEY=VALUE | Tipado (SQLAzure, MySql, Custom, etc.) |
| Acceso desde .NET | `Environment.GetEnvironmentVariable("KEY")` | `Configuration.GetConnectionString("MiBBDD")` |
| Visible en Portal | Valores ocultos | Valores ocultos |
| Uso recomendado | Variables de entorno, feature flags, URLs | Cadenas con credenciales BBDD |

**Nota para M6:** en el curso real, TODO esto irá a Key Vault. Estas son solo las formas "nativas" de App Service — útiles para empezar y para desarrollo.

## Slide 28 — Kudu API: scripting lo que haríais en el navegador

Kudu (slide 13) no es solo una UI — expone una API REST que podéis invocar desde scripts. Útil para automatización:

```bash
# Obtener credenciales de publishing (user:pass para Basic Auth)
CREDS=$(az webapp deployment list-publishing-credentials \
  --name appsvc-aprende-pedro -g rg-aprendizaje-pedro \
  --query "[publishingUserName, publishingPassword]" -o tsv)
USER=$(echo "$CREDS" | head -1)
PASS=$(echo "$CREDS" | tail -1)
AUTH=$(echo -n "$USER:$PASS" | base64)

KUDU=https://appsvc-aprende-pedro.scm.azurewebsites.net

# Ejecutar un comando remoto
curl -X POST $KUDU/api/command \
  -H "Authorization: Basic $AUTH" \
  -H "Content-Type: application/json" \
  -d '{"command":"ls -la","dir":"site/wwwroot"}'

# Listar procesos
curl $KUDU/api/processes -H "Authorization: Basic $AUTH"

# Capturar un mini-dump de un proceso (diagnóstico)
curl -X POST $KUDU/api/processes/<pid>/dump \
  -H "Authorization: Basic $AUTH" -o dump.dmp

# Ver últimos deploys
curl $KUDU/api/deployments -H "Authorization: Basic $AUTH"
```

**Advertencia de seguridad:** Basic Auth con publishing credentials — en entornos enterprise, deshabilitar Basic Auth y usar Entra ID authentication sobre Kudu. Lo veréis en M6.

## Slide 29 — Rollback: volver a una versión anterior

Habéis desplegado algo que ha roto producción. ¿Cómo volvéis atrás rápidamente?

```bash
# Método 1: Deployment Center → Logs → seleccionar deploy anterior → Redeploy
# (Funciona si el deploy estaba vinculado a Git/GitHub/ADO)

# Método 2: Volver a la versión del código y redesplegar
git checkout <commit-anterior>
dotnet publish -c Release -o publish
cd publish && zip -r ../rollback.zip . && cd ..
az webapp deploy --resource-group rg-aprendizaje-pedro \
  --name appsvc-aprende-pedro --src-path rollback.zip --type zip

# Método 3: Deployment slots (VISTO EN M2)
# Preproducción: swap slots (staging↔production) revierte en segundos
# Ésta es la forma profesional de hacer deploys: siempre con swap
```

**Regla de oro:** cualquier aplicación en producción debería usar deployment slots (viene en M2). Sin slots, rollback requiere redeploy (~minutos). Con slots, rollback es swap (~segundos).

## Slide 31 — Custom domain y SSL: bien a bulto el tema

Aunque vuestro curso usa la URL `*.azurewebsites.net`, en producción queréis dominio propio (`miapp.empresa.com`):

```bash
# 1. En vuestro registrador DNS, crear un CNAME:
#    miapp.empresa.com → appsvc-aprende-pedro.azurewebsites.net
# 
# 2. En App Service, registrar el dominio:
az webapp config hostname add \
  --webapp-name appsvc-aprende-pedro \
  --resource-group rg-aprendizaje-pedro \
  --hostname miapp.empresa.com

# 3. Obtener SSL gratis con App Service Managed Certificate
az webapp config ssl create \
  --name appsvc-aprende-pedro \
  --resource-group rg-aprendizaje-pedro \
  --hostname miapp.empresa.com

# 4. Asociarlo al dominio
az webapp config ssl bind \
  --name appsvc-aprende-pedro \
  --resource-group rg-aprendizaje-pedro \
  --certificate-thumbprint <thumbprint> \
  --ssl-type SNI
```

**Importante:** App Service Managed Certificates son GRATIS, se renuevan solos, y soportan solo SNI (no IP-based SSL). Para el 95% de los casos es lo que queréis. Para certs más específicos (wildcard, EV), compráis el cert y lo subís.

## Slide 32 — Backup y restauración: a guardar

Para SKUs Standard+ tenéis backups automáticos de la app:

```bash
# Configurar backups: necesitáis un Storage Account
az storage container create \
  --name appsvc-backups \
  --account-name stappbackups$(whoami)$(date +%s) \
  --auth-mode login

# Configurar backup diario
az webapp config backup create \
  --resource-group rg-aprendizaje-pedro \
  --webapp-name appsvc-aprende-pedro \
  --backup-name backup-diario \
  --container-url "https://stappbackups.blob.core.windows.net/appsvc-backups?sv=..." \
  --frequency 1d \
  --retention 30

# Lista de backups
az webapp config backup list \
  --resource-group rg-aprendizaje-pedro \
  --webapp-name appsvc-aprende-pedro

# Restaurar un backup
az webapp config backup restore \
  --resource-group rg-aprendizaje-pedro \
  --webapp-name appsvc-aprende-pedro \
  --container-url "..." --backup-name backup-diario-20260422
```

**Qué incluye el backup:** código + configuración. **No** incluye: datos externos (BBDD), Files Storage custom. Para un DR completo necesitáis backup de la BBDD por separado.

## Slide 2 — Tres caminos, un destino
Todo lo que se puede hacer en Azure se puede hacer de tres formas distintas:

1. **Portal de Azure** — interfaz web, visual, clic-clic
2. **Azure CLI** — línea de comandos, multiplataforma, scripts bash
3. **Azure PowerShell** — módulo PowerShell, objetos .NET, scripts avanzados

Las tres llegan al mismo sitio: la API REST de Azure Resource Manager (ARM). La diferencia es cómo interactúas con ella. El portal traduce tus clics en llamadas REST. La CLI traduce tus comandos. PowerShell hace lo mismo pero con objetos .NET.

Hay una cuarta vía (ARM REST API directa), que es lo que usan los SDKs de los lenguajes de programación. Pero en la práctica, para gestión de infraestructura, usáis una de las tres de arriba.

## Slide 3 — Azure Resource Manager: lo que hay por debajo

```
  Portal        CLI         PowerShell      SDK (.NET, Python...)
     ↓            ↓              ↓                    ↓
  ┌──────────────────────────────────────────────────────┐
  │          Azure Resource Manager (ARM)                │
  │     API REST — endpoint: management.azure.com        │
  └──────────────────────────────────────────────────────┘
                          ↓
  ┌──────────────────────────────────────────────────────┐
  │              Resource Providers                       │
  │  Microsoft.Web    Microsoft.Compute    Microsoft.Sql  │
  │  (App Service)    (VMs)                (SQL DB)       │
  └──────────────────────────────────────────────────────┘
                          ↓
  ┌──────────────────────────────────────────────────────┐
  │                  Recursos Azure                       │
  │  Web Apps, VMs, Databases, Functions, Storage...     │
  └──────────────────────────────────────────────────────┘
```

Todo pasa por ARM. Si una operación funciona en el portal pero no en CLI, el problema está en cómo CLI construye la petición REST, no en Azure. Y viceversa.

## Slide 4 — La regla del formador
Antes de entrar en detalle, una regla que os va a ahorrar mucho tiempo:

**Si haces algo más de dos veces en el portal, debería ser un script.**

El portal es perfecto para explorar, diagnosticar y aprender. Pero el momento en que te descubres repitiendo los mismos clics para crear un recurso similar al de la semana pasada, es hora de escribir un comando CLI o un template.

La automatización no es un lujo. Es la diferencia entre un entorno reproducible y uno que "solo funciona en mi cuenta porque lo configuré a mano el jueves pasado y no me acuerdo exactamente de qué hice".

## Slide 5 — Azure Portal: la interfaz web
**portal.azure.com** — donde todo el mundo empieza.

El portal es una aplicación web SPA construida con Angular que consume la API de ARM. Cada clic se traduce en una o varias llamadas REST.

**Puntos fuertes:**
- Visual e intuitivo — ves los recursos, sus relaciones, su estado
- Métricas y gráficos en tiempo real (CPU, memoria, peticiones, errores)
- Ideal para explorar servicios que no conoces
- No necesitas instalar nada — funciona en cualquier navegador moderno
- Asistentes guiados para crear recursos paso a paso

**Puntos débiles:**
- Lento para tareas repetitivas (crear 10 recursos → 10 veces el mismo formulario)
- No reproducible — no puedes "guardar" los pasos que seguiste
- Propenso a errores humanos en formularios largos
- No sirve para pipelines CI/CD
- Cambios en la UI con cada actualización de Microsoft

## Slide 6 — Anatomía del Portal: barra superior

La barra superior tiene las herramientas más útiles:

**Buscador global (o tecla `/`):**
La forma más rápida de llegar a cualquier recurso, servicio o configuración. Escribid las primeras letras y seleccionad.

**Cloud Shell (icono `>_`):**
Terminal completa en el navegador — Bash o PowerShell. Sin instalar nada.

**Notificaciones (campana):**
Estado de operaciones en curso: despliegues, creaciones, eliminaciones. Si algo falla, el error aparece aquí con detalle.

**Directorio + Suscripción (filtro):**
En qué tenant y suscripción estáis. CUIDADO: si tenéis acceso a varios tenants (formación + producción), verificad siempre que estáis en el correcto antes de hacer cambios.

**Configuración (engranaje):**
Idioma, tema (claro/oscuro), región por defecto, formato de moneda. Poned la región en "West Europe" para que los formularios de creación la preseleccionen.

## Slide 7 — Anatomía del Portal: panel lateral y blades

**Panel lateral izquierdo (menú de navegación):**
- Favoritos: personalizables. Arrastrad aquí los servicios que usáis a diario.
- Todos los servicios: catálogo completo, organizado por categoría.
- Resource groups: la vista más útil del día a día.
- Dashboards: accesos directos y métricas.

**Blades (paneles de contenido):**
El portal funciona con "blades" que se apilan a la derecha al navegar:
```
[Resource Group] → [App Service] → [Configuration] → [Edit Setting]
```

Cada blade es una "página" dentro de la navegación. Podéis cerrar blades individuales o volver atrás. Si se acumulan demasiados, la navegación se vuelve confusa — cerrad los que no necesitéis.

**Consejo:** Aprended los atajos de teclado del portal:
- `/` → Búsqueda global
- `G + R` → Ir a Resource Groups
- `G + S` → Ir a Suscripciones
- `G + /` → Ir a Todos los servicios

**Tiles útiles para vuestro día a día:**

## Slide 10 — Cloud Shell: terminal en el navegador

Cloud Shell es un terminal completo accesible desde el portal:

**Qué es técnicamente:**
Una máquina Linux (Ubuntu) efímera con almacenamiento persistente (5 GB en Azure Files). Cada vez que la abres, crea un contenedor nuevo pero monta tu carpeta personal.

**Herramientas preinstaladas:**
```
az (Azure CLI)          git
Az (PowerShell module)  vim / nano / code (Monaco)
kubectl                 terraform
docker (en algunos casos)  python3
dotnet                  node / npm
ssh / scp               curl / wget
jq                      helm
```

**Acceso:**
- Desde el portal: icono `>_` en la barra superior
- URL directa: https://shell.azure.com
- App móvil de Azure
- Terminal de Windows (preview)

**Primera vez:** Azure pide crear una cuenta de almacenamiento para persistencia (Azure Files). Coste mínimo (~0.06€/GB/mes).

## Slide 12 — Azure CLI: qué es y por qué es la herramienta principal

Azure CLI (`az`) es la herramienta de línea de comandos oficial y multiplataforma de Microsoft para Azure:

**Características clave:**
- Multiplataforma: Windows, macOS, Linux (mismo binario)
- Sintaxis consistente y predecible: `az <grupo> <acción> --parámetros`
- Salida JSON por defecto (configurable)
- Consultas integradas con JMESPath (sin dependencias externas)
- Autocompletado con Tab
- Open source: github.com/Azure/azure-cli
- Extensiones para servicios adicionales

**¿Por qué CLI y no PowerShell como herramienta principal del curso?**
- Sintaxis más corta y concisa
- Funciona igual en Bash, PowerShell, Zsh
- Los ejemplos de documentación de Microsoft usan CLI primero
- Los pipelines de Azure DevOps usan tareas basadas en CLI
- Multiplataforma sin modificaciones

## Slide 15 — Configuración de defaults (ahorra teclear)

```bash
# Configurar valores por defecto
az configure --defaults \
  group=rg-curso-azure \
  location=westeurope \
  web=mi-app

# Ahora no necesitáis pasar estos parámetros:
az webapp show  # Equivale a: az webapp show --name mi-app --resource-group rg-curso-azure

# Ver defaults actuales
az configure --list-defaults

# Eliminar un default
az configure --defaults group=""
```

**Cambiar formato de salida por defecto:**
```bash
az configure --defaults output=table
# Ahora toda la salida será en formato tabla
```

**Configuración por directorio (.azure/config):**
Podéis tener configuraciones diferentes por proyecto:
```bash
# En la raíz de un proyecto
mkdir .azure
cat > .azure/config << EOF
[defaults]
group = rg-proyecto-x
location = westeurope
EOF
```

Los defaults de directorio tienen prioridad sobre los globales. Así, al entrar en la carpeta del proyecto, CLI usa automáticamente el RG correcto.

## Slide 16 — Estructura de los comandos CLI

Todos los comandos siguen el mismo patrón predecible:

```
az <grupo> [subgrupo] <acción> --parámetros
```

**Grupos comunes:**
```bash
az group ...        # Resource Groups
az webapp ...       # Web Apps (App Service)
az functionapp ...  # Function Apps
az cosmosdb ...     # Cosmos DB
az sql ...          # Azure SQL
az storage ...      # Storage Accounts
az keyvault ...     # Key Vault
az monitor ...      # Azure Monitor
az devops ...       # Azure DevOps
```

**Acciones comunes (patrón CRUD):**
```bash
az <grupo> list     # Listar todos
az <grupo> show     # Ver detalle de uno
az <grupo> create   # Crear nuevo
az <grupo> update   # Modificar existente
az <grupo> delete   # Eliminar
```

**El truco:** Una vez que aprendéis el patrón, podéis adivinar el comando de cualquier servicio. `az cosmosdb list`, `az keyvault create`, `az sql db show`... La estructura es siempre la misma.

## Slide 19 — Formatos de salida: elige el correcto

```bash
# JSON (por defecto) — completo, ideal para scripts
az group list
# [{"name": "mi-rg", "location": "westeurope", ...}]

# Table — legible para humanos
az group list --output table
# Name          Location     Status
# -----------   ----------   ---------
# mi-rg         westeurope   Succeeded

# TSV — valores separados por tabulador, ideal para pipear
az group list --query "[].name" --output tsv
# mi-rg
# otro-rg

# YAML — alternativa legible a JSON
az group list --output yaml

# JSON con JQ (si lo tenéis instalado)
az group list | jq '.[].name'

# JSONC — JSON con colores en terminal
az group list --output jsonc
```

**Cuándo usar cada uno:**
- `table` → consultas rápidas en terminal
- `tsv` → scripts que pipean a otros comandos (`for rg in $(az group list -q "[].name" -o tsv); do ... done`)
- `json` → scripts que necesitan parsear la salida completa
- `jsonc` → depuración visual

## Slide 20 — JMESPath: consultas integradas

El flag `--query` usa JMESPath para filtrar y transformar la salida. Es la feature más potente de CLI y la menos conocida:

**Seleccionar un campo:**
```bash
az account show --query name --output tsv
# mi-suscripcion
```

**Seleccionar múltiples campos con alias:**
```bash
az resource list --resource-group mi-rg \
  --query "[].{nombre:name, tipo:type, region:location}" \
  --output table
```

**Filtrar por condición:**
```bash
# Apps que están corriendo
az webapp list \
  --query "[?state=='Running'].{nombre:name, url:defaultHostName}" \
  --output table

# Recursos de tipo Web App
az resource list --resource-group mi-rg \
  --query "[?type=='Microsoft.Web/sites'].name" \
  --output tsv
```

**Primer elemento:**
```bash
az webapp list --query "[0].defaultHostName" --output tsv
```

**Contar:**
```bash
az resource list --resource-group mi-rg --query "length(@)"
```

## Slide 21 — JMESPath avanzado: patrones útiles

**Filtro con contains (búsqueda parcial):**
```bash
# Recursos cuyo nombre contiene "prod"
az resource list \
  --query "[?contains(name, 'prod')].{nombre:name, tipo:type}" \
  --output table
```

**Filtro con starts_with / ends_with:**
```bash
az resource list \
  --query "[?starts_with(name, 'app-')].name" \
  --output tsv
```

**Múltiples condiciones (AND):**
```bash
az resource list --resource-group mi-rg \
  --query "[?type=='Microsoft.Web/sites' && tags.entorno=='prod'].name" \
  --output tsv
```

**Ordenar resultados:**
```bash
az resource list --resource-group mi-rg \
  --query "sort_by([],&name)[].{nombre:name, tipo:type}" \
  --output table
```

**Acceder a propiedades anidadas:**
```bash
az webapp show --name mi-app --resource-group mi-rg \
  --query "{nombre:name, runtime:siteConfig.netFrameworkVersion, always_on:siteConfig.alwaysOn}" \
  --output table
```

JMESPath parece críptico al principio, pero en cuanto lo pilláis os ahorra instalar jq y escribir pipes complicados. El filtrado va dentro del propio comando de Azure.

## Slide 22 — Scripts reales: inventario de recursos

```bash
#!/bin/bash
# inventario-azure.sh — Genera inventario completo

echo "================================================"
echo "  INVENTARIO AZURE — $(date +'%Y-%m-%d %H:%M')"
echo "  Suscripción: $(az account show --query name -o tsv)"
echo "================================================"

for rg in $(az group list --query "[].name" -o tsv); do
  count=$(az resource list --resource-group $rg --query "length(@)")
  if [ "$count" -gt 0 ]; then
    echo ""
    echo "--- $rg ($count recursos) ---"
    az resource list --resource-group $rg \
      --query "[].{Nombre:name, Tipo:kind, Ubicacion:location}" \
      --output table
  fi
done

echo ""
echo "================================================"
echo "  RESUMEN"
echo "  Total RGs: $(az group list --query 'length(@)')"
echo "  Total recursos: $(az resource list --query 'length(@)')"
echo "================================================"
```

Este script reemplaza 15 minutos de navegación por el portal. Lo ejecutáis, lo guardáis, lo metéis en un cron si queréis un informe diario.

## Slide 26 — CLI vs PowerShell: equivalencias

| Acción | Azure CLI | PowerShell |
|--------|-----------|------------|
| Login | `az login` | `Connect-AzAccount` |
| Ver cuenta | `az account show` | `Get-AzContext` |
| Listar RGs | `az group list` | `Get-AzResourceGroup` |
| Crear RG | `az group create -n x -l y` | `New-AzResourceGroup -Name x -Location y` |
| Eliminar RG | `az group delete -n x --yes` | `Remove-AzResourceGroup -Name x -Force` |
| Listar apps | `az webapp list` | `Get-AzWebApp` |
| Ver app | `az webapp show -n x -g y` | `Get-AzWebApp -Name x -ResourceGroupName y` |
| Config app | `az webapp config show -n x -g y` | `Get-AzWebApp -Name x -RGN y \| Select SiteConfig` |
| Reiniciar | `az webapp restart -n x -g y` | `Restart-AzWebApp -Name x -ResourceGroupName y` |
| Desplegar | `az webapp deploy --src-path x.zip` | `Publish-AzWebApp -ArchivePath x.zip` |

La sintaxis de PowerShell es más verbosa pero los nombres son más descriptivos. `Get-AzResourceGroup` se lee mejor que `az group list`.

## Slide 27 — PowerShell: ventajas únicas

PowerShell tiene capacidades que CLI no tiene:

**Objetos, no texto:**
```powershell
# En CLI, la salida es texto/JSON que parseas con strings
# En PowerShell, la salida es un OBJETO .NET

$app = Get-AzWebApp -Name mi-app -ResourceGroupName mi-rg
$app.State                    # Propiedad del objeto
$app.SiteConfig.AlwaysOn      # Propiedad anidada
$app.HostNames | ForEach-Object { "URL: $_" }  # Iterar
```

**Pipeline con objetos:**
```powershell
# Obtener todas las apps paradas y reiniciarlas
Get-AzWebApp | Where-Object { $_.State -eq "Stopped" } |
  ForEach-Object { 
    Write-Host "Reiniciando $($_.Name)..."
    Start-AzWebApp -Name $_.Name -ResourceGroupName $_.ResourceGroup
  }
```

**Lógica compleja:**
```powershell
# Script con manejo de errores, logging y notificaciones
try {
    $rg = Get-AzResourceGroup -Name "rg-prod"
    $resources = Get-AzResource -ResourceGroupName $rg.ResourceGroupName
    
    foreach ($r in $resources) {
        if (-not $r.Tags.ContainsKey("responsable")) {
            Write-Warning "Sin responsable: $($r.Name)"
        }
    }
} catch {
    Send-MailMessage -To "admin@empresa.com" -Subject "Error Azure" -Body $_.Exception.Message
}
```

## Slide 28 — CLI vs PowerShell: cuándo usar cada uno

**Elegid Azure CLI si:**
- Trabajáis en entornos mixtos (Windows + macOS + Linux)
- Vuestros pipelines son YAML (Azure DevOps, GitHub Actions)
- Preferís scripts bash concisos y rápidos
- Queréis la sintaxis más corta posible

**Para este curso:** CLI como herramienta principal. Cada comando tiene su equivalente en PowerShell, así que quien prefiera PowerShell puede seguir las prácticas con él.

## Slide 30 — Más allá de CLI: el camino hacia Infrastructure as Code

CLI y PowerShell son el paso intermedio. El destino final es Infrastructure as Code (IaC):

**Nivel 1 — Imperativo (CLI):**
```bash
az group create --name mi-rg --location westeurope
az webapp create --name mi-app --resource-group mi-rg --plan mi-plan
```
Problema: dice "haz esto". Si ya existe, puede fallar o duplicar.

**Nivel 2 — Declarativo (Bicep):**
```bicep
resource appServicePlan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: 'mi-plan'
  location: resourceGroup().location
  sku: { name: 'S1' }
}

resource webApp 'Microsoft.Web/sites@2023-12-01' = {
  name: 'mi-app'
  location: resourceGroup().location
  properties: {
    serverFarmId: appServicePlan.id
  }
}
```
Dice "quiero que esto exista". Si ya existe, verifica que está como lo describes. Si falta algo, lo crea. Si sobra algo, lo elimina.

**Nivel 3 — IaC + Pipeline:**
El template Bicep está en un repo. Un pipeline lo aplica automáticamente al hacer push. Los entornos dev, staging y prod se crean con el mismo template y parámetros diferentes.

IaC lo cubrimos en profundidad en el módulo 8.

## Slide 34 — Activity Log: auditoría de lo que pasa en Azure

El Activity Log registra TODAS las operaciones de gestión en Azure:

```bash
# Ver últimas operaciones en un RG
az monitor activity-log list \
  --resource-group mi-rg \
  --query "[].{operacion:operationName.localizedValue, estado:status.localizedValue, quien:caller, cuando:eventTimestamp}" \
  --output table

# Filtrar por operaciones fallidas
az monitor activity-log list \
  --resource-group mi-rg \
  --query "[?status.value=='Failed'].{op:operationName.localizedValue, error:subStatus.localizedValue, quien:caller}" \
  --output table
```

**¿Para qué sirve?**
- "¿Quién eliminó este recurso?" → Activity Log
- "¿Por qué falló esta operación?" → Activity Log con detalle del error
- "¿Qué cambios se hicieron ayer en producción?" → Activity Log filtrado por fecha

Retención: 90 días en el Activity Log. Si necesitáis más, exportadlo a Log Analytics.

## Slide 35 — Azure Resource Graph: KQL sobre tus recursos

Azure CLI es bueno pero tiene un límite: **iterar un recurso cada vez**. Cuando queréis buscar cosas **cross-subscription** o **con criterios complejos**, necesitáis Resource Graph.

```bash
# Resource Graph usa KQL (Kusto Query Language)
# Busca en tus recursos de Azure como si fueran una tabla

# Ejemplo 1: todos los App Services sin HTTPS forzado, en cualquier suscripción
az graph query -q "
Resources
| where type == 'microsoft.web/sites'
| where properties.httpsOnly == false
| project name, resourceGroup, subscriptionId, location
"

# Ejemplo 2: storage accounts con acceso público habilitado (riesgo seguridad)
az graph query -q "
Resources
| where type == 'microsoft.storage/storageaccounts'
| where properties.allowBlobPublicAccess == true
| project name, resourceGroup, subscriptionId
"

# Ejemplo 3: agrupación — recursos por región y tipo
az graph query -q "
Resources
| summarize count=count() by location, type
| order by count desc
"

# Ejemplo 4: recursos sin tags obligatorios
az graph query -q "
Resources
| where isnull(tags.environment) or isnull(tags.project)
| project id, name, type, resourceGroup
"
```

**Para qué:** inventarios rápidos, auditorías de seguridad, búsquedas cross-subscription. Si haceís algo tipo "¿cuántos X tengo en toda mi empresa?", Resource Graph. Si es una operación sobre UN recurso, az CLI normal.

## Slide 36 — az rest: cuando no hay comando específico

A veces queréis hacer algo que el CLI no tiene en su catálogo. **`az rest`** os permite llamar directamente a la API REST de Azure Resource Manager con autenticación automática:

```bash
# Llamada genérica: GET sobre recurso
az rest --method GET \
  --uri "https://management.azure.com/subscriptions/<sub-id>/resourceGroups/rg-ventas-dev?api-version=2021-04-01"

# POST con body
az rest --method POST \
  --uri "https://management.azure.com/..../restart?api-version=2022-03-01" \
  --body '{"force": true}'

# Llamada con headers custom
az rest --method GET \
  --uri "https://graph.microsoft.com/v1.0/me/messages" \
  --headers "Content-Type=application/json" \
  --resource "https://graph.microsoft.com/"
```

**Casos típicos:**
- Features nuevas de Azure que aún no están en az CLI
- Propiedades específicas de un recurso no expuestas
- Hacer llamadas a Microsoft Graph (Entra ID) o Cost Management APIs
- Construir scripts de governance complejos

**Útil saber:** `az rest` maneja la auth por ti. No tienes que gestionar tokens manualmente.

## Slide 37 — Multi-subscription: trabajar con varias suscripciones

Cuando vuestra empresa tiene 3-5 suscripciones (dev, staging, prod, shared-services), cambiar entre ellas es habitual:

```bash
# Listar suscripciones a las que tienes acceso
az account list --query "[].{name:name, id:id, state:state}" -o table

# Cambiar de suscripción activa
az account set --subscription "Ventas-Prod"

# Mostrar la suscripción actual
az account show --query "{name:name, id:id}" -o table

# Ejecutar un comando sin cambiar la activa (con --subscription)
az resource list --subscription "Ventas-Dev" -o table

# Script útil: ejecutar el mismo comando en todas tus suscripciones
for SUB in $(az account list --query "[].id" -o tsv); do
  echo "=== Suscripción: $SUB ==="
  az account set --subscription "$SUB"
  az resource list --query "length(@)" -o tsv
done

# Alias para cambio rápido (.bashrc / .zshrc)
alias azdev="az account set --subscription 'Ventas-Dev'"
alias azprod="az account set --subscription 'Ventas-Prod'"
```

**Regla de seguridad:** antes de comandos destructivos (delete, purge), **siempre** verifica con `az account show` que estás en la sub correcta. Borrar un RG "dev" en la sub de prod es un clásico de los errores de fin de semana.

## Slide 39 — Service Principals: autenticación para scripts y CI/CD

Hasta ahora habéis visto `az login` interactivo. Para automatización, no podéis depender de vuestro usuario humano — necesitáis un **Service Principal (SP)**:

```bash
# Crear Service Principal (usuario "robot" con permisos específicos)
az ad sp create-for-rbac \
  --name "sp-ventas-deploy-pipeline" \
  --role "Contributor" \
  --scopes "/subscriptions/<sub-id>/resourceGroups/rg-ventas-dev"

# Output (SOLO se muestra una vez — guárdalo bien):
# {
#   "appId": "...",           ← clientId
#   "displayName": "...",
#   "password": "...",         ← clientSecret (NO mostrado después)
#   "tenant": "..."
# }

# Login con el SP (en un pipeline, script, o Docker container)
az login --service-principal \
  -u "<appId>" \
  -p "<password>" \
  --tenant "<tenant>"

# En el pipeline de ADO o GitHub Actions:
# Guardáis estos 3 valores como secrets
# El pipeline los usa para autenticarse sin intervención humana
```

**Importante:** El `password` solo se muestra **una vez**. Si lo perdéis, hay que rotar. Guardadlo en Key Vault o en los secrets del pipeline inmediatamente.

**Mejor en 2026:** usad **Federated Credentials (OIDC)** en vez de password. El pipeline se autentica con una identidad federada (no hay secreto almacenado). Lo veréis en M8.

## Slide 40 — az login alternativas: device code, identity, federated

Hay 4 formas principales de autenticarse a Azure CLI según el contexto:

```bash
# 1. Interactive (lo habitual — abre navegador)
az login

# 2. Device code (cuando no hay navegador — SSH a servidor remoto, Codespaces sin popup)
az login --use-device-code
# Te muestra: "Go to https://microsoft.com/devicelogin and enter code: ABCD1234"

# 3. Service Principal (scripts, pipelines)
az login --service-principal -u <appId> -p <password> --tenant <tenantId>

# 4. Managed Identity (cuando el CLI corre DENTRO de Azure — VM, Function, Container)
az login --identity
# Sin credenciales, Azure mismo identifica al recurso

# Bonus: desde WSL usando tokens de Windows
az login --use-device-code  # más fiable en WSL
```

**Tabla de decisión:**

| Contexto | Método recomendado |
|---|---|
| Dev en tu laptop | `az login` (interactive) |
| SSH en VM/servidor | `az login --use-device-code` |
| GitHub Codespaces | `az login` con OAuth integrado |
| Pipeline ADO/GitHub | Service Principal (pronto Federated OIDC) |
| Script corriendo en Azure | `az login --identity` (Managed Identity) |
| Contenedor Docker en Azure | `az login --identity` |

## Slide 41 — Exportar ARM templates desde recursos existentes

Si creáis algo a mano en el portal y luego queréis convertirlo a IaC:

```bash
# Exportar un Resource Group completo a ARM JSON
az group export --name rg-ventas-dev > exported-arm.json

# Exportar un recurso específico
az resource show \
  --ids "/subscriptions/.../sites/appsvc-ventas" \
  --query "." \
  -o json > app-service-export.json

# Convertir ARM a Bicep (mucho más legible)
az bicep decompile --file exported-arm.json
# Genera exported-arm.bicep junto al JSON
```

**Qué esperar del export:**
- ARM exportado es **verboso**: muchas propiedades default, valores hardcoded
- Necesita **limpieza**: parametrizar nombres, SKUs, ubicaciones
- **No siempre es ejecutable tal cual**: algunas propiedades read-only vienen incluidas
- **Buen punto de partida**: usadlo + refinamiento manual

**Pipeline típico:**
1. Crear recurso en portal para entender qué propiedades necesita
2. `az group export` → ARM JSON
3. `az bicep decompile` → Bicep
4. Limpiar (eliminar read-only, parametrizar, añadir comentarios)
5. Modularizar en main.bicep + modules/
6. Commit al repo como IaC

## Slide 43 — Azure Mobile App: gestionar desde el móvil

La app Azure Mobile (iOS/Android) no es para desarrollar, pero sí útil para **ops on-call**:

**Tip:** configurad notificaciones push para alertas críticas de vuestros recursos. Más rápido que emails.

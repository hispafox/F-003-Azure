## Slide 2 — Contexto: IA para desarrollo en 2026
La IA generativa ha cambiado cómo se escribe código. No reemplaza al desarrollador — amplifica su capacidad. Claude Code es una herramienta de línea de comandos que pone un agente IA directamente en vuestro terminal, con acceso al filesystem, git, y herramientas externas vía MCP.

**Lo que Claude Code puede hacer:**
- Generar código a partir de descripciones en lenguaje natural
- Refactorizar código existente
- Escribir tests para código existente
- Crear archivos Bicep/YAML/Dockerfile desde especificaciones
- Depurar errores analizando logs y stack traces
- Ejecutar comandos y analizar resultados

```bash
# Instalar (requiere Node.js 18+)
npm install -g @anthropic-ai/claude-code

# Verificar

# Autenticar (obtener API key en console.anthropic.com)

# O con variable de entorno
export ANTHROPIC_API_KEY="sk-ant-..."
```

**Requisitos:** Node.js 18+, terminal (bash, zsh, PowerShell), cuenta Anthropic con API key.

## Slide 5 — Claude Code vs GitHub Copilot: diferencias clave

| | Claude Code | GitHub Copilot |
|---|:---:|:---:|
| **Modelo** | Claude (Anthropic) | GPT-4/Codex (OpenAI) |
| **Interfaz** | Terminal (CLI) | IDE (VS Code, JetBrains) |
| **Contexto** | Proyecto completo | Archivo actual + vecinos |
| **Agente** | Sí (ejecuta comandos, edita archivos) | Parcial (Copilot Workspace) |
| **MCP** | Sí (conecta con herramientas) | No |
| **Multi-archivo** | Sí (edita N archivos en un paso) | Limitado |
| **Ejecución** | Puede ejecutar build, test, deploy | No (solo genera código) |
| **Coste** | API usage (~$10-50/mes) | $10-19/mes (fijo) |

**No son excluyentes.** Copilot para autocompletado en el IDE. Claude Code para tareas más grandes (generar módulos, refactorizar, IaC, debugging).

## Slide 16 — Claude Code en CI/CD: automatización

```yaml
# Pipeline step: Code review automático con Claude Code
- script: |
    # Obtener diff del PR
    git diff origin/main...HEAD > changes.diff
    
    # Análisis con Claude Code
    cat changes.diff | claude -p "Revisa este diff y reporta:
    1. Problemas de seguridad (crítico)
    2. Problemas de rendimiento (medio)
    3. Violaciones de convenciones (bajo)
    Formato: JSON con {severity, file, line, description}" \
    --no-interactive > review.json
    
    # Verificar si hay problemas críticos
    CRITICAL=$(cat review.json | jq '[.[] | select(.severity=="critical")] | length')
    if [ "$CRITICAL" -gt 0 ]; then
      echo "##vso[task.logissue type=error]$CRITICAL critical issues found"
      cat review.json | jq '.[] | select(.severity=="critical")'
      exit 1
    fi
  displayName: 'AI Code Review'
```

## Slide 18 — Subagents: paralelizar tareas con contexto aislado

Subagents (2026) son Claudes especializados que ejecutan tareas en su propio contexto:

```
Sin subagents:
└── Main Claude
    ├── Hace 10 greps para encontrar algo (consume tokens)
    ├── Lee 20 archivos (consume tokens)
    ├── Ejecuta tests (consume tokens)
    └── Resultado: contexto saturado, prompts caros

Con subagents:
└── Main Claude (tech lead)
    ├── Delega a code-reviewer agent ──→ revisa, devuelve resumen
    ├── Delega a test-runner agent ──→ ejecuta, devuelve resumen
    └── Delega a security-auditor agent ──→ analiza, devuelve resumen
        ↓
    Solo recibe los resúmenes (poco contexto, mucha info)
```

**Crear un subagent custom:**

```bash
# Estructura: .claude/agents/code-reviewer.md (proyecto)
# O ~/.claude/agents/code-reviewer.md (personal)

cat > .claude/agents/code-reviewer.md << 'EOF'
---
name: code-reviewer
description: Expert code review specialist. Proactively reviews code for quality, security, and maintainability. Use immediately after writing or modifying code.
tools: Read, Grep, Glob, Bash
model: sonnet
---

You are a senior code reviewer ensuring high standards of code quality and security.

When reviewing code:
1. Check for security vulnerabilities (SQL injection, XSS, secrets in code)
2. Verify error handling is comprehensive
3. Identify performance bottlenecks
4. Suggest refactoring opportunities
5. Check naming conventions and readability
6. Verify tests exist for new code

Output format:
- Critical issues (must fix)
- Warnings (should fix)
- Suggestions (nice to have)
- Each finding: file:line, current code, recommended change
EOF
```

**Subagent built-in útiles (auto-invocados):**

| Subagent | Para qué |
|---|---|
| **Explore** | Fast read-only, busca "dónde está X" |
| **Plan** | Research-only, scan codebase para planning |
| **General-purpose** | Heavy lifter, read/write/execute |
| **Claude Code Guide** | Documentación experta sobre features de CC |

**Invocar subagents manualmente:**
```bash

```

**Frontmatter completo (todos los campos):**
```yaml

**Casos de uso reales para tu equipo:**

```
1. Architecture explorer:
   .claude/agents/architecture-explorer.md
   - Mapea dependencies entre microservicios
   - Identifica patrones (CQRS, event sourcing, etc.)
   - Documenta findings en .claude/agent-memory/

2. Test runner especializado:
   .claude/agents/test-runner.md
   - Ejecuta tests con ambiente específico
   - Captura logs si fallan
   - Sugiere fixes basados en stack traces

3. Database analyst:
   .claude/agents/db-analyst.md
   - Solo permite SELECTS (read-only)
   - Hook PreToolUse valida queries
   - Genera reports de performance

4. Migration assistant:
   .claude/agents/migration-helper.md
   - Especializado en EF Core migrations
   - Knowledge sobre expand-contract pattern
   - Genera scripts SQL idempotentes
```

**Reglas para diseñar buenos subagents:**
- ✅ **Una responsabilidad clara** (no jack-of-all-trades)
- ✅ **Tools mínimas** (least privilege)
- ✅ **Output structured** (predecible)
- ✅ **Context isolation** (no contamina main thread)
- ❌ NO subagents para tareas single-step (overhead innecesario)
- ❌ NO subagents para tareas que necesitan toda la conversación

**ROI real:**
```
Sin subagents:
├── 1h sesión Claude Code
├── Context saturado al 70%
├── 1 tarea exploratoria + 1 implementación
└── Coste: 5€ tokens

Con subagents:
├── 1h sesión Claude Code
├── Context al 30% (delegado)
├── 5 tareas exploratorias + 3 implementaciones (paralelas)
└── Coste: 4€ tokens (cheaper + 8x throughput)
```

## Slide 19 — Hooks: control determinista del ciclo de vida

Hooks son scripts que se ejecutan en momentos específicos del lifecycle de Claude Code:

```
25 lifecycle hooks. Los más importantes:

BLOQUEANTES (pueden detener acciones):
├── UserPromptSubmit    → Antes de que Claude vea tu prompt
├── PreToolUse          → Antes de cualquier tool execution ⭐
├── PermissionRequest   → Cuando Claude pide permisos
├── Stop / SubagentStop → Cuando Claude termina
└── PreCompact          → Antes de compactación de contexto

INFORMATIVOS (loggean, notifican):
├── SessionStart / SessionEnd
├── PostToolUse / PostToolUseFailure
├── SubagentStart
└── Notification
```

**Configurar hook en settings.json:**
```json
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash ./scripts/validate-bash-cmd.sh"
          }
        ]
      },
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "bash ./scripts/check-file-permissions.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "bash ./scripts/auto-format.sh"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash ./scripts/load-project-context.sh"
          }
        ]
      }
    ]
  }
}
```

**Hook recibe JSON via stdin:**
```bash
#!/bin/bash
# scripts/validate-bash-cmd.sh

# Claude Code pasa input como JSON
INPUT=$(cat)

# Extract command que Claude quiere ejecutar
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

# Validar
if echo "$COMMAND" | grep -E "rm -rf|sudo|format|drop database" > /dev/null; then
  echo "❌ BLOCKED: Dangerous command detected: $COMMAND" >&2
  exit 2  # Exit 2 = block + return error to Claude
fi

# Log
echo "$(date) - Command: $COMMAND" >> ~/.claude/audit.log

exit 0  # Permitir
```

**Casos prácticos para enterprise:**

**Hook 1 — Block secrets accidentales:**
```bash
#!/bin/bash
# scripts/block-secrets.sh
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path')
NEW_CONTENT=$(echo "$INPUT" | jq -r '.tool_input.new_content // .tool_input.content')

# Detect patterns peligrosos
if echo "$NEW_CONTENT" | grep -E "(api[_-]?key|password|secret|token).{0,5}=.{0,5}['\"][^'\"]{15,}['\"]" -i; then
  echo "❌ BLOCKED: Possible secret in $FILE_PATH" >&2
  echo "Use environment variables or Key Vault references" >&2
  exit 2
fi

exit 0
```

**Hook 2 — Auto-format después de Edit:**
```bash
#!/bin/bash
# scripts/auto-format.sh
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path')

case "$FILE_PATH" in
  *.cs)
    dotnet format "$FILE_PATH" 2>/dev/null
    ;;
  *.ts|*.tsx|*.js|*.jsx)
    npx prettier --write "$FILE_PATH" 2>/dev/null
    ;;
  *.bicep)
    az bicep format --file "$FILE_PATH" 2>/dev/null
    ;;
esac

exit 0
```

**Hook 3 — Load context al inicio:**
```bash
#!/bin/bash
# scripts/load-project-context.sh
# Inyecta context de la sesión anterior

cat << EOF
# Previous session context
- Last branch: $(git branch --show-current)
- Last commit: $(git log -1 --oneline)
- Open issues: $(gh issue list --limit 5 --json number,title -q '.[] | "#\(.number) \(.title)"')
- Recent changes: $(git diff --stat HEAD~5)

EOF
```

**Hook 4 — PR validation antes de commit:**
```bash
#!/bin/bash
# scripts/pre-commit-validation.sh
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')

if [[ "$COMMAND" =~ ^git\ commit ]]; then
  # Run linters
  dotnet build 2>/dev/null || { echo "Build failed"; exit 2; }
  dotnet test --no-build 2>/dev/null || { echo "Tests failed"; exit 2; }
  
  # Check no secrets
  git diff --staged | grep -E "password|secret|api_key" -i && {
    echo "Secrets detected"; exit 2;
  }
fi

exit 0
```

**Exit codes que entiende Claude:**
```
exit 0   → Permitir (success)
exit 1   → Error genérico (Claude continúa pero ve el error)
exit 2   → BLOQUEAR + mensaje a Claude
         → Claude reformula su approach
otro     → Tratar como exit 1
```

**Stdout vs stderr:**
- **stdout** → Información para Claude (logs, contexto)
- **stderr** → Error message (cuando exit 2)

**Project vs Personal hooks:**
```
.claude/settings.json (proyecto)
   ├── Compartido vía git con el equipo
   ├── Aplica solo en este proyecto
   └── Best for: team policies

~/.claude/settings.json (personal)
   ├── Privado a tu máquina
   ├── Aplica en TODOS los proyectos
   └── Best for: tu workflow personal
```

**Beneficios reales:**
- ✅ **Determinístico** (no depende de que Claude entienda instrucciones)
- ✅ **Auditable** (logs completos de acciones)
- ✅ **Compliance** (enforcement automático)
- ✅ **Quality gates** automáticos (formato, tests, security)

## Slide 20 — Skills: workflows reutilizables (lo que antes eran commands)

**En 2026, slash commands y skills se unificaron.** Skills es el approach moderno:

```
.claude/skills/ (proyecto, compartido vía git)
~/.claude/skills/ (personal)

Estructura:
.claude/skills/
├── deploy-staging/
│   └── SKILL.md          ← El skill principal
├── code-review/
│   ├── SKILL.md
│   └── helpers.sh         ← Scripts adicionales
└── pr-template/
    ├── SKILL.md
    └── template.md
```

**Crear un skill básico:**
```markdown
<!-- .claude/skills/deploy-staging/SKILL.md -->
---
name: deploy-staging
description: Deploy current branch to staging environment with full validation
user-invocable: true              # Aparece en /menu
disable-model-invocation: true   # Solo manual (no auto)
tools: [Bash, Read]
---

# Deploy to Staging

## Steps
1. Verify clean working directory
   ```bash
   git status --porcelain
   ```
2. Run all tests
   ```bash
   dotnet test --no-build
   ```
3. Build release artifacts
   ```bash
   dotnet publish -c Release -o ./publish
   ```
4. Deploy to staging slot
   ```bash
   az webapp deploy \
     --name app-curso-prod \
     --slot staging \
     --resource-group rg-curso-prod \
     --src-path ./publish.zip
   ```
5. Run smoke tests
6. Report status

## Failure Recovery
If any step fails, report the error and suggest fixes.
Do NOT proceed to subsequent steps.
```

```bash

# Auto-invocación (si disable-model-invocation: false)

## Slide 21 — Plan Mode: pensar antes de actuar

Plan Mode (Shift+Tab dos veces) cambia el comportamiento de Claude Code:

```
Modo normal:
└── Claude actúa inmediatamente
    └── Cambios reales en files
    └── Ejecuta comandos
    └── Útil para: cambios pequeños, edits rápidos

Plan Mode:
└── Claude SOLO investiga + planifica
    ├── Lee archivos (read-only)
    ├── Analiza estructura
    ├── Propone plan detallado
    └── NO modifica nada hasta tu aprobación
```

**Cuándo usar Plan Mode:**

| Situación | Plan Mode |
|---|:---:|
| "Refactor the auth system" | ✅ |
| "Fix this typo on line 12" | ❌ |
| "Implement the new payment flow" | ✅ |
| "Format this file" | ❌ |
| "Migrate from EF6 to EF Core 8" | ✅ |
| "Add a comment here" | ❌ |
| Cambios en > 5 archivos | ✅ |
| Cambios irreversibles (DB, prod config) | ✅ |

**Activar Plan Mode:**
```bash
# Toggle: Shift+Tab dos veces
# O en settings:
{
  "permissionMode": "plan"  # Default por sesión
}
```

**Workflow típico:**
```
1. Activas Plan Mode (Shift+Tab Shift+Tab)
2. Le das tarea compleja a Claude:
   > Migra Order.cs a usar el nuevo IOrderItemsValidator
     extraído del refactor del CreateOrderHandler

3. Claude planifica:
   📋 Plan:
   1. Read Order.cs (current state)
   2. Read IOrderItemsValidator definition
   3. Identify all usages of old validation logic
   4. Propose changes:
      - Order.cs: 12 lines modified
      - Tests/OrderTests.cs: 5 new tests
      - Validators/OrderItemsValidator.cs: new file
   5. Verify tests pass
   
   ¿Apruebas este plan?

4. Tu revisas:
   ✅ Approve → Claude ejecuta
   ❌ Modify → "Add also unit tests for edge case X"
   🔄 Refine → Claude actualiza plan

5. Approval → Plan ejecutado paso a paso
```

**Plan Mode + Plan subagent:**
```bash
# Plan Mode activa automáticamente el "Plan" subagent
# (read-only, optimized para planning)

# Result:
# - Main context limpio (no consume tokens explorando)
# - Plan structured devuelto
# - User puede review antes de actuar
```

**Casos donde Plan Mode salva la vida:**

**Caso 1: Refactor masivo**
```
Sin Plan Mode:
└── Claude empieza a editar 20 archivos
    └── A mitad descubre patrón inesperado
    └── Queda inconsistente
    └── Cuesta horas debug

Con Plan Mode:
└── Claude analiza primero TODO el codebase
    └── Detecta el patrón inesperado en planning
    └── Propone enfoque que lo maneja
    └── Ejecución consistente
```

**Caso 2: Database migration**
```
Sin Plan Mode:
└── Claude crea migration
    └── Pero no consideró FK constraints
    └── Migration falla en mitad
    └── Database en estado inconsistente

Con Plan Mode:
└── Claude analiza schema completo
    └── Identifica todas las dependencies
    └── Propone migration con orden correcto
    └── Tu aprueba antes de ejecutar
```

**Caso 3: Production config**
```
Sin Plan Mode:
└── Claude modifica appsettings.json
    └── Pero rompe sin querer un secret reference
    └── Deploy falla en prod
    └── Rollback necesario

Con Plan Mode:
└── Claude muestra exactos cambios propuestos
    └── Tu detectas el secret reference
    └── Le pides preserve
    └── Ejecuta safe
```

**Tips para mejor planning:**
```
✅ Da context completo al inicio
   ❌ "Fix the bug"
   ✅ "Fix the bug in OrderService.CreateOrder where 
       items count > 100 throws InvalidOp. Should split."

✅ Específico el "done state"
   ❌ "Make it better"
   ✅ "Reduce response time of /api/products from 2s to <500ms 
       with caching strategy"

✅ Pide alternativas en el plan
   ✅ "Plan 3 approaches and recommend one"

✅ Approval explícito antes de ejecutar
   ✅ "Don't execute yet. Show me the plan first."
```

**Plan Mode + permissions:**

Modelos 2026 (en orden de capacidad y coste):

│   ├── Debugging difícil
│   ├── Decisiones críticas
│   └── Code review riguroso
└── Speed: medium

SONNET 4.6 (default, balanced)
├── Coste: $$ ($3 / $15 / 1M tokens)
├── Best for:
│   ├── Coding diario (90% de casos)
│   ├── Implementations standard
│   ├── Bug fixes
│   ├── Tests
│   └── Documentation
└── Speed: fast

HAIKU 4.5 (más rápido, más barato)
├── Coste: $ ($0.80 / $4 / 1M tokens)
├── Best for:
│   ├── File search (Explore subagent)

**Caso uso 1: Auto-fix failed tests en CI:**
```yaml
# .github/workflows/auto-fix-tests.yml
name: Auto-fix failing tests

on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
    
jobs:
  auto-fix:
    if: github.event.workflow_run.conclusion == 'failure'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Claude Code
        uses: anthropic/setup-claude-code@v1
        with:
          api-key: ${{ secrets.ANTHROPIC_API_KEY }}
      
      - name: Run Claude Code to fix tests
        run: |
          npx @anthropic-ai/claude-code-sdk run \
            --prompt "Run failing tests and fix them. \
                      Don't change test assertions, fix the implementation. \
                      If unsure, add // TODO comments." \
            --model claude-sonnet-4-6 \
            --max-turns 30 \
            --tools Read,Edit,Bash \
            --output-format json > fix-result.json
      
      - name: Create PR with fixes
        if: success()
        uses: peter-evans/create-pull-request@v6
        with:
          title: "Auto-fix: failing tests"
          body: |
            Claude Code attempted to fix failing tests.
            
            Files modified: $(jq -r '.filesModified | length' fix-result.json)
            
            ⚠️ Review carefully before merging.
          branch: auto-fix/tests-${{ github.run_number }}
```

## Slide 27 — Extended thinking: razonamiento profundo

Extended thinking permite a Claude pensar más antes de responder (problemas complejos):

```
Default mode:
└── Claude responde inmediatamente
    └── Buena para: tareas comunes
    
Extended thinking:
└── Claude piensa internamente PRIMERO
    ├── Considera multiple approaches
    ├── Evalúa trade-offs
    ├── Valida assumptions
    └── Después responde con mejor solución
```

**Activar extended thinking:**
```bash
# En Claude Code
> /thinking high
> Tu tarea compleja aquí

# Niveles disponibles:
> /thinking minimal  # Quick (default)
> /thinking low      # Some thinking
> /thinking medium   # Moderate
> /thinking high     # Deep thinking
> /thinking extreme  # Maximum (slow but thorough)
```

**Cuándo USAR extended thinking:**

```
✅ Architecture decisions complejas
   "Should we use event sourcing or CQRS for the order service?"

✅ Debugging difícil con poca info
   "Tests fail intermittently in CI but not locally. Why?"

✅ Performance optimization
   "Cómo optimizar esta query que tarda 5s?"

✅ Refactoring legacy con muchas dependencies
   "Cómo extraer este monolito a microservicios?"

✅ Mathematical/logical reasoning
   "Diseñar algoritmo de routing óptimo"

✅ Security analysis
   "Audita este código por vulnerabilities"
```

**Cuándo NO usar:**
```
❌ Tareas simples (es overkill, gasta tokens)
❌ Cuando ya sabes la respuesta
❌ Generación de código boilerplate
❌ Find/replace simple
```

**Comparación de output:**

**Casos reales:**

**Caso 1: Performance debugging**
```bash
> /thinking high
> 
> The /api/orders endpoint went from 200ms to 3s after the deploy.
> The deploy added a new Order.Items navigation property.
> 
> What's causing this and how to fix?

Thinking:
"This sounds like the N+1 query problem. EF Core lazily 
loads navigation properties by default. If we now access 
order.Items in the response, EF executes a separate query 
PER order...

For 100 orders: 1 + 100 = 101 queries instead of 1 with JOIN.

Options:
1. Eager loading: .Include(o => o.Items)
2. Explicit loading: .Load() before serialization  
3. Projection: .Select(o => new { ...., Items = ... })

Best is projection because:
- Loads only needed columns
- Single query
- No tracking overhead"

Response:
"Likely N+1 query issue. The fix is..."
```

**Caso 2: Architecture decision**
```bash
> /thinking extreme
> 
> We have a monolith with 200K LoC. 50 microservices candidates.
> Team of 30 developers. How to migrate?

Thinking (extreme = thorough):
"This is a complex migration. Let me consider:

Strategy options:
1. Strangler Fig pattern (recommended for legacy)
2. Big Bang (high risk, not recommended)
3. Branch by Abstraction (good for shared modules)
4. Database per service first vs services first
5. Domain-Driven decomposition

Considerations:
- 30 devs ÷ 50 services = 0.6 dev per service
  → Too many services for team size!
- 200K LoC / 50 = 4K LoC per service
  → Many will be too small (nano-services smell)
- Team size suggests 8-12 services optimal
  → Need to consolidate the 50 candidates

Phased approach:
Phase 1 (months 1-3): Domain analysis
  - Event storming workshops
  - Identify bounded contexts
  - Realistic target: 8-12 services
  
Phase 2 (months 4-6): Foundation
  - Service template
  - Shared infrastructure (auth, logging)
  - First service: most isolated bounded context
  
Phase 3 (months 7-12): Strangler Fig
  - Extract one service at a time
  - Old system runs en parallel
  - API Gateway routes traffic
  
Phase 4 (months 13-18): Cleanup
  - Decommission monolith parts
  - Optimize service boundaries
  - Final architecture validated"
```

## Slide 17 — Ejercicio 12: AI-augmented troubleshooting

**Objetivo:** Resolver un incident production simulado con IA.

**Setup:**
- Logs reales/simulados de error en producción
- Métricas (App Insights export)
- Código del componente afectado

**Scenario:**
```
Es lunes 10:00 AM. PagerDuty alert:
"API /api/orders 5xx error rate spike: 35% (normal <1%)"

Tienes:
1. App Insights logs últimas 2 horas
2. Métricas de SQL Database (DTU 95%)
3. Código de OrderService.cs
4. Last deploy: viernes 17:00 (3 días sin cambios)

Tu objetivo: identify root cause y mitigate en <30 min.
```

**Workflow con Claude Code:**

**Paso 1: Análisis inicial (5 min)**
```
Tú: "Tenemos production incident. 
Lee logs.txt y dime tu hipótesis inicial.

Synthesize:
- Patrón de errores (timing, frequency, type)
- Componente afectado
- Hipótesis ranked por probabilidad

NO mires el código aún."

Claude Code:
[Analiza logs]
Hipótesis (most likely first):
1. (75%) DB connection pool exhausted
2. (15%) Memory leak en OrderService
3. (5%) External API timeout cascading
4. (5%) DDOS attack
```

**Paso 2: Investigación dirigida (10 min)**
```
Tú: "Hipótesis #1 (DB pool exhausted) parece más probable.
Verifica esto:

1. Lee OrderService.cs y busca:
   - Connection management
   - DbContext lifecycle
   - Async/await patterns
   - Transaction usage

2. Genera KQL query para confirmar:
   - Connection wait time trend
   - Failed connections rate
   - DTU correlation con errors

3. Verifica EF Core configuration"

Claude Code:
[Lee código]
"En OrderService.cs:80 detecté:
```csharp
public async Task<List<Order>> GetOrdersAsync()
{
    var ctx = new MyDbContext();  // ← Crea ctx pero no dispone!
    return await ctx.Orders.ToListAsync();
}
```

Connection leak: cada llamada crea DbContext sin dispose.
Bajo carga, pool se agota."

KQL para confirmar:
```kusto
exceptions
| where timestamp > ago(2h)
| where message contains "Timeout"
| summarize count() by bin(timestamp, 5m)
```
```

**Paso 3: Quick mitigation (5 min)**
```
Tú: "Confirmado. Pero el fix proper requiere refactor + deploy.
Necesitamos mitigation INMEDIATA.

Opciones rápidas:"

Claude Code:
"Mitigations rápidas (en orden de speed):

1. ⚡ INMEDIATA (1 min): Restart App Service
   - Libera todos los connections actuales
   - Buy time: ~30 min antes que se agote otra vez
   ```bash
   az webapp restart --name app-curso-prod -g rg-curso-prod
   ```

2. 🔧 RÁPIDA (5 min): Aumentar connection pool
   ```bash
   az webapp config appsettings set \
     --name app-curso-prod -g rg-curso-prod \
     --settings 'ConnectionStrings__Default=...;Max Pool Size=200'
   az webapp restart ...
   ```
   Pero: ataca síntoma, no causa

3. 📈 ESCALADO (10 min): Scale up SQL DTU temporalmente
   ```bash
   az sql db update --name prod-db --resource-group rg-prod \
     --service-objective S6
   ```

Recomendación: hacer #1 INMEDIATAMENTE, mientras preparamos fix proper."
```

**Paso 4: Fix proper (10 min)**
```
Tú: "Genera fix proper para OrderService.
1. DbContext via DI (no new())
2. Async/await correcto
3. Tests para verificar fix
4. Migration plan (deploy con monitoring)"

Claude Code:
[Genera refactor]
[Genera tests específicos para connection leak]
[Genera deployment plan con feature flag]
```

**Paso 5: Post-incident (5 min)**

## Slide 18 — Ejercicio 13: Build a custom skill (workflow reutilizable)

**Objetivo:** Crear un skill que automatice un workflow recurrente del equipo.

**Concepto:**
Skills son workflows que Claude Code ejecuta cuando detecta el trigger correcto. Reemplazan documentación + reduce errores humanos.

**Ejercicio:**
```
Workflow que automatizar: "Crear nuevo microservicio"

Cuándo se usa: cada vez que alguien necesita nuevo servicio
Frecuencia: 2-3 veces/mes
Pain points actuales:
- Cada dev hace algo diferente
- Olvido pasos (Application Insights, health checks, etc.)
- Inconsistente entre servicios
- Toma 1-2 días hacer correctamente
```

**Crear skill paso a paso:**

**Paso 1: Estructura skill:**
```bash
mkdir -p ~/.claude/skills/create-microservice
cd ~/.claude/skills/create-microservice
touch SKILL.md
```

**Paso 2: SKILL.md content (con Claude Code help):**
```markdown
---
name: create-microservice
description: |
  Crear un nuevo microservicio .NET 8 con todas las convenciones
  del equipo. Incluye proyecto, tests, Bicep, pipeline, monitoring,
  y registry en service catalog. Activa cuando el usuario pida
  crear, scaffold, generar o iniciar nuevo microservicio,
  servicio, API, Web API, .NET service.
---

# Create Microservice

Workflow completo para crear un nuevo microservicio siguiendo 
las convenciones del equipo.

## Trigger
- "Crear microservicio para X"
- "Necesito un servicio nuevo"

### Phase 2: Scaffolding
Use template repo: github.com/empresa/microservice-template

```bash
# Clone template

  --template empresa/microservice-template \
  --private

cd empresa-{dominio}-{capability}

# Configure
./scripts/configure.sh "{dominio}" "{capability}"
```

### Phase 3: Components a generar

#### 3.1 Source code
- src/{Service}.Api/ — Web API entry

- tests/{Service}.Api.Tests/
- tests/{Service}.Application.Tests/

#### 3.2 Configuration
- appsettings.json (template)
- appsettings.Development.json
- Dockerfile multi-stage
- .dockerignore

#### 3.3 Bicep infrastructure
- infra/main.bicep
- infra/main.dev.bicepparam
- infra/main.prod.bicepparam
- infra/modules/ (si custom necesario)

#### 3.4 CI/CD
- .github/workflows/ci.yml (PR validation)
- .github/workflows/deploy.yml (deploy main → dev/staging/prod)
- .github/workflows/security-scan.yml (weekly)

#### 3.5 Observability
- OpenTelemetry setup en Program.cs
- App Insights connection
- Custom metrics structure
- Health checks (/health, /health/ready, /health/live)
- Diagnostic settings en Bicep

#### 3.6 Documentation
- README.md (overview, setup, contribution)

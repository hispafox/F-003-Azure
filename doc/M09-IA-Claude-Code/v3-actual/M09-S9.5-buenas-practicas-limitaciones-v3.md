## Slide 2 — Las 7 reglas de oro del desarrollo asistido por IA

**1. Revisar siempre:** IA genera, humano valida. Nunca mergear código generado sin revisar.

**2. Dar contexto:** "Crea un servicio" produce código genérico. "Crea un PedidoService para .NET 8 con Cosmos DB, Managed Identity, logging estructurado y retry policy" produce código utilizable.

**3. Iterar:** El primer resultado rara vez es perfecto. "Añade validación" → "Cambia el retry a exponential backoff" → "Añade tests".

**4. Tests primero:** Generad tests ANTES del código. Si los tests definen el comportamiento, el código generado es más fiable.

**5. No confiar ciegamente:** IA puede inventar APIs, métodos y configuraciones que no existen. Compilar y ejecutar siempre.

**6. Seguridad:** Nunca pasar secretos reales como parte del prompt. Usar variables de entorno.

**7. Documentar prompts útiles:** Si un prompt funciona bien, guardadlo en el repo (.claude/prompts/).

## Slide 3 — Prompt engineering para desarrollo

```bash
# MAL: demasiado vago
> Haz un servicio de pedidos

# BIEN: contexto + restricciones + formato
> Crea un PedidoService.cs con estas especificaciones:
  - Proyecto .NET 8 con Azure Cosmos DB
  - Inyectar CosmosClient por constructor (no crear instancias)
  - Partition key: /clienteId
  - Métodos: GetByIdAsync, CreateAsync, ListByClienteAsync(paginado)
  - Usar ILogger<PedidoService> para logging estructurado
  - Manejo de excepciones: CosmosException con switch por StatusCode
  - Patrón async/await, CancellationToken en todas las operaciones
  - Records para DTOs (no clases)
```

**Cuanto más específico el prompt, menos iteraciones necesitáis.**

## Slide 4 — Alucinaciones: el riesgo principal

La IA puede inventar:
- **APIs que no existen:** `cosmosClient.GetDatabaseAsync("db").GetContainerAsync("c")` — la API real es diferente
- **Métodos inexistentes:** `builder.Services.AddCosmosDb()` — no existe en el SDK
- **Configuraciones incorrectas:** Parámetros de CLI con nombres equivocados
- **Versiones futuras:** Código para .NET 9 features que no existen en .NET 8

**Cómo detectar:**
- Compilar inmediatamente: si no compila, hay invención
- Ejecutar tests: si fallan, algo está mal
- Verificar documentación: si no aparece en docs.microsoft.com, no existe
- Experiencia: con el tiempo, detectáis patterns sospechosos

## Slide 5 — Cuándo IA acelera y cuándo frena

**IA acelera:**
- Boilerplate (servicios, controllers, DTOs, tests)
- Transformación de datos (SQL → modelo, JSON → DTO)
- IaC (Bicep, YAML pipelines, Dockerfiles)
- Documentación desde código
- Análisis de errores con logs
- Refactoring mecánico

**IA frena (o genera resultado malo):**
- Lógica de negocio compleja y específica del dominio
- Decisiones de arquitectura (IA propone, humano decide)
- Optimización de rendimiento fino (necesita medir, no adivinar)
- Seguridad (IA puede generar código inseguro si no se le pide explícitamente)
- Debugging de race conditions y bugs sutiles

## Slide 12 — Anatomía de un buen prompt para desarrollo

Estructura que reduce iteraciones de 4-5 a 1-2:

```
┌────────────────────────────────────────────────────────┐
│ TEMPLATE: PROMPT EFECTIVO PARA DESARROLLO              │
├────────────────────────────────────────────────────────┤
│ 1. CONTEXTO (qué hace el sistema, stack)               │
│ 2. OBJETIVO (qué quieres lograr)                       │
│ 3. CONSTRAINTS (lo que NO puede hacer)                 │
│ 4. INPUT (datos/archivos relevantes)                   │
│ 5. OUTPUT (formato/estructura esperada)                │
│ 6. EXAMPLES (si hay patrón a seguir)                   │
│ 7. DEFINITION OF DONE (cómo saber si está bien)        │
└────────────────────────────────────────────────────────┘
```

**Ejemplo malo:**
```
"Crea un endpoint para crear pedidos"
```
Resultado: genérico, probablemente no funciona en tu codebase.

**Ejemplo bueno:**
```
CONTEXTO:
API REST .NET 8 con MediatR, EF Core, FluentValidation.
Arquitectura DDD: aggregates en Domain/, handlers en Application/.
Persistence con UnitOfWork pattern.
Auth con MS Entra (claim "sub" = userId).

OBJETIVO:
Crear endpoint POST /api/orders que cree un pedido.

CONSTRAINTS:
- NO añadir dependencias nuevas
- NO modificar Order aggregate (está estable)
- Validation BUSINESS RULES en aggregate (no FluentValidation)
- Validation FORMATO en CreateOrderCommandValidator (FluentValidation)
- Cross-aggregate validation (productId existe) en service nuevo
- Manejar concurrent updates con optimistic concurrency

INPUT:
- Order aggregate: src/Domain/Orders/Order.cs
- Existing handler pattern: src/Application/Orders/Handlers/UpdateOrderHandler.cs

OUTPUT:
- src/Application/Orders/Commands/CreateOrderCommand.cs
- src/Application/Orders/Commands/CreateOrderCommandValidator.cs
- src/Application/Orders/Commands/CreateOrderHandler.cs
- src/Application/Orders/Services/OrderItemsValidator.cs (interface in Application)
- src/Infrastructure/Orders/OrderItemsValidatorService.cs (implementation)
- Tests: tests/Application/Orders/CreateOrderHandlerTests.cs
- Update DependencyInjection.cs si necesario

DOD:
- ✅ Tests unitarios passing (100% cobertura del handler)
- ✅ Test integración con DB en memoria
- ✅ XML docs en publics
- ✅ Sigue convención naming del proyecto
- ✅ Returns 201 Created con Location header
- ✅ Returns 400 con ProblemDetails para validation errors
```

**Resultado:** código directamente integrable, ~85% acertado en primera iteración.

**Ratio mejora:**
- Prompt malo: 5-6 iteraciones, 30-45 min
- Prompt bueno: 1-2 iteraciones, 8-15 min

**Tip pro:** guarda prompts buenos en CLAUDE.md o .claude/prompts/ para reuso.

## Slide 13 — Anti-patterns comunes con Claude Code

Errores que veo en equipos usando Claude Code:

```
❌ ANTI-PATTERN 1: "Escríbeme todo el sistema"
   - Demasiado scope
   - Imposible verificar
   - Resultado: código frankenstein

✅ FIX: Iterar en chunks pequeños
   - 1 endpoint a la vez
   - Verifica antes de seguir
   - Commits frecuentes
```

```
❌ ANTI-PATTERN 2: Aceptar código sin entender
   - "Funciona, no toco"
   - Tech debt acumula sin que nadie sepa
   - Bugs invisibles

✅ FIX: Code review como si fuera un junior
   - Lee cada línea
   - Pregunta el "porqué"
   - Pide explicación de lo que no entiendes
```

```
❌ ANTI-PATTERN 3: No usar contexto del proyecto
   - Cada conversación empieza de cero
   - Claude inventa convenciones
   - Inconsistencia en codebase

✅ FIX: CLAUDE.md robusto
   - Stack tecnológico
   - Convenciones (naming, patterns)
   - Estructura de carpetas
   - Decisiones arquitectónicas
   - Ejemplos de código bien hecho
```

```
❌ ANTI-PATTERN 4: Skip tests "por velocidad"
   - "Lo que más rápido"
   - Bugs descubiertos en prod
   - Refactorizar imposible

✅ FIX: Tests son parte del prompt
   - "Generate code AND tests"
   - "TDD style: tests primero"
   - Tests son DoD
```

```
❌ ANTI-PATTERN 5: Confiar 100% en el primer output
   - Sin verificar
   - Sin ejecutar
   - Sin probar edge cases

✅ FIX: Verifica siempre
   - Run código generado
   - Test edge cases (null, empty, large)
   - Pide a Claude que critique su propio código
```

```
❌ ANTI-PATTERN 6: No usar memory / context
   - Repetir info en cada conversación
   - Claude olvida decisiones tomadas
   - Inconsistencias

✅ FIX: Aprovechar features 2026
   - Memory para preferencias persistentes
   - Subagents para tareas paralelas
   - Skills para workflows reutilizables
   - CLAUDE.md actualizado
```

```
❌ ANTI-PATTERN 7: "Claude lo arregla todo"
   - Escapar de pensar
   - Senior devs se vuelven juniors
   - Equipo no aprende fundamentos

✅ FIX: Claude como pair, no como reemplazo
   - Tú decides, Claude implementa
   - Tú revisa, Claude itera
   - Aprende de su output
```

```
❌ ANTI-PATTERN 8: Generar sin contexto del business
   - Código técnicamente perfecto
   - No resuelve el problema real
   - Stakeholders frustrados

✅ FIX: Incluye contexto de negocio
   - "Esta feature es para X user persona"
   - "El KPI a impactar es Y"
   - "El compliance requirement es Z"
```

```
❌ ANTI-PATTERN 9: Subir secrets/PII a Claude
   - Connection strings reales
   - Production data
   - PII de clientes

✅ FIX: Cleanse antes de compartir
   - Reemplaza secrets con placeholders
   - Sanitiza data
   - Usa MCP con tokens scope-limited
   - Empresa: usar Claude Enterprise (zero retention)
```

```
❌ ANTI-PATTERN 10: Pipeline IA en CI sin guardrails
   - Claude commitea directamente a main
   - Sin review humano
   - Risk de bugs en prod

✅ FIX: Human-in-the-loop
   - Claude crea PR (no merge)
   - Tests automáticos como gate
   - Required review humano
   - Approval explícito
```

**Mantra del equipo maduro:**
> "Claude no reemplaza el thinking. Reemplaza el typing."

3. PR review time
   - Antes: 2-3 días promedio
   - Con IA: 4-8 horas
   ✅ Reviews más fáciles si código limpio

   - Antes: docs desactualizadas

**Práticas de sanitización:**
```python
# Antes de enviar prompts a Claude API
import re

def sanitize_prompt(text):
    # Email addresses
    text = re.sub(r'\b[\w.-]+@[\w.-]+\.\w+\b', '[EMAIL]', text)
    
    # Credit card numbers
    text = re.sub(r'\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b', '[CC]', text)
    
    # SSN (US)
    text = re.sub(r'\b\d{3}-\d{2}-\d{4}\b', '[SSN]', text)
    
    # DNI (España)
    text = re.sub(r'\b\d{8}[A-Z]\b', '[DNI]', text)
    
    # Phone numbers
    text = re.sub(r'\+?\d{1,3}[\s-]?\d{3}[\s-]?\d{3}[\s-]?\d{3,4}', '[PHONE]', text)
    
    # Common secrets patterns
    text = re.sub(r'(api[_-]?key|secret|password|token)\s*[=:]\s*[\'"]?([\w-]+)[\'"]?', 
                  r'\1=[REDACTED]', text, flags=re.IGNORECASE)
    
    # AWS keys
    text = re.sub(r'AKIA[0-9A-Z]{16}', '[AWS_ACCESS_KEY]', text)
    
    # JWT tokens
    text = re.sub(r'eyJ[\w-]+\.[\w-]+\.[\w-]+', '[JWT]', text)
    
    return text

# Usage
prompt = "Debug this: connection failed for user@empresa.com con password=Pass123"
clean_prompt = sanitize_prompt(prompt)
# "Debug this: connection failed for [EMAIL] con password=[REDACTED]"
```

## Slide 16 — Cuándo NO usar IA

IA tiene limitaciones reales — sé honesto cuándo no aplica:

**Casos donde IA falla o no aporta:**

**1. Decisiones arquitectónicas estratégicas:**
```
❌ "¿Microservicios o monolito?"
❌ "¿Qué cloud provider elegir?"
❌ "¿Build vs buy?"

Razón: requieren contexto profundo del negocio,
       trade-offs largos, política organizacional.

✅ Sí útil para: explorar pros/cons, generar comparativas
✅ Decisión final: humanos con context completo
```

**2. Debugging con state distribuido complejo:**
```
❌ "Mi sistema con 12 microservicios, Kafka, Redis cluster, 
   3 DBs y CDN tiene latencia variable random"

Razón: Demasiadas variables, IA no tiene visibilidad full-stack
       Muchos intentos de "esto debe ser X"

✅ Sí útil para: hipótesis iniciales, queries de logs específicas
❌ NO sustitute: senior debugging real con telemetría
```

**3. Performance optimization extrema:**
```
❌ "Optimiza este loop hot path. Necesito 0.5ms más rápido"

Razón: IA conoce patterns generales, no tu hardware específico,
       caché L1/L2/L3, branch prediction, NUMA, etc.

✅ Sí útil para: identificar low-hanging fruit
✅ Performance crítica: profiling humano + low-level expertise
```

**4. Cumplimiento normativo crítico:**
```
❌ "Genera código que cumpla GDPR/HIPAA/SOX/PCI"

Razón: IA puede aproximarse pero compliance requiere
       interpretation legal, audits, certifications.

✅ Sí útil para: explicar regulaciones, drafts iniciales
❌ NO sustituye: legal counsel, compliance officers
```

**5. Algoritmos novedosos / research:**
```
❌ "Inventa un nuevo algoritmo de consensus distribuido"

Razón: IA replica patterns existentes, no innova científicamente
       (al menos en 2026)

✅ Sí útil para: implementar algoritmos existentes
❌ NO sustituye: investigación académica real
```

**6. Refactoring masivo en codebase legacy:**
```
❌ "Modernize este codebase de 10 años, 500K LoC"

Razón: Falta contexto histórico, decisiones implícitas,
       integraciones deprecated, side effects no obvios.

✅ Sí útil para: refactoring incremental, files individuales
❌ NO sustituye: archeology code humana, planning incremental
```

**7. UI/UX desde scratch sin guidelines:**
```
❌ "Diseña interfaz para mi app social"

Razón: UX requiere user research, testing, iteración
       IA genera "average" no diseño excellent.

✅ Sí útil para: implementar designs existentes, generate variations
❌ NO sustituye: UX designers profesionales
```

**8. Negociación con stakeholders:**
```
❌ "Convence al CFO de aprobar este proyecto"

Razón: Negociación requiere entender motivaciones humanas,
       relación previa, política, lectura emocional.

✅ Sí útil para: drafts de email, prep de meeting
❌ NO sustituye: comunicación humana real
```

**9. Tareas con fuerte dependencia de visión actualizada:**
```
❌ "¿Qué framework JS usar en 2026?"

Razón: Knowledge cutoff. Aun con web search, info contradictoria,
       hype cycles, ecosistema cambia mensualmente.

✅ Sí útil para: comparativa basada en data verificable
❌ NO sustituye: leer hands-on developers actuales
```

**10. Tareas con respuesta correcta única conocida:**
```
❌ "Calcula 2 + 2"

Razón: Costo IA > calculadora. Use the right tool.

✅ Sí útil para: explicar matemáticas, programar calculos
❌ NO use para: trivial computation
```

**Framework de decisión:**
```
¿Debe usar IA esta tarea?

Sí:
├── ¿Es repetitivo? ✅
├── ¿Has hecho similar antes? ✅
├── ¿Patterns conocidos aplican? ✅
├── ¿Volumen alto? ✅
├── ¿Es boilerplate? ✅

No:
├── ¿Decisión irreversible y crítica? ❌
├── ¿Falta contexto de negocio? ❌
├── ¿Requiere innovación real? ❌
├── ¿Compliance crítico sin review humano? ❌
├── ¿Vidas en juego? ❌
```

**Honestidad con stakeholders:**
> "IA acelera mucho pero no es magia. 
>  Funciona bien para X, mal para Y, 
>  y necesita supervisión humana en Z."

## Slide 20 — Cuándo no usar IA (la regla del 90/10)

Aún con IA poderosa, hay un 10% donde NO usarla es la decisión correcta:

```
EL 10% DONDE NO USAR IA:

1. Tareas críticas con riesgo asimétrico
   ├── Migración de DB en producción
   ├── Cambios en seguridad core
   ├── Rollback procedures
   └── Disaster recovery

2. Aprendizaje fundamental
   ├── Junior dev aprendiendo conceptos
   ├── Algorithm/data structure basics
   ├── Lenguaje nuevo desde cero
   └── Sistema architecture principles

3. Decisiones únicas/irreversibles
   ├── Hire/fire decisions
   ├── Inversión de tiempo significativo
   ├── Public commitments
   └── Compliance violations

4. Calibration de criterio
   ├── Review código importante (form your own opinion first)
   ├── Architecture review
   ├── Production incidents (debug yourself, learn)
   └── Mentoring otros devs

5. Trabajo creativo personal
   ├── Pet projects (where joy is the goal)
   ├── Learning experiments
   ├── Art/music/writing
   └── Cuando "el viaje" importa más que destination
```

**La regla del 90/10:**
```
90% de tareas → IA acelera enormemente
10% de tareas → IA puede dañar tu desarrollo profesional

El truco: identificar cuál es cuál.

Test sencillo:
├── ¿Esta tarea me hace mejor profesional?
│   └── SÍ: hazla a mano (al menos primero)
├── ¿Es repetitiva sin valor de aprendizaje?
│   └── SÍ: usa IA
├── ¿Sería catastrófico si está mal?
│   └── SÍ: humano + IA con review extra
└── ¿Me aburre y sé hacerla?
    └── SÍ: IA al 100%
```

**El balance saludable:**
```
Una semana típica de senior dev en 2026:

Lunes: Architecture meeting → SIN IA
Lunes-Martes: Implement feature → CON IA (acelera 3x)
Miércoles: Debug production issue → DEBUG humano + IA con queries
Jueves: Code review junior → REVIEW humano (mentoring)
Jueves: Refactor old code → CON IA (boilerplate)
Viernes: Plan próximo sprint → SIN IA (judgment)
Viernes: Update docs → CON IA (drafts)

% IA usage: ~60% del tiempo
% Sin IA: ~40% del tiempo (el critical 40%)
```

**Sobreuso es real:**
```
Síntomas de sobre-dependencia:
├── No sabes explicar tu propio código
├── Resuelves problemas con prompts, no thinking
├── Tu skill estancado o regrediendo
├── Desconfías de tu propio criterio
├── No puedes trabajar offline
└── Stress cuando IA tiene downtime

Test: "¿Puedo hacer esta tarea en una pizarra blanca sin IA?"
- Si NO: tu skill está atrofiando
- Si SÍ: estás usando IA correctamente
```

**El developer ideal 2030:**
```
Skills 100% humanas (no IA):
├── Critical thinking
├── Stakeholder management
├── Architecture vision
├── Trade-off analysis
├── Mentoring
├── Domain knowledge
└── Ethical judgment

Skills augmentadas con IA:
├── Implementation speed (10x)
├── Testing comprehensiveness
├── Documentation
├── Refactoring at scale
├── Code translation
└── Boilerplate generation

Balance: humano DIRIGE, IA EJECUTA.
```

**Mensaje final del módulo:**
> "IA es una herramienta poderosa, pero solo eso: una herramienta.
> 
>  Dominar IA = saber cuándo usarla y cuándo no.
> 
>  El developer que use IA siempre que pueda 
>  pierde frente al developer que sabe cuándo no usarla."

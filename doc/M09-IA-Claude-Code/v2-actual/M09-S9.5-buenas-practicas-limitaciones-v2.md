## Slide 2 — Las 7 reglas de oro del desarrollo asistido por IA

**1. Revisar siempre:** IA genera, humano valida. Nunca mergear código generado sin revisar.

**2. Dar contexto:** "Crea un servicio" produce código genérico. "Crea un PedidoService para .NET 8 con Cosmos DB, Managed Identity, logging estructurado y retry policy" produce código utilizable.

**3. Iterar:** El primer resultado rara vez es perfecto. "Añade validación" → "Cambia el retry a exponential backoff" → "Añade tests".

**4. Tests primero:** Generad tests ANTES del código. Si los tests definen el comportamiento, el código generado es más fiable.

**5. No confiar ciegamente:** IA puede inventar APIs, métodos y configuraciones que no existen. Compilar y ejecutar siempre.

**6. Seguridad:** Nunca pasar secretos reales como parte del prompt. Usar variables de entorno.

**7. Documentar prompts útiles:** Si un prompt funciona bien, guardadlo en el repo (.claude/prompts/).

## Slide 3 — Prompt engineering para desarrollo

```bash
# MAL: demasiado vago
> Haz un servicio de pedidos

# BIEN: contexto + restricciones + formato
> Crea un PedidoService.cs con estas especificaciones:
  - Proyecto .NET 8 con Azure Cosmos DB
  - Inyectar CosmosClient por constructor (no crear instancias)
  - Partition key: /clienteId
  - Métodos: GetByIdAsync, CreateAsync, ListByClienteAsync(paginado)
  - Usar ILogger<PedidoService> para logging estructurado
  - Manejo de excepciones: CosmosException con switch por StatusCode
  - Patrón async/await, CancellationToken en todas las operaciones
  - Records para DTOs (no clases)
```

**Cuanto más específico el prompt, menos iteraciones necesitáis.**

## Slide 4 — Alucinaciones: el riesgo principal

La IA puede inventar:
- **APIs que no existen:** `cosmosClient.GetDatabaseAsync("db").GetContainerAsync("c")` — la API real es diferente
- **Métodos inexistentes:** `builder.Services.AddCosmosDb()` — no existe en el SDK
- **Configuraciones incorrectas:** Parámetros de CLI con nombres equivocados
- **Versiones futuras:** Código para .NET 9 features que no existen en .NET 8

**Cómo detectar:**
- Compilar inmediatamente: si no compila, hay invención
- Ejecutar tests: si fallan, algo está mal
- Verificar documentación: si no aparece en docs.microsoft.com, no existe
- Experiencia: con el tiempo, detectáis patterns sospechosos

## Slide 5 — Cuándo IA acelera y cuándo frena

**IA acelera:**
- Boilerplate (servicios, controllers, DTOs, tests)
- Transformación de datos (SQL → modelo, JSON → DTO)
- IaC (Bicep, YAML pipelines, Dockerfiles)
- Documentación desde código
- Análisis de errores con logs
- Refactoring mecánico

**IA frena (o genera resultado malo):**
- Lógica de negocio compleja y específica del dominio
- Decisiones de arquitectura (IA propone, humano decide)
- Optimización de rendimiento fino (necesita medir, no adivinar)
- Seguridad (IA puede generar código inseguro si no se le pide explícitamente)
- Debugging de race conditions y bugs sutiles

## Slide 6 — Privacidad y compliance

**¿Qué se envía a la API de Anthropic?**
- El contenido de los archivos que Claude Code lee
- Vuestros prompts (incluyendo código)
- Los resultados de comandos que ejecuta

**Consideraciones:**
- Código propietario sale de vuestra red
- Datos de clientes NO deben incluirse en prompts
- Evaluar con el departamento legal antes de usar en proyectos sensibles
- Anthropic tiene política de no entrenar con datos de API

**Alternativas on-premises:**
- Claude Code con API self-hosted (Anthropic Enterprise)
- Modelos open source locales (Llama, Codestral) — menos capaces pero privados

## Slide 7 — Métricas: medir el impacto de IA

```
Antes de IA:
- Tiempo medio para implementar un servicio CRUD: 4 horas
- Tiempo medio para crear pipeline CI/CD: 3 horas
- Tiempo medio para escribir tests: 2 horas por servicio

Con IA:
- Servicio CRUD: 45 minutos (incluida revisión)
- Pipeline CI/CD: 30 minutos
- Tests: 20 minutos (+ 30 min de revisión/ajuste)

Ahorro estimado: 50-70% en tareas de boilerplate
Ahorro real (incluyendo revisión e iteración): 30-50%
```

## Slide 8 — El futuro: agentes autónomos

La IA está evolucionando de "asistente que genera código" a "agente que ejecuta workflows":

```
Hoy (2026):
  Desarrollador → prompt → IA genera → desarrollador revisa → commit

Próximo (2027+):
  Desarrollador define objetivo → IA planifica pasos → ejecuta → tests → PR
  Desarrollador solo revisa el PR final
```

Claude Code ya opera parcialmente como agente (ejecuta comandos, lee resultados, itera). La tendencia es hacia más autonomía con supervisión humana.

---

## Slide 9 — Cierre del submódulo
La IA es una herramienta potente con limitaciones reales. Usadla para lo que es buena (boilerplate, IaC, análisis), revisad siempre el output, y no la uséis como excusa para no entender el código que se genera. El mejor desarrollador con IA es el que ya sabría hacerlo sin IA — pero lo hace 3x más rápido.

Siguiente: práctica con Claude Code y MCP.

## Slide 12 — El futuro: lo que viene en 2026-2027

```
Hoy (2026):
├── Autocompletado en IDE (Copilot)
├── Agente terminal (Claude Code)
├── Conexión con herramientas (MCP)
└── Code review asistido

Próximo (2027):
├── Agentes autónomos que implementan features completas
├── Testing generativo (IA genera tests a partir de specs)
├── Monitoring inteligente (IA diagnostica y sugiere fix automático)

```

La tendencia es clara: más autonomía para la IA, más supervisión para el humano. El rol del developer evoluciona de "escribir código" a "definir qué hay que hacer y revisar que se hizo bien".

## Slide 13 — Cierre del submódulo (v2)
La IA en desarrollo es real, medible y con ROI positivo. Pero requiere disciplina: revisar siempre, dar contexto, documentar prompts útiles, y medir el impacto. No sustituye al programador — lo amplifica. El mejor equipo es el que sabe cuándo usar IA y cuándo pensar por sí mismo.

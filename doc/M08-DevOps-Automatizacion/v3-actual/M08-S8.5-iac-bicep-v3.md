## Slide 2 — Por qué IaC: el problema de la infraestructura manual
Hasta ahora hemos creado recursos con `az` CLI: `az webapp create`, `az cosmosdb create`, etc. Funciona, pero:

- No es reproducible (¿qué comandos ejecutasteis exactamente hace 3 meses?)
- No es versionable (si alguien cambia algo en el portal, no queda registro)
- No es testeable (no podéis validar antes de aplicar)
- No es consistente (staging y producción difieren porque se configuraron a mano)

IaC resuelve todo esto: la infraestructura se define en archivos de texto, se versiona en Git, se valida en CI, y se despliega con pipelines. Reproducible, auditable, testeable.

## Slide 3 — Bicep vs ARM Templates vs Terraform

| | ARM Templates | Bicep | Terraform |
|---|:---:|:---:|:---:|
| Formato | JSON (verbose) | DSL (legible) | HCL (legible) |
| Proveedor | Solo Azure | Solo Azure | Multi-cloud |
| Tooling | Azure CLI | Azure CLI + VS Code | Terraform CLI |
| State management | No (Azure es el state) | No (Azure es el state) | Sí (terraform.tfstate) |
| Módulos | Linked templates (complejo) | Módulos nativos (simple) | Módulos (mature) |
| Learning curve | Alta (JSON) | Baja | Media |
| Microsoft support | Legacy | Recomendado | Tercero |

**Para vuestro equipo:** Bicep. Es el lenguaje IaC recomendado por Microsoft para Azure. Más legible que ARM, sin state file como Terraform, con soporte nativo en Azure CLI y VS Code.

## Slide 4 — Primer archivo Bicep: un App Service

```bicep
// main.bicep
param location string = resourceGroup().location
param appName string = 'app-ventas-prod'
param planName string = 'plan-ventas-prod'

// App Service Plan
resource plan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: planName
  location: location
  sku: {
    name: 'S1'
    tier: 'Standard'
    capacity: 1
  }
}

// Web App
resource app 'Microsoft.Web/sites@2023-12-01' = {
  name: appName
  location: location
  properties: {
    serverFarmId: plan.id
    httpsOnly: true
    siteConfig: {
      netFrameworkVersion: 'v8.0'
      alwaysOn: true
      minTlsVersion: '1.2'
      healthCheckPath: '/health'
      appSettings: [
        { name: 'ASPNETCORE_ENVIRONMENT', value: 'Production' }
      ]
    }
  }
  identity: {
    type: 'SystemAssigned'
  }
}

// Output: URL de la app
output appUrl string = 'https://${app.properties.defaultHostName}'
output principalId string = app.identity.principalId
```

## Slide 5 — Desplegar Bicep

```bash
# Validar (sin desplegar)
az deployment group validate \
  --resource-group rg-ventas-prod \
  --template-file main.bicep \
  --parameters appName=app-ventas-prod

# What-if (preview de cambios)
az deployment group what-if \
  --resource-group rg-ventas-prod \
  --template-file main.bicep \
  --parameters appName=app-ventas-prod
# Muestra: + Create, ~ Modify, - Delete, = NoChange

# Desplegar
az deployment group create \
  --resource-group rg-ventas-prod \
  --template-file main.bicep \
  --parameters appName=app-ventas-prod
```

**Idempotencia:** Podéis ejecutar el despliegue múltiples veces. Si el recurso ya existe con la misma configuración, no cambia nada. Si difiere, se actualiza. Bicep calcula el diff automáticamente.

## Slide 6 — Parámetros y archivos de parámetros

```bicep
// main.bicep — declarar parámetros
@description('Nombre del App Service')
param appName string

@description('SKU del plan')
@allowed(['F1', 'B1', 'S1', 'P1v3'])
param planSku string = 'S1'

@description('Número de instancias')
@minValue(1)
@maxValue(10)
param instanceCount int = 1

@secure()
@description('Connection string de Cosmos DB')
param cosmosConnectionString string
```

```json
// params.prod.json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "appName": { "value": "app-ventas-prod" },
    "planSku": { "value": "S1" },
    "instanceCount": { "value": 2 },
    "cosmosConnectionString": {
      "reference": {
        "keyVault": { "id": "/subscriptions/.../vaults/kv-ventas-prod" },
        "secretName": "CosmosDbConnection"
      }
    }
  }
}
```

**Parámetros @secure():** Se enmascaran en logs. Y podéis referenciar Key Vault directamente en el archivo de parámetros — el secreto nunca aparece en texto plano.

## Slide 7 — Módulos Bicep: organizar la infraestructura

```bicep
// main.bicep — orquesta los módulos
module appService 'modules/app-service.bicep' = {
  name: 'deploy-app-service'
  params: {
    appName: 'app-ventas-prod'
    planSku: 'S1'
    location: location
  }
}

module cosmosDb 'modules/cosmos-db.bicep' = {
  name: 'deploy-cosmos'
  params: {
    accountName: 'cosmos-ventas-prod'
    databaseName: 'tienda'
    containers: ['pedidos', 'productos', 'clientes']
    location: location
  }
}

module storage 'modules/storage.bicep' = {
  name: 'deploy-storage'
  params: {
    accountName: 'stventasprod'
    location: location
  }
}

// Dar acceso de la app a Cosmos DB
module rbac 'modules/cosmos-rbac.bicep' = {
  name: 'assign-cosmos-rbac'
  params: {
    cosmosAccountName: cosmosDb.outputs.accountName
    principalId: appService.outputs.principalId
  }
}
```

```
infrastructure/
├── main.bicep                    ← Orquestador
├── params.dev.json               ← Parámetros de dev
├── params.staging.json           ← Parámetros de staging
├── params.prod.json              ← Parámetros de producción
└── modules/
    ├── app-service.bicep         ← App Service + Plan
    ├── cosmos-db.bicep           ← Cosmos DB + containers
    ├── storage.bicep             ← Storage Account
    ├── key-vault.bicep           ← Key Vault + secretos
    ├── functions.bicep           ← Function App
    ├── service-bus.bicep         ← Service Bus namespace
    └── cosmos-rbac.bicep         ← Role assignments
```

## Slide 9 — Módulo: Function App con Managed Identity

```bicep
// modules/functions.bicep
param functionAppName string
param storageAccountName string
param cosmosEndpoint string
param location string = resourceGroup().location

resource storage 'Microsoft.Storage/storageAccounts@2023-04-01' existing = {
  name: storageAccountName
}

resource plan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: '${functionAppName}-plan'
  location: location
  sku: { name: 'Y1', tier: 'Dynamic' }  // Consumption
}

resource functionApp 'Microsoft.Web/sites@2023-12-01' = {
  name: functionAppName
  location: location
  kind: 'functionapp'
  properties: {
    serverFarmId: plan.id
    httpsOnly: true
    siteConfig: {
      appSettings: [
        { name: 'FUNCTIONS_WORKER_RUNTIME', value: 'dotnet-isolated' }
        { name: 'AzureWebJobsStorage__blobServiceUri', value: 'https://${storageAccountName}.blob.core.windows.net' }
        { name: 'AzureWebJobsStorage__queueServiceUri', value: 'https://${storageAccountName}.queue.core.windows.net' }
        { name: 'CosmosDb__accountEndpoint', value: cosmosEndpoint }
        { name: 'WEBSITE_RUN_FROM_PACKAGE', value: '1' }
      ]
    }
  }
  identity: { type: 'SystemAssigned' }
}

output principalId string = functionApp.identity.principalId
output functionAppName string = functionApp.name
```

**Cero connection strings con password.** Solo endpoints + Managed Identity. Las variables con `__blobServiceUri` le dicen a Functions que use MI.

## Slide 12 — Entornos: dev, staging, prod

```bash

az deployment group create -g rg-ventas-dev \
```

**Mismo template, diferentes parámetros.** La infraestructura de dev, staging y prod es idéntica en estructura. Solo difieren los valores: nombres, SKUs, instancias, connection strings.

## Slide 15 — Infraestructura completa del proyecto: ejemplo real

```bicep
// main.bicep — toda la infraestructura del proyecto Ventas
param environment string
param location string = resourceGroup().location

// Nombres basados en entorno
var suffix = environment == 'prod' ? '' : '-${environment}'
var appName = 'app-ventas${suffix}'
var funcName = 'func-ventas${suffix}'
var cosmosName = 'cosmos-ventas${suffix}'
var storageName = 'stventas${environment}'
var kvName = 'kv-ventas-${environment}'

// Módulos
module storage 'modules/storage.bicep' = { name: 'storage', params: { accountName: storageName, location: location } }
module cosmos 'modules/cosmos-db.bicep' = { name: 'cosmos', params: { accountName: cosmosName, databaseName: 'tienda', containers: ['pedidos','productos'], location: location } }
module keyVault 'modules/key-vault.bicep' = { name: 'kv', params: { vaultName: kvName, location: location } }
module appService 'modules/app-service.bicep' = { name: 'app', params: { appName: appName, planSku: environment == 'prod' ? 'S1' : 'F1', cosmosEndpoint: cosmos.outputs.endpoint, location: location } }
module functions 'modules/functions.bicep' = { name: 'func', params: { functionAppName: funcName, storageAccountName: storageName, cosmosEndpoint: cosmos.outputs.endpoint, location: location } }

// RBAC: dar acceso a las apps
module appRbac 'modules/cosmos-rbac.bicep' = { name: 'app-rbac', params: { cosmosAccountName: cosmosName, principalId: appService.outputs.principalId } }
module funcRbac 'modules/cosmos-rbac.bicep' = { name: 'func-rbac', params: { cosmosAccountName: cosmosName, principalId: functions.outputs.principalId } }
```

**Un solo comando recrea TODA la infraestructura:** `az deployment group create -g rg-ventas-dev -f main.bicep -p environment=dev`

## Slide 18 — Bicep: deployment stacks (gestión de lifecycle)

```bash
# Deployment Stack: gestiona el lifecycle completo (crear Y eliminar)
az stack group create \
  --name stack-ventas-prod \
  --resource-group rg-ventas-prod \
  --template-file main.bicep \
  --parameters @params.prod.json \
  --action-on-unmanage deleteAll \
  --deny-settings-mode denyDelete
```

**Sin stacks:** Si eliminais un recurso del Bicep y redespliegáis, el recurso sigue existiendo en Azure (Bicep no elimina lo que no está en el template).

**Con stacks:** Los recursos que ya no están en el template se eliminan automáticamente. El stack "posee" los recursos y gestiona su lifecycle completo.

## Slide 19 — Bicep: testing con what-if en CI

```yaml
# Pipeline job: validar Bicep en cada PR
- job: ValidateBicep
  steps:
  - task: AzureCLI@2
    displayName: 'Lint Bicep'
    inputs:
      inlineScript: |
        az bicep build --file infrastructure/main.bicep
        echo "✓ Lint passed"

  - task: AzureCLI@2
    displayName: 'Validate deployment'
    inputs:
      inlineScript: |
        az deployment group validate \
          --resource-group rg-ventas-dev \
          --template-file infrastructure/main.bicep \
          --parameters @infrastructure/params.dev.json
        echo "✓ Validation passed"

  - task: AzureCLI@2
    displayName: 'What-if (preview changes)'
    inputs:
      inlineScript: |
        az deployment group what-if \
          --resource-group rg-ventas-dev \
          --template-file infrastructure/main.bicep \
          --parameters @infrastructure/params.dev.json \
          --no-pretty-print > $(Build.ArtifactStagingDirectory)/whatif.txt
        cat $(Build.ArtifactStagingDirectory)/whatif.txt

  - publish: $(Build.ArtifactStagingDirectory)/whatif.txt
    artifact: bicep-whatif
    displayName: 'Publish what-if report'
```

El what-if se ejecuta en cada PR. Los reviewers ven exactamente qué cambios de infraestructura introduce el PR antes de aprobar.

## Slide 22 — Azure Verified Modules (AVM): la nueva forma

**Azure Verified Modules** (AVM, 2024) son módulos Bicep oficiales mantenidos por Microsoft:

```
Antes (sin AVM):
├── Cada equipo escribía sus propios módulos
├── Quality variable, sin testing
├── Bug fixes duplicados
├── Best practices inconsistentes
└── Re-inventando la rueda constantemente

Con AVM:
├── Microsoft + community contributions
├── Tests automatizados, security baseline aplicado
├── Soporte oficial (issues en GitHub)
├── Versionado semver
├── Best practices built-in
└── Centralized en MCR (Microsoft Container Registry)
```

**Catálogo:** https://aka.ms/AVM (300+ módulos, growing)

**Resource modules (single resource):**
```bicep
// Sin AVM
resource sa 'Microsoft.Storage/storageAccounts@2024-01-01' = {
  name: 'stcurso'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: { /* 50+ líneas más */ }
}

// Con AVM (solo registry reference)
module storage 'br/public:avm/res/storage/storage-account:0.14.3' = {
  name: 'storage-deployment'
  params: {
    name: 'stcurso'
    location: location
    skuName: 'Standard_LRS'
    kind: 'StorageV2'
    minimumTlsVersion: 'TLS1_2'
    publicNetworkAccess: 'Disabled'  // Best practice baked-in
    networkAcls: {
      defaultAction: 'Deny'
    }
    diagnosticSettings: [
      {
        workspaceResourceId: logAnalyticsWorkspaceId
      }
    ]
  }
}
```

**Pattern modules (multi-resource scenarios):**
```bicep

}
```

**Ventajas reales:**
- ✅ Testing automatizado (PSRule, what-if, deployment)
- ✅ Security baseline applied (network restrictions, MI defaults)
- ✅ Diagnostic settings included
- ✅ Documentation comprehensive
- ✅ Examples para each module
- ✅ Maintained activamente por MS

**Cuándo NO usar AVM:**
- Casos muy específicos no cubiertos
- Necesitas modificar internal logic
- Performance ultra-crítica (overhead minimal pero existe)

## Slide 23 — Bicep deployment stacks integration

Combinando Bicep + Deployment Stacks para lifecycle management:

```bicep
// main.bicep
targetScope = 'subscription'

@description('Environment: dev, staging, prod')
param env string

@description('Azure region')
param location string = 'westeurope'

// Resource group (managed by stack)
resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: 'rg-curso-${env}'
  location: location
  tags: {
    environment: env
    deployedBy: 'bicep-stack'
  }
}

// All resources (también managed by stack)
module storage 'br/public:avm/res/storage/storage-account:0.14.3' = {
  scope: rg
  name: 'storage-deployment'
  params: {
    name: 'stcurso${env}'
    location: location
    skuName: env == 'prod' ? 'Standard_GRS' : 'Standard_LRS'
  }
}
```

## Slide 24 — Drift detection con Bicep + Stacks

Drift = cuando recursos en Azure no coinciden con tu Bicep (manual changes):

```
Causas comunes de drift:
├── Engineer cambió something via Portal "para probar"
├── Auto-scale modified settings
├── Defender for Cloud applied policy
├── Hot-fix manual sin update Bicep
└── Multiple teams con overlapping ownership
```

**Detect drift con what-if:**
```bash
# Check si Azure state coincide con Bicep
az deployment sub what-if \
  --location westeurope \
  --template-file main.bicep \
  --parameters env=prod

# Output muestra:
# - Resources to be modified (= drift!)
# - Resources to be deleted (= manual additions)
# - Resources to be created (= Bicep additions not yet deployed)
```

**Pipeline para drift detection scheduled:**
```yaml
# .github/workflows/drift-detection.yml
name: Drift Detection

on:
  schedule:
    - cron: '0 8 * * 1'  # Weekly Monday 8am
  workflow_dispatch:  # Manual trigger

jobs:
  detect-drift:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
      issues: write
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      - name: Run what-if
        id: whatif
        run: |
          OUTPUT=$(az deployment sub what-if \
            --location westeurope \
            --template-file infra/main.bicep \
            --parameters env=prod \
            --no-pretty-print)
          
          # Parse JSON for changes
          MODIFY_COUNT=$(echo "$OUTPUT" | jq '[.changes[] | select(.changeType == "Modify")] | length')
          DELETE_COUNT=$(echo "$OUTPUT" | jq '[.changes[] | select(.changeType == "Delete")] | length')
          
          echo "modify=$MODIFY_COUNT" >> $GITHUB_OUTPUT
          echo "delete=$DELETE_COUNT" >> $GITHUB_OUTPUT
          echo "$OUTPUT" > whatif.json
      
      - name: Create issue if drift
        if: steps.whatif.outputs.modify > 0 || steps.whatif.outputs.delete > 0
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const whatif = JSON.parse(fs.readFileSync('whatif.json'));
            
            const drifts = whatif.changes.filter(c => 
              c.changeType === 'Modify' || c.changeType === 'Delete'
            );
            
            const body = `## Infrastructure Drift Detected
            
            ${drifts.length} resources have drifted from Bicep:
            
            ${drifts.map(d => `- **${d.changeType}**: ${d.resourceId}`).join('\n')}
            
            ### Action required:
            1. Review changes
            2. Update Bicep to match (if intentional)
            3. Or revert manual changes
            
            Run: \`az stack sub update --name stack-curso-prod ...\``;
            
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Infrastructure drift detected (${drifts.length} resources)`,
              body: body,
              labels: ['drift', 'infrastructure', 'priority:high']
            });
```

**Auto-remediation (advanced):**
```yaml
# Auto-fix drift by re-applying Bicep
- name: Auto-remediate drift
  if: steps.whatif.outputs.delete > 0  # Solo si hay manual additions
  run: |
    az stack sub create \
      --name stack-curso-prod \
      --location westeurope \
      --template-file infra/main.bicep \
      --parameters env=prod \
      --action-on-unmanage detachAll \
      --deny-settings-mode denyWriteAndDelete \
      --yes
```

**Deny Settings + drift prevention:**
```bash
# Deployment Stack con deny settings = previene drift en primer lugar

  --name stack-curso-prod \
  --deny-settings-mode denyWriteAndDelete \
  --deny-settings-excluded-principals "<security-team-mi>" \
  --deny-settings-excluded-actions \
    "Microsoft.Web/sites/restart/action"

# Result:
# Si alguien intenta modificar resource desde portal:
# Error: "This resource is protected by deny assignment"
```

**Drift detection en Defender for Cloud:**
```bash
# Defender for Cloud has built-in drift detection
az security secure-score-control list \
  --query "[?value.properties.healthyResourceCount > 0]"
```

**Métricas drift importantes:**
```
Healthy IaC team metrics:
├── Drift resolution time: < 1 week
├── Drift recurrence rate: < 5%
├── % infrastructure managed by IaC: > 95%
└── Time from PR to deploy: < 1 hour

Unhealthy:
├── Drift > 1 month: indicates broken process
├── > 20% manual resources: not actually IaC
├── Drift no investigated: tech debt accumulating
```

```yaml
# .github/workflows/publish-bicep-module.yml
name: Publish Bicep Module

on:
  push:
    branches: [main]
    paths: ['modules/**']
  workflow_dispatch:
    inputs:
      version:
        description: 'Module version (semver)'
        required: true

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      # Test before publish
      - name: Bicep build (validate syntax)
        run: |
          for module in modules/*.bicep; do
            echo "Building $module"
            az bicep build --file $module
          done
      
      - name: Lint with PSRule
        run: |
          dotnet tool install -g Microsoft.PSRule.Tool
          ps-rule run --modules PSRule.Rules.Azure --inputPath modules/
      
      # Determine version
      - name: Determine version
        id: version
        run: |
          if [ -n "${{ inputs.version }}" ]; then
            VERSION="${{ inputs.version }}"
          else
            # Auto-increment (last tag + 1)
            VERSION=$(git describe --tags --abbrev=0 2>/dev/null || echo "v0.0.0")
            VERSION=$(echo $VERSION | awk -F. '{$NF++; print}' OFS=.)
          fi
          echo "version=$VERSION" >> $GITHUB_OUTPUT
      
      # Publish to ACR
      - name: Publish modules
        run: |
          for module in modules/*.bicep; do
            MODULE_NAME=$(basename $module .bicep)
            
            az bicep publish \
              --file $module \
              --target br:acrbicepempresa.azurecr.io/bicep/modules/$MODULE_NAME:${{ steps.version.outputs.version }} \
              --documentation-uri "https://wiki.empresa.com/bicep/$MODULE_NAME"
            
            echo "Published $MODULE_NAME version ${{ steps.version.outputs.version }}"
          done
      
      # Tag the release
      - name: Create git tag
        run: |
          git tag ${{ steps.version.outputs.version }}
          git push origin ${{ steps.version.outputs.version }}
```

**Module versioning strategy:**
```

v1.0.1 - Bug fix (backwards compatible)
v1.1.0 - New optional feature
v2.0.0 - Breaking change
v1.0.0-preview - Preview/experimental

Tagging convention:
├── major.minor.patch
├── Always pin in production
├── Never use 'latest' en prod
└── Document breaking changes
```

## Slide 29 — Anti-patterns Bicep comunes

Errores que veo constantemente:

```
❌ ANTI-PATTERN 1: Hardcoded values
resource sa 'Microsoft.Storage/storageAccounts@2024-01-01' = {
  name: 'stcursoprod123'
  location: 'westeurope'
  ...
}
✅ Usar parameters + variables

❌ ANTI-PATTERN 2: Sin uniqueString
resource sa 'Microsoft.Storage/storageAccounts@2024-01-01' = {
  name: 'stcurso'  // collision si otro tenant lo uses
  ...
}
✅ name: 'st${uniqueString(resourceGroup().id)}'

❌ ANTI-PATTERN 3: Outputs of secrets
output connectionString string = sa.listKeys().keys[0].value  // ❌ logged!
✅ Use Key Vault references; nunca output secrets

❌ ANTI-PATTERN 4: Sin location en RG vars
resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: 'rg-curso'
  location: 'westeurope'  // hardcoded
}
✅ param location string = deployment().location

❌ ANTI-PATTERN 5: Using resource() function
var saId = resource('Microsoft.Storage/storageAccounts', 'sa').id  // legacy
✅ Use symbolic name reference: sa.id

❌ ANTI-PATTERN 6: Sin existing keyword
module kv 'modules/key-vault.bicep' = {  // creates duplicate
  name: 'kv-existing'
}
✅ resource kv 'Microsoft.KeyVault/vaults@2024-04-01' existing = {
     name: 'kv-existing'
   }

❌ ANTI-PATTERN 7: Loops sin batchSize
@batchSize(1)  // forced sequential
resource items 'Microsoft.Web/sites@2024-04-01' = [for site in sites: {
  ...
}]
✅ Default es parallel (faster), only batchSize cuando necesario

❌ ANTI-PATTERN 8: API versions outdated
resource sa 'Microsoft.Storage/storageAccounts@2019-06-01' = {  // vieja
  ...
}
✅ Use latest stable API version

❌ ANTI-PATTERN 9: Sin description en params
param name string  // ¿qué espera?
✅ @description('Storage account name (3-24 chars, lowercase alphanumeric)')
   param name string

❌ ANTI-PATTERN 10: Mega-archivo único
// main.bicep con 2000 líneas
✅ Split en módulos lógicos (max 200-300 líneas por archivo)

❌ ANTI-PATTERN 11: Conditions complejas inline
resource sa = if (env == 'prod' && region == 'weu' && (config.deploy ?? false)) {
  ...
}
✅ var shouldDeploy = ...  // separate logic
   resource sa = if (shouldDeploy) { ... }

❌ ANTI-PATTERN 12: Sin parameter validation
@minLength(3)
@maxLength(24)
param storageName string  // missing validations
✅ Add @minLength, @maxLength, @allowed where applicable
```

**Self-check antes de PR:**
```
[ ] All params have @description
[ ] No hardcoded values (use params)
[ ] No secrets en outputs
[ ] uniqueString para names que could collide
[ ] Latest stable API versions
[ ] Diagnostic settings included
[ ] Tags applied consistently
[ ] Tests written (or sandbox tested)
[ ] PSRule passes
[ ] What-if preview reviewed
[ ] Documentation updated
```

## Slide 2 — Qué vais a construir

Un pipeline de GitHub Actions que **automáticamente** despliega vuestra Web App a Azure cada vez que hacéis `git push` a main. Usaremos el método más simple posible: **publish profile**.

**El recorrido:**

```
1. Crear (o reutilizar) una Web App F1 en Azure
2. Subir vuestro código a un repo de GitHub
3. Descargar el publish profile desde Azure
4. Configurar el publish profile como secret en GitHub
5. Crear un workflow .yml básico
6. Hacer push y ver el deploy automático
7. Verificar que la app responde con el código nuevo
8. Limpiar
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ OIDC / Federated identity (eso es M08-S8.P principal)
- ❌ Auto-rollback automático (M08-S8.P)
- ❌ Slots + swap blue/green (M02-S2.P)
- ❌ Approvals manuales / environments (M08-S8.P)
- ❌ Tests automatizados en pipeline (M08-S8.5)
- ❌ Bicep / Infrastructure as Code (M08-S8.5)

**Por qué publish profile como práctica simplificada:**

- ✅ Setup en 5 minutos (vs 30 min con OIDC)
- ✅ Sin App Registration en Microsoft Entra
- ✅ Sin Federated Credentials
- ✅ Modelo mental claro del flujo CI → CD
- ✅ Usable para side-projects personales sin más

**Tiempo estimado:** 45-60 minutos.

**Coste real:** **0€** (Web App F1 gratis + GitHub Actions free tier 2000 min/mes).

## Slide 7 — Paso 4: Descargar el publish profile

El publish profile es el "credential" que GitHub Actions usará para desplegar:

```bash
# Descargar el publish profile a un archivo
az webapp deployment list-publishing-profiles \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --xml > publish-profile.xml

# Ver el contenido (NO lo subáis a git)
cat publish-profile.xml
```

**Contenido típico del publish profile:**

```xml
<publishData>
  <publishProfile profileName="<app> - Web Deploy" 
                  publishMethod="MSDeploy"
                  publishUrl="<app>.scm.azurewebsites.net:443"
                  msdeploySite="<app>"
                  userName="$<app>"
                  userPWD="<password-larguísima>"
                  destinationAppUrl="https://<app>.azurewebsites.net"
                  ...>
  </publishProfile>
  <publishProfile profileName="<app> - FTP" ... />
</publishData>
```

**Lo que contiene:**

```
- profileName: nombre del perfil
- publishUrl: endpoint Kudu para deploy
- userName: identificador (formato $<app>)
- userPWD: password de deploy (¡secreto!)
- destinationAppUrl: URL pública de la app
```

**⚠️ IMPORTANTE: el publish profile contiene una password.**

```
- NUNCA lo subáis a git
- NUNCA lo compartáis públicamente
- Tratad publish-profile.xml como un secreto
- Si se filtra: regenerar las credentials inmediatamente
```

**Regenerar credentials si se compromete:**

```bash
# Regenerar publishing credentials
az webapp deployment list-publishing-credentials \
  --name $APP_NAME \
  --resource-group $RG_NAME

# Esto NO regenera, solo lista. Para regenerar:
# Portal → Web App → Deployment Center → Manage publish profile → Reset
```

## Slide 9 — Paso 6: Crear el workflow

Ahora el archivo más importante: el workflow YAML que define el pipeline.

```bash
# Crear estructura de carpetas
mkdir -p .github/workflows

# Crear el workflow
cat > .github/workflows/deploy.yml << 'EOF'
name: Deploy to Azure Web App

on:
  push:
    branches: [main]
  workflow_dispatch:  # Permite ejecutarlo manualmente desde la UI

env:
  AZURE_WEBAPP_NAME: <CAMBIAD_POR_VUESTRO_APP_NAME>
  DOTNET_VERSION: '8.0.x'

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Restore dependencies
        run: dotnet restore

      - name: Build
        run: dotnet build --no-restore --configuration Release

      - name: Publish
        run: dotnet publish -c Release -o ./publish --no-build

      - name: Deploy to Azure Web App
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ env.AZURE_WEBAPP_NAME }}
          publish-profile: ${{ secrets.AZURE_WEBAPP_PUBLISH_PROFILE }}
          package: ./publish
EOF
```

**Importante: editar el workflow:**

```bash
# Cambiar <CAMBIAD_POR_VUESTRO_APP_NAME> por vuestro app name real
# Por ejemplo: webapp-cicd-pedro-12345

sed -i.bak "s/<CAMBIAD_POR_VUESTRO_APP_NAME>/$APP_NAME/g" .github/workflows/deploy.yml
rm .github/workflows/deploy.yml.bak
```

**Verificar el workflow:**

```bash
cat .github/workflows/deploy.yml | head -10
# Esperado: env.AZURE_WEBAPP_NAME apunta a vuestra app
```

**Anatomía del workflow:**

```
on:
  push:
    branches: [main]    # Se dispara con push a main
  workflow_dispatch:    # Permite ejecutarlo manualmente

jobs:
  build-and-deploy:     # Un solo job
    runs-on: ubuntu-latest
    
    steps:              # Pasos secuenciales
      1. Checkout       # Bajar el código del repo
      2. Setup .NET     # Instalar .NET 8 SDK
      3. Restore        # Restaurar paquetes NuGet
      4. Build          # Compilar
      5. Publish        # Generar artifacts
      6. Deploy         # Subir a Azure
```

## Slide 12 — Smoke tests automatizados

Script bash que valida que el deploy fue exitoso:

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

URL="${1:?Pasa la URL como primer argumento}"

echo "🔍 Smoke tests sobre $URL"

# Test 1: Endpoint raíz responde 200
echo -n "  [1/4] GET /... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$URL/")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 2: Health check responde 200
echo -n "  [2/4] GET /health... "
HTTP_CODE=$(curl -o /dev/null -s -w "%{http_code}" "$URL/health")
[ "$HTTP_CODE" = "200" ] && echo "✓" || { echo "✗ ($HTTP_CODE)"; exit 1; }

# Test 3: La app reporta la versión esperada
echo -n "  [3/4] Version actualizada... "
VERSION=$(curl -s "$URL/" | jq -r '.version')
[ -n "$VERSION" ] && [ "$VERSION" != "null" ] && echo "✓ ($VERSION)" || { echo "✗"; exit 1; }

# Test 4: Latencia razonable (5 requests, P95)
echo -n "  [4/4] Latencia... "
TOTAL=0
for i in 1 2 3 4 5; do
  T=$(curl -o /dev/null -s -w "%{time_total}" "$URL/health")
  TOTAL=$(echo "$TOTAL + $T" | bc -l)
done
AVG=$(echo "scale=3; $TOTAL / 5" | bc -l)
echo "avg ${AVG}s ✓"

echo ""
echo "✅ Smoke tests pasados — deploy verificado"
EOF

chmod +x smoke-tests.sh

# Ejecutar
./smoke-tests.sh "https://$APP_NAME.azurewebsites.net"
```

**Output esperado:**

```
🔍 Smoke tests sobre https://webapp-cicd-pedro-12345.azurewebsites.net
  [1/4] GET /... ✓
  [2/4] GET /health... ✓
  [3/4] Version actualizada... ✓ (2.0.0)
  [4/4] Latencia... avg 0.215s ✓

✅ Smoke tests pasados — deploy verificado
```

## Slide 13 — Comparativa: Publish Profile vs OIDC

¿Por qué hay dos prácticas (esta y M08-S8.P principal)?

| Aspecto | Publish Profile (S8.P2) | **OIDC (S8.P principal)** |
|---|---|---|
| **Setup time** | 5 minutos | **30-60 minutos** |
| **Secret tipo** | Password (longeva) | **Token corto + federación** |
| **Rotación** | Manual al regenerar | **Automática (cada workflow)** |
| **Lifetime del secret** | Hasta que rotéis (años?) | **Minutos** |
| **Riesgo si se filtra** | Acceso total a Web App | **Limitado (token corto)** |
| **Auditabilidad** | Limitada | **Excelente (cada token=auditable)** |
| **Multi-environment** | 1 secret por env | **1 federated credential por env** |
| **Para qué nivel** | Side-projects, MVP | **Producción seria** |

**Cuándo SÍ Publish Profile:**

```
✅ Side-projects personales
✅ MVP / prototipos rápidos
✅ Apps internas con acceso limitado
✅ Aprendiendo CI/CD por primera vez
✅ Cuando no controláis App Registrations en Microsoft Entra
```

**Cuándo SÍ OIDC (M08-S8.P principal):**

```
✅ Aplicaciones de producción
✅ Empresas con políticas estrictas
✅ Auditoría requerida (financial, healthcare, etc.)
✅ Multiple environments (dev/qa/prod)
✅ Equipos grandes con muchos repos
```

**Por qué OIDC es mejor "en teoría":**

```
Publish Profile:
- Es una password
- Si se filtra → acceso permanente hasta rotar
- GitHub almacena un secret estático

OIDC (Federated Identity):
- Cada workflow obtiene un token NUEVO de Microsoft Entra
- Token vive 5-10 minutos
- No hay password almacenada en GitHub
- Microsoft Entra valida que el workflow viene del repo correcto
- Si "se filtra" un token → ya está caducado en minutos
```

**Realidad práctica:**

```
Para esta práctica, publish profile es perfecto:
- Aprendéis el flujo CI/CD sin ahogarse en config
- 90% del valor está en automatizar deploy, no en seguridad avanzada
- El día que necesitéis OIDC, sustituís el step de auth y listo

→ Empezad simple, evolucionad cuando importe
```

## Slide 14 — Variante: añadir tests al pipeline

Mejora muy común: ejecutar tests antes de desplegar:

**Modificar `deploy.yml`:**

```yaml
name: Deploy to Azure Web App

on:
  push:
    branches: [main]
  workflow_dispatch:

env:
  AZURE_WEBAPP_NAME: webapp-cicd-pedro-12345
  DOTNET_VERSION: '8.0.x'

jobs:
  # Job 1: Build + Test
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      
      - name: Restore
        run: dotnet restore
      
      - name: Build
        run: dotnet build --no-restore --configuration Release
      
      - name: Test
        run: dotnet test --no-build --configuration Release --logger "console;verbosity=detailed"

  # Job 2: Deploy (solo si build-test pasó)
  deploy:
    needs: build-test  # ← solo se ejecuta si build-test fue OK
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}
      
      - name: Publish
        run: dotnet publish -c Release -o ./publish
      
      - name: Deploy to Azure Web App
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ env.AZURE_WEBAPP_NAME }}
          publish-profile: ${{ secrets.AZURE_WEBAPP_PUBLISH_PROFILE }}
          package: ./publish
```

**Crear un test sencillo:**

```bash
cd ..  # subir un nivel
dotnet new xunit -n MiAppCicd.Tests
cd MiAppCicd.Tests
dotnet add reference ../MiAppCicd/MiAppCicd.csproj

# Crear un test trivial
cat > BasicTests.cs << 'EOF'
namespace MiAppCicd.Tests;

public class BasicTests
{
    [Fact]
    public void TwoPlusTwoEqualsFour()
    {
        Assert.Equal(4, 2 + 2);
    }
}
EOF

# Probar localmente
dotnet test
```

**Subir cambios:**

```bash
cd ..
git add .
git commit -m "Add tests + 2-job pipeline"
git push
```

**Observar:**

```
GitHub Actions ahora muestra:
✓ build-test
   ↓ (passed)
✓ deploy
```

**Si un test falla:**

```
✗ build-test
   ↓ (failed)
⏭ deploy (skipped)

→ El deploy NO se ejecuta si los tests fallan
→ Nunca llega código roto a producción
→ ESTE es el valor real de CI/CD
```

## Slide 15 — Variante: deploy automático solo a tags (releases)

A veces no queréis deploy en cada push (puede haber commits experimentales en main). Patrón común: solo deployar cuando hacéis `git tag`:

```yaml
on:
  push:
    tags:
      - 'v*'           # solo tags que empiezan con v: v1.0, v1.0.1, etc.
  workflow_dispatch:    # también permitir manual
```

**Workflow del usuario:**

```bash
# Trabajáis normalmente en main (push, push, push)
git push                # NO dispara deploy
git push                # NO dispara deploy
git push                # NO dispara deploy

# Cuando estáis listos para release:
git tag v1.0.0
git push --tags         # ← dispara deploy

# O para hotfix:
git tag v1.0.1
git push --tags
```

**Ventajas:**

```
✅ Control total del momento de deploy
✅ Versión semántica clara (v1.0, v1.1, etc.)
✅ Cada deploy = un tag = trazabilidad histórica
✅ Permite tener "main" para development y deploys explícitos
```

**Anti-patrones a evitar:**

```
❌ Deploy en cada push a main + main es donde experimentáis
   → constantes deploys de cosas no listas

❌ Solo deploy manual sin pipeline
   → defeats the purpose de CI/CD

✅ Pattern moderno: 
   - main: deploy a dev/staging environment
   - tags: deploy a producción
```

**Conditional logic en el workflow:**

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Set env
        run: |
          if [[ "${{ github.ref }}" == "refs/heads/main" ]]; then
            echo "ENV_NAME=staging" >> $GITHUB_ENV
            echo "APP_NAME=webapp-staging-..." >> $GITHUB_ENV
          else
            echo "ENV_NAME=production" >> $GITHUB_ENV
            echo "APP_NAME=webapp-prod-..." >> $GITHUB_ENV
          fi
      
      - name: Deploy
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ env.APP_NAME }}
          ...
```

## Slide 17 — Troubleshooting: errores comunes

Los 6 errores más típicos al configurar CI/CD con publish profile:

**1. "Error: Publish profile is not valid"**

```
Causa: el publish profile que copiasteis al secret está malformado
Síntoma: workflow falla en step "Deploy to Azure Web App"

Diagnóstico:
- ¿Copiasteis TODO el XML, incluyendo <publishData>...</publishData>?
- ¿Vuestra app cambió de plan / region tras descargar el profile?

Fix:
- Re-descargar el profile:
  az webapp deployment list-publishing-profiles \
    --name $APP_NAME -g $RG_NAME --xml > publish-profile.xml
- Actualizar el secret:
  gh secret set AZURE_WEBAPP_PUBLISH_PROFILE < publish-profile.xml
```

**2. "Error: webapps-deploy failed with status 401"**

```
Causa: las credentials del publish profile están caducadas o rotadas
Síntoma: 401 Unauthorized durante el deploy

Fix:
- Reset publishing credentials:
  Portal → Web App → Deployment Center → "Reset publish credentials"
- Re-descargar publish profile y actualizar el secret
```

**3. "Error: webapps-deploy failed with status 503"**

```
Causa: la Web App está down o reiniciándose
Síntoma: 503 Service Unavailable durante deploy

Fix:
- Esperar 1-2 min y re-ejecutar el workflow:
  gh workflow run deploy.yml
  
- Verificar que la app está running:
  az webapp show --name $APP_NAME -g $RG_NAME --query state -o tsv
  # Esperado: "Running"
```

**4. "App responde con código viejo tras deploy"**

```
Causa: caché agresivo o restart no completado
Síntoma: workflow termina OK pero curl devuelve la versión anterior

Diagnóstico:
- Esperar 1-2 minutos más (App Service tarda a veces)
- Hacer hard refresh en navegador (Ctrl+Shift+R)
- Verificar el deployment en portal:
  Portal → Deployment Center → Logs

Fix:
- Forzar restart:
  az webapp restart --name $APP_NAME -g $RG_NAME

- Verificar que el ZIP es correcto:
  Si subisteis basura, el deploy es OK pero la app no funciona
```

**5. "Workflow doesn't trigger on push"**

```
Causa común: workflow file mal ubicado
Verificar:
- Está en .github/workflows/ (con punto inicial)
- Tiene extensión .yml o .yaml
- YAML es válido (sin tabs, indentación correcta)

Diagnóstico:
- gh run list (debería mostrar runs)
- Si vacío, el workflow no se está reconociendo

Fix:
- Verificar la ruta exacta:
  ls -la .github/workflows/
- Validar YAML:
  yamllint .github/workflows/deploy.yml
```

**6. "Cannot find package: ./publish"**

```
Causa: el build no generó el output donde el deploy lo espera
Síntoma: el step de deploy no encuentra los artifacts

Verificar:
- ¿El step Publish corre con el flag correcto?
  dotnet publish -c Release -o ./publish

- ¿La carpeta .csproj está en la raíz del repo o en subdirectorio?

Fix:
- Si vuestro .csproj está en subcarpeta:
  - cd MiAppCicd && dotnet publish -c Release -o ../publish
  
- O ajustar el path del deploy:
  package: ./MiAppCicd/bin/Release/net8.0/publish
```

**Logs detallados:**

```
GitHub Actions UI → workflow run → click en step
→ "Show full logs"

Buscar:
- ERROR / FATAL
- "exit code 1"
- "Process completed with exit code"
```

## Slide 18 — Buenas prácticas para producción

Si vais a usar publish profile + GitHub Actions en producción:

**1. NUNCA commitear publish-profile.xml:**

```bash
# Verificar .gitignore incluye:
*.publish-profile
publish-profile.xml
PublishProfiles/
```

**2. Rotar publish credentials regularmente:**

```bash
# Cada 90 días, regenerar:
az webapp deployment list-publishing-profiles ... --xml > new-profile.xml
gh secret set AZURE_WEBAPP_PUBLISH_PROFILE < new-profile.xml
rm new-profile.xml
```

**3. Usar environments de GitHub:**

```yaml
jobs:
  deploy:
    environment: production    # ← obliga reglas configurables
    runs-on: ubuntu-latest
    steps:
      - ...
```

```
GitHub Settings → Environments → New environment "production"
Configurar:
☑ Required reviewers (1+ personas aprueban)
☑ Wait timer (delay antes de ejecutar)
☑ Branch policy (solo main puede deployar)

Cualquier deploy a production:
1. Workflow llega al job "deploy"
2. PAUSA esperando aprobación de reviewers
3. Aprobación → continúa
4. Sin aprobación → cancelado tras N días
```

**4. Notificaciones:**

```yaml
# Notificar a Slack/Teams al deployar
- name: Notify deployment
  if: success()
  uses: slackapi/slack-github-action@v1
  with:
    webhook-url: ${{ secrets.SLACK_WEBHOOK }}
    payload: |
      {
        "text": "🚀 Deploy completado: ${{ env.AZURE_WEBAPP_NAME }} v${{ github.sha }}"
      }
```

**5. Smoke tests automáticos post-deploy:**

```yaml
- name: Smoke tests
  run: |
    sleep 30
    chmod +x smoke-tests.sh
    ./smoke-tests.sh "https://${{ env.AZURE_WEBAPP_NAME }}.azurewebsites.net"

- name: Notify failure
  if: failure()
  run: echo "❌ Smoke tests failed - manual check required"
```

**6. Multi-environment con publish profiles separados:**

```yaml
secrets:
- AZURE_WEBAPP_PUBLISH_PROFILE_DEV
- AZURE_WEBAPP_PUBLISH_PROFILE_STAGING
- AZURE_WEBAPP_PUBLISH_PROFILE_PROD

# Workflow elige según branch:
- name: Set env
  run: |
    if [[ "${{ github.ref }}" == "refs/heads/main" ]]; then
      echo "PROFILE_SECRET=AZURE_WEBAPP_PUBLISH_PROFILE_DEV" >> $GITHUB_ENV
    fi
```

**7. Considerar OIDC cuando crezca el proyecto:**

```
Indicadores de migrar a OIDC:
- Equipo grande (10+ devs en el repo)
- Compliance requirements (audit logs)
- Multi-environment (dev + qa + staging + prod)
- Cliente externo / cliente regulado

→ Hacer M08-S8.P (la principal) cuando estéis listos
```

## Slide 20 — Retos opcionales

**Reto 1 — Añadir tests al pipeline**

Añadir un step de `dotnet test` antes del deploy. Si los tests fallan, el deploy NO se ejecuta.

**Reto 2 — Deploy solo en tags**

Cambiar el workflow para que solo despliegue cuando hagáis `git tag v1.0.0; git push --tags`. Push a main NO debería desplegar.

**Reto 3 — Notificación en éxito/fallo**

Añadir un step que notifique vía webhook (Slack, Teams, Discord) el resultado del deploy.

**Reto 4 — Multi-environment**

Crear DOS Web Apps (`webapp-dev` y `webapp-prod`). Configurar el workflow para que:
- Push a `develop` → deploy a `webapp-dev`
- Push a `main` → deploy a `webapp-prod`

**Reto avanzado — Migrar a OIDC**

Hacer la práctica principal M08-S8.P y comparar:
- Setup time (mucho más con OIDC)
- Seguridad (mucho mejor con OIDC)
- Tokens en lugar de password
- Federated credentials en Microsoft Entra

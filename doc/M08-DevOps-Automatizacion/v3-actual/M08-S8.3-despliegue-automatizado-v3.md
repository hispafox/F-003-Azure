## Slide 2 — Mapa de despliegue: cada app tiene su flujo
Vuestro equipo tiene 4 tipos de aplicación. Cada uno tiene un flujo de despliegue diferente:

```
ventas-api (App Service) → Build .NET → Zip Deploy → Slot staging → Swap
ventas-functions (Functions) → Build .NET → Func Deploy → Slot staging → Swap
ventas-desktop (MSIX) → Build WPF → Package MSIX → Sign → Upload Blob → AppInstaller
ventas-infra (Bicep) → Validate → What-if → Deploy
```

El pipeline de CI es casi idéntico (build .NET + test). Lo que cambia es el CD (cómo se despliega).

## Slide 3 — Deploy strategies: comparativa

| Estrategia | Downtime | Rollback | Riesgo | Complejidad |
|---|:---:|:---:|:---:|:---:|
| **Direct deploy** | Sí (reinicio) | Redesplegar | Alto | Mínima |
| **Slot swap** | No | Swap inverso | Bajo | Media |
| **Blue/Green** | No | Cambiar DNS | Bajo | Media |
| **Canary** | No | Quitar % tráfico | Muy bajo | Alta |
| **Rolling update** | No | Depende | Medio | Alta |

**Para vuestro equipo:**
- App Service: **Slot swap** (zero downtime, rollback instantáneo)
- Functions: **Slot swap** si Premium, **Direct deploy** si Consumption
- MSIX: **AppInstaller** (auto-update gradual)
- Infra: **What-if → approve → deploy** (IaC con preview)

## Slide 4 — App Service: flujo de deploy completo

```yaml
# 1. Build
- script: dotnet publish -c Release -o $(Build.ArtifactStagingDirectory)/app

# 2. Zip
- task: ArchiveFiles@2
  inputs:
    rootFolderOrFile: '$(Build.ArtifactStagingDirectory)/app'
    archiveType: 'zip'
    archiveFile: '$(Build.ArtifactStagingDirectory)/deploy.zip'

# 3. Deploy a staging
- task: AzureWebApp@1
  inputs:
    azureSubscription: 'Azure-Prod'
    appName: 'app-ventas-prod'
    slotName: 'staging'
    package: '$(Build.ArtifactStagingDirectory)/deploy.zip'
    appSettings: '-ASPNETCORE_ENVIRONMENT Staging'

# 4. Smoke test en staging
- script: |
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://app-ventas-prod-staging.azurewebsites.net/health)
    if [ "$STATUS" != "200" ]; then echo "Smoke test failed!"; exit 1; fi
  displayName: 'Smoke test staging'

# 5. Swap (con aprobación)
- task: AzureAppServiceManage@0
  inputs:
    Action: 'Swap Slots'
    WebAppName: 'app-ventas-prod'
    SourceSlot: 'staging'

# 6. Post-deploy health check
- script: |
    sleep 30
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://app-ventas-prod.azurewebsites.net/health)
    if [ "$STATUS" != "200" ]; then echo "Post-deploy check failed!"; exit 1; fi
  displayName: 'Post-deploy health check'
```

## Slide 6 — MSIX: pipeline de empaquetado y distribución

El pipeline de MSIX es diferente: no despliega a un servidor, sube un archivo que los usuarios descargan.

```yaml
# Resumen del flujo (detalle en 8.2):
# 1. Build WPF project
# 2. Package MSIX (MSBuild con wapproj)
# 3. Sign con AzureSignTool (Key Vault)
# 4. Upload a Blob Storage
# 5. Actualizar AppInstaller XML con nueva versión
# 6. Los usuarios reciben la actualización automáticamente
```

**Diferencia clave:** No hay "deploy a un servidor". Hay "publicar un archivo y actualizar el manifiesto". Los usuarios se actualizan solos.

## Slide 7 — Bicep/IaC: pipeline de infraestructura

```yaml
# El pipeline de infra NO despliega código — despliega RECURSOS Azure
stages:
- stage: Validate
  jobs:
  - job: Lint
    steps:
    - script: az bicep build --file infrastructure/main.bicep
      displayName: 'Lint Bicep'

- stage: Preview
  jobs:
  - job: WhatIf
    steps:
    - task: AzureCLI@2
      inputs:
        inlineScript: |
          az deployment group what-if \
            --resource-group rg-ventas-prod \
            --template-file infrastructure/main.bicep \
            --parameters @infrastructure/params.prod.json
      # Muestra qué va a cambiar sin aplicar

- stage: Deploy
  jobs:
  - deployment: DeployInfra
    environment: 'infra-production'  # Aprobación manual OBLIGATORIA
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureCLI@2
            inputs:
              inlineScript: |
                az deployment group create \
                  --resource-group rg-ventas-prod \
                  --template-file infrastructure/main.bicep \
                  --parameters @infrastructure/params.prod.json
```

**What-if es crítico:** Muestra los cambios antes de aplicar. Si veis "Delete: app-ventas-prod", sabéis que algo va mal antes de ejecutar.

## Slide 8 — Rollback strategies por tipo de app

| App | Rollback method | Tiempo |
|---|---|---|
| App Service (slots) | Swap inverso | ~5 segundos |
| App Service (sin slots) | Redesplegar versión anterior | 2-5 minutos |
| Functions (slots) | Swap inverso | ~5 segundos |
| Functions (sin slots) | Redesplegar | 2-5 minutos |
| MSIX | Publicar versión anterior con build# mayor | 1-24h (auto-update) |
| Infra (Bicep) | Re-deploy estado anterior | Depende de recursos |

**Para rollback de emergencia (App Service):**
```yaml
# Job de rollback manual (trigger manual con parámetro)
parameters:
- name: rollback
  type: boolean
  default: false

- stage: Rollback
  condition: eq('${{ parameters.rollback }}', 'true')
  jobs:
  - deployment: RollbackProd
    environment: 'ventas-production'
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureAppServiceManage@0
            inputs:
              Action: 'Swap Slots'
              WebAppName: 'app-ventas-prod'
              SourceSlot: 'staging'  # staging tiene la versión anterior
```

## Slide 9 — Smoke tests y health checks post-deploy

```yaml
# Health check básico
- script: |
    for i in 1 2 3 4 5; do
      STATUS=$(curl -s -o /dev/null -w "%{http_code}" $URL/health)
      if [ "$STATUS" = "200" ]; then echo "✓ Health OK"; exit 0; fi
      echo "Attempt $i: HTTP $STATUS, retrying in 10s..."
      sleep 10
    done
    echo "✗ Health check failed after 5 attempts"; exit 1

# Smoke test funcional
- script: |
    # Verificar que los endpoints principales responden
    curl -sf "$URL/api/productos" > /dev/null || exit 1
    curl -sf "$URL/api/pedidos?limit=1" > /dev/null || exit 1
    echo "✓ Smoke tests passed"

# Si el smoke test falla, rollback automático
- task: AzureAppServiceManage@0
  condition: failed()
  inputs:
    Action: 'Swap Slots'
    WebAppName: 'app-ventas-prod'
    SourceSlot: 'staging'
  displayName: 'Auto-rollback on failure'
```

## Slide 12 — Canary deployment con App Service

```bash
# Enviar 10% del tráfico al slot staging (canary)
az webapp traffic-routing set --name app-ventas-prod -g rg-ventas-prod \
  --distribution staging=10

# Monitorizar errores en staging
# Si OK después de 30 min, subir a 50%
az webapp traffic-routing set --name app-ventas-prod -g rg-ventas-prod \
  --distribution staging=50

# Si sigue OK, swap completo
az webapp deployment slot swap --name app-ventas-prod -g rg-ventas-prod --slot staging

# Si falla, quitar tráfico
az webapp traffic-routing clear --name app-ventas-prod -g rg-ventas-prod
```

Canary es más seguro que swap directo: si la nueva versión tiene un bug, solo afecta al 10% del tráfico. El 90% sigue en la versión estable.

## Slide 14 — Sticky settings: proteger staging de datos de producción

```bash
# Marcar settings como "sticky" (no se mueven en el swap)
az webapp config appsettings set --name func-ventas-prod -g rg-ventas-prod \
  --slot-settings \
    ASPNETCORE_ENVIRONMENT=Staging \
    CosmosDb__accountEndpoint=https://cosmos-ventas-staging.documents.azure.com:443/ \
    ServiceBusConnection__fullyQualifiedNamespace=sb-ventas-staging.servicebus.windows.net
```

Sin sticky settings, al hacer swap staging→producción, staging empezaría a procesar mensajes de producción con el código anterior. Los sticky settings garantizan que staging SIEMPRE usa la base de datos y colas de staging.

## Slide 15 — Deploy con zero-downtime: warmup

```bash
# Configurar warmup antes del swap
az webapp config set --name app-ventas-prod -g rg-ventas-prod \
  --startup-file "" \
  --generic-configurations '{"applicationInitialization":{"initializationPages":[{"path":"/health"},{"path":"/api/productos?limit=1"}]}}'
```

```yaml
# En el pipeline: esperar warmup antes de swap
- task: AzureAppServiceManage@0
  inputs:
    Action: 'Start Azure App Service'
    WebAppName: 'app-ventas-prod'
    SpecifySlotOrASE: true
    Slot: 'staging'

- script: |
    echo "Waiting for warmup (60s)..."
    sleep 60
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://app-ventas-prod-staging.azurewebsites.net/health)
    echo "Warmup status: HTTP $STATUS"
    [ "$STATUS" = "200" ] || exit 1
  displayName: 'Wait for warmup'

- task: AzureAppServiceManage@0
  inputs:
    Action: 'Swap Slots'
    WebAppName: 'app-ventas-prod'
    SourceSlot: 'staging'
```

Warmup carga la app en memoria antes del swap. Sin warmup, los primeros usuarios después del swap experimentan latencia alta (cold start).

## Slide 18 — Self-hosted agents: cuándo y cómo

```bash
# Instalar agent en una VM o container
mkdir agent && cd agent
curl -O https://vstsagentpackage.azureedge.net/agent/3.x/vsts-agent-linux-x64.tar.gz
tar xzf vsts-agent-linux-x64.tar.gz
./config.sh --url https://dev.azure.com/mi-org --auth pat --token xxx
./run.sh
```

**Cuándo self-hosted:**
- Build necesita software que no está en Microsoft-hosted (herramientas especializadas)
- Necesitáis acceso a red interna (VPN, on-premises)
- Los builds tardan mucho y queréis hardware más potente
- Queréis cachear dependencias entre builds (más rápido)

**Cuándo Microsoft-hosted (default):**
- Para el 90% de los casos
- Sin mantenimiento de infraestructura
- Siempre limpio (no acumula estado entre builds)

## Slide 19 — Blue/Green deployment completo

Blue/Green: dos environments idénticos, switch instantáneo entre ellos:

```
ARQUITECTURA:
                    ┌───────────────────┐
                    │  Traffic Manager  │
                    │  (o Front Door)   │
                    └─────────┬─────────┘
                              │
                  ┌───────────┴───────────┐
                  │                       │
                  ▼                       ▼
         ┌─────────────────┐    ┌─────────────────┐
         │   BLUE (v1.0)   │    │   GREEN (v2.0)  │
         │   100% traffic  │    │   0% traffic    │
         │   (production)  │    │   (idle/test)   │
         └─────────────────┘    └─────────────────┘
                                          │
                                          │ Switch all
                                          ▼
                              [GREEN ahora 100%]
                              [BLUE 0%, listo para v3.0]
```

**Implementación con App Service Slots:**

```yaml
# pipeline-blue-green.yml
trigger:
  - main

stages:
  - stage: Deploy_to_Green
    displayName: "Deploy to Green slot"
    jobs:
      - deployment: DeployGreen
        environment: production-green
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: 'sc-azure-prod'
                    appName: 'app-curso-prod'
                    deployToSlotOrASE: true
                    slotName: 'green'
                    package: '$(Pipeline.Workspace)/drop/*.zip'

  - stage: Smoke_Tests
    displayName: "Validate Green slot"
    dependsOn: Deploy_to_Green
    jobs:
      - job: HealthCheck
        steps:
          - script: |
              # Test Green slot (no production traffic yet)
              GREEN_URL="https://app-curso-prod-green.azurewebsites.net"
              for i in {1..10}; do
                STATUS=$(curl -s -o /dev/null -w "%{http_code}" $GREEN_URL/health)
                if [ "$STATUS" != "200" ]; then
                  echo "Health check failed: $STATUS"
                  exit 1
                fi
                echo "Health check $i: OK"
                sleep 2
              done

  - stage: Switch_Traffic
    displayName: "Swap Blue ↔ Green"
    dependsOn: Smoke_Tests
    jobs:
      - deployment: SwapSlots
        environment: production
        strategy:
          runOnce:
            deploy:
              steps:
                # Manual approval required (configured in environment)
                - task: AzureAppServiceManage@0
                  inputs:
                    azureSubscription: 'sc-azure-prod'
                    Action: 'Swap Slots'
                    WebAppName: 'app-curso-prod'
                    SourceSlot: 'green'
                    SwapWithProduction: true
                    PreserveVnet: true
```

**Sticky settings (NO sigan al swap):**
```bash
# Mark estas settings como "slot-specific"
az webapp config appsettings set \
  --name app-curso-prod \
  --resource-group rg-prod \
  --slot-settings \
    DATABASE_CONNECTION="<slot-specific-value>" \
    LOG_LEVEL="<slot-specific-value>"

# Result:
# Blue → connects to prod DB
# Green → connects to test DB (during deploy)
# Swap: settings stay with their slot
```

**Pros y contras:**

| | Pros | Contras |
|---|---|---|
| **Blue/Green** | Switch instant, easy rollback | 2x cost (running both) |
| **Rolling** | Cheap (no extra resources) | Slow (gradual), partial state |
| **Recreate** | Simple | Downtime |
| **Canary** | Risk-controlled | Complex to set up |

**Cuándo Blue/Green:**
- ✅ Apps stateless
- ✅ Schema DB compatible v1 + v2 simultáneamente  
- ✅ Coste 2x justificado por safety
- ✅ Required: zero-downtime deployments

**Cuándo NO:**
- ❌ DB schema breaking changes
- ❌ Stateful apps con sessions
- ❌ Coste prohibitivo

## Slide 20 — Deployment Stacks: lifecycle management

Deployment Stacks (GA 2024) reemplaza Azure Blueprints (deprecated):

```
Problema sin Stacks:
├── Bicep deploy crea recursos
├── Si quitas un recurso del Bicep, se queda en Azure (orphan)
├── Manual cleanup → mistakes
└── No versioning del deployment overall

Con Stacks:
├── Stack = unidad lifecycle
├── Recursos pertenecen al stack
├── Update stack = sync state (delete orphans automatically)
├── Delete stack = delete TODOS los recursos del stack
└── Versioning, audit, rollback
```

**Crear deployment stack:**
```bash
# Subscription scope
az stack sub create \
  --name "stack-prod-curso" \
  --location westeurope \
  --template-file main.bicep \
  --parameters env=prod \
  --action-on-unmanage detachAll \
  --deny-settings-mode denyDelete

# Resource group scope
az stack group create \
  --name "stack-app-curso" \
  --resource-group rg-prod \
  --template-file app.bicep \
  --action-on-unmanage deleteAll \
  --deny-settings-mode denyWriteAndDelete \
  --deny-settings-excluded-actions "Microsoft.Web/sites/restart/action" \
  --deny-settings-excluded-principals "<my-mi-id>"
```

**Action on unmanage modes:**

| Mode | Behavior |
|---|---|
| `detachAll` | Recursos quedan, pero ya no son del stack |
| `deleteResources` | Borra solo recursos (mantiene RGs) |
| `deleteAll` | Borra recursos + RGs |

**Deny Settings (proteger contra cambios manuales):**

```bash
# Modes:
# - none: No protection
# - denyDelete: Cannot delete from portal/CLI
# - denyWriteAndDelete: Cannot modify or delete

# Útil para: enforce que cambios SOLO via stack update
az stack group create \
  --name stack-prod \
  --resource-group rg-prod \
  --template-file main.bicep \
  --deny-settings-mode denyWriteAndDelete

# Excepciones permitidas
az stack group create \
  --name stack-prod \
  --resource-group rg-prod \
  --template-file main.bicep \
  --deny-settings-mode denyWriteAndDelete \
  --deny-settings-excluded-actions \
    "Microsoft.Web/sites/restart/action" \
    "Microsoft.KeyVault/vaults/secrets/setSecret/action"
```

**Update lifecycle:**
```bash
# Day 1: Crear stack con Bicep que tiene 5 recursos
az stack group create --name stack-app -g rg-prod \
  --template-file v1.bicep --action-on-unmanage deleteAll

# Day 30: Bicep ahora tiene 4 recursos (eliminaste 1)
az stack group create --name stack-app -g rg-prod \
  --template-file v2.bicep --action-on-unmanage deleteAll
# → Recurso eliminado automáticamente

# Day 60: Quieres borrar TODO
az stack group delete --name stack-app -g rg-prod --yes
# → Borra los 4 recursos + el stack
```

**Pipeline integration:**
```yaml
- task: AzureCLI@2
  inputs:
    azureSubscription: 'sc-azure-prod'
    scriptType: 'bash'
    scriptLocation: 'inlineScript'
    inlineScript: |
      az stack group create \
        --name stack-prod-$(Build.BuildId) \
        --resource-group rg-prod \
        --template-file infra/main.bicep \
        --parameters infra/main.prod.bicepparam \
        --action-on-unmanage detachAll \
        --deny-settings-mode denyWriteAndDelete \
        --yes
```

**Deployment Stacks vs alternatives:**

| | Stacks | Bicep what-if | ARM templates |
|---|:---:|:---:|:---:|
| Lifecycle mgmt | ✅ | ❌ | ❌ |
| Drift detection | ✅ | Partial | ❌ |
| Bulk delete | ✅ | ❌ | Manual |
| Deny settings | ✅ | ❌ | ❌ |
| GA status | 2024 | GA | GA |


## Slide 24 — Database migration patterns

Cambios DB son los más arriesgados — patterns para safe deploys:

```
Estrategias de migración DB:

┌─────────────────────────────────────────────────────────────┐
│ EXPAND-CONTRACT (recommended)                                │
├─────────────────────────────────────────────────────────────┤
│ 1. EXPAND: Add new column/table (backwards compatible)      │
│ 2. Deploy new code that uses both old + new                 │
│ 3. MIGRATE data en background                               │
│ 4. Switch reads to new column                               │
│ 5. CONTRACT: Remove old column (after stable)               │
└─────────────────────────────────────────────────────────────┘
```

**Ejemplo: rename column "customer_name" → "full_name":**
```sql
-- ❌ NUNCA: breaking change directo
ALTER TABLE customers RENAME COLUMN customer_name TO full_name;
-- App old: queries break
-- App new: requires deploy first
-- 5 min downtime guaranteed

-- ✅ EXPAND-CONTRACT pattern:

-- Sprint 1: EXPAND
ALTER TABLE customers ADD full_name NVARCHAR(200);
UPDATE customers SET full_name = customer_name WHERE full_name IS NULL;
CREATE TRIGGER trg_sync_name ON customers
  AFTER INSERT, UPDATE
  AS BEGIN
    UPDATE customers SET full_name = customer_name 
    WHERE id IN (SELECT id FROM inserted) AND full_name != customer_name;
    UPDATE customers SET customer_name = full_name 
    WHERE id IN (SELECT id FROM inserted) AND customer_name != full_name;
  END;

-- Deploy app code que reads de full_name (writes ambos)
-- Both columns en sync via trigger

-- Sprint 2: MIGRATE
-- Backfill complete (todos los rows have full_name)
-- Verify ambas columns en sync

-- Sprint 3: SWITCH WRITES
-- App ahora solo writes a full_name
-- Trigger todavía sync (safety net)

-- Sprint 4: CONTRACT
DROP TRIGGER trg_sync_name;
ALTER TABLE customers DROP COLUMN customer_name;
-- Done: zero-downtime migration
```

**EF Core migration patterns:**
```bash
# Crear migration
dotnet ef migrations add AddFullNameColumn

# Inspeccionar SQL
dotnet ef migrations script LastMigration NewMigration > migration.sql

# Apply via pipeline (NOT en runtime)
dotnet ef database update --connection "$DB_CONNECTION"
```

**Pipeline DB migration (con flyway o dbup):**
```yaml

    - deployment: MigrateDatabase
      environment: prod-db
      strategy:

          deploy:
            steps:
              # Backup first
              - task: AzureCLI@2
                displayName: 'Backup database'

                  azureSubscription: 'sc-azure-prod'
                  scriptType: 'bash'
                  scriptLocation: 'inlineScript'
                  inlineScript: |
                    BACKUP_NAME="backup-$(Build.BuildId)"
                    az sql db copy \
                      --name prod-curso \
                      --dest-name $BACKUP_NAME \
                      --resource-group rg-prod \
                      --server sql-prod
              
              # Run migrations
              - task: DotNetCoreCLI@2
                displayName: 'Run EF migrations'
                inputs:
                  command: 'custom'
                  custom: 'ef'
                  arguments: 'database update --connection "$(DB_CONNECTION)"'
              
              # Validate
              - script: |
                  # Test critical queries
                  sqlcmd -S sql-prod.database.windows.net \
                         -d prod-curso \
                         -U $(DB_USER) -P $(DB_PASSWORD) \
                         -Q "SELECT TOP 1 full_name FROM customers"
                displayName: 'Validate migration'
```

**Schema versioning:**
```sql
-- Tabla de control de versiones
CREATE TABLE __SchemaVersions (
    Version NVARCHAR(50) PRIMARY KEY,
    AppliedAt DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    AppliedBy NVARCHAR(100) NOT NULL,
    ScriptHash NVARCHAR(100) NOT NULL,
    DurationMs INT
);

-- En cada migration:
INSERT INTO __SchemaVersions (Version, AppliedBy, ScriptHash)
VALUES ('2026.04.01.001', 'pipeline-$(Build.BuildId)', '<hash>');
```

**Rollback DB plan:**
```bash
# Plan A: Forward fix (preferred)
# - Identify issue
# - Apply corrective migration
# - No data loss

# Plan B: Restore from backup (last resort)
az sql db restore \
  --name prod-curso \
  --dest-name prod-curso-restored \
  --time "2026-04-22T12:00:00Z" \
  --resource-group rg-prod \
  --server sql-prod

# Plan C: Read replica failover (DR scenario)
az sql db replica set-primary \
  --name prod-curso \
  --server sql-secondary \
  --resource-group rg-prod
```

**Anti-patterns a evitar:**
```
❌ ALTER TABLE ... DROP COLUMN sin expand-contract
❌ DROP TABLE sin verificar references
❌ Migrations gigantes (1000+ líneas)
❌ Migrations not idempotent
❌ No backup antes de prod migrations
❌ Schema changes en horario laboral peak
```

## Slide 26 — Disaster Recovery patterns

DR plan documentado para producción crítica:

```
DR objectives:
├── RTO (Recovery Time Objective): tiempo máximo down
│   └── Critical apps: 1 hour, others: 24 hours
└── RPO (Recovery Point Objective): pérdida máxima de datos
    └── Critical: 15 min, others: 1 hour
```

**Multi-region active-passive setup:**
```
                    Traffic Manager / Front Door
                              │
              ┌───────────────┴───────────────┐
              │                               │
        PRIMARY (West Europe)         SECONDARY (North Europe)
              │                               │
        ┌─────┴─────┐                   ┌─────┴─────┐
        │ App Svc   │                   │ App Svc   │
        │ (active)  │                   │ (passive) │
        └─────┬─────┘                   └─────┬─────┘
              │                               │
        ┌─────┴─────┐                   ┌─────┴─────┐
        │ SQL DB    │ ───geo-replica───→│ SQL DB    │
        │ (primary) │                   │ (secondary)│
        └───────────┘                   └───────────┘
        ┌─────┴─────┐                   ┌─────┴─────┐
        │ Storage   │ ───GRS replic.───→│ Storage   │
        │ (primary) │                   │ (secondary)│
```

**Failover procedure (manual triggered):**
```bash
#!/bin/bash
# dr-failover.sh — DR failover automation

echo "=== DR FAILOVER PROCEDURE ==="
echo "WARNING: This will switch production to secondary region"
read -p "Confirm failover? (type 'CONFIRM'): " CONFIRM
[ "$CONFIRM" != "CONFIRM" ] && exit 1

# 1. Failover SQL Database
echo "Failing over SQL Database..."
az sql failover-group set-primary \
  --name fg-prod \
  --resource-group rg-prod \
  --server sql-secondary

# 2. Update Traffic Manager (force secondary)
echo "Updating Traffic Manager..."
az network traffic-manager endpoint update \
  --name primary-weu \
  --profile-name tm-curso \
  --resource-group rg-network \
  --type azureEndpoints \
  --endpoint-status Disabled

# 3. Update Function Apps secrets (point to secondary KV if needed)
# 4. Notify team
curl -X POST $TEAMS_WEBHOOK \
  -d '{"text":"⚠️ DR FAILOVER EXECUTED to secondary region"}'

echo "Failover complete. Verify with smoke tests."
```

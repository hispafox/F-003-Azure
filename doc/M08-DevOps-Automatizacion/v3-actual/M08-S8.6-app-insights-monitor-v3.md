## Slide 2 — Observabilidad: los tres pilares
Un sistema observable tiene tres pilares: métricas (qué pasa), logs (por qué pasa) y traces (cómo fluye una petición a través de los servicios).

**Métricas:** Números que cambian con el tiempo (CPU, latencia, errores/segundo). Para dashboards y alertas.
**Logs:** Eventos con detalle (excepciones, mensajes de debug, audit trail). Para investigar problemas.
**Traces:** El camino de una petición desde el frontend hasta la DB y vuelta. Para entender dependencias.

Application Insights cubre los tres pilares para aplicaciones. Azure Monitor es la plataforma general que incluye App Insights.

## Slide 4 — Custom telemetry: lo que auto-tracking no captura

```csharp
public class PedidoService
{
    private readonly TelemetryClient _telemetry;
    
    public async Task<Pedido> CrearPedidoAsync(CrearPedidoDto dto)
    {
        // Evento custom
        _telemetry.TrackEvent("PedidoCreado", new Dictionary<string, string>
        {
            ["clienteId"] = dto.ClienteId,
            ["itemCount"] = dto.Items.Count.ToString()
        }, new Dictionary<string, double>
        {
            ["total"] = (double)dto.Total
        });
        
        // Métrica custom
        _telemetry.GetMetric("PedidosCreados").TrackValue(1);
        _telemetry.GetMetric("ImportePedido").TrackValue((double)dto.Total);
        
        // Dependency tracking manual (para servicios no-HTTP)
        using var op = _telemetry.StartOperation<DependencyTelemetry>("InventarioService");
        op.Telemetry.Type = "InternalAPI";
        op.Telemetry.Target = "inventario-service";
        try
        {
            var result = await _inventario.ReservarAsync(dto.Items);
            op.Telemetry.Success = true;
            return result;
        }
        catch (Exception ex)
        {
            op.Telemetry.Success = false;
            _telemetry.TrackException(ex);
            throw;
        }
    }
}
```

## Slide 5 — KQL: el lenguaje de queries de App Insights

```kusto
// Top 10 endpoints más lentos (últimas 24h)
requests
| where timestamp > ago(24h)
| summarize avgDuration=avg(duration), count=count() by name
| where count > 100
| order by avgDuration desc
| take 10

// Tasa de errores por hora
requests
| where timestamp > ago(7d)
| summarize total=count(), errores=countif(resultCode >= 500) by bin(timestamp, 1h)
| extend tasaError = round(errores * 100.0 / total, 2)
| where tasaError > 0
| render timechart

// Excepciones agrupadas por tipo
exceptions
| where timestamp > ago(24h)
| summarize count() by type, outerMessage
| order by count_ desc

// Dependencias lentas (DB, APIs)
dependencies
| where timestamp > ago(24h)
| where duration > 1000
| summarize avg(duration), count() by target, type, name
| order by avg_duration desc

// Buscar por correlation ID
union requests, dependencies, exceptions, traces
| where operation_Id == "abc-123-correlation-id"
| order by timestamp asc
```

**Zero configuración.** Solo necesitáis App Insights habilitado. Las alertas llegan por email al equipo.

## Slide 12 — Sampling: controlar el volumen de telemetría

App Insights cobra por GB ingestado (~2.30€/GB). Para apps de alto tráfico, el coste puede ser significativo.

```csharp
// Sampling adaptativo (por defecto): App Insights ajusta el % automáticamente
builder.Services.AddApplicationInsightsTelemetry(options =>
{
    options.EnableAdaptiveSampling = true;  // Default
});

// Sampling fijo: capturar solo el 25% de los eventos
builder.Services.Configure<TelemetryConfiguration>(config =>
{
    var builder = config.DefaultTelemetrySink.TelemetryProcessorChainBuilder;
    builder.UseSampling(25);  // 25% de los eventos
    builder.Build();
});

// Excluir tipos específicos del sampling (siempre capturar excepciones)
builder.Services.AddApplicationInsightsTelemetry(options =>
{
    options.EnableAdaptiveSampling = true;
});
// En host.json (Functions):
{
  "logging": {
    "applicationInsights": {
      "samplingSettings": {
        "isEnabled": true,
        "excludedTypes": "Request;Exception"  // Siempre capturar requests y exceptions
      }
    }
  }
}
```

## Slide 13 — Azure Monitor: más allá de App Insights

Azure Monitor es la plataforma general que incluye:
- **App Insights:** Telemetría de aplicaciones
- **Log Analytics:** Workspace centralizado para logs de TODOS los servicios Azure
- **Metrics:** Métricas de infraestructura (CPU, memory, disk)
- **Alerts:** Reglas y notificaciones
- **Dashboards:** Visualización
- **Workbooks:** Informes interactivos
- **Autoscale:** Escalado basado en métricas

```bash
# Crear Log Analytics Workspace (centralizar logs)
az monitor log-analytics workspace create \
  --workspace-name log-ventas-prod -g rg-ventas-prod --location westeurope

# Conectar App Insights al workspace
az monitor app-insights component update \
  --app ai-ventas-prod -g rg-ventas-prod \
  --workspace "/subscriptions/<id>/.../workspaces/log-ventas-prod"
```

**Centralizar logs** de App Service, Functions, Cosmos DB, SQL, Storage, Key Vault en un solo Log Analytics Workspace. Una sola query para buscar en todo.

## Slide 19 — Correlation: trazar un problema end-to-end

```kusto
// Encontrar todas las operaciones de un usuario en la última hora
let userId = "pedro@empresa.com";
union requests, dependencies, exceptions, traces, customEvents
| where timestamp > ago(1h)
| where customDimensions.userId == userId or user_AuthenticatedId == userId
| project timestamp, itemType, name, duration, success, 
    operation_Id, operation_ParentId
| order by timestamp asc

// Resultado: timeline completa de lo que hizo el usuario
// 10:00:00 request    GET /api/productos         200   150ms
// 10:00:00 dependency cosmos-ventas ReadItem      OK    8ms
// 10:00:15 request    POST /api/pedidos          500   2100ms
// 10:00:15 dependency cosmos-ventas CreateItem    FAIL  2000ms
// 10:00:15 exception  CosmosException: 429        —     —
```

La operation_Id vincula request → dependency → exception. Sin correlation, tenéis logs aislados que no cuentan la historia completa.

## Slide 21 — Runbook de respuesta a incidentes

```
ALERTA: "ventas-5xx" disparada (>5 errores en 5 min)

1. DETECTAR (0-2 min)
   └─ Revisar Live Metrics → ¿errores activos?
   └─ App Insights → Failures → ¿qué endpoint falla?

2. DIAGNOSTICAR (2-10 min)
   └─ Transaction Search → operation_Id del error
   └─ ¿Dependency failure? (DB, API externa, Service Bus)
   └─ ¿Exception? (código, null reference, timeout)
   └─ ¿Deployment reciente? (correlacionar con pipeline runs)

3. MITIGAR (10-20 min)
   └─ Si deployment reciente → rollback (swap slots)
   └─ Si dependency → verificar health del servicio dependiente
   └─ Si throttling (429) → escalar (RU, instancias)
   └─ Si bug en código → feature flag OFF + fix + redeploy

4. RESOLVER (20 min - horas)
   └─ Root cause analysis
   └─ Fix permanente + tests
   └─ Actualizar runbook si es un escenario nuevo

5. POST-MORTEM
   └─ Documentar: qué pasó, por qué, cómo se resolvió
   └─ Acción preventiva: ¿cómo evitar que vuelva a pasar?
```

```csharp
// Program.cs
using Azure.Monitor.OpenTelemetry.AspNetCore;
using OpenTelemetry.Trace;
using OpenTelemetry.Metrics;
using OpenTelemetry.Resources;

var builder = WebApplication.CreateBuilder(args);

// Option 1: Azure Monitor distro (Microsoft recommended)
builder.Services.AddOpenTelemetry()
    .UseAzureMonitor(options =>
    {
        options.ConnectionString = builder.Configuration["APPLICATIONINSIGHTS_CONNECTION_STRING"];
        options.SamplingRatio = 1.0f;  // 100% (adjust for production)
    });

// Option 2: Manual setup with multiple exporters
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService(
        serviceName: "api-pedidos",
        serviceVersion: "2.0.0",
        serviceInstanceId: Environment.MachineName))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation(opts =>
        {
            opts.RecordException = true;
            opts.Filter = ctx => !ctx.Request.Path.StartsWithSegments("/health");
        })
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation(opts =>
        {
            opts.SetDbStatementForText = true;  // Capture SQL queries
        })
        .AddSource("MiApp.Custom")  // Custom activity source
        // Multiple exporters
        .AddAzureMonitorTraceExporter(opts =>
        {
            opts.ConnectionString = builder.Configuration["AppInsightsConnection"];
        })
        .AddOtlpExporter(opts =>
        {
            opts.Endpoint = new Uri("http://otel-collector:4317");
        }))
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()
        .AddMeter("MiApp.Custom")
        .AddAzureMonitorMetricExporter()
        .AddPrometheusExporter());

var app = builder.Build();

// Prometheus scrape endpoint
app.MapPrometheusScrapingEndpoint();

app.Run();
```

**Custom instrumentation:**
```csharp
public class OrderService
{
    private static readonly ActivitySource ActivitySource = new("MiApp.Custom");
    private static readonly Meter Meter = new("MiApp.Custom");
    
    private readonly Counter<long> _ordersCreated = Meter.CreateCounter<long>(
        "orders.created",
        unit: "{order}",
        description: "Total orders created");
    
    private readonly Histogram<double> _orderProcessingDuration = Meter.CreateHistogram<double>(
        "order.processing.duration",
        unit: "ms",
        description: "Order processing duration");
    
    public async Task<Order> CreateOrderAsync(OrderRequest request)
    {
        // Custom span/activity
        using var activity = ActivitySource.StartActivity("CreateOrder", ActivityKind.Internal);
        activity?.SetTag("order.customer_id", request.CustomerId);
        activity?.SetTag("order.amount", request.Total);
        activity?.SetTag("order.items_count", request.Items.Count);
        
        var stopwatch = Stopwatch.StartNew();
        
        try
        {
            // Validate
            using (var validateActivity = ActivitySource.StartActivity("ValidateOrder"))
            {
                await ValidateOrderAsync(request);
                validateActivity?.SetTag("validation.passed", true);
            }
            
            // Save
            using (var saveActivity = ActivitySource.StartActivity("SaveOrder"))
            {
                await _db.Orders.AddAsync(new Order(request));
                await _db.SaveChangesAsync();
            }
            
            // Notify
            using (var notifyActivity = ActivitySource.StartActivity("NotifyCustomer"))
            {
                await _notificationService.SendAsync(request.CustomerId);
            }
            
            // Custom metrics
            _ordersCreated.Add(1, new KeyValuePair<string, object?>("priority", request.Priority));
            
            activity?.SetStatus(ActivityStatusCode.Ok);
            return order;
        }
        catch (Exception ex)
        {
            activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
            activity?.RecordException(ex);
            throw;
        }
        finally
        {
            stopwatch.Stop();
            _orderProcessingDuration.Record(stopwatch.ElapsedMilliseconds);
        }
    }
}
```

```csharp
{
    public async Task InvokeAsync(HttpContext context)
    {
        var currentActivity = Activity.Current;
        if (currentActivity != null)
        {
            // Trace context details
            var traceId = currentActivity.TraceId;

            var parentSpanId = currentActivity.ParentSpanId;
            
            // Custom enrichment
```

```kusto
| extend EstimatedCostEUR = TotalGB * 2.5
| where EstimatedCostEUR > 300  // €300/day = €9K/mes
```

## Slide 29 — Incident response automation

Automate IR para reducir MTTR (Mean Time to Resolve):

```
Manual incident response:
├── 5 min: Alert fired
├── 5 min: Engineer notified
├── 10 min: Engineer logs in
├── 15 min: Investigate root cause
├── 10 min: Apply fix
└── Total MTTR: 45 min

Automated IR:
├── 5 min: Alert fired
├── 30 sec: Auto-runbook executes
├── Self-healed o human only if escalation
└── Total: 5 min average
```

**Logic Apps playbook completo:**
```yaml
# Trigger: Sentinel incident OR App Insights alert
trigger:
  type: SentinelIncident
  severity: high

steps:
  # 1. Enrich with context
  - getIncidentDetails:
      incidentId: ${{ trigger.incidentId }}
  
  # 2. Determine playbook
  - switch:
      input: ${{ getIncidentDetails.tags }}
      cases:
        - case: ["sql", "performance"]
          actions:
            - executeSqlPerformancePlaybook
        - case: ["auth", "brute-force"]
          actions:
            - blockIPInFirewall
            - disableUserTemporarily
        - case: ["application", "crash"]
          actions:
            - restartAppService
            - rollbackDeploymentIfRecent
  
  # 3. Notify team
  - parallel:
      - sendTeamsMessage:
          channel: "#incidents"
          message: "Auto-response executed for ${{ trigger.title }}"
      
      - createJiraTicket:
          project: OPS
          summary: ${{ trigger.title }}
          description: ${{ getIncidentDetails }}
      
      - if: ${{ trigger.severity == 'critical' }}
        then:
          - pagerdutyAlert:
              service: "Production"
              severity: critical
  
  # 4. Wait for human verification
  - waitForApproval:
      timeout: 30m
      approvers: oncall@empresa.com
  
  # 5. Post-incident
  - createPostmortemTemplate
  - scheduleReview
```

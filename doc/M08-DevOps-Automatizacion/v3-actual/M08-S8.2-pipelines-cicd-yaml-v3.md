## Slide 2 — Por qué YAML y no Classic (visual)
Azure DevOps tiene dos formas de crear pipelines: Classic (editor visual, point-and-click) y YAML (código).

**YAML es la forma correcta:**
- Pipeline as Code: vive en el repo, versionado con Git
- Revisable en Pull Requests (cambio en el pipeline = cambio en el código)
- Reproducible: el mismo YAML produce el mismo resultado
- Portátil: podéis copiar entre proyectos
- Branching: cada rama puede tener su propio pipeline
- Template: reutilizar steps entre pipelines

**Classic está en modo mantenimiento.** Microsoft recomienda YAML para todo nuevo desarrollo.

## Slide 3 — Anatomía de un pipeline YAML

```yaml
# azure-pipelines.yml
trigger:                    # ¿Cuándo se ejecuta?
  branches:
    include: [main]
  paths:
    include: [src/*]

pool:                       # ¿Dónde se ejecuta?
  vmImage: 'ubuntu-latest'

variables:                  # Variables reutilizables
  buildConfiguration: 'Release'
  dotnetVersion: '8.x'

stages:                     # Fases del pipeline
- stage: Build              # Fase 1: Build + Test
  jobs:
  - job: BuildAndTest
    steps:                  # Pasos a ejecutar
    - task: UseDotNet@2
      inputs:
        version: $(dotnetVersion)
    - script: dotnet build -c $(buildConfiguration)
    - script: dotnet test --no-build -c $(buildConfiguration)
    - publish: $(Build.ArtifactStagingDirectory)
      artifact: app

- stage: Deploy             # Fase 2: Deploy
  dependsOn: Build
  jobs:
  - deployment: DeployToAzure
    environment: production
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs:
              appName: 'app-ventas-prod'
              package: '$(Pipeline.Workspace)/app/**/*.zip'
```

## Slide 4 — Triggers: cuándo se ejecuta el pipeline

```yaml
# Trigger en push a main
trigger:
  branches:
    include: [main]
    exclude: [feature/experimental/*]
  paths:
    include: [src/*, tests/*]
    exclude: [docs/*, '*.md']

# Trigger en Pull Request (CI para validar antes de merge)
pr:
  branches:
    include: [main]
  paths:
    include: [src/*]

# Trigger programado (nightly build)
schedules:
- cron: '0 2 * * *'  # Cada noche a las 2:00 UTC
  displayName: 'Nightly Build'
  branches:
    include: [main]
  always: true  # Ejecutar aunque no haya cambios

# Sin trigger automático (manual only)
trigger: none
```

## Slide 5 — Stages, Jobs y Steps: la jerarquía

```yaml
stages:                          # Nivel 1: Fases secuenciales
├── stage: Build                 # Fase de build
│   jobs:                        # Nivel 2: Jobs paralelos dentro del stage
│   ├── job: BuildDotNet         # Job 1 (puede ejecutarse en paralelo con job 2)
│   │   steps:                   # Nivel 3: Steps secuenciales dentro del job
│   │   ├── step: checkout       # Descargar código
│   │   ├── step: build          # Compilar
│   │   └── step: test           # Ejecutar tests
│   └── job: BuildFrontend       # Job 2 (en paralelo)
│       steps:
│       ├── step: npm install
│       └── step: npm build
│
├── stage: DeployStaging         # Fase de deploy a staging
│   dependsOn: Build             # Después de Build
│   jobs:
│   └── deployment: DeployStg
│
└── stage: DeployProd            # Fase de deploy a producción
    dependsOn: DeployStaging     # Después de Staging
    condition: succeeded()       # Solo si staging fue OK
    jobs:
    └── deployment: DeployPrd
```

## Slide 6 — Pipeline CI completo para App Service .NET

```yaml
trigger:
  branches: { include: [main] }
  paths: { include: ['src/VentasApi/*'] }

pool:
  vmImage: 'ubuntu-latest'

variables:
  buildConfiguration: 'Release'
  projectPath: 'src/VentasApi/VentasApi.csproj'
  testPath: 'tests/VentasApi.Tests/VentasApi.Tests.csproj'

stages:
- stage: Build
  displayName: 'Build + Test'
  jobs:
  - job: Build
    steps:
    - task: UseDotNet@2
      displayName: 'Install .NET 8'
      inputs: { version: '8.x' }

    - script: dotnet restore $(projectPath)
      displayName: 'Restore packages'

    - script: dotnet build $(projectPath) -c $(buildConfiguration) --no-restore
      displayName: 'Build'

    - script: dotnet test $(testPath) -c $(buildConfiguration) --no-build --collect:"XPlat Code Coverage" --logger trx
      displayName: 'Run tests'

    - task: PublishTestResults@2
      displayName: 'Publish test results'
      inputs:
        testResultsFormat: 'VSTest'
        testResultsFiles: '**/*.trx'

    - task: PublishCodeCoverageResults@2
      displayName: 'Publish code coverage'
      inputs:
        summaryFileLocation: '**/coverage.cobertura.xml'

    - script: dotnet publish $(projectPath) -c $(buildConfiguration) -o $(Build.ArtifactStagingDirectory)/publish
      displayName: 'Publish'

    - task: ArchiveFiles@2
      displayName: 'Zip artifacts'
      inputs:
        rootFolderOrFile: '$(Build.ArtifactStagingDirectory)/publish'
        archiveType: 'zip'
        archiveFile: '$(Build.ArtifactStagingDirectory)/app.zip'

    - publish: $(Build.ArtifactStagingDirectory)/app.zip
      artifact: webapp
      displayName: 'Upload artifact'
```

## Slide 7 — Pipeline CD: deploy a staging y swap a producción

```yaml
- stage: DeployStaging
  displayName: 'Deploy to Staging'
  dependsOn: Build
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: DeployStaging
    displayName: 'Deploy to staging slot'
    environment: 'ventas-staging'
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            displayName: 'Deploy to staging'
            inputs:
              azureSubscription: 'Azure-Ventas-Prod'
              appType: 'webApp'
              appName: 'app-ventas-prod'
              slotName: 'staging'
              package: '$(Pipeline.Workspace)/webapp/app.zip'

          - task: AzureAppServiceManage@0
            displayName: 'Start staging slot'
            inputs:
              azureSubscription: 'Azure-Ventas-Prod'
              Action: 'Start Azure App Service'
              WebAppName: 'app-ventas-prod'
              SpecifySlotOrASE: true
              Slot: 'staging'

- stage: SwapToProduction
  displayName: 'Swap Staging → Production'
  dependsOn: DeployStaging
  jobs:
  - deployment: SwapSlots
    displayName: 'Swap slots'
    environment: 'ventas-production'  # Requiere aprobación manual
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureAppServiceManage@0
            displayName: 'Swap staging to production'
            inputs:
              azureSubscription: 'Azure-Ventas-Prod'
              Action: 'Swap Slots'
              WebAppName: 'app-ventas-prod'
              ResourceGroupName: 'rg-ventas-prod'
              SourceSlot: 'staging'
```

## Slide 9 — Variables y Variable Groups

```yaml
# Variables inline
variables:
  buildConfiguration: 'Release'
  azureSubscription: 'Azure-Ventas-Prod'

# Variable Group (definida en Library, reutilizable entre pipelines)
variables:
- group: 'ventas-shared-vars'  # Contiene: AppName, ResourceGroup, etc.
- group: 'ventas-secrets'       # Linked to Key Vault

# Variables secretas (de Key Vault)
variables:
- group: 'kv-ventas-secrets'
# Las variables del grupo se inyectan automáticamente:
# $(StripeApiKey), $(SendGridApiKey), etc.
```

**Variable Groups linked to Key Vault:**
Library → Variable Groups → New → "Link secrets from Azure Key Vault" → Seleccionar KV → Seleccionar secretos → Los secretos se inyectan como variables del pipeline (enmascarados en logs).

## Slide 11 — Pipeline para MSIX

```yaml
trigger:
  branches: { include: [main] }
  paths: { include: ['src/Desktop/*'] }

variables:
  version: '2.4.$(Build.BuildId).0'

stages:
- stage: BuildMSIX
  jobs:
  - job: Build
    pool: { vmImage: 'windows-latest' }  # Windows obligatorio para MSIX
    steps:
    - task: UseDotNet@2
      inputs: { version: '8.x' }

    # Actualizar versión en manifest
    - powershell: |
        (Get-Content src/Desktop/Package/Package.appxmanifest) `
          -replace 'Version="[\d.]+"', "Version=`"$(version)`"" |
          Set-Content src/Desktop/Package/Package.appxmanifest

    # Build MSIX
    - task: MSBuild@1
      inputs:
        solution: 'src/Desktop/Package/Package.wapproj'
        platform: 'x64'
        configuration: 'Release'
        msbuildArguments: '/p:AppxPackageDir="$(Build.ArtifactStagingDirectory)/" /p:UapAppxPackageBuildMode=SideLoadOnly'

    # Firmar con Azure Key Vault
    - script: |
        dotnet tool install --global AzureSignTool
        AzureSignTool sign \
          --azure-key-vault-url "$(KeyVaultUrl)" \
          --azure-key-vault-certificate "msix-signing-cert" \
          --azure-key-vault-managed-identity true \
          --timestamp-rfc3161 "http://timestamp.digicert.com" \
          --file-digest sha256 \
          "$(Build.ArtifactStagingDirectory)/*.msix"

    - publish: $(Build.ArtifactStagingDirectory)
      artifact: msix

- stage: PublishMSIX
  dependsOn: BuildMSIX
  jobs:
  - deployment: Publish
    environment: 'msix-production'
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureCLI@2
            inputs:
              azureSubscription: 'Azure-Ventas-Prod'
              scriptType: 'bash'
              scriptLocation: 'inlineScript'
              inlineScript: |
                # Subir MSIX a Blob Storage
                az storage blob upload-batch \
                  --account-name stventasprod --destination msix \
                  --source $(Pipeline.Workspace)/msix --overwrite
                
                # Actualizar AppInstaller con nueva versión
                cat > appinstaller.xml << EOF
                <?xml version="1.0" encoding="utf-8"?>
                <AppInstaller Uri="https://stventasprod.blob.core.windows.net/msix/VentasDesktop.appinstaller"
                  Version="$(version)" xmlns="http://schemas.microsoft.com/appx/appinstaller/2018">
                  <MainPackage Name="MiEmpresa.VentasDesktop" Version="$(version)"
                    Publisher="CN=MiEmpresa, O=MiOrg" ProcessorArchitecture="x64"
                    Uri="https://stventasprod.blob.core.windows.net/msix/VentasDesktop_$(version)_x64.msix" />
                  <UpdateSettings>
                    <OnLaunch HoursBetweenUpdateChecks="1" ShowPrompt="true" />
                    <AutomaticBackgroundTask />
                  </UpdateSettings>
                </AppInstaller>
                EOF
                az storage blob upload --account-name stventasprod --container-name msix \
                  --file appinstaller.xml --name VentasDesktop.appinstaller --overwrite
```

## Slide 12 — Templates: reutilizar entre pipelines

```yaml
# templates/dotnet-build.yml (template reutilizable)
parameters:
- name: projectPath
  type: string
- name: configuration
  type: string
  default: 'Release'

steps:
- task: UseDotNet@2
  inputs: { version: '8.x' }
- script: dotnet restore ${{ parameters.projectPath }}
- script: dotnet build ${{ parameters.projectPath }} -c ${{ parameters.configuration }} --no-restore
- script: dotnet test ${{ parameters.projectPath }} -c ${{ parameters.configuration }} --no-build

# azure-pipelines.yml (pipeline que usa el template)
stages:
- stage: Build
  jobs:
  - job: BuildApi
    steps:
    - template: templates/dotnet-build.yml
      parameters:
        projectPath: 'src/VentasApi/VentasApi.csproj'

  - job: BuildFunctions
    steps:
    - template: templates/dotnet-build.yml
      parameters:
        projectPath: 'src/Functions/Functions.csproj'
```

**Templates reducen duplicación.** Si tenéis 5 pipelines que hacen build .NET, cambiad el template y los 5 se actualizan.

## Slide 13 — Conditions: control de flujo

```yaml
# Solo deploy a producción si es merge a main
- stage: DeployProd
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))

# Deploy a staging para cualquier PR (para testing)
- stage: DeployStaging
  condition: eq(variables['Build.Reason'], 'PullRequest')

# Ejecutar step solo si el anterior falló
- script: echo "Build falló, enviando notificación"
  condition: failed()

# Ejecutar step solo si una variable tiene cierto valor
- script: echo "Deploy canary"
  condition: eq(variables['deployType'], 'canary')

# Siempre ejecutar (cleanup)
- script: echo "Limpiando recursos temporales"
  condition: always()
```

## Slide 16 — Caching: acelerar builds

```yaml
# Cache de paquetes NuGet (no descarga cada vez)
- task: Cache@2
  inputs:
    key: 'nuget | "$(Agent.OS)" | **/packages.lock.json'
    restoreKeys: |
      nuget | "$(Agent.OS)"
    path: $(NUGET_PACKAGES)

# Cache de node_modules (para frontends)
- task: Cache@2
  inputs:
    key: 'npm | "$(Agent.OS)" | package-lock.json'
    path: node_modules
```

**Impacto:** Un restore de NuGet que tarda 30 segundos pasa a 2 segundos con cache. Para builds que se ejecutan 20 veces al día, son 10 minutos ahorrados diarios.

## Slide 21 — Troubleshooting de pipelines

| Problema | Causa | Solución |
|---|---|---|
| "No hosted parallelism" | Límite de agents gratuitos | Solicitar más en dev.azure.com (o usar self-hosted agents) |
| "Azure subscription not found" | Service Connection mal configurada | Recrear con permisos correctos |
| Build tarda mucho | Sin caching, restore innecesarios | Añadir Cache task |
| Tests fallan en pipeline pero no local | Diferencias de entorno (OS, timezone) | Usar misma imagen base, fijar timezone |
| Deploy falla con 403 | Service Principal sin permisos | Verificar RBAC en Azure |
| Variables secretas no se inyectan | Variable Group no linked | Library → Link variable group al pipeline |
| "Checkout failed" | Token expirado o permisos de repo | Verificar pipeline permissions en repo settings |

## Slide 22 — OIDC + Federated Identity: zero-secrets pipelines

OIDC elimina secrets en pipelines — la práctica recomendada 2026:

```
ANTES (secrets-based):
├── Service connection con secret hardcoded
├── Secret rotation manual cada N meses
├── Secrets en pipeline logs si fallas
├── Risk: secrets leaked = full Azure access
└── Audit: difícil rastrear "qué pipeline tocó qué"

AHORA (OIDC + Federated Identity):
├── Pipeline solicita short-lived token
├── Azure verifica via federation
├── Token válido solo para esa ejecución
├── No secrets en ningún lado
└── Audit: cada pipeline run es único token
```

**Setup OIDC desde ADO:**

```bash
# 1. Crear App Registration en Entra ID
az ad app create --display-name "ADO-Pipeline-OIDC"

APP_ID=$(az ad app list --display-name "ADO-Pipeline-OIDC" \
  --query [0].appId -o tsv)
SP_ID=$(az ad sp create --id $APP_ID --query id -o tsv)

# 2. Federated credential for ADO service connection
az ad app federated-credential create \
  --id $APP_ID \
  --parameters '{
    "name": "ado-prod-deployments",
    "issuer": "https://vstoken.dev.azure.com/<your-org-id>",
    "subject": "sc://<org>/<project>/<service-connection-name>",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 3. RBAC roles (least privilege)
az role assignment create \
  --role "Contributor" \
  --assignee $SP_ID \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-prod

# 4. En ADO Portal:
# Project Settings → Service connections → New
# - Type: Azure Resource Manager
# - Authentication method: "Workload Identity federation (manual)"
# - Subscription: <sub-id>
# - Service Principal Id: $APP_ID
# - Tenant ID: <tenant-id>
```

**Pipeline usage (cero secrets):**
```yaml
# azure-pipelines.yml
trigger:
  - main

variables:
  - name: serviceConnection
    value: 'sc-prod-oidc'

stages:
  - stage: Deploy
    jobs:
      - job: DeployApp
        steps:
          - task: AzureCLI@2
            displayName: 'Deploy with OIDC'
            inputs:
              azureSubscription: $(serviceConnection)
              scriptType: 'bash'
              scriptLocation: 'inlineScript'
              inlineScript: |
                # Identity heredada via OIDC
                # Sin secrets, sin PATs
                az group list
                az deployment group create \
                  --resource-group rg-prod \
                  --template-file infra/main.bicep \
                  --parameters @infra/main.parameters.json
          
          - task: AzureWebApp@1
            inputs:
              azureSubscription: $(serviceConnection)
              appType: 'webApp'
              appName: 'app-prod'
              package: '$(Pipeline.Workspace)/drop/*.zip'
```

```csharp
// Azure Function que decides if deploy can proceed
[FunctionName("DeploymentApproval")]
public async Task<IActionResult> Run(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequest req,
    ILogger log)
{
    var data = await JsonSerializer.DeserializeAsync<ApprovalRequest>(req.Body);
    
    log.LogInformation($"Approval request: {data.PipelineUrl}");
    
    // Custom logic
    var checks = new[]
    {
        await VerifyTestCoverageAsync(data),
        await VerifyChangeWindowAsync(),
        await VerifyDependentServicesHealthyAsync(),
        await VerifyComplianceTagsAsync(data)
    };
    
    if (checks.All(c => c.Passed))
    {
        return new OkObjectResult(new
        {
            decision = "approved",
            reason = "All checks passed"
        });
    }
    
    var failed = checks.Where(c => !c.Passed).Select(c => c.Reason);
    return new BadRequestObjectResult(new
    {
        decision = "rejected",
        reasons = failed
    });
}

private async Task<CheckResult> VerifyTestCoverageAsync(ApprovalRequest req)
{
    // Query SonarQube API for coverage
    var coverage = await _sonarClient.GetCoverageAsync(req.ProjectName);
    return new CheckResult
    {
        Name = "Test coverage",
        Passed = coverage >= 80.0,
        Reason = $"Coverage: {coverage}% (required: 80%)"
    };
}
```

## Slide 29 — GitHub Actions migration patterns

Si decidís migrar de ADO a GitHub Actions, patterns clave:

```
ADO Pipeline → GitHub Actions equivalente:

ADO YAML:                       GitHub Actions YAML:
─────────────────────────────────────────────────────────
trigger: [main]              ↔  on: { push: { branches: [main] } }
pool: { vmImage: ubuntu-latest } ↔  runs-on: ubuntu-latest
variables: ...              ↔  env: ...
stages:                      ↔  jobs: (no stage concept directly)
  - stage: Build               (use needs: para deps)
    jobs:                       
      - job: ...
jobs (en stage):             ↔  jobs:
  - job: build                 build:
      steps: ...                steps: ...
deployment:                   ↔  jobs.<id>.environment:
  environment: 'prod'           prod:
    strategy:                   ...

variables:                    ↔  secrets / vars:
  - name: foo                   ${{ secrets.FOO }}
    value: bar                  ${{ vars.BAR }}

templates:                    ↔  reusable workflows + composite actions

service connections:          ↔  OIDC + GitHub Environments
```

**ADO pipeline real:**
```yaml
# Original ADO pipeline

variables:
  - group: ProductionSecrets

stages:
  - stage: Build
    jobs:
      - job: BuildApp
        pool:
          vmImage: 'ubuntu-latest'
        steps:
          - task: UseDotNet@2
            inputs: { version: '8.0.x' }
          - script: dotnet build --configuration Release
          - task: DotNetCoreCLI@2
            inputs:
              command: test
              projects: '**/*Tests.csproj'

  - stage: Deploy
    dependsOn: Build
    jobs:
      - deployment: DeployStaging
        environment: 'staging'
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureWebApp@1

                    azureSubscription: 'sc-staging'
                    appName: 'app-staging'
                    package: '$(Pipeline.Workspace)/drop/*.zip'
```

**Equivalente GitHub Actions:**
```yaml

  push:
    branches: [main]

          name: drop

      id-token: write  # OIDC
```

## Slide 30 — Pipeline observability + Insights

Pipelines también necesitan monitoring:

```kusto
// 1. Build success/failure trend
TimelineRecords_CL
| where TimeGenerated > ago(30d)
| where Type == "Stage" or Type == "Job"
| summarize 
    Total = count(),
    Successful = countif(Result == "succeeded"),
    Failed = countif(Result == "failed")
  by bin(TimeGenerated, 1d), Name
| extend SuccessRate = round(100.0 * Successful / Total, 2)
| order by TimeGenerated desc

// 2. Top failure reasons
TimelineRecords_CL
| where TimeGenerated > ago(7d)
| where Result == "failed"
| where isnotempty(ErrorIssues)
| extend ErrorMessage = tostring(ErrorIssues[0].message)
| summarize FailureCount = count() by ErrorMessage
| top 10 by FailureCount

// 3. Flaky tests detection
TestResults_CL
| where TimeGenerated > ago(7d)
| summarize 
    Runs = count(),
    Passed = countif(Outcome == "Passed"),
    Failed = countif(Outcome == "Failed")
  by TestName
| extend PassRate = 100.0 * Passed / Runs
| where PassRate > 0 and PassRate < 100  // Sometimes pass, sometimes fail
| order by PassRate asc

// 4. Pipeline duration p95 trend
TimelineRecords_CL
| where TimeGenerated > ago(30d)
| where Type == "Stage"
| summarize 
    p50 = percentile(DurationSeconds, 50),
    p95 = percentile(DurationSeconds, 95)
  by bin(TimeGenerated, 1d), PipelineName
| render timechart

// 5. Most expensive jobs (Microsoft-hosted minutes)
TimelineRecords_CL
| where TimeGenerated > ago(30d)
| where AgentSpecification == "Microsoft-hosted"
| summarize TotalMinutes = sum(DurationSeconds) / 60.0 by JobName
| extend EstimatedCost = TotalMinutes * 0.008  // Linux pricing
| top 20 by TotalMinutes desc
```

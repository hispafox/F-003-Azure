# Submódulo 8.4 — Azure DevOps vs GitHub Actions

## Slide 1 — Portada
**Módulo 8 · Submódulo 8.4**

Dos plataformas, un objetivo — cuándo elegir cada una

---

## Slide 2 — La convergencia Microsoft
Microsoft es dueña de ambas plataformas. Azure DevOps viene del mundo enterprise (on-premises con TFS). GitHub Actions viene del mundo open source. Están convergiendo: Azure DevOps adopta features de GitHub, GitHub adopta features de Azure DevOps.

La pregunta no es "cuál es mejor" sino "cuál encaja con vuestro equipo".

---

## Slide 3 — Comparativa completa

| Feature | Azure DevOps | GitHub Actions |
|---|:---:|:---:|
| **Repos** | Azure Repos (Git) | GitHub (Git) |
| **CI/CD** | YAML Pipelines | Workflows YAML |
| **Work tracking** | Boards (completo) | Issues + Projects (básico) |
| **Packages** | Artifacts (NuGet, npm) | Packages (NuGet, npm, Docker) |
| **Test Plans** | Sí (completo) | Terceros (Jest, xUnit, etc.) |
| **Wikis** | Integrado | Integrado |
| **Security scanning** | Terceros | Dependabot, CodeQL (nativo) |
| **Environments** | Sí (con aprobaciones) | Sí (con aprobaciones) |
| **Self-hosted agents** | Sí | Sí (runners) |
| **Marketplace** | Extensions | Actions (mucho más grande) |
| **Free tier CI** | 1 parallel job, 1800 min/mes | 2000 min/mes |
| **Precio enterprise** | $6/user/mes (Basic) | $4/user/mes (Team) |
| **On-premises** | Azure DevOps Server | GitHub Enterprise Server |

---

## Slide 4 — Cuándo elegir Azure DevOps

- Ya lo usáis (vuestro caso) y funciona
- Necesitáis Boards completos (sprints, velocity, burn-down)
- Tenéis Azure DevOps Server on-premises
- Necesitáis Test Plans integrados
- La organización está centrada en el ecosistema Microsoft/Azure
- Necesitáis control de acceso granular por proyecto/repo/pipeline

---

## Slide 5 — Cuándo elegir GitHub Actions

- Proyectos open source o mixtos (público + privado)
- Queréis el marketplace de Actions más grande
- Dependabot y CodeQL nativos para seguridad
- Copilot integrado en el IDE y en el repo
- Equipos distribuidos que ya usan GitHub
- CI/CD simple sin necesidad de Boards completos

## Slide 6 — GitHub Actions: ejemplo equivalente

```yaml
# .github/workflows/deploy.yml (equivalente al pipeline de ADO)
name: Build and Deploy
on:
  push:
    branches: [main]
    paths: ['src/VentasApi/**']

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-dotnet@v4
      with: { dotnet-version: '8.x' }
    - run: dotnet build src/VentasApi -c Release
    - run: dotnet test tests/VentasApi.Tests -c Release
    - run: dotnet publish src/VentasApi -c Release -o ./publish
    - uses: actions/upload-artifact@v4
      with: { name: webapp, path: ./publish }

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
    - uses: actions/download-artifact@v4
      with: { name: webapp }
    - uses: azure/webapps-deploy@v3
      with:
        app-name: 'app-ventas-prod'
        slot-name: 'staging'
        package: '.'

  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production  # Requiere aprobación
    steps:
    - uses: azure/login@v2
      with:
        creds: ${{ secrets.AZURE_CREDENTIALS }}
    - run: az webapp deployment slot swap -n app-ventas-prod -g rg-ventas-prod -s staging
```

**Diferencias sintácticas:** `stages/jobs/steps` en ADO → `jobs/steps` en GitHub. `task:` en ADO → `uses:` en GitHub. `$(variable)` en ADO → `${{ variable }}` en GitHub. La lógica es la misma.

## Slide 8 — Hybrid: ADO + GitHub (lo mejor de ambos mundos)

Podéis usar GitHub para repos (Copilot, CodeQL, Dependabot) y Azure DevOps para Boards y Pipelines:

```yaml
# Pipeline en Azure DevOps que se ejecuta con código de GitHub
resources:
  repositories:
  - repository: ventas-api
    type: github
    endpoint: 'GitHub-Connection'
    name: 'mi-org/ventas-api'

trigger:
  - main

steps:
- checkout: ventas-api
- script: dotnet build
```

ADO Boards → linked a GitHub repos → commits y PRs de GitHub aparecen en los work items de ADO. Lo mejor de ambos mundos.

## Slide 9 — GitHub Actions: security features nativos

```yaml
# Dependabot (automático en GitHub)
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "nuget"
    directory: "/"
    schedule: { interval: "weekly" }
    open-pull-requests-limit: 10

# CodeQL (análisis estático de seguridad)
# .github/workflows/codeql.yml
name: CodeQL Analysis
on: [push, pull_request]
jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
    - uses: github/codeql-action/init@v3
      with: { languages: 'csharp' }
    - uses: github/codeql-action/analyze@v3
```

Dependabot crea PRs automáticos para actualizar dependencias vulnerables. CodeQL detecta vulnerabilidades en vuestro código (SQL injection, XSS, etc.). Ambos gratuitos en GitHub.

## Slide 14 — Self-hosted runners on Azure

Self-hosted runners en Azure VMs / VMSS / AKS:

```
Cuándo necesitas self-hosted:
├── Custom hardware (GPU, ARM64, specific OS)
├── Network access privado (on-prem resources)
├── Compliance requirements (data residency)
├── Cost optimization (high-volume builds)
└── Specific software preinstalled
```

**Setup runner en Azure VM:**
```bash
# Crear VM
az vm create \
  --resource-group rg-runners \
  --name vm-github-runner-01 \
  --image Ubuntu2204 \
  --size Standard_D4s_v5 \
  --admin-username azureuser \
  --ssh-key-values ~/.ssh/id_rsa.pub

# SSH y setup runner
ssh azureuser@<vm-ip>

# Download GitHub Actions runner
mkdir actions-runner && cd actions-runner
curl -O -L https://github.com/actions/runner/releases/download/v2.318.0/actions-runner-linux-x64-2.318.0.tar.gz
tar xzf ./actions-runner-linux-x64-2.318.0.tar.gz

# Get token from: GitHub → Settings → Actions → Runners → New
./config.sh --url https://github.com/empresa/repo \
  --token <REGISTRATION_TOKEN> \
  --name azure-runner-01 \
  --labels self-hosted,linux,X64,azure

# Run as service
sudo ./svc.sh install
sudo ./svc.sh start
```

**Auto-scaling con VMSS:**
```bicep
// Bicep para auto-scaling self-hosted runners
resource vmss 'Microsoft.Compute/virtualMachineScaleSets@2024-03-01' = {
  name: 'vmss-runners'

    name: 'Standard_D4s_v5'
    capacity: 2  // Initial count
  }
  properties: {
    upgradePolicy: { mode: 'Manual' }
    virtualMachineProfile: {
      osProfile: {
        computerNamePrefix: 'runner'
        adminUsername: 'azureuser'
        customData: base64('''#cloud-config
runcmd:
  - cd /home/azureuser
  - mkdir actions-runner && cd actions-runner
  - curl -O -L https://github.com/actions/runner/releases/download/v2.318.0/actions-runner-linux-x64-2.318.0.tar.gz
  - tar xzf actions-runner-linux-x64-2.318.0.tar.gz
  - sudo -u azureuser ./config.sh --url $GITHUB_URL --token $REG_TOKEN --unattended
  - sudo ./svc.sh install
  - sudo ./svc.sh start
        ''')
      }
    }
  }
}

// Auto-scale rules
resource autoscale 'Microsoft.Insights/autoscalesettings@2022-10-01' = {
  name: 'autoscale-runners'
  location: location
  properties: {
    profiles: [
      {
        name: 'default'
        capacity: { minimum: '2', maximum: '20', default: '4' }
        rules: [
          {
            // Scale up when queue > 5
            metricTrigger: {
              metricName: 'PendingJobs'  // Custom metric
              operator: 'GreaterThan'
              threshold: 5
              timeAggregation: 'Average'
              timeWindow: 'PT5M'
            }
            scaleAction: {
              direction: 'Increase'
              type: 'ChangeCount'
              value: '2'
              cooldown: 'PT5M'
            }
          }
        ]
      }
    ]
  }
}
```

## Slide 16 — Migration tooling actual (2026)

Si decides migrar de ADO a GitHub, las herramientas oficiales:

```
Migration scope:
├── Source code: Git repos (easy)
├── Pipelines: ADO YAML → GitHub Actions YAML
├── Boards: Work items → Issues
├── Wiki: Markdown migration
└── Artifacts: Packages migration
```

**1. GitHub Actions Importer (oficial):**
```bash
# Install
gh extension install github/gh-actions-importer

# Audit your ADO pipelines (analyze before migration)
gh actions-importer audit azure-devops \
  --azure-devops-organization <org-name> \
  --azure-devops-project <project> \
  --output-dir ./audit-result

# Output: report con conversion feasibility
# - Convertible: 95% of pipelines
# - Manual review: 5%
# - Cannot convert: 0%

# Dry-run conversion
gh actions-importer dry-run azure-devops \
  --azure-devops-organization <org-name> \
  --azure-devops-project <project> \
  --azure-devops-pipeline mi-pipeline \
  --output-dir ./dry-run-result

# Real conversion
gh actions-importer migrate azure-devops \
  --target-url https://github.com/empresa/repo \
  --azure-devops-organization <org-name> \
  --azure-devops-project <project> \
  --azure-devops-pipeline mi-pipeline \
  --output-dir ./migration-result
```

**2. Azure DevOps Demo Generator (template-based migration):**
```
Para empezar nuevo project con same patterns:
└── https://azuredevopsdemogenerator.azurewebsites.net
    ├── Pre-built templates
    ├── Replicate exact structure
    └── No data migration, just structure
```

**3. Boards → Issues (custom script):**
```python
# migrate-boards-to-issues.py
import requests
import json

ADO_TOKEN = "..."
GITHUB_TOKEN = "..."
ADO_ORG = "empresa"
ADO_PROJECT = "mi-proyecto"
GITHUB_REPO = "empresa/repo"

# Get all work items from ADO
ado_url = f"https://dev.azure.com/{ADO_ORG}/{ADO_PROJECT}/_apis/wit/wiql?api-version=7.1"
ado_query = {
    "query": "SELECT [System.Id] FROM WorkItems WHERE [System.WorkItemType] IN ('User Story', 'Task', 'Bug')"
}
ado_response = requests.post(ado_url, json=ado_query, 
    auth=("", ADO_TOKEN))

# For each work item, create GitHub issue
for item in ado_response.json()['workItems']:
    item_id = item['id']
    item_details = requests.get(
        f"https://dev.azure.com/{ADO_ORG}/{ADO_PROJECT}/_apis/wit/workItems/{item_id}?api-version=7.1",
        auth=("", ADO_TOKEN)
    ).json()
    
    fields = item_details['fields']
    
    issue_data = {
        "title": fields['System.Title'],
        "body": f"""
**Migrated from Azure DevOps Work Item #{item_id}**

**Type**: {fields['System.WorkItemType']}
**State**: {fields['System.State']}
**Assigned to**: {fields.get('System.AssignedTo', {}).get('displayName', 'Unassigned')}
**Created**: {fields['System.CreatedDate']}

---

{fields.get('System.Description', '')}
""",
        "labels": [
            fields['System.WorkItemType'].lower(),
            f"state:{fields['System.State'].lower()}"
        ]
    }
    
    github_response = requests.post(
        f"https://api.github.com/repos/{GITHUB_REPO}/issues",
        json=issue_data,
        headers={"Authorization": f"token {GITHUB_TOKEN}"}
    )
    
    print(f"Migrated #{item_id} → GitHub Issue #{github_response.json()['number']}")
```

## Slide 18 — Hybrid: ADO Boards + GitHub Code

Pattern emerging: usar lo mejor de cada uno:

```
Hybrid setup:
├── GitHub: Code, PRs, Actions (development workflow)
├── ADO Boards: Work items, sprints (PM workflow)
└── Sync: GitHub Issues ↔ ADO Work Items
```

**Setup integration:**
```bash
# 1. Install Azure Boards GitHub app
# https://github.com/marketplace/azure-boards

# 2. Configure repository connection
# ADO → Project Settings → GitHub connections
# Add: empresa/repo

# 3. Now:
# - GitHub Issues create ADO Work Items
# - Mention AB#123 in commits → links to Work Item
# - Branch naming: AB#123-feature → linked
```

**Workflow ejemplo:**
```bash
# 1. PM creates work item en ADO Boards
ADO: User Story #456 - "Add export to Excel"

# 2. Dev creates branch en GitHub
git checkout -b AB#456-export-excel
# Branch automatically linked to work item

# 3. Commit references work item
git commit -m "AB#456 Add Excel export endpoint"

# 4. PR mentions work item
gh pr create --title "Export to Excel feature" \
  --body "Implements AB#456. ..."

# 5. Merge → ADO work item updates automatically
# State: Active → Resolved (or Done)

# 6. CI/CD via GitHub Actions
# 7. Deployment status reported back to ADO
```

**Custom GitHub Action que actualiza ADO:**
```yaml
# .github/workflows/sync-to-ado.yml
name: Sync deployment to ADO

on:
  workflow_run:
    workflows: ["Deploy to Production"]
    types: [completed]

jobs:
  update-ado:
    runs-on: ubuntu-latest
    steps:
      - name: Update ADO Work Items
        run: |
          # Get PR linked work items
          PR_NUMBER=${{ github.event.workflow_run.pull_requests[0].number }}
          
          # Extract AB#XXX references
          gh api repos/${{ github.repository }}/pulls/$PR_NUMBER \
            --jq '.body' | grep -oP 'AB#\d+' | while read ref; do
              ID=${ref#AB#}
              
              # Update work item
              curl -X PATCH \
                "https://dev.azure.com/$ORG/$PROJECT/_apis/wit/workItems/$ID?api-version=7.1" \
                -H "Authorization: Basic $(echo -n :$ADO_PAT | base64)" \
                -H "Content-Type: application/json-patch+json" \
                -d '[
                  {"op":"add","path":"/fields/Microsoft.VSTS.Common.ResolvedReason","value":"Deployed to Production"},
                  {"op":"add","path":"/fields/System.State","value":"Closed"}
                ]'
          done
        env:
          ORG: ${{ secrets.ADO_ORG }}
          PROJECT: ${{ secrets.ADO_PROJECT }}
          ADO_PAT: ${{ secrets.ADO_PAT }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**Benefits del hybrid:**
- ✅ Devs use familiar GitHub workflow
- ✅ PMs use mature ADO Boards
- ✅ Audit trail completo en ambos
- ✅ Reporting/analytics de ADO
- ✅ Best of both

**Costs hybrid:**
- ADO Basic ($6/user) for board access
- GitHub Team ($4/user) for code
- Total: $10/user vs $21 Enterprise

**Anti-pattern:**
```
❌ Don't duplicate work
   - PM creates ADO Item
   - Dev creates GitHub Issue
   - Sync drifts
   
✅ One source of truth (ADO Boards)
   - GitHub Issues solo para community/users
   - Internal: ADO Work Items
```

## Slide 20 — Lessons learned migrations reales

3 casos reales de empresas migrando ADO ↔ GitHub:

**Case 1: SaaS startup → GitHub (success)**
```
Empresa: 30 devs, SaaS B2B
Estado inicial: ADO Basic (1 año uso)
Razón migración: Open source contributions, Copilot
Duración: 6 semanas
Coste: €15K (consultant 2 semanas)

Resultados:
├── ✅ Devs satisfaction +35%
├── ✅ PR review time -40%
├── ✅ CI/CD time -25% (better caching)
├── ✅ Marketplace actions ahorraron 200h custom code
└── Issue: Boards migration tooling limitada
       └── Workaround: started fresh en GitHub Issues
```

**Case 2: Banco grande → Stay ADO (decisión informada)**
```
Empresa: 800 devs, banking
Estado: ADO 8 años, mature setup
Considerado migrar: ¿GitHub Enterprise?
Decisión: Quedarse ADO

Razones:
├── Test Plans crítico (compliance manual testing)
├── Process customization profundo (auditor requirements)
├── 200+ custom extensions
├── Visual Studio licenses bundle saving
├── Migration cost estimated: €2M+
└── Risk: too high para reward marginal

Result: 
├── Continued ADO investment
├── GHAS for ADO addon (security parity)
├── Self-hosted Azure runners para cost
└── Hybrid: GitHub Enterprise para small subsidiary
```

**Case 3: Healthcare → Hybrid (compromiso)**
```
Empresa: 150 devs, healthcare SaaS
Stack mix: ADO 5 años + 1 acquired team en GitHub
Challenge: Unify or maintain hybrid?

Decision: Hybrid permanente
├── ADO Boards: Single source PM (compliance)
├── GitHub: Code + Actions (better DX)
├── Sync via Azure Boards GitHub app
└── Custom integrations Mantenidas

Investment:
├── Setup: €30K (3 weeks engineering)
├── Maintenance: 0.5 FTE ongoing
├── Tooling: €4K/mes hybrid licenses
└── Total Year 1: ~€100K

Benefits:
├── No forced migration trauma
├── Acquired team kept productive
├── Best practices from both worlds
└── Compliance stays intact (audit trail)
```

**Common patterns:**
```
✅ WHAT WORKS:
├── Pilot small team first
├── Run parallel during transition (1-2 sprints)
├── Train developers (1-2 days)
├── Document new workflows
├── Migrate code first, history can stay frozen
└── Communicate aggressive timeline (avoid drift)

❌ WHAT FAILS:
├── Big bang migration entire org
├── Skipping training "they'll figure it out"
├── Not updating CI/CD references comprehensively
├── Forgetting integrations (Slack, Teams, JIRA)
├── Migrating before team is ready
└── Underestimating Boards/Issues differences
```

**Recommendation final 2026:**
> "If you're starting fresh: GitHub.
>  If you have ADO and it works: keep it, augment with GHAS for ADO.
>  Don't migrate just because it's trendy — migrate because there's clear ROI."

## Slide 21 — Cierre del submódulo
ADO y GitHub son excelentes. Para vuestro equipo (Azure-centric, sprints, 6-10 personas), ADO es la elección correcta: Boards completos, integración nativa con Azure, y buen precio. GitHub si necesitáis Copilot, Dependabot nativo, o CodeQL. Podéis combinar ambos: repos en GitHub, Boards en ADO.

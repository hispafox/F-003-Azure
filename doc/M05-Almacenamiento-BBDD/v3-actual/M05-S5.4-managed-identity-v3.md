## Slide 2 — El problema con las connection strings
Cada servicio Azure necesita una cadena de conexión para autenticarse. Esas cadenas contienen secretos (passwords, keys). Y esos secretos:

- Acaban en `appsettings.json` → en el repo → cualquiera con acceso los ve
- Se copian en App Settings → cualquier Contributor las lee en el portal
- Se comparten por Slack/email → sin control de quién las tiene
- No se rotan → la misma key lleva 3 años activa
- Si se filtran → acceso total al servicio

**Managed Identity elimina este problema.** Tu app se autentica con su propia identidad, sin passwords, sin keys, sin secretos que rotar.

---

## Slide 3 — Qué es Managed Identity
Managed Identity es una identidad de Entra ID asignada automáticamente a un recurso Azure:

```
Sin Managed Identity:
App Service → "Hola Cosmos, soy la app, aquí está mi password: abc123"
Cosmos DB → "OK, password correcto, pasa"

Con Managed Identity:
App Service → "Hola Cosmos, soy la app (identidad verificada por Entra ID)"
Cosmos DB → "Verifico con Entra ID... sí, eres quien dices ser, y tienes permiso. Pasa"
```

**No hay password.** Entra ID emite un token temporal, la app lo usa para autenticarse, el token expira automáticamente. Sin secretos que filtrar, rotar ni gestionar.

## Slide 4 — System-assigned vs User-assigned

**System-assigned:**
- Se crea automáticamente al habilitarla en el recurso
- Vinculada 1:1 con el recurso (si borras la app, se borra la identidad)
- Cada recurso tiene su propia identidad

```bash
az webapp identity assign --name app-ventas -g rg-ventas-prod
# Devuelve: principalId (el ID de la identidad)
```

**User-assigned:**
- Se crea como recurso independiente
- Se puede asignar a múltiples recursos
- Persiste aunque borres los recursos

```bash
az identity create --name id-ventas-shared -g rg-ventas-prod
az webapp identity assign --name app-ventas -g rg-ventas-prod \
  --identities /subscriptions/<id>/.../id-ventas-shared
```

**¿Cuál usar?** System-assigned para la mayoría de casos (más simple). User-assigned cuando múltiples recursos necesitan la misma identidad.

## Slide 5 — Habilitar Managed Identity + dar permisos

**Paso 1: Habilitar en la app:**
```bash

# Output: { "principalId": "abc-123-..." }
```

```bash
  --assignee $PRINCIPAL_ID \

  --scope "/subscriptions/<id>/.../storageAccounts/stventasprod"

# Permiso para leer secretos de Key Vault
az keyvault set-policy --name kv-ventas-prod \
  --object-id $PRINCIPAL_ID \
  --secret-permissions get list
```

## Slide 6 — Usar Managed Identity en código .NET

```csharp
using Azure.Identity;

// DefaultAzureCredential funciona automáticamente:
// - En local: usa az cli login, Visual Studio login, o environment variables
// - En Azure: usa Managed Identity
var credential = new DefaultAzureCredential();

// Cosmos DB
var cosmosClient = new CosmosClient(
    "https://cosmos-ventas-prod.documents.azure.com:443/",
    credential);

// Blob Storage
var blobClient = new BlobServiceClient(
    new Uri("https://stventasprod.blob.core.windows.net"),
    credential);

// Key Vault
var kvClient = new SecretClient(
    new Uri("https://kv-ventas-prod.vault.azure.net/"),
    credential);

// Azure SQL (en connection string)
// Authentication=Active Directory Default
```

**La magia de DefaultAzureCredential:** Prueba múltiples métodos de autenticación en orden. En local usa vuestro login de `az cli`. En Azure usa la Managed Identity del recurso. El mismo código funciona en ambos entornos sin cambios.

## Slide 7 — DefaultAzureCredential: cadena de autenticación

```
DefaultAzureCredential intenta en orden:
1. EnvironmentCredential (variables de entorno: AZURE_CLIENT_ID, etc.)
2. WorkloadIdentityCredential (Kubernetes)
3. ManagedIdentityCredential (en Azure: App Service, Functions, VM)
4. SharedTokenCacheCredential
5. VisualStudioCredential (Visual Studio)
6. VisualStudioCodeCredential (VS Code Azure extension)
7. AzureCliCredential (az login)
8. AzurePowerShellCredential (Connect-AzAccount)
9. AzureDeveloperCliCredential (azd)
```

**En local:** Llega al paso 7 y usa vuestro `az login`.
**En Azure:** Para en el paso 3 y usa la Managed Identity.

No necesitáis cambiar código ni configuración entre entornos. Solo aseguraos de que en local estáis logueados con `az login`.

## Slide 8 — Ejemplo completo: App Service → Cosmos DB con MI

```bash
# 1. Habilitar Managed Identity
az webapp identity assign --name app-ventas -g rg-ventas-prod

# 2. Obtener principal ID
PRINCIPAL_ID=$(az webapp identity show --name app-ventas -g rg-ventas-prod -q principalId -o tsv)

# 3. Asignar rol en Cosmos DB

  --principal-id $PRINCIPAL_ID --scope "/"

# 4. Configurar App Setting (solo la URL, sin key)
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --settings CosmosDbEndpoint="https://cosmos-ventas-prod.documents.azure.com:443/"
```

```csharp
// Program.cs — sin connection string, sin key
var endpoint = builder.Configuration["CosmosDbEndpoint"];
builder.Services.AddSingleton(new CosmosClient(endpoint, new DefaultAzureCredential()));
```

**Resultado:** Cero secretos en configuración. Cero passwords en el código. Si alguien ve vuestros App Settings, solo ve una URL — no puede conectarse sin la identidad.


**Para bindings de Functions con MI:**
```json
// local.settings.json / App Settings
{
  "Values": {
    "CosmosDbConnection__accountEndpoint": "https://cosmos-ventas-prod.documents.azure.com:443/",
```

El sufijo `__accountEndpoint` o `__blobServiceUri` indica a Functions que use MI en vez de connection string.

## Slide 10 — Key Vault References: para lo que no puede ser MI

Algunos servicios no soportan MI directamente (APIs externas, servicios de terceros). Para esos, usáis Key Vault:

```bash
# Guardar secreto
az keyvault secret set --vault-name kv-ventas-prod \
  --name "ApiExternaKey" --value "sk_live_abc123..."

# Referenciar desde App Settings
az webapp config appsettings set --name app-ventas -g rg-ventas-prod \
  --settings ApiExternaKey="@Microsoft.KeyVault(VaultName=kv-ventas-prod;SecretName=ApiExternaKey)"
```

**El flujo:**
1. App Service lee App Setting `ApiExternaKey`
2. Detecta que es una referencia a Key Vault (`@Microsoft.KeyVault(...)`)
3. Usa su Managed Identity para autenticarse con Key Vault
4. Obtiene el valor real del secreto
5. Lo inyecta como variable de entorno normal

Tu código lee `Configuration["ApiExternaKey"]` y obtiene `sk_live_abc123...` sin saber que viene de Key Vault.

## Slide 11 — Cifrado de datos

**En reposo (at rest):**
Azure cifra TODOS los datos almacenados automáticamente con AES-256. Storage, SQL, Cosmos DB, Key Vault — todo cifrado por defecto. No necesitáis configurar nada.

**Opciones de cifrado:**
- **Microsoft-managed keys (MMK):** Azure gestiona las claves. Por defecto, gratis, sin configuración.
- **Customer-managed keys (CMK):** Vosotros gestionáis las claves en Key Vault. Más control. Para compliance avanzado.

**En tránsito (in transit):**
TLS 1.2 mínimo en todos los servicios. Las connection strings de Cosmos DB, SQL y Storage incluyen `Encrypt=true` por defecto.

```bash
# Forzar TLS 1.2 en Storage Account
az storage account update --name stventasprod -g mi-rg --min-tls-version TLS1_2

# Forzar HTTPS en App Service
az webapp update --name app-ventas -g mi-rg --https-only true
```

## Slide 12 — Rotación de keys

Aunque uséis Managed Identity para la mayoría de conexiones, puede que todavía tengáis keys (APIs externas, Storage account keys para SAS):

```bash
# Rotar storage account key
az storage account keys renew --account-name stventasprod -g mi-rg --key key1

# Rotar Cosmos DB keys
az cosmosdb keys regenerate --name cosmos-ventas-prod -g mi-rg --key-kind primary
```

**Automatizar rotación con Key Vault + Event Grid:**
1. Key Vault genera un nuevo secreto
2. Event Grid notifica
3. Azure Function actualiza la configuración del servicio

En la práctica, si usáis Managed Identity para todo lo que lo soporta, la rotación de keys se reduce a servicios de terceros — y esas keys se gestionan en Key Vault con expiración.

## Slide 16 — Troubleshooting de Managed Identity

**"403 Forbidden" al acceder a Cosmos DB:**
→ Verificad que el rol RBAC está asignado al `principalId` correcto:
```bash
az cosmosdb sql role assignment list --account-name cosmos-ventas-prod -g mi-rg --output table
```

**"DefaultAzureCredential failed" en local:**
→ No estáis logueados: `az login`
→ O el tenant es incorrecto: `az login --tenant <id>`

**"AADSTS700024: Client assertion is not within its valid time range":**
→ El reloj de vuestra máquina está desincronizado. Sincronizad la hora.

**"ManagedIdentityCredential: IMDS" timeout en local:**
→ Normal. DefaultAzureCredential intenta MI primero (falla en local), luego prueba az cli (funciona). Podéis acelerar:
```csharp
var credential = new DefaultAzureCredential(new DefaultAzureCredentialOptions
{
    ExcludeManagedIdentityCredential = true // Solo en desarrollo local
});
```

**Funciona en local pero no en Azure:**
→ La app tiene MI habilitada pero no tiene permisos asignados. Verificad role assignments.

## Slide 18 — Cifrado avanzado: Customer-Managed Keys

Si el requisito de compliance exige que VOSOTROS controléis las claves de cifrado:

```bash
# Crear Key Vault con claves de cifrado
az keyvault create --name kv-keys-prod -g rg-ventas-prod --enable-purge-protection

# Crear una clave RSA
az keyvault key create --vault-name kv-keys-prod --name storage-key --kty RSA --size 2048

# Configurar Storage Account con CMK
az storage account update --name stventasprod -g mi-rg \
  --encryption-key-source Microsoft.Keyvault \

```

**¿Cuándo CMK?** Solo si regulación lo exige (banca, sanidad, gobierno). Para la mayoría de casos, Microsoft-Managed Keys (MMK, por defecto) es suficiente y más simple.

## Slide 19 — Workload Identity Federation 2025

WIF (Workload Identity Federation) elimina secrets en escenarios externos:

```
Antes (con secret):
GitHub Actions ───── client_secret ─────▶ Entra ID ─── token ───▶ Azure
                    (secret en GH)

Ahora (con WIF):
GitHub Actions ───── OIDC token ─────▶ Entra ID ─── token ───▶ Azure
                    (federación)
```

**Setup completo (lo viste en M4 con OIDC):**
```bash
# 1. Crear App Registration
APP_ID=$(az ad app create --display-name "github-actions-mi" \
  --query appId -o tsv)
OBJ_ID=$(az ad app show --id $APP_ID --query id -o tsv)

# 2. Service Principal
az ad sp create --id $APP_ID

# 3. Permisos sobre RG
az role assignment create \
  --role "Contributor" \
  --assignee $APP_ID \
  --scope "/subscriptions/$(az account show --query id -o tsv)/resourceGroups/rg-curso"

# 4. Federated credential para branch main
az ad app federated-credential create --id $OBJ_ID \
  --parameters '{
    "name": "github-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:mi-org/mi-repo:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 5. WIF también para Kubernetes (cualquier issuer compatible)
az ad app federated-credential create --id $OBJ_ID \
  --parameters '{
    "name": "k8s-prod",
    "issuer": "https://oidc.eks.eu-west-1.amazonaws.com/id/ABCXYZ",
    "subject": "system:serviceaccount:default:my-app",
    "audiences": ["api://AzureADTokenExchange"]
  }'
```

**Issuers soportados:**
- GitHub Actions
- Azure DevOps
- AWS (cross-cloud)
- Google Cloud (cross-cloud)
- Kubernetes clusters (incluido EKS, GKE, OKE)
- BitBucket Pipelines
- GitLab CI
- Cualquier OIDC-compliant identity provider

**Usar en código (Python ejemplo):**
```python
from azure.identity import DefaultAzureCredential

# Sin client_secret — WIF intercambia el token automáticamente
credential = DefaultAzureCredential()

# Usar contra cualquier servicio Azure
blob_client = BlobServiceClient(
    account_url="https://stcurso.blob.core.windows.net",
    credential=credential
)
```

**Cross-cloud scenario:**
```yaml
# AWS Lambda → Azure Storage (via WIF)
# AWS configura federation con Azure
# Lambda usa AWS Cognito identity → exchange por Azure token

# .github/workflows/cross-cloud.yml
permissions:
  id-token: write

steps:
  - uses: aws-actions/configure-aws-credentials@v4
  - run: |
      AZURE_TOKEN=$(curl -s -H "Authorization: $AWS_TOKEN" \
        https://login.microsoftonline.com/$TENANT/oauth2/v2.0/token \
        -d "grant_type=client_credentials&client_id=$APP_ID...")
```

**Casos de uso real:**

| Escenario | WIF beneficia |
|---|---|
| Multi-cloud deployments | Sin secrets cross-cloud |
| Hybrid on-prem + Azure | K8s on-prem → Azure resources |
| CI/CD modernos | Sin secrets en git/ADO |
| Workloads K8s | Pod identity sin secrets |

**Anti-pattern a evitar:**
```
❌ Usar Service Principal con client_secret en pipeline
   → Rotación manual, leak risk
❌ Compartir client_secret entre projects
   → Compromise = N proyectos comprometidos
```

## Slide 20 — Conditional Access for Managed Identity

Conditional Access (CA) policies aplicadas a workload identities (preview/GA 2024):

```
Antes: CA solo para usuarios humanos
       MI tenía acceso "todo o nada" basado en role

Ahora: CA puede aplicar a Service Principals + MI
       Puedes restringir:
       - IP origen
       - Network location
       - Sign-in risk
       - Authentication strength
```

**Crear CA policy para MI:**
```
Portal → Entra ID → Conditional Access → New policy

Name: "Restrict MI access from unknown IPs"

Assignments:
├── Cloud apps: All cloud apps
├── Conditions:
│   └── Workload identities: Service principals
│       └── Include specific SPs (your MI principal IDs)
└── Locations: Exclude trusted IPs (office, datacenters)

Access controls:
└── Block access (when condition matches = block)

Enable policy: ON
```

**Use cases:**

```
Escenario 1: MI solo accede desde tu RG VNet
└── CA: Block if NOT from VNet IPs
    → Robar credentials no funciona desde otro lado

Escenario 2: MI con acceso solo a horario laboral
└── CA: Block outside 8am-8pm CET
    → Prevent off-hours misuse

Escenario 3: Require multi-factor for sensitive MIs
└── CA: Require auth strength = "phishing-resistant"
    → Solo certain identities pueden authenticate
```

**Ejemplo Bicep:**
```bicep
resource caPolicy 'Microsoft.Authorization/policies@2024-01-01' = {
  name: 'mi-restrict-network'
  properties: {
    displayName: 'MI: Block from non-corp networks'
    conditions: {
      clientApplications: {
        includeServicePrincipals: ['<MI-PRINCIPAL-ID>']
      }
      locations: {
        excludeLocations: ['trusted-corp-network']
      }
    }
    grantControls: {
      operator: 'OR'
      builtInControls: ['block']
    }
  }
}
```

**Audit y monitoring:**
```kusto
// Sign-ins de MI bloqueados por CA
AADServicePrincipalSignInLogs
| where ConditionalAccessStatus == "failure"
| project TimeGenerated, ServicePrincipalName, IPAddress, 
          ConditionalAccessPoliciesApplied
| order by TimeGenerated desc
```

**Combinado con MI:**
- MI = WHO (identidad sin password)
- CA = WHEN/WHERE (cuándo y desde dónde puede usar)
- RBAC = WHAT (qué puede hacer)

Defense in depth completo.

## Slide 21 — Token caching: optimizar performance

`DefaultAzureCredential` cachea tokens automáticamente, pero hay matices:

```csharp
// Por default, cada CosmosClient/BlobClient mantiene su propio cache
// PROBLEMA: si creas client por request → no cache benefit

// ❌ MAL — nuevo client per request, no caching
public async Task<Order> GetOrder(string id)
{
    var client = new CosmosClient(uri, new DefaultAzureCredential());
    // ↑ Token call cada request (slow + rate limited)
}

// ✅ BIEN — singleton + cache nativo
public class CosmosService
{
    private static readonly CosmosClient _client = new(
        accountEndpoint: _endpoint,
        tokenCredential: new DefaultAzureCredential(),
        clientOptions: new CosmosClientOptions
        {
            // Token se cachea internamente
            // Refresh 5 min antes de expirar
        });
    
    public Container Orders => _client.GetContainer("db", "orders");
}
```

**DI registration adecuada:**
```csharp
// Program.cs
builder.Services.AddSingleton<TokenCredential>(_ => new DefaultAzureCredential());

builder.Services.AddSingleton(sp =>
{
    var credential = sp.GetRequiredService<TokenCredential>();
    return new CosmosClient(
        accountEndpoint: builder.Configuration["CosmosEndpoint"],
        tokenCredential: credential);
});

builder.Services.AddSingleton(sp =>
{
    var credential = sp.GetRequiredService<TokenCredential>();
    return new ServiceBusClient(
        builder.Configuration["SbNamespace"],
        credential);
});

builder.Services.AddSingleton(sp =>
{
    var credential = sp.GetRequiredService<TokenCredential>();
    return new BlobServiceClient(
        new Uri($"https://{accountName}.blob.core.windows.net"),
        credential);
});
```

**Verificar token caching funciona:**
```csharp
// Habilitar logging para ver token requests
DefaultAzureCredentialOptions options = new()
{
    Diagnostics =
    {
        IsLoggingContentEnabled = true,
        IsLoggingEnabled = true
    }
};

var credential = new DefaultAzureCredential(options);

// En logs verás:
// - Primer request: "Acquiring token" + "Token acquired"
// - Requests subsiguientes: "Token cache hit"
```

**Token lifetime:**
- AAD tokens: 60-90 minutes typical
- SDKs refresh automáticamente 5 min antes de expirar
- No necesitáis manual refresh

**Anti-pattern detection:**
```kusto
// En App Insights, buscad demasiados auth calls
dependencies
| where target contains "login.microsoftonline.com"
| summarize count() by bin(timestamp, 5m)
| render timechart
// Si veis spikes regulares = posible token thrashing
```

## Slide 22 — User-Assigned MI: cuándo usar

System-Assigned vs User-Assigned MI tienen patrones distintos:

```
SYSTEM-ASSIGNED MI                    USER-ASSIGNED MI
──────────────────                    ────────────────
1 MI por recurso                      1 MI shared by N recursos
Ciclo de vida = recurso               Ciclo de vida independiente
Borras recurso = borras MI            MI persiste si borras recurso
Permisos por recurso                  Permisos centralizados

Caso simple:                          Caso complejo:
└── App Service único                 └── 10 Function Apps que necesitan
    └── 1 MI con acceso a SQL            mismos permisos sobre Cosmos
                                          └── 1 UAMI assigned to all 10
```

**Crear User-Assigned MI:**
```bash
# 1. Crear el UAMI
az identity create \
  --name uami-shared-prod \
  --resource-group rg-curso \
  --location westeurope

UAMI_ID=$(az identity show -n uami-shared-prod -g rg-curso --query id -o tsv)
UAMI_PRINCIPAL_ID=$(az identity show -n uami-shared-prod -g rg-curso --query principalId -o tsv)
UAMI_CLIENT_ID=$(az identity show -n uami-shared-prod -g rg-curso --query clientId -o tsv)

# 2. Asignar al UAMI permisos sobre recursos
az role assignment create \
  --role "Cosmos DB Data Contributor" \
  --assignee $UAMI_PRINCIPAL_ID \
  --scope $(az cosmosdb show -n cosmos-curso -g rg-curso --query id -o tsv)

# 3. Assignar el UAMI a múltiples Function Apps
for func in func-pedidos func-clientes func-pagos; do
    az functionapp identity assign \
      --name $func \
      --resource-group rg-curso \
      --identities $UAMI_ID
done
```

**Uso en código (especificar UAMI):**
```csharp
// Si tienes múltiples MIs assigned, debes especificar cuál usar
var credential = new DefaultAzureCredential(
    new DefaultAzureCredentialOptions
    {
        ManagedIdentityClientId = "<UAMI_CLIENT_ID>"
    });

var cosmosClient = new CosmosClient(endpoint, credential);
```

**Decisión rápida:**

```
Use System-Assigned cuando:
✅ Recurso único y aislado
✅ MI debe morir con el recurso
✅ Simple (no quieres gestión extra)

Use User-Assigned cuando:
✅ Múltiples recursos comparten permisos
✅ Pre-create MI before recursos (Bicep clean)
✅ Necesitas que MI sobreviva a recursos
✅ Compliance: separar lifecycle de identity
```

**Patrón común producción:**
```
Producción:
├── UAMI "uami-prod-storage-readers" (10 Functions read storage)
├── UAMI "uami-prod-cosmos-writers" (5 Functions write cosmos)
└── UAMI "uami-prod-keyvault-readers" (15 services read secrets)

Cada recurso puede tener varios UAMIs assigned (multi-identity).
```

## Slide 23 — RBAC granularidad: roles built-in vs custom

Azure tiene **400+ roles built-in**. Saber cuál usar:

```bash
# Ver roles built-in para Cosmos DB
az role definition list --query "[?contains(name, 'Cosmos')].{Name:roleName, Id:name}"

# Ejemplos:
# - Cosmos DB Account Reader Role
# - Cosmos DB Operator
# - Cosmos DB Data Contributor (data plane)
# - Cosmos DB Built-in Data Reader

# Para Storage:
# - Storage Blob Data Owner (full access blob)
# - Storage Blob Data Contributor (read/write/delete)
# - Storage Blob Data Reader (read only)
# - Storage Queue Data Contributor (queues)
```

**Principio: least privilege**

```
❌ MAL: Function MI con "Contributor" sobre el RG
   → Puede borrar TODO el RG
   → Si comprometida, daño total

✅ BIEN: Function MI con roles específicos
   ├── "Storage Blob Data Reader" sobre 1 container
   ├── "Cosmos DB Data Contributor" sobre 1 container
   └── "Key Vault Secrets User" sobre 1 secret específico
   → Solo lo que necesita, scope mínimo
```

**Asignar a scope granular:**
```bash
# Container específico de storage (no toda la cuenta)
az role assignment create \
  --role "Storage Blob Data Reader" \
  --assignee $MI_PRINCIPAL_ID \
  --scope "$(az storage account show -n stcurso -g rg-curso --query id -o tsv)/blobServices/default/containers/uploads"

# Secret específico de Key Vault (no todos los secrets)
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee $MI_PRINCIPAL_ID \
  --scope "$(az keyvault show -n kv-curso --query id -o tsv)/secrets/cosmos-connection"

# Container específico de Cosmos (no todo el account)
az cosmosdb sql role assignment create \
  --account-name cosmos-curso \
  --resource-group rg-curso \
  --scope "/dbs/PedidosDb/colls/orders" \
  --principal-id $MI_PRINCIPAL_ID \
  --role-definition-id "00000000-0000-0000-0000-000000000002"
```

**Custom roles (cuando built-in no encaja):**
```bash
# Crear role custom: solo READ y CREATE en blobs (no delete, no list)
cat > custom-role.json <<EOF
{
  "Name": "Custom Blob Reader Creator",
  "Description": "Read and create blobs but cannot delete or list",
  "Actions": [],
  "DataActions": [
    "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read",
    "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/write",
    "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/add/action"
  ],
  "NotDataActions": [
    "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/delete"
  ],
  "AssignableScopes": [
    "/subscriptions/<SUB_ID>"
  ]
}
EOF

az role definition create --role-definition custom-role.json

# Asignar
az role assignment create \
  --role "Custom Blob Reader Creator" \
  --assignee $MI_PRINCIPAL_ID \
  --scope <scope>
```

**RBAC vs ACL (Storage):**
```
ACL (legacy, en ADLS Gen2):
├── POSIX-style permissions per file/folder
├── 32 entries max per item
├── Más granular pero complejo

RBAC (moderno):
├── Identity → role → resource
├── Scoped (subscription, RG, resource, container, blob)
├── Más simple, suficiente en 95% casos
```

**Recomendación 2026:** RBAC con scopes granulares. ACL solo si necesitáis permisos POSIX-style heredados.

## Slide 24 — MI in production: troubleshooting completo

Cuando MI falla en producción, sigue este flow:

```
PROBLEMA: "Function devuelve 401/403 al acceder a Cosmos"
                        │
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 1: ¿MI está habilitada en la Function? │
   └─────────────────────────────────────────────┘
   az functionapp identity show -n func -g rg
   
   Esperado: principalId = <UUID>, type = SystemAssigned
   
   Si vacío:
   az functionapp identity assign -n func -g rg
   
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 2: ¿MI tiene el role correcto?          │
   └─────────────────────────────────────────────┘
   az role assignment list --assignee <PRINCIPAL_ID> -o table
   
   Esperado: ver el role asignado al scope correcto
   
   Si vacío o equivocado:
   az role assignment create --role "..." --assignee ... --scope ...
   
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 3: ¿Role propagación completa?         │
   └─────────────────────────────────────────────┘
   RBAC propagation tarda 5-10 min después de asignar
   
   Esperar y reintentar
   
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 4: ¿Código usa MI correctamente?       │
   └─────────────────────────────────────────────┘
   ¿Usas DefaultAzureCredential?
   ¿No estás passing keys o connection strings?
   
   Verificar logs locales:
   var credential = new DefaultAzureCredential(new() { 
       Diagnostics = { IsLoggingEnabled = true } 
   });
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 5: ¿Endpoint correcto?                  │
   └─────────────────────────────────────────────┘
   Cosmos: https://<account>.documents.azure.com (no .azure.com)
   Storage: https://<account>.blob.core.windows.net
   Key Vault: https://<vault>.vault.azure.net (NOT keys/...)
   
                        ▼
   ┌─────────────────────────────────────────────┐
   │ STEP 6: Network blocked?                     │
   └─────────────────────────────────────────────┘
   ¿Cosmos/Storage tienen firewall que bloquea?
   ¿Function en VNet con UDR mal configurada?
   
   Test desde Function Console (Kudu):
   curl -v https://cosmos-curso.documents.azure.com
```

**Logs útiles en App Insights:**
```kusto
// Auth failures de MI
exceptions
| where outerMessage contains "ManagedIdentity" or 
        outerMessage contains "DefaultAzureCredential"
| project timestamp, message, outerMessage, problemId
| order by timestamp desc

// Specific Cosmos auth errors
exceptions
| where type == "Microsoft.Azure.Cosmos.CosmosException"
| where outerMessage contains "Forbidden" or outerMessage contains "Unauthorized"
| project timestamp, outerMessage
```

**Common errors y fixes:**

| Error | Causa | Fix |
|---|---|---|
| `ManagedIdentityCredential authentication failed` | MI not enabled | `az functionapp identity assign` |
| `Endpoint forbidden` | RBAC no asignado | Add role assignment |
| `Forbidden 403` Cosmos | Role + scope wrong | Check `az cosmosdb sql role assignment` |
| `Unauthorized 401` Key Vault | RBAC vs Access Policies mismatch | Use RBAC mode (--enable-rbac-authorization true) |
| Timeout | Network/firewall | Verify VNet, NSG, firewall rules |

## Slide 25 — Cross-tenant scenarios

A veces necesitáis MI accediendo a recursos en otro tenant (multi-tenant SaaS, partner):

```
Tu tenant (Provider):                Cliente tenant:
┌──────────────────┐                 ┌──────────────────┐
│  Function App    │ ─── access ───▶ │  Storage Account │
│  (tu MI)         │                 │  (his data)      │
└──────────────────┘                 └──────────────────┘
```

**Setup:**
```bash
# 1. Tu MI (en tu tenant) ya existe
PROVIDER_MI_PRINCIPAL=$(az functionapp identity show -n func-app -g rg --query principalId -o tsv)

# 2. Tu cliente debe agregar tu MI como guest en su tenant
# (esto lo hace el cliente, no tú)
# Cliente: Entra ID → Users → Invite external user
# Email: <tu-MI-objectId>@<tu-tenant>

# 3. Cliente asigna RBAC al guest (tu MI)
# az role assignment create \
#   --role "Storage Blob Data Reader" \
#   --assignee <tu-MI-objectId> \
#   --scope <su-storage-id>

# 4. En tu código:
var credential = new DefaultAzureCredential(
    new DefaultAzureCredentialOptions
    {
        // Tenant ID del cliente
        TenantId = "<cliente-tenant-id>",
        
        // Your MI ID
        ManagedIdentityClientId = "<tu-uami-client-id>"
    });
```

**Casos de uso real:**

| Scenario | Cross-tenant pattern |
|---|---|
| SaaS multi-tenant | Tus services acceden a customer storage |
| Partner integration | Tu MI lee data del partner |
| Acquisitions | Compañía A absorbida → MI de A accede a B |
| Compliance | Auditor accede a datos de subsidiaria |

**Service Provider Multi-tenancy:**
```csharp
// Tu app gestiona N customers, cada uno con sus recursos
public class CustomerStorageService
{
    private readonly Dictionary<string, BlobServiceClient> _clients = new();
    
    public BlobServiceClient GetClientForCustomer(string customerId)
    {
        if (!_clients.ContainsKey(customerId))
        {
            var customer = LookupCustomer(customerId);
            
            var credential = new DefaultAzureCredential(
                new DefaultAzureCredentialOptions
                {
                    TenantId = customer.TenantId,  // dynamic per customer
                    ManagedIdentityClientId = "<your-uami>"
                });
            
            _clients[customerId] = new BlobServiceClient(
                new Uri(customer.StorageEndpoint),
                credential);
        }
        return _clients[customerId];
    }
}
```

**Anti-pattern:** crear N MIs, una por customer. Mejor 1 MI con acceso cross-tenant invitada en cada tenant.

```csharp
// Llamar a Logic App / Function externa con MI auth
public class AzureApiClient
{
    private readonly TokenCredential _credential;
    private readonly HttpClient _http;
    
    public async Task<T> CallAzureApiAsync<T>(string url, string scope)
    {
        var token = await _credential.GetTokenAsync(
            new TokenRequestContext(new[] { scope }));
        
        using var request = new HttpRequestMessage(HttpMethod.Get, url);
        request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token.Token);
        
        var response = await _http.SendAsync(request);
        return await response.Content.ReadFromJsonAsync<T>();
    }
}

// Uso:
```

## Slide 27 — Anti-patterns MI: errores comunes

```
❌ ANTI-PATTERN 1: Mezclar MI con keys "por si acaso"
   var client = new CosmosClient(endpoint, accountKey);  // ← key
   if (production)
       client = new CosmosClient(endpoint, new DefaultAzureCredential());
   
   ✅ Solo MI en todos los entornos. Local: usa az login + Azure CLI.

❌ ANTI-PATTERN 2: Hardcodear MI tenant en código
   var credential = new DefaultAzureCredential(
       new() { TenantId = "fixed-tenant-id" });  // ← bad
   
   ✅ Tenant via App Setting (varía dev/prod)

❌ ANTI-PATTERN 3: Roles "Owner" o "Contributor" para MI
   az role assignment create --role "Owner" ...  # too much!
   
   ✅ Roles granulares: "Cosmos DB Data Reader", scope al container

❌ ANTI-PATTERN 4: Compartir MI entre apps no relacionadas
   App A (no-prod) y App B (prod) usan mismo UAMI
   → Incident en A puede afectar B
   
   ✅ MI por boundary lógico (per-environment, per-app)

❌ ANTI-PATTERN 5: No revocar MI tras decommission
   Function App eliminada, UAMI sigue con permisos
   → Surface attack innecesaria
   
   ✅ Cleanup en script de decommission

❌ ANTI-PATTERN 6: No monitorear sign-ins de MI
   ✅ Alerta en Entra ID logs si MI se autentica desde IP unusual

❌ ANTI-PATTERN 7: Usar MI Service Principal para human-style operations
   "Tu MI ejecuta migraciones de DB en deploy" 
   → Audit confuso (parece que MI hizo cambios manuales)
   
   ✅ MI para runtime, separadas para CI/CD operations

❌ ANTI-PATTERN 8: MI con Reader sobre toda la subscription
   ✅ Granular scope: solo el RG/recurso que necesita
```

**El más común:**
```
"Compartir cosmos read key entre 5 microservicios"
→ Si 1 service comprometido, todos comprometidos
→ Migrate to MI: 5 separate identities, granular roles
→ Compromiso de 1 = blast radius limited a esa identity
```

## Slide 28 — Cierre del submódulo
Managed Identity es el cambio más importante que podéis hacer en la seguridad de vuestras apps. Elimina passwords, simplifica rotación, y funciona en todos los servicios Azure principales.

DefaultAzureCredential es el pegamento que hace que el mismo código funcione en local (az cli) y en Azure (MI). Un solo patrón para todos los servicios.

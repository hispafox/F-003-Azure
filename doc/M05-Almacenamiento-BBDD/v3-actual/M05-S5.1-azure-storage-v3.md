## Slide 2 — Contexto: almacenamiento en vuestro stack
En los módulos anteriores hemos usado almacenamiento sin profundizar: Blob Storage para archivos en triggers, Queue Storage para mensajes en Functions, Cosmos DB como base de datos principal. Este módulo conecta los puntos.

Azure tiene decenas de servicios de almacenamiento, pero los cuatro que viven dentro de un Storage Account son los fundamentales. El 80% de lo que necesitéis como desarrolladores pasa por aquí.

## Slide 3 — Azure Storage Account: el contenedor de todo

```
Storage Account (stventasprod)
├── Blob Storage     → Archivos: imágenes, PDFs, backups, logs, exports
├── Table Storage    → Datos NoSQL sencillos: key-value con esquema flexible
├── Queue Storage    → Mensajes: comunicación asíncrona entre servicios
└── File Storage     → File shares: SMB/NFS compartidos (como un NAS en la nube)
```

```bash
az storage account create \
  --name stventasprod \
  --resource-group rg-ventas-prod \
  --location westeurope \
  --sku Standard_LRS \
  --kind StorageV2 \
  --min-tls-version TLS1_2 \
  --allow-blob-public-access false \
  --tags entorno=prod proyecto=ventas
```

**Decisiones al crear:**
- **Nombre:** 3-24 chars, solo minúsculas y números, único globalmente
- **Kind:** StorageV2 (siempre — es el más completo)
- **SKU:** Redundancia (LRS, ZRS, GRS, GZRS)
- **Public access:** `false` en producción (bloquear acceso anónimo a blobs)
- **TLS:** Mínimo 1.2

## Slide 4 — Redundancia: cómo protege Azure tus datos

| SKU | Copias | Distribución | Durabilidad | Coste relativo |
|-----|:------:|:------------:|:-----------:|:--------------:|
| **LRS** | 3 | Mismo datacenter | 11 nueves | 1x |
| **ZRS** | 3 | 3 zonas, misma región | 12 nueves | 1.25x |
| **GRS** | 6 | 3 local + 3 en región par | 16 nueves | 2x |
| **GZRS** | 6 | 3 zonas + 3 en región par | 16 nueves | 2.25x |
| **RA-GRS** | 6 | GRS + lectura en secundaria | 16 nueves | 2.1x |
| **RA-GZRS** | 6 | GZRS + lectura en secundaria | 16 nueves | 2.4x |

**RA = Read-Access:** Podéis leer de la réplica secundaria (útil para distribuir carga de lectura o para DR con lectura inmediata).

**¿Cuál elegir?**
- Desarrollo y prácticas: **LRS**
- Producción estándar: **ZRS** (protege contra fallo de una zona de disponibilidad)
- Producción crítica con DR: **GRS** o **GZRS** + failover manual/automático
- Producción con lectura distribuida: **RA-GRS** o **RA-GZRS**

## Slide 5 — Access Tiers: optimizar coste de almacenamiento

| Tier | Almacenamiento (€/GB/mes) | Lectura (€/10K ops) | Escritura (€/10K ops) | Ideal para |
|------|:------------------------:|:-------------------:|:--------------------:|-----------|
| **Hot** | ~0.018€ | ~0.004€ | ~0.05€ | Datos activos, lectura frecuente |
| **Cool** | ~0.010€ | ~0.01€ | ~0.10€ | Datos < 1 lectura/mes, retención 30+ días |
| **Cold** | ~0.005€ | ~0.01€ | ~0.18€ | Datos raramente accedidos, retención 90+ días |
| **Archive** | ~0.002€ | ~5€ + horas de espera | ~0.10€ | Compliance, históricos, backup largo plazo |

El almacenamiento es más barato en tiers fríos, pero las operaciones son más caras. El truco es poner los datos en el tier correcto según cuánto los accedéis.

**Lifecycle Management (automatizar):**
```bash
az storage account management-policy create \
  --account-name stventasprod -g mi-rg \
  --policy @lifecycle-policy.json
```

```json
{
  "rules": [
    {
      "name": "mover-a-cool-30d",
      "type": "Lifecycle",
      "definition": {
        "filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["logs/", "exports/"] },
        "actions": {
          "baseBlob": {
            "tierToCool": { "daysAfterModificationGreaterThan": 30 },
            "tierToArchive": { "daysAfterModificationGreaterThan": 180 },
            "delete": { "daysAfterModificationGreaterThan": 365 }
```

## Slide 6 — Blob Storage: jerarquía y tipos

```
Storage Account → Container → Blobs
stventasprod    → facturas   → 2025/06/factura-001.pdf
                              → 2025/06/factura-002.pdf
                → imagenes   → productos/laptop.jpg
                → backups    → 2025/06/15/backup-diario.zip
```

**Tipos de blob:**
- **Block Blob** (99% de los casos): archivos hasta 190.7 TB. Upload en bloques paralelos. Para imágenes, PDFs, vídeos, backups, logs, exports, cualquier archivo.
- **Append Blob**: solo se puede añadir al final. Perfecto para logs y auditoría donde nunca editas lo anterior.
- **Page Blob**: acceso random read/write de 512-byte pages. Usado internamente para discos de VMs. Raramente lo usaréis directamente.

**"Carpetas" en Blob Storage:** No existen realmente. `/2025/06/factura-001.pdf` es un blob cuyo nombre incluye barras. Pero las herramientas (portal, SDK, Explorer) las muestran como carpetas para comodidad.

## Slide 7 — Blob Storage: conexión y CRUD con SDK

```csharp
using Azure.Storage.Blobs;
using Azure.Storage.Blobs.Models;
using Azure.Identity;

// Conexión con Managed Identity (producción)
var client = new BlobServiceClient(
    new Uri("https://stventasprod.blob.core.windows.net"),
    new DefaultAzureCredential());

// Conexión con connection string (desarrollo)
// var client = new BlobServiceClient(connectionString);

// Obtener/crear contenedor
var container = client.GetBlobContainerClient("facturas");
await container.CreateIfNotExistsAsync(PublicAccessType.None);

// SUBIR archivo
var blob = container.GetBlobClient("2025/06/factura-001.pdf");
await blob.UploadAsync("./factura-001.pdf", new BlobUploadOptions
{
    Metadata = new Dictionary<string, string>
    {
        ["clienteId"] = "cli-001",
        ["fechaEmision"] = "2025-06-15",
        ["importe"] = "1299.99"
    },
    HttpHeaders = new BlobHttpHeaders { ContentType = "application/pdf" }
});

// SUBIR desde stream (para archivos grandes o generados en memoria)
using var stream = new MemoryStream(Encoding.UTF8.GetBytes(jsonContent));
await blob.UploadAsync(stream, overwrite: true);
```

## Slide 8 — Blob Storage: descargar, listar, propiedades

```csharp
// DESCARGAR a archivo
await blob.DownloadToAsync("./descarga/factura-001.pdf");

// DESCARGAR a memoria
var response = await blob.DownloadContentAsync();
var contenido = response.Value.Content.ToString();  // Para texto/JSON
var bytes = response.Value.Content.ToArray();         // Para binario

// LISTAR blobs con prefijo (simular carpetas)
await foreach (var item in container.GetBlobsAsync(prefix: "2025/06/"))
{
    Console.WriteLine($"  {item.Name} | {item.Properties.ContentLength} bytes | {item.Properties.LastModified}");
    // Metadata
    foreach (var (key, value) in item.Metadata)
        Console.WriteLine($"    {key}: {value}");
}

// LISTAR por "carpetas" (jerárquico)
await foreach (var item in container.GetBlobsByHierarchyAsync(delimiter: "/", prefix: "2025/"))
{
    if (item.IsPrefix)
        Console.WriteLine($"  [carpeta] {item.Prefix}");
    else
        Console.WriteLine($"  [archivo] {item.Blob.Name}");
}

// PROPIEDADES de un blob
var props = await blob.GetPropertiesAsync();
Console.WriteLine($"Tamaño: {props.Value.ContentLength}");
Console.WriteLine($"Content-Type: {props.Value.ContentType}");
Console.WriteLine($"Creado: {props.Value.CreatedOn}");
Console.WriteLine($"ETag: {props.Value.ETag}");

// ELIMINAR
await blob.DeleteIfExistsAsync(DeleteSnapshotsOption.IncludeSnapshots);

// COPIAR entre contenedores
var destBlob = client.GetBlobContainerClient("archivados").GetBlobClient("factura-001.pdf");
await destBlob.StartCopyFromUriAsync(blob.Uri);
```

## Slide 9 — Blob Storage: upload de archivos grandes

Para archivos > 256 MB, el SDK automáticamente usa block upload paralelo:

```csharp
// Upload de archivo grande con progreso
var options = new BlobUploadOptions
{
    TransferOptions = new StorageTransferOptions
    {
        MaximumConcurrency = 8,              // 8 bloques en paralelo
        MaximumTransferSize = 4 * 1024 * 1024, // Bloques de 4 MB
        InitialTransferSize = 4 * 1024 * 1024
    },
    ProgressHandler = new Progress<long>(bytesTransferred =>
    {
        Console.WriteLine($"Subido: {bytesTransferred / 1024 / 1024} MB");
    })
};

await blob.UploadAsync("./backup-2gb.zip", options);
```

**Para uploads desde el navegador (sin pasar por tu API):**
Genera un SAS token y deja que el frontend suba directamente a Storage:
```csharp
// API genera SAS → frontend sube directo a Blob
var sasUri = blob.GenerateSasUri(BlobSasPermissions.Write, DateTimeOffset.UtcNow.AddMinutes(30));
return Ok(new { uploadUrl = sasUri.ToString() });
// Frontend: fetch(uploadUrl, { method: 'PUT', body: file, headers: { 'x-ms-blob-type': 'BlockBlob' } })
```

## Slide 10 — SAS Tokens en detalle

```csharp
// SAS para un blob específico (1 hora, solo lectura)
var sasBuilder = new BlobSasBuilder
{
    BlobContainerName = "facturas",
    BlobName = "factura-001.pdf",
    Resource = "b",  // "b" = blob, "c" = container
    ExpiresOn = DateTimeOffset.UtcNow.AddHours(1),
    StartsOn = DateTimeOffset.UtcNow.AddMinutes(-5),  // Margen por clock skew
    IPRange = new SasIPRange(IPAddress.Parse("203.0.113.0"), IPAddress.Parse("203.0.113.255"))  // Solo desde la oficina
};
sasBuilder.SetPermissions(BlobSasPermissions.Read);

var sasUri = blob.GenerateSasUri(sasBuilder);

// SAS para un container completo (upload de múltiples archivos)
var containerSasBuilder = new BlobSasBuilder
{
    BlobContainerName = "uploads-temp",
    Resource = "c",
    ExpiresOn = DateTimeOffset.UtcNow.AddHours(2)
};
containerSasBuilder.SetPermissions(BlobContainerSasPermissions.Write | BlobContainerSasPermissions.Create);
```

**User Delegation SAS (más seguro, recomendado):**
En vez de firmar con la account key (si se filtra, acceso total), firma con credenciales de Entra ID:
```csharp
var userDelegationKey = await client.GetUserDelegationKeyAsync(
    DateTimeOffset.UtcNow, DateTimeOffset.UtcNow.AddHours(1));
var sasBuilder = new BlobSasBuilder { ... };
var sasUri = new BlobUriBuilder(blob.Uri) { Sas = sasBuilder.ToSasQueryParameters(userDelegationKey, client.AccountName) }.ToUri();
```

## Slide 11 — Table Storage: cuándo y cómo

Table Storage es un almacén NoSQL key-value extremadamente simple y barato. No es Cosmos DB — es mucho más limitado pero también mucho más barato.

**Estructura:**
- **PartitionKey + RowKey** = clave primaria compuesta
- Queries por PartitionKey: rápidas (datos co-localizados)
- Queries sin PartitionKey: table scan (lento con muchos datos)
- Sin índices secundarios, sin JOINs, sin schema fijo

**Cuándo usar:** Metadata de aplicación, configuración, registros de auditoría, datos de telemetría de alto volumen y baja complejidad, caché persistente simple.

**Cuándo NO usar:** Queries complejas, relaciones, índices secundarios, consistencia fuerte → Cosmos DB. Datos relacionales con JOINs → SQL.

## Slide 12 — Table Storage: CRUD con SDK

```csharp
using Azure.Data.Tables;

var tableClient = new TableClient(connectionString, "AuditLog");
await tableClient.CreateIfNotExistsAsync();

// INSERTAR
var entry = new TableEntity("2025-06-15", Guid.NewGuid().ToString())
{
    { "Usuario", "pedro@empresa.com" },
    { "Accion", "CrearPedido" },
    { "Detalle", "Pedido PED-001 creado por €1299.99" },
    { "Timestamp", DateTime.UtcNow },
    { "IP", "203.0.113.50" }
};
await tableClient.AddEntityAsync(entry);

// LEER por clave exacta (< 1ms)
var entity = await tableClient.GetEntityAsync<TableEntity>("2025-06-15", "abc-123");

// QUERY por PartitionKey (rápido)
var logs = tableClient.QueryAsync<TableEntity>(e => e.PartitionKey == "2025-06-15");
await foreach (var log in logs)
    Console.WriteLine($"{log["Usuario"]} → {log["Accion"]}");

// QUERY con filtro (OData)
var errores = tableClient.QueryAsync<TableEntity>(
    filter: $"PartitionKey eq '2025-06-15' and Accion eq 'Error'");

// BATCH (hasta 100 operaciones en la misma partición)
var batch = new List<TableTransactionAction>();
for (int i = 0; i < 50; i++)
    batch.Add(new TableTransactionAction(TableTransactionActionType.Add,
        new TableEntity("2025-06-15", $"batch-{i}") { { "Dato", $"valor-{i}" } }));
await tableClient.SubmitTransactionAsync(batch);
```

## Slide 13 — Queue Storage: mensajería simple

```csharp
using Azure.Storage.Queues;
using Azure.Storage.Queues.Models;

var queue = new QueueClient(connectionString, "pedidos-nuevos",
    new QueueClientOptions { MessageEncoding = QueueMessageEncoding.Base64 });
await queue.CreateIfNotExistsAsync();

// ENVIAR mensaje
var pedido = new { Id = "PED-001", Total = 99.99, Cliente = "cli-001" };
await queue.SendMessageAsync(JsonSerializer.Serialize(pedido));

// ENVIAR con delay (invisible 5 minutos, para procesamiento diferido)
await queue.SendMessageAsync(
    JsonSerializer.Serialize(pedido),
    visibilityTimeout: TimeSpan.FromMinutes(5));

// ENVIAR con TTL (expira en 1 hora si nadie lo procesa)
await queue.SendMessageAsync(
    JsonSerializer.Serialize(pedido),
    timeToLive: TimeSpan.FromHours(1));

// RECIBIR (peek lock: invisible para otros durante 30s)
var mensajes = await queue.ReceiveMessagesAsync(
    maxMessages: 10,
    visibilityTimeout: TimeSpan.FromSeconds(30));

foreach (var msg in mensajes.Value)
{
    var body = JsonSerializer.Deserialize<JsonElement>(msg.Body.ToString());
    Console.WriteLine($"Pedido: {body.GetProperty("Id")}");
    
    // Procesar OK → eliminar
    await queue.DeleteMessageAsync(msg.MessageId, msg.PopReceipt);
}

// PEEK (ver sin sacar de la cola)
var peek = await queue.PeekMessagesAsync(maxMessages: 5);

// Cuántos mensajes hay
var props = await queue.GetPropertiesAsync();
Console.WriteLine($"En cola: {props.Value.ApproximateMessagesCount}");
```

## Slide 14 — Queue Storage vs Service Bus: decisión

| | Queue Storage | Service Bus |
|---|:---:|:---:|
| Coste | ~gratis | ~10€/mes |
| Mensaje máximo | 64 KB | 256 KB (Std) / 100 MB (Prem) |
| TTL máximo | 7 días | Ilimitado |
| FIFO garantizado | No | Sí (sessions) |
| Dead-letter | Poison queue básica | DLQ completa con metadata |
| Deduplicación | No | Sí |
| Transacciones | No | Sí |
| Topics (pub/sub) | No | Sí |
| Batch receive | 32 mensajes | Configurable |
| Tamaño cola | 500 TB | 80 GB (Std) |

**Queue Storage:** Barato, alto volumen, sin garantías avanzadas. Para Functions triggers internos, señales entre servicios, trabajo encolado simple.

**Service Bus:** Enterprise. FIFO, dead-letter, topics, transacciones. Para procesamiento de pedidos, facturación, cualquier cosa donde perder un mensaje es inaceptable.

## Slide 15 — Azure Files: file shares en la nube

```bash
# Crear file share (100 GB de cuota)
az storage share create --account-name stventasprod --name documentos --quota 100

# Subir archivo
az storage file upload --account-name stventasprod --share-name documentos \
  --source ./informe.pdf --path informes/2025/informe-junio.pdf

# Listar archivos
az storage file list --account-name stventasprod --share-name documentos \
  --path informes/2025 --output table

# Montar como unidad de red (Windows)
net use Z: \\stventasprod.file.core.windows.net\documentos /u:stventasprod <key>

# Montar en Linux
sudo mount -t cifs //stventasprod.file.core.windows.net/documentos /mnt/docs \
  -o username=stventasprod,password=<key>,serverino,dir_mode=0777,file_mode=0777
```

**Azure File Sync:** Sincroniza Azure Files con Windows Server on-premises. Caché local + cloud storage. Para migración gradual de file servers.

**¿Azure Files vs Blob?**
- Acceso SMB/NFS (como disco de red) → Files
- Acceso por API/SDK desde código → Blob (más barato, más escalable, más features)

## Slide 19 — Soft delete, versionado e immutability

```bash
# Soft delete para blobs (recuperable 30 días)
az storage account blob-service-properties update \
  --account-name stventasprod -g mi-rg \
  --enable-delete-retention true --delete-retention-days 30

# Soft delete para containers
az storage account blob-service-properties update \
  --account-name stventasprod -g mi-rg \
  --enable-container-delete-retention true --container-delete-retention-days 14

# Versionado (mantener todas las versiones de cada blob)
az storage account blob-service-properties update \
  --account-name stventasprod -g mi-rg --enable-versioning true

# Immutability (compliance: blobs que NO se pueden modificar ni eliminar)
az storage container immutability-policy create \
  --account-name stventasprod --container-name legal --period 365
```

**Recuperar un blob eliminado:**
```bash
az storage blob undelete --account-name stventasprod --container-name facturas --name factura-borrada.pdf
```

## Slide 23 — Patrones de uso con Azure Functions

**Blob trigger + output binding (procesamiento de archivos):**
```csharp
[Function("ProcesarFactura")]
[BlobOutput("procesados/{nombre}-resultado.json", Connection = "StorageConnection")]
public string Procesar(
    [BlobTrigger("uploads/{nombre}.pdf", Connection = "StorageConnection")] Stream pdf, string nombre)
{
    // Leer PDF → extraer datos → devolver JSON
    return JsonSerializer.Serialize(new { factura = nombre, procesado = DateTime.UtcNow });
}
```

**Queue trigger + blob output (procesamiento asíncrono):**
```csharp
[Function("GenerarInforme")]
[BlobOutput("informes/{rand-guid}.pdf", Connection = "StorageConnection")]
public byte[] Generar([QueueTrigger("informes-pendientes", Connection = "StorageConnection")] string msg)
{
    var datos = JsonSerializer.Deserialize<InformeRequest>(msg);
    return GenerarPDF(datos);
}
```

**Timer + blob (exports programados):**
```csharp
[Function("ExportDiario")]
[BlobOutput("exports/{DateTime:yyyy-MM-dd}/ventas.csv", Connection = "StorageConnection")]
public string Export([TimerTrigger("0 0 2 * * *")] TimerInfo timer) => GenerarCSVVentas();
```

## Slide 25 — Checklist de Storage para producción

- [ ] Public access deshabilitado (`--allow-blob-public-access false`)
- [ ] Firewall: `--default-action Deny` + excepciones
- [ ] TLS 1.2 mínimo

- [ ] Redundancia según SLA (ZRS mínimo para producción)
- [ ] Diagnostic logs habilitados
- [ ] Alertas de availability, egress anormal y auth errors
- [ ] Resource Lock en el Storage Account de producción

## Slide 27 — ADLS Gen2: Data Lake en Azure

Para analytics y big data, ADLS Gen2 es el estándar:

```
Storage Account v2 + HNS habilitado
└── File system (= "container" pero con jerarquía real)
    └── Carpetas/
        └── Subcarpetas/
            └── archivo.parquet
                
ACL granulares por carpeta y archivo (POSIX-style):
├── owner:rwx
├── group:r-x
└── other:r--
```

**Crear y trabajar con ADLS:**
```bash
# Crear file system (= container)
az storage fs create --name datos-empresa \
  --account-name stcursodatalake --auth-mode login

# Crear directorio
az storage fs directory create --name "ventas/2026/q1" \
  --file-system datos-empresa --account-name stcursodatalake \
  --auth-mode login

# Subir archivo a directorio específico
az storage fs file upload \
  --source ventas-q1.parquet \
  --path "ventas/2026/q1/ventas-q1.parquet" \
  --file-system datos-empresa \
  --account-name stcursodatalake \
  --auth-mode login

# ACL: dar permisos a un grupo solo en /ventas/
az storage fs access set --acl "user::rwx,group:VentasGroup:rwx,other::r-x" \
  --path "ventas" --file-system datos-empresa \
  --account-name stcursodatalake --auth-mode login
```

**Diferencias vs Blob normal:**

| Feature | Blob Storage | ADLS Gen2 |
|---|:---:|:---:|
| API REST | Blob API | Blob API + Data Lake API |
| Jerarquía | Flat (paths simulados) | Real (carpetas y archivos) |
| ACL | RBAC + SAS | RBAC + ACL POSIX |
| Atomic rename | No (copia + delete) | Sí (rename real) |
| HDFS compatible | No | Sí |
| Coste | Estándar | Estándar (mismo precio) |
| Recomendado para | Apps web, archivos | Data engineering, analytics |

**Casos de uso reales:**
- Data Lake corporativo: raw, processed, curated layers
- Data Warehouse moderno (con Synapse, Databricks)
- Logs centralizados estructurados
- ML training datasets

**Gotcha**: SDK Blob normal funciona en ADLS, pero pierdes algunas features (rename atómico, ACL). Usar SDK específico `Azure.Storage.Files.DataLake` para sacar todo.

## Slide 28 — Lifecycle Management: ahorrar dinero automáticamente

Política para mover blobs entre tiers automáticamente según su edad:

```json
// Crear política con CLI o JSON
{
  "rules": [
    {
      "name": "ArchiveOldData",
      "enabled": true,
      "type": "Lifecycle",
      "definition": {
        "filters": {
          "blobTypes": ["blockBlob"],
          "prefixMatch": ["logs/", "archives/"]
        },
        "actions": {
          "baseBlob": {
            "tierToCool": {
              "daysAfterModificationGreaterThan": 30
            },
            "tierToCold": {
              "daysAfterModificationGreaterThan": 90
            },
            "tierToArchive": {
              "daysAfterModificationGreaterThan": 180,
              "daysAfterLastTierChangeGreaterThan": 7
            },
            "delete": {
              "daysAfterModificationGreaterThan": 2555
            }
          },
          "snapshot": {
            "delete": {
              "daysAfterCreationGreaterThan": 90
            }
          },
          "version": {
            "delete": {
              "daysAfterCreationGreaterThan": 365
            }
          }
        }
      }
    }
  ]
}
```

**Aplicar:**
```bash
az storage account management-policy create \
  --account-name stcurso \
  --resource-group rg-curso \
  --policy @lifecycle-policy.json
```

**Tiers disponibles 2026:**

| Tier | Latencia first byte | Coste GB/mes | Min retention | Caso uso |
|---|---|---:|---:|---|
| **Hot** | <100ms | €0.018 | None | Acceso frecuente |
| **Cool** | <100ms | €0.010 | 30 días | <1×/mes |
| **Cold** | <100ms | €0.0036 | 90 días | <1×/año (GA 2023) |
| **Archive** | hours | €0.00099 | 180 días | Compliance, raw data |

**Coste real anual de 1TB:**
```
Hot:     €216/año  (storage)
Cool:    €120/año  (storage) + read fees if accessed
Cold:    €43/año   (storage) + higher read fees  
Archive: €12/año   (storage) + retrieval cost + 1-15h wait
```

**Trampa:** mover a Cool/Cold/Archive **antes del minimum retention** dispara penalty. Lifecycle bien configurado es la única forma sana.

**Real-world example:**
```
App de e-commerce con 10TB de imágenes:
├── 0-30 días: Hot (productos activos, vistas)         → €180/mes
├── 30-180 días: Cool (productos descatalogados)        → €100/mes
├── 180-1825 días: Cold (compliance fiscal)             → €36/mes
└── 1825+ días: Delete (RGPD)                            → €0

Sin lifecycle: 10TB × Hot todo el año = €2160/año
Con lifecycle: ahorro ~70% = €650 saved/año
```

## Slide 29 — Blob versioning + Soft delete: protección contra disasters

Dos features que te salvan cuando alguien borra algo por error:

```bash
# Habilitar Soft Delete para blobs
az storage account blob-service-properties update \
  --account-name stcurso \
  --resource-group rg-curso \
  --enable-delete-retention true \
  --delete-retention-days 30

# Habilitar Soft Delete para containers
az storage account blob-service-properties update \
  --account-name stcurso \
  --resource-group rg-curso \
  --enable-container-delete-retention true \
  --container-delete-retention-days 30

# Habilitar Versioning de Blobs
az storage account blob-service-properties update \
  --account-name stcurso \
  --resource-group rg-curso \
  --enable-versioning true

# Habilitar Change Feed (audit log de cambios)
az storage account blob-service-properties update \
  --account-name stcurso \
  --resource-group rg-curso \
  --enable-change-feed true \
  --change-feed-retention-days 90
```

**Cómo funcionan en conjunto:**

```
Estado inicial: blob "doc.pdf" v1
│
├── Someone updates → blob actualizado a v2
│   └── v1 queda como version anterior (versioning)
│
├── Someone deletes → blob marcado como deleted
│   └── v1 y v2 quedan retrievables (soft delete) durante 30 días
│
└── Recovery:
    ├── Listar versiones soft-deleted
    │   az storage blob list --account-name X \
    │     --container-name Y --include vd
    │
    └── Restaurar versión específica
        az storage blob undelete --account-name X \
          --container-name Y --name doc.pdf
```

**Recovery completo (ejemplo real):**
```bash
# Alguien borró todo el container "facturas" por error

# 1. Restore container completo (si soft-delete container está activo)
az storage container restore \
  --account-name stcurso \
  --name facturas \
  --deleted-version "01D..." \
  --resource-group rg-curso

# 2. Si el container existe pero blobs están borrados
az storage blob undelete \
  --account-name stcurso \
  --container-name facturas \
  --name "factura-2026-001.pdf"

# 3. Restaurar versión específica anterior
az storage blob copy start \
  --account-name stcurso \
  --destination-container facturas \
  --destination-blob "factura-2026-001.pdf" \
  --source-uri "https://stcurso.blob.core.windows.net/facturas/factura-2026-001.pdf?versionid=2026-04-15T10:00:00Z"
```

**Coste extra:** versions cuentan como blobs adicionales (mismo precio que blob normal). Soft-deleted no se factura. Configurad lifecycle para borrar versiones viejas.

**Combinación recomendada para producción:**
- Versioning: ON
- Soft delete blobs: 30 días
- Soft delete containers: 30 días
- Change feed: 90 días (audit)
- Lifecycle: borrar versions > 90 días

## Slide 30 — Immutable Blobs (WORM): compliance y legal hold

Para datos que **nunca pueden cambiar** (auditoría, finanzas, sanidad):

```bash
# Time-based immutability: bloqueado durante N días
az storage container immutability-policy create \
  --account-name stcurso \
  --container-name auditoria \
  --period 365 \
  --resource-group rg-curso

# Lock the policy (NUNCA podrá cambiarse, ni borrarse)
az storage container immutability-policy lock \
  --account-name stcurso \
  --container-name auditoria \
  --resource-group rg-curso \
  --if-match "<etag-from-previous-command>"

# Legal hold: bloqueado indefinidamente hasta que se quite
az storage container legal-hold set \
  --account-name stcurso \
  --container-name evidencia-legal \
  --tags "case-2026-001"

# Quitar legal hold (requiere permisos elevados + audit)
az storage container legal-hold clear \
  --account-name stcurso \
  --container-name evidencia-legal \
  --tags "case-2026-001"
```

**Comportamiento:**

```
Container con immutability policy LOCKED 365 días:
├── ✅ Subir blobs nuevos
├── ✅ Leer blobs existentes
├── ❌ Modificar blobs (UPDATE)
├── ❌ Borrar blobs (DELETE)
├── ❌ Cambiar/borrar la política
└── ✅ Pasados 365 días desde subida → permite delete
```

**Casos de uso reales:**

| Sector | Aplicación | Retention |
|---|---|---|
| Finanzas | Logs de transacciones | 7-10 años |
| Salud | Historias clínicas (HIPAA) | 7+ años |
| Seguros | Pólizas y reclamaciones | 30+ años |
| Legal | Evidencias electrónicas | Indefinido (legal hold) |
| Energía | Logs SCADA / IoT industrial | 10+ años |

**Compliance mode vs Unlocked:**

```
Modo "Unlocked" (testing, antes de lock):
├── Política existe pero se puede modificar/borrar
└── Útil para validar antes de comprometerse

Modo "Locked" (definitivo):
├── Microsoft NO PUEDE quitarla (ni con soporte)
├── Cumple con regulaciones SEC, FINRA, CFTC, FDA, HIPAA
└── ⚠️ Decisión irreversible — testear muy bien antes
```

**Gotcha brutal:** si lockáis una política de 10 años y os equivocáis con un blob, se queda 10 años. Procesos de aprobación humana **antes de subir**.

## Slide 31 — Event-driven blob processing: arquitectura moderna

En lugar de polling, reaccionar a eventos en tiempo real:

```
┌─────────────┐    upload    ┌─────────────────┐    event    ┌──────────────┐
│   Cliente   │ ──────────▶  │  Blob Storage    │ ──────────▶ │ Event Grid   │
│   (web)     │              │  /uploads/       │             │  Topic       │
└─────────────┘              └─────────────────┘             └──────┬───────┘
                                                                     │
                              ┌──────────────────────────────────────┼─────────┐
                              │                                      │         │
                              ▼                                      ▼         ▼
                       ┌──────────────┐              ┌──────────────┐  ┌──────────┐
                       │  Function    │              │  Function    │  │  Logic   │
                       │  Thumbnail   │              │  Virus Scan  │  │  App     │
                       │  Generator   │              │  + Quarantine│  │  Notify  │
                       └──────────────┘              └──────────────┘  └──────────┘
```

**Configurar Event Grid subscription:**
```bash
# Suscripción que enruta eventos de blob a una Function
az eventgrid event-subscription create \
  --name sub-blob-uploads \
  --source-resource-id $(az storage account show \
    -n stcurso -g rg-curso --query id -o tsv) \
  --endpoint-type azurefunction \
  --endpoint $(az functionapp function show \
    --resource-group rg-curso \
    --name func-procesador \
    --function-name ProcesarBlob \
    --query id -o tsv) \
  --included-event-types Microsoft.Storage.BlobCreated \
  --subject-begins-with /blobServices/default/containers/uploads/ \
  --subject-ends-with .jpg
```

**Function que reacciona:**
```csharp
[Function(nameof(ProcesarBlob))]
public async Task ProcesarBlob(
    [EventGridTrigger] EventGridEvent eventGridEvent,
    [BlobInput("{data.url}", Connection = "Storage")] BlobClient blob,
    [BlobOutput("thumbnails/{data.url}", Connection = "Storage")] Stream thumbnail)
{
    _logger.LogInformation("Procesando {url}", eventGridEvent.Subject);
    
    var data = eventGridEvent.Data.ToObjectFromJson<BlobCreatedEventData>();
    
    // Descargar blob original
    var originalStream = (await blob.DownloadStreamingAsync()).Value.Content;
    
    // Generar thumbnail
    using var image = await Image.LoadAsync(originalStream);
    image.Mutate(x => x.Resize(200, 200));
    await image.SaveAsJpegAsync(thumbnail);
    
    _logger.LogInformation("Thumbnail generado para {url}", data.Url);
}

public class BlobCreatedEventData
{
    public string Api { get; set; }
    public string ContentType { get; set; }
    public long ContentLength { get; set; }
    public string BlobType { get; set; }
    public string Url { get; set; }
    public string Sequencer { get; set; }
}
```

**Eventos disponibles:**

| Evento | Cuándo se dispara |
|---|---|
| `Microsoft.Storage.BlobCreated` | Nuevo blob (PUT, POST) |
| `Microsoft.Storage.BlobDeleted` | Blob borrado |
| `Microsoft.Storage.BlobRenamed` | Rename (solo ADLS Gen2) |
| `Microsoft.Storage.BlobTierChanged` | Cambio de tier |
| `Microsoft.Storage.AsyncOperationInitiated` | Async copy/restore |
| `Microsoft.Storage.DirectoryCreated` | Solo ADLS Gen2 |

**Filtros en suscripción** (recomendado):
- `subjectBeginsWith` = `/blobServices/default/containers/uploads/`
- `subjectEndsWith` = `.jpg` o `.png`
- `includedEventTypes` para filtrar tipos
- Advanced filters: por size, content-type, custom properties

**Por qué event-driven > polling:**
- ✅ Latencia: <1 segundo entre upload y procesamiento
- ✅ Coste: pagas solo cuando hay eventos
- ✅ Escalable: si suben 1000 blobs/s, Functions escalan
- ❌ Polling: revisión cada N min, latencia alta, coste constante

## Slide 32 — Network security: firewall + Private Endpoints + service endpoints

Por defecto Storage está expuesto a internet. Para producción seria, **bloquead todo y abrid lo justo**:

```bash
# 1. Firewall: bloquear todo el tráfico público
az storage account update --name stcurso --resource-group rg-curso \
  --default-action Deny

# 2. Whitelist IPs específicas (oficina, CI/CD)
az storage account network-rule add --account-name stcurso \
  --resource-group rg-curso \
  --ip-address 203.0.113.42

# 3. Permitir un rango
az storage account network-rule add --account-name stcurso \
  --resource-group rg-curso \
  --ip-address 203.0.113.0/24

# 4. Allow desde una VNet (Service Endpoint)
az network vnet subnet update \
  --resource-group rg-curso \
  --vnet-name vnet-curso --name subnet-app \
  --service-endpoints Microsoft.Storage

az storage account network-rule add --account-name stcurso \
  --resource-group rg-curso \
  --vnet-name vnet-curso --subnet subnet-app

# 5. Trusted Azure services (Function Apps, Key Vault, etc.)
az storage account update --name stcurso --resource-group rg-curso \
  --bypass AzureServices
```

**Service Endpoint vs Private Endpoint:**

```
┌────────────────────────┬──────────────────────────┬──────────────────────────┐
│                        │ Service Endpoint         │ Private Endpoint         │
├────────────────────────┼──────────────────────────┼──────────────────────────┤
│ IP del Storage         │ Pública (firewall whitel)│ Privada (en tu VNet)     │
│ Coste                  │ Gratis                   │ €0.01/h por endpoint     │
│ DNS                    │ DNS público              │ Private DNS zone         │
│ Tráfico cross-region   │ Sí, sale de Azure       │ Solo en mismo region/peer│
│ Compliance             │ Bueno                    │ Excelente (zero internet)│
│ Setup complejidad      │ Baja                     │ Media-alta               │
└────────────────────────┴──────────────────────────┴──────────────────────────┘
```

**Private Endpoint setup completo:**
```bash

  --resource-group rg-curso \

    -n stcurso -g rg-curso --query id -o tsv) \
  --group-id blob \
  --connection-name storage-connection

az network private-dns zone create \
  --resource-group rg-curso \
  --name privatelink.blob.core.windows.net

# Link a tu VNet
az network private-dns link vnet create \
  --resource-group rg-curso \
  --zone-name privatelink.blob.core.windows.net \
```

```
└─────────────────────────────────────────────────────────────────┘
```

**Configurar CMK con Key Vault:**
```bash
# 1. Crear Key Vault con purge protection (REQUERIDO para CMK)

  --resource-group rg-curso --location westeurope \
  --enable-purge-protection true \
  --enable-rbac-authorization true

# 2. Crear key

  --name storage-encryption-key \
  --kty RSA --size 2048

# 3. Habilitar System-Assigned MI en Storage
az storage account update --name stcurso \
  --resource-group rg-curso \
  --assign-identity

# 4. Dar permisos al MI sobre Key Vault

KV_ID=$(az keyvault show -n kv-curso --query id -o tsv)

az role assignment create \
  --role "Key Vault Crypto Service Encryption User" \
  --assignee $PRINCIPAL_ID --scope $KV_ID

# 5. Configurar Storage para usar la CMK
KEY_URI=$(az keyvault key show --vault-name kv-curso \
  --name storage-encryption-key --query key.kid -o tsv)

az storage account update --name stcurso --resource-group rg-curso \
  --encryption-key-source Microsoft.Keyvault \
  --encryption-key-vault https://kv-curso.vault.azure.net \
  --encryption-key-name storage-encryption-key

# 6. Double Encryption (solo al crear cuenta)

  --kind StorageV2 --sku Standard_LRS \
  --require-infrastructure-encryption true
```

## Slide 34 — Replication scenarios: cuándo usar cada SKU

Más allá de "LRS o GRS", hay 6 opciones de replicación:

```
┌─────────────┬──────────────────────────────────┬─────────────┬──────────┐
│   SKU       │ Replicación                      │  SLA        │ Coste vs │
│             │                                  │  Durab.     │  LRS     │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ LRS         │ 3 copias en mismo data center    │ 11 nines    │   1.0x   │
│ Local Red.  │ Same AZ                          │             │          │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ ZRS         │ 3 copias en 3 AZs distintas      │ 12 nines    │   1.25x  │
│ Zone Red.   │ Misma region                     │             │          │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ GRS         │ 6 copias: 3 LRS primary +        │ 16 nines    │   2.0x   │
│ Geo-Red.    │ 3 LRS secondary (other region)   │             │          │
│             │ Failover MANUAL                  │             │          │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ RA-GRS      │ GRS + read access secondary      │ 16 nines    │   2.5x   │
│ Read-Access │                                  │             │          │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ GZRS        │ 6 copias: ZRS primary +          │ 16 nines    │   2.5x   │
│ Geo-Zone    │ LRS secondary                    │             │          │
├─────────────┼──────────────────────────────────┼─────────────┼──────────┤
│ RA-GZRS     │ GZRS + read access secondary     │ 16 nines    │   3.0x   │
│             │ ⭐ Máxima disponibilidad        │             │          │
└─────────────┴──────────────────────────────────┴─────────────┴──────────┘
```

**Decisión:**

```
Dev / Test → LRS (más barato)
Prod no-crítico → ZRS (zone redundancy intra-region)
Prod crítico → GZRS (zone + geo redundancy)  
DR active-active → RA-GZRS (lecturas en 2 regiones)
Compliance estricto → CMK + GZRS o RA-GZRS
```

**Cambiar SKU:**
```bash
# Most upgrades possible online (LRS → GRS, ZRS → GZRS)
az storage account update --name stcurso --resource-group rg-curso \
  --sku Standard_GRS

# Algunos requieren recrear (LRS → ZRS, etc) — Microsoft puede asistir
```

**Failover manual a secondary region (GRS/GZRS):**
```bash
# Verificar si hay secundario disponible
az storage account show --name stcurso --resource-group rg-curso \
  --expand geoReplicationStats

# Failover (DESTRUCTIVO — no marcha atrás fácil)
az storage account failover --name stcurso --resource-group rg-curso

# Después del failover:
# - Cuenta es ahora LRS en la secondary region
# - Hay que reconfigurar replicación
# - RPO: ~15 minutos antes del failover típicamente
```

**Coste real ejemplo:**
```
1 TB Storage Account:
├── LRS:     €18/mes
├── ZRS:     €23/mes
├── GRS:     €36/mes
├── RA-GRS:  €45/mes
├── GZRS:    €45/mes
└── RA-GZRS: €54/mes
```

3x diferencia entre LRS y RA-GZRS — pero también 1000x diferencia en disponibilidad.

## Slide 35 — Blob Inventory: visibilidad de qué tienes

Cuando tienes millones de blobs, necesitas saber qué hay y cuánto cuesta:

```bash
# Habilitar Blob Inventory (genera reports diarios)
az storage account blob-inventory-policy create \
  --account-name stcurso \
  --resource-group rg-curso \
  --policy '{
    "enabled": true,
    "type": "Inventory",
    "rules": [{
      "name": "InventarioCompleto",
      "enabled": true,
      "destination": "inventory-reports",
      "definition": {
        "filters": {
          "blobTypes": ["blockBlob", "appendBlob", "pageBlob"],
          "includeBlobVersions": true,
          "includeSnapshots": true,
          "includeDeleted": true
        },
        "format": "Parquet",
        "schedule": "Daily",
        "objectType": "Blob",
        "schemaFields": [
          "Name", "Last-Modified", "Content-Length",
          "BlobType", "AccessTier", "AccessTierChangeTime",
          "Etag", "Metadata", "ContentMD5", "Tags"
        ]
      }
    }]
  }'
```

**Output:** archivos Parquet diarios en `inventory-reports/<date>/<inventoryRule>.parquet` con TODA la metadata de tus blobs.

**Análisis con Synapse o Databricks:**
```sql
-- ¿Cuánto storage por tier?
SELECT AccessTier, 
       COUNT(*) AS BlobCount,
       SUM(ContentLength) / 1e9 AS TotalGB
FROM blob_inventory
GROUP BY AccessTier;

-- ¿Top 100 blobs más grandes?
SELECT Name, ContentLength / 1e6 AS SizeMB, AccessTier
FROM blob_inventory
ORDER BY ContentLength DESC
LIMIT 100;

-- ¿Blobs no accedidos en último año (candidatos a Cold/Archive)?
SELECT Name, AccessTier, LastModified, ContentLength / 1e6 AS SizeMB
FROM blob_inventory
WHERE LastModified < CURRENT_DATE - INTERVAL '365 days'
  AND AccessTier = 'Hot'
ORDER BY ContentLength DESC;

-- ¿Cuánto cuesta cada container?
SELECT 
  SPLIT(Name, '/')[0] AS Container,
  SUM(CASE WHEN AccessTier = 'Hot' THEN ContentLength ELSE 0 END) * 0.018 AS HotCost,
  SUM(CASE WHEN AccessTier = 'Cool' THEN ContentLength ELSE 0 END) * 0.010 AS CoolCost,
  COUNT(*) AS Blobs
FROM blob_inventory
GROUP BY Container
ORDER BY HotCost DESC;
```

**Power BI dashboard típico:**
- Total storage by tier
- Cost trend over time  
- Top 20 containers by size
- Aging analysis (blobs por edad)
- Anomalies (sudden size growth)

**Sin inventory:** estás "ciego". Puedes ver el total de la cuenta, pero no qué archivos consumen qué.

**Coste:** $0.001 per million objects scanned. Para 10M blobs = $10/mes. Worth it.

## Slide 36 — Anti-patterns y trampas comunes

Los errores caros que veo repetir:

```
❌ ANTI-PATTERN 1: Account keys hardcoded en código
   → Con MI no necesitas connection strings
   ✅ DefaultAzureCredential + RBAC

❌ ANTI-PATTERN 2: Container público "para que funcione el upload"
   → Quien sea puede listar/descargar TODO
   ✅ Container privado + SAS para uploads específicos
   ✅ O App genera SAS y devuelve al cliente

❌ ANTI-PATTERN 3: Un solo container "data" con 50M blobs
   → Listings tardan minutos
   → Difícil de auditar
   ✅ Containers por customer / tenant / fecha
   ✅ Naming convention: 2026/04/customer-id/blob-name

❌ ANTI-PATTERN 4: Archivar a Archive sin pensar
   → "Archivar es barato" pero retrieval cuesta y tarda HORAS
   ✅ Cool/Cold para acceso ocasional
   ✅ Archive solo para "puede que nunca lo necesite"

❌ ANTI-PATTERN 5: Hot tier para todo "por si acaso"
   → 10x más caro que Cool/Cold para datos no accedidos
   ✅ Lifecycle automatic tiering desde día 1

❌ ANTI-PATTERN 6: Sin soft delete en producción
   → Junior dev borra container → game over
   ✅ Soft delete activo siempre

❌ ANTI-PATTERN 7: Blob de 5GB en una request
   → Timeout, memory pressure
   ✅ Streaming con chunks
   ✅ Parallel block upload (SDK lo hace solo)

❌ ANTI-PATTERN 8: Polling continuo de blob existence
   → Pagas por cada GET, ineficiente
   ✅ Event Grid trigger (event-driven)

❌ ANTI-PATTERN 9: Sin tags ni naming convention
   → 1 año después: "¿qué es este blob? ¿se puede borrar?"
   ✅ Metadata + Index Tags desde día 1

❌ ANTI-PATTERN 10: Storage account abierto a internet en prod
   → Brute force attacks contra account keys
   → Compliance fail
   ✅ Private Endpoints + firewall + MI
```

**El más común y caro:**
```
"Tenemos 50TB en Hot que no se accede. Estimado: €12K/año.
 Lifecycle policy: 30 días, Hot → Cool, → Cold después de 180 días.
 Coste post-policy: €1.5K/año.
 Ahorro: €10.5K/año por escribir 1 archivo JSON."
```

```
¿Necesitas SMB/NFS file share?
```

## Slide 40 — Cierre del submódulo
Azure Storage es la base de almacenamiento de casi todo en Azure. Cuatro servicios, un solo account, un solo sistema de seguridad. Blob para el 80% de lo que necesitéis, Queue para mensajes simples, Table para key-value barato, File para shares SMB.

Lo que más importa: Managed Identity en vez de keys, firewall cerrado por defecto, soft delete activado, y lifecycle management para no acumular costes innecesarios.

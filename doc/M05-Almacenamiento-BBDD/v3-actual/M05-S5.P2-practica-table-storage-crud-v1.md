## Slide 2 — Qué vais a construir

Una API .NET 8 que persiste productos en **Azure Table Storage** usando connection string. Es la opción más simple y barata para empezar con persistencia en Azure.

**El recorrido:**

```
1. Crear Storage Account (gratis dentro del free tier)
2. Crear proyecto .NET 8 minimal API
3. Implementar CRUD con TableClient
4. Probar en local con Azurite
5. Probar contra el Storage real con connection string
6. Comparar Table Storage vs Cosmos DB
7. Limpiar recursos
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ Cosmos DB (eso es la práctica principal M05-S5.P)
- ❌ Managed Identity (también principal — más complejo)
- ❌ RBAC ni roles (M06)
- ❌ Web App ni Functions desplegadas (M02 / M03)
- ❌ Particiones avanzadas (a nivel intro)

**Por qué Table Storage:**

- ✅ Más barato que Cosmos (~10x menos)
- ✅ Modelo NoSQL key-value simple
- ✅ Mismo Storage Account que ya usáis para Functions
- ✅ Perfecto para configs, logs, datos sencillos
- ✅ API mínima, fácil de entender

**Tiempo estimado:** 45-60 minutos.

**Coste real:** **0€** (Storage Account dentro del free tier).

**Conceptos previos a tener frescos:**

```
Table Storage:
- BBDD NoSQL key-value en Azure Storage
- Cada fila se llama "Entity"
- Identificada por dos claves:
  ├── PartitionKey: agrupa entities (clave primaria parcial)
  └── RowKey: identifica entity dentro de la partition (clave única en partition)
- (PartitionKey + RowKey) = clave única total

Por qué dos claves:
- PartitionKey define cómo se distribuyen físicamente los datos
- Queries con misma PartitionKey son MUY rápidas
- Queries cross-partition son más lentas
```

**Comparativa visual:**

```
SQL clásico:
┌────┬────────┬───────┐
│ id │ nombre │ stock │
├────┼────────┼───────┤
│  1 │ Laptop │     5 │
│  2 │ Mouse  │    20 │
└────┴────────┴───────┘

Table Storage:
┌──────────────┬─────────┬────────┬───────┐
│ PartitionKey │ RowKey  │ nombre │ stock │
├──────────────┼─────────┼────────┼───────┤
│ electronica  │ laptop1 │ Laptop │     5 │
│ accesorios   │ mouse1  │ Mouse  │    20 │
└──────────────┴─────────┴────────┴───────┘
```

**Coste estimado:**

```
Storage Account standard LRS:
- Almacenamiento: ~€0.045/GB/mes (los primeros GB son ~gratis)
- Operaciones: ~€0.00036 por 10.000 operaciones
- Esta práctica: <€0.001 (despreciable)
```

## Slide 4 — Paso 1: Crear el Storage Account

```bash
RG_NAME="rg-curso-tables-<tu-nombre>"
LOCATION="westeurope"
STORAGE_NAME="stcurso<tu-nombre>$(date +%s | tail -c 5)"

# Crear RG
az group create --name $RG_NAME --location $LOCATION

# Crear Storage Account (Standard LRS, lo más barato)
az storage account create \
  --name $STORAGE_NAME \
  --resource-group $RG_NAME \
  --location $LOCATION \
  --sku Standard_LRS \
  --kind StorageV2

# Obtener la connection string
CONN_STRING=$(az storage account show-connection-string \
  --name $STORAGE_NAME \
  --resource-group $RG_NAME \
  --query connectionString -o tsv)

echo "Connection String:"
echo "$CONN_STRING"

# Guardadla en una variable de entorno temporalmente
export AZURE_STORAGE_CONNECTION_STRING="$CONN_STRING"
```

**Anatomía de la connection string:**

```
DefaultEndpointsProtocol=https;
AccountName=stcursopedro12345;
AccountKey=<base64-key-larguísima>;
EndpointSuffix=core.windows.net
```

**Importante: la connection string contiene la AccountKey**

```
La AccountKey:
- Da acceso TOTAL al Storage Account
- Permite leer/escribir/borrar TODO
- NO debéis subirla a git ni compartirla
- En producción: Managed Identity (cubierto en M05-S5.P principal)
- Para esta práctica: la usamos por simplicidad pedagógica
```

**Verificar el storage:**

```bash

  --resource-group $RG_NAME \
  --query "{Name:name, Sku:sku.name, Kind:kind, ProvisioningState:provisioningState}" \
  -o table
```

```bash
  --table-name productos \

    precio=89.90 \
    stock=30
```

**Listar lo insertado:**

```bash
az storage entity query \
  --table-name productos \
  --connection-string "$CONN_STRING" \
  --output table
```

**Output esperado:**

```

------------  -----------  -------------------  -------  -----
electronica   laptop001    Laptop Dell          1299.00      5
electronica   monitor001   Monitor 27 pulgadas   349.00     12
accesorios    teclado001   Teclado mecánico       89.90     30
```

**Decisión de PartitionKey:**

Aquí usamos "categoría" (electronica, accesorios) como PartitionKey. **Por qué:**

- ✅ Queries por categoría son rápidas (misma partition)
- ✅ Distribución razonable si hay muchas categorías
- ⚠️ Mala si una sola categoría concentra el 90% (hot partition)

## Slide 7 — Paso 4: Modelo y servicio

Definimos un modelo `Producto` que herede de `ITableEntity`:

```bash
cat > Producto.cs << 'EOF'
using Azure;
using Azure.Data.Tables;

namespace MiTablesApi;

public class Producto : ITableEntity
{
    // Campos obligatorios de ITableEntity
    public string PartitionKey { get; set; } = string.Empty;
    public string RowKey { get; set; } = string.Empty;
    public DateTimeOffset? Timestamp { get; set; }
    public ETag ETag { get; set; }

    // Campos del dominio
    public string Nombre { get; set; } = string.Empty;
    public double Precio { get; set; }
    public int Stock { get; set; }
}
EOF
```

**Por qué `double` en vez de `decimal`:**

```
Table Storage NO soporta decimal nativamente.
Soporta: int, long, double, bool, string, DateTime, byte[], Guid

Para precios en producción real:
- Usar long (cents): precio en céntimos en lugar de euros con decimales
- O guardar como string y parsear al leer

Para esta práctica: double es suficiente (1299.00 funciona).
```

**Servicio que encapsula el acceso a la tabla:**

```bash
cat > ProductosService.cs << 'EOF'
using Azure.Data.Tables;

namespace MiTablesApi;

public interface IProductosService
{
    Task<List<Producto>> GetAllAsync();
    Task<List<Producto>> GetByCategoriaAsync(string categoria);
    Task<Producto?> GetByIdAsync(string categoria, string id);
    Task<Producto> CreateAsync(Producto producto);
    Task<bool> UpdateAsync(Producto producto);
    Task<bool> DeleteAsync(string categoria, string id);
}

public class ProductosService : IProductosService
{
    private readonly TableClient _table;

    public ProductosService(IConfiguration config)
    {
        var connectionString = config["Storage:ConnectionString"]
            ?? throw new InvalidOperationException("Storage:ConnectionString no configurada");
        
        _table = new TableClient(connectionString, "productos");
    }

    public async Task<List<Producto>> GetAllAsync()
    {
        var resultado = new List<Producto>();
        await foreach (var entity in _table.QueryAsync<Producto>())
        {
            resultado.Add(entity);
        }
        return resultado;
    }

    public async Task<List<Producto>> GetByCategoriaAsync(string categoria)
    {
        var resultado = new List<Producto>();
        await foreach (var entity in _table.QueryAsync<Producto>(
            filter: $"PartitionKey eq '{categoria}'"))
        {
            resultado.Add(entity);
        }
        return resultado;
    }

    public async Task<Producto?> GetByIdAsync(string categoria, string id)
    {
        try
        {
            var response = await _table.GetEntityAsync<Producto>(categoria, id);
            return response.Value;
        }
        catch (Azure.RequestFailedException ex) when (ex.Status == 404)
        {
            return null;
        }
    }

    public async Task<Producto> CreateAsync(Producto producto)
    {
        await _table.AddEntityAsync(producto);
        return producto;
    }

    public async Task<bool> UpdateAsync(Producto producto)
    {
        try
        {
            await _table.UpdateEntityAsync(producto, ETag.All);
            return true;
        }
        catch (Azure.RequestFailedException ex) when (ex.Status == 404)
        {
            return false;
        }
    }

    public async Task<bool> DeleteAsync(string categoria, string id)
    {
        try
        {
            await _table.DeleteEntityAsync(categoria, id);
            return true;
        }
        catch (Azure.RequestFailedException ex) when (ex.Status == 404)
        {
            return false;
        }
    }
}
EOF
```

## Slide 8 — Paso 5: API endpoints en Program.cs

Sustituid el contenido de `Program.cs`:

```bash
cat > Program.cs << 'EOF'
using MiTablesApi;

var builder = WebApplication.CreateBuilder(args);

// DI
builder.Services.AddSingleton<IProductosService, ProductosService>();

var app = builder.Build();

// GET /productos — listar todos
app.MapGet("/productos", async (IProductosService svc) =>
{
    var productos = await svc.GetAllAsync();
    return Results.Ok(new { total = productos.Count, productos });
});

// GET /productos/categoria/{categoria} — listar por categoría
app.MapGet("/productos/categoria/{categoria}", async (string categoria, IProductosService svc) =>
{
    var productos = await svc.GetByCategoriaAsync(categoria);
    return Results.Ok(new { categoria, total = productos.Count, productos });
});

// GET /productos/{categoria}/{id} — obtener uno
app.MapGet("/productos/{categoria}/{id}", async (string categoria, string id, IProductosService svc) =>
{
    var producto = await svc.GetByIdAsync(categoria, id);
    return producto is null
        ? Results.NotFound(new { error = $"Producto {id} no encontrado en {categoria}" })
        : Results.Ok(producto);
});

// POST /productos — crear nuevo
app.MapPost("/productos", async (Producto producto, IProductosService svc) =>
{
    if (string.IsNullOrEmpty(producto.PartitionKey) || string.IsNullOrEmpty(producto.RowKey))
    {
        return Results.BadRequest(new { error = "PartitionKey y RowKey son obligatorios" });
    }
    
    try
    {
        var creado = await svc.CreateAsync(producto);
        return Results.Created($"/productos/{creado.PartitionKey}/{creado.RowKey}", creado);
    }
    catch (Azure.RequestFailedException ex) when (ex.Status == 409)
    {
        return Results.Conflict(new { error = "Ya existe un producto con esa PartitionKey + RowKey" });
    }
});

// PUT /productos/{categoria}/{id} — actualizar
app.MapPut("/productos/{categoria}/{id}", async (string categoria, string id, Producto producto, IProductosService svc) =>
{
    producto.PartitionKey = categoria;
    producto.RowKey = id;
    
    var actualizado = await svc.UpdateAsync(producto);
    return actualizado
        ? Results.Ok(producto)
        : Results.NotFound(new { error = $"Producto {id} no encontrado" });
});

// DELETE /productos/{categoria}/{id} — borrar
app.MapDelete("/productos/{categoria}/{id}", async (string categoria, string id, IProductosService svc) =>
{
    var borrado = await svc.DeleteAsync(categoria, id);
    return borrado
        ? Results.NoContent()
        : Results.NotFound(new { error = $"Producto {id} no encontrado" });
});

app.Run();
EOF
```

**Endpoints resultantes:**

```
GET    /productos                           - listar todos
GET    /productos/categoria/{categoria}     - filtrar por partition
GET    /productos/{categoria}/{id}          - obtener uno
POST   /productos                           - crear
PUT    /productos/{categoria}/{id}          - actualizar
DELETE /productos/{categoria}/{id}          - borrar
```

**Verificar build:**

```bash
dotnet build
```

Esperado: `Build succeeded`. Si hay errores, revisad imports y namespace.

```bash
# Filtrar con OData query
az storage entity query \
  --table-name productos \
  --connection-string "$CONN_STRING" \
  --filter "PartitionKey eq 'electronica' and stock lt 10" \
  --output table

  --table-name productos \

  --output table
```

**Sintaxis de OData filter:**

```
eq    igual                  PartitionKey eq 'electronica'
ne    distinto               stock ne 0
lt    menor                  precio lt 100
le    menor o igual          precio le 500
gt    mayor                  precio gt 1000
ge    mayor o igual          stock ge 5

Combinaciones:
and   PartitionKey eq 'electronica' and stock lt 10
or    precio lt 100 or stock gt 50
not   not (stock eq 0)
```

## Slide 12 — Comparativa: Table Storage vs Cosmos DB

Ambos son NoSQL. ¿Cuándo usar cada uno?

| Aspecto | Table Storage | **Cosmos DB (Table API)** |
|---|---|---|
| **Coste mínimo** | ~€0.05/mes | **~€20/mes (provisioned)** o pago por request |
| **Latencia** | <100 ms | **<10 ms** |
| **SLA** | 99.9% | **99.999%** |
| **Replicación geo** | Configurable (LRS/GRS) | **Multi-región automática** |
| **Throughput máximo** | 20.000 ops/segundo | **Millones de ops/segundo** |
| **Auto-indexing** | Solo PartitionKey + RowKey | **Todas las propiedades indexadas** |
| **Multi-master writes** | ❌ | **✅** |
| **API compatibility** | Nativa (Storage) | **Misma + APIs de SQL, MongoDB, Cassandra, Gremlin** |

**Cuándo SÍ Table Storage:**

```
✅ Datos sencillos, queries por PartitionKey + RowKey
✅ Volumen bajo o moderado (<10K ops/seg)
✅ Coste es PRIORITARIO (10x más barato que Cosmos)
✅ No necesitáis multi-región
✅ Queries simples (sin agregaciones complejas)
✅ Logging, configs, metadata, cache distribuido
```

**Cuándo SÍ Cosmos DB:**

```
✅ Aplicación global con usuarios en múltiples regiones
✅ SLA crítico (99.999%)
✅ Throughput muy alto (millones ops/seg)
✅ Queries complejas con múltiples filtros
✅ Modelo de datos complejo (jerárquico, JSON anidado)
✅ Necesitáis Change Feed (M03-S3.5)
```

**Caso real típico:**

```
App e-commerce mediano:

✅ Cosmos DB: catalog, pedidos (queries complejas, alta concurrencia)
✅ Table Storage: configs, logs, audit trail (datos simples, baratos)

→ Combinación ahorra dinero y mantiene buena UX
```

**Migración Table Storage → Cosmos:**

```
Cosmos DB Table API es 100% compatible con Table Storage:
- Mismo SDK
- Mismas queries
- Mismo modelo PartitionKey + RowKey
- Solo cambia la connection string

Tabla Storage:
"DefaultEndpointsProtocol=https;AccountName=...;AccountKey=..."

Cosmos Table API:
"DefaultEndpointsProtocol=https;AccountName=cosmos-account;AccountKey=...;TableEndpoint=https://...;"

→ Migración es trivial cuando la app crece
```

## Slide 14 — Patrones útiles en Table Storage

Estos patrones os servirán cuando queráis llevar esto a producción:

**Patrón 1: PartitionKey por fecha**

```
Útil para series temporales (logs, telemetría, eventos)

PartitionKey: 2026-04-28
RowKey: timestamp-uuid

Ventajas:
- Queries por día son rápidas
- Easy de eliminar logs viejos (borrar particion entera)
- Particiones con tamaño manejable (1 día de datos)
```

**Patrón 2: PartitionKey por tenant**

```
Útil para SaaS multi-tenant

PartitionKey: tenant-acme
RowKey: 2026-04-28-pedido-001

Ventajas:
- Aislamiento por tenant
- Queries por tenant son rápidas
- Compliance: borrar datos de un tenant es trivial
```

**Patrón 3: RowKey con timestamp invertido**

```
Útil cuando queréis los más recientes primero

RowKey: $((9999999999 - $(date +%s)))-uuid

Por qué:
- Storage Table devuelve por orden alfabético de RowKey
- Timestamp invertido: los más recientes tienen valores menores
- Query "primeros 10" = "10 más recientes"
```

**Patrón 4: Soft delete con flag**

```csharp
// En lugar de borrar, marcar como deleted
producto.Eliminado = true;
producto.FechaEliminacion = DateTime.UtcNow;
await _table.UpdateEntityAsync(producto, ETag.All);

// Filtrar al leer
var activos = _table.QueryAsync<Producto>(
    filter: $"PartitionKey eq '{cat}' and Eliminado eq false");
```

**Patrón 5: Concurrency control con ETag**

```csharp
// Leer con etag
var response = await _table.GetEntityAsync<Producto>(cat, id);
var etag = response.Value.ETag;

// Actualizar solo si nadie modificó
try
{
    await _table.UpdateEntityAsync(producto, etag);
}
catch (Azure.RequestFailedException ex) when (ex.Status == 412)
{
    // Otro proceso modificó la entity → conflicto
    return BadRequest("La entity fue modificada por otro usuario");
}
```

**Patrón 6: Batch operations (transacciones)**

```csharp
// Hasta 100 operaciones en una sola request (atómica)
var batch = new List<TableTransactionAction>
{
    new TableTransactionAction(TableTransactionActionType.Add, p1),
    new TableTransactionAction(TableTransactionActionType.Add, p2),
    new TableTransactionAction(TableTransactionActionType.UpdateMerge, p3),
};

// IMPORTANTE: todas deben tener LA MISMA PartitionKey
await _table.SubmitTransactionAsync(batch);
```

## Slide 15 — Limitaciones de Table Storage

Conviene saber qué NO podéis hacer (para no estrellaros en producción):

**Límite 1: Solo 2 índices (PartitionKey + RowKey)**

```
Si necesitáis buscar por otro campo:
- Hacer scan completo (LENTO si hay muchos datos)
- O duplicar datos con otra PartitionKey
- O migrar a Cosmos DB

Ejemplo problema:
"Buscar todos los productos con precio < 50€" en una tabla de 1M productos
→ Scan completo, MUY lento
```

**Límite 2: Sin joins ni queries cross-table**

```
SQL:
  SELECT p.nombre, c.nombre as categoria
  FROM productos p
  JOIN categorias c ON p.categoriaId = c.id

Table Storage:
  ❌ No hay JOIN
  ✅ Solución: desnormalizar (guardar nombre de categoría en cada producto)
```

**Límite 3: Tipos de dato limitados**

```
Soportados: int, long, double, bool, string, DateTime, byte[], Guid
NO soportados: decimal, lists, nested objects, binary >64KB

Para almacenar JSON complejo:
- Serializar a string al guardar
- Deserializar al leer
- O migrar a Cosmos DB (que sí soporta JSON nativo)
```

**Límite 4: Tamaño de entity**

```
- Entity max: 1 MB (incluyendo todas las propiedades)
- Property max: 64 KB (cada una)
- Properties por entity: 252 + 3 sistema (PK, RK, Timestamp)

Si necesitáis blobs grandes:
→ Guardar referencia (URL) en Table, blob en Blob Storage
```

**Límite 5: Sin transacciones cross-partition**

```
✅ OK: 100 operations en MISMA PartitionKey, atómicas
❌ NO: 2 operations en DIFERENTES PartitionKeys, atómicas

Si necesitáis transacciones distribuidas:
→ Cosmos DB con stored procedures (mismo partition)
→ O patrón Saga (eventually consistent)
→ O migrar a Azure SQL (ACID completo)
```

**Cuándo migrar a Cosmos:**

```
Indicadores de que Table Storage se queda corto:
- Necesitáis queries por más campos que PartitionKey
- Latencia <10ms importante (Tables es 50-200ms)
- Multi-región necesario
- Throughput >10K ops/seg sostenido
- Modelo de datos complejo con JSON anidado

Migración: cambiar connection string + algunos ajustes
(Cosmos Table API es compatible 1:1)
```

## Slide 17 — Troubleshooting

Los 5 errores más típicos y cómo resolverlos:

**1. "404 The specified resource does not exist"**

```
Causa común: la tabla no existe o nombre mal escrito
Verificar:
  az storage table list \
    --connection-string "$CONN_STRING" \
    -o table

Fix:
- Crear la tabla: az storage table create --name productos --connection-string ...
- Verificar nombres case-sensitive en código vs storage
```

**2. "The credentials provided for the storage account were invalid"**

```
Causa: connection string corrupta o key rotada
Diagnóstico:
  echo "$CONN_STRING" | grep AccountKey

Fix:
- Regenerar la key:
  az storage account keys renew --name $STORAGE_NAME -g $RG_NAME --key key1
  
- Recargar connection string:
  CONN_STRING=$(az storage account show-connection-string \
    --name $STORAGE_NAME -g $RG_NAME --query connectionString -o tsv)
```

**3. "The specified entity already exists" al crear**

```
Causa: PartitionKey + RowKey duplicados
Síntoma: 409 Conflict al hacer POST

Recordad:
- (PartitionKey, RowKey) = clave única total
- 2 entities con mismas PK+RK = error

Fix:
- Cambiar RowKey
- O usar UpsertEntity en lugar de AddEntity (sobrescribe si existe)
```

**4. "Error decoding 'producto'" al hacer POST**

```
Causa: el JSON del body no coincide con el modelo C#
Verificar que enviáis:
  - partitionKey (camelCase)
  - rowKey (camelCase)
  - nombre, precio, stock

Issue común: enviar PascalCase ("PartitionKey") cuando ASP.NET espera camelCase
Fix: ya está manejado por defecto en ASP.NET Core
```

**5. "Connection string contains invalid character"**

```
Causa: escape de caracteres en bash al usar variables
Síntoma: la app no arranca

Fix:
- Usar comillas dobles al exportar: export VAR="value"
- Verificar que '=' en la key no rompe parsing
- En producción: connection string en App Settings de Azure (no shell)
```

**Comando útil: ver entities actuales en producción**

```bash
az storage entity query \
  --table-name productos \
  --connection-string "$CONN_STRING" \
  --output json | jq '.[].PartitionKey + "/" + .[].RowKey'
```

## Slide 18 — Buenas prácticas para producción

Si vais a llevar Table Storage a producción de verdad, considerad esto:

**1. NO usar connection string con AccountKey en código:**

```
❌ Connection string con key en App Settings → cualquiera con acceso a config la lee

✅ Managed Identity (cubierto en M05-S5.P principal):
   - Vuestra app tiene una identidad Azure
   - Acceso al Storage vía RBAC
   - Sin secretos en el código ni config
```

**2. Replicación adecuada:**

```
LRS (Local-Redundant Storage):
- 3 copias en una zona
- Más barato (~€0.045/GB)
- ❌ Si la zona se cae → sin acceso

GRS (Geo-Redundant Storage):
- 6 copias en 2 regiones
- Más caro (~€0.062/GB)
- ✅ Tolera caída completa de una región

ZRS (Zone-Redundant Storage):
- 3 copias en 3 zonas distintas
- ~€0.057/GB
- ✅ Tolera caída de una zona

Recomendación:
- Dev / staging: LRS
- Producción: ZRS o GRS según RPO/RTO requirement
```

**3. Backups y soft delete:**

```bash
# Habilitar soft delete (recovery 7-365 días)
az storage account update \
  --name $STORAGE_NAME \
  --resource-group $RG_NAME \
  --enable-table-delete-retention true \
  --table-delete-retention-days 7

# Si alguien borra una tabla por error → recovery posible
```

**4. Throttling y retries:**

```csharp
// Configurar policy de retries en el SDK
var options = new TableClientOptions

    {
        MaxRetries = 5,
        Mode = Azure.Core.RetryMode.Exponential,
        Delay = TimeSpan.FromSeconds(1),
        MaxDelay = TimeSpan.FromSeconds(30)
    }
};

var client = new TableClient(connStr, "productos", options);

// El SDK reintenta automáticamente:
// - 503 Server Busy
// - 500 Internal Server Error
// - Network timeouts
```

**5. Observability:**

```bash
# Habilitar diagnostic settings
az monitor diagnostic-settings create \
  --name tables-diagnostics \
  --resource $(az storage account show -n $STORAGE_NAME -g $RG_NAME --query id -o tsv)/tableServices/default \
  --workspace <log-analytics-workspace-id> \

    {"category":"StorageRead", "enabled":true},
```

## Slide 2 — Qué vais a hacer
Vais a configurar una Web App que se conecta a Cosmos DB usando Managed Identity en vez de connection string con key. El flujo:

1. Crear una Cosmos DB con una base de datos y un contenedor
2. Crear una Web App con Managed Identity habilitada
3. Asignar permisos de la identidad en Cosmos DB (RBAC)
4. Desplegar una app que usa DefaultAzureCredential (sin keys)
5. Verificar que funciona: la app lee y escribe en Cosmos sin ningún secreto

**Tiempo estimado:** 20-25 minutos
**Entregable:** App desplegada conectándose a Cosmos DB sin connection string con password

## Slide 8 — Paso 5: Crear la app

```bash
cd curso-azure/modulo-05
dotnet new web -n cosmos-mi-app
cd cosmos-mi-app
dotnet add package Microsoft.Azure.Cosmos
dotnet add package Azure.Identity
```

`Program.cs`:
```csharp
using Azure.Identity;
using Microsoft.Azure.Cosmos;

var builder = WebApplication.CreateBuilder(args);

// Cosmos DB con Managed Identity (sin key!)
var endpoint = builder.Configuration["CosmosEndpoint"]
    ?? "https://localhost:8081"; // Fallback para desarrollo local

builder.Services.AddSingleton(new CosmosClient(endpoint, new DefaultAzureCredential(),
    new CosmosClientOptions { SerializerOptions = new() { PropertyNamingPolicy = CosmosPropertyNamingPolicy.CamelCase } }));

var app = builder.Build();

app.MapGet("/", () => Results.Json(new {
    mensaje = "Cosmos DB con Managed Identity — sin passwords",
    endpoint
}));

app.MapGet("/productos", async (CosmosClient cosmos) =>
{
    var container = cosmos.GetContainer("tienda", "productos");
    var query = container.GetItemQueryIterator<dynamic>("SELECT * FROM c");
    var productos = new List<dynamic>();
    while (query.HasMoreResults)
        productos.AddRange(await query.ReadNextAsync());
    return Results.Json(productos);
});

app.MapPost("/productos", async (CosmosClient cosmos, HttpRequest req) =>
{
    var producto = await req.ReadFromJsonAsync<Dictionary<string, object>>();
    producto!["id"] = Guid.NewGuid().ToString();
    var container = cosmos.GetContainer("tienda", "productos");
    await container.CreateItemAsync(producto, new PartitionKey(producto["categoria"].ToString()));
    return Results.Created($"/productos/{producto["id"]}", producto);
});

app.MapGet("/health", () => Results.Ok(new { status = "healthy" }));

app.Run();
```

## Slide 11 — Partition key strategy: la decisión que define el rendimiento

Habéis usado `/categoria` como partition key. Es OK para esta práctica, pero **es la decisión más crítica en Cosmos** y conviene entender por qué.

**Reglas para elegir partition key:**

```
✅ BUENA partition key:
- Alta cardinalidad (muchos valores únicos)
- Distribución uniforme (no hot partitions)
- Aparece en la mayoría de queries (filtros + reads)
- Estable (no cambia tras crear el documento)

❌ MALA partition key:
- Baja cardinalidad (ej: /tipo con solo "user" y "admin")
- Distribución sesgada (ej: 90% pedidos van a 1 cliente)
- No aparece en queries comunes (cross-partition queries son caras)
- Cambia frecuentemente (no se puede modificar tras crear)
```

**Comparativa para vuestra app de productos:**

| Partition Key | Pros | Contras |
|---|---|---|
| `/categoria` (actual) | Queries por categoría son rápidas | Solo ~10-20 categorías → hot partitions si una es popular |
| `/id` (cada producto su partición) | Distribución perfecta | Cada query "listar todos" es cross-partition (cara) |
| `/proveedorId` | Distribución según proveedores | Solo útil si filtráis mucho por proveedor |
| `/categoria/proveedorId` (sintético) | Mejor distribución | Más complejo; requiere construir el campo |

**Verificar distribución de vuestras particiones:**

```bash
# Ver throughput por partición física
az cosmosdb sql container show \
  --account-name cosmos-curso-<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --database-name tienda \
  --name productos \
  --query "resource.statistics[].partitionKeyRangeStatistics[].sizeInKB" -o table

# Si veis una partición >>> que las otras → hot partition problem
```

**Query patterns y su coste:**

```sql
-- ✅ BARATO (~3 RU): query con partition key + filtro
SELECT * FROM c WHERE c.categoria = 'electronica' AND c.precio < 100

-- ⚠️ MEDIO (~10-30 RU): query sin partition key (cross-partition fan-out)
SELECT * FROM c WHERE c.precio < 100

-- ❌ CARO (>100 RU): query con ORDER BY sin partition key
SELECT * FROM c ORDER BY c.fechaCreacion DESC

-- ❌ MUY CARO: agregaciones cross-partition
SELECT VALUE COUNT(1) FROM c WHERE c.precio > 50
```

**Patrón que escala bien para producción** (no esta práctica, pero importante saberlo):

```
Si vuestro patrón de acceso es "siempre por cliente":
  → /clienteId como partition key

Si vuestro patrón es "siempre por fecha + tipo":
  → /yyyy-MM/tipo como partition key sintética
  
Si vuestro patrón es muy variado (analytics):
  → Considerar Synapse Link o exportar a Data Lake
```

## Slide 12 — Monitoring de RU consumption: lo que NO se ve mata

Cosmos cobra por RUs (Request Units). Si no monitorizáis consumo, la primera factura sorprende.

**1. Ver RU consumidas por query** (durante desarrollo):

```csharp
// En vuestro código .NET - inspeccionar response headers
var response = await container.ReadItemAsync<Producto>(id, new PartitionKey(categoria));
var ruCharge = response.RequestCharge;
_logger.LogInformation("Read costó {RU} RUs", ruCharge);

// Para queries
var query = container.GetItemQueryIterator<Producto>(
    "SELECT * FROM c WHERE c.precio < 100");
double totalRU = 0;
while (query.HasMoreResults)
{
    var page = await query.ReadNextAsync();
    totalRU += page.RequestCharge;
}
_logger.LogInformation("Query total: {RU} RUs", totalRU);
```

**2. Métricas en Azure Portal:**

```
Cosmos Account → Metrics → Total Request Units
- Filtrar por: DatabaseName, CollectionName
- Granularidad: 1 minuto
- Top consumers: ver qué queries pegan más
```

**3. KQL queries útiles** (si tenéis App Insights conectado):

```kusto
// Top 10 queries más caras de la última hora
dependencies
| where timestamp > ago(1h)
| where target == "cosmos-curso-..."
| where customDimensions.requestCharge != ""
| extend RU = todouble(customDimensions.requestCharge)
| top 10 by RU desc
| project timestamp, name, data, RU, duration

// Total RU consumidas en el día
dependencies
| where timestamp > ago(24h)
| where target contains "cosmos-curso"
| extend RU = todouble(customDimensions.requestCharge)
| summarize TotalRU = sum(RU) by bin(timestamp, 1h)
| render timechart
```

**4. Configurar alertas para RU consumption alta:**

```bash
az monitor metrics alert create \
  --name alert-cosmos-ru-high \
  --resource-group rg-curso-azure-<tu-nombre> \
  --scopes $(az cosmosdb show -n cosmos-curso-<tu-nombre> -g rg-curso-azure-<tu-nombre> --query id -o tsv) \
  --condition "avg NormalizedRUConsumption > 80" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --description "Cosmos RU >80% sostenido"
```

**5. Trampa común con Serverless:**

```
Serverless: pay per RU (sin throttling artificial)
- Pro: nunca veréis 429 (Throttled)
- Con: si un bug genera queries en loop, la factura SÍ explota

Provisioned: throughput fijo (ej: 400 RU/s)
- Pro: coste predecible
- Con: si superáis: 429 (la app debe retry con backoff)

Para producción: Provisioned con autoscale es lo más balanceado.
```

**6. Optimizaciones típicas:**

```csharp
// ❌ MAL: traer todo y filtrar en cliente
var todos = await container.GetItemQueryIterator<Producto>("SELECT * FROM c").ReadNextAsync();
var baratos = todos.Where(p => p.Precio < 100);  // Filtra después de traer

// ✅ BIEN: filtrar en el servidor
var baratos = await container.GetItemQueryIterator<Producto>(
    "SELECT * FROM c WHERE c.precio < 100").ReadNextAsync();

// ✅ MEJOR: además, partition key en la query
var baratosCategoria = await container.GetItemQueryIterator<Producto>(
    "SELECT * FROM c WHERE c.categoria = 'electronica' AND c.precio < 100",
    requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey("electronica") }
).ReadNextAsync();
```

## Slide 20 — Troubleshooting común durante la práctica

Errores que SIEMPRE aparecen — aquí los fixes:

```
ERROR 1: "Forbidden" cuando la app intenta leer Cosmos DB
─────────────────────────────────────────────────────
Causas posibles:
├── 1. MI no asignada al App Service
│      Fix: az webapp identity assign -n <app> -g <rg>
├── 2. Role assignment no propagado (5-10 min de delay)
│      Fix: esperar 10 min y reintentar
├── 3. Role asignado pero scope incorrecto
│      Fix: scope debería ser /dbs/<db>/colls/<container>, no solo cuenta
└── 4. Endpoint mal configurado en App Settings
       Fix: debe ser https://<account>.documents.azure.com (sin slash al final)

ERROR 2: "DefaultAzureCredential failed to retrieve a token"
──────────────────────────────────────────────────────────
Causas:
├── 1. App corre en local sin az login
│      Fix: az login en terminal
├── 2. App corre como Container con identity propia
│      Fix: configurar AZURE_CLIENT_ID env var
└── 3. MI deshabilitada por error
       Fix: az webapp identity show -n <app> -g <rg>

ERROR 3: "401 Unauthorized" en Key Vault
────────────────────────────────────────
Causas:
├── 1. Key Vault con Access Policies (legacy) en vez de RBAC
│      Fix: az keyvault update --enable-rbac-authorization true
├── 2. Role missing: "Key Vault Secrets User"
│      Fix: az role assignment create --role ...
└── 3. KV Reference mal configurada
       Fix: @Microsoft.KeyVault(VaultName=<vault>;SecretName=<name>)

ERROR 4: Cosmos request charge muy alto (1000+ RU per query)
──────────────────────────────────────────────────────────────
Causas:
├── 1. Cross-partition query
│      Fix: include partition key in query WHERE
├── 2. SELECT * en colecciones grandes
│      Fix: project specific fields needed
└── 3. Indexing incluye TODO
       Fix: Custom indexing policy

ERROR 5: SQL connection timeout
────────────────────────────────
Causas:
├── 1. Firewall block tu IP
│      Fix: az sql server firewall-rule create
├── 2. Connection string usa Authentication=SqlPassword pero MI configured
│      Fix: cambiar a Active Directory Default
└── 3. Connection pool exhausted
       Fix: increase Max Pool Size o reusar conexiones
```

## Slide 21 — Reto 4: Implementar soft-delete recovery

Probad la recuperación ante un disaster simulado:

**Setup:**
```bash
# Habilitar soft-delete en blob storage de la práctica
az storage account blob-service-properties update \
  --account-name stcurso<tu-nombre> \
  --resource-group rg-curso-azure-<tu-nombre> \
  --enable-delete-retention true \
  --delete-retention-days 7 \
  --enable-container-delete-retention true \
  --container-delete-retention-days 7
```

**Disaster simulation:**
```bash
# 1. Crear container y subir blobs de prueba
az storage container create --name productos-imagenes \
  --account-name stcurso<tu-nombre> --auth-mode login

for i in 1 2 3; do
  echo "imagen $i" > img$i.txt
  az storage blob upload --container-name productos-imagenes \
    --file img$i.txt --name "img$i.txt" \
    --account-name stcurso<tu-nombre> --auth-mode login
done

# 2. "OOPS" - Dev junior borra el container completo
az storage container delete --name productos-imagenes \
  --account-name stcurso<tu-nombre> --auth-mode login

# 3. Verificar que la app falla porque no encuentra blobs
curl https://app-curso-<tu-nombre>.azurewebsites.net/api/productos
# Debería devolver error 500
```

**Recovery:**
```bash
# 1. Listar containers soft-deleted
az storage container list \
  --account-name stcurso<tu-nombre> \
  --auth-mode login \
  --include-deleted \
  --query "[?deleted==\`true\`].{Name:name, Version:version, DeletedTime:properties.deletedTime}"

# 2. Restore el container
DELETED_VERSION=$(az storage container list \
  --account-name stcurso<tu-nombre> \
  --auth-mode login \
  --include-deleted \
  --query "[?name=='productos-imagenes'].version" -o tsv)

az storage container restore \
  --account-name stcurso<tu-nombre> \
  --auth-mode login \
  --name productos-imagenes \
  --deleted-version $DELETED_VERSION

# 3. Verificar blobs están de vuelta
az storage blob list \
  --account-name stcurso<tu-nombre> \
  --container-name productos-imagenes \
  --auth-mode login --output table

# 4. Reintentar la app
curl https://app-curso-<tu-nombre>.azurewebsites.net/api/productos
# Debería funcionar ✅
```

**Reflexión:**
- Sin soft-delete: data perdida, recovery from backups (horas)
- Con soft-delete: 30 segundos de comando, cero data perdida
- Coste: ~€0 extra (storage soft-deleted no se factura)

## Slide 23 — Reto 6: Deploy con GitHub Actions + OIDC

Llevad la práctica al siguiente nivel: deploy automático sin secrets:

```yaml
# .github/workflows/deploy.yml
name: Deploy to Azure

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  id-token: write   # ← clave para OIDC
  contents: read

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0'
      
      - name: Build
        run: |
          dotnet restore
          dotnet build --configuration Release --no-restore
          dotnet publish --configuration Release --no-build -o ./publish
      
      - name: Login to Azure (OIDC, no secrets!)
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      - name: Deploy to App Service
        uses: azure/webapps-deploy@v3
        with:
          app-name: app-curso-${{ github.actor }}
          package: ./publish
      
      - name: Health check
        run: |
          sleep 30
          curl -f https://app-curso-${{ github.actor }}.azurewebsites.net/health \
            || (echo "Health check failed" && exit 1)
      
      - name: Logout
        if: always()
        run: az logout
```

**Setup OIDC:**
```bash
# 1. Crear App Registration
APP_ID=$(az ad app create --display-name "github-curso-deploy" \
  --query appId -o tsv)
OBJ_ID=$(az ad app show --id $APP_ID --query id -o tsv)

# 2. Service Principal
az ad sp create --id $APP_ID

# 3. Federated credential para tu repo
az ad app federated-credential create --id $OBJ_ID \
  --parameters '{
    "name": "github-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:<tu-org>/<tu-repo>:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 4. Permisos sobre el RG
az role assignment create \
  --role "Contributor" \
  --assignee $APP_ID \
  --scope "/subscriptions/$(az account show --query id -o tsv)/resourceGroups/rg-curso-azure-<tu-nombre>"

# 5. Configurar GitHub Secrets
echo "Add these to your GitHub repo Settings → Secrets:"
echo "AZURE_CLIENT_ID = $APP_ID"
echo "AZURE_TENANT_ID = $(az account show --query tenantId -o tsv)"
echo "AZURE_SUBSCRIPTION_ID = $(az account show --query id -o tsv)"
```

**Beneficios:**
- ✅ Cero secrets en GitHub (solo IDs públicos)
- ✅ Auto-rotación de tokens
- ✅ Audit completo de deploys
- ✅ Funciona también para push a otras branches con federated credentials adicionales

## Slide 24 — Cleanup script + verificación de costes

Después de la práctica, limpiar recursos para no acumular coste:

```bash
#!/bin/bash
# cleanup.sh — borrar todo el RG después de la práctica

RG="rg-curso-azure-<tu-nombre>"

# 1. Verificar coste consumido durante la práctica
echo "=== Coste estimado de la práctica ==="
az consumption usage list \
  --start-date $(date -u -d '7 days ago' +%Y-%m-%d) \
  --end-date $(date -u +%Y-%m-%d) \
  --query "[?contains(instanceId, '$RG')].{
    Resource: instanceName,
    Cost: pretaxCost,
    Currency: currency
  }" \
  --output table

TOTAL=$(az consumption usage list \
  --start-date $(date -u -d '7 days ago' +%Y-%m-%d) \
  --end-date $(date -u +%Y-%m-%d) \
  --query "[?contains(instanceId, '$RG')] | [].pretaxCost" \
  --output tsv | awk '{sum+=$1} END {print sum}')

echo ""
echo "Total spent: €$TOTAL"
echo ""

# 2. Listar recursos antes de borrar
echo "=== Resources to delete ==="
az resource list -g $RG --output table

# 3. Confirmar
read -p "Delete all resources in $RG? (yes/no): " CONFIRM
if [ "$CONFIRM" != "yes" ]; then
  echo "Aborted"
  exit 0
fi

# 4. Soft-delete protections que necesitan disable primero
echo "Disabling soft-delete protections..."
KV_NAME=$(az keyvault list -g $RG --query "[].name" -o tsv | head -1)
if [ -n "$KV_NAME" ]; then
  echo "WARNING: Key Vault $KV_NAME has purge protection - cannot fully delete"
  echo "Will be in soft-deleted state for 90 days"
fi

# 5. Borrar el RG completo
echo "Deleting RG $RG..."
az group delete --name $RG --yes --no-wait

echo "Cleanup initiated. Will complete in ~10 minutes."

# 6. Verificación post-cleanup (manual, después)
echo ""
echo "Run later to verify:"
echo "  az group exists -n $RG  # should return false"
echo "  az keyvault list-deleted  # check for any soft-deleted vaults"
```

**Coste típico de la práctica completa (1 semana):**
```
Cosmos DB Free Tier:        €0
App Service B1:             €13
Azure SQL Serverless:       €5  (mostly idle)
Storage Account (LRS):      €1
Key Vault (operations):     €0.50
─────────────────────────────────
Total:                      ~€20

Si dejas todo running 1 mes: ~€60-80
Si limpias después de práctica: ~€20 total
```

**Por qué es importante limpiar:**
- App Service Plans facturan aunque la app esté stopped
- Storage acumula sin límite si no borras
- Key Vault con purge protection persiste 90 días
- Cosmos DB Free Tier solo permite 1 cuenta gratuita

## Slide 2 — La pregunta que nadie quiere hacerse
"¿Qué pasa si perdemos la base de datos?" No es una pregunta teórica. Pasa: un DELETE sin WHERE, un script que corrompe datos, un error en una migración, un ransomware, un fallo de región.

La diferencia entre un desastre y un susto de 30 minutos es tener backups probados y un plan de recuperación documentado.

---

## Slide 3 — Backups por servicio: qué viene incluido

| Servicio | Backup automático | Retención | Point-in-time restore |
|----------|:-----------------:|:---------:|:---------------------:|
| **Cosmos DB** | ✓ (cada 4h) | 30 días (configurable) | ✓ (resolución de 1h) |
| **Azure SQL** | ✓ (continuo) | 7-35 días según tier | ✓ (resolución de segundos) |
| **Blob Storage** | Soft delete + Versioning | Configurable | ✓ (con versionado) |
| **Table Storage** | No automático | — | No |
| **App Service** | Configurable (no por defecto) | Configurable | No (restore de snapshot) |

**Lo que NO tiene backup automático y debéis configurar vosotros:** Table Storage, Queue Storage (los mensajes son efímeros por diseño), y App Service (configuración + contenido).

## Slide 4 — Cosmos DB: backups

**Continuous backup (recomendado):**
```bash
az cosmosdb create \
  --name cosmos-ventas-prod -g rg-ventas-prod \
  --backup-policy-type Continuous \
  --continuous-tier Continuous30Days
```

Permite point-in-time restore a cualquier momento en los últimos 30 días.

```bash
# Restaurar a un punto en el tiempo
az cosmosdb restore \
  --account-name cosmos-ventas-prod -g rg-ventas-prod \
  --target-database-account-name cosmos-ventas-restored \
  --restore-timestamp "2025-06-15T14:30:00Z" \
  --location westeurope
```

**Periodic backup (clásico):**
Snapshot cada 4 horas, retención configurable. Más barato pero resolución de 4h (peor RPO).

**Recomendación:** Continuous para producción. El coste adicional es mínimo comparado con la tranquilidad de poder restaurar a cualquier segundo.

## Slide 5 — Azure SQL: backups y point-in-time restore

Azure SQL hace backups continuos automáticamente:

```bash
# Restaurar a un punto en el tiempo
az sql db restore \
  --server sql-ventas-prod -g rg-ventas-prod \
  --name db-ventas \
  --dest-name db-ventas-restored \
  --time "2025-06-15T14:30:00Z"

# La DB restaurada es una DB nueva (no sobreescribe la original)
# Verificad los datos, y si están bien, renombrad
```

**Retención:**
- Basic: 7 días
- Standard: 35 días
- Premium: 35 días
- Long-term retention (LTR): hasta 10 años

```bash
# Configurar retención a largo plazo
az sql db ltr-policy set \
  --server sql-ventas-prod -g rg-ventas-prod --database db-ventas \
  --weekly-retention P4W \
  --monthly-retention P12M \
  --yearly-retention P5Y \
  --week-of-year 1
```

## Slide 6 — Blob Storage: protección contra borrado

```bash
# Soft delete (recuperar blobs eliminados)
az storage account blob-service-properties update \
  --account-name stventasprod -g mi-rg \
  --enable-delete-retention true --delete-retention-days 30

# Versionado (mantener todas las versiones)
az storage account blob-service-properties update \
  --account-name stventasprod -g mi-rg --enable-versioning true

# Immutability (blobs que no se pueden modificar ni eliminar — compliance)
az storage container immutability-policy create \
  --account-name stventasprod --container-name legal \
  --period 365  # No se puede tocar durante 365 días
```

**Recuperar un blob eliminado (soft delete):**
```bash
az storage blob undelete \
  --account-name stventasprod --container-name facturas --name factura-001.pdf
```

## Slide 7 — Replicación geográfica

**Cosmos DB:** Multi-region writes nativo.
```bash
az cosmosdb update --name cosmos-ventas-prod -g rg-ventas-prod \
  --locations regionName=westeurope failoverPriority=0 isZoneRedundant=true \
  --locations regionName=northeurope failoverPriority=1 isZoneRedundant=true
```
Failover automático si West Europe cae.

**Azure SQL:** Active geo-replication.
```bash
az sql db replica create \
  --server sql-ventas-prod -g rg-ventas-prod --name db-ventas \
  --partner-server sql-ventas-dr --partner-resource-group rg-ventas-dr
```
Réplica de lectura en otra región. Failover manual o automático.

**Blob Storage:** GRS o GZRS (visto en 5.1). Replicación automática a la región par.

## Slide 8 — Plan de recuperación ante desastres (DR)

Un plan de DR documenta qué hacer cuando algo va mal:

**RPO (Recovery Point Objective):** ¿Cuántos datos podemos perder? ¿5 minutos? ¿1 hora? ¿0?
**RTO (Recovery Time Objective):** ¿Cuánto tiempo puede estar caído? ¿5 minutos? ¿1 hora? ¿4 horas?

| Servicio | RPO | RTO | Estrategia |
|----------|:---:|:---:|-----------|
| Cosmos DB | ~0 (continuous) | Minutos (failover auto) | Multi-region + continuous backup |
| Azure SQL | Segundos (point-in-time) | Minutos-horas (restore) | Geo-replication + PITR |
| Blob Storage | ~0 (GRS) | Horas (failover manual) | GRS + soft delete + versioning |
| App Service | N/A (stateless) | Minutos (redeploy) | Pipeline CI/CD + IaC |
| Functions | N/A (stateless) | Minutos (redeploy) | Pipeline CI/CD + IaC |

**Para apps stateless (App Service, Functions):** El DR es redesplegar desde el pipeline. El código está en Git, la infraestructura en Bicep. Tiempo de recuperación = tiempo de ejecutar el pipeline.

## Slide 9 — Probar el DR: la parte que nadie hace

Un plan de DR que no se prueba no es un plan — es una esperanza.

**Pruebas recomendadas (trimestralmente):**
1. Restaurar Cosmos DB a un punto en el tiempo → verificar datos
2. Restaurar Azure SQL → verificar que la app funciona con la DB restaurada
3. Recuperar blobs eliminados con soft delete
4. Ejecutar failover de Cosmos DB a la región secundaria
5. Redesplegar la app completa desde pipeline en una región nueva

**Documentar:**
- Quién ejecuta el DR (responsable + backup)
- Pasos exactos con comandos
- Contactos de escalación
- Criterios de éxito/fracaso

## Slide 10 — App Service: backup y restore

App Service NO tiene backup automático por defecto. Hay que configurarlo:

```bash
# Crear backup manual
az webapp config backup create \
  --webapp-name app-ventas-prod -g rg-ventas-prod \
  --container-url "https://stventasprod.blob.core.windows.net/backups?sv=...&sig=..."  \
  --backup-name "backup-$(date +%Y%m%d)"

# Configurar backup automático (diario)
az webapp config backup update \
  --webapp-name app-ventas-prod -g rg-ventas-prod \
  --container-url "https://stventasprod.blob.core.windows.net/backups?sv=...&sig=..." \
  --frequency 1d --retain-one true --retention 30

# Restaurar
az webapp config backup restore \
  --webapp-name app-ventas-prod -g rg-ventas-prod \
  --container-url "https://stventasprod.blob.core.windows.net/backups?sv=...&sig=..." \
  --backup-name "backup-20250615" --overwrite
```

**¿Qué incluye?** Configuración de la app, contenido de wwwroot, opcionalmente bases de datos vinculadas. **Requiere tier Standard+.**

## Slide 11 — Estrategia 3-2-1 en Azure

La regla clásica de backups aplicada a la nube:

**3** copias de los datos:
- Original en producción (Cosmos/SQL/Storage)
- Backup automático del servicio (PITR)
- Backup adicional en otra región o cuenta

**2** tipos de almacenamiento diferentes:
- Datos en Cosmos DB (documents)
- Backup en Blob Storage (snapshots/exports)

**1** copia offsite (otra región):
- Storage Account con GRS (réplica automática)
- O exportación explícita a otra región

```bash
# Exportar Cosmos DB a Blob (backup adicional)
az cosmosdb dts copy \
  --account-name cosmos-ventas-prod -g rg-ventas-prod \
  --source-cosmos-container tienda/pedidos \
  --dest-blob-container stventasprod/cosmos-backup
```

## Slide 12 — Runbook de recuperación: ejemplo real

**Escenario: alguien ejecutó DELETE FROM pedidos WHERE 1=1 a las 15:00**

**Paso 1 (15:02) — Detectar:**
Alerta de Application Insights: "0 pedidos devueltos en queries GET /api/pedidos"

**Paso 2 (15:05) — Evaluar:**
Verificar en Cosmos DB → container vacío. Verificar Change Feed → avalancha de deletes a las 15:00.

**Paso 3 (15:10) — Restaurar Cosmos DB:**
```bash
az cosmosdb restore \
  --account-name cosmos-ventas-prod -g rg-ventas-prod \
  --target-database-account-name cosmos-ventas-restored \
  --restore-timestamp "2025-06-15T14:59:00Z" \
  --location westeurope
```

**Paso 4 (15:25) — Verificar datos restaurados:**
Conectar a la cuenta restaurada, verificar que los pedidos están ahí.

**Paso 5 (15:30) — Redirigir la app:**
Actualizar App Setting `CosmosEndpoint` para apuntar a la cuenta restaurada.

**Paso 6 (15:35) — Verificar producción:**
GET /api/pedidos devuelve datos. Los usuarios confirman que funciona.

**Tiempo total de recuperación: ~35 minutos.** Sin backup continuous, serían horas o imposible.

## Slide 14 — Disaster Recovery: RTO y RPO por servicio

| Servicio | RPO (datos perdidos) | RTO (tiempo caída) | Acción |
|----------|:--------------------:|:-------------------:|--------|
| Cosmos DB | ~0 (continuous) | 5-30 min (restore) | PITR a nueva cuenta |

| Functions | N/A (stateless) | 5-15 min | Redesplegar pipeline |
| Key Vault | ~0 (built-in repl) | Automático | Nada (geo-redundante) |

**Para apps stateless (App Service, Functions):** Redesplegar desde el pipeline CI/CD. El código está en Git, la infra en Bicep. Tiempo = ejecutar el pipeline.

## Slide 17 — Azure Backup Vault: el orquestador centralizado

Azure Backup vault unifica backups de múltiples servicios en un único panel:

```bash
# 1. Crear Backup Vault (recomendado para producción)
az dataprotection backup-vault create \
  --resource-group rg-curso \
  --vault-name bv-curso-prod \
  --location westeurope \
  --type SystemAssigned \
  --storage-settings datastore-type="VaultStore" type="ZoneRedundant"

# 2. Crear backup policy (define cuándo y cuánto retener)
cat > policy-daily.json <<EOF
{
  "name": "DailyPolicy30Days",
  "objectType": "BackupPolicy",
  "datasourceTypes": ["Microsoft.Sql/servers/databases"],
  "policyRules": [
    {
      "name": "BackupDaily",
      "objectType": "AzureBackupRule",
      "trigger": {
        "objectType": "ScheduleBasedTriggerContext",
        "schedule": {
          "repeatingTimeIntervals": ["R/2026-04-22T22:00:00Z/P1D"]
        }
      },
      "lifecycles": [{
        "deleteAfter": {
          "objectType": "AbsoluteDeleteOption",
          "duration": "P30D"
        },
        "sourceDataStore": {
          "dataStoreType": "VaultStore",
          "objectType": "DataStoreInfoBase"
        }
      }]
    }
  ]
}
EOF

az dataprotection backup-policy create \
  --resource-group rg-curso \
  --vault-name bv-curso-prod \
  --backup-policy-name DailyPolicy30Days \
  --policy @policy-daily.json

# 3. Aplicar policy a un recurso
az dataprotection backup-instance create \
  --resource-group rg-curso \
  --vault-name bv-curso-prod \
  --backup-instance @backup-instance-sql.json
```

**Servicios soportados (2026):**

| Tipo | Backup support |
|---|:---:|
| Azure VM | ✅ |
| Azure Files | ✅ |
| Azure SQL DB | ✅ |
| Azure SQL Managed Instance | ✅ |
| SAP HANA | ✅ |
| Blob Storage | ✅ (operational + vaulted) |
| AKS persistent volumes | ✅ |
| PostgreSQL Flexible Server | ✅ |
| Azure Disks | ✅ |

**Vault vs Snapshot tier:**
```
Snapshot tier (operational):
├── Faster restore (~minutos)
├── Stored cerca del recurso
└── Solo retención corta (días)

Vault tier (long-term):
├── Aislado del recurso (compliance)
├── Hasta 99 años retention
├── Cross-region restore
└── Slower restore (horas para muchos GB)
```

**Best practice:** ambos. Snapshot para recovery rápido, Vault para compliance.

## Slide 18 — Cross-region restore: DR a otra región

Cuando una región Azure cae completa (raro pero pasa):

```bash
# Configurar Cross-Region Restore (CRR) en el Vault
az backup vault backup-properties set \
  --resource-group rg-curso \
  --name bv-curso-prod \
  --cross-region-restore-flag true

# Backups se replican a paired region automáticamente
# West Europe ↔ North Europe
# East US ↔ West US
# UK South ↔ UK West

# Restore a la región paired
az dataprotection backup-instance restore-trigger \
  --resource-group rg-curso \
  --vault-name bv-curso-prod \
  --backup-instance-name "MyBackup" \
  --restore-request-object '{
    "objectType": "AzureBackupRestoreWithRehydrationRequest",
    "restoreLocation": "northeurope",
    "rehydrationPriority": "Standard"
  }'
```

**Region pairing en Azure (2026):**
```
West Europe   ↔   North Europe
East US       ↔   West US
UK South      ↔   UK West
France Central↔   France South
Germany WC    ↔   Germany N
Sweden Central↔   Sweden S
```

**Workflow real de DR:**
```
Day 0: West EU completa caída
├── Detected via Service Health alerts
├── Decision: failover a North Europe
└── Trigger restore process

Step 1: Restore Storage Accounts (CRR)
├── Backup vault tiene last 30 days
├── Restore latest backup → North EU storage
├── Time: 2-4 hours per TB

Step 2: Restore Cosmos DB
├── Continuous backup retains 30 days
├── Restore to point-in-time → cosmos-recovered-northeu
├── Time: ~30 min for 100GB

Step 3: Restore Azure SQL
├── Geo-restore from geo-redundant backup
├── Time: ~1 hour per TB (tier-dependent)

Step 4: Update DNS / Traffic Manager
├── Point all DNS to North EU resources
└── App continúa funcionando
```

**Verificar que CRR está activo:**
```bash
az backup vault backup-properties show \
  --resource-group rg-curso \
  --name bv-curso-prod \
  --query "crossRegionRestoreFlag"
# Esperado: true
```

**Costes adicionales CRR:**
- Storage replicado a paired region (~2x storage cost)
- Bandwidth durante backup replication
- Restore: standard restore charges + cross-region transfer

**Important:** Solo aplicable a vaults configurados como GRS (no LRS).

## Slide 19 — Soft-delete recovery walkthrough

Soft-delete es tu última línea de defensa contra borrado accidental:

```
Niveles de soft-delete en Azure:
┌─────────────────────────────────────────────────────────────────┐
│  RECURSO          │ SOFT-DELETE | RETENTION DEFAULT             │
├─────────────────────────────────────────────────────────────────┤
│  Blob Storage     │ ✅ ON       | 7 días (configurable 1-365)   │
│  Container        │ ✅ ON       | 7 días (configurable 1-365)   │
│  Storage Account  │ ❌ NO       | Una vez borrado, se va        │
│  Azure SQL DB     │ ✅          | 7 días después de drop        │
│  Cosmos DB        │ ⚠️ Beta     | Recovery via support ticket  │
│  Key Vault        │ ✅ ON       | 90 días (configurable 7-90)   │
│  Recovery Vault   │ ✅ ON       | 14 días (no configurable)    │
└─────────────────────────────────────────────────────────────────┘
```

**Recovery completo Blob:**
```bash
# Escenario: alguien borró el container "facturas-2026"

# 1. Listar containers soft-deleted
az storage container list \
  --account-name stcurso \
  --auth-mode login \
  --include-deleted \
  --query "[?deleted==\`true\`].{Name:name, Version:version, DeletedTime:properties.deletedTime}"

# 2. Restore el container
az storage container restore \
  --account-name stcurso \
  --auth-mode login \
  --name facturas-2026 \
  --deleted-version "01D8FDD..."

# 3. Verificar blobs están de vuelta
az storage blob list \
  --account-name stcurso \
  --container-name facturas-2026 \
  --auth-mode login --output table
```

**Recovery Azure SQL:**
```bash
# 1. Ver databases soft-deleted
az sql db list-deleted \
  --resource-group rg-curso \
  --server sql-curso

# 2. Restore desde deleted (point-in-time)
az sql db restore \
  --resource-group rg-curso \
  --server sql-curso \
  --name PedidosDb-restored \
  --deleted-time "2026-04-22T10:00:00Z" \
  --time "2026-04-22T09:30:00Z" \
  --source-database PedidosDb
```

**Recovery Key Vault:**
```bash
# 1. Listar deleted vaults
az keyvault list-deleted

# 2. Recover (must be done within retention period)
az keyvault recover --name kv-curso

# 3. Recover individual deleted secret
az keyvault secret recover \
  --vault-name kv-curso \
  --name api-key
```

**Best practice — habilitar soft-delete en TODO:**
```bash
# Storage
az storage account blob-service-properties update \
  --account-name stcurso \
  --resource-group rg-curso \
  --enable-delete-retention true \
  --delete-retention-days 30 \
  --enable-container-delete-retention true \
  --container-delete-retention-days 30

# Key Vault — purge protection ALWAYS ON en prod
az keyvault update --name kv-curso \
  --enable-purge-protection true

# Cuidado: purge protection NO se puede deshabilitar
```

**Real-world incident:**
```
Lunes 09:00  Junior dev script borra "test-*" containers
              accidentally borra "test-prod-data" también
Lunes 09:15  Production app falling, recovery iniciado
Lunes 09:30  Container restored from soft-delete
Lunes 09:35  App back online
Lunes total: 30 min downtime, no data loss
            
Sin soft-delete: data perdida + horas de restore desde backups offline
```

## Slide 20 — Compliance retention requirements

Distintos sectores tienen requisitos de retención obligatorios:

```
┌─────────────────┬─────────────────────────┬──────────────┐
│ REGULACIÓN      │ DATOS                   │ RETENTION    │
├─────────────────┼─────────────────────────┼──────────────┤
│ SEC 17a-4       │ Comunicaciones broker   │ 6 años WORM  │
│ FINRA 4511      │ Records financieros     │ 6 años       │
│ HIPAA           │ Healthcare records      │ 6 años       │
│ Sarbanes-Oxley  │ Financial statements    │ 7 años       │
│ RGPD            │ Personal data           │ Right to erase│
│ FDA 21 CFR P11  │ Pharma manufacturing    │ Permanente   │
│ PCI DSS         │ Cardholder data         │ Min necesario│
│ Tax (España)    │ Records contables       │ 6 años       │
│ Legal (España)  │ Documents juicios       │ 30 años+     │
└─────────────────┴─────────────────────────┴──────────────┘
```

**Implementar compliance retention:**
```bash
# Para SEC/FINRA — Immutable Blobs con WORM
az storage container immutability-policy create \
  --account-name stcurso \
  --container-name compliance-records \
  --period 2555  # 7 años in días
  --resource-group rg-curso

az storage container immutability-policy lock \
  --account-name stcurso \
  --container-name compliance-records \
  --resource-group rg-curso \
  --if-match "<etag>"

# Para Backup vault — Long-term retention
cat > policy-compliance.json <<EOF
{
  "policyRules": [
    {
      "name": "DailyBackup",
      "trigger": {
        "schedule": {"repeatingTimeIntervals": ["R/2026-04-22T22:00:00Z/P1D"]}
      },
      "lifecycles": [{
        "deleteAfter": {"objectType": "AbsoluteDeleteOption", "duration": "P30D"}
      }]
    },
    {
      "name": "WeeklyBackup",
      "trigger": {
        "schedule": {"repeatingTimeIntervals": ["R/2026-04-22T22:00:00Z/P1W"]}
      },
      "lifecycles": [{
        "deleteAfter": {"objectType": "AbsoluteDeleteOption", "duration": "P52W"}
      }]
    },
    {
      "name": "YearlyBackup",
      "trigger": {
        "schedule": {"repeatingTimeIntervals": ["R/2026-04-22T22:00:00Z/P1Y"]}
      },
      "lifecycles": [{
        "deleteAfter": {"objectType": "AbsoluteDeleteOption", "duration": "P7Y"}
      }]
    }
  ]
}
EOF
```

**RGPD: right to erase + backup conflict:**
```
Problema:
├── User pide RGPD erasure de sus datos
├── Pero backups inmutables existen 7 años
└── Conflict: legal vs RGPD

Solución típica:
├── 1. Borrar datos en producción inmediatamente
├── 2. Documentar la solicitud RGPD
├── 3. Configurar backup retention para RGPD-eligible data:
│      └── Retention 30-90 días (no 7 años)
├── 4. Para datos compliance-locked:
│      └── Documentar por qué backup retention es legítima
│      └── Mostrar al user que datos en prod están borrados
└── 5. Cuando expire backup, datos truly gone
```

## Slide 21 — Game day DR drill: ejecutar el plan

Drill = simulacro de DR completo. Hacedlo cada 6 meses:

```
Game Day Plan template:
─────────────────────────────────────────────────────────────────

Pre-drill (1 semana antes):
├── [ ] Notificar stakeholders (Ops, Dev, Business)
├── [ ] Reservar ventana (sábado mañana típicamente)
```

## Slide 22 — RPO/RTO measurement real

No basta con definir RPO/RTO en papel — hay que medirlos:

```
RPO (Recovery Point Objective):
└── Cuánto data puedes perder
    Si RPO = 15 min:
    └── En desastre, pierdes max 15 min de data

RTO (Recovery Time Objective):
└── Cuánto puedes estar caído
    Si RTO = 1 hora:
    └── Desde "down" hasta "back online" max 1 hora
```

**Por servicio Azure (defaults):**

```
┌─────────────────────────┬──────────┬──────────┐
│ SERVICIO                │ RPO típ. │ RTO típ. │
├─────────────────────────┼──────────┼──────────┤
│ Cosmos DB (multi-region) │ < 1 sec  │ < 1 min  │
│ Cosmos DB (single region)│ ~15 min  │ ~30 min  │
│ Azure SQL (Bus.Crit)     │ < 5 sec  │ ~30 sec  │
│ Azure SQL (Standard)     │ ~5 min   │ ~30 min  │
│ Azure SQL (FOG)          │ ~5 sec   │ < 1 min  │
│ Storage GZRS             │ ~15 min  │ Manual   │
│ Storage RA-GZRS          │ ~15 min  │ < 1 min  │
│ App Service (multi-rgn)  │ N/A      │ ~1 min   │
│ Service Bus Premium GeoR │ < 1 sec  │ < 1 min  │
└─────────────────────────┴──────────┴──────────┘
```

**Medir tu RPO/RTO real (no asumido):**

## Slide 23 — Restore validation testing

Restore que no se prueba = backup que puede fallar:

```
Test mensual obligatorio:
├── Restore from backup → temp resource
├── Sample data validation
├── App pointing to restored data → smoke test
└── Cleanup
```

**Script de validation automatizado:**
```bash
#!/bin/bash
# restore-validation.sh — corre cada mes

set -e

DATE=$(date +%Y-%m-%d)
TEMP_RG="rg-restore-test-$DATE"

echo "=== Restore Validation Test - $DATE ==="

# 1. Crear RG temporal
az group create -n $TEMP_RG -l westeurope

# 2. Restore Cosmos DB to temp
echo "Restoring Cosmos DB..."
az cosmosdb restore \
  --resource-group $TEMP_RG \
  --target-database-account-name "cosmos-restore-test-$DATE" \
  --account-name cosmos-curso-prod \
  --restore-timestamp "$(date -u -d '1 day ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --location westeurope

# 3. Validate data
echo "Validating data..."
COUNT=$(az cosmosdb sql container show \
  --account-name "cosmos-restore-test-$DATE" \
  --database-name PedidosDb \
  --name orders \
  --resource-group $TEMP_RG \
  --query "resource.statistics.documentCount" -o tsv)

if [ "$COUNT" -lt 1000 ]; then
  echo "❌ ERROR: Only $COUNT documents restored (expected > 1000)"
  exit 1
fi

# 4. Run sample queries
echo "Running smoke tests..."
RESULT=$(az cosmosdb sql query \
  --account-name "cosmos-restore-test-$DATE" \
  --database-name PedidosDb \
  --container-name orders \
  --query-text "SELECT TOP 1 * FROM c WHERE c.status = 'completed'" \
  --output json)

if [ -z "$RESULT" ]; then
  echo "❌ ERROR: Sample query returned no data"
  exit 1
fi

echo "✅ Validation passed: $COUNT docs restored, queries OK"

# 5. Cleanup (siempre, aunque falle)
trap "az group delete -n $TEMP_RG --yes --no-wait" EXIT

echo "=== Validation completed ==="
```


## Slide 24 — Cost of DR: presupuestar realmente

DR no es gratis. Estimaciones reales:

```
┌──────────────────────────────────────────────────────────────────┐
│  COSTE TÍPICO DR PARA APP MEDIA                                   │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│ Componente            │ Cost-Active   │ Cost-Cold (warm)        │
│ ──────────────────────┼───────────────┼─────────────────────────│
│ Storage (1TB GRS)     │ +€18/mes      │ Same                    │
│ Cosmos secondary read │ +€500/mes     │ ~€100 (cold standby)    │
│ Azure SQL secondary   │ +€450/mes     │ ~€90 (cold standby)     │
│ App Service plan 2    │ +€140/mes     │ €70 (small SKU standby) │
│ Service Bus Premium   │ +€650/mes     │ Included en geo-DR      │
│ DNS / Traffic Manager │ +€10/mes      │ Same                    │
│ Bandwidth cross-rgn   │ +€50-200/mes  │ Mostly idle             │
│ Backup vault          │ +€30-100/mes  │ Same                    │
│ ──────────────────────┼───────────────┼─────────────────────────│
│ TOTAL                 │ +€1500/mes    │ +€500/mes               │
│ Annual                │ +€18K/año     │ +€6K/año                │
└──────────────────────────────────────────────────────────────────┘
```

**3 estrategias de DR:**

```
1. ACTIVE-ACTIVE (más caro, mejor)
   ├── Both regions live, traffic split
   ├── RTO: < 1 min
   ├── RPO: < 1 sec (Cosmos multi-write)
   └── Cost: 2x base
   
2. WARM STANDBY (recomendado típicamente)
   ├── Secondary running but smaller
   ├── On failover: scale up secondary
   ├── RTO: 15-60 min
   ├── RPO: 5-15 min
   └── Cost: 1.3-1.5x base

3. COLD STANDBY (más barato)
   ├── Secondary infrastructure exists pero off
   ├── On failover: provision + restore from backups
   ├── RTO: 4-24 hours
   ├── RPO: hours (depending backup frequency)
   └── Cost: 1.05-1.1x base (storage only)
```

**Decisión por criticidad:**
```
Mission-critical (banking, healthcare critical):
└── Active-Active multi-region
    Cost justified by zero downtime requirement

Important (e-commerce, CRM):
└── Warm Standby
    Balance cost vs availability

Internal tools, dev/test:
└── Cold Standby
    Acceptable downtime for cost savings
```

**Hidden costs:**
- Cross-region bandwidth (€0.087/GB)
- Backup storage (€0.024/GB/month for vault)
- Restore charges (puede ser caros para archive tier)
- Engineering time (drills, training)
- Compliance overhead (audits)

**ROI calculation:**
```
Sin DR:
├── Probability mayor outage: 1-2/año
├── Average outage: 8 horas
├── Revenue per hour: €20K
└── Annual loss: €320K-€640K

Con Warm Standby DR:
├── Cost: €18K/año
├── Outage shortened to 30 min
├── Annual loss: €20K
├── Net saving: €300K-€620K/año
└── ROI: 16-34x
```

## Slide 25 — Recovery automation con scripts

Manual recovery = lento + error-prone. Automate everything:

```bash
#!/bin/bash
# dr-failover.sh — script de failover orchestration

set -e

PRIMARY_RG="rg-prod-westeu"
SECONDARY_RG="rg-prod-northeu"
APP_NAME="mi-app"

echo "=== DR Failover started: $(date) ==="

# 1. Health check primary
echo "Checking primary region..."
PRIMARY_HEALTH=$(curl -s -o /dev/null -w "%{http_code}" \
  https://app-prod-westeu.azurewebsites.net/health || echo "000")

if [ "$PRIMARY_HEALTH" == "200" ]; then
  echo "Primary still healthy. Aborting failover."
  exit 1
fi

echo "Primary unhealthy ($PRIMARY_HEALTH). Proceeding..."

# 2. Failover Cosmos DB
echo "Triggering Cosmos failover..."
az cosmosdb failover-priority-change \
  --name cosmos-prod \
  --resource-group $PRIMARY_RG \
  --failover-policies northeurope=0 westeurope=1

# 3. Failover Azure SQL (FOG)
echo "Triggering SQL failover..."
az sql failover-group set-primary \
  --name fog-prod \
  --resource-group $PRIMARY_RG \
  --server sql-prod-westeu

# 4. Update Traffic Manager
echo "Updating Traffic Manager..."
az network traffic-manager profile update \
  --name tm-app \
  --resource-group $PRIMARY_RG \
  --routing-method Priority \
  --set "endpoints[?name=='primary'].priority=2" \
  --set "endpoints[?name=='secondary'].priority=1"

# 5. Scale up secondary (if cold/warm standby)
echo "Scaling up secondary App Service..."
az appservice plan update \
  --name plan-prod-northeu \
  --resource-group $SECONDARY_RG \
  --sku P2v3

# 6. Verify new primary works
echo "Verifying new primary..."
sleep 30
NEW_HEALTH=$(curl -s -o /dev/null -w "%{http_code}" \
  https://app-prod-northeu.azurewebsites.net/health)

if [ "$NEW_HEALTH" == "200" ]; then
  echo "✅ Failover successful. New primary: North Europe"
  
  # 7. Notify stakeholders
  curl -X POST $TEAMS_WEBHOOK \
    -H "Content-Type: application/json" \
    -d "{\"text\":\"🚨 DR Failover completed at $(date). Primary now: North Europe\"}"
else
  echo "❌ Failover validation failed"
  exit 1
fi

echo "=== DR Failover completed: $(date) ==="
```

**Trigger options:**
- Manual: human runs script when needed
- Automated: monitoring detects + auto-trigger (risky, can flap)
- Semi-automated: monitoring opens incident → human approves → script runs

**Recommended: semi-automated**
```yaml
# Azure DevOps pipeline triggered by manual approval
trigger: none
parameters:
  - name: confirmFailover
    type: string
    default: 'no'
    values: ['no', 'YES_FAILOVER']

steps:
  - task: AzureCLI@2
    condition: eq('${{ parameters.confirmFailover }}', 'YES_FAILOVER')
    inputs:
      scriptType: bash
      scriptPath: scripts/dr-failover.sh
```

**Failback (volver a primary):**
```bash

# Reverse de failover script
# Importantes: validar primary stable antes de switch
```

## Slide 26 — Monitoring backups: alertar fallos

Backups que fallan silenciosamente = surprise el día del desastre:

```bash
# 1. Habilitar diagnostic settings en Backup vault
az monitor diagnostic-settings create \
  --name diag-bv \
  --resource $(az dataprotection backup-vault show \
    -n bv-curso -g rg-curso --query id -o tsv) \
  --workspace $(az monitor log-analytics workspace show \
    -n law-curso -g rg-curso --query id -o tsv) \
  --logs '[
    {"category": "AddonAzureBackupJobs", "enabled": true},
    {"category": "AddonAzureBackupAlerts", "enabled": true},
    {"category": "CoreAzureBackup", "enabled": true}
  ]'

# 2. Alert: backup job failed
az monitor scheduled-query create \
  --name "backup-failed-alert" \
  --resource-group rg-curso \
  --scopes $(az monitor log-analytics workspace show \
    -n law-curso -g rg-curso --query id -o tsv) \
  --condition "count > 0" \
  --condition-query 'AddonAzureBackupJobs | where JobStatus == "Failed" | where TimeGenerated > ago(1h)' \
  --description "Backup job failed in last hour" \
  --evaluation-frequency 15m \
  --window-size 1h \
  --severity 1 \
  --action-groups $(az monitor action-group show -n ag-prod -g rg-curso --query id -o tsv)

# 3. Alert: backup hasn't run in 25 hours (expected daily)
az monitor scheduled-query create \
  --name "backup-missing-alert" \
  --resource-group rg-curso \
  --scopes ... \
  --condition "count == 0" \
  --condition-query 'AddonAzureBackupJobs | where JobStatus == "Completed" | where TimeGenerated > ago(25h)' \
  --description "Daily backup did not complete" \
  --severity 0
```

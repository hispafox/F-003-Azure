## Slide 3 — Cosmos DB: modelo mental

```
Cosmos DB Account (cosmos-ventas-prod)
├── Database: "tienda"
│   ├── Container: "pedidos" (partition key: /clienteId)
│   │   ├── Documento: { id: "ped-1", clienteId: "cli-001", items: [...] }
│   │   ├── Documento: { id: "ped-2", clienteId: "cli-001", items: [...] }
│   │   └── Documento: { id: "ped-3", clienteId: "cli-002", items: [...] }
│   │
│   └── Container: "productos" (partition key: /categoria)
│       ├── Documento: { id: "prod-1", categoria: "electrónica", nombre: "Laptop" }
│       └── Documento: { id: "prod-2", categoria: "accesorios", nombre: "Mouse" }
```

**Account** → **Database** → **Container** → **Documents (JSON)**

Un container es como una tabla, pero sin schema fijo. Cada documento puede tener campos diferentes. La partition key define cómo se distribuyen los datos.

## Slide 4 — Partition Key: la decisión más importante

La partition key determina cómo Cosmos DB distribuye los datos entre particiones físicas:

```
Container "pedidos" (partition key: /clienteId)

Partición física A          Partición física B          Partición física C
┌─────────────────┐        ┌─────────────────┐        ┌─────────────────┐
│ clienteId: cli-001│       │ clienteId: cli-002│       │ clienteId: cli-003│
│ pedido-1         │        │ pedido-3         │        │ pedido-5         │
│ pedido-2         │        │ pedido-4         │        │ pedido-6         │
│ pedido-7         │        │                  │        │ pedido-8         │
└─────────────────┘        └─────────────────┘        └─────────────────┘
     5000 RU/s                  5000 RU/s                  5000 RU/s
```

**Queries dentro de una partición:** Rápidas y baratas (Cosmos sabe exactamente dónde buscar).
**Queries cross-partition:** Lentas y caras (Cosmos tiene que buscar en TODAS las particiones).

---

## Slide 5 — Elegir la partition key correcta

**Buena partition key:**
- Alta cardinalidad (muchos valores distintos): `clienteId`, `userId`, `orderId`
- Distribución uniforme: cada partición tiene un volumen similar
- Alineada con tus queries: las queries más frecuentes filtran por esta clave

**Mala partition key:**
- Baja cardinalidad: `pais` (si el 80% de datos son de España, una partición se sobrecarga)
- Hot partition: `fecha` como partition key → todos los datos de hoy van a la misma partición
- No alineada con queries: partition key es `categoría` pero siempre buscas por `clienteId`

**¿Cómo decidir?** Preguntaos: "¿Cuál es la query más frecuente?" Si el 80% de las queries son "dame los pedidos del cliente X", entonces `clienteId` es la partition key correcta.

## Slide 7 — Request Units (RU): la moneda de Cosmos DB

Cada operación consume **Request Units (RU)**. Es la unidad universal de coste:

| Operación | RU aproximadas |
|-----------|:--------------:|
| Leer 1 documento de 1 KB por ID | 1 RU |
| Leer 1 documento de 1 KB por query | 2-3 RU |
| Escribir 1 documento de 1 KB | 5-6 RU |
| Query sin índice (table scan) | 50-500+ RU |
| Query cross-partition | 10-100x más que single-partition |

**Provisioned throughput:** Reserváis X RU/s. Si superáis, Cosmos devuelve HTTP 429 (throttling).

**Autoscale:** Escala entre un mínimo y un máximo de RU/s según demanda.

**Serverless:** Pago por RU consumida (sin provisioning). Ideal para desarrollo.

```bash
# Ver RU provisionadas
az cosmosdb sql container throughput show \
  --account-name cosmos-ventas-prod -g mi-rg \
  --database-name tienda --name pedidos
```

## Slide 8 — Optimizar RU: la diferencia entre céntimos y euros

```csharp
// MAL: query cross-partition sin filtro (table scan) — 500+ RU
var todos = container.GetItemQueryIterator<Pedido>("SELECT * FROM c");

// BIEN: query single-partition con filtro — 3-5 RU
var query = new QueryDefinition("SELECT * FROM c WHERE c.clienteId = @clienteId")
    .WithParameter("@clienteId", "cli-001");
var opciones = new QueryRequestOptions { PartitionKey = new PartitionKey("cli-001") };
var pedidos = container.GetItemQueryIterator<Pedido>(query, requestOptions: opciones);

// MEJOR: leer por ID directo — 1 RU
var response = await container.ReadItemAsync<Pedido>(
    "ped-001", new PartitionKey("cli-001"));

// Ver cuántas RU consumió la operación
Console.WriteLine($"RU consumidas: {response.RequestCharge}");
```

**Reglas de optimización:**
1. Siempre incluir partition key en queries → single-partition
2. Leer por ID cuando sea posible → 1 RU
3. Proyectar solo los campos necesarios (`SELECT c.id, c.total FROM c`)
4. Usar índices (automáticos por defecto en Cosmos DB)
5. Monitorizar RU por query con `RequestCharge`

## Slide 10 — Queries con SQL API

Cosmos DB soporta un subconjunto de SQL para queries:

```csharp
// Query básica
var query = new QueryDefinition(
    "SELECT * FROM c WHERE c.clienteId = @clienteId AND c.total > @minTotal")
    .WithParameter("@clienteId", "cli-001")
    .WithParameter("@minTotal", 100);

var iterator = container.GetItemQueryIterator<Pedido>(query);
var resultados = new List<Pedido>();
while (iterator.HasMoreResults)
{
    var page = await iterator.ReadNextAsync();
    resultados.AddRange(page);
    Console.WriteLine($"Página: {page.Count} docs, RU: {page.RequestCharge}");
}
```

**SQL soportado:** SELECT, FROM, WHERE, ORDER BY, TOP, OFFSET LIMIT, GROUP BY, agregaciones (COUNT, SUM, AVG, MIN, MAX), funciones de cadena, matemáticas, arrays.

**SQL NO soportado:** JOIN entre containers (cada container es independiente), subqueries correlacionadas, UNION.

## Slide 11 — Niveles de consistencia

Cosmos DB ofrece 5 niveles de consistencia. La elección afecta latencia, disponibilidad y coste:

| Nivel | Garantía | Latencia | RU |
|-------|----------|:--------:|:--:|
| **Strong** | Lectura siempre devuelve la última escritura | Mayor | 2x |
| **Bounded Staleness** | Lecturas retrasan máx N versiones o T tiempo | Media-alta | 2x |
| **Session** (default) | Consistente dentro de la sesión del cliente | Media | 1x |
| **Consistent Prefix** | Lecturas nunca ven escrituras fuera de orden | Baja | 1x |
| **Eventual** | Sin garantías de orden ni recencia | Mínima | 1x |

**Session (por defecto) es la opción correcta para el 90% de los casos.** Garantiza que el usuario que escribió un dato lo ve inmediatamente, pero otro usuario puede ver una versión ligeramente antigua.

**Strong** dobla el coste de RU y añade latencia, pero garantiza que todos ven lo mismo. Solo usadlo si el negocio lo requiere (transacciones financieras, inventario crítico).

## Slide 12 — Change Feed: repaso rápido y buenas prácticas

Ya lo usáis con Azure Functions. Recordatorio de buenas prácticas:

**El Change Feed es un log de cambios ordered by partition, not globally.** Los cambios de la misma partición llegan en orden. Los cambios de diferentes particiones pueden llegar en cualquier orden relativo.

**Buenas prácticas:**
- Container de leases separado por cada consumidor
- Funciones idempotentes (at-least-once delivery)
- No depender del orden entre particiones
- Soft delete para "detectar" eliminaciones (Change Feed no las registra)
- MaxItemsPerInvocation para controlar el tamaño del batch

```csharp
// Soft delete
pedido.Eliminado = true;
pedido.EliminadoEn = DateTime.UtcNow;
await container.UpsertItemAsync(pedido);
// El Change Feed detecta la actualización → tu función puede reaccionar al campo "eliminado"
```

## Slide 13 — Indexing en Cosmos DB

Por defecto, Cosmos DB indexa TODAS las propiedades de todos los documentos. Esto hace que todas las queries sean rápidas, pero consume más RU en escrituras.

**Personalizar la política de indexación:**
```json
{
  "indexingMode": "consistent",
  "automatic": true,
  "includedPaths": [
    { "path": "/clienteId/?" },
    { "path": "/estado/?" },
    { "path": "/total/?" },
    { "path": "/creadoEn/?" }
  ],
  "excludedPaths": [
    { "path": "/items/*" },
    { "path": "/descripcion/?" },
    { "path": "/*" }
  ],
  "compositeIndexes": [
    [
      { "path": "/clienteId", "order": "ascending" },
      { "path": "/creadoEn", "order": "descending" }
    ]
  ]
}
```

**Regla:** Si tenéis documentos grandes con campos que nunca se consultan (descripción larga, arrays anidados), excluidlos del índice. Ahorra RU en escrituras.

**Composite indexes:** Necesarios para ORDER BY con múltiples campos.

## Slide 14 — Modelo de datos: desnormalización

En bases relacionales, normalizáis para evitar duplicación. En Cosmos DB, **desnormalizáis para optimizar lecturas**:

**Modelo relacional (SQL):**
```
Pedidos: { id, clienteId, fecha, total }
Clientes: { id, nombre, email }
Items: { id, pedidoId, productoId, cantidad }
→ Para mostrar un pedido completo: 3 JOINs
```

**Modelo Cosmos DB (desnormalizado):**
```json
{
  "id": "ped-001",
  "clienteId": "cli-001",
  "clienteNombre": "Pedro García",
  "clienteEmail": "pedro@empresa.com",
  "items": [
    { "productoId": "p-1", "nombre": "Laptop", "cantidad": 1, "precio": 999.99 },
    { "productoId": "p-2", "nombre": "Mouse", "cantidad": 2, "precio": 29.99 }
  ],
  "total": 1059.97,
  "creadoEn": "2025-06-15T10:30:00Z"
}
```
→ Para mostrar un pedido completo: 1 lectura, 1 RU.

**Trade-off:** Si el nombre del cliente cambia, hay que actualizarlo en todos sus pedidos. Pero si la query "obtener pedido completo" se ejecuta 10.000 veces al día y "cambiar nombre de cliente" se ejecuta 1 vez al año, la desnormalización gana por goleada.

## Slide 17 — Transacciones en Cosmos DB
Cosmos DB soporta transacciones ACID pero solo dentro de la misma partición lógica:

```csharp
var container = cosmosClient.GetContainer("tienda", "pedidos");
var partitionKey = new PartitionKey("cli-001");

var batch = container.CreateTransactionalBatch(partitionKey)
    .CreateItem(new { id = "ped-100", clienteId = "cli-001", total = 500m, estado = "confirmado" })
    .CreateItem(new { id = "mov-100", clienteId = "cli-001", tipo = "cargo", importe = -500m })
    .ReplaceItem("cli-001-saldo", new { id = "cli-001-saldo", clienteId = "cli-001", saldo = 1500m });

var response = await batch.ExecuteAsync();
if (response.IsSuccessStatusCode)
    Console.WriteLine($"Transacción OK. RU: {response.RequestCharge}");
else
    Console.WriteLine($"Transacción falló: {response.StatusCode}");
```

**Límites:** Máximo 100 operaciones o 2 MB por batch. Todos los documentos deben tener la misma PartitionKey. Si necesitáis transacciones cross-partition, usad el patrón Saga (módulo 4).

## Slide 18 — Stored Procedures y UDFs

```javascript
// Stored Procedure (JavaScript, se ejecuta en el servidor)
function crearPedidoConMovimiento(pedido, movimiento) {
    var context = getContext();
    var container = context.getCollection();
    var response = context.getResponse();
    
    container.createDocument(container.getSelfLink(), pedido, function(err, doc) {
        if (err) throw err;
        container.createDocument(container.getSelfLink(), movimiento, function(err, doc2) {
            if (err) throw err;
            response.setBody({ pedido: doc.id, movimiento: doc2.id });
        });
    });
}
```

**¿Cuándo stored procedures?** Solo cuando necesitáis lógica transaccional en el servidor que no puede hacerse con TransactionalBatch. Son JavaScript (no C#), difíciles de depurar y mantener. En la práctica, TransactionalBatch cubre el 95% de los casos.

## Slide 20 — Multi-region y distribución global

```bash
# Añadir región secundaria
az cosmosdb update --name cosmos-ventas-prod -g mi-rg \
  --locations regionName=westeurope failoverPriority=0 isZoneRedundant=true \
  --locations regionName=northeurope failoverPriority=1 isZoneRedundant=false

# Habilitar multi-region writes (cada región puede escribir)
az cosmosdb update --name cosmos-ventas-prod -g mi-rg --enable-multiple-write-locations true
```

**Single-region writes (por defecto):** Escrituras solo en la primaria. Lecturas en cualquier réplica. Failover automático si la primaria cae.

**Multi-region writes:** Cualquier región puede escribir. Latencia mínima para usuarios globales. Conflictos se resuelven con Last Writer Wins (LWW) por defecto.

**Para vuestro equipo:** Si todos los usuarios están en España, single-region con la primaria en West Europe o Spain Central es suficiente. Multi-region writes solo si tenéis usuarios distribuidos globalmente.

## Slide 21 — Cosmos DB: coste real y optimización

**Ejemplo de coste mensual (West Europe):**
| Config | RU/s | Storage | Coste aprox |
|--------|:----:|:-------:|:-----------:|
| Serverless (dev) | Variable | 5 GB | ~5€ |
| 400 RU/s (mínimo provisioned) | 400 | 10 GB | ~25€ |
| 1000 RU/s (app pequeña) | 1000 | 50 GB | ~60€ |
| 4000 RU/s (app media) | 4000 | 100 GB | ~230€ |
| Autoscale 400-4000 | 400-4000 | 100 GB | ~60-230€ |

**Autoscale vs Provisioned:**
- Provisioned: fijo, predecible, más barato si la carga es constante
- Autoscale: escala 1x-10x según demanda, pagas el máximo alcanzado por hora
- Serverless: pago por RU consumida, ideal para dev y cargas bajas

**Optimizaciones que más ahorran:**
1. Reads por ID en vez de queries → 1 RU vs 3-5 RU
2. Projection (solo campos necesarios) → menos RU por query
3. Partition key alineada con queries → single-partition vs cross-partition
4. Excluir campos grandes del índice → menos RU en writes

## Slide 22 — Patrones de modelado avanzado

**Patrón Reference (like relacional):**
```json
// pedidos/{pedidoId} - partitionKey: /clienteId
{ "id": "ped-001", "clienteId": "cli-001", "items": ["prod-001", "prod-002"], "total": 1299 }

// productos/{productoId} - partitionKey: /categoria
{ "id": "prod-001", "categoria": "electrónica", "nombre": "Laptop", "precio": 999 }
```
Pros: sin duplicación. Contras: 2 reads para un pedido completo.

**Patrón Embed (desnormalizado):**
```json
// pedidos/{pedidoId} - partitionKey: /clienteId
{ "id": "ped-001", "clienteId": "cli-001", "items": [
    { "productoId": "prod-001", "nombre": "Laptop", "precio": 999 },
    { "productoId": "prod-002", "nombre": "Mouse", "precio": 29.99 }
  ], "total": 1028.99 }
```
Pros: 1 read. Contras: duplicación si el producto cambia.

**Patrón Hybrid:** Embed datos estables (nombre, precio al momento de compra), reference datos que cambian (stock, disponibilidad).

**Regla:** Si el dato embebido cambia < 1% de las veces que se lee, embed. Si cambia frecuentemente, reference.

## Slide 23 — Vector Search en Cosmos DB (GA 2024)

Cosmos DB tiene búsqueda vectorial nativa para escenarios RAG/AI:

```bash
# Habilitar Vector Search en cuenta Cosmos
az cosmosdb update \
  --resource-group rg-curso \
  --name cosmos-curso \
  --capabilities EnableNoSQLVectorSearch
```

**Crear container con vector index:**
```csharp
var containerProperties = new ContainerProperties
{
    Id = "documentos",
    PartitionKeyPath = "/categoria",
    
    // Vector embedding policy
    VectorEmbeddingPolicy = new(new Collection<Embedding>
    {
        new Embedding
        {
            Path = "/embedding",
            DataType = VectorDataType.Float32,
            DistanceFunction = DistanceFunction.Cosine,
            Dimensions = 1536  // OpenAI text-embedding-ada-002
        }
    }),
    
    // Vector index
    IndexingPolicy = new IndexingPolicy
    {
        VectorIndexes = new()
        {
            new VectorIndexPath
            {
                Path = "/embedding",
                Type = VectorIndexType.QuantizedFlat  // o DiskANN
            }
        }
    }
};

await database.CreateContainerAsync(containerProperties, throughput: 4000);
```

**Insert documento con embedding:**
```csharp
public class Documento
{
    [JsonProperty("id")]
    public string Id { get; set; }
    
    [JsonProperty("categoria")]
    public string Categoria { get; set; }
    
    [JsonProperty("titulo")]
    public string Titulo { get; set; }
    
    [JsonProperty("contenido")]
    public string Contenido { get; set; }
    
    [JsonProperty("embedding")]
    public float[] Embedding { get; set; }  // 1536 dimensions
}

// Generar embedding con Azure OpenAI
var embeddingClient = new OpenAIClient(...);
var response = await embeddingClient.GetEmbeddingsAsync(
    new EmbeddingsOptions("text-embedding-ada-002", new[] { texto }));
var embedding = response.Value.Data[0].Embedding.ToArray();

await container.CreateItemAsync(new Documento
{
    Id = "doc-1",
    Categoria = "manual",
    Titulo = "Manual de seguridad",
    Contenido = texto,
    Embedding = embedding
});
```

**Vector search query:**
```csharp
var queryText = "¿Cómo configurar 2FA?";
var queryEmbedding = await GetEmbeddingAsync(queryText);

var query = new QueryDefinition(@"
    SELECT TOP 5
        c.id, c.titulo, c.contenido,
        VectorDistance(c.embedding, @vec) AS similarity
    FROM c
    WHERE c.categoria = @cat
    ORDER BY VectorDistance(c.embedding, @vec)")
    .WithParameter("@vec", queryEmbedding)
    .WithParameter("@cat", "manual");

var iterator = container.GetItemQueryIterator<DocumentoSearchResult>(query);
while (iterator.HasMoreResults)
{
    foreach (var doc in await iterator.ReadNextAsync())
    {
        Console.WriteLine($"{doc.Titulo} (similarity: {doc.Similarity})");
    }
}
```

**Hybrid search** (texto + vector):
```sql
SELECT TOP 10
    c.id, c.titulo,
    VectorDistance(c.embedding, @vec) AS vec_dist
FROM c
WHERE 
    CONTAINS(c.contenido, @keyword)  -- full-text filter
    AND VectorDistance(c.embedding, @vec) < 0.3
ORDER BY VectorDistance(c.embedding, @vec)
```

**Use cases:**
- RAG (Retrieval Augmented Generation) para chatbots
- Búsqueda semántica de productos
- Recommendation engines
- Image similarity (con embeddings de visión)

**Vs alternativas:**

| | Cosmos Vector | Azure AI Search | Pinecone |
|---|---|---|---|
| Setup | Single service | Aparte | Externa |
| Multi-region | ✅ Nativo | Single region | Limitada |
| Pricing | RU consumption | Search units | Per query |
| Hybrid query | ✅ SQL+vector | ✅ Especializado | Solo vector |
| Mejor para | App principal | Search dedicado | Vector-only |

## Slide 24 — Hierarchical Partition Keys

Feature 2024: partition keys con hasta 3 niveles de jerarquía:

```
Tradicional:
  /tenantId   → un solo nivel
  
Hierarchical:
  /tenantId/userId/sessionId   → tres niveles
```

**Crear container con HPK:**
```csharp
var containerProperties = new ContainerProperties
{
    Id = "events",
    PartitionKeyPaths = new List<string>
    {
        "/tenantId",   // Level 1
        "/userId",     // Level 2  
        "/sessionId"   // Level 3
    }
};

await database.CreateContainerAsync(containerProperties);
```

**Insert con full HPK:**
```csharp
var item = new EventDoc
{
    Id = "event-123",
    TenantId = "tenant-abc",
    UserId = "user-456",
    SessionId = "session-789",
    EventType = "click"
};

await container.CreateItemAsync(
    item,
    new PartitionKeyBuilder()
        .Add(item.TenantId)
        .Add(item.UserId)
        .Add(item.SessionId)
        .Build());
```

**Queries eficientes con HPK:**
```csharp
// Query a NIVEL 1 — todas las sesiones de un tenant
var query1 = new QueryDefinition("SELECT * FROM c");
var iterator1 = container.GetItemQueryIterator<EventDoc>(
    query1,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKeyBuilder()
            .Add("tenant-abc")
            .Build()  // solo tenantId
    });

// Query a NIVEL 2 — todas las sesiones de un user
var iterator2 = container.GetItemQueryIterator<EventDoc>(
    query1,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKeyBuilder()
            .Add("tenant-abc")
            .Add("user-456")
            .Build()
    });

// Query a NIVEL 3 — eventos de una sesión específica
var iterator3 = container.GetItemQueryIterator<EventDoc>(
    query1,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKeyBuilder()
            .Add("tenant-abc")
            .Add("user-456")
            .Add("session-789")
            .Build()
    });
```

**Por qué HPK es revolucionario para multi-tenant:**

```
Antes (single-level partition by tenantId):
├── Tenants pequeños: muchos en pocas particiones (OK)
├── Tenant gigante: una partición saturada (10GB limit)
└── No había escape: cambiar partition key = recrear

HPK (tenantId/userId/sessionId):
├── Datos distribuidos por las 3 dimensiones
├── Una partición lógica = combinación específica
├── Tenant grande con muchos users = bien distribuido
└── Queries a nivel tenant siguen siendo single-partition (eficiente)
```

**Cuándo usar HPK:**
- ✅ Multi-tenant SaaS (tenant + sub-entity)
- ✅ Datos con jerarquía natural (org/department/team)
- ✅ Time-series (year/month/day en lugar de timestamp único)
- ❌ No queries por nivel intermedio (no aprovecharías HPK)

**Limitación:** decidir HPK al crear container — no se puede cambiar después.

## Slide 25 — Continuous backup vs Periodic

Cosmos DB tiene 2 modos de backup:

```
┌─────────────────────────────────────────────────────────────────┐
│ PERIODIC BACKUP (default)                                       │
├─────────────────────────────────────────────────────────────────┤
│ Microsoft toma snapshots cada 4h                                │
│ Retención: 8 horas (default) hasta 30 días                      │
│ Restore: solo via support ticket (manual, lento)                │
│ Granularidad: cuenta entera o database                          │
│ Coste: incluido sin extra                                       │
│                                                                 │
│ Cuando usar: dev/test, datos no críticos                       │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ CONTINUOUS BACKUP ⭐ Recomendado producción                      │
├─────────────────────────────────────────────────────────────────┤
│ Snapshot continuo cada segundo                                  │
│ Retención: 7 días o 30 días (tier dependiente)                  │
│ Restore: self-service via Portal/CLI                            │
│ Granularidad: database, container, hasta point-in-time exacto   │
│ Coste: ~25% más por GB                                          │
│                                                                 │
│ Cuando usar: producción, datos críticos                        │
└─────────────────────────────────────────────────────────────────┘
```

**Habilitar Continuous Backup:**
```bash

  --name cosmos-curso-prod \
```

**Restore point-in-time:**
```bash

  --resource-group rg-curso \
  --target-database-account-name cosmos-curso-restored \
  --account-name cosmos-curso-prod \
  --restore-timestamp "2026-04-22T10:30:00Z" \
  --location westeurope \

```

**Use case real:**
```

13:50  Bug: app borra todos los pedidos del día
13:55  Detectado, app revertida pero datos perdidos
14:00  Restore a 13:44:59 → recovery completa
14:30  Datos validados, app de nuevo en producción
```

**Costes 2026:**
```
1 TB Cosmos DB en West Europe:
├── Periodic backup:   incluido (€0)
├── Continuous 7 días: ~€20/mes adicional
└── Continuous 30 días: ~€80/mes adicional
```

## Slide 26 — Materialized Views (preview 2025)

Vistas materializadas auto-actualizadas para queries optimizadas:

```
Container fuente: Pedidos (1M docs)
   │
   ▼
Materialized View: PedidosPorCliente
   ├── Pre-aggregated by cliente
   ├── Auto-updated cuando cambian los pedidos
   └── Queries: instant + RU bajo
```

**Crear materialized view:**
```bash
# Habilitar feature en la cuenta
az cosmosdb update \
  --resource-group rg-curso \
  --name cosmos-curso \
  --capabilities EnableMaterializedViews

# Crear container destino para la view
az cosmosdb sql container create \
  --account-name cosmos-curso \
  --database-name PedidosDb \
  --resource-group rg-curso \
  --name PedidosPorCliente \
  --partition-key-path /clienteId \
  --is-materialized-view true \
  --source-container-name Pedidos \
  --materialized-view-definition '
    SELECT 
      c.clienteId,
      COUNT(1) AS totalPedidos,
      SUM(c.importe) AS totalImporte,
      MAX(c.fecha) AS ultimoPedido
    FROM c
    GROUP BY c.clienteId'
```

**Cómo funciona:**
```
1. Cliente inserta pedido al container Pedidos
2. Cosmos detecta cambio
3. Material View Builder (background) actualiza la view
4. Query a la view devuelve datos actualizados
5. Lag típico: <1 segundo
```

**Casos de uso:**

| Escenario | Container fuente | Materialized View |
|---|---|---|
| Dashboard ventas | Orders (1M docs) | Sales by region/day |
| Catálogo + reviews | Products | Avg rating by product |
| Métricas user | Events | DAU/MAU stats |
| Inventory | Stock movements | Current stock by SKU |

**Comparativa con queries directas:**
```
Query directa:
  SELECT clienteId, COUNT(1) FROM Pedidos GROUP BY clienteId
  ├── Cross-partition query (caro)
  ├── 200 RU típico
  └── Latencia: 200-500ms

Query a materialized view:
  SELECT * FROM PedidosPorCliente WHERE clienteId = @id
  ├── Single-partition (clienteId es PK)
  ├── 3 RU típico
  └── Latencia: 5-10ms
```

**Trade-offs:**
- ✅ Queries más rápidas y baratas
- ✅ Auto-updated (eventual consistency)
- ❌ Storage extra (otra copia de datos)
- ❌ RU adicional para mantener la view
- ❌ Lag eventual (no real-time perfecto)

**Cuándo NO usar:**
- View cambia muy frecuentemente (background work agotador)
- Datos pequeños (overhead no compensa)
- Queries que cambian seguido (rebuild constante)

## Slide 27 — Burst Capacity: ahorrar en picos

Burst Capacity (GA 2023) permite usar más RU/s temporalmente sin pagar por adelantado:

```
Sin Burst:
└── Provisioned 1000 RU/s
    ├── Pico de tráfico necesita 1500 RU/s → 429 errors
    └── Solo opciones: scale up o suffer

Con Burst (default ON desde 2023):
└── Provisioned 1000 RU/s
    ├── Pico necesita 1500 RU/s
    ├── Burst usa hasta 10x = 10000 RU/s temporalmente
    ├── Burst capacity acumula durante 5 min de "no use"
    └── Sin throttling extra, sin cargo adicional
```

**Funciona así:**
```
Tiempo  | Usado RU/s | Provisioned | Burst available
────────┼────────────┼─────────────┼─────────────────
00:00   |    300     |    1000     |    +700/min × 5min = 3500 acumulado
01:00   |    300     |    1000     |    burst: 7000 acumulado
02:00   |    300     |    1000     |    burst: 10000 (cap) acumulado
03:00   |   2500     |    1000     |    usa 1500 extra = burst: 8500
04:00   |   1500     |    1000     |    usa 500 extra = burst: 8000
05:00   |    300     |    1000     |    burst: 8700 acumulado
```

**Calcular si tu workload se beneficia:**
```csharp
// En el SDK, ver cuánto burst se ha usado
ResponseMessage response = await container.UpsertItemStreamAsync(stream, partitionKey);
double rusConsumed = double.Parse(response.Headers["x-ms-request-charge"]);
double rusAvailable = double.Parse(response.Headers.GetValues("x-ms-bursting-units-available").FirstOrDefault() ?? "0");
double rusUsed = double.Parse(response.Headers.GetValues("x-ms-bursting-units-used").FirstOrDefault() ?? "0");

Console.WriteLine($"Burst used: {rusUsed}, available: {rusAvailable}");
```

**Ejemplo: caso real**
```
Aplicación e-commerce:
├── 90% del tiempo: 200 RU/s (browsing, searches)
├── 10% del tiempo (peak): 5000 RU/s (checkout rush, sales)
├── Provisioned tradicional: 5000 RU/s × €0.008/RU/h = €290/mes
└── Con Burst: 500 RU/s provisioned + burst para picos
    └── Coste: €29/mes (-90%)
```

**Activar/verificar:**
```bash
# Ya está enabled por default — verificar:
az cosmosdb sql container show \
  --resource-group rg-curso \
  --account-name cosmos-curso \
  --database-name PedidosDb \
  --name orders \
  --query "resource.{
    Throughput: options.throughput,
    ManualThroughput: options.manualThroughput,
    AutoscaleSettings: options.autoscaleSettings
  }"
```

**Limitaciones:**
- Solo aplica con throughput provisioned manual (no autoscale)
- Burst max = 10x provisioned (no infinito)
- Buffer agotado = 429 normales

**Combinado con autoscale:**
- Manual + Burst → mejor para workloads bursty conocidos
- Autoscale → mejor para crecimiento progresivo
- No se pueden combinar (autoscale ya tiene su lógica)

## Slide 28 — Multi-tenancy patterns en Cosmos

Diseñar para SaaS multi-tenant: 3 estrategias:

**1. Database per tenant** (aislamiento máximo, coste alto):
```
Account: cosmos-saas
├── tenant-abc-db
│   ├── orders, customers, products
├── tenant-xyz-db
│   ├── orders, customers, products
└── ...
```
- ✅ Aislamiento total
- ✅ Pricing per tenant claro
- ❌ N tenants = N × throughput minimum (caro)
- ❌ No queries cross-tenant

**2. Container per tenant** (aislamiento medio):
```
Account: cosmos-saas
└── shared-db
    ├── orders-tenant-abc
    ├── orders-tenant-xyz
    └── products-tenant-abc
```
- ✅ Aislamiento decente
- ✅ Comparten DB throughput
- ❌ Container por tenant + tipo de entidad = explosión

**3. Partition per tenant** (más eficiente, requiere disciplina):
```
Account: cosmos-saas
└── shared-db
    ├── orders (PK = /tenantId)
    │   ├── tenant-abc partition
    │   ├── tenant-xyz partition
    │   └── ...
    └── products (PK = /tenantId)
```
- ✅ Económico (compartir RU/s)
- ✅ Queries cross-tenant posibles si necesitas
- ❌ Requiere isolation lógica en código
- ❌ Tenant gigante puede saturar partition

**Híbrido recomendado para SaaS modernos** (HPK):
```
Account: cosmos-saas
└── shared-db
    └── orders (HPK = /tenantId/userId)
        ├── Tenants pequeños: comparten partitions
        ├── Tenants grandes: HPK distribuye
        └── Queries por tenant siguen siendo eficientes
```

**Implementación con isolation:**
```csharp
public class TenantContext
{
    public string TenantId { get; set; }
    
    // Helper: garantiza queries siempre filtradas por tenant
    public IQueryable<T> Query<T>(Container container) where T : class, ITenantOwned
    {
        return container.GetItemLinqQueryable<T>(
            requestOptions: new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(TenantId)
            })
            .Where(x => x.TenantId == TenantId);  // double check
    }
}

// Uso:
var orders = await _tenantContext.Query<Order>(_ordersContainer)
    .Where(o => o.Status == "pending")
    .ToListAsync();
// Imposible accidentalmente leer datos de otro tenant
```

**Audit/compliance:**
```sql
-- Auditoría: ¿alguien accedió fuera de su tenant?
SELECT * FROM CosmosDBAuditLogs
WHERE OperationName == 'ReadFeedItems'
  AND PartitionKey != UserClaim['TenantId']  -- mismatch
```

## Slide 29 — Cosmos NoSQL vs MongoDB API vs PostgreSQL API

Cosmos DB ofrece múltiples APIs para distinto público:

```
┌──────────────────────────────────────────────────────────────────┐
│  APIs DE COSMOS DB                                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  NoSQL (Core)        ⭐ Native, mejor performance, todas features │
│  └── SQL syntax for queries                                       │
│  └── .NET, Java, Python, JS first-class                           │
│  └── Vectores, hierarchical PK, materialized views                │
│                                                                   │
│  MongoDB API         Para apps existentes con MongoDB drivers     │
│  └── Wire protocol compatible (drivers MongoDB funcionan)         │
│  └── Soporta v3.6, v4.0, v4.2, v5.0                              │
│  └── Algunas features Mongo no soportadas (revisar matrix)        │
│                                                                   │
│  PostgreSQL API      ⭐ Newer (Citus distribuido)                  │
│  └── PostgreSQL completo + Citus para distribución                │
│  └── Para apps que necesitan PostgreSQL real                      │
│  └── Multi-region, scale horizontal                               │
│                                                                   │
│  Cassandra API       Para apps con CQL                            │
│  └── Wire protocol compatible                                     │
│                                                                   │
│  Gremlin API (graph) Para datos de grafo                          │
│  └── Apache Gremlin compatible                                    │
│                                                                   │
│  Table API           Para Storage Tables (legacy)                 │
│  └── Migration path desde Storage Tables                          │
└──────────────────────────────────────────────────────────────────┘
```

**Decisión:**

```
¿App nueva, sin legacy?
   → NoSQL API (mejor todo)

¿Migrating from MongoDB self-hosted?
   → MongoDB API (zero code change)
   → Después migrar a NoSQL si quieres más features

¿Migrating from PostgreSQL on-prem?
   → PostgreSQL API (lift-and-shift)
   → O Azure PostgreSQL Flexible Server (más simple)

¿Datos de grafo (relaciones complejas)?
   → Gremlin API o Neo4j en VM

¿Multi-tenant SaaS muy grande?
   → NoSQL con HPK + materialized views
```

**MongoDB API: ¿qué pierdes vs Mongo native?**

| Feature | MongoDB Native | Cosmos MongoDB API |
|---|:---:|:---:|
| Aggregation Pipeline | ✅ | ✅ (la mayoría) |
| Transactions multi-doc | ✅ | ✅ (within partition) |
| Change Streams | ✅ | ✅ |
| Sharding manual | ✅ | Automatic only |
| GridFS | ✅ | ❌ |
| Map-Reduce (deprecated) | ✅ | ❌ |
| Time-series collections | ✅ (5.0+) | Limited |

**Cuándo migrar de MongoDB API → NoSQL API:**
- Quieres usar Hierarchical Partition Keys
- Necesitas Vector Search (NoSQL only)
- Materialized Views
- Lower latency (NoSQL es más optimizado)

**Migración:**
```csharp
// Tools: Azure Cosmos DB Data Migration Tool
// O: dump-restore con mongodump/mongorestore + validation
// O: dual-write durante migration period
```

## Slide 31 — Patterns de modelado: 5 reales

Common patterns que veréis en producción:

**1. Embedding vs Referencing:**
```javascript
// EMBED (data junta) — para datos que se acceden juntos
{
  "id": "order-123",
  "customer": "Pedro García",
  "items": [
    { "product": "Laptop", "qty": 1, "price": 1200 },
    { "product": "Mouse", "qty": 2, "price": 25 }
  ],
  "total": 1250
}

// REFERENCE (separate documents) — para datos que cambian independiente
{
  "id": "order-123",
  "customerId": "cust-456",   // ← reference
  "itemIds": ["item-1", "item-2"]
}
```

**Regla:** embed si <100KB total y se lee siempre junto; reference si data > 100KB o cambia independientemente.

**2. Document type discriminator (multi-type collection):**
```javascript
// Mix de tipos en un container — útil para related data
{ "id": "1", "type": "customer", "name": "Pedro", ... }
{ "id": "2", "type": "address", "customerId": "1", "street": "..." }
{ "id": "3", "type": "order", "customerId": "1", "items": [...] }

// Query con discriminator
SELECT * FROM c WHERE c.customerId = "1"
// Devuelve customer + address + orders en una sola query
```

**3. Bucket pattern (time-series):**
```javascript
// En lugar de 1 doc per evento (caro)
{ "id": "evt-1", "deviceId": "dev-1", "timestamp": "2026-04-22T10:00:00Z", "value": 23.5 }

// Bucket: 1 doc por hora con array de eventos
{
  "id": "dev-1-2026-04-22-10",
  "deviceId": "dev-1",
  "hour": "2026-04-22T10:00:00Z",
  "events": [
    { "ts": "10:00:00", "value": 23.5 },
    { "ts": "10:00:30", "value": 23.7 },
    // ... 120 events for the hour
  ]
}
// Reads más eficientes (1 doc → 120 datapoints)
```

**4. Computed properties (aggregates pre-calculated):**
```javascript
{
  "id": "order-123",
  "items": [...],
  
  // Computed at write-time (denormalization)
  "totalAmount": 1250,
  "itemCount": 3,
  "avgItemPrice": 416.67
}
// Query no necesita SUM/COUNT — instant
```

**5. Wide table pattern (extending docs):**
```javascript
// Document que crece con el tiempo
{
  "id": "user-123",
  "core": {
    "name": "Pedro",
    "email": "p@ex.com"
  },
  "preferences": { "theme": "dark", "lang": "es" },
  "stats": { "loginCount": 542, "lastLogin": "..." },
  "subscription": { "plan": "pro", "renewedAt": "..." }
  // Add more fields as needed without schema migration
}
```

**Anti-pattern: don't do this:**
```javascript
// ❌ Schema demasiado normalizado (esto NO es SQL!)
{ "id": "1", "userId": "u1", "type": "preference", "key": "theme", "value": "dark" }
{ "id": "2", "userId": "u1", "type": "preference", "key": "lang", "value": "es" }
// 100 queries to assemble user preferences
```

## Slide 32 — Anti-patterns Cosmos: errores caros

Los más comunes y costosos:

```
❌ ANTI-PATTERN 1: Wrong partition key
   → Hot partitions, throttling, queries lentas
   ✅ Pensar PK al diseñar, distribución uniforme + access pattern

❌ ANTI-PATTERN 2: Cross-partition queries en cada request
   → SELECT * FROM c WHERE c.email = @e (sin PK)
   → Costoso (50+ RU vs 3 RU)
   ✅ Diseñar PK alineado con query patterns
   ✅ Materialized View si necesitas otra perspectiva

❌ ANTI-PATTERN 3: SELECT * everywhere
   → Más data, más RU, más slow
   ✅ Solo properties necesarias

❌ ANTI-PATTERN 4: Throughput a ojo
   → 400 RU "porque sí"
   ✅ Monitor Real RU/s usage durante 1 semana, dimensionar
   ✅ Autoscale para workloads variables

❌ ANTI-PATTERN 5: No retry policy en SDK
   → Transient throttles (429) fallan request
   ✅ SDK config con retries automáticos
       new CosmosClientOptions { 
           MaxRetryAttemptsOnRateLimitedRequests = 9,
           MaxRetryWaitTimeOnRateLimitedRequests = TimeSpan.FromSeconds(30)
       }

❌ ANTI-PATTERN 6: Documentos > 1 MB
   → Limit duro de Cosmos
   ✅ Splittear en sub-docs, bucket pattern, blob external

❌ ANTI-PATTERN 7: Indexing TODO por defecto
   → Writes lentos, RU alto
   ✅ Custom indexing policy: solo properties que querys

❌ ANTI-PATTERN 8: Eventually Consistent en transactional data
   → Race conditions, datos inconsistentes
   ✅ Strong consistency para escrituras críticas

❌ ANTI-PATTERN 9: Sin TTL = data growth infinito
   → Storage cost balloon
   ✅ TTL en docs efímeros (sessions, logs, cache)

❌ ANTI-PATTERN 10: Sin diagnostic settings
   → No saber qué pasa cuando falla
   ✅ Log Analytics + dashboards + alerts
```

**El más caro que he visto:**
```
Cliente con 50TB en Cosmos:
├── Indexing default: TODO indexed
├── Writes: 50 RU/doc (paga 200 RU)
├── Custom indexing: solo 3 properties
├── Writes: 8 RU/doc
├── Ahorro: 75% RU = €18K/año
└── Tiempo: 30 min de policy update
```

## Slide 33 — Cierre del submódulo
Cosmos DB es la base de datos más potente de Azure si la usáis bien. La partition key, el modelo de datos y la consistencia son las tres decisiones de diseño que determinan si vuestra experiencia es excelente o frustrante.

RU es la moneda: optimizad queries (read por ID, projection, single-partition), y usad autoscale para cargas variables. TTL para auto-limpieza, transactional batch para ACID, y Change Feed para reactivity.

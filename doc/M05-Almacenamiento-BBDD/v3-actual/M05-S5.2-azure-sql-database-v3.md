## Slide 2 — Qué es Azure SQL Database
Azure SQL Database es SQL Server como servicio PaaS. El motor es el mismo SQL Server que conocéis, pero Azure gestiona el OS, los parches, los backups, la replicación y el escalado.

**Lo que Azure gestiona:** OS, parches de seguridad, backups automáticos (hasta 35 días), alta disponibilidad, réplicas de lectura, cifrado en reposo.

**Lo que gestionas tú:** El schema (tablas, índices, stored procedures), las queries, la configuración de rendimiento (DTU/vCores), firewall de acceso, connection strings.

No es una VM con SQL Server instalado. Es un motor SQL Server nativo en la nube, optimizado para PaaS.

## Slide 4 — Modelos de compra: DTU vs vCore

**DTU (Database Transaction Unit):** Paquete predefinido de CPU + memoria + I/O. Simple de elegir.

| Tier | DTU | Storage | Precio aprox |
|------|:---:|:-------:|:------------:|
| Basic | 5 | 2 GB | ~4€/mes |
| S0 | 10 | 250 GB | ~13€/mes |
| S1 | 20 | 250 GB | ~25€/mes |
| S2 | 50 | 250 GB | ~63€/mes |
| P1 | 125 | 500 GB | ~380€/mes |

**vCore:** Eliges CPU y memoria por separado. Más control.

| Tier | vCores | RAM | Precio aprox |
|------|:------:|:---:|:------------:|
| General Purpose 2 | 2 | 10 GB | ~160€/mes |
| General Purpose 4 | 4 | 20 GB | ~320€/mes |
| Business Critical 2 | 2 | 10 GB | ~410€/mes |

**¿Cuál elegir?**
- Cargas predecibles y simples → DTU (más fácil de entender)
- Necesitáis control fino de CPU/RAM → vCore
- Necesitáis réplicas de lectura → Business Critical (vCore)

Para el curso y desarrollo: **S0 (10 DTU)** es suficiente.

## Slide 5 — Serverless tier: pago por uso real

Azure SQL tiene un tier serverless que escala automáticamente y se pausa cuando no hay actividad:

```bash
az sql db create \
  --server sql-ventas-dev \
  --resource-group rg-ventas-dev \
  --name db-ventas-dev \
  --edition GeneralPurpose \
  --family Gen5 \
  --capacity 2 \
  --compute-model Serverless \
  --auto-pause-delay 60  # Pausar tras 60 min sin actividad
```

**Cómo funciona:**
- Sin actividad durante 60 min → la DB se pausa (no pagas CPU)
- Llega una query → la DB se "despierta" (10-30 seg de cold start)
- Escala automáticamente entre 0.5 y N vCores según carga

**Ideal para:** Desarrollo, entornos de staging, apps con tráfico intermitente. **No ideal para:** Producción con latencia sensible (el cold start de despertar la DB es notable).

## Slide 7 — Entity Framework Core: el ORM

```csharp
// DbContext
public class VentasDbContext : DbContext
{
    public VentasDbContext(DbContextOptions<VentasDbContext> options) : base(options) { }
    
    public DbSet<Producto> Productos => Set<Producto>();
    public DbSet<Pedido> Pedidos => Set<Pedido>();
    
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Producto>(e =>
        {
            e.HasKey(p => p.Id);
            e.Property(p => p.Nombre).HasMaxLength(200).IsRequired();
            e.Property(p => p.Precio).HasColumnType("decimal(18,2)");
            e.HasIndex(p => p.Nombre);
        });
    }
}

// Operaciones CRUD
public class ProductoService
{
    private readonly VentasDbContext _db;
    
    public async Task<List<Producto>> ListarAsync()
        => await _db.Productos.OrderBy(p => p.Nombre).ToListAsync();
    
    public async Task<Producto?> GetAsync(int id)
        => await _db.Productos.FindAsync(id);
    
    public async Task<Producto> CrearAsync(Producto producto)
    {
        _db.Productos.Add(producto);
        await _db.SaveChangesAsync();
        return producto;
    }
}
```

## Slide 9 — Rendimiento: índices y query optimization

**Monitorizar queries lentas:**
```sql
-- Top 10 queries más costosas (en Azure SQL)
SELECT TOP 10
    qs.total_elapsed_time / qs.execution_count AS avg_time_ms,
    qs.execution_count,
    SUBSTRING(qt.text, 1, 200) AS query_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
ORDER BY avg_time_ms DESC;
```

**Azure SQL tiene recomendaciones automáticas:**
```bash
az sql db advisor list --server sql-ventas-prod -g mi-rg --database db-ventas --output table
```

Azure analiza las queries y sugiere: crear índices, eliminar índices no usados, parametrizar queries. Podéis habilitar auto-tuning para que aplique las recomendaciones automáticamente.

## Slide 10 — Connection pooling: rendimiento crítico

**El error más caro:** Crear una conexión nueva por cada petición.

```csharp
// MAL: nueva conexión cada vez
using var conn = new SqlConnection(connString);
await conn.OpenAsync();
// ... query
// conn se cierra y destruye

// BIEN: EF Core gestiona el pool automáticamente
// Solo registradlo en DI una vez:
builder.Services.AddDbContext<VentasDbContext>(options =>
    options.UseSqlServer(connString));
// EF Core reutiliza conexiones del pool
```

**Configurar pool en connection string:**
```
...;Max Pool Size=100;Min Pool Size=5;Connection Lifetime=300;
```

Azure SQL tiene un límite de conexiones por tier. S0 = 60 conexiones simultáneas. Si agotáis el pool, las queries empiezan a fallar con "Login failed due to resource limit".

## Slide 11 — Backups automáticos

Azure SQL hace backups automáticos sin configuración:

| Tipo | Frecuencia | Retención |
|------|:----------:|:---------:|
| Full backup | Semanal | 7-35 días (según tier) |
| Differential | Cada 12-24h | Mismo |
| Transaction log | Cada 5-10 min | Mismo |

```bash
# Ver backups disponibles
az sql db ltr-backup list --server sql-ventas-prod -g mi-rg --database db-ventas

# Restaurar a un punto en el tiempo (point-in-time restore)
az sql db restore \
  --server sql-ventas-prod -g mi-rg \
  --name db-ventas-restored \
  --dest-name db-ventas-restored \
  --time "2025-06-15T14:30:00Z"
```

**Point-in-time restore** es la feature más valiosa: podéis restaurar la DB a cualquier segundo de los últimos 7-35 días. Si alguien ejecuta un DELETE sin WHERE a las 15:00, restauráis a las 14:59.

## Slide 12 — Azure SQL vs Cosmos DB: cuándo usar cada uno

| Criterio | Azure SQL | Cosmos DB |
|----------|:---------:|:---------:|
| Modelo de datos | Relacional (tablas, filas, SQL) | Documentos JSON, key-value, graph |
| Schema | Fijo (migraciones) | Flexible (schema-free) |
| Queries | SQL completo (JOIN, GROUP BY) | SQL limitado (sin JOINs cross-partition) |
| Transacciones | ACID completas | ACID por partición |
| Escalado | Vertical (más DTU/vCores) | Horizontal (más RU, más particiones) |
| Distribución global | Geo-replicación (read replicas) | Multi-region writes nativo |
| Latencia | ~5-20ms | ~5-10ms (single-digit) |
| Coste mínimo | ~4€/mes (Basic) | ~25€/mes (400 RU) o free tier |

**Regla simple:**
- Datos con relaciones claras, JOINs complejos, transacciones ACID → **SQL**
- Documentos JSON, alta escala, distribución global, Change Feed → **Cosmos DB**
- Ambos pueden coexistir: SQL para datos transaccionales, Cosmos para datos de alta lectura

## Slide 13 — Resiliencia de conexión con EF Core
Las conexiones a Azure SQL pueden fallar temporalmente (transient errors). EF Core tiene retry automático:

```csharp
builder.Services.AddDbContext<VentasDbContext>(options =>
    options.UseSqlServer(connectionString, sqlOptions =>
    {
        sqlOptions.EnableRetryOnFailure(
            maxRetryCount: 5,
            maxRetryDelay: TimeSpan.FromSeconds(30),
            errorNumbersToAdd: new List<int> { 4060, 40197, 40501, 40613, 49918, 49919, 49920 });
        sqlOptions.CommandTimeout(60);
    }));
```

Los error numbers son los códigos de transient errors de Azure SQL. EF Core los reintenta automáticamente con backoff. Sin esto, vuestra app falla ante cualquier blip de red.

## Slide 16 — Auto-tuning: Azure optimiza por ti

```bash
# Habilitar auto-tuning
az sql db update --server sql-ventas-prod -g mi-rg --name db-ventas \
  --set createIndex=on dropIndex=on forceLastGoodPlan=on
```

**Qué hace:**
- **Create Index:** Detecta queries lentas y crea índices automáticamente
- **Drop Index:** Elimina índices que no se usan (ahorran espacio y aceleran writes)
- **Force Last Good Plan:** Si SQL Server elige un plan de ejecución peor que el anterior, vuelve al bueno

Azure SQL analiza vuestras queries 24/7 y aplica optimizaciones. Es como tener un DBA automático.

## Slide 17 — Elastic Pool: compartir recursos entre DBs

Si tenéis varias bases de datos pequeñas, un Elastic Pool comparte DTU/vCores entre ellas:

```bash
az sql elastic-pool create \
  --server sql-ventas-prod -g mi-rg \
  --name pool-ventas \
  --edition Standard --dtu 100 --db-dtu-max 50 --db-dtu-min 5

# Mover DB al pool
az sql db update --server sql-ventas-prod -g mi-rg --name db-ventas \
  --elastic-pool pool-ventas
```

**Ejemplo:** 5 bases de datos que individualmente necesitarían S1 (10 DTU = 13€/mes = 65€/mes total). En un pool de 50 DTU (~50€/mes), las 5 comparten los DTU — más barato si no todas están al máximo a la vez.

## Slide 18 — Geo-replicación y failover

```bash
# Crear réplica de lectura en otra región
az sql db replica create \
  --server sql-ventas-prod -g rg-ventas-prod --name db-ventas \
  --partner-server sql-ventas-dr --partner-resource-group rg-ventas-dr

# Crear failover group (failover automático)
az sql failover-group create \
  --server sql-ventas-prod -g rg-ventas-prod \
  --name fg-ventas \
  --partner-server sql-ventas-dr --partner-resource-group rg-ventas-dr \
  --failover-policy Automatic --grace-period 60 \
  --add-db db-ventas
```

**Con Failover Group:** La connection string usa el nombre del grupo (`fg-ventas.database.windows.net`). Si la región primaria cae, Azure redirige automáticamente al secundario. Sin cambiar la connection string de tu app.

| | Azure SQL DB | SQL Managed Instance | SQL Server en VM |
|---|:---:|:---:|:---:|

## Slide 21 — Hyperscale tier: la opción "infinita"

Hyperscale es un tier especial de Azure SQL para BBDD muy grandes (hasta 100 TB):

```
Servive tiers de Azure SQL DB:

┌────────────────┬───────────────┬───────────────────────────────────┐
│ Tier           │ Max size      │ Casos                             │
├────────────────┼───────────────┼───────────────────────────────────┤
│ Basic          │ 2 GB          │ Dev/test, small apps              │
│ Standard       │ 1 TB          │ Small-medium prod                 │
│ Premium        │ 4 TB          │ High IOPS, low latency            │
│ Business Crit. │ 4 TB          │ Always On, fast failover          │
│ Hyperscale     │ 100 TB ⭐     │ Large databases, unbounded growth │
│ Serverless     │ 1 TB          │ Sporadic workloads                │
└────────────────┴───────────────┴───────────────────────────────────┘
```

**Crear Hyperscale:**
```bash
az sql db create \
  --resource-group rg-curso \
  --server sql-curso \
  --name db-grande \
  --edition Hyperscale \
  --family Gen5 \
  --capacity 4 \
  --read-replicas 2  # secondary read-only replicas
```

**Características únicas:**

```
✅ Storage hasta 100 TB (creciendo según uses)
✅ Backup en segundos (snapshot-based, no copia datos)
✅ Restore en minutos (de snapshots)
✅ Read replicas: 0-4 (escalado de lectura)
✅ Compute scale up/down: minutos
✅ Storage compute desacoplados
✅ No hay tempdb limit (el de tu tier)

❌ No soporta: long-term retention diferente
❌ No soporta: Failover groups con Geo-replication
❌ No soporta: Database copy
❌ Migración: One-way (puedes ir a Hyperscale, pero no volver)
```

**Cuándo usar Hyperscale:**
- DBs > 1 TB que crecen rápido
- Necesitáis ramp-up rápido de compute
- Read scaling con múltiples replicas
- Backup/restore muy rápido es crítico

**Cuándo NO:**
- DBs < 100 GB (overkill, más caro)
- Necesitáis features que Hyperscale no soporta
- Workload muy bursty con periodos largos idle (Serverless mejor)

**Coste comparativo:**
```
1 TB Database:
├── Standard:    €450/mes
├── Premium:     €1100/mes
├── Bus.Critical:€1400/mes
└── Hyperscale:  €380/mes (compute) + €0.115/GB (storage)
                ≈ €495/mes (1TB) — competitive
```

**Migration to Hyperscale:**
```bash
# Cambiar tier (online, ~30 min para DB 100GB)
az sql db update \
  --resource-group rg-curso \
  --server sql-curso \
  --name db-existing \
  --edition Hyperscale \
  --family Gen5 \
  --capacity 4
# Datos se migran en background, app sigue funcionando
```

## Slide 22 — JSON nativo + Vector Search 2025

Azure SQL desde 2024 tiene soporte first-class para JSON y vectores (RAG, AI):

**JSON nativo (mejorado 2024):**
```sql
-- Tipo nativo JSON (antes: NVARCHAR(MAX))
CREATE TABLE Productos (
    Id INT PRIMARY KEY,
    Nombre NVARCHAR(100),
    Atributos JSON  -- ⭐ tipo nativo, validado, indexable
);

-- Insert
INSERT INTO Productos VALUES (
    1,
    'Laptop Pro',
    '{"cpu":"M3","ram":16,"specs":{"display":"14inch","battery":"18h"}}'
);

-- Query JSON path
SELECT 
    Nombre,
    JSON_VALUE(Atributos, '$.cpu') AS CPU,
    JSON_VALUE(Atributos, '$.specs.display') AS Display,
    JSON_QUERY(Atributos, '$.specs') AS SpecsObject
FROM Productos
WHERE JSON_VALUE(Atributos, '$.ram') > 8;

-- Update JSON
UPDATE Productos
SET Atributos = JSON_MODIFY(Atributos, '$.specs.battery', '20h')
WHERE Id = 1;

-- Index sobre JSON property (computed column)
ALTER TABLE Productos
ADD CpuIndexed AS JSON_VALUE(Atributos, '$.cpu') PERSISTED;

CREATE INDEX IX_Cpu ON Productos(CpuIndexed);
```

**Vector Search (GA Marzo 2025):**
```sql
-- Crear tabla con columna VECTOR
CREATE TABLE Documentos (
    Id INT PRIMARY KEY,
    Titulo NVARCHAR(200),
    Contenido NVARCHAR(MAX),
    Embedding VECTOR(1536)  -- ⭐ tamaño típico OpenAI ada-002
);

-- Insertar embedding (generado por OpenAI/Azure AI)
INSERT INTO Documentos VALUES (
    1,
    'Manual de seguridad',
    'Contenido completo del manual...',
    '[0.012, -0.034, 0.567, ...]'  -- 1536 dimensions
);

-- Búsqueda por similaridad (cosine)
DECLARE @QueryEmbedding VECTOR(1536) = '[0.011, -0.030, ...]';

SELECT TOP 5
    Id, Titulo,
    VECTOR_DISTANCE('cosine', Embedding, @QueryEmbedding) AS Similarity
FROM Documentos
ORDER BY Similarity ASC;  -- closest first

-- Crear índice vectorial (DiskANN)
CREATE VECTOR INDEX IX_Embedding 
ON Documentos(Embedding)
WITH (METRIC = 'cosine', TYPE = 'diskann', NEIGHBORS = 32);
```

**Use cases:**

| Caso | Antes | Ahora |
|---|---|---|
| Productos con specs variables | NoSQL aparte | JSON column en SQL |
| RAG (chat sobre tu data) | Vector DB aparte (Pinecone) | Vectors en SQL |
| Hybrid search (texto + vector) | 2 sistemas | 1 query SQL |
| Audit logs estructurados | Logs externos | JSON en SQL |

**Función completa RAG en SQL:**
```sql
-- Búsqueda híbrida: texto + similaridad vectorial
WITH textos_relevantes AS (
    SELECT Id, Titulo, Contenido,
           CONTAINS(Contenido, 'seguridad informática') as text_match,
           VECTOR_DISTANCE('cosine', Embedding, @query_vector) as vector_dist
    FROM Documentos
)
SELECT TOP 10 *
FROM textos_relevantes
WHERE text_match = 1 OR vector_dist < 0.3
ORDER BY 
    CASE WHEN text_match = 1 THEN 0 ELSE 1 END,
    vector_dist ASC;
```

## Slide 23 — Always Encrypted: cifrado client-side transparente

Para columnas con datos sensibles (SSN, tarjetas, salud), Always Encrypted cifra **antes** de salir del cliente:

```
Cliente (vuestra app)              Azure SQL Database
┌────────────────────┐            ┌────────────────────┐
│  Plaintext: SSN    │            │  Ciphertext stored │
│  "123-45-6789"     │            │  "0xa3F..."        │
│  ┌──────────┐      │   TLS      │                    │
│  │ Driver   │ ──── encrypt ───▶ │  Microsoft NUNCA   │
│  │ encrypts │      │            │  ve plaintext      │
│  └──────────┘      │            │                    │
│   Key in CMK       │            │  DBA NUNCA ve      │
│   (Key Vault)      │            │  plaintext         │
└────────────────────┘            └────────────────────┘
```

**Setup:**
```sql
-- 1. Crear Column Master Key (referencia a Key Vault)
CREATE COLUMN MASTER KEY MyCMK
WITH (
    KEY_STORE_PROVIDER_NAME = 'AZURE_KEY_VAULT',
    KEY_PATH = 'https://kv-curso.vault.azure.net/keys/cmk-pii/abc123'
);

-- 2. Crear Column Encryption Key (cifrada con CMK)
CREATE COLUMN ENCRYPTION KEY MyCEK
WITH VALUES (
    COLUMN_MASTER_KEY = MyCMK,
    ALGORITHM = 'RSA_OAEP',
    ENCRYPTED_VALUE = 0x01700000016C00...
);

-- 3. Cifrar columna (al crear tabla)
CREATE TABLE Pacientes (
    Id INT PRIMARY KEY,
    Nombre NVARCHAR(100),
    SSN VARCHAR(11) COLLATE Latin1_General_BIN2 ENCRYPTED WITH (
        COLUMN_ENCRYPTION_KEY = MyCEK,
        ENCRYPTION_TYPE = DETERMINISTIC,  -- permite búsqueda exacta
        ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256'
    ),
    HistorialMedico NVARCHAR(MAX) ENCRYPTED WITH (
        COLUMN_ENCRYPTION_KEY = MyCEK,
        ENCRYPTION_TYPE = RANDOMIZED,  -- solo INSERT/UPDATE/SELECT, no WHERE
        ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256'
    )
);
```

**Connection string:**
```csharp
// Connection string con Always Encrypted
var connStr = "Server=tcp:sql-curso.database.windows.net;" +
              "Database=Hospital;Authentication=Active Directory Default;" +
              "Column Encryption Setting=Enabled;" +
              "Attestation Protocol=AAS;" +
              "Enclave Attestation Url=https://sharedweu.weu.attest.azure.net/attest/SgxEnclave";

using var conn = new SqlConnection(connStr);
await conn.OpenAsync();

// Insert: el driver cifra automáticamente
using var cmd = new SqlCommand(
    "INSERT INTO Pacientes (Id, Nombre, SSN) VALUES (@id, @n, @ssn)", conn);
cmd.Parameters.AddWithValue("@id", 1);
cmd.Parameters.AddWithValue("@n", "Pedro García");
cmd.Parameters.AddWithValue("@ssn", "123-45-6789");  // se cifra antes de enviar
await cmd.ExecuteNonQueryAsync();

// Select: el driver descifra automáticamente
using var reader = await new SqlCommand(
    "SELECT Nombre, SSN FROM Pacientes WHERE Id = @id", conn).ExecuteReaderAsync();
// reader["SSN"] devuelve "123-45-6789" (descifrado en cliente)
```

**Tipos de encryption:**

| Tipo | Permite | Uso |
|---|---|---|
| **DETERMINISTIC** | Equality search, JOIN, GROUP BY | Email, SSN, IDs |
| **RANDOMIZED** | Solo INSERT/SELECT | Datos sensibles sin búsqueda |

**Always Encrypted with secure enclaves** (más nuevo):
- Permite operaciones más complejas (LIKE, range queries) sobre datos cifrados
- Requiere Intel SGX en server (Premium tier)
- Compliance ultra-estricto

**Trade-offs:**
- ✅ Microsoft no puede leer datos (zero-trust real)
- ✅ DBA roles separados de data access
- ❌ Performance impact (~2-3x más lento)
- ❌ Algunas queries no funcionan
- ❌ Setup complejo

## Slide 24 — Ledger tables: blockchain en SQL

Ledger es una feature de Azure SQL que provee **immutability + cryptographic verification** (compliance):

```sql
-- Crear tabla updatable ledger (audit + immutable history)
CREATE TABLE Transacciones (
    Id INT PRIMARY KEY,
    Cuenta VARCHAR(20),
    Importe DECIMAL(18,2),
    Fecha DATETIME2,
    
    -- Generated by ledger
    [ledger_start_transaction_id] BIGINT GENERATED ALWAYS AS TRANSACTION_ID START HIDDEN,
    [ledger_end_transaction_id] BIGINT GENERATED ALWAYS AS TRANSACTION_ID END HIDDEN,
    [ledger_start_sequence_number] BIGINT GENERATED ALWAYS AS SEQUENCE_NUMBER START HIDDEN,
    [ledger_end_sequence_number] BIGINT GENERATED ALWAYS AS SEQUENCE_NUMBER END HIDDEN,
    
    PERIOD FOR SYSTEM_TIME ([ledger_start_transaction_id], [ledger_end_transaction_id])
)
WITH (
    LEDGER = ON (
        APPEND_ONLY = OFF,
        LEDGER_VIEW = TransaccionesLedgerView
    )
);

-- Append-only ledger table (solo INSERT, immutable)
CREATE TABLE LogAuditoria (
    Id INT IDENTITY PRIMARY KEY,
    Usuario VARCHAR(100),
    Accion NVARCHAR(500),
    Timestamp DATETIME2 DEFAULT GETUTCDATE()
)
WITH (LEDGER = ON (APPEND_ONLY = ON));
```

**Cómo funciona el ledger:**
```
Cada modificación (INSERT/UPDATE/DELETE):
├── 1. Se ejecuta normalmente
├── 2. Hash criptográfico del cambio se calcula
├── 3. Hash se añade a Merkle tree
├── 4. Database digest se actualiza
└── 5. Digest puede publicarse a:
    ├── Azure Confidential Ledger (servicio Azure)
    ├── Azure Storage (write-once container)
    └── Tu propio sistema externo
```

**Verificar integridad:**
```sql
-- ¿Han manipulado los datos?
EXEC sp_verify_database_ledger '{
    "block_id": 0,
    "block_size": 6,
    "digest": "0xABC..."
}';

-- Si alguien (incluido un DBA con sysadmin) modificó datos
-- saltándose el ledger, esta verificación FALLA
```

**Query histórico de cambios:**
```sql
-- Ver TODAS las versiones de una fila
SELECT * FROM Transacciones FOR SYSTEM_TIME ALL
WHERE Id = 1
ORDER BY ledger_start_transaction_id;

-- Ver quién modificó qué (con la ledger view)
SELECT 
    UserName,
    TransactionId,
    LedgerOperationType,  -- 1=INSERT, 2=DELETE
    Cuenta, Importe
FROM TransaccionesLedgerView
WHERE Cuenta = 'ES1234567890'
ORDER BY TransactionId;
```

**Casos de uso reales:**

| Sector | Aplicación |
|---|---|
| Banca | Transactions log inmutable |
| Sanidad | Historial clínico verificable |
| Gov | Registro de propiedades |
| Supply chain | Trazabilidad productos |
| Audit | Logs que no se pueden alterar |

**Vs blockchain dedicada:**
- ✅ Same SQL skills, no learning curve
- ✅ Performance similar a SQL normal
- ✅ Sin transaction fees
- ❌ No descentralizado (depende de Azure)
- ❌ Solo applicable a un punto único de truth

## Slide 26 — Query Store: ver qué pasa con tus queries

Query Store es como "AppInsights para SQL" — tracking automático de queries:

```sql
-- Habilitar Query Store (default ON en Azure SQL)
ALTER DATABASE PedidosDb SET QUERY_STORE = ON
(
    OPERATION_MODE = READ_WRITE,
    DATA_FLUSH_INTERVAL_SECONDS = 900,
    INTERVAL_LENGTH_MINUTES = 60,
    MAX_STORAGE_SIZE_MB = 1000,
    QUERY_CAPTURE_MODE = AUTO  -- captura queries con uso significativo
);

-- Top 10 queries por consumo de CPU
SELECT TOP 10
    qsq.query_id,
    qsqt.query_sql_text,
    SUM(rs.count_executions) AS TotalExecutions,
    SUM(rs.avg_cpu_time * rs.count_executions) / 1000 AS TotalCpuMs,
    AVG(rs.avg_duration) / 1000 AS AvgDurationMs
FROM sys.query_store_query qsq
JOIN sys.query_store_query_text qsqt ON qsq.query_text_id = qsqt.query_text_id
JOIN sys.query_store_plan qsp ON qsq.query_id = qsp.query_id
JOIN sys.query_store_runtime_stats rs ON qsp.plan_id = rs.plan_id
WHERE rs.last_execution_time > DATEADD(hour, -1, GETUTCDATE())
GROUP BY qsq.query_id, qsqt.query_sql_text
ORDER BY TotalCpuMs DESC;

-- Queries que han REGRESADO en performance (más lentas que antes)
SELECT 
    qsqt.query_sql_text,
    AVG(CASE WHEN qsrs.first_execution_time > DATEADD(day, -7, GETUTCDATE()) 
             THEN qsrs.avg_duration ELSE NULL END) AS recent_avg,
    AVG(CASE WHEN qsrs.first_execution_time <= DATEADD(day, -7, GETUTCDATE()) 
             THEN qsrs.avg_duration ELSE NULL END) AS historical_avg
FROM sys.query_store_runtime_stats qsrs
JOIN sys.query_store_plan qsp ON qsrs.plan_id = qsp.plan_id
JOIN sys.query_store_query qsq ON qsp.query_id = qsq.query_id
JOIN sys.query_store_query_text qsqt ON qsq.query_text_id = qsqt.query_text_id
GROUP BY qsqt.query_sql_text
HAVING AVG(CASE WHEN qsrs.first_execution_time > DATEADD(day, -7, GETUTCDATE()) 
                THEN qsrs.avg_duration ELSE NULL END) > 
       AVG(CASE WHEN qsrs.first_execution_time <= DATEADD(day, -7, GETUTCDATE()) 
                THEN qsrs.avg_duration ELSE NULL END) * 1.5;
```

**Forced plans (workaround para regression):**
```sql
-- Hay query con plan A (rápido) y plan B (lento, optimizer eligió mal)
-- Forzar al optimizer a usar siempre el plan A:

EXEC sp_query_store_force_plan @query_id = 1234, @plan_id = 5678;

-- Quitar el plan forzado
EXEC sp_query_store_unforce_plan @query_id = 1234, @plan_id = 5678;
```

**Portal:**
```
SQL Database → Query Performance Insight
├── Top resource consuming queries
├── Long running queries
├── Custom: queries that regressed
└── Recommendations: indexes to create/drop
```

**Real-world workflow:**
```
Lunes:  Deploy nuevo feature
Martes: App lenta, users quejándose
        → Query Store muestra query nueva consumiendo 80% CPU
        → SQL plan exhibits missing index
        → Crear index sugerido
        → CPU drops 95%
        → Crisis evitada
```

## Slide 28 — Elastic Pool: economía de escala para muchas BBDD

Si tenéis 20+ DBs pequeñas, es más barato compartir recursos:

```
Escenario sin pool: 20 DBs Standard S1 (10 DTU c/u)
├── Cada DB: 10 DTU
├── Total: 200 DTU comprados
├── Pero: solo 5-6 DBs están activas a la vez
└── Coste: 20 × €15 = €300/mes

Escenario con pool: 20 DBs en Standard 50 DTU pool
├── Pool: 50 DTU compartidos
├── Cualquier DB puede usar 0-50 DTU según necesidad
├── Promedio: 30 DTU usados, 20 disponibles
└── Coste: €60/mes (-80%)
```

**Crear pool:**
```bash
# 1. Crear pool
az sql elastic-pool create \
  --resource-group rg-curso \
  --server sql-curso \
  --name pool-multitenancy \
  --edition Standard \
  --capacity 50 \
  --db-min-capacity 0 \
  --db-max-capacity 50

# 2. Mover DBs existentes al pool
az sql db update \
  --resource-group rg-curso \
  --server sql-curso \
  --name customer-001 \
  --elastic-pool pool-multitenancy

# 3. Crear nuevas DBs en el pool
az sql db create \
  --resource-group rg-curso \
  --server sql-curso \
  --name customer-021 \
  --elastic-pool pool-multitenancy
```

**Casos ideales:**

| Caso | Beneficio |
|---|---|
| Multi-tenant SaaS (1 DB por cliente) | Pool absorbe picos individuales |
| Dev environments (10 devs × 5 DBs) | Solo paga por DTU efectivos |
| Migración legacy (muchas BBDD pequeñas) | Lift-and-shift económico |
| Microservices con DB cada uno | Comparten compute |

**Anti-pattern:**
```
20 DBs todas con tráfico simultáneo de 50 DTU
→ Pool de 50 DTU se ahoga
→ Mejor: pool de 100 DTU (más caro pero suficiente)
   o DBs individuales de 10 DTU c/u
```

**Monitoring del pool:**
```sql
-- Ver uso del pool
SELECT 
    elastic_pool_name,
    AVG(avg_cpu_percent) as AvgCPU,
    MAX(avg_cpu_percent) as MaxCPU,
    AVG(avg_data_io_percent) as AvgIO,
    AVG(used_storage_mb) as AvgStorageMB
FROM sys.elastic_pool_resource_stats
WHERE start_time > DATEADD(hour, -24, GETUTCDATE())
GROUP BY elastic_pool_name;

-- ¿Qué DB consume más en este momento?
SELECT 
    database_name,
    avg_cpu_percent,
    max_dtu_percent,
    avg_log_write_percent
FROM sys.dm_db_resource_stats
ORDER BY end_time DESC;
```

**Pricing tip:** monitorizar 2-4 semanas el patrón real, luego dimensionar el pool. Empezar con 70% del peak teórico.

## Slide 29 — Geo-replication + Failover Groups

Para DR (disaster recovery) automatizado:

```
Active geo-replication:
West Europe              North Europe
┌──────────┐    sync     ┌──────────┐
│ PRIMARY  │ ──────────▶ │ READABLE │
│  read+wr │             │ SECONDARY│
│          │             │ (read-only)│
└──────────┘             └──────────┘

Si West Europe cae:
├── Manual failover required
├── Secondary se vuelve PRIMARY
├── Apps deben reconfigurar connection
└── RTO: minutos
```

**Setup geo-replication:**
```bash
# Crear secondary readable
az sql db replica create \
  --resource-group rg-curso \
  --server sql-curso \
  --name PedidosDb \
  --partner-server sql-curso-northeu \
  --partner-resource-group rg-curso-northeu

# Failover manual cuando primary cae
az sql db replica set-primary \
  --resource-group rg-curso-northeu \
  --server sql-curso-northeu \
  --name PedidosDb
```

**Failover Groups (más recomendado):**
```bash
# Failover Group abstrae el endpoint
az sql failover-group create \
  --resource-group rg-curso \
  --server sql-curso \
  --name fog-pedidos \
  --partner-server sql-curso-northeu \
  --add-db PedidosDb \
  --failover-policy Automatic \
  --grace-period 1  # horas antes de auto-failover
```

**Endpoints automatic:**
```
fog-pedidos.database.windows.net          → Primary (read/write)
fog-pedidos.secondary.database.windows.net → Secondary (read-only)
```

**Ventajas Failover Groups:**
- ✅ DNS-based routing (no reconfigurar apps)
- ✅ Auto-failover policy (grace period configurable)
- ✅ Múltiples DBs en el mismo group
- ✅ Server-level: incluye logins, firewall rules
- ❌ Solo dos regiones (primary + secondary)

**Aplicación con conexión read-only para queries no críticas:**
```csharp
// Connection string para writes
var primaryConn = "Server=fog-pedidos.database.windows.net;...";

// Connection string para reads (puede ir a secondary)
var readOnlyConn = "Server=fog-pedidos.secondary.database.windows.net;ApplicationIntent=ReadOnly;...";

// Use read replica para reports/analytics (offload primary)
public async Task<List<SalesReport>> GetSalesReportAsync()
{
    using var conn = new SqlConnection(_readOnlyConn);  // ← read replica
    return await conn.QueryAsync<SalesReport>("SELECT ... heavy query ...");
}

public async Task CreateOrderAsync(Order order)
{
    using var conn = new SqlConnection(_primaryConn);  // ← primary
    await conn.ExecuteAsync("INSERT ...");
}
```

**Costes:**
- Secondary se factura como otra DB del mismo tier
- 2x SQL costs aprox
- Plus: cross-region data transfer

## Slide 31 — Anti-patterns SQL en Azure

Errores caros que veo repetir:

```
❌ ANTI-PATTERN 1: Connection per request
   var conn = new SqlConnection(...); conn.Open();  // cada request
   → Pool exhaustion, slow
   ✅ Pool habilitado por defecto si reusas connection string

❌ ANTI-PATTERN 2: SELECT * everywhere
   → Más data over network, más memory, más slow
   ✅ Solo columns que necesitas

❌ ANTI-PATTERN 3: ORM lazy loading sin pensar
   foreach (var pedido in db.Pedidos)
       Console.WriteLine(pedido.Cliente.Nombre);  // N+1 query
   ✅ Include() explícito o projections

❌ ANTI-PATTERN 4: Sin retry policy
   → Transient errors fallan request
   ✅ AddDbContext().UseSqlServer(opts => opts.EnableRetryOnFailure())

❌ ANTI-PATTERN 5: Connection string con password
   → Compromise = game over
   ✅ Managed Identity + Microsoft Entra Authentication

❌ ANTI-PATTERN 6: Single Standard tier para todo
   → Producción crítica como dev
   ✅ Bus.Critical para mission-critical, Std/Basic otros

❌ ANTI-PATTERN 7: Sin geo-replication para prod
   → Region down = your business down
   ✅ Failover groups para apps críticas

❌ ANTI-PATTERN 8: Migrations en runtime de la app
   → Race conditions, deploy lock
   ✅ Migrations en pipeline (DbUp, dotnet ef en CI)

❌ ANTI-PATTERN 9: Dev connection pointing a prod
   → "Just one quick test in prod" = disaster
   ✅ Connection strings por ambiente, never overlap

❌ ANTI-PATTERN 10: Sin index strategy
   → Scans en lugar de seeks
   ✅ Query Store + Index recommendations + manual review
```

**El más común y caro:**
```
"Tenemos una stored procedure que tarda 30 segundos.
 La mejoramos a 50ms.
 Cliente ahorra 100 DTU consumidos => downgrade S3 → S0
 Ahorro: €270/mes
 Tiempo invertido: 4 horas
 ROI: instant"
```

**Reglas de decisión:**

```
✅ Azure SQL si:
   - Stack .NET / Microsoft existente
   - Requirements relacionales (FK, JOIN, transactions complejas)
   - Reports + analytics SQL-based
   - Compliance que requiere SQL Server features
   - Equipo ya conoce SQL Server

✅ Cosmos DB si:
   - Multi-region read+write
   - Schema flexible o evolving
   - Throughput > 10K req/s
   - Latencia p99 garantizada
   - Web/mobile apps modernas

✅ Azure PostgreSQL si:
   - Stack open source (Java, Python, Node)
   - Necesitáis features PostgreSQL (extensions, JSON, GIS)
   - Migración from on-prem PostgreSQL
   - Coste relativo menor que SQL Server licensing
```

**Hybrid approach (común en 2026):**
```
App moderna típica:
├── Azure SQL → entities transaccionales (Orders, Customers)
├── Cosmos DB → catálogo, configs, sesiones (high read, schema-less)
├── Blob Storage → archivos, blobs, backups
├── Redis Cache → cache de queries frecuentes
└── ADLS + Synapse → analytics warehouse
```

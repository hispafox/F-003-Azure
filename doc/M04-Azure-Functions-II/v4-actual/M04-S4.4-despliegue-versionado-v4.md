## Slide 3 — Core Tools: el método de desarrollo

```bash
# Publicar directamente desde local
func azure functionapp publish func-ventas-dev

# Publicar con build local (no build en Azure)
func azure functionapp publish func-ventas-dev --dotnet

# Publicar solo la configuración (app settings)
func azure functionapp publish func-ventas-dev --publish-settings-only

# Publicar sin confirmar
func azure functionapp publish func-ventas-dev --force
```

**Lo que hace:**
1. `dotnet publish` local
2. Empaqueta la salida en un zip
3. Lo sube al endpoint de Kudu
4. Reinicia el Function App

**Cuándo usarlo:** Desarrollo y testing. Para producción, un pipeline automatizado.

## Slide 4 — Run from Package: producción

Run from Package ejecuta la función directamente desde el zip, sin extraer:

```bash
# Habilitar
az functionapp config appsettings set --name func-ventas-prod -g mi-rg \
  --settings WEBSITE_RUN_FROM_PACKAGE=1

# Desplegar
func azure functionapp publish func-ventas-prod
```

**Ventajas:**
- Despliegue atómico: la versión anterior funciona hasta que la nueva está lista al 100%
- Arranque más rápido (sin paso de extracción)
- Filesystem read-only → más seguro
- Rollback más fiable

**Limitación:** El filesystem de la app es read-only. Si tu función escribe archivos locales, usa `/tmp` o almacenamiento externo.

## Slide 5 — Slots de despliegue en Functions

Azure Functions soporta slots igual que App Service (requiere plan Premium o Dedicated):

```bash
# Crear slot staging
az functionapp deployment slot create \
  --name func-ventas-prod -g mi-rg --slot staging

# Configurar settings sticky
az functionapp config appsettings set --name func-ventas-prod -g mi-rg \
  --slot-settings \
    ASPNETCORE_ENVIRONMENT=Production \
    CosmosDbConnection="@Microsoft.KeyVault(VaultName=kv-prod;SecretName=CosmosDb)" \
    ServiceBusConnection="@Microsoft.KeyVault(VaultName=kv-prod;SecretName=ServiceBus)"

# Desplegar al slot staging
func azure functionapp publish func-ventas-prod --slot staging

# Swap
az functionapp deployment slot swap \
  --name func-ventas-prod -g mi-rg \
  --slot staging --target-slot production
```

**Cuidado con triggers en staging:** Si el slot staging tiene las mismas connection strings que producción, sus triggers también se dispararán con datos reales. Solución: connection strings de staging apuntando a recursos de staging (marcadas como sticky).

## Slide 6 — Versionado: organizar funciones

**Opción 1 — Todas las funciones en un Function App:**
```
func-ventas (Function App)
├── ProcesarPedido (HTTP)
├── NotificarCliente (Service Bus)
├── LimpiezaNocturna (Timer)
└── ReaccionarCambios (Cosmos DB)
```
Ventaja: simple, un solo despliegue. Desventaja: un cambio en una función redespliega todas.

**Opción 2 — Function Apps por dominio:**
```
func-ventas-api      (HTTP triggers → APIs)
func-ventas-workers  (Queue/SB triggers → procesamiento)
func-ventas-cron     (Timer triggers → tareas programadas)
```
Ventaja: escalado independiente, despliegue independiente. Desventaja: más recursos que gestionar.

**Opción 3 — Function Apps por equipo:**
```
func-equipo-backend  (APIs + procesamiento)
func-equipo-data     (ETL + sincronización)
func-equipo-ops      (Monitorización + limpieza)
```

**Recomendación para vuestro equipo:** Empezad con opción 1 (un Function App). Cuando el número de funciones supere 10-15, separarlas por dominio (opción 2).

## Slide 7 — Versionado de APIs HTTP

Si exponéis APIs HTTP con Functions, necesitáis versionado:

```csharp
// Versión en la ruta
[HttpTrigger(AuthorizationLevel.Function, "get", Route = "v1/productos")]
[HttpTrigger(AuthorizationLevel.Function, "get", Route = "v2/productos")]

// O con host.json: quitar el prefijo /api
// host.json: "routePrefix": ""
// URLs: /v1/productos, /v2/productos
```

**Estrategia de deprecación:**
1. Publicar v2 junto a v1
2. Notificar a consumidores que v1 se depreca
3. Monitorizar uso de v1
4. Cuando v1 no tenga tráfico, eliminarla

## Slide 8 — Pipeline CI/CD para Functions (preview)

En el módulo 8 veremos esto en profundidad, pero así luce un pipeline de Azure DevOps para Functions:

```yaml
trigger:
  branches:
    include: [main]
  paths:
    include: [src/Functions/*]

stages:
- stage: Build
  jobs:
  - job: Build
    steps:
    - task: UseDotNet@2
      inputs: { version: '8.x' }
    - script: dotnet publish src/Functions -c Release -o $(Build.ArtifactStagingDirectory)
    - publish: $(Build.ArtifactStagingDirectory)
      artifact: functions

- stage: DeployStaging
  dependsOn: Build
  jobs:
  - deployment: Deploy
    environment: functions-staging
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureFunctionApp@2
            inputs:
              azureSubscription: 'mi-conexion'
              appType: functionApp
              appName: func-ventas-prod
              slotName: staging
              package: $(Pipeline.Workspace)/functions

- stage: SwapProd
  dependsOn: DeployStaging
  jobs:
  - deployment: Swap
    environment: functions-production  # Aprobación manual
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureAppServiceManage@0
            inputs:
              Action: Swap Slots
              WebAppName: func-ventas-prod
              SourceSlot: staging
```

## Slide 10 — Monitorización post-despliegue

Después de cada despliegue, verificad:

```bash
# 1. Funciones disponibles
func azure functionapp list-functions func-ventas-prod

# 2. Estado del Function App
az functionapp show --name func-ventas-prod -g mi-rg --query state

# 3. Logs en streaming (buscar errores de arranque)
az webapp log tail --name func-ventas-prod -g mi-rg

# 4. Métricas de errores (últimos 30 minutos)
az monitor metrics list \
  --resource "/subscriptions/<id>/.../Microsoft.Web/sites/func-ventas-prod" \
  --metric "FunctionExecutionErrors" \
  --interval PT5M --output table
```

**Checklist post-despliegue:**
- [ ] Todas las funciones aparecen en la lista
- [ ] No hay errores en los primeros 5 minutos de logs
- [ ] HTTP triggers responden correctamente
- [ ] Timer triggers se ejecutan según su CRON
- [ ] Las métricas de error no suben respecto al baseline

## Slide 11 — Blue/Green deployment para Functions

Sin slots (plan Consumption), podéis hacer blue/green con dos Function Apps:

```bash
# Blue (producción actual)
func-ventas-blue.azurewebsites.net  → activo

# Green (nueva versión)
func-ventas-green.azurewebsites.net → desplegáis aquí

# Verificar green
curl https://func-ventas-green.azurewebsites.net/api/health

# Swap DNS (o APIM) para redirigir tráfico
# Blue pasa a inactivo, Green pasa a producción
```

**Con Azure API Management** (módulo 7): APIM actúa como proxy y podéis cambiar el backend de blue a green sin cambiar la URL que usan los clientes.

## Slide 14 — Monitorización post-despliegue avanzada

```bash
# Script post-deploy verificación completa
#!/bin/bash
APP="func-ventas-prod"
RG="rg-ventas-prod"

echo "=== POST-DEPLOY CHECK ==="

# 1. ¿Todas las funciones existen?
echo "Funciones desplegadas:"
az functionapp function list --name $APP -g $RG --query "[].name" -o tsv

# 2. ¿HTTP triggers responden?
for func in $(az functionapp function list --name $APP -g $RG --query "[?config.bindings[?type=='httpTrigger']].name" -o tsv); do
  URL="https://$APP.azurewebsites.net/api/$func"
  CODE=$(curl -s -o /dev/null -w "%{http_code}" "$URL")
  echo "  $func → HTTP $CODE"
done

# 3. ¿Métricas de error en los últimos 5 min?
ERRORS=$(az monitor metrics list \
  --resource "/subscriptions/<id>/.../sites/$APP" \
  --metric "FunctionExecutionErrors" --interval PT5M \
  --query "value[0].timeseries[0].data[-1].total" -o tsv 2>/dev/null)
echo "Errores últimos 5 min: ${ERRORS:-0}"

# 4. ¿App running?
STATE=$(az functionapp show --name $APP -g $RG --query state -o tsv)
echo "Estado: $STATE"

echo "=== CHECK COMPLETADO ==="
```

## Slide 15 — Rollback strategies

**Con slots:** Swap inverso (instantáneo).

**Sin slots (Consumption):** 
```bash
# Opción 1: Redesplegar la versión anterior desde el pipeline
# (el artefacto de la versión anterior debe estar en el artifact store)

# Opción 2: Git revert + redeploy
git revert HEAD
git push  # Trigger de pipeline → redeploy versión anterior

# Opción 3: Deployment history en Kudu
# https://func-ventas-prod.scm.azurewebsites.net/api/deployments
# Cada despliegue tiene un ID — podéis reactivar uno anterior
az functionapp deployment source config-zip --name func-ventas-prod -g mi-rg \
  --src <url-del-artefacto-anterior>
```

**Regla:** Siempre tened disponible el artefacto de la versión anterior. En Azure DevOps, los artifacts del pipeline se retienen por defecto 30 días.

## Slide 16 — Feature flags para despliegue seguro

En vez de rollback, usad feature flags para activar/desactivar funcionalidad nueva:

```bash
# Desplegar con feature desactivada
az functionapp config appsettings set --name func-ventas-prod -g mi-rg \
  --settings FEATURE_NUEVO_PROCESAMIENTO=false

# Verificar que todo funciona
# Activar la feature gradualmente
az functionapp config appsettings set --name func-ventas-prod -g mi-rg \
  --settings FEATURE_NUEVO_PROCESAMIENTO=true
```

```csharp
[Function("ProcesarPedido")]
public async Task Procesar([ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg)
{
    var useNewProcessing = Environment.GetEnvironmentVariable("FEATURE_NUEVO_PROCESAMIENTO") == "true";
    
    if (useNewProcessing)
        await _newProcessor.ProcessAsync(msg);
    else
        await _legacyProcessor.ProcessAsync(msg);
}
```

Si la nueva lógica falla, desactiváis el flag sin redesplegar. Mucho más rápido que un rollback.

## Slide 18 — Flex Consumption deploy: el nuevo estándar

Flex Consumption (GA 2024) introdujo cambios en el modelo de deploy:

```
Classic Consumption               Flex Consumption
─────────────────────            ─────────────────────
- Deploy zip-based               - Deploy One-per-instance model  
- Scale: 0 → 200 (slow)          - Scale: 0 → 1000 (faster)
- Cold start: 2-5 s              - Cold start: <1 s típico
- VNet: Premium only             - VNet: included
- Concurrency: 1 req/instance    - Concurrency: 16-100/instance
- Pricing: per execution         - Pricing: por GB-seconds
```

**Crear Flex Consumption:**
```bash
# Crear Storage (requisito)
az storage account create --name stfunccurso \
  --resource-group rg-curso --location westeurope --sku Standard_LRS

# Crear Function App con Flex
az functionapp create \
  --resource-group rg-curso \
  --name func-curso-flex \
  --storage-account stfunccurso \
  --flexconsumption-location westeurope \
  --runtime dotnet-isolated \
  --runtime-version 8 \
  --instance-memory 2048 \    # MB por instance (512, 2048, 4096)
  --maximum-instance-count 100
```

**Deploy a Flex:**
```bash
# El mismo comando que antes
func azure functionapp publish func-curso-flex --dotnet-isolated

# O con zip deploy
dotnet publish -c Release -o ./publish
cd publish && zip -r ../deploy.zip .
az functionapp deployment source config-zip \
  --resource-group rg-curso \
  --name func-curso-flex \
  --src ../deploy.zip
```

**Diferencias importantes de config:**
```bash
# En Flex, concurrency es configurable
az functionapp config set \
  --resource-group rg-curso \
  --name func-curso-flex \
  --generic-configurations "{'alwaysReady':[{'name':'http','instanceCount':1}]}"

# Always Ready instances: evitar cold start críticos
# Coste: instance always-on, pero latency predecible
```

**Cuándo elegir Flex vs Premium vs Consumption:**
```
Consumption (clásico): desarrollo, poca carga, muy bursty
Flex Consumption: general-purpose 2026 (recomendado)
Premium: requisitos estrictos de VNet, always-on, 5+ instances baseline
App Service Plan: función comparte plan con web app
```

## Slide 19 — Deployment Stacks: reemplazo de Blueprints

Azure anunció deprecation de Blueprints (2026) → usar **Deployment Stacks** (GA 2024):

```bash
# Instalar extensión
az extension add --name stack-deployment

# Crear un stack (agrupación de recursos gestionados como unidad)
az stack sub create \
  --name prod-stack-v1 \
  --location westeurope \
  --template-file main.bicep \
  --parameters environment=prod \
  --action-on-unmanage deleteResources \
  --deny-settings-mode DenyDelete

# Update atómico de todos los recursos del stack
az stack sub create \
  --name prod-stack-v1 \
  --template-file main-v2.bicep \
  --action-on-unmanage deleteResources

# Si queréis quitar el stack (y todos sus recursos)
az stack sub delete --name prod-stack-v1 --action-on-unmanage deleteResources --yes
```

**Qué garantiza un Deployment Stack:**
```
✅ Atomicidad: todos los recursos o ninguno
✅ Inventory: "estos recursos pertenecen a este stack"
✅ Deletion protection: no se pueden borrar por accidente
✅ Drift detection: detectar cambios fuera de bicep
✅ Clean removal: borrar stack = borrar TODO lo que crea
```

**Action on unmanage** (qué pasa si quitáis un recurso del bicep):
- `deleteResources`: se borra el recurso de Azure
- `deleteAll`: borra recurso Y estado del stack
- `detachAll`: solo desvincula del stack (conserva en Azure)

**Ejemplo: Function App con stack completo:**
```bicep
// main.bicep
targetScope = 'subscription'

param location string = 'westeurope'
param environment string = 'prod'

resource rg 'Microsoft.Resources/resourceGroups@2023-07-01' = {
  name: 'rg-functions-${environment}'
  location: location
  tags: { env: environment, managedBy: 'deployment-stack' }
}

module funcApp './functionApp.bicep' = {
  name: 'funcAppDeployment'
  scope: rg
  params: { location: location, environment: environment }
}

output appName string = funcApp.outputs.appName
```

**Ventaja clave:** si quitáis `module funcApp` del bicep y redeployáis el stack, la Function App se borra automáticamente. Con `az deployment group create` tradicional no pasa.

## Slide 20 — GitHub Actions workflow completo para Functions

Workflow production-ready con OIDC, tests, y deploy a slot:

```yaml
# .github/workflows/deploy-functions.yml
name: Deploy Azure Functions

on:
  push:
    branches: [main]
    paths:
      - 'src/Functions/**'
      - 'tests/Functions.Tests/**'
      - '.github/workflows/deploy-functions.yml'
  pull_request:
    branches: [main]

permissions:
  id-token: write  # Para OIDC
  contents: read

env:
  DOTNET_VERSION: '8.0.x'
  FUNCTION_APP_NAME: 'func-curso-prod'
  RESOURCE_GROUP: 'rg-curso-prod'
  AZURE_FUNCTIONAPP_PACKAGE_PATH: './publish'

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with: { dotnet-version: ${{ env.DOTNET_VERSION }} }
      
      - name: Restore
        run: dotnet restore
      
      - name: Build
        run: dotnet build -c Release --no-restore
      
      - name: Test
        run: dotnet test -c Release --no-build --logger trx --collect:"XPlat Code Coverage"
      
      - name: Publish test results
        uses: dorny/test-reporter@v1
        if: success() || failure()
        with:
          name: Test Results
          path: '**/TestResults/*.trx'
          reporter: dotnet-trx
      
      - name: Code coverage
        uses: codecov/codecov-action@v4
        with:
          files: '**/coverage.cobertura.xml'

  build:
    needs: test
    runs-on: ubuntu-latest
    if: github.event_name == 'push'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: ${{ env.DOTNET_VERSION }} }
      
      - name: Publish
        run: dotnet publish src/Functions -c Release -o ${{ env.AZURE_FUNCTIONAPP_PACKAGE_PATH }}
      
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: function-package
          path: ${{ env.AZURE_FUNCTIONAPP_PACKAGE_PATH }}

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://${{ env.FUNCTION_APP_NAME }}-staging.azurewebsites.net
    steps:
      - uses: actions/download-artifact@v4
        with: { name: function-package, path: ${{ env.AZURE_FUNCTIONAPP_PACKAGE_PATH }} }
      
      - name: Login with OIDC
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      - name: Deploy to staging slot
        uses: Azure/functions-action@v1
        with:
          app-name: ${{ env.FUNCTION_APP_NAME }}
          slot-name: staging
          package: ${{ env.AZURE_FUNCTIONAPP_PACKAGE_PATH }}
      
      - name: Smoke test staging
        run: |
          sleep 30
          curl -sf https://${{ env.FUNCTION_APP_NAME }}-staging.azurewebsites.net/api/health

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://${{ env.FUNCTION_APP_NAME }}.azurewebsites.net
    steps:
      - name: Login
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      
      - name: Swap staging to production
        run: |
          az functionapp deployment slot swap \
            --name ${{ env.FUNCTION_APP_NAME }} \
            --resource-group ${{ env.RESOURCE_GROUP }} \
            --slot staging \
            --target-slot production
      
      - name: Smoke test production
        run: |
          sleep 60
          curl -sf https://${{ env.FUNCTION_APP_NAME }}.azurewebsites.net/api/health
```

**Environments en GitHub:** required reviewers para production, secrets scoped por environment, deployment history auditable.

## Slide 21 — OIDC Federated Credentials: sin passwords

Paso a paso para configurar OIDC (OpenID Connect) — autenticación moderna sin secretos:

```bash
# 1. Crear Entra ID App Registration
APP_JSON=$(az ad app create --display-name "github-actions-curso" --query "{id:id, appId:appId}" -o json)
APP_ID=$(echo $APP_JSON | jq -r .appId)
OBJECT_ID=$(echo $APP_JSON | jq -r .id)

# 2. Crear Service Principal
az ad sp create --id $APP_ID

# 3. Dar permisos al SP sobre el Resource Group
SUBSCRIPTION_ID=$(az account show --query id -o tsv)
az role assignment create \
  --role "Contributor" \
  --assignee $APP_ID \
  --scope "/subscriptions/$SUBSCRIPTION_ID/resourceGroups/rg-curso"

# 4. Crear federated credential para branch main
az ad app federated-credential create --id $OBJECT_ID \
  --parameters '{
    "name": "github-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:mi-org/mi-repo:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 5. Federated credential para environments
az ad app federated-credential create --id $OBJECT_ID \
  --parameters '{
    "name": "github-env-production",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:mi-org/mi-repo:environment:production",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# 6. En GitHub → Settings → Secrets and variables → Actions
# Crear SECRETS:
# AZURE_CLIENT_ID        = $APP_ID
# AZURE_TENANT_ID        = $(az account show --query tenantId -o tsv)
# AZURE_SUBSCRIPTION_ID  = $SUBSCRIPTION_ID
# 
# NO se guarda client secret — OIDC lo hace sin passwords
```

**Ventajas sobre Service Principal con client secret:**
- ❌ Old way: secret en GitHub, rotación manual, auditable pero exponible
- ✅ OIDC: GitHub presenta un token OIDC, Azure lo valida contra el federated credential
- ✅ Nunca hay secret que robar
- ✅ Granular: un credential por branch / environment / repo

**Patrón recomendado 2026:**
```
1 App Registration por ambiente
├── Federated credential: "branch:main" → rg-dev
├── Federated credential: "env:staging" → rg-staging
├── Federated credential: "env:production" → rg-production (con manual approval)
```

## Slide 22 — Deployment strategies: canary, blue-green, rolling

Estrategias de deploy comparadas:

```
┌────────────────────────────────────────────────────────────────┐
│ RECREATE (simple, con downtime)                                │
├────────────────────────────────────────────────────────────────┤
│ 1. Stop v1                                                     │
│ 2. Deploy v2                                                   │
│ 3. Start v2                                                    │
│ ❌ Downtime: minutos                                            │
│ ✅ Simple, atómico                                              │
│ Uso: servicios internos, horarios de mantenimiento             │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ BLUE-GREEN (zero-downtime, full cutover)                       │
├────────────────────────────────────────────────────────────────┤
│ Blue (v1) ◀── traffic                                          │
│ Green (v2) ──── staged                                         │
│                                                                │
│ swap: traffic ──▶ Green (v2)                                   │
│                                                                │
│ Rollback: traffic ──▶ Blue (v1) instantáneo                   │
│ ✅ Zero downtime                                               │
│ ✅ Rollback rápido                                             │
│ ❌ Requiere 2x infraestructura                                  │
│ En Functions: deployment slots (swap)                          │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ CANARY (gradual rollout)                                       │
├────────────────────────────────────────────────────────────────┤
│ Deploy v2 a % pequeño (5%) de usuarios                         │
│ Monitor 30 min → si OK, aumentar a 25%                         │
│ Monitor → 50% → 75% → 100%                                     │
│ Abort si metrics empeoran                                      │
│ ✅ Risk minimized                                              │
│ ✅ Real user testing                                           │
│ ❌ Complex (traffic splitting)                                 │
│ En Functions: slot traffic routing %                           │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ FEATURE FLAGS (code-level canary)                              │
├────────────────────────────────────────────────────────────────┤
│ Deploy v2 con feature flag OFF                                 │
│ Activar flag para usuarios piloto                              │
│ Expandir audiencia gradualmente                                │
│ ✅ Desacopla deploy de release                                 │
│ ✅ Rollback instantáneo (flag off)                             │
│ ❌ Complexity en código                                        │
│ Herramientas: Azure App Configuration, LaunchDarkly            │
└────────────────────────────────────────────────────────────────┘
```

**Traffic routing en slots:**
```bash

  --resource-group rg-curso \
  --name func-curso \
  --distribution staging=10

# Si va bien después de 30min, subir a 50%
az functionapp traffic-routing set \
  --name func-curso -g rg-curso \
  --distribution staging=50

# Swap final
az functionapp deployment slot swap -n func-curso -g rg-curso --slot staging
```

- **Geographic**: usuario → región según país

**Pattern común:** priority + performance combinados → usuario va al más cercano, failover automático si cae.

## Slide 25 — Rollback automation: quitar el miedo al deploy

Rollback manual tarda → gente teme deployar. Solución: automation.

```yaml
# Post-deploy verification + automatic rollback
deploy-and-verify:
  runs-on: ubuntu-latest
  steps:
    - name: Deploy to staging
      run: # ... deploy steps
    
    - name: Smoke tests (must pass)
      run: |
        ./tests/smoke.sh staging
        if [ $? -ne 0 ]; then
          echo "::error::Smoke tests failed"
          exit 1
        fi
    
    - name: Production swap
      run: |
        az functionapp deployment slot swap \
          -g rg-curso -n func-curso \
          --slot staging --target-slot production
    
    - name: Monitor production for 5 minutes
      run: |
        START=$(date +%s)
        ERRORS=0
        
        while [ $(($(date +%s) - $START)) -lt 300 ]; do
          CODE=$(curl -s -o /dev/null -w "%{http_code}" \
            https://func-curso.azurewebsites.net/api/health)
          
          if [ "$CODE" != "200" ]; then
            ERRORS=$((ERRORS+1))
            echo "Error $ERRORS: HTTP $CODE"
            
            if [ $ERRORS -ge 5 ]; then
              echo "::error::Too many errors, rolling back"
              # Auto-rollback: swap again
              az functionapp deployment slot swap \
                -g rg-curso -n func-curso \
                --slot staging --target-slot production
              exit 1
            fi
          fi
          
          sleep 10
        done
        
        echo "✅ Deploy verified healthy"
```

**Más sofisticado: comparar metrics before/after:**
```bash
# Get baseline metrics (1h antes del deploy)
BASELINE_ERRORS=$(az monitor metrics list \
  --resource $FUNC_ID --metric "FunctionExecutionCount" \
  --filter "Status eq 'Failed'" \
  --interval PT5M --start-time $(date -u -d '-1 hour' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u -d '-5 minutes' +%Y-%m-%dT%H:%M:%SZ) \
  --query "value[0].timeseries[0].data | sum_by(total)" -o tsv)

# Wait 10min post-deploy
sleep 600

# Compare
CURRENT_ERRORS=$(az monitor metrics list ...)

if [ $CURRENT_ERRORS -gt $((BASELINE_ERRORS * 3)) ]; then
  echo "Errors tripled vs baseline — rolling back"
  # swap atrás
fi
```

**Kill switch:** siempre tened un feature flag o config que desactive la nueva funcionalidad sin deploy:
```csharp
if (configuration.GetValue<bool>("FEATURE_NEW_PROCESSING", defaultValue: false))
{
    await NewProcessing(msg);
}
else
{
    await OldProcessing(msg);
}
```

## Slide 27 — Configuration as code: gestión de App Settings

Separar config de código es crítico. Pattern recomendado:

```bicep
// settings.bicep — configuración por environment
param funcAppName string

@secure()
param cosmosConnectionString string

@secure()
param serviceBusConnectionString string

param keyVaultUri string
param environmentName string

resource settings 'Microsoft.Web/sites/config@2023-12-01' = {
  name: '${funcAppName}/appsettings'
  properties: {
    // De aplicación (no secretos)
    ENVIRONMENT: environmentName
    LOG_LEVEL: environmentName == 'prod' ? 'Warning' : 'Information'
    FEATURE_NEW_VALIDATION: 'false'
    MAX_CONCURRENT_ORDERS: '100'
    
    // Secretos via Key Vault (NO inline)
    CosmosConnection: '@Microsoft.KeyVault(VaultName=${split(keyVaultUri, '/')[2]};SecretName=cosmos-connection)'
    ServiceBusConnection: '@Microsoft.KeyVault(VaultName=${split(keyVaultUri, '/')[2]};SecretName=sb-connection)'
    
    // Functions runtime
    FUNCTIONS_EXTENSION_VERSION: '~4'
    FUNCTIONS_WORKER_RUNTIME: 'dotnet-isolated'
    APPLICATIONINSIGHTS_CONNECTION_STRING: appInsights.properties.ConnectionString
  }
}
```

**Estrategias de secretos:**

| Estrategia | Pros | Contras | Cuándo |
|---|---|---|---|
| **Key Vault refs** | Central, auditable, rotatable | Requires MI + network | Producción |
| **App Settings direct** | Simple | No auditable, visible | Demos only |
| **Env-specific bicep params** | Versionado | Puede leak si no .gitignore | Dev |
| **GitHub secrets** | Federa bien con pipelines | Solo en CI | Pipelines |

**Workflow típico:**
```
Dev local:
  local.settings.json (en .gitignore) + User Secrets (.NET)

Dev cloud:
  App Settings direct (no-prod, menos fricción)

Staging/Prod:
  Key Vault references via Managed Identity
```

**Verificar config en runtime:**
```bash
# Ver settings actuales
az functionapp config appsettings list -n func-curso -g rg-curso -o table

# Verificar que secretos llegan bien
az functionapp config appsettings list -n func-curso -g rg-curso \
  --query "[?contains(value, '@Microsoft.KeyVault')].{Name:name, Ref:value}" -o table
# Deben tener @Microsoft.KeyVault(...) format
```

## Slide 28 — Feature flags con Azure App Configuration

Desacoplar deploy de release usando feature flags centralizados:

```bash
# Crear App Configuration
az appconfig create \
  --resource-group rg-curso \
  --name appcfg-curso \
  --location westeurope \
  --sku standard

# Crear un feature flag
az appconfig feature set \
  --name appcfg-curso \
  --feature NewOrderProcessing \
  --description "Enables new order processing logic"

# Activar para todos
az appconfig feature enable --name appcfg-curso --feature NewOrderProcessing

# Activar para 25% (gradual rollout)
az appconfig feature filter add \
  --name appcfg-curso \
  --feature NewOrderProcessing \
  --filter-name Microsoft.Targeting \
  --filter-parameters '{"Audience":{"DefaultRolloutPercentage":25}}'
```

**Uso en código:**
```csharp
// Program.cs
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options.Connect(new Uri("https://appcfg-curso.azconfig.io"),
                    new DefaultAzureCredential())
        .UseFeatureFlags(featureOptions =>
        {
            featureOptions.CacheExpirationInterval = TimeSpan.FromMinutes(5);
        });
});

builder.Services.AddFeatureManagement();

// Uso en función
[Function(nameof(ProcesarPedido))]
public async Task ProcesarPedido(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg,
    IFeatureManager features)
{
    if (await features.IsEnabledAsync("NewOrderProcessing"))
    {
        await _newProcessor.ProcessAsync(msg);
    }
    else
    {
        await _oldProcessor.ProcessAsync(msg);
    }
}
```

**Patrones comunes:**

| Pattern | Uso |
|---|---|
| **Percentage rollout** | 5% → 25% → 100% gradual |
| **User targeting** | Usuarios piloto específicos |
| **Time window** | Feature activa entre 9am-5pm |
| **Environment** | Solo en staging, no prod |
| **Kill switch** | Desactivar en emergencia |

**Ventajas vs App Settings:**
- Dynamic reload (no restart)
- Audit log de cambios
- Percentage rollouts built-in
- Targeting context (users, groups)
- Separación clear entre config vs features

## Slide 29 — Monitoring post-deploy: primera hora crítica

Primera hora tras deploy: observación intensiva de métricas clave:

```
T+0: Deploy completa
│
├── T+0:00 → Smoke tests (automático)
├── T+0:05 → Manual verification: 5 requests tipos diferentes
├── T+0:10 → Check metrics:
│   ├── Error rate estable vs baseline
│   ├── Latencia p95/p99 no degradada
│   └── DLQ size sin aumentar
│
├── T+0:15 → Business metrics:
│   ├── Orders/min sigue normal
│   ├── Revenue sigue normal
│   └── No clientes reportando issues
│
├── T+0:30 → Stakeholder update
│   └── "Deploy OK, metrics verdes, monitorizando"
│
├── T+1:00 → Declare stable
│   ├── Si metrics OK → release notes públicas
│   └── Si NO OK → rollback o hotfix
│
└── T+24:00 → Post-deploy review
    └── "¿Hubo issues? Lecciones para próximo deploy"
```

**Query KQL para deploy monitoring:**
```kusto
// Comparar métricas 1h pre-deploy vs 1h post-deploy
let deployTime = datetime(2026-04-22T10:00:00Z);
let preDeployStart = deployTime - 1h;
let postDeployEnd = deployTime + 1h;

requests
| where timestamp between (preDeployStart .. postDeployEnd)
| where name startswith "Functions."
| extend period = iff(timestamp < deployTime, "pre-deploy", "post-deploy")
| summarize 
    count = count(),
    avgDuration = avg(duration),
    p95 = percentile(duration, 95),
    errorRate = countif(success == false) * 100.0 / count()
    by period, name
| order by name, period
```

**Red flags que dispararían rollback:**
- ⚠️ Error rate > 2× baseline
- ⚠️ P95 latency > 1.5× baseline
- ⚠️ DLQ size aumentando rápidamente
- ⚠️ Cold start rate aumentando sin explicación
- ⚠️ Outgoing dependencies (cosmos, SB) failing

## Slide 30 — Cierre del submódulo
El despliegue de Functions sigue los mismos principios que App Service pero con peculiaridades: triggers que pueden dispararse en staging con datos de producción (cuidado con sticky settings), Run from Package para atomicidad, y feature flags como alternativa más segura al rollback.

Core Tools para desarrollo, pipeline para producción, slots para zero-downtime, y siempre un plan de rollback probado.

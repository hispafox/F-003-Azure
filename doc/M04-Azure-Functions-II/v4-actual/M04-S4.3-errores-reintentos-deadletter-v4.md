## Slide 2 — Las cosas VAN a fallar
En un sistema distribuido, los fallos no son excepciones: son la norma. La red falla. La base de datos tiene timeouts. La API externa devuelve 503. El disco se llena. El certificado caduca.

La pregunta no es "¿va a fallar?", sino "¿qué pasa cuando falle?". Un sistema bien diseñado no evita los fallos — los maneja con gracia.


---

## Slide 3 — Tipos de errores

**Errores transitorios (se arreglan solos):**
- Timeout de red
- HTTP 429 (rate limit) o 503 (servicio no disponible)
- Throttling de Cosmos DB (exceso de RU)
- Conexión rechazada temporalmente
→ **Solución:** Reintentar con backoff

**Errores permanentes (no se arreglan reintentando):**
- Datos inválidos (JSON malformado, campo requerido faltante)
- Recurso no encontrado (404)
- Autorización denegada (401/403)
- Violación de business rule
→ **Solución:** Dead-letter + alerta + investigación manual

**Errores de infraestructura (fuera de tu control):**
- Function App caída
- Storage Account inaccesible
- Region de Azure con problemas
→ **Solución:** Redundancia, health checks, alertas

## Slide 4 — Reintentos automáticos por trigger

Cada trigger tiene su propio mecanismo de reintentos:

| Trigger | Reintentos | Configuración |
|---------|-----------|---------------|
| **HTTP** | 0 (el cliente decide) | N/A |
| **Timer** | 0 (se ejecuta en la siguiente ventana) | N/A |
| **Queue Storage** | 5 (configurable) | `host.json` → `maxDequeueCount` |
| **Service Bus** | 10 (configurable) | Cola → `maxDeliveryCount` |
| **Blob** | 5 veces | Automático, poison blob container |
| **Cosmos DB** | Infinito (Change Feed) | El Change Feed reintenta hasta éxito |
| **Event Grid** | 24 horas | Backoff exponencial, dead-letter |

**Cosmos DB Change Feed no pierde mensajes.** Si tu función falla, el checkpoint no avanza y los mismos documentos se reprocesan en el siguiente intento. Es el trigger más resiliente.

## Slide 5 — Retry Policy explícita (para cualquier trigger)

```csharp
// host.json — retry policy global
{
  "retry": {
    "strategy": "exponentialBackoff",
    "maxRetryCount": 5,
    "minimumInterval": "00:00:05",
    "maximumInterval": "00:15:00"
  }
}
```

```csharp
// O por función con atributo
[Function("ProcesarConReintentos")]
[ExponentialBackoffRetry(5, "00:00:05", "00:15:00")]
public async Task Procesar(
    [ServiceBusTrigger("mi-cola", Connection = "SBConn")]
    ServiceBusReceivedMessage mensaje)
{
    // Si esta función lanza excepción, se reintenta con backoff:
    // Intento 1: espera 5s
    // Intento 2: espera ~10s
    // Intento 3: espera ~20s
    // Intento 4: espera ~40s
    // Intento 5: espera ~80s (o 15min máximo)
    // Si sigue fallando: el mensaje va a dead-letter
}

// Fixed delay retry
[Function("ProcesarConReintentosSimples")]
[FixedDelayRetry(3, "00:00:10")]  // 3 intentos, 10 segundos entre cada uno
public async Task ProcesarSimple(
    [QueueTrigger("mi-cola", Connection = "StorageConn")]
    string mensaje)
{
    // 3 intentos con 10s de espera entre cada uno
}
```

## Slide 6 — Backoff exponencial: por qué importa

```
Sin backoff (mal):
Intento 1: falla → reintento inmediato
Intento 2: falla → reintento inmediato
Intento 3: falla → reintento inmediato
→ Bombardeas al servicio que ya está con problemas → lo empeoras

Con backoff exponencial (bien):
Intento 1: falla → espera 5s
Intento 2: falla → espera 10s
Intento 3: falla → espera 20s
Intento 4: falla → espera 40s
→ Das tiempo al servicio para recuperarse

Con jitter (mejor):
Intento 1: falla → espera 5s + random(0-2s)
Intento 2: falla → espera 10s + random(0-4s)
→ Si 100 funciones fallan a la vez, no reintentan todas al mismo segundo
```

**¿Cuántos reintentos?** Depende del SLA y del tipo de error. Para errores transitorios (429, 503, timeout), 3-5 reintentos suelen ser suficientes. Si después de 5 reintentos con backoff sigue fallando, probablemente no es transitorio.

## Slide 7 — Dead-Letter Queue: el cementerio de mensajes

Cuando un mensaje agota todos sus reintentos, va a la **dead-letter queue (DLQ)**:

```
Cola principal                         Dead-Letter Queue
┌──────────────┐                      ┌──────────────┐
│ Mensaje A ✓  │ → procesado          │ Mensaje D ✗  │ ← 10 intentos fallidos
│ Mensaje B ✓  │ → procesado          │ Mensaje F ✗  │ ← datos inválidos
│ Mensaje C ✓  │ → procesado          │ Mensaje H ✗  │ ← error permanente
│ Mensaje D ✗  │ → falla × 10         └──────────────┘
│ Mensaje E ✓  │ → procesado              ↓
└──────────────┘                    Alerta → Investigar → Fix → Reenviar
```

**Service Bus DLQ:**
```bash
# Ver mensajes en dead-letter de una cola
az servicebus queue show \
  --namespace-name sb-ventas-prod -g mi-rg \
  --name pedidos-a-procesar \
  --query "countDetails.deadLetterMessageCount"

# Leer mensajes dead-letter (para investigar)
# Usar Azure Service Bus Explorer o código
```

**Storage Queue poison queue:**
Cuando un mensaje falla `maxDequeueCount` veces, Azure crea una cola `{original}-poison` y mueve el mensaje ahí.

## Slide 8 — Procesar dead-letter automáticamente

```csharp
// Función que procesa la dead-letter queue
[Function("ProcesarDeadLetterPedidos")]
public async Task ProcesarDeadLetter(
    [ServiceBusTrigger("pedidos-a-procesar/$deadletterqueue", 
        Connection = "ServiceBusConnection")]
    ServiceBusReceivedMessage mensaje,
    ServiceBusMessageActions actions,
    ILogger logger)
{
    logger.LogWarning("Mensaje en dead-letter: {MessageId}, razón: {Reason}", 
        mensaje.MessageId, mensaje.DeadLetterReason);
    
    var body = mensaje.Body.ToObjectFromJson<PedidoMensaje>();
    
    // Opción 1: Intentar reprocesar con lógica diferente
    try
    {
        await _procesadorAlternativo.ProcesarAsync(body);
        await actions.CompleteMessageAsync(mensaje);
        logger.LogInformation("Dead-letter {Id} reprocesado con éxito", mensaje.MessageId);
    }
    catch (Exception ex)
    {
        // Opción 2: Guardar para investigación manual
        await _auditoria.GuardarMensajeFallidoAsync(mensaje, ex);
        await actions.CompleteMessageAsync(mensaje);  // Sacarlo de DLQ
        
        // Alertar al equipo
        await _alertas.NotificarAsync($"Mensaje {mensaje.MessageId} requiere investigación manual");
    }
}
```

## Slide 9 — Circuit Breaker: no reintentar lo imposible

Si un servicio externo está caído, reintentar miles de mensajes no ayuda — solo genera carga inútil:

```csharp
public class ApiExternaService
{
    private readonly IHttpClientFactory _httpFactory;
    private static int _fallosConsecutivos = 0;
    private static DateTime _circuitoAbiertoHasta = DateTime.MinValue;

    public async Task<Response> LlamarAsync(string endpoint)
    {
        // Circuit breaker: si hay muchos fallos, no intentar
        if (_fallosConsecutivos > 5 && DateTime.UtcNow < _circuitoAbiertoHasta)
        {
            throw new CircuitBreakerOpenException(
                $"Circuito abierto hasta {_circuitoAbiertoHasta}. " +
                $"Fallos consecutivos: {_fallosConsecutivos}");
        }
        
        try
        {
            var client = _httpFactory.CreateClient("ApiExterna");
            var response = await client.GetAsync(endpoint);
            response.EnsureSuccessStatusCode();
            
            _fallosConsecutivos = 0;  // Reset al tener éxito
            return await response.Content.ReadFromJsonAsync<Response>();
        }
        catch (HttpRequestException)
        {
            _fallosConsecutivos++;
            _circuitoAbiertoHasta = DateTime.UtcNow.AddMinutes(2);  // Esperar 2 min
            throw;
        }
    }
}
```

**En producción, usad Polly** (librería de resiliencia para .NET):
```bash
dotnet add package Microsoft.Extensions.Http.Polly
```

```csharp
builder.Services.AddHttpClient("ApiExterna")
    .AddTransientHttpErrorPolicy(p => 
        p.WaitAndRetryAsync(3, retryAttempt => 
            TimeSpan.FromSeconds(Math.Pow(2, retryAttempt))))
    .AddTransientHttpErrorPolicy(p => 
        p.CircuitBreakerAsync(5, TimeSpan.FromMinutes(1)));
```

## Slide 10 — Idempotencia: la defensa definitiva

Si una función se ejecuta dos veces con los mismos datos, el resultado debe ser el mismo:

**Mal (no idempotente):**
```csharp
// Si se ejecuta dos veces: el cliente recibe 2 emails
await _email.EnviarAsync(cliente, "Tu pedido está confirmado");

// Si se ejecuta dos veces: el saldo se descuenta dos veces
await _banco.CobrarAsync(cliente, importe);
```

**Bien (idempotente):**
```csharp
// Verificar antes de actuar
if (!await _registro.ExisteNotificacion(pedidoId, "confirmacion"))
{
    await _email.EnviarAsync(cliente, "Tu pedido está confirmado");
    await _registro.MarcarNotificacion(pedidoId, "confirmacion");
}

// Usar operaciones idempotentes (upsert en vez de insert)
await _cosmos.UpsertItemAsync(documento);  // OK si se ejecuta 2 veces

// Usar claves de idempotencia con APIs externas
await _stripe.ChargeAsync(new ChargeRequest {
    IdempotencyKey = $"pedido-{pedidoId}-cobro",  // Stripe ignora duplicados
    Amount = importe
});
```

## Slide 11 — Logging estructurado para errores

```csharp
[Function("ProcesarPedido")]
public async Task Procesar(
    [ServiceBusTrigger("pedidos", Connection = "SBConn")]
    ServiceBusReceivedMessage mensaje,
    ILogger logger)
{
    var pedidoId = mensaje.MessageId;
    var intento = mensaje.DeliveryCount;
    
    using var scope = logger.BeginScope(new Dictionary<string, object>
    {
        ["PedidoId"] = pedidoId,
        ["Intento"] = intento,
        ["CorrelationId"] = mensaje.CorrelationId ?? "N/A"
    });
    
    logger.LogInformation("Procesando pedido (intento {Intento})", intento);
    
    try
    {
        await ProcesarInternoAsync(mensaje);
        logger.LogInformation("Pedido procesado con éxito");
    }
    catch (TransientException ex)
    {
        logger.LogWarning(ex, "Error transitorio — se reintentará");
        throw;  // Service Bus reintentará
    }
    catch (ValidationException ex)
    {
        logger.LogError(ex, "Error de validación — enviando a dead-letter");
        throw;  // Irá a dead-letter después de maxDeliveryCount
    }
    catch (Exception ex)
    {
        logger.LogCritical(ex, "Error inesperado — requiere investigación");
        throw;
    }
}
```

**En Application Insights:**
Podéis buscar por PedidoId, filtrar por nivel de severidad, ver el trace completo de un pedido a través de todos los servicios.

## Slide 13 — Estrategia completa de errores

```
Mensaje llega
     ↓
┌─ ¿Error transitorio? (timeout, 429, 503)
│  SÍ → Reintentar con backoff exponencial
│       ↓
│  ¿Agotó reintentos?
│  SÍ → Dead-letter queue
│  NO → Reintentar
│
├─ ¿Error de validación? (datos inválidos)
│  SÍ → Dead-letter inmediato (no reintentar)
│       + Log de error con datos del mensaje
│       + Alerta al equipo
│
├─ ¿Error de negocio? (saldo insuficiente)
│  SÍ → Dead-letter + notificar al cliente
│
└─ ¿Error desconocido?
   SÍ → Log critical + Dead-letter + Alerta urgente
```

## Slide 14 — Compensación (Saga Pattern)

Cuando un flujo de múltiples pasos falla a mitad de camino:

```csharp
[Function("OrquestarConCompensacion")]
public static async Task Orquestar(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var pedido = context.GetInput<Pedido>();
    Reserva? reserva = null;
    Pago? pago = null;
    
    try
    {
        // Paso 1
        reserva = await context.CallActivityAsync<Reserva>("ReservarInventario", pedido);
        
        // Paso 2
        pago = await context.CallActivityAsync<Pago>("ProcesarPago", pedido);
        
        // Paso 3
        await context.CallActivityAsync("EnviarPedido", new { pedido, reserva, pago });
    }
    catch (Exception ex)
    {
        // COMPENSACIÓN: deshacer lo que se hizo
        if (pago is not null)
            await context.CallActivityAsync("RevertirPago", pago.TransaccionId);
        
        if (reserva is not null)
            await context.CallActivityAsync("LiberarInventario", reserva.ReservaId);
        
        // Notificar
        await context.CallActivityAsync("NotificarFalloPedido", pedido.Id);
        
        throw;  // Marcar orquestación como Failed
    }
}
```

## Slide 16 — Poison messages: el patrón dead-letter processor

Cuando mensajes acaban en DLQ, **alguien tiene que procesarlos**. Patrón real:

```csharp
// Function que procesa DLQ automáticamente
[Function(nameof(ProcesarDeadLetter))]
public async Task ProcesarDeadLetter(
    [ServiceBusTrigger("pedidos/$deadletterqueue", Connection = "SB")]
    ServiceBusReceivedMessage msg,
    FunctionContext ctx)
{
    _logger.LogWarning(
        "Dead-lettered message {id}. Reason: {reason}. Description: {desc}",
        msg.MessageId,
        msg.DeadLetterReason,
        msg.DeadLetterErrorDescription);
    
    // Categorizar el error
    var action = ClassifyPoisonMessage(msg);
    
    switch (action)
    {
        case PoisonAction.Retry:
            // El error era transient, reencolarlo a la original
            await _originalSender.SendMessageAsync(
                new ServiceBusMessage(msg.Body) {
                    MessageId = msg.MessageId,
                    CorrelationId = msg.CorrelationId
                });
            break;
            
        case PoisonAction.Quarantine:
            // Error permanente, guardar para investigación manual
            await _quarantineStorage.SaveAsync(msg);
            await _alerts.SendAsync(
                $"Poison message needs manual review: {msg.MessageId}");
            break;
            
        case PoisonAction.Discard:
            // Error conocido, descartable (ej: formato viejo)
            _logger.LogInformation("Discarded known-bad message {id}", msg.MessageId);
            break;
            
        case PoisonAction.NotifyAndRetry:
            // Retry con delay + alerta
            await _alerts.SendAsync($"Retrying DLQ message {msg.MessageId}");
            await Task.Delay(TimeSpan.FromMinutes(5));
            await _originalSender.SendMessageAsync(...);
            break;
    }
}

private PoisonAction ClassifyPoisonMessage(ServiceBusReceivedMessage msg)
{
    var reason = msg.DeadLetterReason ?? "";
    var desc = msg.DeadLetterErrorDescription ?? "";
    
    if (reason.Contains("MaxDeliveryCount")) return PoisonAction.Quarantine;
    if (desc.Contains("JsonException")) return PoisonAction.Discard;
    if (desc.Contains("timeout")) return PoisonAction.NotifyAndRetry;
    return PoisonAction.Quarantine;
}
```

**Estructura recomendada:**
```
Queue principal ──▶ Function ──▶ (falla) ──▶ DLQ
                                              │
                                              ▼
                                    Function DLQ handler
                                              │
                                      ┌───────┼───────────┐
                                      ▼       ▼           ▼
                                   Retry  Quarantine   Discard
                                                        + Log
```

**Alerts obligatorias:**
- DLQ size > 0 → Slack/Teams/PagerDuty
- DLQ size > 100 → escalar urgente
- Quarantine size → revisar semanalmente

## Slide 17 — Outbox pattern: consistencia entre BD y mensajes

Problema real: transacción en BD + publicar evento = 2 operaciones, una puede fallar:

```csharp
// ❌ MAL: inconsistencia posible
public async Task CrearPedido(Pedido p)
{
    await _db.SaveAsync(p);                          // OK, commit
    await _serviceBus.SendMessageAsync(pedidoEvent); // si falla → BD OK pero mensaje perdido
    // Resultado: pedido en BD, pero nadie se enteró
}
```

**✅ Outbox pattern:**
```
┌─────────────────────────────────────────────────────────┐
│  TRANSACCIÓN ATÓMICA en BD                              │
│  ├── INSERT INTO pedidos (...)                          │
│  └── INSERT INTO outbox (event_type, payload, ...)      │
│  COMMIT                                                 │
└────────────────────┬────────────────────────────────────┘
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│  Relay process (Function con Timer o Change Feed)      │
│  Lee outbox → publica al broker → marca como enviado   │
└────────────────────────────────────────────────────────┘
```

```csharp
// Al crear pedido — atómico
public async Task CrearPedido(Pedido p)
{
    using var tx = await _db.BeginTransactionAsync();
    
    await _db.InsertAsync("pedidos", p);
    
    await _db.InsertAsync("outbox", new OutboxMessage
    {
        EventType = "PedidoCreado",
        Payload = JsonSerializer.Serialize(p),
        Created = DateTime.UtcNow,
        Sent = false
    });
    
    await tx.CommitAsync();
}

// Function relay que publica outbox → broker
[Function(nameof(PublicarOutbox))]
public async Task PublicarOutbox(
    [TimerTrigger("*/10 * * * * *")] TimerInfo timer)  // cada 10s
{
    var pendientes = await _db.QueryAsync<OutboxMessage>(
        "SELECT * FROM outbox WHERE Sent = false ORDER BY Created LIMIT 100");
    
    foreach (var msg in pendientes)
    {
        try
        {
            await _serviceBus.SendMessageAsync(new ServiceBusMessage(msg.Payload)
            {
                MessageId = msg.Id.ToString(),  // idempotency
                Subject = msg.EventType
            });
            
            await _db.UpdateAsync("outbox", 
                "UPDATE outbox SET Sent = true, SentAt = @now WHERE Id = @id",
                new { now = DateTime.UtcNow, id = msg.Id });
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed publishing outbox message {id}", msg.Id);
            // No actualiza → se reintenta en próxima ejecución
        }
    }
}
```

**Con Cosmos DB, más elegante aún:** usar Change Feed como relay (lo veis en M5).

**Garantías:**
- **At-least-once delivery** (mensaje se publica ≥ 1 vez)
- **Consistencia BD + mensajes** (o todo o nada)
- **Consumers deben ser idempotentes**

## Slide 18 — Inbox pattern: deduplicación del lado consumer

Complemento al outbox — cómo los consumers evitan procesar duplicados:

```csharp
[Function(nameof(ProcesarPedidoInbox))]
public async Task ProcesarPedidoInbox(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg)
{
    var idempotencyKey = msg.MessageId;  // de outbox pattern
    
    // 1. Check inbox
    var yaProcesado = await _db.QuerySingleAsync<bool>(
        "SELECT COUNT(1) FROM inbox WHERE message_id = @id",
        new { id = idempotencyKey });
    
    if (yaProcesado)
    {
        _logger.LogInformation("Message {id} already processed, skipping", 
            idempotencyKey);
        return;  // complete sin procesar
    }
    
    // 2. Procesar + registrar en inbox atómicamente
    using var tx = await _db.BeginTransactionAsync();
    try
    {
        await ProcessBusinessLogicAsync(msg);
        
        await _db.InsertAsync("inbox", new InboxRecord
        {
            MessageId = idempotencyKey,
            ProcessedAt = DateTime.UtcNow,
            MessageType = msg.Subject
        });
        
        await tx.CommitAsync();
    }
    catch
    {
        await tx.RollbackAsync();
        throw;  // SB reintentará
    }
}
```

**Estructura inbox:**
```sql
CREATE TABLE inbox (
    message_id VARCHAR(100) PRIMARY KEY,
    processed_at DATETIME2 NOT NULL,
    message_type VARCHAR(100),
    INDEX idx_processed (processed_at)  -- para limpieza
);

-- Cleanup job (mensual): borrar inbox entries > 90 días
DELETE FROM inbox WHERE processed_at < DATEADD(day, -90, GETUTCDATE());
```

**Combinación outbox + inbox garantiza:**
- ✅ Ningún mensaje se pierde (outbox)
- ✅ Ningún mensaje se procesa 2 veces (inbox)
- ✅ Consistencia BD + broker
- ✅ Simple de explicar al equipo

**Coste:** 1 tabla extra en cada lado + relay job. Overhead minúsculo para la tranquilidad.

## Slide 19 — Error taxonomy: clasificar para tratar

No todos los errores son iguales. Clasificación útil:

```
┌─────────────────────────────────────────────────────────────────────┐
│ TIPO             │ EJEMPLOS              │ ACCIÓN                    │
├─────────────────────────────────────────────────────────────────────┤
│ TRANSIENT        │ - TimeoutException    │ ✅ Retry con backoff      │
│ (temporal)       │ - HttpException 5xx   │                           │
│                  │ - Cosmos 429 (throttle)│                          │
│                  │ - Network glitch      │                           │
├─────────────────────────────────────────────────────────────────────┤
│ POISON           │ - JsonException       │ ❌ NO retry → DLQ         │
│ (mensaje malo)   │ - ValidationException │    inmediatamente         │
│                  │ - ArgumentException   │                           │
├─────────────────────────────────────────────────────────────────────┤
│ CONFIGURATION    │ - ConnectionString    │ ❌ Fail fast → alerta     │
│ (vuestro error)  │   missing/wrong       │    ops inmediato          │
│                  │ - MissingAppSetting   │                           │
│                  │ - AuthorizationFail   │                           │
├─────────────────────────────────────────────────────────────────────┤
│ DEPENDENCY       │ - DB unavailable      │ ⚠️ Circuit breaker        │
│ (sistema ext)    │ - API partner down    │    + fallback si posible  │
│                  │ - Storage 503         │                           │
├─────────────────────────────────────────────────────────────────────┤
│ BUSINESS         │ - Stock insuficiente  │ ✅ NO es error técnico    │
│ (regla negocio)  │ - Credit declined     │    → publicar evento     │
│                  │ - Deadline passed     │    "PedidoRechazado"      │
└─────────────────────────────────────────────────────────────────────┘
```

**Implementación en código:**
```csharp
[Function(nameof(ProcesarPedido))]
public async Task ProcesarPedido(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg,
    ServiceBusMessageActions actions)
{
    try
    {
        var pedido = JsonSerializer.Deserialize<Pedido>(msg.Body);
        if (pedido == null) 
            throw new PoisonMessageException("Body empty or invalid");
        
        await _validator.ValidateAsync(pedido);  // throws ValidationException
        await _service.ProcesarAsync(pedido);
        
        await actions.CompleteMessageAsync(msg);
    }
    catch (PoisonMessageException ex)
    {
        _logger.LogError(ex, "Poison message {id}", msg.MessageId);
        await actions.DeadLetterMessageAsync(msg, reason: "PoisonMessage",
            errorDescription: ex.Message);
    }
    catch (ConfigurationException ex)
    {
        _logger.LogCritical(ex, "Configuration error — ops alert");
        await _alerts.SendCriticalAsync($"Config error: {ex.Message}");
        throw;  // let SB retry even though it won't help
    }
    catch (Exception ex) when (IsTransient(ex))
    {
        _logger.LogWarning(ex, "Transient error on {id} — will retry", msg.MessageId);
        throw;  // SB retry with backoff
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Unexpected error");
        throw;
    }
}

private static bool IsTransient(Exception ex) => ex switch
{
    TimeoutException => true,
    HttpRequestException http when http.StatusCode >= 500 => true,
    CosmosException cosmos when cosmos.StatusCode == 429 => true,
    _ => false
};
```

## Slide 20 — Correlation IDs: W3C TraceContext en Functions

Propagar el trace ID entre servicios para trazabilidad completa:

```csharp
// Program.cs — habilitar OpenTelemetry con W3C
builder.Services.ConfigureFunctionsApplicationInsights();

// En el HTTP Trigger de entrada, capturar traceparent
[Function(nameof(CrearPedido))]
public async Task<HttpResponseData> CrearPedido(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
{
    // Azure Functions captura automáticamente traceparent del HTTP header
    var traceId = Activity.Current?.TraceId.ToString();
    
    // Propagar al mensaje que vamos a publicar
    var pedido = await req.ReadFromJsonAsync<Pedido>();
    var mensaje = new ServiceBusMessage(JsonSerializer.Serialize(pedido))

        CorrelationId = traceId,
        ApplicationProperties =
        {
            ["traceparent"] = Activity.Current?.Id,
            ["tracestate"] = Activity.Current?.TraceStateString
        }
    };
    
    await _sender.SendMessageAsync(mensaje);
    
    var resp = req.CreateResponse();
    await resp.WriteAsJsonAsync(new { correlationId = traceId, status = "accepted" });
    return resp;
}

// En el SB Trigger que procesa, extraer y continuar el trace
[Function(nameof(ProcesarPedido))]
public async Task ProcesarPedido(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg)
{

    if (msg.ApplicationProperties.TryGetValue("traceparent", out var traceparent))

        Activity.Current?.SetParentId(traceparent.ToString()!);
    }
    
    _logger.LogInformation("Procesando pedido, correlacion {correlationId}",
        msg.CorrelationId);
    
    // Las llamadas HTTP salientes propagarán el trace automáticamente
    using var httpClient = new HttpClient();
    await httpClient.GetAsync("https://api.external.com/validate");  // add traceparent
}
```

## Slide 21 — Error budget y SLOs

SRE practices para production serias — **Error Budget**:

```
SLO (Service Level Objective): 99.5% uptime
├── Ventana: 30 días (43.200 minutos)
├── Error budget: 0.5% = 216 minutos de downtime permitidos
└── Por debajo: release freeze hasta recuperar
```

**Aplicado a Functions:**
```
Function "ProcesarPedido":
├── SLO: 99.9% éxito (1 en 1000 puede fallar)
├── Tráfico: 100K req/día = 3M req/mes
├── Error budget: 0.1% = 3000 fallos/mes
│
├── Primera semana: 1200 fallos → vamos al 40% del budget
├── Segunda semana: 800 fallos → 66% del budget
├── Si al 80% del budget en 2 semanas → BLOCK releases, 
│   investigar root cause
└── Si excede 100% → incident postmortem obligatorio
```

**Metrics en AppInsights:**
```kusto
// Success rate de las últimas 24h
requests
| where name startswith "ProcesarPedido"
| where timestamp > ago(24h)
| summarize total = count(), errors = countif(success == false)
| extend success_rate = 1.0 - (errors * 1.0 / total)
| extend error_budget_used_pct = (errors * 1.0 / total) / 0.001  // 0.1% budget

// Alert si exceed 50% del error budget
AlertRule:
  query: above
  threshold: error_budget_used_pct > 0.5
  severity: Warning
```

**Práctica organizacional:**
```
Review semanal de error budgets
├── ¿Qué funciones superan 50% del budget?
├── ¿Qué tipo de errores? (transient, poison, config)
├── ¿Qué mejoras están planeadas?
└── ¿Necesitamos hacer release freeze?
```

**Cultural shift:** en vez de "tenemos 0 errores" (imposible y carísimo), "estamos dentro del budget aceptable". Da libertad para innovar sin miedo.

## Slide 22 — Chaos engineering: romper a propósito

Provocar fallos para verificar que la resiliencia funciona. Azure Chaos Studio hace esto gestionado:

```bash
  "properties": {
    "selectors": [{
      "id": "target-functions",
      "type": "List",
      "targets": [{
        "type": "ChaosTarget",
        "id": "$TARGET_ID"
      }]
    }],
    "steps": [{
      "name": "Step 1",
      "branches": [{
        "name": "Branch 1",
        "actions": [{
          "type": "continuous",
          "name": "urn:csci:microsoft:azureFunctionApp:stop/1.0",
          "duration": "PT5M",
          "selectorId": "target-functions"
        }]
      }]
    }]
  }
}
EOF
```

**Fault injection común:**

| Fault | Qué prueba |
|---|---|
| `AzureFunctionApp:stop` | Resiliencia a "la Function está caída" |
| `NetworkDelay` | Latencia alta a dependencies |
| `CPU:pressure` | Comportamiento bajo presión |
| `Memory:pressure` | Memory leaks / OOM handling |
| `Cosmos:throttle` | 429 responses |
| `Storage:throttle` | Slow storage |

**Chaos day ritual:**
```
Pre-chaos:
├── Define hypothesis: "Si Cosmos 429s 30% → pedidos completan con delay"
├── Metrics baseline: latencia actual, success rate, DLQ size
├── Abort condition: "si success rate < 95%, cancel experiment"
└── Notificación a stakeholders: "chaos en 10 min"

During:
├── Run experiment (ej: 5 min de throttling)
├── Monitor dashboards en real-time
└── Abort si aborto condition

Post:
├── Validate metrics: ¿la hypothesis se cumplió?
├── Document: ¿qué se rompió que no debía?
├── Fix: las mejoras van a backlog
└── Aprender: próximo chaos prueba otra cosa
```

**Gotcha:** no hagáis chaos en producción sin feature flags y red team preparado. Staging es mejor primer paso.

## Slide 24 — Playbook: qué hacer cuando algo rompe en producción

Runbook estándar cuando suena la alerta:

```
PASO 1: ACK + reducir ruido (5 min)
├── Acknowledge alert (vuestro sistema paging)
├── Join war room (Slack channel / Teams meeting)
├── First responder designado
└── Stop la hemorragia: ¿hay feature flag para desactivar algo?

PASO 2: Assess impact (5-15 min)
├── ¿Cuántos usuarios afectados?
├── ¿Qué % de requests failing?
├── ¿Cuánto tiempo lleva fallando? (correlación con releases)
├── ¿Solo una región o global?
└── Decision: ¿rollback ya o investigar más?

PASO 3: Mitigate (15-60 min)
├── Opción A: Rollback (si fue un release reciente)
│   └── GitHub Actions → "Revert workflow" en 1 clic
├── Opción B: Scale up (si es saturación)
│   └── az functionapp plan update --sku P2v3
├── Opción C: Feature flag off (si es feature nueva)
├── Opción D: Redirect traffic (si hay multi-region)
└── Mientras: actualizar a stakeholders cada 15 min

PASO 4: Monitor recovery (15-30 min)
├── Metrics volviendo a verde
├── Usuarios confirmando
└── Cerrar incident formalmente

PASO 5: Postmortem (24-72h después)
├── Timeline of events
├── Root cause analysis (5 whys)
├── Action items: para evitar repetición
│   ├── Bug fix obvio
│   ├── Mejor monitoring
│   ├── Runbook updates
│   └── Chaos engineering experiment
├── Blameless (culpar al sistema, no a personas)
└── Compartir con el equipo — learning opportunity
```

**Herramientas prácticas:**
- PagerDuty / Opsgenie para alertas
- Slack/Teams para war room
- Azure Portal pinned dashboard
- Runbook en Notion/Confluence
- Template postmortem en Google Docs

## Slide 26 — Saga Pattern: transacciones distribuidas

Problema: "reserva + pago + envío" debe ser atómico, pero cada uno es servicio distinto. Solución: Saga.

```csharp
// Orchestration-based saga con Durable Functions
[Function(nameof(SagaPedido))]
public async Task SagaPedido(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var pedido = ctx.GetInput<Pedido>();
    var steps = new List<(string step, string compensate)>();
    
    try
    {
        // Step 1: Reservar stock
        await ctx.CallActivityAsync("ReservarStock", pedido);
        steps.Add(("ReservaStock", "LiberarStock"));
        
        // Step 2: Cobrar tarjeta
        var chargeId = await ctx.CallActivityAsync<string>("CobrarTarjeta", pedido);
        steps.Add(("Cobro", "ReembolsarTarjeta"));
        
        // Step 3: Crear envío
        await ctx.CallActivityAsync("CrearEnvio", pedido);
        steps.Add(("Envio", "CancelarEnvio"));
        
        // Step 4: Notificar (non-compensable, pero no crítica)
        await ctx.CallActivityAsync("Notificar", pedido);
        
        // Todo OK — commit
        await ctx.CallActivityAsync("MarcarPedidoCompleto", pedido);
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Saga failed at step {step}. Compensating...", 
            steps.Count);
        
        // Compensate en orden inverso
        foreach (var (step, compensate) in steps.AsEnumerable().Reverse())
        {
            try
            {
                await ctx.CallActivityAsync(compensate, pedido);
            }
            catch (Exception compensateEx)
            {
                _logger.LogCritical(compensateEx, 
                    "Compensation {step} failed — manual intervention required",
                    step);
                // Alert a ops — situación grave
            }
        }
        
        // Notificar fallo al cliente
        await ctx.CallActivityAsync("NotificarFallo", 
            new { pedido, error = ex.Message });
    }
}
```

**Variantes de Saga:**

| Tipo | Pros | Contras |
|---|---|---|
| **Orchestration** (Durable F) | Lógica centralizada | Single point of failure |
| **Choreography** (eventos) | Descentralizado, escalable | Difícil de razonar |

**Para el curso: Orchestration** (más explícito). En sistemas muy distribuidos, choreography tiene sentido.

**Gotcha crítico:** compensaciones deben ser **idempotentes** y **casi-siempre-exitosas**. Si `LiberarStock` falla, estáis en trouble. Por eso muchas veces las compensaciones escriben a una "acción pendiente" para intentar repetidamente.

## Slide 27 — Cierre del submódulo

La gestión de errores no es un "nice to have" que añades al final. Es parte del diseño desde el principio. Cada función que escribáis debería responder a: ¿qué pasa si esto falla?

Lo esencial:
- Errores transitorios → reintentar con backoff exponencial
- Errores permanentes → dead-letter + alerta + investigación
- Idempotencia obligatoria en funciones que procesan mensajes
- Circuit breaker para proteger servicios externos (Polly)
- Compensación (Saga) para flujos de múltiples pasos
- Logging estructurado para trazabilidad end-to-end
- Alertas proactivas — no enterarse por el cliente

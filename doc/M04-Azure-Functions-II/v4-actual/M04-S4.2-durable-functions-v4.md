# Submódulo 4.2 — Durable Functions: orquestación de flujos

## Slide 2 — El problema que resuelven
Las funciones normales son stateless y de corta duración. Perfecto para tareas simples. Pero ¿qué pasa cuando necesitáis:

- Ejecutar 5 pasos en secuencia, donde cada paso depende del anterior
- Lanzar 100 tareas en paralelo y esperar a que todas terminen
- Monitorizar un proceso externo cada 5 minutos hasta que complete
- Esperar a que un humano apruebe algo antes de continuar

Una función normal no puede hacer esto. Durable Functions sí.


---

## Slide 3 — Qué son Durable Functions
Durable Functions es una extensión de Azure Functions que permite escribir flujos de trabajo (workflows) como código:

**Tres tipos de funciones:**

| Tipo | Rol | Analogía |
|------|-----|----------|
| **Orchestrator** | Dirige el flujo, decide qué ejecutar y cuándo | Director de orquesta |
| **Activity** | Ejecuta una tarea concreta (el trabajo real) | Músico individual |
| **Entity** | Mantiene estado entre ejecuciones | Variable persistente |

```
Cliente → Starter (HTTP) → Orchestrator → Activity A
                                        → Activity B
                                        → Activity C
                                        → Resultado
```

El Orchestrator define el flujo. Las Activities hacen el trabajo. El estado se persiste automáticamente en Azure Storage.


---

## Slide 4 — La magia: replay y checkpointing

El Orchestrator NO se ejecuta de forma continua. Funciona con un patrón de **replay**:

```
1. Orchestrator arranca → llama a Activity A → se DUERME
2. Activity A termina → Orchestrator se DESPIERTA (replay)
3. Orchestrator ve que A terminó → llama a Activity B → se DUERME
4. Activity B termina → Orchestrator se DESPIERTA (replay)
5. ... hasta completar el flujo
```

**¿Por qué replay?**
- El Orchestrator no consume recursos mientras espera
- Si la instancia se recicla, el Orchestrator se reconstruye desde el historial
- El flujo puede durar horas, días o semanas sin mantener un proceso vivo

**Implicación:** El código del Orchestrator se ejecuta MÚLTIPLES VECES (una por cada replay). Por eso tiene reglas especiales.


---

## Slide 5 — Reglas del Orchestrator (CRÍTICAS)

El código del Orchestrator DEBE ser determinista. Eso significa:

**PROHIBIDO en el Orchestrator:**
```csharp
// ✗ NO usar DateTime.UtcNow (diferente en cada replay)
var hora = DateTime.UtcNow;  // MAL

// ✗ NO usar Random
var n = Random.Shared.Next();  // MAL

// ✗ NO hacer I/O directamente (HTTP, DB, archivos)
var data = await httpClient.GetAsync("...");  // MAL

// ✗ NO usar Thread.Sleep
Thread.Sleep(5000);  // MAL

// ✗ NO usar bucles infinitos sin await
while(true) { }  // MAL
```

**PERMITIDO en el Orchestrator:**
```csharp
// ✓ Usar context.CurrentUtcDateTime
var hora = context.CurrentUtcDateTime;  // Determinista

// ✓ Usar context.NewGuid()
var id = context.NewGuid();  // Determinista

// ✓ Llamar a Activities (el I/O va ahí)
var data = await context.CallActivityAsync("LeerDatos");

// ✓ Usar context.CreateTimer
await context.CreateTimer(context.CurrentUtcDateTime.AddMinutes(5));
```

**Regla simple:** El Orchestrator solo decide qué hacer. Las Activities hacen el trabajo real.

## Slide 6 — Patrón 1: Encadenamiento (Chaining)

Ejecutar pasos en secuencia, donde cada paso recibe el resultado del anterior:

```csharp
[Function("OrquestarPedido")]
public static async Task<string> OrquestarPedido(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var pedidoId = context.GetInput<string>();
    
    // Paso 1: Validar el pedido
    var pedido = await context.CallActivityAsync<Pedido>("ValidarPedido", pedidoId);
    
    // Paso 2: Reservar inventario
    var reserva = await context.CallActivityAsync<Reserva>("ReservarInventario", pedido);
    
    // Paso 3: Procesar pago
    var pago = await context.CallActivityAsync<Pago>("ProcesarPago", new { pedido, reserva });
    
    // Paso 4: Enviar confirmación
    await context.CallActivityAsync("EnviarConfirmacion", new { pedido, pago });
    
    return $"Pedido {pedidoId} completado. Pago: {pago.TransaccionId}";
}
```

```csharp
[Function("ValidarPedido")]
public async Task<Pedido> ValidarPedido(
    [ActivityTrigger] string pedidoId)
{
    // Aquí SÍ puedes hacer I/O, llamar a DB, HTTP, etc.
    var pedido = await _cosmos.GetPedidoAsync(pedidoId);
    if (pedido.Items.Count == 0) throw new Exception("Pedido vacío");
    return pedido;
}

[Function("ReservarInventario")]
public async Task<Reserva> ReservarInventario(
    [ActivityTrigger] Pedido pedido)
{
    return await _inventarioService.ReservarAsync(pedido.Items);
}

[Function("ProcesarPago")]
public async Task<Pago> ProcesarPago(
    [ActivityTrigger] dynamic datos)
{
    return await _pagoService.CobrarAsync(datos.pedido, datos.reserva);
}
```

**Si el paso 3 falla**, el Orchestrator lanza excepción. Los pasos 1 y 2 ya se ejecutaron y no se repiten (están en el historial). Podéis implementar compensación (rollback del inventario) en un catch.

## Slide 7 — Patrón 2: Fan-out/Fan-in

Lanzar N tareas en paralelo y esperar a que TODAS terminen:

```csharp
[Function("ProcesarLoteFacturas")]
public static async Task<ResumenLote> ProcesarLote(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var facturaIds = context.GetInput<List<string>>();
    
    // Fan-out: lanzar todas las tareas en paralelo
    var tareas = facturaIds.Select(id => 
        context.CallActivityAsync<ResultadoFactura>("ProcesarFactura", id)
    ).ToList();
    
    // Fan-in: esperar a que TODAS terminen
    var resultados = await Task.WhenAll(tareas);
    
    // Consolidar resultados
    return new ResumenLote
    {
        Total = resultados.Length,
        Exitosas = resultados.Count(r => r.Exito),
        Fallidas = resultados.Count(r => !r.Exito),
        ImporteTotal = resultados.Where(r => r.Exito).Sum(r => r.Importe)
    };
}
```

**Si tenéis 500 facturas**, Azure Functions lanza 500 Activities en paralelo (distribuidas entre instancias). Cuando todas terminan, el Orchestrator recibe los 500 resultados y consolida.

**Control de paralelismo:**
Si 500 es demasiado y saturáis la DB, limitad:
```csharp
// Procesar en lotes de 50
var lotes = facturaIds.Chunk(50);
foreach (var lote in lotes)
{
    var tareas = lote.Select(id => context.CallActivityAsync<Resultado>("Procesar", id));
    await Task.WhenAll(tareas);
}
```

## Slide 8 — Patrón 3: Monitor (polling periódico)

Verificar periódicamente si algo ha terminado:

```csharp
[Function("MonitorizarExportacion")]
public static async Task<string> Monitorizar(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var jobId = context.GetInput<string>();
    var expirationTime = context.CurrentUtcDateTime.AddHours(2);
    
    while (context.CurrentUtcDateTime < expirationTime)
    {
        // Verificar estado
        var estado = await context.CallActivityAsync<string>("CheckEstadoExport", jobId);
        
        if (estado == "completado")
        {
            // Descargar resultado
            var url = await context.CallActivityAsync<string>("DescargarResultado", jobId);
            return $"Exportación completada: {url}";
        }
        
        if (estado == "error")
            throw new Exception($"Exportación {jobId} falló");
        
        // Esperar 5 minutos antes de verificar otra vez
        // NO es Thread.Sleep — el Orchestrator se duerme y no consume recursos
        var nextCheck = context.CurrentUtcDateTime.AddMinutes(5);
        await context.CreateTimer(nextCheck, CancellationToken.None);
    }
    
    throw new TimeoutException($"Exportación {jobId} no completó en 2 horas");
}
```

**La clave:** `context.CreateTimer` no mantiene un proceso vivo. El Orchestrator se duerme completamente y Azure lo despierta cuando el timer expira. Podéis monitorizar algo durante días sin coste.

## Slide 9 — Patrón 4: Human Interaction (esperar aprobación)

```csharp
[Function("PedidoConAprobacion")]
public static async Task<string> PedidoConAprobacion(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var pedido = context.GetInput<Pedido>();
    
    // Si el importe supera 5000€, requiere aprobación del manager
    if (pedido.Total > 5000)
    {
        // Enviar notificación al manager
        await context.CallActivityAsync("NotificarManager", pedido);
        
        // Esperar aprobación (con timeout de 72 horas)
        var aprobado = false;
        using var cts = new CancellationTokenSource();
        var timeout = context.CreateTimer(
            context.CurrentUtcDateTime.AddHours(72), cts.Token);
        var aprobacion = context.WaitForExternalEvent<bool>("AprobacionManager");
        
        var ganador = await Task.WhenAny(aprobacion, timeout);
        
        if (ganador == aprobacion)
        {
            cts.Cancel(); // Cancelar el timer
            aprobado = aprobacion.Result;
        }
        
        if (!aprobado)
        {
            await context.CallActivityAsync("NotificarRechazo", pedido);
            return $"Pedido {pedido.Id} rechazado o expirado";
        }
    }
    
    // Procesar el pedido (aprobado o < 5000€)
    await context.CallActivityAsync("ProcesarPedido", pedido);
    return $"Pedido {pedido.Id} procesado";
}
```

**Enviar la señal de aprobación (desde una API):**
```csharp
[Function("AprobarPedido")]
public async Task<IActionResult> Aprobar(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "pedidos/{instanceId}/aprobar")]
    HttpRequest req, string instanceId,
    [DurableClient] DurableTaskClient client)
{
    await client.RaiseEventAsync(instanceId, "AprobacionManager", true);
    return new OkObjectResult(new { mensaje = "Aprobación enviada" });
}
```

## Slide 10 — Patrón 5: Sub-orquestaciones

Un Orchestrator puede llamar a otro Orchestrator:

```csharp
[Function("ProcesarPedidoCompleto")]
public static async Task ProcesarPedido(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var pedido = context.GetInput<Pedido>();
    
    // Sub-orquestación: procesar pago (tiene su propio flujo)
    var pago = await context.CallSubOrchestratorAsync<Pago>("FlujoDepago", pedido);
    
    // Sub-orquestación: gestionar envío (tiene su propio flujo)
    var envio = await context.CallSubOrchestratorAsync<Envio>("FlujoDeEnvio", 
        new { pedido, pago });
    
    // Notificar
    await context.CallActivityAsync("NotificarCliente", new { pedido, envio });
}
```

Útil para reutilizar flujos y mantener los Orchestrators manejables.

## Slide 11 — Iniciar una orquestación

```csharp
// Starter: la función que inicia la orquestación
[Function("IniciarProcesoPedido")]
public async Task<IActionResult> Iniciar(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "pedidos/procesar")]
    HttpRequest req,
    [DurableClient] DurableTaskClient client)
{
    var pedido = await req.ReadFromJsonAsync<Pedido>();
    
    // Iniciar la orquestación — devuelve un ID único
    var instanceId = await client.ScheduleNewOrchestrationInstanceAsync(
        "OrquestarPedido", pedido);
    
    // Devolver URLs de gestión (status, terminate, send event)
    return new OkObjectResult(new
    {
        instanceId,
        statusUrl = $"/api/pedidos/estado/{instanceId}",
        mensaje = "Orquestación iniciada"
    });
}

// Consultar estado
[Function("EstadoOrquestacion")]
public async Task<IActionResult> Estado(
    [HttpTrigger(AuthorizationLevel.Function, "get", Route = "pedidos/estado/{instanceId}")]
    HttpRequest req, string instanceId,
    [DurableClient] DurableTaskClient client)
{
    var estado = await client.GetInstanceAsync(instanceId);
    
    if (estado is null)
        return new NotFoundResult();
    
    return new OkObjectResult(new
    {
        instanceId,
        runtimeStatus = estado.RuntimeStatus.ToString(),
        input = estado.ReadInputAs<Pedido>(),
        output = estado.ReadOutputAs<string>(),
        createdAt = estado.CreatedAt,
        lastUpdatedAt = estado.LastUpdatedAt
    });
}
```

## Slide 12 — Estados de una orquestación

| Estado | Significado |
|--------|-------------|
| **Pending** | En cola, aún no ha empezado |
| **Running** | Ejecutándose (o esperando a una Activity/timer) |
| **Completed** | Terminó correctamente |
| **Failed** | Terminó con excepción |
| **Terminated** | Cancelada manualmente |
| **Suspended** | Pausada (se puede resumir) |

```bash
# Ver orquestaciones en curso
az functionapp durableorchestration list \
  --name mi-func -g mi-rg \
  --status Running \
  --output table

# Terminar una orquestación
az functionapp durableorchestration terminate \
  --name mi-func -g mi-rg \
  --instance-id "abc-123" \
  --reason "Cancelado por el administrador"

# Purgar historial antiguo
az functionapp durableorchestration purge-history \
  --name mi-func -g mi-rg \
  --created-before "2025-01-01T00:00:00Z"
```

## Slide 13 — Gestión de errores en Durable Functions

```csharp
[Function("OrquestarConReintentos")]
public static async Task<string> Orquestar(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var pedidoId = context.GetInput<string>();
    
    // Retry policy: 3 intentos, backoff exponencial
    var retryPolicy = new TaskOptions(
        new TaskRetryOptions(new RetryPolicy(
            maxNumberOfAttempts: 3,
            firstRetryInterval: TimeSpan.FromSeconds(5),
            backoffCoefficient: 2.0  // 5s, 10s, 20s
        )));
    
    try
    {
        // Activity con reintentos automáticos
        var pedido = await context.CallActivityAsync<Pedido>(
            "ValidarPedido", pedidoId, retryPolicy);
        
        var pago = await context.CallActivityAsync<Pago>(
            "ProcesarPago", pedido, retryPolicy);
        
        return $"Pedido {pedidoId} completado";
    }
    catch (TaskFailedException ex)
    {
        // Después de agotar reintentos
        context.SetCustomStatus("Error: " + ex.Message);
        
        // Compensación: deshacer lo que se hizo
        await context.CallActivityAsync("CompensarPedido", pedidoId);
        
        throw;  // Re-throw marca la orquestación como Failed
    }
}
```

**Patrón Saga (compensación):**
Si el paso 3 falla después de que los pasos 1 y 2 se completaron, necesitáis deshacer los pasos previos (liberar inventario, revertir pago). Esto se llama compensación o patrón Saga.

## Slide 14 — Persistencia y Storage

Durable Functions usa Azure Storage (Table Storage + Queue Storage) para persistir:

- **Historial de ejecución:** cada paso se registra en Table Storage
- **Cola de trabajo:** las Activities se encolan en Queue Storage
- **Estado:** el estado actual de cada orquestación

```json
// host.json — configuración de storage
{
  "extensions": {
    "durableTask": {
      "storageProvider": {
        "connectionStringName": "AzureWebJobsStorage",
        "partitionCount": 4
      },
      "maxConcurrentActivityFunctions": 10,
      "maxConcurrentOrchestratorFunctions": 5
    }
  }
}
```

**Implicación de coste:** Cada Activity genera escrituras en Table Storage y Queue Storage. Para orquestaciones con cientos de pasos, el coste de Storage puede ser significativo. Monitorizar.

## Slide 16 — Cuándo usar Durable Functions y cuándo no

**Usa Durable Functions cuando:**
- Necesitas orquestar múltiples pasos con dependencias
- El flujo puede tardar más de 5-10 minutos
- Necesitas fan-out/fan-in (muchas tareas en paralelo)
- Necesitas esperar a eventos externos (aprobación humana)
- Necesitas monitorización periódica con backoff
- Necesitas compensación/rollback en caso de error

**NO uses Durable Functions cuando:**
- Una función normal basta (< 5 min, sin dependencias entre pasos)
- Solo necesitas encolar trabajo → Service Bus
- Solo necesitas notificar → Event Grid
- El flujo es simple y lineal sin reintentos complejos

**Alternativas:**
- Logic Apps: flujos visuales (low-code), mejor para integraciones con SaaS
- Azure Data Factory: pipelines de datos (ETL)
- Power Automate: automatización de oficina

## Slide 17 — Durable Entities: estado persistente

Las Entities son objetos con estado que persisten entre ejecuciones:

```csharp
// Definir una Entity
[Function(nameof(ContadorEntity))]
public static void ContadorEntity(
    [EntityTrigger] TaskEntityDispatcher dispatcher)
{
    dispatcher.DispatchAsync<ContadorState>();
}

public class ContadorState
{
    public int Valor { get; set; }
    
    public void Incrementar() => Valor++;
    public void Reset() => Valor = 0;
    public int Get() => Valor;
}
```

```csharp
// Usar la entity desde un orchestrator o función
[Function("IncrementarContador")]
public async Task Incrementar(
    [HttpTrigger(AuthorizationLevel.Anonymous, "post")] HttpRequest req,
    [DurableClient] DurableTaskClient client)
{
    var entityId = new EntityInstanceId(nameof(ContadorEntity), "visitas-hoy");
    await client.Entities.SignalEntityAsync(entityId, "Incrementar");
}

[Function("GetContador")]
public async Task<IActionResult> Get(
    [HttpTrigger(AuthorizationLevel.Anonymous, "get")] HttpRequest req,
    [DurableClient] DurableTaskClient client)
{
    var entityId = new EntityInstanceId(nameof(ContadorEntity), "visitas-hoy");
    var state = await client.Entities.GetEntityAsync<ContadorState>(entityId);
    return new OkObjectResult(new { visitas = state?.State?.Valor ?? 0 });
}
```

**Casos de uso:** Contadores, agregaciones en tiempo real, estado de sesión, locks distribuidos, carritos de compra.

## Slide 18 — Eternal Orchestrations: procesos que nunca terminan

Para procesos que deben monitorizar indefinidamente:

```csharp
[Function("MonitorizarServicio")]
public static async Task Monitorizar(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var servicio = context.GetInput<string>();
    
    while (true)
    {
        var estado = await context.CallActivityAsync<string>("CheckHealth", servicio);
        
        if (estado != "healthy")
        {
            await context.CallActivityAsync("EnviarAlerta", 
                new { servicio, estado, hora = context.CurrentUtcDateTime });
        }
        
        // Esperar 5 minutos (sin consumir recursos)
        await context.CreateTimer(context.CurrentUtcDateTime.AddMinutes(5), CancellationToken.None);
        
        // ContinueAsNew: reinicia la orquestación limpiando el historial
        // Sin esto, el historial crece indefinidamente y consume storage
        context.ContinueAsNew(servicio);
    }
}
```

**`ContinueAsNew` es crítico.** Sin él, el historial de la orquestación crece con cada iteración hasta que el rendimiento se degrada. Con él, se reinicia limpio cada vez.

## Slide 19 — Timeouts y cancelación

```csharp
[Function("ProcesoConTimeout")]
public static async Task<string> ConTimeout(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    using var cts = new CancellationTokenSource();
    
    // Crear timer de timeout (30 minutos)
    var timeout = context.CreateTimer(
        context.CurrentUtcDateTime.AddMinutes(30), cts.Token);
    
    // Lanzar el trabajo real
    var trabajo = context.CallActivityAsync<string>("TrabajoLargo", "datos");
    
    // Esperar al primero que termine
    var ganador = await Task.WhenAny(trabajo, timeout);
    
    if (ganador == trabajo)
    {
        cts.Cancel();  // Cancelar el timer
        return trabajo.Result;
    }
    else
    {
        // Timeout — cancelar y compensar
        await context.CallActivityAsync("CancelarTrabajo", "datos");
        throw new TimeoutException("El proceso no completó en 30 minutos");
    }
}
```

## Slide 20 — Versioning de orquestaciones

Cuando cambiáis la lógica de un orchestrator que tiene instancias en ejecución:

**Problema:** Las instancias que están a mitad de ejecución esperan que el código sea el mismo que cuando empezaron (replay).

**Solución — Side-by-side:**
```csharp
// Versión 1 (instancias existentes)
[Function("OrquestarPedido")]
public static async Task OrquestarPedidoV1(...) { ... }

// Versión 2 (nuevas instancias)
[Function("OrquestarPedidoV2")]
public static async Task OrquestarPedidoV2(...) { ... }
```

Iniciáis nuevas instancias con V2. Las V1 que están en ejecución terminan con el código V1. Cuando no queden V1 activas, eliminais la función V1.

## Slide 21 — Performance: mejores prácticas

**1. Activities pequeñas y rápidas**
Una Activity que tarda 30 minutos es una señal de que debería partirse en varias.

**2. Fan-out con control de paralelismo**
```csharp
// No lanzar 10.000 activities a la vez — saturáis el storage
var batches = items.Chunk(100);
foreach (var batch in batches)
{
    var tasks = batch.Select(i => context.CallActivityAsync("Procesar", i));
    await Task.WhenAll(tasks);
}
```

**3. Purgar historial antiguo**
```bash
az functionapp durableorchestration purge-history --name mi-func -g mi-rg \
  --created-before "2025-01-01T00:00:00Z"
```
El historial consume Table Storage. Purgad periódicamente.

**4. maxConcurrentActivityFunctions**
```json
// host.json
{ "extensions": { "durableTask": { "maxConcurrentActivityFunctions": 10 } } }
```
Limitar si las activities consumen muchos recursos (DB, API externa).

## Slide 22 — Task Hubs: aislamiento y naming

El Task Hub es el nombre lógico de una instancia de Durable Functions dentro del Storage account:

```json
// host.json
{
  "version": "2.0",
  "extensions": {
    "durableTask": {
      "hubName": "TaskHubProduccion"
    }
  }
}
```

**Qué es un Task Hub internamente:**
```
Storage Account
└── Tablas:
    ├── <HubName>History          ← eventos de orquestaciones
    ├── <HubName>Instances        ← estado actual de cada instancia
    └── <HubName>NewEvents        ← eventos pendientes
└── Queues:
    ├── <HubName>-control-00..03  ← control queues (partitioned)
    └── <HubName>-workitems       ← actividades a ejecutar
└── Blob containers:
    └── <HubName>-largemessages   ← payloads grandes
```

**Reglas de Task Hub:**
```
- Nombre: alfanuméricos, 3-45 chars, NO guiones
- Si múltiples Functions comparten mismo Storage + mismo HubName:
  → comparten estado (peligroso, pueden robarse orquestaciones)
- Environment (Dev/Test/Prod) → hub diferente por env
- Naming convention: <entorno>-<app>-<hub>
  ej: "prodPedidosHub", "devPedidosHub"
```

**Aislamiento por entorno:**
```csharp
// Program.cs — leer hub name de App Settings
builder.Services.AddDurableTaskClient(builder =>
{
    builder.UseStorage(storageConnection);
    builder.UseHubName(Environment.GetEnvironmentVariable("HUB_NAME") 
                       ?? "DefaultHub");
});

// App Settings por entorno:
// Dev:  HUB_NAME = "DevHub"
// Prod: HUB_NAME = "ProdHub"
```

**Gotcha real:** cambiar hub name → orquestaciones en curso quedan huérfanas (no se pierden datos, pero ya no se ejecutan). Siempre drain antes de cambiar.

## Slide 23 — Storage providers: Storage, Netherite, MSSQL

Durable Functions soporta 3 backends diferentes (GA 2022+):

```
┌─────────────────┬──────────────────┬──────────────────┬──────────────────┐
│                 │ Azure Storage    │ Netherite        │ MSSQL            │
├─────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Default         │ ✅ Sí            │ ❌               │ ❌               │
```

## Slide 24 — Durable Task Scheduler (preview 2025)

Microsoft anunció en 2025 **Durable Task Scheduler** — servicio gestionado separado de Functions:

```
Durable Functions (clásico):
```

| Monitoring | Ajustar vosotros | Built-in |

```csharp
[Function(nameof(ApprovalWorkflowOrchestrator))]

    var solicitud = ctx.GetInput<SolicitudVacaciones>();
    
    // 1. Notificar al manager
    await ctx.CallActivityAsync("NotificarManager", solicitud);
    
    // 2. Esperar respuesta (con timeout)

        "ManagerApproval", 
        TimeSpan.FromDays(7));

            await ctx.CallActivityAsync("ConfirmarVacaciones", solicitud);
        else
            await ctx.CallActivityAsync("NotificarRechazo", solicitud);
    }
    else
    {
        // Timeout: escalado automático al director
        await ctx.CallActivityAsync("EscalarADirector", solicitud);
    }
}

await _durableClient.RaiseEventAsync(
```

## Slide 26 — Sub-orchestrations avanzado

Orquestadores que llaman a otros orquestadores → modularización:

```csharp
// Orchestrator padre
[Function(nameof(ProcesarPedidoCompleto))]
public async Task ProcesarPedidoCompleto(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var pedido = ctx.GetInput<Pedido>();
    
    // 1. Validar (sub-orchestrator)
    var validado = await ctx.CallSubOrchestratorAsync<bool>(
        "ValidarPedidoOrchestrator", pedido);
    
    if (!validado) return;
    
    // 2. Reserva + Pago en paralelo (sub-orchestrators)
    var reservaTask = ctx.CallSubOrchestratorAsync<ReservaResult>(
        "ReservaOrchestrator", pedido);
    var pagoTask = ctx.CallSubOrchestratorAsync<PagoResult>(
        "PagoOrchestrator", pedido);
    
    await Task.WhenAll(reservaTask, pagoTask);
    
    // 3. Envío (si ambos OK)
    if (reservaTask.Result.Ok && pagoTask.Result.Ok)
        await ctx.CallSubOrchestratorAsync("EnvioOrchestrator", pedido);
}

// Sub-orchestrator "ValidarPedidoOrchestrator"
[Function(nameof(ValidarPedidoOrchestrator))]
public async Task<bool> ValidarPedidoOrchestrator(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var pedido = ctx.GetInput<Pedido>();
    
    // Lógica compleja de validación
    var precioOk = await ctx.CallActivityAsync<bool>("ValidarPrecio", pedido);
    var stockOk = await ctx.CallActivityAsync<bool>("ValidarStock", pedido);
    var clienteOk = await ctx.CallActivityAsync<bool>("ValidarCliente", pedido);
    
    return precioOk && stockOk && clienteOk;
}
```

**Ventajas:**
- **Modularidad**: cada sub-orchestrator es testeable independientemente
- **Reusabilidad**: ValidarPedidoOrchestrator reutilizable en otros flows
- **Observabilidad**: en el dashboard cada sub se ve como instancia hija

**Gotchas:**
- Each sub-orchestration = nueva instance ID en historial
- Overhead pequeño (1-2 storage ops por call)
- El parent espera al child — cuidado con timeouts

## Slide 27 — Durable Entities: estado persistente con lógica

Las Durable Entities son "actores" con estado — pequeños agregados:

```csharp
// Definición de la entity
[Function(nameof(CounterEntity))]
public void CounterEntity(
    [EntityTrigger] TaskEntityDispatcher dispatcher)
{
    dispatcher.DispatchAsync<Counter>();
}

public class Counter
{
    public int Value { get; set; }
    
    public void Increment() => Value++;
    public void Decrement() => Value--;
    public void Reset() => Value = 0;
    public int Get() => Value;
}

// Invocar la entity desde un orchestrator
[Function(nameof(OrchestratorConCounter))]
public async Task OrchestratorConCounter(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var entityId = new EntityInstanceId("Counter", "global-counter");
    
    // Fire-and-forget
    ctx.SignalEntity(entityId, "increment");
    ctx.SignalEntity(entityId, "increment");
    
    // Request-response
    var currentValue = await ctx.CallEntityAsync<int>(entityId, "get");
}

// Desde HTTP trigger (DurableTaskClient)
[Function(nameof(GetCounterValue))]
public async Task<IActionResult> GetCounterValue(
    [HttpTrigger("get", Route = "counters/{id}")] HttpRequestData req,
    [DurableClient] DurableTaskClient client,
    string id)
{
    var entityId = new EntityInstanceId("Counter", id);
    var state = await client.Entities.GetEntityAsync<Counter>(entityId);
    return new OkObjectResult(new { value = state?.State?.Value ?? 0 });
}
```

**Casos de uso reales:**

| Entity | Ejemplo concreto |
|---|---|
| Shopping cart | Items por usuario, TTL 30 min |
| Contador distribuido | Rate limiting, métricas |
| Aggregator | Acumulación de eventos por tenant |
| State machine | Workflow con estados (draft → review → approved) |
| Locks distribuidos | Sección crítica entre orquestaciones |

**Limitaciones:**
- Una entity procesa mensajes uno-a-uno (no paralelismo interno)
- No son para high-throughput counters (usad Redis/Cosmos)
- Gotcha: entity "muere" si no se usa ~30 días → re-hidrata desde historial

## Slide 28 — Correlation IDs y distributed tracing

En sistemas con orquestadores + actividades + external services, tracing es vital:

```csharp
[Function(nameof(OrchestratorConTracing))]
public async Task OrchestratorConTracing(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    // Durable Functions propaga automáticamente:
    // - TraceId (W3C)
    // - ParentSpanId
    // - InstanceId (ctx.InstanceId)
    
    _logger.LogInformation(
        "Orchestrator started. InstanceId: {id}, TraceId: {trace}",
        ctx.InstanceId, 
        Activity.Current?.TraceId);
    
    // Activity 1: cada activity se correlaciona automáticamente
    var result1 = await ctx.CallActivityAsync<string>("Activity1", input);
    
    // HTTP externo: propagar el tracing
    var result2 = await ctx.CallActivityAsync<string>(
        "CallExternalApi", 
        new { 
            endpoint = "https://api.partner.com/data",
            traceparent = Activity.Current?.Id  // W3C header
        });
}

// En la activity que llama a API externa:
[Function(nameof(CallExternalApi))]
public async Task<string> CallExternalApi(
    [ActivityTrigger] dynamic input)
{
    var httpClient = new HttpClient();
    var request = new HttpRequestMessage(HttpMethod.Get, (string)input.endpoint);
    
    // Propagar W3C trace header
    request.Headers.Add("traceparent", (string)input.traceparent);
    
    var response = await httpClient.SendAsync(request);
    return await response.Content.ReadAsStringAsync();
}
```

## Slide 30 — Retry policies avanzadas en Durable

Durable Functions tiene retry policies más ricas que las básicas:

```csharp
// Retry con backoff exponencial + max attempts
var options = TaskOptions.FromRetryPolicy(new RetryPolicy(
    maxNumberOfAttempts: 5,
    firstRetryInterval: TimeSpan.FromSeconds(2),
    backoffCoefficient: 2.0,           // 2s, 4s, 8s, 16s, 32s
    maxRetryInterval: TimeSpan.FromMinutes(5),
    retryTimeout: TimeSpan.FromMinutes(10)));

await ctx.CallActivityAsync("FlakeyActivity", input, options);

// Retry condicional (solo para ciertas excepciones)
var policy = new RetryPolicy(
    maxNumberOfAttempts: 3,
    firstRetryInterval: TimeSpan.FromSeconds(5))
{
    Handle = ex => ex is HttpRequestException  // solo transient HTTP
              && ex.Message.Contains("503")   // 503 Service Unavailable
};

await ctx.CallActivityAsync("CallExternalApi", input, 
    TaskOptions.FromRetryPolicy(policy));
```

**Patrón "Retry with compensation":**
```csharp
var attempts = 0;
while (attempts < maxAttempts)
{
    try
    {
        return await ctx.CallActivityAsync<Result>("RiskyOperation", input);
    }
    catch (TaskFailedException ex) when (attempts < maxAttempts - 1)
    {
        // Log + cleanup before next attempt
        await ctx.CallActivityAsync("CleanupFailedAttempt", 
            new { attempt = attempts, error = ex.Message });
        
        await ctx.CreateTimer(
            ctx.CurrentUtcDateTime.AddSeconds(Math.Pow(2, attempts)),
            CancellationToken.None);
        
        attempts++;
    }
}
throw new InvalidOperationException("All retries exhausted");
```

**Circuit breaker pattern:**
```csharp
// Si una activity falla mucho, usar entidad "CircuitBreaker"
var breakerState = await ctx.CallEntityAsync<string>(

if (breakerState == "OPEN")

else
{

    {

        // Success: reset breaker

                        "success");
    }

    }
}
```

## Slide 31 — Versioning: estrategias reales

Actualizar código de un orchestrator en producción sin romper instancias en curso:

```
Escenario: versión 1 corre instance A
           Despliegas versión 2
           Instance A sigue con la versión 1 (replay usa histórico)
           Nueva instance B usa versión 2

Problema: si quitáis una línea de código,
          replay de A no encuentra el call → INCONSISTENT_REPLAY error
```

**3 estrategias:**

**1. Versioning por Hub Name (la más agresiva):**
```json
// Versión 2 usa un nuevo hub
{
  "extensions": {
    "durableTask": {
      "hubName": "MyHub-v2"  // era "MyHub"
    }
  }
}
// Instancias v1 quedan huérfanas (drain manual)
// Instancias v2 empiezan fresh
```

**2. Versioning por función (paralelo):**
```csharp
// Ambas versiones coexisten
[Function(nameof(OrchestratorV1))]
public Task OrchestratorV1(...) { /* código viejo */ }

[Function(nameof(OrchestratorV2))]
public Task OrchestratorV2(...) { /* código nuevo */ }

// Nuevas invocaciones usan V2, las en curso terminan en V1
// Quitas V1 cuando no queden instances ejecutándose
```

**3. Feature flags dentro del orchestrator:**
```csharp
[Function(nameof(MiOrchestrator))]
public async Task MiOrchestrator(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var version = ctx.GetInput<InputDto>().Version;
    
    if (version >= 2)
    {
        // nueva lógica
        await ctx.CallActivityAsync("NuevaActividad", input);
    }
    else
    {
        // vieja lógica (compat)
        await ctx.CallActivityAsync("ViejaActividad", input);
    }
}
```

**Recomendación:** para cambios simples, feature flags. Para rediseños, versioning por función. Para mayor claridad, nuevo hub.

## Slide 32 — Performance: límites y tuning

Durable Functions tiene límites que afectan a escala:

```
Defaults (ajustables en host.json):

Control queues: 4 partitions
  → max orchestrators en paralelo: 4 × instances Functions
  → Para 1000 orq concurrentes con 10 instances, subir a 16 partitions

ActivityTask max concurrency:
  → Consumption: 10 per instance
  → Premium/Flex: más alta, ajustable

ControlQueue:
  → control de orquestaciones
  → cada control msg es ~4KB
  → throughput limitado por Storage queue
```

**Tuning host.json:**
```json
{
  "extensions": {
    "durableTask": {
      "hubName": "MyHub",
      "storageProvider": {
        "partitionCount": 16,
        "controlQueueBatchSize": 64,
        "controlQueueBufferThreshold": 256
      },
      "maxConcurrentActivityFunctions": 50,
      "maxConcurrentOrchestratorFunctions": 200,
      "extendedSessionsEnabled": true,
      "extendedSessionIdleTimeoutInSeconds": 30
    }
  }
}
```

**Benchmarks típicos:**

| Setup | Orquestaciones concurrentes | Activities/s |
|---|---:|---:|
| Consumption + Storage default | 50-100 | 200-500 |
| Premium + Storage optimizado | 1K-5K | 5K-20K |
| Premium + Netherite | 10K+ | 50K+ |
| Flex Consumption 2026 | 1K-3K | 2K-10K |

**Anti-patterns que matan performance:**

```csharp
// ❌ Orchestrator pesado (lógica de negocio dentro)
public async Task Orchestrator(...)
{
    for (int i = 0; i < 1000; i++)
    {
        var data = HeavyComputation();  // MAL: replay repite esto
    }
}

// ✅ Orchestrator ligero (solo coordina)
public async Task Orchestrator(...)
{
    var batches = await ctx.CallActivityAsync("GenerateBatches", input);
    // Activities hacen el trabajo pesado
}

// ❌ Muchas activities pequeñas
for (int i = 0; i < 10000; i++)
    await ctx.CallActivityAsync("ProcessOne", items[i]);

// ✅ Fan-out/fan-in con batches
var batches = items.Chunk(100);
var tasks = batches.Select(b => ctx.CallActivityAsync("ProcessBatch", b));
await Task.WhenAll(tasks);
```

```csharp
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var fecha = ctx.GetInput<DateTime>();
    
    // 1. Listar archivos a procesar
    var files = await ctx.CallActivityAsync<string[]>(

    var tasks = files.Select(f =>

    await ctx.CallActivityAsync("EnviarReporte", summary);
}
```

```csharp
[Function(nameof(SyncConMarketplace))]
public async Task SyncConMarketplace(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var productos = await ctx.CallActivityAsync<Producto[]>("GetProductos", null);
    
    // API externa limita 100 req/s — procesamos en batches con throttling
    foreach (var batch in productos.Chunk(100))
    {
        var tasks = batch.Select(p => 
            ctx.CallActivityAsync("UploadProducto", p));
        await Task.WhenAll(tasks);
        
        // Esperar 1s antes de siguiente batch (rate limiting)

    }
}
```

## Slide 34 — Migration de v2 a v3: Isolated Worker

Cambio importante: Durable Functions tiene dos sabores de SDK:

```
v2 (In-process): deprecated 2026
├── Using Microsoft.Azure.WebJobs.Extensions.DurableTask
├── Mismos packages que runtime Functions
└── Sharing AppDomain con host → limitaciones

v3 (Isolated Worker): recomendado
├── Using Microsoft.DurableTask y Microsoft.DurableTask.Worker.AzureFunctions
├── Proceso separado del host
├── .NET 8/9/10 libremente
├── Mejor observability
└── API ligeramente diferente
```

**Migración código — antes/después:**

```csharp
// v2 (in-process)
public static class Orchestrator
{
    [FunctionName("Orchestrator")]
    public static async Task<string> Run(
        [OrchestrationTrigger] IDurableOrchestrationContext context)
    {
        var result = await context.CallActivityAsync<string>("Activity", "input");
        return result;
    }
}

// v3 (isolated)
public class Orchestrator
{
    [Function(nameof(Run))]
    public async Task<string> Run(
        [OrchestrationTrigger] TaskOrchestrationContext ctx)
    {
        var result = await ctx.CallActivityAsync<string>("Activity", "input");
        return result;
    }
}
```

**Cambios clave en v3:**
- `IDurableOrchestrationContext` → `TaskOrchestrationContext`
- `[FunctionName("X")]` → `[Function("X")]`
- `Task<ActivityResult> context.CallActivityAsync<T>` — API idéntica
- Entity y Client APIs con nombres diferentes
- Registration en Program.cs explícita

**Pasos para migrar:**
1. Mover proyecto a Isolated Worker
2. Actualizar paquetes a `Microsoft.DurableTask.*`
3. Renombrar contextos y atributos
4. Testing exhaustivo — ¡stateful!
5. Deploy con nuevo Hub Name para aislamiento

**Para el curso: todo en v3** desde el principio. v2 está deprecated.

## Slide 35 — Testing Durable Functions

## Slide 36 — Durable Functions: cuándo NO usarlas

Importante conocer los límites — Durable no es oro para todo:

**❌ NO usar Durable cuando:**

```
1. Simple fan-out sin coordinación
   → Usad ServiceBus topic + queues + Functions normales
   → Menos overhead, más simple

2. Real-time low-latency (< 100ms)
   → Storage ops + replay añaden latencia
   → Durable tiene overhead ~50-200ms por call
   → Para tiempo real: Event Hubs + Stream Analytics

3. Transformaciones stateless
   → Una Function normal basta
   → No necesitáis workflow si son pasos independientes

4. Trabajos periódicos simples
   → Timer Trigger + lógica lineal
   → Durable solo si necesitáis fan-out

5. Cuando no hay estado compartido entre pasos
   → Cola de mensajes es suficiente

6. Volumen extremo (>100K orquestaciones/s)
   → Storage backend no escala tanto
   → Netherite o arquitectura custom
```

**✅ SÍ usar Durable cuando:**

```
1. Long-running (minutos → días)
   → Approval workflows, sagas

2. Coordinación entre pasos con estado
   → ETL: "procesar N archivos Y luego agregar"

3. Waiting for external event
   → "Esperar hasta que llegue X, o timeout"

4. Fan-out/fan-in con límites externos
   → Rate limiting, batch sizes

5. Sagas transaccionales
   → Compensación automática ante fallos

6. Workflows visualizables / auditables
   → Dashboard, historial consultable
```

**Diagrama de decisión:**
```
¿Necesitas estado entre pasos?
├── NO → Function normal o messaging
└── SÍ → ¿Es coordinación de pasos?
    ├── NO, solo contador/estado → Durable Entity
    └── SÍ, workflow → ¿Short (segundos) o Long (min/h)?
        ├── Short → Orchestration con Storage
        └── Long → Orchestration + considerar Netherite
```

## Slide 37 — Cierre del submódulo
Durable Functions convierte Azure Functions en un motor de workflows. Los 5 patrones (chaining, fan-out/fan-in, monitor, human interaction, sub-orchestrations) más Entities para estado y Eternal Orchestrations para procesos permanentes cubren prácticamente cualquier flujo de negocio.

Lo crítico: el Orchestrator es determinista (sin I/O directo), las Activities hacen el trabajo real, y el estado se persiste automáticamente. ContinueAsNew para orquestaciones de larga duración, y purgar historial periódicamente.

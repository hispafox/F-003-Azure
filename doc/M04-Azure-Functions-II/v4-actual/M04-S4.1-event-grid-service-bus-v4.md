## Slide 2 — De triggers aislados a sistemas conectados
En el módulo 3 construimos funciones individuales: una reacciona a HTTP, otra a un timer, otra a un blob. Cada una hace su trabajo y termina.

En producción real, las funciones no trabajan solas. Necesitan comunicarse entre sí y con otros servicios. Ahí entran dos herramientas fundamentales: **Event Grid** (eventos) y **Service Bus** (mensajes).

La diferencia parece sutil pero es crucial:
- **Evento:** "Ha pasado algo" — le interese a quien le interese
- **Mensaje:** "Haz esto" — dirigido a un destinatario concreto


---

## Slide 3 — Eventos vs Mensajes: la diferencia que importa

**Eventos (Event Grid):**
- Notifican que algo ocurrió: "Se creó un blob", "Se modificó un recurso"
- El emisor no sabe ni le importa quién escucha
- Puede haber 0, 1 o 100 suscriptores
- Semántica: "esto pasó, por si os interesa"
- Entrega: best-effort con reintentos (at-least-once)

**Mensajes (Service Bus):**
- Envían una instrucción: "Procesa este pedido", "Envía este email"
- El emisor espera que alguien lo procese
- Exactamente un consumidor procesa cada mensaje
- Semántica: "haz esto"
- Entrega: garantizada con FIFO, transacciones y dead-letter

**Regla práctica:**
- ¿Quiero notificar? → Event Grid
- ¿Quiero encolar trabajo? → Service Bus

## Slide 4 — Azure Event Grid: visión general

Event Grid es un servicio de enrutamiento de eventos serverless:

```
FUENTE DE EVENTOS          EVENT GRID           SUSCRIPTORES
┌──────────────┐          ┌──────────┐         ┌──────────────┐
│ Blob Storage │──evento──│          │──push──→│ Function A   │
│ Cosmos DB    │──evento──│  Event   │──push──→│ Function B   │
│ Resource Mgr │──evento──│  Grid    │──push──→│ Logic App    │
│ Custom app   │──evento──│  (router)│──push──→│ Webhook      │
│ IoT Hub      │──evento──│          │──push──→│ Event Hub    │
└──────────────┘          └──────────┘         └──────────────┘
```

**Características clave:**
- Latencia < 1 segundo (típicamente ~100ms)
- Escala automáticamente a millones de eventos/segundo
- Modelo push (Event Grid envía al suscriptor, no al revés)
- Reintentos con backoff exponencial
- Dead-lettering para eventos no entregados
- Filtrado de eventos en el suscriptor

Muchos servicios Azure emiten eventos automáticamente:

|--------|---------|-------------|

**Para vuestro equipo:** El más relevante es **Blob Storage → BlobCreated** como alternativa al Blob Trigger (más rápido y fiable que polling).

```csharp
        _logger.LogInformation("  Tipo: {ContentType}", datos.ContentType);
        
        // Procesar el blob...
    }
}
```

## Slide 7 — Event Grid vs Blob Trigger: comparativa directa

| Característica | Blob Trigger (polling) | Event Grid Trigger |
|----------------|:---------------------:|:------------------:|
| Latencia | 1-10 minutos | < 1 segundo |
| Fiabilidad alto volumen | Media | Alta |
| Configuración | Simple (1 atributo) | Requiere subscription |
| Recibe contenido del blob | Sí (stream directo) | No (recibe URL, tú lo descargas) |
| Coste adicional | Ninguno | ~0.50€/millón de eventos |
| Requiere Storage Account | Sí (para leases) | No |
| Detección de subcarpetas | Sí | Sí (con filtros) |

**¿Cuándo usar cada uno?**
- Blob Trigger: desarrollo, bajo volumen, quieres el contenido directamente
- Event Grid: producción, alto volumen, baja latencia, necesitas fiabilidad

## Slide 8 — Crear una suscripción de Event Grid

```bash
# Crear suscripción: cuando se crea un blob en "uploads" → dispara la función
az eventgrid event-subscription create \
  --name sub-blob-uploads \
  --source-resource-id "/subscriptions/<id>/resourceGroups/mi-rg/providers/Microsoft.Storage/storageAccounts/mistorage" \
  --endpoint "https://mi-func.azurewebsites.net/runtime/webhooks/eventgrid?functionName=BlobCreadoViaEventGrid&code=<system-key>" \
  --endpoint-type webhook \
  --included-event-types Microsoft.Storage.BlobCreated \
  --subject-begins-with "/blobServices/default/containers/uploads/"
```

**Filtros disponibles:**
- `--included-event-types`: solo ciertos tipos de evento
- `--subject-begins-with`: solo blobs en cierta ruta
- `--subject-ends-with`: solo ciertos tipos de archivo (`.csv`, `.pdf`)
- `--advanced-filter`: filtros sobre propiedades del evento

## Slide 9 — Eventos custom: emitir desde tu app

Podéis crear vuestros propios eventos:

```csharp
// Publicar un evento custom
public class EventPublisher
{
    private readonly EventGridPublisherClient _client;
    
    public EventPublisher(EventGridPublisherClient client) => _client = client;
    
    public async Task PublicarPedidoCreado(Pedido pedido)
    {
        var evento = new EventGridEvent(
            subject: $"/pedidos/{pedido.Id}",
            eventType: "Tienda.Pedido.Creado",
            dataVersion: "1.0",
            data: new {
                pedidoId = pedido.Id,
                clienteId = pedido.ClienteId,
                total = pedido.Total,
                items = pedido.Items.Count
            });
        
        await _client.SendEventAsync(evento);
    }
}
```

```bash
# Crear un Topic custom
az eventgrid topic create \
  --name topic-pedidos \
  --resource-group mi-rg \
  --location westeurope
```

**Patrón:** Tu API crea un pedido → publica evento "PedidoCreado" → N suscriptores reaccionan (enviar email, actualizar inventario, generar factura). La API no sabe ni le importa cuántos suscriptores hay.

## Slide 10 — Azure Service Bus: visión general

Service Bus es un broker de mensajería enterprise:

```
EMISOR                    SERVICE BUS              CONSUMIDOR
┌──────────┐             ┌──────────────┐         ┌──────────┐
│ API      │──mensaje──→ │  QUEUE       │──pull──→│ Function │
│ Function │──mensaje──→ │  (1 a 1)     │         │ (uno)    │
└──────────┘             └──────────────┘         └──────────┘

┌──────────┐             ┌──────────────┐         ┌──────────┐
│ API      │──mensaje──→ │  TOPIC       │──pull──→│ Func A   │
│          │             │  ├─ Sub A ────┼────────→│ (sub A)  │
│          │             │  └─ Sub B ────┼────────→│ Func B   │
└──────────┘             └──────────────┘         └──────────┘
```

**Queue:** Un mensaje → un consumidor. El primer consumidor que lo lee, lo procesa. FIFO.
**Topic + Subscriptions:** Un mensaje → múltiples suscriptores. Cada suscripción recibe una copia.


---

## Slide 11 — Queue vs Topic: cuándo usar cada uno

| | Queue | Topic |
|---|:---:|:---:|
| Consumidores | 1 | N (uno por suscripción) |
| Semántica | "Procesa esto" | "Ha pasado esto, reaccionad" |
| Ejemplo | "Envía este email" | "Pedido creado" → email + factura + inventario |
| Orden | FIFO garantizado (con sessions) | FIFO por suscripción |
| Filtrado | No | Sí (SQL-like filters en suscripciones) |

**Regla:**
- ¿Solo un consumidor necesita este mensaje? → **Queue**
- ¿Varios consumidores necesitan reaccionar? → **Topic + Subscriptions**

## Slide 12 — Service Bus Trigger en Azure Functions

```csharp
public class ProcesadorPedidos
{
    private readonly ILogger<ProcesadorPedidos> _logger;
    private readonly IEmailService _email;

    public ProcesadorPedidos(ILogger<ProcesadorPedidos> logger, IEmailService email)
    {
        _logger = logger;
        _email = email;
    }

    // Trigger de Queue
    [Function("ProcesarPedidoCola")]
    public async Task ProcesarDeCola(
        [ServiceBusTrigger("pedidos-a-procesar", Connection = "ServiceBusConnection")]
        ServiceBusReceivedMessage mensaje)
    {
        var pedido = mensaje.Body.ToObjectFromJson<PedidoMensaje>();
        
        _logger.LogInformation("Procesando pedido {Id} de la cola", pedido.Id);
        
        await _email.EnviarConfirmacionAsync(pedido.ClienteEmail, pedido.Id);
        
        _logger.LogInformation("Pedido {Id} procesado", pedido.Id);
    }

    // Trigger de Topic + Subscription
    [Function("NotificarPedidoTopic")]
    public async Task NotificarDeTopic(
        [ServiceBusTrigger("pedidos-eventos", "sub-notificaciones", 
            Connection = "ServiceBusConnection")]
        ServiceBusReceivedMessage mensaje)
    {
        var evento = mensaje.Body.ToObjectFromJson<PedidoEvento>();
        _logger.LogInformation("Notificación de pedido {Id}: {Tipo}", evento.PedidoId, evento.Tipo);
    }
}
```

## Slide 13 — Service Bus Output Binding

```csharp
// Enviar mensajes a Service Bus desde una función
[Function("CrearPedido")]
[ServiceBusOutput("pedidos-a-procesar", Connection = "ServiceBusConnection")]
public string CrearPedido(
    [HttpTrigger(AuthorizationLevel.Function, "post", Route = "pedidos")] 
    HttpRequest req)
{
    var pedido = req.ReadFromJsonAsync<CrearPedidoDto>().Result;
    pedido!.Id = Guid.NewGuid().ToString();
    
    // El return va directamente a la cola de Service Bus
    return JsonSerializer.Serialize(new {
        id = pedido.Id,
        clienteEmail = pedido.Email,
        total = pedido.Total,
        creadoEn = DateTime.UtcNow
    });
}
```

**Flujo completo:**
```
POST /api/pedidos → Function (HTTP) → Service Bus Queue → Function (SB Trigger) → Email
```

La API responde inmediatamente al cliente. El procesamiento pesado (enviar email, generar factura) ocurre de forma asíncrona en la cola.

## Slide 15 — Propiedades del mensaje Service Bus

```csharp
[Function("EnviarMensajeAvanzado")]
public async Task Enviar(
    [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequest req,
    [ServiceBusOutput("pedidos-a-procesar", Connection = "ServiceBusConnection")]
    OutputBinding<ServiceBusMessage> output)
{
    var pedido = await req.ReadFromJsonAsync<PedidoDto>();
    
    var mensaje = new ServiceBusMessage(JsonSerializer.Serialize(pedido))
    {
        ContentType = "application/json",
        MessageId = pedido!.Id,                    // Deduplicación
        Subject = "pedido-nuevo",                  // Label/filtro
        CorrelationId = Guid.NewGuid().ToString(), // Trazabilidad
        TimeToLive = TimeSpan.FromDays(7),         // Expira en 7 días
        ScheduledEnqueueTime = DateTimeOffset.UtcNow.AddMinutes(5), // Entrega diferida
        ApplicationProperties = {
            ["prioridad"] = "alta",
            ["region"] = "europa",
            ["version"] = "2.0"
        }
    };
    
    output.SetValue(mensaje);
}
```

**Propiedades útiles:**
- `MessageId`: deduplicación (Service Bus descarta duplicados con el mismo ID)
- `ScheduledEnqueueTime`: programar entrega futura
- `TimeToLive`: mensaje expira y va a dead-letter si no se procesa
- `ApplicationProperties`: metadata custom para filtrado

## Slide 16 — Filtros en suscripciones de Topics

```bash
# Crear filtro SQL: solo pedidos de más de 100€
az servicebus topic subscription rule create \
  --namespace-name sb-ventas-prod \
  --resource-group mi-rg \
  --topic-name pedidos-eventos \
  --subscription-name sub-facturacion \
  --name filtro-importe-alto \
  --filter-sql-expression "total > 100"

# Crear filtro por propiedad custom
az servicebus topic subscription rule create \
  --namespace-name sb-ventas-prod \
  --resource-group mi-rg \
  --topic-name pedidos-eventos \
  --subscription-name sub-notificaciones \
  --name filtro-prioridad-alta \
  --filter-sql-expression "prioridad = 'alta'"
```

**Resultado:** La suscripción `sub-facturacion` solo recibe pedidos > 100€. La suscripción `sub-notificaciones` solo recibe mensajes con prioridad alta. Filtrado en el broker, no en tu código.

## Slide 17 — Sessions: orden garantizado

Por defecto, Service Bus procesa mensajes en cualquier orden (parallel). Si necesitáis FIFO por entidad:

```bash
# Crear cola con sessions habilitadas
az servicebus queue create \
  --namespace-name sb-ventas-prod \
  --resource-group mi-rg \
  --name pedidos-ordenados \
  --enable-session true
```

```csharp
// Al enviar: asignar session ID (agrupa mensajes del mismo pedido)
var mensaje = new ServiceBusMessage(body)
{
    SessionId = pedido.ClienteId  // Todos los mensajes del mismo cliente van juntos, en orden
};

// Al recibir: el trigger procesa mensajes de la misma session en orden
[Function("ProcesarOrdenado")]
public void Procesar(
    [ServiceBusTrigger("pedidos-ordenados", Connection = "ServiceBusConnection",
        IsSessionsEnabled = true)]
    ServiceBusReceivedMessage mensaje,
    ServiceBusMessageActions actions)
{
    // Los mensajes con el mismo SessionId llegan EN ORDEN
    // Procesar...
    
    // Confirmar procesamiento
    actions.CompleteMessageAsync(mensaje);
}
```

**Caso de uso:** Pedidos de un cliente deben procesarse en orden (no puedes enviar antes de confirmar). Sin sessions, el procesamiento paralelo podría desordenarlos.

## Slide 18 — Peek Lock vs Receive and Delete

Service Bus tiene dos modos de recepción:

**Peek Lock (por defecto, recomendado):**
1. El consumidor "bloquea" el mensaje (nadie más lo ve)
2. Procesa el mensaje
3. Si OK → `Complete` (mensaje eliminado de la cola)
4. Si fallo → `Abandon` (mensaje vuelve a la cola para reintento)
5. Si timeout → mensaje se desbloquea automáticamente

**Receive and Delete:**
1. El consumidor recibe el mensaje (se elimina inmediatamente de la cola)
2. Si el procesamiento falla, el mensaje se pierde

```csharp
// Peek Lock — control manual de complete/abandon
[Function("ProcesarConPeekLock")]
public async Task Procesar(
    [ServiceBusTrigger("mi-cola", Connection = "SBConnection")]
    ServiceBusReceivedMessage mensaje,
    ServiceBusMessageActions actions)
{
    try
    {
        await ProcesarMensajeAsync(mensaje);
        await actions.CompleteMessageAsync(mensaje);  // Éxito → eliminar
    }
    catch (TransientException)
    {
        await actions.AbandonMessageAsync(mensaje);    // Error temporal → reintentar
    }
    catch (PermanentException)
    {
        await actions.DeadLetterMessageAsync(mensaje,  // Error permanente → dead-letter
            deadLetterReason: "ProcessingFailed",
            deadLetterErrorDescription: "No se pudo procesar");
    }
}
```

## Slide 19 — Event Grid + Service Bus: combinaciones potentes

**Patrón: Event Grid para detectar, Service Bus para procesar**

```
Blob creado → Event Grid → Function "clasificar"
                                ↓ (según tipo)
                          ┌─────┴──────┐
                    Queue "facturas"   Queue "imágenes"
                          ↓                  ↓
                    Func procesar        Func redimensionar
```

```csharp
[Function("ClasificarArchivo")]
public async Task Clasificar(
    [EventGridTrigger] EventGridEvent evento,
    [ServiceBusOutput("facturas", Connection = "SBConn")] OutputBinding<string> colaFacturas,
    [ServiceBusOutput("imagenes", Connection = "SBConn")] OutputBinding<string> colaImagenes)
{
    var data = evento.Data.ToObjectFromJson<StorageBlobCreatedEventData>();
    var url = data.Url;
    
    if (url.EndsWith(".pdf"))
        colaFacturas.SetValue(JsonSerializer.Serialize(new { url, tipo = "factura" }));
    else if (url.EndsWith(".jpg") || url.EndsWith(".png"))
        colaImagenes.SetValue(JsonSerializer.Serialize(new { url, tipo = "imagen" }));
}
```

## Slide 24 — Event Grid vs Event Hubs: la tercera pata

Event Grid, Service Bus y Event Hubs se confunden a menudo. Aclaremos las diferencias definitivamente:

```
┌────────────────────┬──────────────────┬──────────────────┬──────────────────┐
│                    │  Event Grid      │  Event Hubs      │  Service Bus     │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Propósito          │ Eventos discretos│ Ingesta masiva   │ Messaging enterp │
│                    │ "Algo pasó"      │ Big Data/IoT     │ Comandos+transac │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Patrón             │ Pub/Sub reactivo │ Streaming        │ Queue/Topic      │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Throughput típico  │ 10M eventos/s    │ Millones/s       │ Miles/s          │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Ordering           │ Sin garantía     │ Por partición    │ FIFO con Sessions│
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Replay eventos     │ No               │ Sí (retención)   │ No (DLQ aparte)  │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Consumer model     │ Push             │ Pull (checkpoint)│ Push o Pull      │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Retención          │ 24h              │ 1-90 días        │ 14 días (std)    │
├────────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ Tamaño mensaje     │ 1 MB             │ 1 MB             │ 256 KB (100 MB P)│
```

## Slide 25 — CloudEvents: el schema estándar

Azure adoptó CloudEvents (CNCF) como formato estándar en 2021:

```json
{
  "specversion": "1.0",
  "type": "com.miempresa.pedido.creado",
  "source": "/sistemas/ecommerce/api",
  "subject": "pedidos/12345",
  "id": "event-abc-123",
  "time": "2026-04-22T10:30:00Z",
  "datacontenttype": "application/json",
  "data": {
    "pedidoId": "12345",
    "importe": 99.50,
    "cliente": "pedro@example.com"
  }
}
```

**Campos obligatorios:**
- `specversion` — versión del spec (1.0 hoy)
- `type` — qué evento es (reverse DNS convention)
- `source` — quién lo emite (URI)
- `id` — identificador único (para deduplicación)

**Campos recomendados:**
- `subject` — granularidad adicional
- `time` — timestamp ISO 8601
- `datacontenttype` — MIME type del data

**Ventajas de CloudEvents:**
- **Interoperable**: Functions, Logic Apps, AWS, K8s, todos lo entienden
- **Self-describing**: no necesitas documentación externa para entender un evento
- **Evolution-friendly**: campos custom en `data` no rompen consumers

**Event Grid soporta dos schemas:**
```
1. Event Grid schema (legacy)       ← default histórico
2. CloudEvents v1.0 schema          ← RECOMENDADO 2026
```

**Crear topic con CloudEvents:**
```bash
az eventgrid topic create \
  --name evt-pedidos \
  --location westeurope \
  --resource-group rg-curso \
  --input-schema CloudEventSchemaV1_0
```

**En Functions:** si configuráis el topic con CloudEvents, el binding recibe el schema estándar automáticamente.

## Slide 27 — Service Bus: Sessions avanzado

Sessions garantizan orden FIFO por **session ID**, clave en escenarios reales:

```csharp
// Enviar mensajes con session ID
var sender = serviceBusClient.CreateSender("pedidos-ordenados");
await sender.SendMessageAsync(new ServiceBusMessage(json)
{
    SessionId = $"cliente-{clienteId}",     // ⭐ Agrupa por cliente
    CorrelationId = correlationId,
    ContentType = "application/json"
});

// Recibir mensajes de una session específica
// Session A → Consumer 1 procesa mensajes de A en orden
// Session B → Consumer 2 procesa mensajes de B en orden
// Paralelismo ENTRE sessions, orden DENTRO de cada session
```

**En Functions con Session Trigger:**
```csharp
[Function(nameof(ProcesarPedidoOrdenado))]
public async Task ProcesarPedidoOrdenado(
    [ServiceBusTrigger("pedidos-ordenados", Connection = "SB", 
                       IsSessionsEnabled = true)]
    ServiceBusReceivedMessage msg,
    FunctionContext ctx)
{
    _logger.LogInformation(
        "Session {session} | Message {id} | Sequence {seq}",
        msg.SessionId, msg.MessageId, msg.SequenceNumber);
    
    // Azure Functions automáticamente:
    // - Lockea la session mientras esta instance procesa
    // - Otras instances NO reciben mensajes de esta session
    // - Garantiza orden dentro de la session
}
```

**Session State (estado por session):**
```csharp
// Durante procesamiento de una session, podéis guardar estado
// que persiste entre mensajes de la misma session
var receiver = client.CreateSessionReceiverAsync("queue", sessionId);
var sessionState = await receiver.GetSessionStateAsync();
// Proceso mensaje
await receiver.SetSessionStateAsync(BinaryData.FromString(nuevoEstado));
```

**Cuándo usar Sessions:**
- Saga por entidad (ej: estado de un pedido)
- Orden estricto por usuario / tenant
- Long-running workflows con estado intermedio
- Batch processing agrupado lógicamente

**Trade-off:** sessions reducen paralelismo. Si tenéis 100 sessions activas pero 10 instances, cada instance procesa varias sessions secuencialmente.

## Slide 28 — Service Bus: scheduled messages y message deferral

Dos features muy potentes poco conocidas:

**Scheduled Messages — enviar al futuro:**
```csharp
// Mensaje que se ENTREGA en el futuro (no ahora)
var sender = client.CreateSender("notificaciones");

await sender.ScheduleMessageAsync(
    new ServiceBusMessage("Recordatorio: reunión mañana") 
    { 
        ContentType = "text/plain" 
    },
    scheduledEnqueueTime: DateTimeOffset.UtcNow.AddHours(24)
);

// Devuelve un sequence number → puedes cancelar antes
var seqNum = await sender.ScheduleMessageAsync(...);
await sender.CancelScheduledMessageAsync(seqNum);  // cancela
```

**Casos de uso scheduled:**
- Recordatorios (24h antes de cita médica)
- Retries con backoff custom (reintento en 5, 30, 120 min)
- Workflow delay ("esperar 1h antes de cobrar la tarjeta")
- Acciones programadas sin Timer Trigger

**Message Deferral — "aplazar" un mensaje:**
```csharp
// Recibir un mensaje, pero no procesarlo ahora
public async Task ProcesarOPosponer(
    [ServiceBusTrigger("pedidos")] ServiceBusReceivedMessage msg,
    ServiceBusMessageActions actions)
{
    if (DebeProcesarAhora(msg))
    {
        await ProcessAsync(msg);
        await actions.CompleteMessageAsync(msg);
    }
    else
    {
        // Aplazar: sale de la queue pero no se pierde
        await actions.DeferMessageAsync(msg);
        // El sequenceNumber lo guardáis para recuperar después
    }
}

// Recuperar mensaje aplazado específico
var receiver = client.CreateReceiver("pedidos");
var message = await receiver.ReceiveDeferredMessageAsync(sequenceNumber);
```

**Uso típico de deferral:**
- Mensajes que requieren pre-procesamiento async
- Scatter-gather (recolectar varios mensajes antes de procesar)
- Handling out-of-order (llega M2 antes que M1, aplazáis M2 hasta recibir M1)

## Slide 29 — Service Bus: auto-forward y message chaining

Feature "invisible" pero extremadamente útil:

```
Queue A          Queue B
─────    ──▶    ─────
                   │
                   ▼
               Queue C
               
Auto-forward: los mensajes que llegan a Queue A
se copian automáticamente a Queue B.
Sin consumer intermedio.
```

**Configurar auto-forward:**
```bash
az servicebus queue create \
  --resource-group rg-curso \
  --namespace-name sb-curso \
  --name pedidos-raw \
  --forward-to pedidos-procesados
```

**Casos de uso:**
```
Caso 1: Fan-out a múltiples queues
├── Topic pedidos-incoming
│   ├── Subscription → auto-forward → queue-inventory
│   ├── Subscription → auto-forward → queue-billing
│   └── Subscription → auto-forward → queue-notifications
│   
│   (sin Function intermedia, Service Bus maneja el routing)

Caso 2: Cross-namespace forwarding
├── Namespace-A (region West) → Namespace-B (region North)
│   (mensajes se replican a otra región automáticamente)

Caso 3: Dead Letter consolidation
├── queue-A.dead-letter → auto-forward → queue-dlq-global
├── queue-B.dead-letter → auto-forward → queue-dlq-global
│   (todos los DLQ a un único monitor)
```

**Ventajas:**
- Zero code — solo configuración
- Menos latencia que tener una Function intermedia
- Menos coste (no consumes ni Functions ni compute)

**Limitaciones:**
- 4 hops max (evitar loops)
- No transformación del payload (solo routing)
- Si la queue destino está llena, source también se bloquea

## Slide 30 — Service Bus: transacciones y duplicates

Features críticas para sistemas que no pueden permitirse errores:

**Transacciones locales (dentro de un namespace):**
```csharp
// Atomicidad: o TODAS las operaciones, o NINGUNA
using var ts = new TransactionScope(TransactionScopeAsyncFlowOption.Enabled);

await queueA.SendMessageAsync(msg1);
await queueB.SendMessageAsync(msg2);
await topicC.SendMessageAsync(msg3);

ts.Complete();  // commit
// Si no llegáis aquí, ninguno se envía
```

**Casos:**
- "Enviar a queue Y mover a queue dead-letter solo si SendAsync OK"
- "Confirmar mensaje Y publicar notificación atómicamente"

**Limitación:** transacciones solo dentro de un namespace. No hay DTC a través de servicios.

**Duplicate detection:**
```bash
# Habilitar al crear la queue
az servicebus queue create \
  --resource-group rg \
  --namespace-name sb \
  --name pedidos \
  --enable-duplicate-detection true \
  --duplicate-detection-history-time-window PT10M
  # 10 min de ventana: si llega msg con mismo MessageId en <10 min, se descarta
```

```csharp
// En el código, set MessageId explícitamente
var msg = new ServiceBusMessage(body)
{
    MessageId = $"pedido-{pedidoId}-{version}"  // idempotency key
};
await sender.SendMessageAsync(msg);
// Si este MessageId ya entró en los últimos 10 min → dedup automático
```

**Gotcha:** duplicate detection usa storage extra (coste). Y la ventana máxima es 7 días (Premium). No es para dedup "de por vida".

## Slide 37 — Idempotencia: el tema ignorado hasta que duele

Sistemas distribuidos **van a duplicar mensajes**. Vuestro código debe tolerarlo:

```csharp
// ❌ MAL: non-idempotent
[Function(nameof(ProcesarPagoMal))]
public async Task ProcesarPagoMal(
    [ServiceBusTrigger("pagos")] PagoDto pago)
{
    // Si este mensaje llega 2 veces → cobras 2 veces → disaster
    await _stripe.ChargeAsync(pago.TarjetaId, pago.Importe);
    await _db.InsertarAsync(pago);
}

// ✅ BIEN: idempotente con idempotency key
[Function(nameof(ProcesarPagoBien))]
public async Task ProcesarPagoBien(
    [ServiceBusTrigger("pagos")] PagoDto pago,
    FunctionContext ctx)
{
    var idempotencyKey = pago.TransactionId;  // el cliente lo provee
    
    // 1. Check si ya procesamos este TransactionId
    var existing = await _db.GetByTransactionIdAsync(idempotencyKey);
    if (existing != null)
    {
        _logger.LogInformation("Duplicate {key} ignored", idempotencyKey);
        return; // ya procesado, mensaje completado
    }
    
    // 2. Atomic: guardar transactionId + ejecutar pago
    using var tx = await _db.BeginTransactionAsync();
    try
    {
        await _db.InsertarAsync(new Pago 
        { 
            TransactionId = idempotencyKey, 
            Status = "processing"
        });
        
        var chargeResult = await _stripe.ChargeAsync(
            pago.TarjetaId, pago.Importe, idempotencyKey);  // Stripe también soporta it
        
        await _db.UpdateStatusAsync(idempotencyKey, "completed");
        await tx.CommitAsync();
    }
    catch
    {
        await tx.RollbackAsync();
        throw;  // SB reintentará
    }
}
```

**Patrones de idempotencia:**

| Patrón | Cuándo |
|---|---|
| **Idempotency key** en BD | Pagos, transacciones críticas |
| **Upsert** (insert-or-update) | Datos de estado (stock, perfil) |
| **Compare-And-Set** con version | Edición colaborativa |
| **Deduplication window** (SB) | Ventana temporal corta (10 min) |
| **Natural idempotency** | Operación ya es idempotente (DELETE /x) |

**Regla:** si vuestra Function hace algo que "no se puede repetir" (cobrar, enviar email, crear recurso externo), **necesitáis idempotencia explícita**. No confiéis en "el mensaje solo llegará una vez".

## Slide 39 — Patrones anti-patrón: qué NO hacer con messaging

Lecciones de proyectos reales:

**❌ Anti-pattern 1: Messaging como RPC**
```csharp
// MAL: esperar respuesta de forma síncrona
var response = await serviceBus.SendAndWaitAsync(request, timeout: 30s);
// Introduce latencia alta + acoplamiento + dolor
```
**✅ BIEN:** Si necesitáis request/response, usad HTTP directamente. Messaging es para fire-and-forget o eventual consistency.

**❌ Anti-pattern 2: Business logic en el sender**
```csharp
// MAL: el publisher decide quién consume
await PublishAsync(topic: "pedidos",
    subscribers: new[] { "billing", "inventory", "shipping" });
```
**✅ BIEN:** el broker maneja routing. El publisher solo publica. Los consumers se suscriben independientemente.

**❌ Anti-pattern 3: Orchestration en flujo de eventos**
```
Event A → Function 1 → Event B → Function 2 → Event C → Function 3
                                                       → Event D → Function 4
                                                       (chain de 10 eventos, imposible de debuggear)
```
**✅ BIEN:** si hay un flow coordinado, usad **Durable Functions** (siguiente submódulo). Event chains para flows largos es pesadilla.

**❌ Anti-pattern 4: Ignorar DLQ**
```csharp
// "Si va al DLQ, alguien lo arreglará"
// (nadie lo arregla nunca)
```
**✅ BIEN:** alertas de DLQ size > 0. Función que procese DLQ (puede ser manual o automática). Dashboards.

**❌ Anti-pattern 5: Sin deduplicación porque "no pasa"**
```csharp
// "En testing no se duplica"
// (en producción SÍ pasa, por restart, retries, network)
```
**✅ BIEN:** idempotencia por defecto. Pensad que todo mensaje llega ≥ 1 vez.

**❌ Anti-pattern 6: Payloads gigantes**
```csharp
msg.Body = BinaryData.FromBytes(File.ReadAllBytes("/tmp/video.mp4"));
// 500 MB → falla (256 KB en Standard, 100 MB en Premium)
```
**✅ BIEN:** claim-check pattern. Subir el blob a Storage, en el mensaje solo el URL/ID.

## Slide 40 — Cierre del submódulo

Event Grid y Service Bus son las herramientas que convierten funciones aisladas en un sistema conectado. Event Grid para "ha pasado algo", Service Bus para "procesa esto".

Lo esencial:
- Eventos (Event Grid): notificación, múltiples suscriptores, latencia mínima
- Mensajes (Service Bus): trabajo encolado, FIFO, dead-letter, transacciones
- Queues para 1:1, Topics para 1:N
- Filtros SQL en suscripciones de Topics
- Sessions para orden garantizado
- Peek Lock para procesamiento seguro
- Combinad ambos: Event Grid detecta, Service Bus procesa

Siguiente submódulo: Durable Functions — cuando una función necesita orquestar otras funciones.

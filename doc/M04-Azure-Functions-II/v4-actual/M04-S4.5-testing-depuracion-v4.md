## Slide 2 — Estrategia de testing para Functions

```
                    ┌──────────────┐
                    │  E2E Tests   │  ← Pocos, lentos, en staging
                   ┌┴──────────────┴┐
                   │ Integration    │  ← Con emuladores locales
                  ┌┴────────────────┴┐
                  │  Unit Tests      │  ← Muchos, rápidos, sin Azure
                 ┌┴──────────────────┴┐
                 │  Ejecución local   │  ← func start + REST Client
                 └────────────────────┘
```

**Ejecución local:** `func start` + peticiones manuales. Para verificar que funciona.
**Unit tests:** Prueban la lógica de negocio sin Azure. Rápidos y aislados.
**Integration tests:** Prueban con emuladores (Azurite, Cosmos Emulator). Verifican la integración.
**E2E tests:** En un entorno de staging real. Verifican todo el flujo.

## Slide 3 — Ejecución local: el flujo de desarrollo

```bash
# Terminal 1: Emuladores
azurite --silent --location ./azurite-data

# Terminal 2: Functions
func start

# Terminal 3: Testing
# Usar REST Client o curl para probar HTTP triggers
# Subir blobs con az storage para probar Blob triggers
# Insertar docs en Cosmos para probar Change Feed triggers
```

**Todos los triggers funcionan en local con Core Tools.** Pero algunos necesitan servicios reales o emuladores:
- HTTP: funciona sin nada extra
- Timer: funciona sin nada extra (se ejecuta según el CRON)
- Blob: necesita Azurite o Storage Account real
- Cosmos DB: necesita Emulator o Cosmos DB real
- Service Bus: necesita Service Bus real (no hay emulador oficial)

## Slide 6 — Unit Test de un HTTP Trigger

```csharp
public class ProductosApiTests
{
    private readonly Mock<IProductoService> _mockService;
    private readonly ProductosApi _api;

    public ProductosApiTests()
    {
        _mockService = new Mock<IProductoService>();
        _api = new ProductosApi(_mockService.Object);
    }

    [Fact]
    public async Task GetProducto_Existe_DevuelveOk()
    {
        // Arrange
        var producto = new Producto("1", "Laptop", 999.99m);
        _mockService.Setup(s => s.GetAsync("1")).ReturnsAsync(producto);

        var httpContext = new DefaultHttpContext();
        httpContext.Request.RouteValues["id"] = "1";

        // Act
        var result = await _api.Get(httpContext.Request, "1");

        // Assert
        var okResult = result.Should().BeOfType<OkObjectResult>().Subject;
        var data = okResult.Value.Should().BeOfType<Producto>().Subject;
        data.Nombre.Should().Be("Laptop");
        data.Precio.Should().Be(999.99m);
    }

    [Fact]
    public async Task GetProducto_NoExiste_Devuelve404()
    {
        _mockService.Setup(s => s.GetAsync("999")).ReturnsAsync((Producto?)null);

        var httpContext = new DefaultHttpContext();
        var result = await _api.Get(httpContext.Request, "999");

        result.Should().BeOfType<NotFoundResult>();
    }

    [Fact]
    public async Task CrearProducto_DatosValidos_Devuelve201()
    {
        var dto = new CrearProductoDto { Nombre = "Mouse", Precio = 29.99m };
        _mockService.Setup(s => s.CrearAsync(It.IsAny<CrearProductoDto>()))
            .ReturnsAsync(new Producto("new-1", "Mouse", 29.99m));

        var httpContext = new DefaultHttpContext();
        httpContext.Request.Body = new MemoryStream(
            System.Text.Encoding.UTF8.GetBytes(JsonSerializer.Serialize(dto)));
        httpContext.Request.ContentType = "application/json";

        var result = await _api.Crear(httpContext.Request);

        result.Should().BeOfType<CreatedResult>();
    }
}
```

**La clave:** La lógica de negocio está en `IProductoService`, no en la función. La función es solo el "pegamento" que conecta el trigger con el servicio. Los tests mockean el servicio y prueban que la función devuelve las respuestas correctas.

## Slide 14 — Test pyramid adaptado a Azure Functions

La tradicional "test pyramid" aplicada a Functions tiene particularidades:

```
                      ╱╲
                     ╱E2╲              ~5% tests
                    ╱ E2 ╲             Slow (seconds-minutes)
                   ╱──────╲            Cover: flujos críticos
                  ╱        ╲           End-to-end real
                 ╱ INTEGR.  ╲          ~15% tests  
                ╱  TESTS     ╲         Medium (100ms-2s)
               ╱──────────────╲        Cover: interaction Functions + deps
              ╱                ╲       Emuladores (Azurite, SB emu, Cosmos emu)
             ╱   UNIT TESTS     ╲      ~80% tests
            ╱                    ╲     Fast (ms)
           ╱──────────────────────╲    Cover: business logic, validators
          ╱                        ╲   Mocks all dependencies
         ╱──────────────────────────╲
```

**Distribución ideal de tiempo:**

| Level | Cuándo | Velocidad | Confianza |
|---|---|---|---|
| Unit tests | Cada commit | < 10s para todos | ⭐⭐ |
| Integration | Cada push | 1-5 min | ⭐⭐⭐⭐ |
| E2E | Daily / pre-deploy | 10-30 min | ⭐⭐⭐⭐⭐ |

**Anti-pattern: cone invertido (pocos unit, muchos E2E):**
```
❌ Muchos E2E:
   - Slow (no corren en cada PR)
   - Flaky (dependen de red, recursos reales)
   - Caros (consumen Azure)
   - Difíciles de debuggear
```

**Balance saludable:**
```
Función "ProcesarPedido":
├── 15 unit tests   (validación, lógica, mocks)
├── 3 integration   (con Azurite + real Cosmos emulator)
└── 1 E2E          (staging real — creates order, verifies full flow)
```

## Slide 15 — Testcontainers: emuladores programáticos

**Testcontainers** (.NET library) permite lanzar containers desde tests:

```csharp
// Install NuGet
// dotnet add package Testcontainers.Azurite
// dotnet add package Testcontainers.CosmosDb

public class FunctionIntegrationTests : IAsyncLifetime
{
    private AzuriteContainer _azurite = null!;
    private CosmosDbContainer _cosmos = null!;
    private IHost _functionsHost = null!;
    
    public async Task InitializeAsync()
    {
        // 1. Lanzar Azurite (Storage emulator)
        _azurite = new AzuriteBuilder()
            .WithImage("mcr.microsoft.com/azure-storage/azurite:latest")
            .Build();
        await _azurite.StartAsync();
        
        // 2. Lanzar Cosmos DB emulator
        _cosmos = new CosmosDbBuilder()
            .WithImage("mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator:latest")
            .Build();
        await _cosmos.StartAsync();
        
        // 3. Crear Functions host en memoria con config apuntando a containers
        _functionsHost = new HostBuilder()
            .ConfigureFunctionsWorkerDefaults()
            .ConfigureAppConfiguration(cfg =>
            {
                cfg.AddInMemoryCollection(new[]
                {
                    new KeyValuePair<string, string?>(
                        "AzureWebJobsStorage", _azurite.GetConnectionString()),
                    new KeyValuePair<string, string?>(
                        "CosmosConnection", _cosmos.GetConnectionString())
                });
            })
            .Build();
        
        await _functionsHost.StartAsync();
    }
    
    [Fact]
    public async Task FullFlow_OrderCreatesInvoice()
    {
        // Arrange: insert order to Cosmos
        var container = GetCosmosContainer();
        var order = new Order { Id = "o1", Amount = 100 };
        await container.CreateItemAsync(order);
        
        // Act: wait for change feed + function processes
        await Task.Delay(5000);  // let function react
        
        // Assert: invoice should exist
        var invoices = await GetInvoicesByOrderAsync("o1");
        Assert.Single(invoices);
        Assert.Equal(100, invoices[0].Amount);
    }
    
    public async Task DisposeAsync()
    {
        await _functionsHost.StopAsync();
        await _azurite.DisposeAsync();
        await _cosmos.DisposeAsync();
    }
}
```

**Beneficios clave:**
- ✅ Tests reproducibles (no dependes de dev environment)
- ✅ Portable a CI sin setup extra (solo Docker)
- ✅ Aislados (cada test suite tiene sus propios containers)
- ✅ Realistas (código real + servicios reales, no mocks)

**Trade-off:** tests más lentos (~5-30s setup por container).

**k6 como alternativa (si preferís JS):**
```javascript
// load-test.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m',  target: 20 },   // ramp up a 20 VUs
    { duration: '3m',  target: 100 },  // ramp up a 100 VUs
    { duration: '5m',  target: 100 },  // mantain
    { duration: '1m',  target: 0 },    // ramp down
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],   // p95 < 500ms
    http_req_failed: ['rate<0.01'],     // error rate < 1%
  },
};

export default function () {
  const url = 'https://func-curso-staging.azurewebsites.net/api/pedidos';
  const payload = JSON.stringify({ 
    productId: `p-${__VU}-${__ITER}`, 
    quantity: 1 
  });
  const params = { headers: { 'Content-Type': 'application/json' } };
  
  const res = http.post(url, payload, params);
  
  check(res, {
    'status 201': (r) => r.status === 201,
    'response < 500ms': (r) => r.timings.duration < 500,
  });
  
  sleep(1);
}

// Run: k6 run load-test.js
```

**Qué medir:**
- Throughput (req/s sostenido)
- Latency distribution (p50, p95, p99)
- Error rate
- Cold start impact
- Scale-out behavior (cuántas instances se crean)
- Resource saturation (CPU, memory en Portal)

**Decision criteria:**
```
Requirement: 1000 req/s con p95 < 200ms
│
└── Load test muestra: 800 req/s con p95 500ms 
    → escalar SKU, optimizar queries, cacheo, más Functions instances
```

## Slide 17 — Azure Chaos Studio: resilience testing

Chaos engineering managed por Azure (GA 2023):

```bash
# Enable chaos provider
az provider register --namespace Microsoft.Chaos

# Crear target (cualquier recurso que soporte chaos)
az rest --method put \
  --uri "https://management.azure.com/subscriptions/$SUB_ID/resourceGroups/rg-curso/providers/Microsoft.Web/sites/func-curso/providers/Microsoft.Chaos/targets/Microsoft-AzureFunctionApp?api-version=2023-11-01" \
  --body '{"properties":{}}'

# Crear experimento
az rest --method put \
  --uri "https://management.azure.com/subscriptions/$SUB_ID/resourceGroups/rg-curso/providers/Microsoft.Chaos/experiments/stop-func-5min?api-version=2023-11-01" \
  --body '{
    "identity": { "type": "SystemAssigned" },
    "location": "westeurope",
    "properties": {
      "selectors": [{
        "type": "List",
        "id": "Selector1",
        "targets": [{
          "id": "/subscriptions/.../sites/func-curso/providers/Microsoft.Chaos/targets/Microsoft-AzureFunctionApp",
          "type": "ChaosTarget"
        }]
      }],
      "steps": [{
        "name": "Step1",
        "branches": [{
          "name": "Branch1",
          "actions": [{
            "type": "continuous",
            "name": "urn:csci:microsoft:azureFunctionApp:stop/1.0",
            "duration": "PT5M",
            "selectorId": "Selector1"
          }]
        }]
      }]
    }
  }'
```

**Faults comunes para Functions:**

| Fault | Qué prueba |
|---|---|
| `AzureFunctionApp:stop` | Resiliencia a Function App caída |
| `VirtualMachine:shutdown` | Recovery tras loss de instance |
| `NetworkSecurityGroup:disable` | Network isolation fault |
| `CosmosDB:failover` | Failover region Cosmos |
| `ServiceBus:stopQueue` | Queue offline temporalmente |
| `KeyVault:revoke` | Auth/secrets no accesibles |

**Game day ritual:**
```
1. Hypothesis: "Si Cosmos falla en West Europe, Functions usan read 
   replica en North Europe, latencia aumenta +50ms pero success rate > 99%"

2. Baseline: correr 30 min sin chaos, anotar métricas

3. Experiment: chaos studio ejecuta el fault durante 10 min

4. Validate: 
   - ¿Success rate bajó por debajo de 99%?
   - ¿Latencia aumentó más de 50ms?
   - ¿Hubo user-facing errors?

5. Post-mortem: documentar findings y mejoras
```

**Gotcha crítico:** **no hacer chaos en producción** hasta haber hecho en staging muchas veces. Y siempre con abort conditions claras.

## Slide 18 — Contract testing con Pact

Consumer-driven contract testing para APIs: el consumer define el contrato, el provider lo cumple.

```csharp
// En el proyecto del consumer (mobile app, otra Function, etc)
// 1. Install: dotnet add package PactNet
// 2. Definir el contrato esperado
public class PedidosConsumerTests
{
    [Fact]
    public async Task GetOrder_ReturnsOrderInExpectedFormat()
    {
        var pact = Pact.V3("mobile-app", "pedidos-api");
        
        pact.UponReceiving("a request for order 123")
            .Given("an order 123 exists")
            .WithRequest(HttpMethod.Get, "/api/orders/123")
            .WithHeader("Accept", "application/json")
            .WillRespond()
            .WithStatus(HttpStatusCode.OK)
            .WithHeader("Content-Type", "application/json; charset=utf-8")
            .WithJsonBody(new
            {
                id = "123",
                total = Match.Number(99.99m),
                items = Match.EachLike(new { productId = "p1", quantity = 2 }),
                status = Match.Regex("(pending|paid|shipped)", "pending")
            });
        
        await pact.VerifyAsync(async ctx =>
        {
            var client = new HttpClient { BaseAddress = ctx.MockServerUri };
            var response = await client.GetAsync("/api/orders/123");
            response.EnsureSuccessStatusCode();
        });
    }
}

// Al correr: genera "pedidos-api.json" contract file
// Subir a Pact Broker (SaaS) o file system
```

**En el provider (Azure Functions):**
```csharp
// 3. En el provider, verificar que cumplimos el contrato
public class PedidosProviderTests
{
    [Fact]
    public async Task VerifyConsumerContracts()
    {
        // Arrange: levantar tu Function host
        var app = CreateFunctionHost();
        await app.StartAsync();
        
        // Act: Pact ejecuta las requests del contrato contra tu API
        var config = new PactVerifierConfig
        {
            LogLevel = PactLogLevel.Information
        };
        
        new PactVerifier("pedidos-api", config)
            .WithHttpEndpoint(new Uri("http://localhost:7071"))
            .WithFileSource(new FileInfo("./pacts/mobile-app-pedidos-api.json"))
            .WithProviderStateUrl(new Uri("http://localhost:7071/provider-states"))
            .Verify();
        
        await app.StopAsync();
    }
}
```

**Beneficios:**
- Cambios breaking se detectan antes de deploy
- Cada consumer documenta qué necesita
- El provider valida cumplimiento en CI
- **Evita el "API sorpresa"** que rompe clients

**Cuándo usarlo:** >2 equipos distintos, APIs internas críticas. Si eres el único consumer, overkill.

## Slide 21 — Property-based testing con FsCheck

Mientras unit tests prueban ejemplos específicos, property-based genera inputs aleatorios:

```csharp
// Install: dotnet add package FsCheck.Xunit
public class OrderValidatorTests
{
    // Unit test clásico: 1 ejemplo
    [Fact]
    public void ValidatesSimpleOrder()
    {
        var order = new Order { Amount = 100, Items = new[] { new Item() } };
        var result = new OrderValidator().Validate(order);
        result.IsValid.Should().BeTrue();
    }
    
    // Property-based: 100+ ejemplos aleatorios
    [Property]
    public Property OrderWithPositiveAmount_IsAlwaysValid(PositiveInt amount, NonEmptyArray<Item> items)
    {
        var order = new Order 
        { 
            Amount = amount.Get, 
            Items = items.Get 
        };
        
        var result = new OrderValidator().Validate(order);
        
        return (result.IsValid == true).ToProperty();
        // FsCheck prueba con ~100 combinaciones random de amount/items
    }
    
    // Property: idempotencia de ciertas operaciones
    [Property]
    public Property CalculatingDiscountTwice_YieldsSameResult(Order order, decimal discountRate)
    {
        var discount1 = OrderService.CalculateDiscount(order, discountRate);
        var discount2 = OrderService.CalculateDiscount(order, discountRate);
        
        return (discount1 == discount2).ToProperty();
        // Verifica: calcular 2 veces → mismo resultado
    }
    
    // Property: invariant matemática
    [Property]
    public Property OrderTotal_NeverNegative(Order order)
    {
        var total = OrderService.CalculateTotal(order);
        return (total >= 0).ToProperty();
        // FsCheck prueba con orders arbitrarios → total nunca < 0
    }
}
```

**Cuándo property-based shines:**

| Tipo de código | Beneficio |
|---|---|
| Parseo/serialización | Encuentra inputs que rompen |
| Cálculos financieros | Verifica invariantes matemáticas |
| Transformaciones | Redonda trip (encode → decode) |
| Validadores | Edge cases que olvidasteis |
| Algoritmos | Properties generales (sorted list sigue sorted) |

**Lo que descubre:**
```
OrderWithPositiveAmount_IsAlwaysValid — FsCheck found counterexample:
  amount = 999999999999
  items  = [Item { Quantity = 0, Price = 0 }]
  → Validation failed: quantity cannot be 0
  → Bug: validator failed este caso que no estaba cubierto
```

**Gotcha:** property-based NO reemplaza unit tests ejemplares. Son complementarios.

## Slide 22 — Mutation testing con Stryker

Mutation testing mide si vuestros tests realmente detectan bugs:

```bash
# Install: dotnet tool install -g dotnet-stryker

# Ejecutar en tu proyecto de Functions
cd src/Functions
dotnet stryker

# Output:
# ┌──────────────────────────────────┬─────────┐
# │ Stryker.Core.InjectedHelpers.cs  │ 100.00% │
# │ OrderValidator.cs                │  85.00% │  ← 85% de mutaciones detectadas
# │ PedidosFunction.cs               │  40.00% │  ← problema: tests insuficientes
# └──────────────────────────────────┴─────────┘
# Overall mutation score: 72.5%
```

**Qué hace Stryker:**
```
Código original:
  if (amount > 100) { ApplyDiscount(); }

Mutations generadas automáticamente:
  if (amount >= 100) { ApplyDiscount(); }    ← Mutation 1
  if (amount < 100)  { ApplyDiscount(); }    ← Mutation 2
  if (amount > 99)   { ApplyDiscount(); }    ← Mutation 3
  if (amount > 100)  { }                     ← Mutation 4 (removed call)
  if (true)          { ApplyDiscount(); }    ← Mutation 5

Ejecuta vuestros tests contra cada mutation:
  - Mutation 1: tests PASS → mala noticia (no detectan el cambio)
  - Mutation 2: tests FAIL → buena noticia (tests son sensibles)
  - etc.

Mutation score: (mutations killed / total mutations) × 100
```

**Objetivos saludables:**
- Excellent: >80% mutation score
- Good: 60-80%
- Concerning: <60% → tests superficiales
- Bad: <40% → tests "pasan sin verificar"

**Configuración:**
```json
// stryker-config.json
{
  "stryker-config": {
    "project": "Functions.csproj",
    "test-projects": ["../Functions.Tests/Functions.Tests.csproj"],
    "mutate": [
      "!**/Program.cs",
      "!**/Obsolete/**"
    ],
    "thresholds": {
      "high": 80,
      "low": 60,
      "break": 50
    },
    "concurrency": 4,
    "reporters": ["html", "progress", "cleartext"]
  }
}
```

**En CI:**
```yaml
- name: Mutation testing
  run: dotnet stryker --threshold-break 60
  # Falla el build si mutation score < 60%
```

**Trade-off:** lento (puede tardar 30min-2h para proyecto mediano). Correr semanalmente, no en cada PR.

## Slide 23 — Performance benchmarking con BenchmarkDotNet

Para código hot-path dentro de Functions (validación compleja, parsing, etc):

```csharp
// Install: dotnet add package BenchmarkDotNet

[MemoryDiagnoser]
[SimpleJob(RuntimeMoniker.Net80)]
public class OrderParsingBenchmarks
{
    private string _orderJson = null!;
    private byte[] _orderBytes = null!;
    
    [GlobalSetup]
    public void Setup()
    {
        _orderJson = File.ReadAllText("sample-order.json");
        _orderBytes = File.ReadAllBytes("sample-order.json");
    }
    
    [Benchmark(Baseline = true)]
    public Order ParseWithNewtonsoftJson()
    {
        return JsonConvert.DeserializeObject<Order>(_orderJson)!;
    }
    
    [Benchmark]
    public Order ParseWithSystemTextJson()
    {
        return JsonSerializer.Deserialize<Order>(_orderJson)!;
    }
    
    [Benchmark]
    public Order ParseWithSystemTextJsonUtf8()
    {
        return JsonSerializer.Deserialize<Order>(_orderBytes)!;
    }
}

// Ejecutar
// dotnet run -c Release --project benchmarks
```

**Output real típico:**
```
|                   Method |       Mean |   Allocated |
|------------------------- |-----------:|------------:|
| ParseWithNewtonsoftJson  |  3,125 ns  |     5.2 KB  |  ← baseline
| ParseWithSystemTextJson  |    812 ns  |     0.8 KB  |  ← 4x faster
| ParseWithSystemTextJsonUtf8|  645 ns  |     0.3 KB  |  ← 4.8x faster, 17x less memory
```

**Cuándo usar BenchmarkDotNet:**
- Parseo de payloads grandes
- Serialización para mensajes Service Bus
- Validaciones ejecutadas miles de veces
- Hot paths identificados por profiling
- Comparar librerías alternativas

**En Functions — perf del host ya está optimizado.** BenchmarkDotNet es para **vuestro código dentro de la función**, no el runtime.

**Regla pragmática:**
```
1. Profile first (find bottleneck)
2. Benchmark the bottleneck (quantify)
3. Optimize
4. Re-benchmark (confirm)
```

No optimicéis a ciegas. "Premature optimization is the root of all evil" — Knuth.

## Slide 25 — Observability-driven testing

Concepto moderno: testing en producción con observabilidad:

```
Dev environment:             Production:
├── Unit tests            ├── Production monitoring
├── Integration tests     ├── Synthetic probes (cada 1 min)

                          ├── Canary analysis

- Real user patterns
- Carga real de producción
- Dependencies externas reales
```

## Slide 26 — Cierre del submódulo

El testing de Functions no es diferente al testing de cualquier aplicación .NET — si separáis bien la lógica del trigger:

Lo esencial:
- Extraer lógica de negocio a servicios testeables
- Unit tests para lógica, mocking para dependencias
- Integration tests con emuladores (Azurite, Cosmos Emulator)

- F5 en VS Code para debugging con breakpoints
- Timer triggers: ejecutar manualmente o testear el servicio
- Patrón: función = cable, servicio = lógica testeable

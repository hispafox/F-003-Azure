## Slide 2 — Qué vais a construir

Una Durable Function que orquesta un workflow simple: recibir una lista de nombres y saludar a cada uno, en paralelo, con resultado consolidado al final. **Patrón fan-out / fan-in** en su forma más mínima.

**El recorrido:**

```
1. Crear proyecto Functions con extension Durable Functions
2. Escribir tres funciones:
   - HTTP Starter: arranca el orchestrator
   - Orchestrator: define el workflow
   - Activity: hace el trabajo (saludar a un nombre)
3. Probar en local con func start
4. Inspeccionar el estado del orchestrator (status URL)
5. Desplegar a Azure (Consumption Plan)
6. Limpiar recursos
```

**Lo que NO hay en esta práctica** (a propósito):

- ❌ Service Bus (cubierto en M04-S4.P principal)
- ❌ Event Grid (también principal)
- ❌ Cosmos DB ni persistencia externa (M05)
- ❌ Patrones avanzados (eternal orchestrator, sub-orchestrators, etc.)
- ❌ Auth ni Key Vault (M06)

**Por qué Durable Functions Hello World:**

- ✅ Concepto clave (orchestrator stateful) en su forma mínima
- ✅ Sin emuladores externos complicados
- ✅ Visual y rápido de entender (paralelismo "se ve")
- ✅ Base mental para flujos más complejos en M04-S4.P

**Tiempo estimado:** 45-60 minutos.

**Coste real:** **0€** (Consumption Plan + Storage Account dentro del free tier).

## Slide 5 — Paso 2: La Activity (el "trabajador")

Empezamos por la pieza más simple: la activity que hace el trabajo real. En nuestro caso, "saludar a alguien":

```bash
cat > SaludarActivity.cs << 'EOF'
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

namespace MiDurableFunction;

public class SaludarActivity
{
    [Function(nameof(Saludar))]
    public string Saludar(
        [ActivityTrigger] string nombre,
        FunctionContext executionContext)
    {
        var logger = executionContext.GetLogger(nameof(SaludarActivity));
        logger.LogInformation("Saludando a {Nombre}", nombre);
        
        // Simulamos un trabajo "lento" (llamada a API, cálculo, etc.)
        Thread.Sleep(2000);  // 2 segundos
        
        var saludo = $"¡Hola, {nombre}! ({DateTime.UtcNow:HH:mm:ss})";
        logger.LogInformation("Saludo generado: {Saludo}", saludo);
        
        return saludo;
    }
}
EOF
```

**Anatomía de una Activity:**

```
[ActivityTrigger]:
- Marca el parámetro que recibe la entrada
- El tipo del parámetro DEBE ser serializable (string, record, class simple)

Activity behavior:
- Se ejecuta como una function normal
- Puede llamar a APIs externas (HttpClient)
- Puede leer/escribir BBDD
- Puede tirar excepciones (el orchestrator decide qué hacer)
- Es la ÚNICA pieza donde hacéis "trabajo real"
```

**Por qué `Thread.Sleep(2000)`:**

Simulamos que el saludo "tarda" en hacerse. Cuando llamemos a varias activities en paralelo, este sleep nos permitirá ver visualmente que el paralelismo funciona.

En código de verdad: **NUNCA `Thread.Sleep` en producción.** Aquí es solo demo.

## Slide 6 — Paso 3: El Orchestrator (el "coordinador")

Ahora la pieza clave: define qué activities llamar y en qué orden:

```bash
cat > SaludosOrchestrator.cs << 'EOF'
using Microsoft.Azure.Functions.Worker;
using Microsoft.DurableTask;
using Microsoft.Extensions.Logging;

namespace MiDurableFunction;

public class SaludosOrchestrator
{
    [Function(nameof(SaludarATodos))]
    public async Task<List<string>> SaludarATodos(
        [OrchestrationTrigger] TaskOrchestrationContext context)
    {
        ILogger logger = context.CreateReplaySafeLogger(nameof(SaludarATodos));
        
        // Recibir input del client (lista de nombres)
        var nombres = context.GetInput<List<string>>() ?? new List<string>();
        
        if (nombres.Count == 0)
        {
            logger.LogWarning("Lista de nombres vacía");
            return new List<string>();
        }
        
        logger.LogInformation("Iniciando orquestación para {Count} nombres", nombres.Count);
        
        // Fan-out: lanzar todas las activities en paralelo
        var tareas = new List<Task<string>>();
        foreach (var nombre in nombres)
        {
            var tarea = context.CallActivityAsync<string>(
                nameof(SaludarActivity.Saludar),
                nombre);
            tareas.Add(tarea);
        }
        
        // Fan-in: esperar a que TODAS terminen
        var saludos = await Task.WhenAll(tareas);
        
        logger.LogInformation("Todas las activities completadas. Total: {Count}", saludos.Length);
        
        return saludos.ToList();
    }
}
EOF
```

**Conceptos clave del Orchestrator:**

```
[OrchestrationTrigger]:
- Recibe el TaskOrchestrationContext
- Es el "cerebro" de la orquestación

context.GetInput<T>():
- Lee el input que pasó el client al iniciar el orchestrator

context.CallActivityAsync<T>():
- Llama a una activity por nombre
- Devuelve un Task<T> que podemos await

Task.WhenAll(tareas):
- Espera a que TODAS las tareas en paralelo terminen
- Si una falla, lanza excepción que el orchestrator puede capturar
```

**Reglas críticas del Orchestrator:**

```
❌ NUNCA hagáis I/O directo (HttpClient, File.Read, DB calls)
   → eso lo hacen las activities

❌ NUNCA uséis DateTime.Now, Random, Guid.NewGuid()
   → no son deterministas, romperán el replay
   → si necesitáis: usad context.CurrentUtcDateTime, context.NewGuid()

❌ NUNCA uséis Thread.Sleep o Task.Delay
   → bloquean el worker, malgastáis recursos
   → si necesitáis esperar: context.CreateTimer()

✅ El orchestrator se EJECUTA MUCHAS VECES (replay):
   - Cada vez que una activity termina, el orchestrator se "rebobina"
   - Se ejecuta desde el principio replay-ando lo ya hecho
   - Por eso debe ser determinista
```

## Slide 7 — Paso 4: El Client (HTTP starter)

Última pieza: el endpoint HTTP que arranca el orchestrator y devuelve URLs de inspección:

```bash
cat > SaludosClient.cs << 'EOF'
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Mvc;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Azure.Functions.Worker.Http;
using Microsoft.DurableTask;
using Microsoft.DurableTask.Client;
using Microsoft.Extensions.Logging;
using System.Text.Json;

namespace MiDurableFunction;

public class SaludosClient
{
    [Function(nameof(IniciarSaludos))]
    public async Task<HttpResponseData> IniciarSaludos(
        [HttpTrigger(AuthorizationLevel.Anonymous, "post", Route = "saludos")]
        HttpRequestData req,
        [DurableClient] DurableTaskClient client,
        FunctionContext executionContext)
    {
        var logger = executionContext.GetLogger(nameof(SaludosClient));
        
        // Leer la lista de nombres del body
        var body = await new StreamReader(req.Body).ReadToEndAsync();
        var nombres = JsonSerializer.Deserialize<List<string>>(body)
            ?? new List<string>();
        
        if (nombres.Count == 0)
        {
            var errorResponse = req.CreateResponse(System.Net.HttpStatusCode.BadRequest);
            await errorResponse.WriteAsJsonAsync(new { error = "Lista de nombres vacía" });
            return errorResponse;
        }
        
        // Iniciar el orchestrator (devuelve un instanceId único)
        string instanceId = await client.ScheduleNewOrchestrationInstanceAsync(
            nameof(SaludosOrchestrator.SaludarATodos),
            nombres);
        
        logger.LogInformation(
            "Orchestrator iniciado: {InstanceId} con {Count} nombres",
            instanceId, nombres.Count);
        
        // Devolver URLs de inspección (status, terminate, etc.)
        return await client.CreateCheckStatusResponseAsync(req, instanceId);
    }
}
EOF
```

**Lo que hace el Client:**

```
1. Recibe HTTP POST con lista de nombres
2. Llama a ScheduleNewOrchestrationInstanceAsync()
   → asigna un instanceId único
   → encola el orchestrator para ejecutar
   → devuelve INMEDIATAMENTE (no espera al resultado)
3. Genera URLs de management:
   - statusQueryGetUri: para ver el estado
   - sendEventPostUri: para enviar eventos al orchestrator
   - terminatePostUri: para abortar el orchestrator
   - purgeHistoryDeleteUri: para limpiar el historial

El orchestrator se ejecuta en BACKGROUND.
El cliente HTTP se libera inmediatamente.
```


Esperado: `Build succeeded`. Si hay errores, revisad que todos los `using` están y que el namespace coincide en los 3 archivos.

## Slide 10 — Estados posibles del Orchestrator

Un orchestrator pasa por varios estados durante su ciclo de vida:

```
┌──────────────┐
│   Pending    │ ← creado pero no iniciado todavía
└──────┬───────┘
       │
       ▼
┌──────────────┐
│   Running    │ ← ejecutándose (esperando activities)
└──────┬───────┘
       │
       ├──→ ┌──────────────┐
       │    │  Completed   │ ← terminó OK con output
       │    └──────────────┘
       │
       ├──→ ┌──────────────┐
       │    │   Failed     │ ← excepción no capturada
       │    └──────────────┘
       │
       ├──→ ┌──────────────┐
       │    │  Terminated  │ ← alguien llamó a terminate URL
       │    └──────────────┘
       │
       └──→ ┌──────────────┐
            │   Canceled   │ ← raro, cancelación cooperativa
            └──────────────┘
```

**Workflows comunes para cada estado:**

```
Running:
- Polling cada 5-10 seg para ver si terminó
- Mostrar barra de progreso si tiene customStatus

Completed:
- Leer output y mostrar al usuario
- Limpiar instancia con purgeHistoryDeleteUri

Failed:
- Logear error
- Posiblemente reintentar con nuevo orchestrator
- Notificar a soporte

Terminated:
- Saber que alguien lo paró manualmente
- Generalmente operación administrativa
```

**Operaciones admin sobre el orchestrator:**

```bash
# Terminar (kill) un orchestrator en ejecución
TERMINATE_URL="<terminatePostUri>"
curl -X POST "$TERMINATE_URL" -d '"motivo: testing"' -H "Content-Type: application/json"

# Borrar el historial (después de Completed)
PURGE_URL="<purgeHistoryDeleteUri>"
curl -X DELETE "$PURGE_URL"
```

**¿Qué pasa si paráis Functions con el orchestrator en Running?**

```
1. Estado se persiste en Storage (Azurite localmente)
2. Al rearrancar Functions con `func start`...
3. El orchestrator REASUME desde donde estaba
4. Activities ya completadas no se re-ejecutan
5. → Esa es la magia de "durable" 
```

## Slide 11 — Variante: orchestrator secuencial

Hasta ahora hicimos paralelo. ¿Qué pasa si necesitamos ejecutar activities **una tras otra** porque la siguiente depende de la anterior?

**Modificar el orchestrator (variante secuencial):**

```csharp
[Function(nameof(SaludarSecuencial))]
public async Task<List<string>> SaludarSecuencial(
    [OrchestrationTrigger] TaskOrchestrationContext context)
{
    var nombres = context.GetInput<List<string>>() ?? new List<string>();
    var saludos = new List<string>();
    
    foreach (var nombre in nombres)
    {
        // Cada activity se llama Y SE ESPERA antes de la siguiente
        var saludo = await context.CallActivityAsync<string>(
            nameof(SaludarActivity.Saludar),
            nombre);
        saludos.Add(saludo);
    }
    
    return saludos;
}
```

**Comparativa de tiempos:**

```
3 activities, cada una tarda 2 segundos:

Paralelo (Task.WhenAll):
  ~3 segundos total
  ████████████████ Pedro
  ████████████████ Ana    (todas a la vez)
  ████████████████ Luis

Secuencial (foreach + await):
  ~6 segundos total
  ████████████████ Pedro
                  ████████████████ Ana
                                  ████████████████ Luis
```

**¿Cuándo cada uno?**

```
PARALELO cuando:
✅ Activities son independientes entre sí
✅ Queréis máximo throughput
✅ El orden de finalización no importa

SECUENCIAL cuando:
✅ Cada activity depende del resultado de la anterior
✅ Necesitáis un orden estricto
✅ Hay coordinación con sistemas externos rate-limited

MIXTO cuando:
✅ Algunas paralelas y otras secuenciales
✅ Por ejemplo: 3 lookups en paralelo → 1 procesamiento que los combina
```

**Patrón mixto típico:**

```csharp
// 1. Fan-out: 3 lookups en paralelo
var datos = await Task.WhenAll(
    context.CallActivityAsync<Datos>("LookupA", input),
    context.CallActivityAsync<Datos>("LookupB", input),
    context.CallActivityAsync<Datos>("LookupC", input));

// 2. Procesamiento secuencial usando los 3 resultados
var combinado = await context.CallActivityAsync<Resultado>("Combinar", datos);

// 3. Notificar (fire and forget no es posible en orchestrator)
await context.CallActivityAsync("Notificar", combinado);
```

## Slide 12 — Paso 7: Crear recursos en Azure

```bash
RG_NAME="rg-curso-durable-<tu-nombre>"
LOCATION="westeurope"
STORAGE_NAME="stdurable<tu-nombre>$(date +%s | tail -c 5)"
APP_NAME="func-durable-<tu-nombre>-$(date +%s | tail -c 5)"

# Resource Group
az group create --name $RG_NAME --location $LOCATION

# Storage Account
az storage account create \
  --name $STORAGE_NAME \
  --resource-group $RG_NAME \
  --location $LOCATION \
  --sku Standard_LRS

# Function App (.NET 8 isolated, Linux Consumption)
az functionapp create \
  --name $APP_NAME \
  --resource-group $RG_NAME \
  --consumption-plan-location $LOCATION \
  --runtime dotnet-isolated \
  --runtime-version 8 \
  --functions-version 4 \
  --storage-account $STORAGE_NAME \
  --os-type Linux

echo "URL: https://$APP_NAME.azurewebsites.net"
```

**Tiempo estimado:** 2-3 minutos.

**Para Durable Functions, el Storage Account NO ES OPCIONAL**. Lo usa internamente para:

```
- Tablas que persisten estado del orchestrator
- Queues que coordinan entre orchestrator y activities
- Tracking de history para replay
- Distributed locking entre instancias
```


## Slide 14 — Smoke tests automatizados

Script bash que valida el flujo end-to-end con polling automático del estado:

```bash
cat > smoke-tests.sh << 'EOF'
#!/bin/bash
set -e

BASE="${1:?Pasa la URL base como primer argumento}"

echo "🔍 Smoke tests sobre $BASE"

# Test 1: Iniciar orchestrator
echo -n "  [1/3] POST /api/saludos... "
RESP=$(curl -s -X POST "$BASE/api/saludos" \
  -H "Content-Type: application/json" \
  -d '["A","B","C"]')

INSTANCE_ID=$(echo $RESP | jq -r '.id')
STATUS_URL=$(echo $RESP | jq -r '.statusQueryGetUri')

if [ -n "$INSTANCE_ID" ] && [ "$INSTANCE_ID" != "null" ]; then
  echo "✓ ($INSTANCE_ID)"
else
  echo "✗ - respuesta: $RESP"
  exit 1
fi

# Test 2: Esperar a que complete (polling con timeout 30s)
echo -n "  [2/3] Esperar completion... "
ATTEMPTS=0
MAX_ATTEMPTS=15

while [ $ATTEMPTS -lt $MAX_ATTEMPTS ]; do
  STATUS=$(curl -s "$STATUS_URL" | jq -r '.runtimeStatus')
  
  if [ "$STATUS" = "Completed" ]; then
    echo "✓ ($ATTEMPTS reintentos)"
    break
  elif [ "$STATUS" = "Failed" ] || [ "$STATUS" = "Terminated" ]; then
    echo "✗ ($STATUS)"
    exit 1
  fi
  
  ATTEMPTS=$((ATTEMPTS + 1))
  sleep 2
done

if [ "$STATUS" != "Completed" ]; then
  echo "✗ (timeout, último estado: $STATUS)"
  exit 1
fi

# Test 3: Verificar output
```

## Slide 15 — Comparativa: Durable Functions vs Functions normales

¿Cuándo usar Durable Functions y cuándo NO?

| Aspecto | Functions normales | **Durable Functions** |
|---|---|---|
| **State** | Stateless (perdidos entre invocations) | **Stateful (persistencia automática)** |
| **Long-running** | Max 5-10 min en Consumption | **Sin límite (días, semanas)** |
| **Coordinación** | Manual (entre N functions) | **Automática (orchestrator)** |
| **Replay tras crash** | Manual | **Automático** |
| **Patterns soportados** | Básicos | **Fan-out/in, async APIs, monitoring, human interaction** |
| **Coste** | Por ejecución | **Por ejecución + Storage extra** |
| **Complejidad** | Baja | **Media-alta** |

**Cuándo SÍ Durable Functions:**

```
✅ Workflows de larga duración (>10 min)
✅ Coordinar muchas activities (3+)
✅ Necesitáis persistencia automática del estado
✅ Patterns: fan-out/fan-in, async APIs, monitoring polling
✅ Workflows con human interaction (esperar aprobación)
✅ Necesitáis history y poder hacer replay
```

**Cuándo NO Durable Functions:**

```
❌ Una operación HTTP simple (tirad HTTP Trigger normal)
❌ Reaccionar a un evento (Queue Trigger / Service Bus Trigger)
❌ Tarea programada simple (Timer Trigger)
❌ Si tu equipo no domina las reglas de orchestrator (replay safety)
❌ Si necesitáis latencia <1 segundo end-to-end
```

**Patrones típicos de Durable Functions:**

```
1. Function Chaining
   activity1 → activity2 → activity3 (cada uno espera al anterior)

2. Fan-out / Fan-in (lo que hicimos)
   Lanzar N activities en paralelo, esperar a todas

3. Async HTTP APIs
   Cliente llama API, recibe URL para consultar estado, polling

4. Monitoring
   Orchestrator que se "duerme" y despierta periódicamente

5. Human Interaction
   Workflow espera evento externo (aprobación de un usuario)

6. Aggregator
   Suma N eventos antes de proceder
```

## Slide 16 — Reglas críticas: orchestrator determinista

Esto es **crítico** entenderlo. Sin esto, vuestros orchestrators serán impredecibles:

**¿Por qué el orchestrator se ejecuta múltiples veces?**

```
1. Orchestrator empieza, llama Activity A
   → se DUERME esperando resultado

2. Activity A termina (ej. 2 segundos después)
   → Storage notifica al orchestrator
   → Orchestrator se "despierta"
   → Pero Functions descarta el estado en memoria
   → ¡Se ejecuta el orchestrator DESDE EL PRINCIPIO!

3. La 2ª ejecución pasa por Activity A
   → Pero como ya hay resultado en history,
     NO se vuelve a ejecutar Activity A
   → Devuelve el resultado que ya está guardado

4. Sigue con Activity B
   → la llama por primera vez, se duerme

5. Activity B termina
   → Orchestrator se ejecuta DESDE EL PRINCIPIO otra vez
   → Replay de A y B (sin re-ejecutar)
   → Llega a Activity C, etc.

→ Por eso el orchestrator DEBE ser determinista
```

**Reglas que NUNCA podéis romper en orchestrator:**

```csharp
// ❌ MAL: DateTime.Now cambia entre replays
var ahora = DateTime.Now;

// ✅ BIEN: usar context (determinista, mismo valor en todos los replays)
var ahora = context.CurrentUtcDateTime;

// ❌ MAL: Random distinto cada replay
var random = new Random().Next(100);

// ✅ BIEN: Guid determinista
var id = context.NewGuid();

// ❌ MAL: HttpClient directo
var data = await httpClient.GetAsync("https://api.com/data");

// ✅ BIEN: hacerlo en activity
var data = await context.CallActivityAsync<Data>("LookupData", input);

// ❌ MAL: Thread.Sleep, Task.Delay
await Task.Delay(TimeSpan.FromMinutes(5));

// ✅ BIEN: timer determinista
var dueTime = context.CurrentUtcDateTime.AddMinutes(5);
await context.CreateTimer(dueTime, CancellationToken.None);

// ❌ MAL: try/catch genérico
try { /* ... */ } catch (Exception ex) { /* ... */ }

// ✅ BIEN: catch específico de OrchestrationException
try { /* ... */ } catch (TaskFailedException ex) { /* ... */ }
```

**Logger seguro para replay:**

```csharp
// El orchestrator se ejecuta múltiples veces
// Si usáis ILogger normal, veréis logs duplicados

// ❌ MAL: log normal (se duplica en replay)
logger.LogInformation("Iniciando");

// ✅ BIEN: replay-safe logger
ILogger logger = context.CreateReplaySafeLogger("MiOrchestrator");
logger.LogInformation("Iniciando");
// → solo se loguea en la PRIMERA ejecución, no en los replays
```

## Slide 18 — Troubleshooting Durable Functions

Los 5 errores más típicos y cómo resolverlos:

**1. "Function host is not running" tras deploy**

```
Causa: paquete DurableTask faltante o versión incompatible
Diagnóstico:
  az webapp log tail --name $APP_NAME -g $RG_NAME

Verificar versiones:
  cat *.csproj | grep DurableTask
  
Esperado:
  <PackageReference Include="Microsoft.Azure.Functions.Worker.Extensions.DurableTask" Version="1.x.x" />

Fix: actualizar a la versión más reciente
  dotnet add package Microsoft.Azure.Functions.Worker.Extensions.DurableTask
```

**2. "Unable to start the orchestrator: instance not found"**

```
Causa: el cliente intentó ScheduleNewOrchestrationInstanceAsync pero falló
Verificar:
- El nombre del orchestrator existe (Function name correcto)
- El input es serializable (no objetos complicados)
- El AzureWebJobsStorage está configurado

Fix:
  az functionapp config appsettings list --name $APP_NAME -g $RG_NAME \
    --query "[?name=='AzureWebJobsStorage'].value"
```

**3. "Orchestrator queda en Running indefinidamente"**

```
Causa común: una activity está fallando con excepción no capturada
Diagnóstico:
- Ver log de la activity:
  az webapp log tail --name $APP_NAME -g $RG_NAME

- Ver historial del orchestrator (lo cuenta todo):
  curl "$STATUS_URL?showHistory=true" | jq

Fix:
- Si la activity falla, capturad TaskFailedException en el orchestrator
- O reescribid la activity para que sea idempotente y reintentable
```

**4. "Non-deterministic exception in orchestrator"**

```
Causa: usasteis algo no determinista (DateTime.Now, Random, await externo)
Síntoma: orchestrator se "atasca" o falla de forma errática

Diagnóstico:
- Revisad el código del orchestrator
- Buscad: DateTime.Now, Random, Guid.NewGuid(), HttpClient, Task.Delay

Fix:
- Mover I/O a activities
- Usar context.CurrentUtcDateTime, context.NewGuid()
- Usar context.CreateTimer() en lugar de Task.Delay
```

**5. "Tests locales funcionan, en Azure no"**

```
Causa común: Storage local (Azurite) vs Storage Azure tienen versiones distintas
Síntoma: orchestrator se ejecuta en local pero no en Azure

Verificar versión de Azurite:
  azurite --version

Verificar conection string en Azure:
  az functionapp config appsettings list --name $APP_NAME -g $RG_NAME \
    --query "[?contains(name, 'AzureWebJobsStorage')]" -o table

Fix:
- Actualizar Azurite a la última versión
- O probar en Azure directo (saltarse local si no es crítico)
```

**Comando útil: ver historial completo del orchestrator**

```bash
# El historial muestra TODOS los eventos: starts, activity calls, results
curl -s "$STATUS_URL?showHistory=true" | jq '.historyEvents[] | {EventType, Timestamp, Name, FunctionName}'
```

Esto es **oro** para debugging. Muestra exactamente qué se ejecutó, en qué orden, y con qué resultado.

## Slide 20 — Retos opcionales

**Reto 1 — Variante secuencial**

Reescribid el orchestrator usando el patrón secuencial (foreach + await). Comparad tiempos:

```bash
# Tiempo paralelo: ~3 seg
# Tiempo secuencial: ~6 seg
```

**Reto 2 — Manejo de errores**

Modificad la activity para que falle si el nombre tiene 1 sola letra:

```csharp
if (nombre.Length < 2)
    throw new ArgumentException($"Nombre demasiado corto: {nombre}");
```

Y manejad el error en el orchestrator:

```csharp
try
{
    var saludo = await context.CallActivityAsync<string>(...);
}
catch (TaskFailedException ex)
{
    // Log y continuar con los demás
    logger.LogError("Falló para {Nombre}: {Msg}", nombre, ex.Message);
}
```

**Reto 3 — Custom status**

Añadid `customStatus` que muestre el progreso:

```csharp
var totalSaludos = 0;
foreach (var nombre in nombres)
{
    var saludo = await context.CallActivityAsync<string>(...);
    totalSaludos++;
    
    // Actualizar status
    context.SetCustomStatus(new
    {
        progreso = $"{totalSaludos}/{nombres.Count}",
        ultimoSaludo = saludo
    });
}
```

Consultad `statusQueryGetUri` durante la ejecución y veréis `customStatus` actualizándose.

**Reto 4 — Monitor pattern**

Crear un orchestrator que se ejecute cada minuto durante 10 minutos, llamando a una activity en cada iteración. Esto introduce `context.CreateTimer()`.
